摘要

大语言模型（LLM）编码智能体通过实验来开发软件，这为设计支撑其自身运行的服务系统提供了机会。有效的服务需要在会话依赖、延迟约束和正确性要求下协调实现决策与运行决策。我们提出了 ServerBench，一个用于评估智能体设计完整、专用 LLM 服务系统的基准测试。智能体围绕一个共同目标进行实验——"美元每美元"（dollars per dollar）：每美元 GPU 成本所产生的延迟达标的 token 价值。有状态回放保留会话依赖关系，独立验证则检查提交的系统。在 11 个编码智能体模型和三种部署配置中，Claude Sonnet 5.5 在 Gemma E4B 上达到 2.97 美元每美元，是 vLLM 参考基准的 4.87 倍；33 次运行中有 22 次产生通过验证的系统，13 次超过最强基线。我们的分析得出三项发现：高价值设计将容量改进与负载选择相协调；智能体通过与工作负载相关的实验来解读性能反馈；可靠交付需要对优化所引入的执行路径进行验证。总体而言，ServerBench 支持系统性地研究智能体如何将服务目标和反馈转化为针对给定任务规范的有效、经过验证的服务系统。

1 引言

大语言模型（LLM）编码智能体建立在代码生成能力之上（Zheng et al., 2025; Zhou et al., 2026a），利用工具和执行反馈来承担软件开发和专业工作流程（Yang et al., 2024; Xiao et al., 2025; Chan et al., 2025; Sun et al., 2026）。这些工作流程依赖于 LLM 服务系统，后者负责运行模型并处理请求（Kwon et al., 2023; Zheng et al., 2024; Zhou et al., 2026b）。这为编码智能体设计这些系统创造了机会。服务提供商需要正确的模型执行和及时的响应。因此我们提出问题：编码智能体如何在满足给定部署和服务约束的同时设计 LLM 服务系统？

图 2：智能体设计服务器，并针对给定的模型、GPU 分配和工作负载选择其同时服务的会话数量。回放保留了请求之间的共享上下文和依赖关系；最终检查评估模型正确性和完整的工作负载执行。

尽管智能体驱动的系统优化进展迅速，现有基准测试仅在预设测试条件下评估单个内核、代码补丁或服务器（Ouyang et al., 2025; Nangia et al., 2026; Williams et al., 2026; Yeon et al., 2026; Xu et al., 2026），在评估智能体如何设计完整服务系统方面留下了三个空白：

  • 过度简化的工作负载。 先前基准测试发出独立请求或固定的预填充、解码和吞吐量场景（Yeon et al., 2026; Xu et al., 2026）。在请求长度均匀和批次固定的情况下，静态批次几乎与生产引擎一样好，因此真实部署所依赖的技术（如连续批处理和分页注意力）（Yu et al., 2022; Kwon et al., 2023）带来的收益甚微。而编码智能体等真实应用混合了短请求和长请求，在多轮交互中扩展共享上下文，并分叉出并行子智能体，其中前缀复用、内存管理和预填充-解码干扰决定了性能（Zheng et al., 2024; Srivatsa et al., 2025; Agrawal et al., 2024; Zhong et al., 2024）。

  • 仅关注加速比的目标。 现有基准测试相对于基线对加速比或吞吐量进行评分（Ouyang et al., 2025; Yeon et al., 2026; Xu et al., 2026）。此类目标忽略了延迟要求和 GPU 成本，并固定了供给负载，而服务提供商必须决定服务多少工作负载，同时将首 token 时间（TTFT）和每输出 token 时间（TPOT）保持在目标范围内。

  • 仅关注正确性的验证。 验证通常根据参考实现或测试套件检查输出（Ouyang et al., 2025; Williams et al., 2026; Xu et al., 2026）。服务系统还必须满足部署工作负载上的尾延迟目标，并完整执行该工作负载，包括完整的提示、规定的输出长度和一致的流式传输。投机解码、状态复用和自定义调度等优化引入了短时或孤立测试很少触及的执行路径。

我们提出了 ServerBench，在该基准中，编码智能体为给定的模型、GPU 分配和工作负载构建完整的 LLM 服务系统，并决定其服务的工作负载量（图 2）。从一个最小的 Transformers 服务器开始，智能体在固定的开发预算内规划实验并修改其系统。ServerBench 通过三项设计弥补了这三个空白。

1. 工作负载：真实的编码智能体轨迹。 ServerBench 回放录制的编码智能体会话（SemiAnalysis, 2026a），保留其请求长度、多轮结构、共享前缀、并行子智能体分支和轮间延迟。请求等待它们所依赖的响应，因此服务延迟决定了在测量窗口内完成的工作量（第 3.2 节）。

2. 目标：美元每美元。 我们以固定的 API 费率为每个已完成请求的输入和输出 token 定价，仅统计同时满足 TTFT 和 TPOT 目标的请求，并除以测量窗口的 GPU 成本（第 3.1 节）。例如，3.65 美元的合格 token 价值除以 0.83 美元的 GPU 成本得分为 4.40。该目标将容量改进与匹配的负载选择一起奖励：只有当请求仍满足其延迟目标时，服务更多工作负载才会提高总价值。

3. 验证：超越正确性。 延迟目标是 SGLang 参考系统在其模型特定配置下的 p90 TTFT 和 TPOT，在开发前冻结（第 3.1 节）。提交的系统在全新部署中重建，并在留出种子上回放。独立检查验证完整的提示、输出长度、流式一致性、对检查点的生成保真度以及留出问题的答案准确性；运行后审查检查代码和记录的操作是否存在禁止的捷径（第 3.4 节）。只有通过验证的系统才能获得分数。

我们在三种模型-硬件部署上评估了 11 个编码智能体模型。Claude Sonnet 5.5 在 Gemma E4B 上达到 2.97 美元每美元，是 vLLM 服务基线的 4.87 倍（第 4.2 节）。轨迹分析得出三项发现。

高价值设计协调容量与并发。 Sonnet 5.5 在提高并发之前先改进其服务器，然后在额外会话恶化 TPOT 时限制负载（第 4.3 节）。

在工作负载上下文中解读反馈以指导优化。 一次随机文本探测导致一个智能体拒绝某项优化；工作负载回复揭示了其收益并引导另一个智能体采用它（第 4.4 节）。

验证必须匹配部署的工作负载。 智能体的短时或孤立检查可能遗漏长上下文停滞和跨请求崩溃；已知故障可能在提交系统的编辑之后持续存在或复发（第 4.5 节）。

我们的贡献是：

  • ServerBench，一个用于设计完整 LLM 服务系统以最大化每 GPU 美元服务价值的基准测试（第 3.1 节）。智能体设计服务器并设置并发应用会话的数量。

  • 一个评估协议，回放具有共享上下文和依赖请求的编码会话，支持智能体设计的实验，并独立验证最终系统（第 3.2 至 3.4 节）。

  • 一项跨三种部署的 11 个编码智能体模型的研究，使用受控比较和轨迹分析来解释系统设计、实验判断和验证中的成功与失败（第 4.2 至 4.6 节）。

2 相关工作

2.1 推理系统优化

Orca 和 vLLM 改进了请求调度和内存管理（Yu et al., 2022; Kwon et al., 2023）。SGLang 和 Preble 利用前缀复用（Zheng et al., 2024; Srivatsa et al., 2025），而 Sarathi-Serve 和 DistServe 通过分块预填充和预填充-解码分离来缓解预填充-解码干扰（Agrawal et al., 2024; Zhong et al., 2024）。AlphaEvolve 和 AI 驱动的系统研究（ADRS）使用评估器反馈来生成和改进算法与系统代码（Novikov et al., 2025; Cheng et al., 2025）。Vortex 使智能体能够在可编程服务系统中生成和改进稀疏注意力算法（Chen et al., 2026）。ServerBench 研究智能体是否能在固定部署条件下将此类优化集成到系统中。

2.2 推理性能基准测试

MLPerf Inference 标准化了工作负载、质量目标和部署场景（Reddi et al., 2020）。面向智能体的基准测试评估正确性和性能：KernelBench 针对 PyTorch 参考实现测试所生成 GPU 内核的正确性和加速比（Ouyang et al., 2025），ISO-Bench 将 vLLM 和 SGLang 优化补丁与专家实现进行比较（Nangia et al., 2026），Φ-Bench 涵盖从内核补全到端到端基础设施优化（Ding et al., 2026）。SWE-Serve 测试 SGLang 中的生产功能（Williams et al., 2026），而 InferenceBench 在预填充、解码、并发吞吐量和平衡场景上使用相对基线的加速比评估完整服务器（Yeon et al., 2026）。ServerBench 将这一评估路线扩展到响应依赖的有状态会话和延迟合格的收入-成本目标，将实现与运行选择同完整系统所提供的服务联系起来。

3 ServerBench

ServerBench 通过服务目标、有状态工作负载回放、迭代实验和最终验证来评估智能体设计。任务配置见第 6 节和第 9 节。

3.1 任务与服务目标

每个任务固定一个模型检查点、GPU 分配、编码会话工作负载和服务要求。从一个最小的 Transformers 服务器 S₀ 开始，智能体有时间预算 B 来开发服务系统。其提交包括一个实现 S_B 和会话并发 c_B。智能体可以在规定的检查点、精度和推理语义下重新设计执行、批处理、内存管理、调度和状态复用（Yu et al., 2022; Kwon et al., 2023; Zheng et al., 2024）。智能体优先考虑满足服务目标的更改。

美元每美元。 目标"美元每美元"衡量同时满足两个延迟目标的已完成 token 价值除以每美元 GPU 成本。对于请求 i，客户端测量的输入和输出计数 x_i、y_i 给出 v_i = (p_in·x_i + p_out·y_i)/10⁶，价格以每百万 token 美元计。当其有限的 TTFT 和 TPOT 满足目标 τ_first、τ_token 时，令 q_i = 1，否则为零。一个经过验证的系统在 d 个 GPU 上预热后测量 W 秒，以每 GPU 小时 r 美元定价，得到：

D(S_B, c_B) = Σ_{i∈ℛ} q_i·v_i / [d·r·(W/3600)]　(1)

其中 ℛ 包含已完成的请求。定义总价值 G = Σ_{i∈ℛ} v_i / [d·r·(W/3600)] 和价值加权合格份额 f = D/G（当 G > 0 时）；因此 D = G·f。输入价值包括缓存前缀，每个逻辑请求按全价计算一次。例如，3.65 美元的合格价值除以 0.83 美元的 GPU 成本得到 4.40。

延迟校准。 在开发之前，我们使用 SGLang 的模型特定 cookbook 配置选择参考工作点（Zheng et al., 2024）。在参考工作点，重复回放产生种子 j 的 p90 TTFT a_j 和 TPOT b_j。我们设置 τ_first = max_j a_j 和 τ_token = max_j b_j，然后在智能体开发之前冻结这些请求级目标。取最大值为观察到的运行间变化提供了余量。智能体选择其提交服务器所使用的并发。

3.2 有状态工作负载与闭环回放

编码会话包含依赖轮次、共享上下文和并行子智能体分支。使用 AgentX 工具（SemiAnalysis, 2026a），我们使用录制的轮间延迟回放响应依赖的轮次和并行分支，并压缩较长的全局空闲期。

供给并发限制活动的顶层会话数量，其分支可以发出额外请求。因此响应时间影响会话进度和测量窗口内完成的工作。

隐私保护的重建替换提示和工具内容，同时保留请求长度、共享前缀和会话拓扑。任务固定重建的提示和输出长度。共享上下文支持计算复用（Zheng et al., 2024; Srivatsa et al., 2025），而保留的状态和活动请求竞争内存。智能体负责将这些工作负载特征转化为优化，同时保持模型行为并完整执行工作负载。

增长的上下文支持复用，而新会话增加与解码竞争的预填充工作（Agrawal et al., 2024; Zhong et al., 2024）。会话进度因此结合了提示处理、生成和保留状态。

3.3 智能体环境与开发循环

图 3：有状态回放将会话进度与智能体的设计实验联系起来。最终评估验证发布的系统，并针对校准的延迟目标测量请求价值。

智能体在禁用互联网的 Harbor 沙箱中工作，具有容器或 Modal 后端（Merrill et al., 2026）。他们收到一个最小服务器、只读模型权重、参考配置、测量工具和已发布的性能流程。任务指令要求模型保真度和完整的工作负载执行，并禁止操纵评估。独立正确性测试的细节被保留，可信的评估组件保持在可编辑的服务实现之外。

工具报告延迟、吞吐量和请求价值。智能体组织自己的实验、诊断瓶颈并修改实现（Yang et al., 2024）。他们为回放、诊断和开发分配时间。发布操作将实现和并发与性能测试分开固定；当分配的开发时间到期时，最后发布的版本成为提交。

智能体选择实验规模：诊断测试隔离疑似瓶颈，而完整回放测试交互请求。他们决定哪些观察值得进一步测试、保留哪些更改以及何时发布。版本化提交将这些决策与开发后评估的实现联系起来。

3.4 系统验证

开发之后，ServerBench 在全新部署中重建提交的系统，并回放使用与开发不相交的种子采样的会话。独立测试和运行后审查检查生成的系统（图 3）。

工作负载和输出验证。 回放检查涵盖完整的提示、输出长度、流式一致性和会话进度。定时回放禁用 EOS 停止以生成规定的输出长度；单独的 EOS 探针测试自然停止。参考评分的续写检查针对检查点的生成。留出问题将答案正确性与同一模型的普通实现进行比较，使用任务的准确性容差来筛选实质性回归和绕过模型计算的捷径。

全新部署还测试开发状态之外的行为。

运行后审查。 审查智能体和人工检查审查提交的代码和记录的操作，以确认检查点保真度、推理语义和工作负载执行。审查可以识别行为测试遗漏的禁止捷径，并在检查确认符合任务要求时推翻自动判定的失败。这些检查决定得分资格（公式 1）。

4 评估

4.1 实验设置

我们评估了 11 个编码智能体模型（表 1）：Claude（Anthropic, 2026b; Anthropic, 2026c; Anthropic, 2026d）、GPT（OpenAI, 2026b）、Kimi（Kimi Team, 2026）、GLM（Z.ai, 2026）、DeepSeek（DeepSeek-AI, 2026）、MiMo（Xiaomi MiMo, 2026）和 Qwen（Qwen Team, 2026a）模型。全部在 Qwen3.5 9B（2×L40）、Gemma-4-E4B-it（Gemma E4B；1×L40）和 Qwen3.8 27B INT4（2×L40）上使用最大推理努力。在 Harbor 中，GPT 模型使用 Codex（OpenAI, 2026a），其他模型使用 Claude Code（Anthropic, 2026a）。每个智能体-部署对允许一次 8 小时的开发运行和 1,800 秒的最终回放，对于明显异常的失败结果最多重新运行一次。我们报告每对在表 1 的 33 个条目中最强的已验证最终提交；开发分析侧重于具有服务器执行记录的 30 次运行。

基线是 SGLang v0.5.19 和 vLLM v0.28.0（Zheng et al., 2024; Kwon et al., 2023）。SGLang 使用每个模型的 cookbook 配置；参考结果在固定并发下对回放种子取平均。受控比较在共同种子上回放冻结的实现和中间版本。

4.3 高价值设计协调容量与并发

图 5：录制的并发路径和最终结果。颜色标记相对于最强基线的价值；标签计数运行次数。面板下方的点标记首次负载声明。

在固定的 GPU 成本下，额外的会话可以增加 token 价值，但通过排队和争用提高 TTFT 和 TPOT。智能体必须使负载与服务容量匹配。

图 5 将录制的并发模式与最终经济结果联系起来；提高并保持负载的运行更常超过最强参考。在达到至少两倍最强参考的运行中，17 个负载决策中有 7 个改善了后续测量的价值，而低于参考分数的已验证运行中为 23 个中的 2 个。

早期的端到端回放给智能体留出时间在调整负载的同时开发容量。前一组在 0.90 小时的中位数时间内达到可用回放，而后一组为 2.96 小时。第 10.4 节中的优化清单和受控比较将这些运行决策与执行、状态管理和调度的变化联系起来。更高价值的系统倾向于组合更多的服务优化，包括投机解码、主机内存状态存储和延迟感知调度。跨轮复用在所有审计系统中都很常见。

受控比较说明了这一区别。在 16 个会话下，Opus 5.5 的 v1→v2 Qwen 重新设计在匹配种子上将价值提高了 1.32–1.88 倍。对于冻结的 Gemma 系统，Sonnet 5.5 将价值从两个会话的 1.30 提高到 32 个会话的 2.97。Sonnet 5.5 在修改引擎时保持四个 Gemma 会话，然后随着进一步的实现更改增加负载。该轨迹说明了在增加负载之前的容量开发。

在 Qwen 上，Opus 5 反而在完善实现时将并发从四降低到二再到一。Kimi 在识别出干扰解码的长预填充后同样将负载降低到一。负载减少缓解争用；容量改进支持更多同时进行的工作。

智能体以不同的方式估计经济工作点。Opus 5.5 使用工作负载模拟器指导 Qwen 负载测试，然后在 20 会话回放产生更多总价值但只有 64% 合格价值后保留 16 个会话。Sonnet 5.5 在 Gemma 上比较固定种子上的设置：36 个会话产生更多总价值但导致更多 TPOT 未达标，因此提交 32。这些决策在延迟目标内使供给负载与服务容量匹配。

4.4 使用反馈指导优化

智能体使用性能测量和诊断测试来保留、修改或放弃更改。有用的反馈需要在相关的工作负载条件下测试更改。昂贵的回放和种子变化使诊断测试和工作负载分析在开发预算内必不可少。

图 6 将保留的设计决策与支持它们的测试联系起来。在达到至少两倍最强参考的运行中，49% 的保留决策遵循工作负载相关测试的改进，而失败运行中为 25%；没有此类测试的决策分别占 13% 和 40%。在其他已验证组中，39% 仍未确认。这些结果突出了决定保留哪些更改时进行测试和跟进的重要性。

图 6：保留的更改在 ≥2× 组中更常显示工作负载相关收益；代表性轨迹显示其跟进。分组使用相对于最强基线的最终价值。

在 Gemma 上，实验判断改变了智能体是否追求提示查找投机。Opus 5 接受来自合成随机文本探测的零结果并省略该优化。Opus 5.5 使用回放中的 60 个回复调查其初始零结果，修复其模拟器，并在采用投机之前测量到每步 2.09–2.34 个接受的 token。在固定的假设草稿成本下，修正的、长度匹配的探测从合成文本中选择的草稿比从工作负载回复中选择的更小（第 11 节）。

为了测试这种工作负载反馈对智能体决策的影响，我们从相同的检查点恢复 Opus 5，每个分支两小时，有或没有来自其自身回放回复的反馈。只有反馈分支重新采用投机；其服务器在两个新的共同种子上提供 1.13–1.31 倍的合格价值。工作负载反馈改善了智能体的设计决策及其提交服务器的价值。

有利的反馈也可能导致智能体保留在其他工作负载条件下表现不佳的配置。在 Qwen3.8 27B INT4 上的一次 Opus 5.5 运行中，智能体将并发从 10 提高到 16 并修改调度，观察到分数从 2.20 增加到 2.99。它认识到过载并承认更换种子使比较复杂化，但判断额外价值值得延迟损失。临近截止日期时，一项调度修复仍处于预热中，因此它返回到由一次完成的 900 秒回放支持的配置。在最终回放中，相同实现的合格份额从 76.0% 下降到 16.8%，分数下降到 0.48。

工作负载覆盖可以廉价地检查。我们对 128 个额外种子上的工作负载生成器进行 CPU 扫描仅需要 7.71 秒：开发抽取位于初始流可用性的第四百分位数附近，而最终抽取接近中位数。该智能体检查过语料库统计信息，却使用异常轻的初始分支条件来验证其最终配置（第 10.5 节）。

零结果和有利结果都需要检查测试实际测试的内容。检查测试输入和分析工作负载变化帮助智能体为昂贵的回放选择具有代表性和苛刻的条件，支持保留、修改或放弃设计的决策。

4.5 验证必须匹配部署的工作负载

验证检查受准入、调度和状态复用更改影响的请求边界和状态转换，包括在后续编辑之后。

图 7 显示提交时的稀疏覆盖：33 个条目中只有 5 个在负载或长上下文下对提交系统有自然停止的记录检查。

图 7： 提交实现上的工作负载相关检查。 相关症状在 11 次未通过运行中的 8 次中先于提交出现；标记区分响应和记录的提交时间。

准入策略需要检查哪些请求可以取得进展。在 Qwen3.5 9B 上，Qwen3.8-Max-0902 收紧准入以保护 TPOT，然后检查一个短提示和一个完成 11 个请求的回放。其提交的策略使一段允许的提示长度范围即使在其他请求完成后也无法进入执行。最终评估在此范围内的 315K token 输入上停滞。成功的短测试使新策略的提示长度边界未被检查。

状态复用需要检查跨请求的行为。在 Qwen3.8 27B INT4 上，Kimi 的回放暴露了前缀缓存异常和数值错误。该智能体修复数值路径并使用新引擎成功重新测试了孤立的长提示。对提交缓存的单独检查在第一次插入时成功，但在再次插入相同前缀时崩溃；该异常也在最终评估中复发。孤立测试遗漏了跨请求的前缀复用。

Opus 5.5 在 Gemma 上明确测试了其设计所涉及的运行条件。在添加抢占和缓存恢复以协调 TTFT 和 TPOT 后，它减少缓存容量以强制执行这些路径。压力测试暴露了未初始化缓存存储产生的无效输出。该缺陷先于抢占更改存在。该智能体修复缓存访问，检查填充 NaN 的未使用槽不能影响有效计算，并在将恢复的输出与孤立执行进行比较的同时重新运行强制抢占。最终系统保留了这些修复。减少池复制在修复回退时通过 0/3 测试，修复后通过 3/3。

可靠交付需要测试准入边界、共享状态和恢复，然后在修复后重新运行受影响的检查。

4.6 设计与工作负载消融

发现指导的更改改善了服务价值和正确性（第 11 节）。在最终 1,800 秒协议下的两个新共同种子上，Opus 5.5 的 Qwen v1→v6 重新设计在 c=16 下将合格价值提高了 1.35 倍和 1.15 倍。在 c=40 的冻结 Gemma 上，工作负载选择的草稿长度 7 比合成选择的长度 3 高 3.0% 和 3.9%。对于工作负载匹配的验证，Opus 5.5 的 Gemma 缓存修复通过了所有 3 个减少池压力测试（第 4.5 节）。

图 8 固定实现、并发和会话。跨部署，300 秒窗口平均为 1,800 秒分数的 1.42–1.70 倍，而 900 秒时为 1.04–1.21 倍。对于 Qwen 上的 Opus 5.5，将窗口从 300 秒扩展到 1,800 秒将跨种子变异系数从 0.37 降低到 0.19，产生更稳定的性能估计。

900 秒时更接近的一致性支持使用中间回放来指导开发。剩余的变化促使将这些测量与工作负载分析和有针对性的诊断相结合，以为更长的回放选择配置和工作负载条件。

5 结论

ServerBench 通过经济服务目标、有状态闭环回放和独立验证来评估智能体对完整、专用 LLM 服务系统的设计。三种部署的结果显示了实质性收益与不均衡的交付并存。轨迹分析和受控比较突出了三个优先事项：将容量改进与运行负载协调，围绕工作负载特征和变化设计实验，以及验证系统更改引入的执行路径。

局限性

我们的评估涵盖三种模型-硬件部署和一个编码轨迹源。开发和最终抽取共享一个语料库；重建的输入保留工作负载结构而不重现原始编码任务。闭环回放不同于开环生产需求，限制了对其他架构、加速器和到达模式的泛化。比较表征的是测量到的工件。相关性、源码检查和选定轨迹不能建立因果优化效果或设计成功率。需要重复的智能体运行和回放来将智能体可变性与工作负载可变性分开。版本说明记录报告的设计更改，可能遗漏实现细节。行为测试和代码审查的覆盖范围有限，校准依赖于参考引擎。固定价格的 token 价值衡量部署效率，不包括开发和其他运营成本，而非实现的利润。

伦理考虑

录制的编码会话可能包含敏感信息，智能体生成的服务代码可能引入不安全行为。ServerBench 在工作负载重建期间替换原始会话内容，并在具有受限网络访问的隔离环境中执行生成的代码。任何轨迹或智能体轨迹的发布都应审查敏感信息并遵守源许可证。运行后代码和操作审查支持识别未经授权的行为。受控的 GPU 分配和实验资源报告支持负责任的使用。这些控制减少了暴露，但不能确定任意生成的代码是安全的。
