URL 来源: https://www.anthropic.com/news/mozilla-firefox-security Markdown 内容： AI 模型现在可以独立识别复杂软件中的高危漏洞。正如我们最近所记录的，Claude 在经过充分测试的开源软件中发现了超过 500 个 [零日漏洞](https://red.anthropic.com/2026/zero-days/)（即软件维护者未知的安全缺陷）。

在本文中，我们分享了与 Mozilla 研究人员合作的详细情况：Claude Opus 4.6 在两周内发现了 22 个漏洞。其中，Mozilla 将 [14 个漏洞评定为高危级别](https://www.mozilla.org/en-US/security/advisories/mfsa2026-13/)——这几乎占 2025 年所有已修复的高危 Firefox 漏洞的五分之一。换句话说：AI 正在使我们能够以极快的速度检测出严重安全漏洞。

从模型评估到安全合作 ------------------ 2025 年底，我们注意到 Opus 4.5 已经接近解决 [CyberGym](https://www.cybergym.io/) 中的所有任务，这是一个用于测试大语言模型是否能够重现已知安全漏洞的基准。我们希望构建一个更具挑战性和更贴近现实的评估，其中包含更高密度的技术复杂漏洞，例如现代网络浏览器中常见的漏洞。因此，我们构建了一个包含以往 Firefox 常见漏洞和暴露（CVE）的数据集，以检验 Claude 是否能够重现这些漏洞。

我们选择 Firefox，是因为它不仅代码库复杂，而且是全球最经过充分测试和最安全的开源项目之一。这使得它比我们之前用于测试模型的开源软件更能检验 AI 发现新型安全漏洞的能力。数亿用户每天依赖它，而浏览器漏洞尤其危险，因为用户经常接触不受信任的内容，并且依赖于

浏览器以确保它们的安全。

我们的第一步是使用 Claude 在较旧版本的 Firefox 代码库中查找之前已识别的 CVE。我们惊讶地发现，Opus 4.6 能够重现其中很大一部分历史 CVE，考虑到每一个 CVE 都耗费了大量的人力才被发现。但当时我们仍不清楚应该在多大程度上信任这一结果，因为至少部分历史 CVE 可能已经包含在 Claude 的训练数据中。

因此，我们要求 Claude 在 _当前_ 版本的 Firefox 中寻找全新的漏洞——这些漏洞按定义不可能之前被报告过。我们首先聚焦于 Firefox 的 JavaScript 引擎，随后扩展到浏览器的其他部分。JavaScript 引擎是一个方便的切入点：它是 Firefox 代码库中一个独立的部分，可以单独分析，而且由于其广泛的攻击面（在用户浏览网页时处理不受信任的外部代码），确保其安全尤为重要。

仅仅探索了二十分钟后，Claude Opus 4.6 就报告称在 JavaScript 引擎中发现了一个“Use After Free”漏洞（一种内存漏洞，攻击者可能借此用任意恶意内容覆盖数据）。我们的一位研究人员在独立的虚拟机中使用最新版 Firefox 验证了该漏洞，随后将该漏洞转交给另外两位 Anthropic 的研究人员，他们也成功验证了该漏洞。我们随后在 [Bugzilla](https://bugzilla.mozilla.org/enter_) 提交了漏洞报告。

从识别漏洞到编写原始利用代码 -------------------------------------------------------------- 为了衡量 Claude 在网络安全能力方面的上限，我们还开发了一项新的评估，以确定 Claude 是否能够 _利用_ 我们发现的任何漏洞。换句话说，我们希望了解 Claude 是否也能开发出黑客用来利用这些漏洞执行恶意代码的工具。 为此，我们向 Claude 提供了已提交给 Mozilla 的漏洞信息，并要求 Claude 针对每个漏洞编写一个利用程序。为了证明其成功利用了漏洞，我们要求 Claude 提供一个可运行的 PoC（概念验证）代码，展示其能够触发漏洞并执行任意代码。

利用漏洞后，我们要求 Claude 演示一次真实的攻击。具体来说，我们要求它在目标系统中读取和写入本地文件，就像攻击者实际操作那样。

我们使用不同的起始点进行了数百次测试，花费了大约 4,000 美元的 API 信用额度。尽管如此，Opus 4.6 仅在两种情况下成功将漏洞转化为实际利用。这告诉我们两点：第一，Claude 在发现这些漏洞方面远胜于利用它们；第二，识别漏洞的成本比为其创建利用程序要便宜一个数量级。然而，Claude 能够在少数情况下自动开发出粗糙的浏览器利用程序，这一事实令人担忧。

这里的“粗糙”是一个重要的限定词。Claude 编写的利用程序仅在我们的测试环境中有效，而该环境有意移除了现代浏览器中的一些安全功能。其中最重要的是 [沙箱](https://wiki.mozilla.org/Security/Sandbox)，其目的是降低此类漏洞的影响。因此，Firefox 的“纵深防御”策略足以有效缓解这些特定的利用程序。但绕过沙箱的漏洞并非罕见，而 Claude 的攻击是端到端利用链中的一个必要组成部分。您可以在我们的 [Frontier Red Team 博客](https://red.anthropic.com/2026/exploit/) 中了解更多关于 Claude 如何开发其中一种 Firefox 利用程序的细节。

AI赋能网络安全的下一步 ---------------------------------------- 这些早期迹象表明，AI驱动的漏洞利用开发凸显了加快防御者“发现并修复”流程的重要性。为此，我们希望分享在进行此项分析过程中总结出的一些技术和流程最佳实践。

首先，在研究“补丁代理”（即利用大语言模型开发和验证漏洞修复方案的工具）时，我们开发了一些方法，希望有助于维护者更高效地使用像Claude这样的大语言模型，快速处理和响应安全报告。1

根据我们的经验，当Claude能够借助其他工具自行验证其工作成果时，效果最佳。我们将这类工具称为“任务验证器”（task verifier）：一种可信的方法，用于确认AI代理的输出是否真正实现了其目标。任务验证器在AI代理探索代码库时提供实时反馈，使其能够不断迭代，直至成功。

任务验证器帮助我们发现了上述Firefox漏洞，2 并且在另一项独立研究中，我们发现它们在**修复**漏洞方面同样有用。一个优秀的补丁代理需要至少验证两件事：一是漏洞是否已被真正消除，二是程序的预期功能是否得以保留。在我们的工作中，我们构建了自动测试工具，用于验证在提出修复方案后原始漏洞是否仍可被触发，并单独运行测试套件以捕获回归问题（即因更改而意外破坏其他功能的情况）。我们预期

维护者最清楚如何为自己的代码库构建这些验证器；关键在于，为代理提供一种可靠的方式来检查这两个属性，能显著提升其输出质量。

我们无法保证所有通过这些测试的代理生成的补丁都足以立即合并。但任务验证器让我们更有信心：生成的补丁能够修复特定漏洞，同时保持程序功能不变——从而达到被认为是合理补丁的最低要求。当然，在审查由 AI 生成的补丁时，我们建议维护者对其施加与审查任何其他外部作者提交的补丁相同的严格审查。

从提交漏洞和补丁的整体流程来看：我们知道维护者已经不堪重负。因此，我们的方法是提供维护者所需的信息，以帮助他们信任并验证报告。Firefox 团队指出了我们提交报告中的三个关键组成部分，这些是他们信任我们结果的重要依据：

1. 附带的最小测试用例 2. 详细的概念验证 3. 候选补丁

我们强烈建议使用基于大语言模型（LLM）的漏洞研究工具的研究人员，在提交基于此类工具输出的报告时，也包含类似的验证和可复现性证据。

当前的紧迫性 ------------------------- 前沿语言模型现已具备世界级的漏洞研究能力。除了在 Firefox 中发现的 22 个 CVE 外，我们还使用 Claude Opus 4.6 在其他重要软件项目（如 Linux 内核）中发现了漏洞。在接下来的数周和数月里，我们将持续报告我们如何使用这些模型，以及如何与开源社区合作提升安全性。

Opus 4.6 当前在识别和修复漏洞方面远优于利用漏洞的能力。这为防御方提供了优势。同时，随着近期 [Claude Code Security](https://www.anthropic.com/news/claude-code-security) 在有限研究预览版中的发布，我们已将漏洞发现（及修复）能力直接提供给客户和开源维护者。

但考虑到技术进步的速度，前沿模型在漏洞发现与利用能力之间的差距不太可能长期存在。如果未来语言模型突破了利用漏洞的技术壁垒，我们将需要考虑额外的安全防护措施或其他行动，以防止我们的模型被恶意行为者滥用。
