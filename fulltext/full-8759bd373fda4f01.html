📅 2026-10-28 📄 VentureBeat AI 🔗 原文链接

原标题：Liquid AI’s new LFM3 models put browser agents, voice commands, and image recognition onto enterprise-controlled devices

中文摘要： Liquid AI 发布 LFM3 模型家族，涵盖语言、视觉、语音和结构化决策共六款模型，基于 17 亿参数基础，可部署于企业自有设备、私有服务器或云端。公司报告其 1.7B 文本模型在浏览器自动化和函数调用任务上超越更大的 Qwen3.5-9B，但在编码、知识和长上下文方面仍有差距。模型支持 256K 上下文（API 版为 128K），四比特精度下约 1GB。托管服务定价低廉且零数据保留；本地部署需注意年收入超 1000 万美元的企业须另行签订商业许可协议。

Liquid AI 正在推出 LFM3——一系列紧凑型 AI 模型，旨在将更多企业工作负载迁移到公司自控的硬件上。该公司报告的结果显示，其最小的文本模型在部分浏览器自动化和软件工具使用任务上能够超越规模大得多的竞争对手。

10 月 27 日的发布包括六个模型，涵盖语言、视觉、语音和结构化决策。它们共享一个 17 亿参数的基础，专用版本约为 20 亿参数。Liquid 表示，企业可以使用单块 GPU 对每个模型进行定制，并将其部署在设备、私有服务器或云基础设施上。

这一卖点对于构建可重复工作流的公司尤其相关：路由请求、从文档中提取信息、检查图像或操作业务应用。一个能够可靠处理特定任务的小型模型可以减少对远程 AI 服务的依赖，并让组织对推理发生的位置拥有更多控制权。

对于偏好托管服务的公司，Liquid 登录后的控制台将文本模型定价为每百万输入 token 0.08 美元、每百万输出 token 0.20 美元，缓存输入定价为 0.02 美元。开发者必须登录 Liquid 控制台才能查看 LFM3 费率卡并获取直接 API 访问的凭证。

Liquid 的详细结果也显示了尚存的权衡。其文本模型在若干编码、知识和长上下文评估中落后于 Qwen3.5-9B，且托管服务的上下文限制小于可下载的文本模型。

这使得 LFM3 成为定向试点的候选者，其商业价值取决于工作负载、部署成本和许可条款。

旗舰产品 LFM3-1.7B 文本模型支持有文档记录的 256K token 上下文窗口——即输入和输出的总预算。Liquid 的托管控制台为其 API 版本列出 128,000 token 的上下文限制，企业在选择托管部署与自主管理部署时应考虑这一区别。Liquid 表示，它训练该模型在包括 OpenClaw、Hermes Agent 和 Pi 在内的智能体框架中工作，支持收件箱整理、日程安排和网络研究等任务。

其企业相关性的最强证据来自单项基准测试，而非总体平均值。

在 Liquid 的测试中，LFM3-1.7B 在 WebArena-Verified 上得分为 38.42，而 Qwen3.5-9B 为 28.94，Liquid 之前的 LFM2.5-2.6B 为 3.02。在 AutomationBench 的公开评估中，它得分为 41.29，而后两者分别为 15.10 和 0.94。

以下选录既包括优势也包括弱点。这些是 Liquid 报告的结果，并非 VentureBeat 的独立测试。

评估项目 LFM3-1.7B LFM2.5-2.6B Qwen3.5-9B
WebArena-Verified 38.42 3.02 28.94
AutomationBench（公开） 41.29 0.94 15.10
BFCL V4（函数调用） 71.39 55.89 62.83
EnterpriseOps-Gym 28.20 7.94 28.97

这些差异表明不应将 LFM3 视为大型模型的通用替代品。它在选定的浏览器和函数调用测试中领先，但在 MCP-Atlas 上落后，在 EnterpriseOps-Gym 上略低于 Qwen。其宣传的上下文容量也不应被误认为在长输入上具有更高的准确性。

Liquid 在给 VentureBeat 的书面回复中承认了这一更广泛的局限："在智能体编码和知识方面，大型模型仍然胜出，因为这些领域最依赖规模。"

其文档表述更为明确："由于其规模较小，不建议将其用于智能体编码或复杂的多步推理。"

该公司没有直接回答每次比较是否使用了同等的工具和推理额度。其发布的公告将梅赛德斯-奔驰和 Shopify 列为发布前测试和评估模型的合作伙伴，但没有提供基准测试结果的独立验证。团队在预测生产环境节省之前，应测试自己的工作流，包括失败的工具调用、重试和升级到另一个模型的情况。

LFM3 的架构变化旨在让更小的体积发挥更大作用。新设计将卷积层（高效处理邻近信息）与注意力机制（检查有限窗口或更广泛的上下文）相结合。Liquid 称之为三混合架构。

共享基础模型在 22 万亿 token 上进行了预训练。后续训练强调工具使用、业务工作流和其他智能体任务。Liquid 表示，最终的 1.7B 文本模型尽管参数量减少约 35%，但仍优于其之前的 2.6B 版本。

内存需求需要特别注意。Liquid 描述该文本模型在四比特精度下可容纳于约 1GB 中。然而，这并不能证明整个应用可以在 1GB 内运行，尤其是在处理长输入时。

该公司最新的回复澄清，其针对 128K token 上下文的单独 1.6GB 数字指的是 KV 缓存——生成过程中用于保留信息的工作内存。模型存储和其他运行时需求仍是额外的考虑因素。Liquid 没有提供最大 256K 上下文长度下的完整内存预算。

在本地速度测试中，Liquid 在 AMD Ryzen AI Max+ 395 系统、Apple M5 Max 系统和 iPhone 17 Pro 上对模型进行了比较。它报告的生成速度是每次比较中次快模型的 1.8 到 2.8 倍，测试使用 llama.cpp、四比特 Q4_0 模型、32K token 输入和单次请求。

已发布的性能表为这一说法提供了具体数字：

测试系统 输入处理（token/秒） 生成（token/秒） 报告内存
AMD Ryzen AI Max+ 395 3,771 129.6 2.75GB
Apple M5 Max 8,028 237.1 2.25GB
iPhone 17 Pro 1,061 43.6 1.90GB

Liquid 对 LFM3-1.7B 的测量条件：Q4_0 GGUF、llama.cpp、32K 输入 token、100 输出 token、单次请求和 GPU 卸载。AMD 内存结合了主机和 GPU 的峰值使用量；Apple 数据反映统一内存。

这些实测数据进一步说明，为什么约 1GB 的模型大小声明不应被用作总部署内存预算。这些数字描述的是特定的压缩模型和工作负载，并非对每台设备或应用的保证。

在服务器规模上，Liquid 报告单块 Nvidia B300 在 1,024 个并发请求下每日可生成相当于 36 亿 token 的容量。该测试使用 BF16 精度、SGLang、每请求 1,024 输入 token 和 256 输出 token，取三次运行的平均值。它测量的是总吞吐量，而非单个用户完成复杂任务的速度。

在单块 Nvidia B200 上的另一项延迟测试报告，在每秒 500 个请求下，使用 128 输入 token 和 64 输出 token，第 95 百分位完成时间为 150 毫秒。在该测试中，95% 的请求在报告时间内完成。对于 1,024 输入 token 和 256 输出 token 的较长请求，该数字在每秒 100 个请求下上升至 668 毫秒。

在此比较中，Liquid 对自己的模型使用其 RIPL 服务软件，对竞争对手使用 vLLM。该结果评估的是模型与服务系统的组合；它既没有单独隔离架构本身，也没有确定客户通过托管 API 体验到的延迟。

除了文本智能体之外，该模型家族还扩展了 Liquid 可以处理的应用类型。

模型 Liquid 描述的能力 潜在企业试点
LFM3-1.7B 语言生成和工具使用；模型上下文 256K，所列 API 为 128,000 范围明确的内部智能体
LFM3-VL-2B 图像和视频解读，以文本响应 文档处理或检查辅助
LFM3-Audio-2B 语音和文本输入；语音或文本响应；18 种语言 本地转录或语音操作工具
LFM3-Omni-2B 视觉、音频和文本组合输入；语音和文本响应 可解读图像的免提助手
d1-2B 从文本和图像进行结构化决策 工单分类或发票提取
d1-Omni-2B 结合音频的结构化决策 路由语音请求

试点建议属于编辑分析，并非已确立的客户部署声明。

视觉模型为 Liquid 的 LFM 视觉系列增加了视频输入。据该公司报告，其在 62 项评估中的平均分为 71.4，而 LFM2.5-VL-3B 为 57.6，Qwen3.5-2B 为 64.0。该汇总值是 62 项评估的未加权平均值。在文档、光学字符识别和图表类别中，Liquid 报告 LFM3-VL-2B 为 83.9，而其前代产品为 71.2，Qwen3.5-2B 为 79.1。这些结果比总体平均值与文档处理试点的相关性更直接，尽管它们仍然不能证明在客户自己的文档上的准确性。

音频模型增加了解读录音以及根据语音请求触发软件工具的能力。Liquid 表示，其新编码器在说话者说完之前就处理传入的语音，使第一个响应 token 最快可在 50 毫秒后到达。这是该公司报告的最佳情况数字，并非完整的语音响应时间或 API 服务保证。

LFM3-Omni-2B 是 Liquid 首个以这种方式结合视觉、语音和语言的模型。尽管产品名称经过四舍五入，它实际拥有 22 亿参数，能够结合音轨解读视频，或将语音指令与图像结合以产生工具调用。

已发布的公告提供了一个具体的企业方向：梅赛德斯-奔驰正在探索本地 AI 如何改进其 MBUX 虚拟助手。该公告将梅赛德斯-奔驰和 Shopify 列为发布前测试合作伙伴，但没有提供任何一家公司确认生产部署 LFM3 的消息，也没有测得的客户业务成果。

决策模型提供了不同于对话式智能体的方法。Liquid 将 d1-2B 定位为 d1-3B 的继任者，新的结构化答案格式扩展了早期模型的是/否、选择和评分能力。Liquid 表示，它们在一次处理中评估关于输入的多个问题，并返回带概率的结构化答案。新的答案格式包括提取字段、定位对象、估计数值和选择多个适用选项。

对于需要对传入工单进行分类或提取发票日期的企业来说，这种更窄的输出可能比生成对话式响应更有用。在驱动自动化决策之前，概率分数仍需针对公司自己的记录进行验证。

Liquid 还提供了一个具体的定制示例。它使用大约 3,000 张公开的风力涡轮机图像对 LFM3-VL-2B 进行了适配，在 Nvidia A100 上进行了数小时训练，然后在约 1,400 张保留图像上进行了评估。

该公司报告分类准确率为 67%，而专业化之前低于 10%。然而，其单独的检测 F1 分数——反映识别和定位缺陷的性能——仅达到 0.11，从 0.003 提升。该示例展示了任务特定训练带来的显著收益；但它并不能证明已具备自主工业检查的条件。公告链接到风力涡轮机定制示例和微调笔记本，供评估该方法的开发者使用。

一个机器人示例在 AMD Instinct MI325X 上使用约六个 GPU 小时，适配视觉模型以通过软件工具操作模拟机器人手臂。Liquid 将机器人技术描述为研究扩展，因此该结果应与生产部署区分开来。

控制台定价使托管部署选项更加具体。

开发者必须登录 Liquid 控制台才能查看这些 LFM3 价格并获取 API 密钥以直接调用新模型。VentureBeat 审查的已认证目录列出了四个 LFM3 生成模型，并将每个模型标记为在该服务内公开可用。

LFM3-1.7B $0.08 $0.02 $0.20 — —
LFM3-VL-2B $0.10 $0.02 $0.50 — —
LFM3-Audio-2B $0.10 $0.02 $1.00 $2.00 $10.00

来源：Liquid AI 的已认证模型目录。价格为每百万 token 的美元金额；音频费用按每百万音频 token 计，而非按分钟计。合同定价可能有所不同。

按这些费率，使用 LFM3-1.7B 处理一百万未缓存输入 token 并生成一百万输出 token 的成本为 0.28 美元。视觉模型的等效文本 token 总额为 0.60 美元，Audio 或 Omni 为 1.10 美元，不含任何音频 token 费用。这些计算说明的是 token 成本，而非完成特定业务任务的成本。

所有四个托管的 LFM3 条目都列出了 128,000 token 的上下文限制。它们的速率限制字段包含破折号，但控制台并未承诺无限请求：其随附通知称使用限制在组织的 API 密钥之间共享。

控制台还列出了 d1.1，每百万输入 token 0.02 美元，缓存输入价格相同，且无输出费用。该托管标识符与可下载的 d1-2B 名称不同；截图并不能证明它们是同一个模型。

对于对隐私敏感的买家，控制台声明所有列出的模型均零数据保留。Liquid 表示，它使用提交的材料来满足请求，不会保留或记录该内容，也不会将其用于训练。这是该公司声明的服务承诺；所审查的材料中未指明托管区域和支持保证。

选择本地部署的团队有不同的成本结构。Liquid 链接到 Hugging Face 上的 LFM3 权重、其 Playground 和其 API 控制台。其模型目录记录了可用的格式和运行时，文本、视觉、音频和决策模型的支持情况各不相同。买家应检查特定模型和格式，而不是假设每项功能在每个运行时中都能工作。

可下载的权重还附带商业条件。LFM3-1.7B 文档明确标明 LFM Open License v1.0。根据 Liquid 公布的许可条款，年收入超过 1000 万美元的企业需要单独签订协议才能商业使用。组织可以将其改编版本保密，Liquid 的定价页面表示企业许可费用取决于部署规模。

这意味着本地部署可以消除按 token 计费的 API 费用，但不能消除许可、硬件、电力或运营费用。即使在公司硬件上进行模型推理，本地运行的智能体仍可以通过连接的网络搜索、消息传递和其他外部工具传输信息。

对于企业技术领导者来说，最站得住脚的起点是具有可衡量结果的有限工作流：要提取的文档字段、要分配的工单类别，或一系列经批准的工具调用。评估部署版本的准确性和延迟，然后考虑许可、硬件、维护和人工审查。

Liquid 的结果为测试小型模型能执行多少有用工作提供了可信的依据。LFM3 能否赢得生产角色，将取决于它能否可靠地完成企业需要完成的特定工作。
