中文摘要： 本文提出了一种基于大型语言模型（LLM）的进化程序搜索系统，用于生成可执行的游戏内容生成器。研究引入了持续抽象发现（CAD）机制，在搜索过程中从高适应度程序中提取、验证并重用辅助函数。在四个游戏领域的实验表明，无论是否使用专家API，CAD均能显著提升生成器的最终适应度，且学习到的库被后续程序广泛采用，有效改进了程序化内容元生成。

摘要
大型语言模型能够生成可执行程序，这使得直接搜索程序化内容生成器而非单个关卡成为可能。我们在《推箱子》、《塞尔达》、《危险戴夫》和《淘金者》中研究了这种方法。每次运行都通过语言模型变异和交叉来演化完整的 Python 生成器。我们引入了持续抽象发现（CAD），它从高适应度程序中提取可重用的原语到特定运行的辅助模块中。一个 2×2 的实验将 CAD 与对固定手写领域 API 的访问进行了交叉。完整的数据集包含 160 次完整运行，每个单元格中至少有十次 50 代的运行。CAD 在所有八个领域和 API 比较中都提高了平均最终最佳适应度。在所有 CAD 运行中，学习到的库被大多数后续程序采用，并反复重新发现验证、可达性和结构实用工具。这些结果支持了发现可重用原语能改进内容生成器的进化程序搜索。

I 引言
具有程序化生成内容的游戏通常依赖于为特定游戏的机制、约束和设计目标量身定制的自定义生成器。创建这些生成器需要大量的工程和反复的评估。程序化内容生成器生成旨在通过搜索生成器本身而不是直接搜索单个工件来自动化这一过程 [5]。这个过程也可以称为程序化内容元生成。

现有方法通过进化计算、机器学习或强化学习来学习生成器 [5, 8, 20, 6, 11]。许多方法产生神经或不透明的表示。这些生成器可能有效，但很难检查和编辑。可执行源代码提供了一种不同的表示。程序可以被编译、测试、由设计者修改，并在搜索系统之外重用。

大型语言模型在编写和修改代码方面越来越有能力。这使得将代码生成模型置于进化循环中成为可能。候选生成器被执行，其关卡被评估，由此产生的反馈指导后续的变异和交叉调用。相关系统已使用语言模型作为可执行程序搜索的变异算子 [14, 1, 17]。程序化内容元生成提出了这个问题的一个苛刻实例，因为生成器的质量只能通过重复执行和行为评估来判断。

对原始代码的搜索固定了可用于变异的词汇表。随着程序的增长，用于可达性、实体规范化、修复和结构构建的有用例程可能会在许多候选者中独立重新创建。手写的辅助 API 可以公开可重用的操作，尽管其词汇表在搜索开始之前保持固定。我们引入了持续抽象发现（CAD），作为一种让可执行原语集合在运行期间增加的方法。CAD 从高适应度程序中提取可重用的实用工具到特定运行的辅助模块中，验证该模块，并在可以安全执行时重构程序以使用学习到的实用工具。

我们在 PCG Benchmark 的四个领域 [7] 上评估了该系统。主要研究将固定的领域辅助 API 与 CAD 交叉。这种设计将对可重用词汇表的访问与搜索期间词汇表的发现分离开来。

我们做出了四项贡献。
• 我们展示了在《推箱子》、《塞尔达》、《危险戴夫》和《淘金者》中基于 LLM 的可执行 Python 级生成器的进化搜索。
• 我们引入了 CAD，这是一种搜索时机制，用于提取、验证和重用在具有高适应度的程序中发现的辅助函数。
• 我们提出了一项 2×2 的研究，在 160 次完成的运行中将 CAD 与对固定专家 API 的访问分离开来。
• 我们展示了在 4 个游戏领域中的积极 CAD 效应，并对学习库的增长、采用和原语进行了分析。

II 相关工作
各种各样的计算方法已被应用于生成游戏内容，特别是游戏关卡。这些方法从进化计算 [23] 和约束满足 [18] 到监督学习 [20] 和强化学习 [6]。已发布的游戏通常依赖于为特定游戏专门设计的构造性生成器 [16]，这限制了可重用性。

最近，研究人员将 LLM 应用于生成游戏关卡 [22, 19, 3, 2, 21, 12, 13, 4]。结果喜忧参半。为了以 LLM 能够理解的方式表示游戏关卡，需要以某种方式将其转换为字符串。通常，这意味着将关卡表示为一系列行，其中每个字符代表一个图块。初步结果表明，在特定游戏的关卡上微调生成器提高了生成能力，并且更现代和最新的 LLM 在关卡生成方面优于较旧和较小的 LLM（就像在大多数其他方面一样）[22]。

然而，当前 LLM 在生成游戏内容时存在局限性，特别是诸如关卡之类的空间内容。例如，LLM 往往在确保从 A 点到 B 点存在清晰路径，以及存在正确数量的各种类型的物品和角色（例如恰好一个玩家角色，以及与钥匙数量相同的门）方面存在问题。LLM 生成的游戏关卡的其他病理似乎源于薄弱的空间推理 [22, 2, 12]。

LLM 的主要用例之一是代码生成。软件工程目前正被能够从非正式规范中产生工作代码的 LLM 的出现所改变。然而，在许多情况下，你知道你想要什么，但不知道确切如何实现。在这些情况下，你可以创建一个衡量你想要什么的适应度函数，然后将生成代码的 LLM 嵌入到进化循环中。这种方法被 AlphaEvolve [14] 推广，除其他外，它发现了一种改进的矩阵乘法算法，类似的方法也被应用于创建科学数据分析解决方案和金融交易策略 [1, 17]。

在进化循环中使用 LLM 生成代码可以被视为遗传编程的一种形式，它是进化计算在程序合成中的应用 [15, 9]。从这个角度来看，LLM 正在执行遗传编程中的变异和/或交叉操作。遗传编程中的一个重要概念是自动定义函数，其中一组可调用函数与主程序一起演化，构成了一种演化抽象的形式 [10]。

持续抽象发现（CAD）也与最近关于智能体技能库的工作有关，其中存储了可重用的代码或行为以供以后使用，例如 Voyager 的 Minecraft 智能体技能库 [24]。我们设置中的关键区别在于，该库不是已解决任务或手动公开技能的记录，而是在正在进行的进化搜索期间从高性能生成器程序中提取的、不断更新的辅助函数集合。因此，CAD 充当搜索时的表示机制。在种群仍在优化的同时，它更改了后续变异、交叉和重构调用可用的程序原语。

回到 PCG 研究，通过机器学习 [20]（包括强化学习 [6]）进行 PCG 的工作通常会学习生成器，然后使用这些生成器来生成游戏内容。然而，它们大多学习神经网络或其他类型的黑盒表示，这些表示不允许轻松进行人工解释和编辑。也有例外情况，其中使用进化或类似方法来学习以符号表示表示的生成器 [5, 8]。本文提出的方法可以被视为程序化程序化内容生成器生成，或程序化内容元生成，使用在生成器空间中由 LLM 代码编写增强的基于搜索的方法。除了工具和领域的组合之外的一项关键发明是持续抽象发现机制，它类似于自动定义函数，但使用 LLM 驱动的进化。

III 方法
III-A 程序表示
每个个体都是一个完整的 Python 程序，定义了 generate(context_dict)。该函数接收网格维度和初始关卡，并返回一个图块网格。程序可以包含局部函数、常量和布局例程，而公共接口在整个种群中保持不变。这种表示允许每个候选者使用相同的测试工具进行编译、执行、检查和评估。

所有运行都从一个最小的种子程序开始。该种子包含图块常量和一个空白或复制的初始网格，没有生成逻辑。它被评估一次并成为档案的根。档案保留每个成功评估的个体。

III-B 进化搜索
在每一代中，从档案中以与适应度成正比的概率采样一个父代。适应度值在归一化之前被下限为 10^{-6}。当档案包含至少两个个体时，以 0.25 的概率选择交叉。然后以相同的规则采样第二个父代。交叉尝试失败则回退到变异。

变异和交叉由 LLM 执行。提示包含父程序、领域描述、累积的运行内存和固定的生成器契约。变异要求进行强烈的行为编辑。交叉要求模型将两个父代的兼容机制组合成一个完整的可执行程序。

每个候选者都要经过鲁棒性管道。程序必须编译并完成五次冒烟测试执行中的至少三次。失败会触发以错误为条件的 LLM 纠正调用。变异或交叉循环最多尝试四次。从未产生有效候选者的一代被记录为适应度为零。解析失败、编译失败、冒烟测试失败和超时被单独记录。

在每一代之后，LLM 反思调用将一个结构化条目附加到每次运行的内存文件中。每个条目记录尝试的更改、观察到的结果以及供以后搜索使用的全局经验。累积的全局经验被提供给后续的变异和交叉调用，以代替原始的每个父代评估反馈。

III-C 评估和适应度
每个候选者执行 30 次。采样的关卡使用 PCG Benchmark [7] 提供的质量、有效性和多样性函数进行评估。我们计算完全有效关卡的比例、平均基准质量和所有采样关卡对的平均成对多样性。适应度定义为

F = 1/3 * (V + Q + D), (1)

其中 V 是质量等于 1.0 的关卡比例，Q 是平均关卡质量，D 是平均成对多样性。所有项都在 [0, 1] 范围内。崩溃或验证失败的候选者适应度为零。

III-D 持续抽象发现
这项工作的贡献之一是持续抽象发现。从第 8 代开始，此后每五代，系统会识别运行中适应度处于或高于第 75 百分位的程序。LLM 提取调用分析这些程序，并从该代码中提出可重用的实用工具函数。

提取的函数必须编译并通过冒烟测试。系统最多允许两次编译纠正。然后重构源程序以调用新的辅助函数。仅当重构后的程序在固定种子行为测试上与原始程序匹配时（生成的关卡具有相似的行为特征），才接受重构。接受的重构将被重新评估，并更新其档案条目。在十代预热后，如果重构成功率仍低于 30%，则禁用重构。提取的函数记录在系统库中，供程序在进化期间使用。

IV 实验设计
IV-A 领域
我们评估了来自 PCG Benchmark 的四个基于图块的领域：
• 推箱子：是一个 5x5 的日本解谜游戏，玩家需要将箱子推到特定的目标位置。
• 塞尔达：是一个 7x11 的地牢爬行游戏，灵感来自最初《塞尔达传说》游戏的地牢房间。关卡的目标是获取钥匙并到达出口而不被怪物杀死。
• 危险戴夫：是一个 7x11 的平台游戏，基于同名游戏。游戏的目标是让玩家拿到钥匙并到达终点而不被尖刺杀死。
• 淘金者：是一个 11x16 的解谜平台游戏，基于同名游戏。游戏的目标是让玩家收集所有金币并避免被敌人抓住。解谜元素是玩家不能跳跃；他们只能通过行走、挖穿地板、爬梯子和穿过绳索来在关卡中移动。

对于所有这些问题，我们使用框架的质量和多样性输出。这些输出主要使用 A* 求解器来计算质量，并使用一些行为和视觉特征来计算多样性。对生成器的每次调用限制为两秒。

IV-B 因子条件
主要研究测试了 4 个实验，测试拥有辅助函数的有用性。为了评估这一点，我们有两个正在测试的参数：
• CAD：允许 LLM 抽象程序并生成辅助函数，如第 III-D 节所述。
• 专家 API：拥有一组在 PCG 中常用的手工设计的辅助函数。该库包含用于实体规范化、可达性、修复和特定领域结构操作的已验证原语。示例包括 connect_floors_with_ladder 和 ensure_one_player。专家 API 测试提供辅助函数是否足够，或者仍然需要 CAD。

每个实验使用相同的最小种子、进化搜索、反思内存、纠正管道、评估预算和适应度函数。我们将每个实验运行 10 次，持续 50 代。

IV-C LLM 和执行配置
所有语言模型调用均使用 GLM 5.2。变异使用温度 0.2。纠正和重构使用温度 0.1。平均 50 代运行使用了大约 950 万个输入 token 和 260 万个输出 token。平均成本约为 25 美元，平均挂钟时间约为 2.5 小时。每次运行存储每代统计信息、程序源码、评估分析、提示、有效渲染关卡、进化树、反思内存、CAD 条件的辅助模块快照以及 token 和时间日志。

VI 讨论
VI-A 跨领域证据
结果表明，一个进化程序搜索框架可以在具有不同网格大小和基准评估器的四个游戏中运行。CAD 在每个领域都提高了平均适应度。最大的效果出现在专家 API 可用时的《淘金者》中。在这种条件下，搜索已经具有特定于领域的可调用例程，但特定于运行的学习词汇仍然提高了最佳适应度。其他三个 API 单元也倾向于 CAD，尽管它们的测试未达到 p<0.05。

VI-B 作为表示适应的 CAD
CAD 在搜索期间更改了后续变异调用可用的操作。可执行基础仍然是 Python，而有效词汇随着提取辅助函数而增长。机制测量表明，生成的函数被后续程序采用并重复调用。通常重复出现的辅助函数解决了诸如实体规范化、玩家放置、可达性、连通性和结构构建等模式。这些是基于图块的生成器设计中的核心操作。大量特定于运行的尾部也表明 CAD 不会收敛到一个固定的库。它将重复出现的核心与由领域和搜索历史塑造的实用工具结合起来。

程序大小分析支持相关的解释。CAD 缩短了最佳基础程序，而固定 API 已经产生了紧凑的源库。这并不能证明较短的程序本质上更好。它表明可重用的可调用词汇可以将逻辑从主生成器中卸载，这可能会使后续的编辑更容易表达和保留。

VI-C 实际意义和局限性
可解性、基准质量和多样性不能完全捕捉视觉风格、节奏、新颖性或设计者意图。当所需的生成器具有基准中不存在的美学或体验目标时，人工审查仍然很重要。

计算成本是相当大的。典型的 50 代运行使用接近前沿级模型的数百万个 token 和数小时的挂钟时间。CAD 引入了额外的提取、纠正和重构调用。未来的工作应该评估适应度增益与 token 使用和挂钟成本的对比。

CAD 被评估为一个完整的管道。辅助提取、模块纠正和源重构没有被分离到单独的消融中。机制追踪显示了增长、采用和程序大小的变化，尽管它们没有隔离每个组件的因果贡献。额外的工作应该测试更长的预算、其他语言模型、非图块内容、跨运行库转移以及设计者对发现的辅助函数的编辑。

VII 结论
我们提出了一个进化程序搜索系统，该系统使用 LLM 来生成可执行的程序化内容生成器。评估涵盖了《推箱子》、《塞尔达》、《危险戴夫》和《淘金者》，每个游戏运行 10 次。无论你是从空的辅助库还是专家辅助函数开始，持续抽象发现都提高了平均最终最佳适应度。

在所有 CAD 运行中，学习到的库不断增长，被后续程序采用，并反复恢复验证、可达性和结构实用工具。结果支持 CAD 作为在程序化内容元生成期间调整可搜索程序词汇表的实用机制。
