OctoLong：基于跨仓库代码上下文的中期训练增强长上下文建模

Indraneil Paul1, Falko Helm1, Goran Glavaš2, and Iryna Gurevych1
1 UKP Lab & Center for Applied Cybersecurity ATHENE, TU Darmstadt
2 CAIDAS, University of Würzburg

摘要

受上下文学习、自我提升和长程智能体工作流的需求驱动，语言模型（LM）的上下文长度大幅增加。然而，现有的长上下文语料库主要由书籍、学术文章和代码仓库组成，这些资源不仅有限，而且通常缺乏长距离依赖关系。在本研究中，我们提出了 OctoLong，这是一个上下文工程流水线，它利用 AST 解析器、语言服务器后端和包管理器来促进代码引用的递归检索，从而能够整理出长达数百万 token 且富含依赖关系的代码上下文。随后，我们训练了 OctoLong-Instruct，这是一系列强大的长上下文开源语言模型，基于 600M 到 14B 参数的基础模型。训练过程包括在包含约 500 亿 token 的混合数据（其中包含约 62 亿 token 的 OctoLong 代码上下文）上进行上下文扩展中期训练，随后进行约 100 亿 token 的指令微调。我们的训练消融实验和针对 18 个强大的长上下文开源权重语言模型的实验评估表明，仅用 OctoLong 数据替换 12% 的传统上下文扩展语料库，就能在长程检索、长期状态跟踪、仓库级代码理解和下游智能体任务中取得显著提升，同时也增强了短上下文编程场景中的 API 使用能力。

1 引言

诸如上下文学习（Bertsch 等，2025）、检索增强生成（Qian 等，2025；Kang 等，2025）和智能体工具使用（Merrill 等，2026；Jimenez 等，2024）等新兴语言模型（LM）应用需要长程能力（Kwa 等，2025），这呈指数级推高了对 LM 预期支持的上下文长度的需求（参见图 1）。先前扩展上下文长度的尝试主要涉及架构干预，例如稀疏注意力（Yuan 等，2025；Han 等，2024；Beltagy 等，2020）和线性注意力（Hatamizadeh 等，2026；Dao 和 Gu，2024）。孤立地看，这些方法在较长上下文上的性能会下降（Lu 等，2024；Huang，2024），促使 LM 开发者转向正交的改进轴，如硬件使用改进（Li 等，2023a；Liu 等，2023）、推理时上下文管理（Li 等，2024c；Zhang 等，2023b）和更好的数据工程（Li 等，2025b）。

用于上下文扩展的数据工程。 用于长上下文训练的数据工程（Fu 等，2024）核心在于构建具有高密度引用（即依赖关系）且跨越不同距离的长文本输入。现有方法涵盖了 token 级别的依赖过滤（Deng 等，2025；Rathi 和 Radford，2026）、在上下文中整理多个显著文档（Gao 等，2025b；Jia 等，2025；Li 等，2024a）以及基于引用的打包（Zhuang 等，2025；Staniszewski 等，2025）。然而在实践中，这些方法构建的上下文通常缺乏复杂的多跳依赖（Li 等，2024b），并且会挖掘到无关或矛盾的信息（Du 等，2025b；Tang 等，2025）。在本研究中，我们引入了跨仓库代码依赖挖掘。这种引用打包技术利用公开可用的代码数据，解锁了一个几乎无限的、跨越仓库边界且富含多跳引用的上下文来源。

贡献。 我们解决了上述研究空白，并做出了以下贡献：
1. 我们提出了 OctoLong，这是一个协同使用 AST 解析器、LSP 服务器和包管理器来生成跨仓库代码上下文的流水线。对注意力图和模型似然性的分析表明，我们的流水线产生了异常富含依赖关系的长上下文（第 3 节）。
2. 我们使用 OctoLong 流水线收集了约 62 亿 token 的跨仓库长上下文数据，并将其与其他长数据源结合，整理出包含约 500 亿 token 的 OctoLong-LCFT 语料库。随后，我们编译了包含约 100 亿 token 的开源指令和智能体数据混合集 OctoLong-SFT（第 4 节）。
3. 使用上述语料库，我们对 Qwen3 稠密基础模型进行了长上下文微调（LCFT），将其支持的上下文长度翻两番至 128K，随后进行了监督微调（SFT），从而获得了 OctoLong-Instruct 系列（第 4 节）。
4. 通过广泛的实验和消融研究，我们证实，在长上下文数据混合中使用我们的 OctoLong 数据进行 LCFT，不仅在长上下文代码任务中带来了显著改善，而且在包括智能体用例在内的通用领域长上下文应用中也取得了进步，同时对短上下文 LM 能力没有产生负面影响（第 5 节）。

2 相关工作

我们简要概述了两个相关的现有工作脉络：1 跨文档上下文工程，2 长上下文代码数据挖掘。

跨文档上下文工程。 先前致力于构建跨文档上下文的工作依赖于超链接（Zhuang 等，2025；Yasunaga 等，2022）、书籍 BISAC 代码（Jia 等，2026）、事件共指（Caciularu 等，2021）和仓库级代码依赖（Guo 等，2024）。这些方法要么难以扩展，要么产生关联松散的上下文。相比之下，我们详细说明了如何递归挖掘超出仓库边界的被引用类和函数实现——这是一个尚未开发的紧密耦合数据源，其获取易于扩展。

挖掘长自包含代码数据。 早期在文件级别挖掘长代码数据的尝试发现，长代码文件通常是低质量的配置文件和无信息的构建产物（Singh 等，2024）。随后的方法转向在仓库级别序列化代码（Ding 等，2024；Deng 等，2024）。序列化后的仓库随后成为中期训练（Liu 等，2025a；Blakeney 等，2024）和上下文扩展（Mo 等，2025）语料库的锚点。然而，大多数代码在仓库级别并不是自包含的（Yu 等，2024），这限制了模型对多仓库项目的推理能力（Chen 等，2026）。在跨仓库上下文上训练的尝试因工具不足而受阻（Usai 等，2026），因此仅限于获取依赖库名称（Liao 等，2024）。在第 3 节中，我们详细描述了一个新颖的流水线，用于获取超出仓库边界的被引用实现。

3 OctoLong 数据集

为语言建模获取长上下文代码传统上侧重于按依赖遍历顺序序列化单个代码仓库（Lozhkov 等，2024；Guo 等，2024；Zhang 等，2023a；Shrivastava 等，2023；Sapronov 和 Glukhov，2025）。为了测试我们在第 1 节中提出的假设，我们开发了 OctoLong 流水线，以跨仓库边界检索代码依赖。

语言服务器协议。 我们利用了语言服务器协议（LSP）¹，这是一个 JSON-RPC 标准，通过前置特定语言的编译器，为源代码分析提供了统一的、与语言和客户端无关的连线接口。对我们的目的至关重要的是，针对流行编程语言的成熟语言服务器实现可以利用检测到的包管理器的既定约定，结合编译器生成的抽象语法树（AST）信息，来映射导入的类和函数的位置。LSP 生态系统传统上被 IDE 使用，它提供了一种稳健的、类型和作用域感知的方法来检索依赖代码，这是依赖纯语法解析的前辈方法无法实现的²。

OctoLong 数据获取。 图 2 展示了用于长代码上下文的 OctoLong 数据获取流水线的所有阶段。我们首先从 SEART Hub（Dabic 等，2024）获取信誉良好且积极维护的 Python 仓库³，这些仓库至少有 15 个 GitHub 星标和 5 个以上的贡献者。从中，我们只保留那些 声明依赖且 可安装的仓库，最终得到 12K 个仓库。保留仓库中的每个 Python 文件都成为一个候选种子：我们保留了通过 OpenCoder 默认代码质量过滤流水线的 92K 个种子（Huang 等，2025）。随后，我们在一个容器化的沙箱中为每个种子配置其仓库和依赖环境，并通过广度优先搜索（BFS）遍历依赖图。我们遍历到预设的 10 步深度，或者直到收集到 128K token 的代码（以先满足者为准），将每一步检索到的代码前置到上下文中。

每一跳包括一个 tree-sitter⁴ 查询，用于提取类和函数调用点，然后对每个调用点使用 jedi⁶ 语言服务器进行 GoToDeclaration 调用⁵；接着进行另一个 tree-sitter 查询，获取函数或类的边界并从目标文件中提取实现。我们确保从不重复类和函数。我们还会丢弃浅于 5 层的上下文以及跳转成功率低于 60% 的上下文。遵循此流程，我们最终获得了约 62 亿代码 token。

长上下文数据源比较。 我们的目标是测试我们的假设，即跨仓库代码上下文构成了一个非常好的长且富含依赖的数据源。为此，我们额外从各种传统来源获取了预处理的长上下文语料库，包括书籍、代码仓库、引用图和检索到的文档，并将它们与通过 OctoLong 流水线获取的数据进行比较，不设 token 长度限制，BFS 深度限制分别为 8、10 和 15。上下文长度分布的比较表 1 显示，我们的 OctoLong 流水线产生的上下文比任何现有来源的上下文都要长几个数量级。

此外，我们比较了长上下文数据源中依赖关系的密度、均匀性和显著性。这种比较至关重要，因为在缺乏依赖的长上下文上进行训练，相比于短上下文语言建模，带来的性能提升有限（Chen 等，2024；Deng 等，2025），同时却大幅增加了训练成本。我们使用修改后的 LongAttn（Wu 等，2025b）分数检查了表 1 中的所有长上下文语料库（公式如下）。具体来说，我们使用 Phi3 模型的第一个注意力层（Microsoft，2024）⁷ 来计算最后 2K 查询 token 对前缀中最近的八分之一、四分之一和二分之一 (n-2)K token 键的平均注意力质量 M。我们按如下方式取平均（在表 1 中记为 Dep. Mean）：

𝜇_Dep. = (1/6K) * Σ_{j=1}^{3} Σ_{q=(n-2)K+1}^{nK} Σ_{i=b_j}^{(n-2)K} M_{i,q}

其中 b_j = (n-2)K - c_j + 1，c_j = (n-2)K / 2^j，j ∈ {1, 2, 3}。

我们还跟踪最后 2K token 分配给前四个 sink 位置的平均注意力质量比例（表 1 中的 Sink Prop.）。这些指标共同测试了数据引起的“丢失中间”模式（Salvatore 等，2025；Liu 等，2024b），即人类展示的近因性（Baddeley 和 Hitch，1993）和首因性（Asch，1946）偏见溢出到数据分布中。表 1 的 LongAttn 部分表明，与其他长上下文数据源相比，OctoLong 数据表现出明显更低的 sink 集中度，以及显著较低的“丢失中间”（即更高的 Dep. Mean）模式发生率。

4 OctoLong-Instruct 模型

我们分两个阶段训练我们的 OctoLong-Instruct 模型：1 上下文扩展/长上下文微调（LCFT）阶段，随后是 2 监督微调（SFT）阶段，即指令微调。

中期训练数据。 为了彻底验证我们在第 1 节中陈述的假设，我们寻求进行约 500 亿 token 的现实大规模 LCFT 阶段。我们如第 3 节所述获取了约 62 亿 token 的 OctoLong 数据，并将其与各种传统的短和长上下文中期训练数据源混合。我们的辅助数据混合涵盖了 ProLong（Gao 等，2025c）语料库的类别。我们将长度限制设置为 128K token，应用了仅限英语的过滤器（Fedorova 等，2026），并进行了 MinHash 去重（Broder，1997）。表 2 比较了我们的 LCFT 语料库与一个规模匹配但比例忠实复制的 ProLong 语料库的类别组成。

SFT 数据。 我们编译了一个约 100 亿 token 的 SFT 混合集，用于微调我们所有的模型（包括消融变体）。尽管一些长上下文基准测试支持基础模型评估（Hsieh 等，2024；Yen 等，2025；Kuratov 等，2024），但出于实际原因，我们选择进行 SFT：大多数与用户和行业相关的长上下文基准测试需要指令遵循、结构化输出和/或多轮交互。虽然早期的工作表明，在 LCFT 之后进行短上下文 SFT 足以训练出可靠的长上下文 LM（Gao 等，2025c；Zhao 等，2024a），但最近的证据表明，专门的长序列对齐对于在生成和推理繁重的长上下文任务中解锁有竞争力的性能至关重要。因此，我们的 SFT 混合集涵盖了广泛的领域、上下文长度和交互轮次分布，并接受了与我们的 LCFT 数据相同的过滤流水线。我们在附录 B 中提供了最终 LCFT 和 SFT 混合集中数据集的详细描述和来源。

训练配置。 所有 OctoLong 模型均源自大小从 600M 到 14B 参数的 Qwen3 稠密基础模型。我们的 LCFT 阶段采用 ABF RoPE 缩放（Xiong 等，2024），我们将基础频率从 Qwen3 默认的 1M 提高到 10M，同时将其上下文长度从 32K 扩展到 128K token。我们决定不使用多阶段上下文扩展设置，因为我们的探索性运行表明单阶段设置不会产生性能损失。尽管我们试图通过在中期训练混合中混合短和长上下文数据来减轻短输入上的性能回归，但短输入回归仍然可能持续存在。因此，我们遵循行业实践，对 LCFT 前后的检查点进行模型合并，获得了 OctoLong-Base 系列。随后，我们使用修改后的 RoPE 频率和上下文长度进行 SFT，获得了 OctoLong-Instruct 系列。图 3 显示了两个训练阶段的损失曲线。

我们所有的训练运行都使用修改版的 Swift 框架，利用 DeepSpeed-Ulysses 序列并行和 Liger kernel 优化来促进高效的长序列训练。我们使用最佳适应递减方案将训练样本打包到 128K 上下文中，以实现最大效率⁹。我们采用 AdamW 优化器，峰值学习率为 1e-5，并使用 WSD 调度器以确保恢复友好性，同时采用 5% 的预热以确保平滑的持续训练。表 5 详细说明了我们 LCFT 和 SFT 训练阶段的所有训练参数。

5 结果与讨论

我们将我们的 OctoLong-Instruct 系列模型与 18 个支持至少 64K token 上下文的开源权重基线进行了比较，涵盖了一系列长上下文能力评估和短上下文回归测试。我们还进行了三个关键的消融实验：1 在 LCFT 期间用 ProLong 控制语料库替换 OctoLong 数据（称为 -Cross-Repo Code），2 在 SFT 阶段之前跳过模型合并（称为 -Model Merging），3 跳过 LCFT 并直接在我们的 SFT 混合集上进行微调（称为 -Context Extension）。我们跳过了平均超过 128K token 的基准测试子集，以确保结果的忠实性。在所有推理运行中，我们使用核采样进行解码，p 设为 0.95，温度为 0.6，token 预算为 2K。

RQ1：OctoLong 是否提高了长上下文编程性能？
在对 OctoLong 最“内在”的评估中，我们测试了使用跨仓库上下文进行训练是否能在长代码输入上提高模型的召回率和状态跟踪能力，在这些输入中，相关信息出现在一系列跨度大小和分散设置中（Goldman 等，2024）。

  • LooGLE V2： 我们利用 LooGLE V2 的代码子集。这包含测试仓库级别两个调用点之间高分散调用堆栈依赖跟踪的 MCQ Call Graph 任务，以及要求模型检测两个仓库快照之间多文件更改的 Version Control 字符串相似性任务。
  • LongCodeQa： 我们还使用来自 LongCodeQA 的 64K 和 128K 子集的 MCQ 任务测试模型在仓库级别上下文中的纯召回能力。
  • RepoQa： 纯召回测试可能会因模型使用表面匹配而受到影响。因此，我们通过在 RepoQA 的 64K 和 128K 子集上评估模型，来审计模型根据自然语言描述查询从仓库级别上下文中召回“针”函数实现的能力。我们在召回的实现上使用 0.8 的 BLEU 分数作为接受阈值。

结果。 表 3 显示，OctoLong-Instruct 系列在长上下文代码状态跟踪和检索场景中表现出持续强劲的性能，包括词汇重叠较低的情况。这种模式适用于所有大小类别和序列长度。比较我们使用 OctoLong 数据训练和不使用 OctoLong 数据训练的 8B 变体，我们观察到富含依赖的跨仓库代码数据对性能的巨大贡献。我们观察到 OctoLong 跨仓库上下文在 Call Graph 任务上带来了特别显著的收益。该任务上较差的基线分数支持了先前的发现，即高分散长上下文构成了 LM 特别具有挑战性的场景。我们的模型在 64K 和 128K 设置之间表现出最小的性能回归，这对于处于其支持上下文能力边缘的模型来说是罕见的。最后，我们看到 OctoLong 数据的绩效增强价值超出了其领域的迹象。具体来说，尽管我们将数据收集限制在 Python 上下文，但我们在涵盖五种编程语言的 RepoQA 任务上观察到了强劲的平均表现。

RQ2：OctoLong 是否增强了通用领域的长上下文性能？
为了测试我们的 OctoLong 配方在代码之外的迁移效果，我们运行了各种基准测试，以测试“通用领域”中的上下文学习、检索、状态跟踪和综合能力。

  • LongBench V2： 我们使用 LongBench V2 的单文档和多文档 QA MCQ 子集评估集中和分散的通用领域检索。我们还测试了 Long ICL MCQ 子集的性能，作为长输入上上下文学习的衡量标准。此外，我们使用 Long Dialog MCQ 子集对模型的会话状态跟踪能力进行压力测试。我们在所有子集的 32K–128K（中等）长度部分进行基准测试。
  • OpenAi Mrcr： 我们利用 OpenAI MRCR 发布的 64K 和 128K 限制长度子集的 2-Needle 多轮共指解析任务。这个字符串相似性任务要求模型召回关于多轮聊天的查询的哈希答案内容。它代表了在具有多个干扰项的高分散设置中对模型召回能力的现实评估。
  • Aa-Lcr： 长上下文评估主要围绕直接和间接检索，然而不管多么具有挑战性，这都可能隐藏模型在自由形式生成中推理能力的巨大回归。为了杜绝这种可能性，我们在 AA-LCR 上进行评估，这是一个行业标准测试，要求模型在各种领域的上下文文档上进行多跳推理和推断。评分依赖于使用 Qwen3-235B-A22B-Instruct-2507 判别模型的 pass@1 答案匹配。

结果。 表 3 总结了回答我们 RQ2 的结果。我们的 LCFT 数据混合在通用领域长上下文任务上全面带来了强劲的结果。特别是，OctoLong-Instruct 系列在与 -Cross-Repo Code 消融的比较中表现优异，突显了在跨仓库上下文上进行训练如何正向迁移到通用领域。我们的 OctoLong-Instruct-4B 与强大的经过上下文扩展和 RL 后训练的 Qwen3 模型 Qwen3-4B-Instruct-2507 相比具有竞争力，同时在所有其他大小类别中占据主导地位。令人鼓舞的是，我们的配方在与行业相关的 MRCR 和 AA-LCR 基准测试中表现出色，这表明我们训练的富含依赖的数据在最具挑战性、充满干扰项、高分散和推理密集的设置中产生了切实的收益。我们还注意到模型合并在通用领域的不可忽视的贡献。

RQ3：OctoLong 的收益是否延伸到下游智能体用例？

  • Bfcl V3： 我们在 BFCL V3 的实时、非实时和多轮拆分上评估模型。该基准测试在单轮和多轮工具调用中对模型进行压力测试，同时还评估了对常见病理场景（如缺失参数和实时 API 变更）的适应能力。
  • 𝜏2-Bench： 我们进一步报告了 𝜏2-Bench 的 pass@1 分数，这是一个具有挑战性的工具调用基准测试，由未充分指定的查询组成，这些查询提供大量特定领域的工具，并根据环境级数据库中的状态等效性进行评分。除了多轮能力外，该基准测试还要求长上下文多步支持，每条轨迹有多个模拟用户轮次¹⁰。此外，评估还具有双重控制场景，即模拟用户对共享环境状态进行并发更改，从而构成了长程用户-LM 合作的现实验证。

RQ4：OctoLong 是否保留了短上下文编程和 API 使用能力？
最后，我们求助于短上下文执行验证的代码生成测试，以分析在长跨仓库数据上训练对模型在短上下文编程任务上性能的影响。在所有基准测试中，我们报告了模型在采样组大小 N=50 上的 pass@{1,5,10,25}。

  • LiveCodeBench V6： 我们通过获取 LiveCodeBench V6 的代码评判问题来对算法编程能力进行基准测试¹¹。
  • BigCodeBench Hard： OctoLong 流水线通常将函数和类调用点及其引用实现一起放在同一上下文中。先前的工作表明这可以改善 API 使用。我们通过 BigCodeBench Instruct Hard 直接测试这一点。

结果。 表 4 显示 OctoLong-Instruct 模型在所有大小类别的短长度代码生成上产生了强劲的结果。我们的上下文扩展在很大程度上保留了短长度编程能力。我们的模型超越了几种在后训练中针对代码生成进行过优化的基线，同时在较低的采样预算上与经过后训练的 Qwen3-8B 模型具有竞争力，并在较高的预算上轻松超越它。这种差异可能源于 RL 后训练期间的分布锐化。-Cross-Repo Code 消融结果还分离了 OctoLong 数据的特定收益，特别是对于 API 使用任务。-Model Merging 消融表明，与 LCFT 前的检查点合并对于保留短上下文性能是有效的。最后，Llama 3.1、ProLong 和 UltraLong 的比较结果表明，在已经后训练的模型上进行上下文扩展的常见做法是次优的，可能导致短上下文性能的回归。

6 结论

在这项工作中，我们提出了 OctoLong，这是一项通过跨仓库边界递归检索代码来构建富含依赖的长上下文语料库的努力。我们详细描述了一个流水线，它在依赖配置的容器化环境中协同运行 AST 查询和语言服务器后端，以尽可能获取被引用的类和函数实现。我们使用这个流水线整理了约 62 亿 token 的高质量、富含依赖的上下文，长度上限为 128K token。随后，我们将我们的跨仓库上下文与从传统长上下文来源获取的数据混合，编译出约 500 亿 token 的 OctoLong-LCFT 语料库。该语料库与我们的约 100 亿 token 智能体和指令微调数据整理混合集 OctoLong-SFT 一起，使我们能够开发出 OctoLong-Instruct 系列 128K 上下文模型（源自 Qwen3），参数量在 600M 到 14B 之间。广泛的实验和消融表明，使用富含依赖的代码数据进行上下文扩展可以改善上下文检索、状态跟踪和仓库级代码理解，同时解锁卓越的智能体能力和 API 使用。我们希望我们的工作能帮助模型支持更大的上下文长度，同时最大限度地减少上下文衰减，使它们能够应对测试时训练和递归自我改进等新兴挑战。

局限性

我们通过省略低资源语言数据、将模型大小限制在 14B 参数并将上下文长度限制在 128K token 来简化训练运行。这些中的每一项都代表了与大多数前沿 LM 当前操作模式的重大偏离。然而，有重要迹象表明 OctoLong 应该在这些轴向上很好地迁移。首先，先前构建长上下文的方法由于多语言长上下文数据的稀缺性而省略了这些数据，但仍然能很好地泛化到此类设置。其次，我们在第 5 节中的实验详细说明了 OctoLong-Instruct 模型如何随着大小的增加在更长的上下文上变得越来越熟练，遵循现有文献中描述的趋势。第三，我们在第 3 节中的分析证明了 OctoLong 如何在不牺牲依赖密度或显著性的情况下获取数百万 token 的代码上下文。

最后，我们注意到 OctoLong 中的递归依赖检索仅限于语言服务器后端可以轻松利用包管理器约定来定位实现的语言内代码。我们的流水线可能无法解释复杂代码库中的重要依赖，这些代码库包含调用代码通过应用程序二进制接口（ABI）或外部函数接口（FFI）与之交互的以不同语言编译的子例程。处理此类情况需要多语言静态分析和控制流跟踪，这是一个活跃的研究领域。
