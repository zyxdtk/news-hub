摘要
答案准确性对于LLM数据代理而言是一个不充分的可靠性信号。在结构化数据任务中，基准正确的答案可能是由无效的轨迹生成的。本文引入了“轨迹完整性”，这是一种部署可靠性标准，用于评估答案背后记录的计算是否是显式的、可执行的、模式有效的、算子忠实的、可重放的、答案一致的以及可审计的。我们将“结构鸿沟”确定为使轨迹完整性成为必要的部署失败模式：自然语言推理和自由格式的理由无法可靠地指定真实世界系统所需的算子级程序。我们通过执行契约将轨迹完整性操作化，这是一种结构化工件，将用户意图与模式元素、算子计划、假设、可执行查询、验证状态和最终答案链接绑定在一起。我们还引入了CAIT（正确答案/无效轨迹）率，用于衡量仅基于答案的评估将计算上不受支持的输出计为成功的频率。在BIRD Mini-Dev上的实证演示中，直接SQL、操作摘要+SQL和契约优先SQL分别实现了20%、22%和24%的答案准确率，而它们的轨迹完整性通过率分别为39%、43%和40%，其CAIT率仍然高达55%、59.1%和45.8%，这表明答案准确性、轨迹有效性和静默失败风险是不同的评估信号。因此，对于真实世界的LLM数据代理，评估不应仅仅基于其输出是否匹配参考答案，还应基于这些输出是否有可审计的计算作为支撑。
1
引言
LLM数据代理正在成为操作数据的接口。它们检查模式、生成SQL、调用工具、执行查询、总结结果，并向分析师、操作员、临床医生、审计人员和客户展示结论。这使得数据库、电子表格、日志、记录和企业分析系统更容易被查询，但也改变了可靠性问题。问题不再仅仅是系统是否返回了预期值。数据代理可能会返回一个看似合理或基准正确的答案，而该答案背后的计算却应用了错误的过滤器、连接、聚合、时间窗口、分组键或模式绑定。
考虑一位业务分析师的提问：
上个季度（不包括试用账户）每个活跃客户平均收入最高的地区是哪个？
系统可能会返回一个充满自信的地区名称，同时却静默地计算总收入而不是平均收入，包含了试用账户，按销售办事处而不是客户地区分组，使用日历季度而不是财季，或者通过脆弱的名称字段而不是稳定的标识符连接客户和收入记录。仅基于答案的评估无法区分忠实的计算和偶然的成功。部署团队不仅需要知道生成了什么答案，还需要知道实际执行了什么计算。
这是一个部署问题，而不仅仅是一个基准问题。在操作工作流中，答案通常由无法重构查询的人使用：BI用户、合规审查员、数据工程师或领域专家。这些用户不仅需要流畅的解释，还需要一个可检查的工件，展示哪些模式元素、过滤器、连接、聚合、假设和执行结果支持该答案。
本文认为，真实世界的LLM数据代理需要一个将计算轨迹视为一等对象的可靠性标准。我们将此标准称为轨迹完整性。当答案背后记录的计算是显式的、可执行的、模式有效的、算子忠实的、可重放的、答案一致的和可审计的时，轨迹就具有完整性。这一主张故意比一般的可信度范围更窄。轨迹完整性并不证明底层数据是完整的、公平的或适合下游决策的。它解决了一个特定的部署风险：答案正确性不足以证明系统执行了用户请求的计算。
对轨迹级评估的需求源于更广泛的“结构鸿沟”。语言模型将推理表达为标记序列，而结构化数据任务需要具有明确定义语义的算子级程序。一个有效的答案可能依赖于投影、过滤、连接、分组、聚合、排序、排名、时间约束和模式绑定。Text-to-SQL和表格推理基准暴露了这种压力，因为成功取决于将自然语言请求映射到可执行的计算，而不仅仅是产生看似合理的解释

核心的隐藏失败案例是正确答案伴随无效轨迹。这种输出在仅基于答案的评估中获得分数，但它不是一个可靠的数据代理响应，因为记录的计算不支持该答案。我们将这种情况称为正确答案/无效轨迹，并用CAIT率来衡量它。CAIT问道：在系统答对的问题中，有多少比例是由无效计算支持的？高CAIT率意味着仅基于答案的评估正在将计算上不受支持的输出计为成功。
这项工作为那个隐藏象限开发了词汇、工件和测量协议。结构鸿沟命名了自然语言推理无法指定算子级计算的部署失败模式，轨迹完整性给出了可靠性标准，执行契约使该标准可操作，隔离原则提供了默认的规划准则，而CAIT率将正确答案/无效轨迹的失败转化为一个可以在系统和数据集之间报告的指标。
我们包含了一个概念验证，以表明这种部署风险出现在可测量的系统行为中。在100个BIRD Mini-Dev示例上，我们比较了直接SQL、操作摘要+SQL和契约优先SQL。这三种方法分别实现了20.0%、22.0%和24.0%的答案准确率，而它们的轨迹完整性通过率分别为39.0%、43.0%和40.0%。它们的CAIT率仍然很高，分别为55.0%、59.1%和45.8%。这些结果表明，答案准确性、轨迹有效性和静默失败风险是不同的信号，部署团队应该共同监控。预期的贡献是为LLM数据代理提供一个实用的评估框架：如果LLM数据代理要作为操作数据的可靠接口，对它们的评估不仅应基于它们返回了什么答案，还应基于该答案背后的计算是否可以被检查、重放和信任。
2
轨迹完整性问题
2.1
算子承诺与结构鸿沟
结构化数据问题需要操作承诺：包括哪些记录，对齐哪些实体，计算哪些度量，哪个分组定义了比较，使用哪个时间窗口，以及哪个排序决定了最高级。如果用户要求每个活跃客户的平均收入，计算必须定义分子和分母。如果用户要求上个季度，计算必须解析出一个时间间隔。如果用户要求地区级别的结果，计算必须绑定预期的地区字段，而不是表面相似的位置属性。
我们将结构鸿沟定义为自然语言推理与算子级计算之间的不匹配。自然语言表达了意图，但它没有强制执行结构化数据答案所需的离散操作：过滤、连接、分组、聚合、排名、时间限制和模式绑定。模型可以合理地陈述预期的操作，同时却省略了连接，将平均值更改为总和，将过滤器应用于错误的表，或者按表面形式相似但语义不同的字段分组。在部署的数据代理中，这样的错误是可靠性失败，因为答案不再有计算的支持。
这种框架是表征性的，而不是声称语言模型缺乏一般推理能力。有效的结构化数据答案必须将用户请求绑定到可执行的计算。Text-to-SQL任务使这一点变得可见，因为目标输出是算子级表示
(
Zhong et al., 2017
;
Yu et al., 2018
)
。表格推理和事实验证任务在不太严格的关系设置中显示了同样的压力
(
Pasupat and Liang, 2015
;
Chen et al., 2019
;
Chen et al., 2020
)
。
2.2
操作数据工作流中的静默失败
静默的结构化数据失败是危险的，因为它们看起来像正常的完成。一个生成SQL的代理可能会产生一个执行无误但按错误键分组的查询。一个使用工具的代理可能会调用正确的数据库，但省略了所需的排除过滤器。理由可能会说排除了试用账户，而执行的查询却包含了它们。在每种情况下，接口都返回一个答案，而让用户几乎没有理由怀疑计算已经偏离了请求。
这些失败出现在普通的数据代理工作流中。在商业智能中，当决策取决于每位客户的收入时，模型可能会报告总收入。在合规报告中，它可能会计算所有交易，而不是受监管司法管辖区内的交易。在临床分析中，它可能会使用就诊日期而不是诊断日期来定义队列。部署的后果是，最终答案作为可靠性工件是不够的：计算必须可供检查。
2.3
CAIT失败模式
答案准确性将几种可靠性状态合并为一个结果。具有有效轨迹的正确答案是忠实的成功。具有无效轨迹的错误答案是可见的结构性失败。具有有效轨迹的错误答案可能反映了数据问题、执行问题、用户请求中的歧义，或者基准参考与另一种可辩护的解释之间的不匹配。与部署最相关的隐藏案例是具有无效轨迹的正确答案。尽管记录的计算不支持该答案，但这种输出在仅基于答案的评估中仍会获得分数。
我们将这种隐藏的成功案例称为正确答案/无效轨迹，并用CAIT率来衡量它。CAIT问道：在系统答对的问题中，有多少比例是由无效计算支持的？高CAIT率意味着仅基于答案的评估通过将计算上不受支持的输出计为成功而夸大了可靠性。执行成功也是不够的，因为查询可以运行但仍然回答错误的问题。轨迹完整性解决了一个更狭窄的操作问题：记录的计算是否是显式的、可执行的、模式有效的、算子忠实的、可重放的、答案一致的和可审计的。
3
轨迹完整性作为审计契约
3.1
轨迹完整性的定义
轨迹完整性是指结构化数据答案背后记录的轨迹以一种可以检查、重放和审计的形式指定计算的属性。相关的轨迹不是私有的模型推理，也不是冗长的自然语言解释。它是决定答案是否有计算支持的系统记录：模式元素、过滤器、连接、分组、聚合、排序、假设、执行的查询或程序，以及最终答案的链接。当轨迹满足表1中的维度时，它就通过了完整性。这些维度比完全的语义正确性要窄，因为它们定义了数据代理答案可被视为有其记录的计算支持的最低条件。这种分离使得CAIT率成为必要：当轨迹仍然无效时，答案可能与参考相匹配。

3.2
执行契约
执行契约是一个紧凑的工件，用于在执行之前或伴随执行记录预期的计算。它将用户意图与模式元素、算子计划、假设、执行查询、验证状态和最终答案绑定在一起。该契约不是冗长的解释，也不能替代确定性执行。它的作用是使代理的计算承诺对验证者、审计人员和下游答案生成器可用。

3.3
隔离原则
隔离原则指出，默认情况下，LLM数据代理应在访问值级别数据之前指定其预期的计算。其动机是，值访问可以让模型回顾性地完成一个未充分指定的计划，并对其从未承诺的计算产生合理的解释。从用户请求、模式、元数据和策略上下文进行规划，迫使代理在看到可能使无效计算看起来成功的结果值之前陈述所需的操作。该原则不应作为僵化的禁止访问规则来应用。探索性摘要、异常值检测、分析、去重和依赖于值的阈值处理可能需要值检查。在这些情况下，契约应记录为什么需要值访问，授予了什么访问权限，以及它如何改变了计划。因此，隔离的部署价值在于它默认将规范与执行分开，并使偏离该分离的行为变得可审计。

4
实证演示：测量隐藏的轨迹失败
我们使用BIRD Mini-Dev来测试答案正确性和轨迹有效性在现实的数据库接地设置中是否会产生分歧。BIRD很有用，因为它比小型的合成表任务更强调更大和更异构的数据库
(
Li et al., 2023
)
。本概念验证使用BIRD Mini-Dev，因为本研究关注的是更接近操作分析的数据代理行为。
4.1
研究设计
概念验证使用100个BIRD Mini-Dev示例。对于每个示例，我们执行黄金SQL以获得参考结果，针对同一数据库执行生成的SQL，并将生成的轨迹与规范化的黄金轨迹进行比较。主要模型是claude-haiku-4-5，温度为0.0。我们比较了三种提示条件。直接SQL根据问题和模式生成查询。操作摘要+SQL在生成SQL之前编写预期操作的简明自然语言摘要。契约优先SQL在生成SQL之前发出结构化的执行契约。所有三个条件都接收相同的问题和模式上下文，并使用相同的执行器和轨迹验证器进行评估。

验证器倾向于可检查的失败规则，而不是完全的语义等价。当轨迹相对于规范化的黄金轨迹包含严重的不匹配时，或者对于契约优先SQL，当契约与生成的SQL之间存在不匹配时，轨迹未通过完整性。严重失败包括错误或缺失的聚合、缺失的过滤器、缺失的连接、错误的连接路径、错误的分组键、错误的排序或限制、无效的模式引用、不可执行的SQL、答案-轨迹不匹配以及契约-SQL不匹配。当检查器无法证明等价性时，它可能会过度标记语义上有效的重写。然而，对于本研究中的诊断问题来说，这种局限性是可以接受的：最终答案正确性和轨迹有效性在实践中是否分离。
4.3
结果
在三种条件下，答案准确率从20.0%到24.0%不等，但许多正确答案并没有得到有效轨迹的支持。直接SQL获得了20.0%的答案准确率、39.0%的轨迹完整性通过率和55.0%的CAIT率。操作摘要+SQL获得了22.0%的答案准确率，最高的轨迹完整性通过率43.0%，以及最高的CAIT率59.1%。契约优先SQL获得了最高的答案准确率24.0%和最低的CAIT率45.8%，但其轨迹完整性通过率为40.0%，低于操作摘要+SQL。因此，该结果作为证据表明，答案准确性、轨迹有效性和静默失败风险是不同的部署信号。表2显示了主要结果。
图2可视化了同样的分离。操作摘要+SQL具有最高的轨迹完整性通过率，而契约优先SQL具有最低的CAIT率。这对部署很重要，因为系统可能在一个可靠性信号下看起来更好，而在另一个信号下更差。因此，生产评估应同时报告答案准确率和轨迹级指标，而不是将执行准确性作为唯一的成功标准。
图3将结果显示为答案-轨迹象限。左下角的单元格是CAIT单元格：正确答案，无效轨迹。直接SQL有11个，操作摘要+SQL有13个，契约优先SQL有11个这样的情况。在这里，尽管记录的计算无效，但仅基于答案的评估仍将其计为成功。这些矩阵使论文的核心实证点变得可见：表面上成功的输出并不是同质的。
在300个方法-示例预测中，有51个查询未执行，占所有预测的17.0%。这些可见的失败解释了轨迹完整性失败质量的一部分。更重要的部署经验是，验证器还定位了仅基于答案的评估所隐藏的失败：错误的连接或聚合、与生成的SQL不一致的操作摘要，以及缺失过滤器或契约-查询不匹配的契约优先输出。这就是轨迹完整性的实用价值：失败可以被诊断为模式有效性问题、算子不匹配、契约-查询不一致或答案-轨迹不一致，而不是消失在流畅的答案背后。
5
部署影响和结论
轨迹完整性是一个部署标准，而不仅仅是一个评估指标。生产数据代理可以将执行契约与答案一起存储，在执行前验证契约，当答案和轨迹不一致时发出警报，并将失败的轨迹重用为回归测试。同一个工件可以支持分析师审查、合规审查、调试、事件响应和模式漂移监控。
概念验证表明，答案准确率、轨迹完整性通过率和CAIT率衡量的不是同一属性。重要的结果不是契约优先提示解决了Text-to-SQL，而是表面上正确的答案可能由无效的计算支持，而仅基于答案的评估没有暴露这种风险。
因此，LLM数据代理不仅应该回答结构化数据问题。它们应该留下可以被检查、重放、质疑并在失败时转化为回归对象的计算。对于企业分析、合规报告、财务分析、医疗保健分析以及其他结构化数据答案影响决策的设置，这种区别是一个有时能得到正确答案的系统与一个能够展示为什么其答案应该被信任的系统之间的区别。
6
局限性
本研究是一个愿景，包含一个范围有限的概念验证，用于测量LLM数据代理中的答案-轨迹分歧，而不是对模型家族或提示策略的全面基准测试。实验使用了100个分层的BIRD Mini-Dev示例和一个模型Claude Haiku 4.5，在固定的提示和执行设置下。因此，绝对比率应被解释为答案正确性、轨迹有效性和静默失败风险在实践中可以分离的证据，而不是特定模型或提示格式的稳定排名。
轨迹验证器使用确定性的算子级检查。这种设计使评估具有可重复性和可检查性：轨迹失败可归因于具体问题，如缺失连接、错误聚合、缺失过滤器、无效模式引用、错误分组键、错误排序或限制操作、答案-轨迹不匹配以及契约-SQL不匹配。同时，结构验证不是完全的语义等价检查。当检查器无法证明与规范化黄金轨迹的等价性时，一些语义上有效的SQL重写可能会受到惩罚，而且BIRD Mini-Dev可以接受同一问题的多个有效SQL程序。由于这个原因，CAIT率应被解读为计算支持的诊断信号，而不是对每个单独查询的最终语义判断。
执行失败也占了轨迹完整性失败质量的一个有意义的份额。这些失败是部署的Text-to-SQL可靠性的一部分，但它们与CAIT针对的静默失败案例不同。论文核心主张的最有力证据来自执行成功且仅基于答案的评估仍然未能揭示记录的计算无效的情况。
7
伦理考量
本研究使用现有的Text-to-SQL基准BIRD Mini-Dev，不收集新的人类受试者数据。评估仅针对基准问题、基准数据库模式、生成的SQL输出、执行结果和派生的轨迹工件进行。研究中未使用任何私人用户数据、交互式用户日志或新收集的个人身份信息。
轨迹完整性的动机既是伦理上的，也是技术上的。在结构化数据设置中，流畅或基准正确的答案可能掩盖无效的计算。如果此类输出用于现实世界的决策支持设置中，用户可能会信任实际上不受底层查询或数据转换支持的答案。轨迹级评估可以通过使连接、过滤器、聚合、假设、执行结果和答案-轨迹一致性可供检查来降低这种风险。同时，轨迹工件产生了自身的治理责任。在部署的系统中，执行契约和轨迹日志可能会暴露敏感细节。因此，应像对待其他操作数据工件一样小心保护它们。存储轨迹的系统应应用适当的访问控制、保留限制、修订策略和审计日志。轨迹完整性不应被解释为暴露隐藏模型推理或不必要的敏感值的理由；拟议的契约旨在记录计算承诺，而不是私有的思维链或不受限制的数据快照。
轨迹完整性还应被理解为支持负责任审查的机制，而不是取代领域判断。有效的轨迹可以使系统的计算更容易被检查、重放和质疑，但它本身并不能确定底层数据是否足以用于下游决策。在高风险设置中，因此应将轨迹工件与现有的数据治理程序、人工审查和机构监督一起使用。
