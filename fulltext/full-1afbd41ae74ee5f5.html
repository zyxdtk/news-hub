Jev 等决策模型不解释答案，上下文成了你的问题

📅 2026-11-08 📄 VentureBeat AI 🔗 原文链接

原标题：Decision models like Jev don’t explain their answers. That makes context your problem

中文摘要： 决策模型（如 TypeSafe AI 的 Jev、Cloudflare 的 Clef、OpenAI 的 Decisions API）跳过冗长文本生成，直接返回 JSON 结构化输出和置信概率，实现低延迟并节省 token。但这种“系统 1”思维不包含推理轨迹，模型无法解释其答案，可能产生误导。这要求 AI 构建者掌握上下文设计技能，提前为模型打包所有相关信息。决策模型适用于 LLM 裁判、工单分类等场景，是 LLM 技术的重大升级，但可解释性的缺失也带来了技术债务风险。

决策模型如今炙手可热：互联网上热议 Jev（来自 TypeSafe AI）、Cloudflare 的 Clef 以及 OpenAI 的 Decisions API。这些模型通过跳过冗长的文本生成，返回 JSON 格式的结构化输出以及置信概率，从而实现低延迟。

软件开发人员非常喜欢这种确定性，因为它让结构化数据可以轻松集成到应用程序中。提出一个问题，就能得到一个固定的 JSON，可以使用库来提取；无需复杂的文本解析或格式理解。

一个有意识的选择

在底层，每个现代大语言模型（LLM）都遵循相同的 transformer 编码器-解码器架构。提示词被摄取并编码到较小的维度，然后解包以一次生成一个 token，这些 token 被统一组合以生成输出文本。

拥有数十亿参数的模型在数万亿行文本上进行训练，学习复杂的语言模式，以确保生成的文本遵循模拟人类思维和对话的模式。冗长的文本输出通常包含模型得出结论所使用的推理过程。这非常有用，以至于出现了一个单独的模型类别——推理模型，专注于创建专门的推理轨迹来支持决策。

但对于决策模型，我们做出了一个有意识的选择：不包含冗长的推理轨迹，直接给出答案。这种所谓的“系统 1”思维在特定场景中非常有用，因为我们可以更快地获得答案，并显著节省 token。然而，我们通常最终会在系统中积累技术债务。因此，我们实际上失去了让 LLM 如此强大的核心能力。

让我们看一个例子。我通过 OpenRouter 接口向不同类型的模型提问：“今天会下雨吗？”传统 LLM 会使用推理来理解什么是必要的以及存在哪些限制，然后再做出预测。

现在，如果你向 Jev 这样的决策模型提出同样的问题，它会以数据结构 "noul"（以伟大的瑞士数学家和物理学家丹尼尔·伯努利命名）返回响应。

Noul 只携带一个值：true 或 false。因此，模型不做任何解释，就会给出一个通用的响应：true 或 false。这可能会产生极大的误导，尤其是当我们使用模型回答关键问题时。

这并不意味着决策模型没有用处或不正确。这只是意味着这些模型不像传统 LLM 那样可解释。这将一项关键责任转移到了 AI 构建者和软件开发人员身上：如果模型不会为你推理，你就必须提前为它推理。这正是上下文设计成为 AI 构建者所能掌握的最重要技能的原因。

通过上下文设计，你的目标是将所有相关信息打包到上下文或状态中，以便模型做出明智的决策。使用传统的 LLM 驱动的智能体，你可以提出模糊的问题，模型通常会提出澄清性的问题，或者详细解释它所做的假设。

而对于决策模型，则没有这样的机制。模型接受你给它的任何上下文，将其与其训练内容进行映射，并返回结构化输出——通常是一个单一值。你可以利用这个值和概率在应用程序中编写适当的操作。然而，由于没有决策轨迹或日志，因此无法完全清楚地了解模型为何做出其决策。

决策模型在某些场景中大放异彩；例如，LLM 充当裁判（LLM-as-a-judge），即将聊天机器人的答案与预先定义的真实“黄金”答案进行比较。另一个领域是支持工单分类和类别映射。支持工单通常包含冗长的文本，需要理解这些文本才能将其映射到适当的类别或团队。

时间会告诉我们还会出现哪些其他重要用例。但有一点是肯定的：决策模型是 LLM 丰富发展历程中的一次重大技术升级。
