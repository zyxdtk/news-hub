原标题：TokTier: Exact Stateful Tokenization for Agentic LLM Serving

中文摘要： 本文提出了TokTier，一种面向智能体大模型服务的精确有状态分词系统。针对编程智能体流量中频繁的小文本追加和罕见的大上下文重建这两种工作负载模式，TokTier设计了双路径执行策略：对于会话延续，通过增量边界修复机制在稳定边界处安全拼接，避免全量重分词；对于无前缀的初始化请求，将GPT系列预分词重构为局部运行规则并在GPU上执行精确BPE编码。实验表明，该系统在保证与参考分词器零偏差的前提下，显著降低了首字时间（TTFT），大幅提升了系统吞吐量。

TokTier：面向智能体大模型服务的精确有状态分词 Zhenyu Zhang 亚利桑那州立大学 坦佩 亚利桑那州 美国 zzhan641@asu.edu 和 Zhichao Cao 亚利桑那州立大学 坦佩 亚利桑那州 美国 Zhichao.Cao@asu.edu

摘要。 大模型服务系统会缓存提示词的 KV 状态，但大多数前端在每次调用时仍会对完整的请求文本进行重新分词。这种不匹配对于编程智能体来说代价最为高昂，因为它们的会话会在追加少量工具结果后，反复提交长篇记录。复用先前的分词结果十分困难，因为即使是很短的追加，也可能改变前一个序列末尾附近的分词边界。在来自两个智能体生态系统的 153,951 次调用中，中位数的调用会追加约 1.4K 个字符，而仅有 1.0–3.6% 的调用会启动或重建会话。然而，这些调用携带的完整上下文可达数百万字符。在集群层面，聚合提示词缓存命中率为 94.1%，当其接近 0.99 时，在我们的组件测量中，分词占首字时间（TTFT）的比例从 10% 增长到了 64%。 我们提出了 TokTier，一种针对这种双模式工作负载的有状态分词服务。TokTier 强制执行一项契约：输出的 Token ID 始终与对请求文本进行完整参考分词的结果完全一致。对于会话延续，TokTier 会保留该会话先前的 Token 序列，对追加内容附近的一小段窗口进行重新分词，并且仅当逐请求检查发现稳定的预分词边界时，才接受此拼接。检查失败会触发更宽的窗口或完整的参考分词。对于没有可复用前缀的调用，TokTier 将 GPT 系列的正则表达式预分词分解为局部运行规则，并在 GPU 上执行精确的预分词和 BPE。一个采样的影子验证器会根据参考实现重新检查实时流量。 在 17 个生产级分词器系列中，我们的差异化测试活动包含了 1.50×10^10 次拆分检查、对 12.4 TB 真实文本语料库的全面扫描，以及超过 93,000 个重放的智能体步骤，所有这些均实现了零偏差。从 100K 到 3M 字符，增量修复耗时 0.5–1.1 毫秒，比 HF 分词快达 437 倍；在 1M 字符时，比最强的基于缓存的基线（即 GigaToken）在其最有利的完全预热模式下快 2.1 倍。GPU 完整分词在 0.87 毫秒内编码 1M 字符的请求，比 HF 分词快达 491 倍，在相同文本和协议下比先前发表的最快 CPU 方法快 23.4 倍。在接入 vLLM 的端到端测试中，TokTier 在高负载情况下将首字时间中位数降低了 16–34%，在记录的突发到达下将 P99 降低了 23%。在 50 毫秒 P99 目标下，一个 4 核修复池加一块 GPU 可维持 1,821 请求/秒的吞吐量，而 16 核无状态 CPU 前端在 40 请求/秒时即达到饱和。

1. 引言 编程智能体通过一系列模型调用进行工作。它读取文件、进行编辑、运行工具、观察结果，并决定下一步做什么 (Yao et al., 2023; Yang et al., 2024)。每次调用都携带会话记录，而每次工具结果都会在下一次调用发出前扩展该记录。一条用户指令可以扇出数十次调用。这些调用以机器节奏到达，记录在每一轮中不断增长。

图 1. 通过当今技术栈和通过 TokTier 的一个智能体轮次。该请求向先前轮次已分词的记录中追加了中位数约 1.4K 字符，而当今的前端会在前缀缓存发挥作用之前重新扫描完整上下文。TokTier 围绕追加内容修复会话延续，将罕见的初始化和重建路由到精确的 GPU 路径或参考 CPU 路径，并通过影子验证器对所有输出进行采样。延迟是在 1M 字符上下文下测量的 P50，两个粗体数字分别是每条路径在服务等效和扫描统计下测得的最佳单请求吞吐量，两者从不混用 (§5.3)。

这种访问模式暴露了当前服务栈中的不匹配。前缀缓存允许模型复用提示词未更改部分的 KV 状态，但前端仍在每次调用时将完整的请求文本转换为 Token ID。在我们测量的编程智能体流量中，集群级别的提示词缓存命中率为 94.1%。中位数调用向 86K 到 123K Token 的上下文中追加约 1.4K 字符。模型可能只处理未缓存的一小部分后缀，而分词器却扫描整个记录。当命中率接近 0.99 时，在我们的组件扫描中，分词占首字时间的比例从 10% 增长到 64% (§2)。

该工作负载具有两种截然不同的模式。大多数请求是会话延续。它们扩展了片刻前生成的 Token 序列的会话。在我们的追踪中，有一小部分（1.0–3.6%）不携带可复用的前缀。会话启动、压缩历史被重建，或者请求到达一个不持有会话状态的 Worker。此类调用很少见，但它们携带完整上下文并呈突发性到达。这两种模式要求不同的执行策略。增量修复应执行与新文本成比例的工作。完整分词应以较低的长尾延迟处理以前未见过的庞大上下文。

跨轮次复用 Token ID 比复用字节前缀更难。分词不具备可组合性。对于字符串 A 和 B，tok(A) || tok(B) 可能与 tok(A || B) 不同。当 B 到达时，预分词器可能会移动片段边界，随后 BPE 可能会在该片段内选择不同的合并。例如，“pipeline”一词内部的边界会将一个参考 Token 变成两个不同的 Token (§3.1)。固定的重叠启发式方法无法解决问题，因为某些分词器规则允许更改传播超过任何选定的半径。生产系统必须知道何时缓存的前缀可以安全拼接，并且必须在该条件无法满足时进行回退。

没有可复用前缀的调用带来了另一个问题。GPT 系列分词器从最左优先的正则匹配开始，随后是 BPE (Radford et al., 2019)。正则表达式在其通常形式下是串行的，因为每次匹配都从前一次匹配结束的地方开始。现有的 GPU 分词器通过简化此阶段或针对不同方案来获得并行性 (Kadamba and Jaisankar, 2026; You, 2025; Jawa, 2021)。Token ID 既是模型输入也是前缀缓存键，因此单个更改的 ID 就可能改变模型行为并悄无声息地使缓存复用失效。

我们围绕这两种模式和一项正确性契约设计了 TokTier。对于每个请求，输出的 ID 必须等同于冻结的参考分词器在完整文本上产生的 ID。TokTier 存储每个实时会话的 Token ID 和字节跨度。在会话追加时，它对新文本加上旧上下文的一小部分后缀进行重新分词。它比较新的和缓存的 Token 记录，并且仅当匹配区域通过稳定边界检查（一种预分词器可证明无法跨越的逐请求测试）时才进行拼接。当检查失败时，TokTier 会扩大窗口并最终在完整请求上运行参考分词器。因此，不成功的修复只会增加延迟而不会改变输出。

对于没有可复用前缀的调用，TokTier 使用派生自 GPT 系列预分词等价表示的 GPU 分词器。输入被分类为最大字符类运行。然后，片段的起始取决于运行内的位置、有限数量的相邻文本以及一些运行级别的摘要。这种运行分解移除了串行正则扫描同时保留了其输出，随后由 GPU BPE 流水线对生成的片段进行编码。小片段保留在 CPU 上，并且每个实现都绑定到内容寻址的分词器注册表。后台验证器对实时请求进行采样，并将其 ID 与参考实现进行比较。此防护涵盖了依赖于执行历史的 Bug，因此能够逃脱全新进程测试。

评估旨在探究该设计是否精确，其两条路径是否与测量的工作负载相匹配，以及前端的增益在接触服务引擎后能否存活。我们检查了带有版本固定构件的 17 个分词器系列。差异化活动包括合成和对抗性输入、对 12.4 TB 真实文本语料库的全面扫描，以及超过 93,000 个重放的智能体步骤。测试的配置与参考相比没有产生偏差。从 100K 到 3M 字符，增量修复保持在 0.5–1.1 毫秒。在 1M 字符时，它比最强的基于缓存的替代方案快 2.1 倍，在 2M 时快 3.0 倍。GPU 路径维持 3.8–4.7 GB/s 并在 0.87 毫秒内编码 1M 字符的完整上下文，比先前发表的最快 CPU 方法低 23.4 倍。在接入 vLLM 的情况下，TokTier 在高负载下将首字时间中位数减少了 16–34%，在记录的突发到达下 P99 减少了 23%。在 50 毫秒 P99 目标下，4 核修复池和一块 GPU 维持 1,821 请求/秒，而 16 核无状态 CPU 前端为 40 请求/秒 (§5)。

本文做出三项贡献。它表征了会话级别的分词，据我们所知这是首次针对编程智能体流量，表明该流由频繁的小更新和罕见的大重建组成 (§2)。它提出了一种精确的有状态分词服务，包括用于会话延续的受检边界修复和用于 GPU 完整分词的 GPT 系列预分词的局部运行重构 (§3, §4)。它还开发了一种验证方法，结合了逐请求检查、版本固定的差异化测试、真实文本扫描和运行时采样，然后在 vLLM 前端评估了完整服务 (§5)。

2. 背景与工作负载 服务研究通常通过提示词长度、输出长度和到达时间来总结请求。分词还需要一个区别。它必须将当前会话中已看到的文本与新到达的文本分开。我们用 N 表示完整上下文，用 Δ 表示新文本，用 h 表示服务 API 报告的提示词缓存命中率。完整重新分词读取 N 个字符。理想的增量修复将读取接近 Δ 的字符，同时返回完全相同的 Token ID。

2.1. 分词的位置 服务前端接收文本，应用添加 Token 处理、规范化、预分词和子词编码，然后将 Token ID 发送给模型引擎。前缀缓存在这些 ID 存在后才开始。因此，高 KV 缓存命中率消除了模型侧的预填充工作，但并未消除前端工作。 输出也必须与模型使用的参考分词器匹配，因为 Token ID 是模型输入的一部分，并且大多数前缀缓存以 Token 序列作为其条目的键。近似的分词器可能会改变模型行为、减少缓存复用，或两者兼有。我们在整篇论文中使用参考分词器的全文本输出作为契约。

2.2. 追踪来源 我们的主要数据集包含来自 6 名用户在 9 台机器上十个月日常使用 Claude Code 和 Codex CLI 的 153,951 次调用。本地收集器解析智能体的会话日志并仅导出计数（附录 B 列出了字段）。文本在内存中进行长度计数后被丢弃，标识符使用永不离开源机器的密钥进行 HMAC 哈希处理。解析器还检测重复和重放的日志记录。此检查移除了 26,578 次虚假调用，占一个生态系统解析数据的 14.7%。收集、同意和解析的详细信息见附录 B。 我们针对三个独立来源检查这些追踪。提供商侧的聚合涵盖了相同类型流量的约 5.12 亿个 Token。在此处及全文中，调用的命中率是指 API 报告从提示词缓存读取的输入 Token 份额，而 Token 加权聚合是在除法之前对所有调用的两个计数求和。按照这种计算，集群命中率为 94.1%。一个公开的自主智能体追踪 (codex_swebenchpro) 包含了来自 610 次成功的 SWE-Bench Pro 试验的 20,230 次调用及完整对话文本 (Jimenez et al., 2024; Inferact, 2026)，其独立报告的聚合命中率为 94.2%。TraceLab 语料库 (Zhu et al., 2026) 包含了在另一家机构收集的来自 4,265 个 Claude Code 和 Codex 会话的 357K 步骤。TraceLab 省略了文本，因此无法重放分词，但它在外部检查了上下文大小、追加大小、命中率和步调（附录 B）。这些来源没有共享收集管道，也没有共享用户。在它们重叠的地方，结果是一致的。

2.3. 大多数调用向大上下文添加少量文本 图 2. 在 153,951 次交互式调用中，上下文大小 N 和每次调用新 Token 数 Δ 的联合分布（按 API 的 Token 统计）。会话延续集中在对角线以下一到三个数量级，因此大多数调用向大上下文添加少量文本。会话初始化和重建位于 Δ=N 对角线上，并携带高达 10^6 个 Token 的完整上下文。边际分布和每个来源的详细信息见附录 B 的图 15。 图 2 总结了常见情况。在交互式追踪中，中位数追加约为 1.4K 字符，P90 接近 9–14K。公开的自主追踪更重，中位数为 3.8K 字符，但形状相同。中位数上下文大小为 86K（Codex）到 123K（Claude Code）Token，并向百万 Token 延伸。同时，74–87% 的调用具有 h>0.9，中位数调用的 h 在 0.98 和 0.99 之间。 这些值暴露了完整重新分词的工作放大。TraceLab 的中位数步骤携带 126,180 个缓存前缀 Token 和 857 个追加 Token。其每步骤的完整上下文与追加的比率中位数为 132，Token 加权聚合为 23.5。相同的 Token 加权比率在我们的每调用追踪上约为 10，在集群 94.1% 的命中率下约为 17。因此，当前的文本接口处理的材料比请求添加的多一到两个数量级。 这些调用还形成深度循环。一次用户轮次在中位数下产生 3–5 次模型调用，P90 为 27–34 次，P99 为 87–103 次。自主追踪在中位数下每次试验运行 30 次调用。分词在每一步都要付出代价，因此对于上下文单调增长的会话，O(N) 分词器会累积 O(N^2) 的工作量。

2.4. 会话初始化和重建罕见且庞大 用追踪术语来说，完整上下文调用到达时没有缓存前缀 (h=0)，而会话延续到达时其部分提示词已被缓存。用层级术语来说，会话状态未命中到达一个没有可复用 Token 状态的 Worker。这发生在会话开始、历史压缩和迁移之后。按追踪来源汇总，完整上下文调用占 1.0–3.6%。它们的大小与典型追加相差两个数量级。它们携带 10^4 到 10^6 个 Token 的完整上下文，并且通常在许多会话同时启动或重建时一起到达。

2.5. 会话状态可以比 KV 状态寿命长 相对于默认的提示词缓存生命周期，人类的停顿很长。在我们的追踪中，用户轮次之间的中位数间隔为 3.6–6.4 分钟。大约 55% 的 Claude Code 间隔和 42% 的 Codex 间隔超过了 5 分钟的默认缓存 TTL。TraceLab 从提供商侧显示了相同的衰减，其中步骤的缓存份额平均值从亚分钟停顿的 0.96 下降到一小时以上的 0.17（附录 B）。Token ID 和字节跨度每个 Token 消耗几十字节，远少于 KV 状态。因此，即使在引擎驱逐相应的 KV 块之后，分词服务仍可保留会话状态。当会话返回时，即使模型必须重建其部分缓存，该服务也能在几毫秒内修复 Token 序列。第 5.7 节测量了这种状态的内存成本以及更长保留期带来的会话状态命中率（图 14）。

2.6. 设计要求 这些测量得出了四个要求。常见路径必须保留每会话的 Token 状态，并使其工作跟随更改而不是完整上下文。完整分词必须吸收大请求而不产生 CPU 长尾。两条路径都必须支持多个冻结的分词器版本，因为我们的追踪中同时出现了 12 个以上的模型版本。最后，每条路径都必须返回参考 Token 序列，因为输出的 ID 是前缀缓存键。最后一个要求排除了边界启发式方法和近似的 GPU 分词器，即使它们的平均吞吐量很高。 在某些当前的部署中，绝对的 CPU 成本是可控的，但其趋势是不利的。在测量的混合负载下，在现代 Rust 分词器上进行完整重新分词每请求花费 13.4 毫秒的核心时间，这在 0.5 请求/秒/GPU 下读数为每 1000 个 GPU 6.7 个前端核心（附录 17）。三个趋势使这个数字成倍增加：更快的模型推理提高了每 GPU 完成的请求数，更长的上下文增加了完整分词时间，而上升的命中率消除了模型侧的工作而保持前端工作不变（附录 B.6）。我们将这一趋势视为动机，而不是集群规模预测。第 5 节直接测量了当前的服务时间、长尾和容量效应。

3. 系统设计 TokTier 是放置在请求路由器和模型引擎之间的分词服务。它接受请求文本和模型标识符，然后返回等效于参考的 Token ID。该服务为实时会话保留 Token 状态，并根据该状态和请求大小选择执行路径。图 3 显示了数据流。

图 3. 通过 TokTier 的请求生命周期。路由器检查实时会话 Token 状态，然后将 会话延续发送到边界修复，将大型状态未命中片段发送到 GPU 路径，将小片段或任何快速路径失败发送到参考 CPU 路径。会话存储为每个实时会话保留 Token ID 和字节跨度。影子验证器针对参考引擎重新分词一部分采样的输出 ID，并隔离偏差。 每个分词器版本通过内容哈希注册。其条目携带添加 Token 规则、规范化配置、预分词规则、词汇表、合并表以及修复和 GPU 路径使用的系列特定检查。请求永远不会通过环境进程状态来解释，并且在一个分词器版本下创建的会话永远不会在另一个版本下修复。 路由器根据会话状态对每个请求进行分类。会话状态命中会找到一个兼容的会话记录，即其文本前缀与新请求匹配的记录。该记录保存了上一次调用的 Token ID 和源字节跨度，服务在更改附近修复此记录。会话状态未命中找不到兼容记录，因此该请求是会话初始化或历史重建，其上下文将被完整分词。路由器在分词层内部决定此状态，独立于第 2 节的引擎侧提示词缓存复用 h，因此两层持有具有不同生命周期的独立状态。大型状态未命中片段进入第 4 节的 GPU 路径。小片段使用参考 CPU 分词器，因为内核启动开销将占主导地位。路由仅影响成本。每条路径都遵守一个输出契约。 输出的 Token ID 始终与请求文本的完整参考分词相同。下面的每种机制都可能失败并转向更多的工作、更宽的窗口、完整的重新分词或 CPU 回退，而绝不会转向不同的 ID。

3.1. 为什么追加会更改旧 Token 现代 BPE 分词器应用两个阶段。预分词器将文本划分为短片段，通常使用正则表达式，然后 BPE 独立编码每个片段，因此任意的文本边界并不是 Token 边界。

图 4. “pipeline”一词内部的边界改变了 Token 序列（Llama-3.1-8B 分词器，每个框下方为真实的 Token ID）。独立分词产生两个 Token（␣pipe + line），而完整分词产生一个（␣pipeline）。修复对受影响区域进行重新分词，并且仅在找到稳定边界后复用缓存的前缀，逐位重现串行流。 图 4 给出了一个真实的例子。前一个请求在“pipe”之后结束，下一个请求追加“line”。参考分词器将“␣pipeline”视为一个片段并发出一个词汇表 Token。独立对两边进行分词会发出“␣pipe”和“line”两个 Token。追加的文本改变了旧前缀的尾部 Token，并移动了后面的每个位置。由于 Token ID 序列是前缀缓存键，这种偏移会悄无声息地使会话其余部分的复用失效。 两种机制造成了这种影响。当文本从右侧到达时，预分词器可以移动片段边界。然后，生成片段内的 BPE 合并顺序可能会改变。追加周围的固定重叠半径并不是正确性规则。数字分组、空格前瞻和换行符吸收可以将影响推过任何选定的半径，并且我们的对抗性预言机为我们制定的每个有界半径规则产生了级联的反例。因此，我们仅使用窗口来搜索可复用的边界。接受取决于从分词器系列派生的单独逐请求检查。发表的记录表明这种困难通常被低估。LoPT，唯一经过同行评审的分段分词器，提供了一个逃脱其自身安全定理前提的配置 (Shao et al., 2026)。Gigatoken，一个广泛采用的工业引擎，在没有证明的情况下断言安全的边界行为 (Rød, 2026)。

3.2. 增量修复

图 5. 图 4 运行示例上的增量修复（相同的冻结分词器，每个 Token ID 都是真实的引擎输出）。服务对追加内容和存储上下文的后缀进行重新分词，匹配新的和缓存的 Token 记录，检查相等的运行是否包含稳定的预分词边界（星号标记的类转换，在附录 A 的形式化中称为证书），并在该运行结束时进行拼接。检查失败会扩大窗口，并最终回退到完整的参考分词。 增量修复更新先前的 Token 序列而不是重建它。假设一个会话存储了文本 A 的分词，下一个请求是 A||B。服务取 A 的最后 w 个字符（默认 w=512），追加 B，并使用与会话使用的相同的参考兼容引擎对该窗口进行分词。然后，它将新记录与重叠窗口旧部分的缓存记录进行比较。 图 5 显示了完整操作。服务找到在位置和 Token ID 上都一致的最长记录运行。然后，稳定边界检查通过三个条件接纳该运行。该运行必须包含至少两个 Token。它必须覆盖比词汇表可发出的最长 Token（按分词器探测，Llama 系列为 128）更多的规范化字符，这排除了意外的单 Token 匹配。最重要的是，该运行必须包含一个特定于系列的稳定边界，即一个字符类转换，在此处预分词器右侧的输出可证明不依赖于左侧的文本。仅匹配的 ID 运行是不够的，因为依赖于上下文的数字分组会击败它，这是我们的证书级预言机以对抗方式暴露的失败。附录 A 将稳定边界形式化为同步边界，并证明了拼接定理。 当条件成立时，匹配运行之前保留缓存记录，之后保留新记录。实现在相等运行的末尾进行拼接，推论 A.6 表明这与在其中稳定边界处拼接是可互换的。生成的 ID 序列等于 A||B 的完整分词。当条件失败时，服务将 w 加倍并重试，最多五次，然后将完整请求发送到参考引擎。搜索可能会错过可用的边界，但不能接受无效的边界。因此，未命中只会花费额外的工作，而永远不会改变返回的 ID。在编辑两侧应用相同的过程可处理上下文中部的突变，而两次搜索都失败的大型重写将被完整分词。

3.3. 为什么拼接检查是充分的 在系统层面，形式化论证很短。预分词器将输入映射到有序的片段序列，BPE 在没有其他片段状态的情况下对每个片段进行编码。在稳定边界处，右侧的片段序列独立于左侧上下文。如果缓存和新记录在包含此类边界的运行中一致，则两次执行都达到了相同的片段序列和相同的 BPE 输出。因此，缓存记录可以服务于左侧，新记录可以服务于右侧。 证明由冻结的分词器配置参数化。我们确定哪些字符类转换同步每个支持的系列，并检查配置是否满足证明假设。我们检查的 17 个系列中有 15 个满足这些条件。另外两个可证明在谓词类之外（一个规范化器完全擦除了空格结构，没有留下内部边界可供修复），并且始终采用完整重新分词路径。 该定理涵盖了系列级别的边界抽象。它没有证明不断发展的 Rust、Python 和 CUDA 实现。我们通过对参考分词器进行版本固定的差异化活动来验证实现，并在运行时对部署的输出进行采样。第 5.2 节区分了这些形式的证据并报告了它们的覆盖率，附录 16 将两个最近的邻居置于由此产生的保证阶梯上。

3.4. 状态管理 会话存储保存 Token ID、字节跨度、分词器哈希以及从文本位置到 Token 记录的紧凑索引。修复就地编辑这些数组，派生索引被延迟更新，因此簿记成本跟随修复窗口而不是完整上下文。早期的实现在每一轮都重建偏移数组，并悄无声息地恢复了 O(N) 行为，即使分词只涉及窗口。修复此问题后，该协议端到端执行 O(Δ+w) 工作，与 N 无关。 状态在会话结束时回收，因此内存跟踪实时会话而不是内容历史，并且它可以使用比 KV 缓存更长的生命周期 (§2.5)。Worker 拥有分配给它的会话。失去亲和性的请求成为会话状态未命中，但保持正确。跨 Worker 状态转移是当前系统不需要的优化。

4. 精确的 GPU 分词 会话初始化和历史重建不包含可复用的会话状态。它们的上下文大到足以产生很长的 CPU 服务时间，特别是当多个会话同时启动或重建时。完整分词将这项工作移至 GPU，同时保留参考 Token 序列。

4.1. 移除串行正则扫描 GPT 系列分词器将预分词指定为带有回溯的最左优先交替正则表达式 (Radford et al., 2019)。在直接实现中，每次匹配都从前一次匹配的结束处开始。这种依赖性阻止了任意块的独立匹配，并且首先拆分文本会重新创建第 3.1 节的接缝问题。先前的 GPU 分词器通过削弱规范来解决这种紧张关系 (Kadamba and Jaisankar, 2026; You, 2025; Jawa, 2021)。

图 6. 运行分解。参考正则表达式暴露了匹配之间的串行依赖。等价公式通过并行传递计算字符类、最大运行和局部片段起始谓词。生成的片段馈送到大小专用的 BPE 内核。 我们的核心观察是，我们研究的生产模式从不需要回溯引擎。我们将每个字符分类为四类之一（字母、数字、空格、其他）并形成最大的同类运行。一个字符是否开始一个片段仅取决于它在运行中的偏移量、跨运行边界的最多四个字符的回溯，以及三个每运行聚合（运行开始、第一个非 CRLF 位置、最后一个 CRLF 位置）。字符分类是并行的，运行摘要来自前缀扫描，片段起始测试是独立的每字符谓词（图 6）。 我们一次从正则表达式的一个替代项派生规则。cl100k 谱系直接映射到四个类和局部运行规则。o200k 谱系添加了大小写边界规则和稀疏收缩路径，Unicode 标记采用狭窄的稀疏回退，而常见路径保持向量化。DeepSeek 系列分词器 (DeepSeek-AI, 2024) 依次应用三个拆分器。它们的组合折叠到相同的每字符谓词中，前提是每个拆分器重新拆分前一阶段的每个片段，并且未匹配的跨度作为隐式片段存活。推导是构造性的，说明了哪个运行规则对应于每个正则表达式替代项，以及在哪些冻结的 Unicode 和分词器表下对应关系成立。然后，差异化测试在片段边界级别和最终 Token ID 级别检查实现 (§5.2)。这种分离很重要，因为相同的 Token ID 有时会隐藏错误的片段划分。

4.2. GPU BPE 预分词后，每个片段独立编码。合并排名、词汇表条目和字节字符串被打包到 GPU 哈希表中。两个等价性许可了并行调度。一轮的最小合并排名标识一个对值，并且合并该对所有最左侧非重叠出现等于迭代的单次合并。只有与已完成合并相邻的对必须再次探测。 工作按片段长度分派。最多 32 字节的片段（自然文本中的绝大多数）以每片段一线程运行，序列在寄存器中。33–128 字节的片段以每片段一 Warp 运行。32 个通道并行探测候选对，Shuffle 归约找到最小排名，投票将命中位置具体化为位掩码，并且最左侧非重叠选择在该掩码上以封闭形式评估。更长的片段落入每片段一块的内核，带有共享内存候选位图。ignore_merges 系列（Llama 3, gpt-oss）首先尝试整个片段的词汇表命中并短路。完整的预分词路径由设备上的 UTF-8 解码、字符分类、运行构造、规则谓词和两个前缀扫描组成。多文档批次连接输入并在文档边界处切断运行，每个小文档 0.36 µs。在一个 RTX PRO 6000 上，仅预分词就达到 30–77 GB/s，具体取决于脚本混合。包括 BPE 和输出压缩在内的完整路径在英语、中日韩和模板化语料库中维持 3.8–4.7 GB/s（876–1206 Mtok/s），与参考实现字节相同。

4.3. 单请求路径 批量吞吐量并不能决定单个状态未命中请求的延迟。传统的 GPU 流水线在选择下一次启动之前将中间计数读回主机。这些同步在批量基准测试中是不可见的，而在单个请求中是可见的，特别是当主机繁忙时。TokTier 将片段计数、分派列表和输出长度保留在设备内存中。内核几何形状取决于缓冲区容量而不是主机可见计数，并且整个字节到 ID 的链被捕获为在一小组输入大小桶上的 CUDA 图。主机同步从每请求八次下降到两次。在 CPU 争用下，图路径保持 P99 接近其空闲值，而急切流水线的 P99 翻倍 (§5.4)。

4.4. 范围和回退 GPU 路径涵盖了本文评估的 cl100k、o200k 和 DeepSeek 模式系列的分词器主体。添加 Token 的字面提取在系列分派之前运行。对于需要它的一个系列，NFC 规范化保留在 CPU 上。GPU 路径目前返回的 ID 没有源字节跨度，因此必须为以后的修复初始化会话状态的状态未命中请求使用参考分词器来获取跨度。不支持的分词器和未通过系列检查的请求保留在 CPU 参考路径上，而高于 2 KB 阈值的片段进入 GPU，较小的片段保留在 CPU 上。路由器还在 GPU 背压下溢出到 CPU。这些情况会改变延迟和容量，而输出契约保持不变。

4.5. 服务实现 会话存储和修复逻辑在 Rust 中实现。分词器条目在注册后是不可变的，并且 Worker 使用会话亲和性，因此会话延续到达其上一轮创建的状态。添加和特殊 Token 是模型保留作为单个 ID 的文字字符串，例如。最左侧最长的字面传递在分词器系列处理剩余片段之前提取它们。 参考 CPU 路径。此路径是冻结的 HuggingFace 参考实现。它服务于小片段、不支持的系列、修复回退、背压溢出以及需要源跨度的状态重建。在我们的服务混合中，它承载了不到 0.3% 的请求字符，因此参考速度就足够了。该层还提供了最快的可用 Rust 分词器，但严格作为时序基线。我们的验证器恰好捕获了这类返回依赖于历史 ID 的引擎 (§5.8)，因此速度和正确性锚定在构造上被分配给不同的引擎。修复窗口引擎本身是可插拔的。我们在 Python 参考栈和 Rust crate 上运行相同的协议不变，并以第 5.2 节的认证重放活动作为准入门槛。 引擎接口。TokTier 通过 vLLM 的 prompt_token_ids 接口提交 Token ID。我们验证了通过文本和通过 ID 插入的前缀共享相同的 vLLM 前缀缓存键空间。文本写入的前缀被 ID 提交的请求以 99.84% 的速率命中（反向为 99.94%），输出相同，因此引擎不需要修改。对 vLLM 0.25 进行插桩还定位了引擎调度之前 API 服务器进程中的原始分词工作，这就是删除它会改变首字时间的原因。 影子验证。后台线程对发出的序列进行采样，并使用参考引擎对相同的文本进行重新分词。验证器精确比较 ID，并使用内容哈希隔离任何不匹配以供离线重现。如果它落后，它会丢弃样本并增加一个可见的计数器。在服务实验中采样率为 5%，在离线扫描中为 100%。运行时采样涵盖了任何全新进程测试都无法执行的依赖于历史的实现失败 (§5.8)。

5. 评估 我们首先将两条执行路径与测量的基线进行对比，然后针对冻结的参考分词器对它们进行测试。我们分别测量增量修复和 GPU 完整分词，然后评估突发长尾、容量和接入 vLLM 的首字时间。最后的实验涵盖资源使用和运行时验证。GPU 路径的限制与其他限制一起在第 7 节中讨论。 实验在具有四块 96 GB RTX PRO 6000 Blackwell GPU 的双插槽 AMD EPYC 9115 主机（32 个物理核心，禁用 SMT）上运行。CPU 实验是 NUMA 固定的。除非另有说明，一块 GPU 服务于启用了前缀缓存的 vLLM 0.25，另一块服务于 TokTier。分词器构件、数据集和依赖版本由内容寻址清单冻结。CPU 一次性延迟使用每个进程一次测量的编码，因为 Rust 分词器在调用间保留字缓存。 参考是每个冻结模型的 HuggingFace 快速分词器。主要的 CPU 性能基线是 fastokens，即 vLLM 附带的 Rust 分词器。我们还与 Gigatoken (Rød, 2026)（一种基于缓存的高性能 CPU 分词器）以及我们净室复现的 LoPT (Shao et al., 2026) 进行了比较。近似的 GPU 分词器仅出现在正确性比较中，因为它们不满足输出契约。
