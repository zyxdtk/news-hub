摘要

多智能体大语言模型（LLM）工作流通过专业化 LLM 智能体之间的协作推理，已成为解决复杂开放式任务的强大范式，但由于频繁的 LLM 调用和长时序上下文积累，其运营成本高昂。现有的级联路由方法仅进行一次性查询级决策，无法适应多步工作流动态且状态相关的特性。在这些工作流中，每一步选择合适的 LLM 取决于不断演变的任务进度、剩余任务难度和成本效率要求。我们提出了 ProgRouter，这是一个在线进度引导路由框架，能够在工作流各步骤中自适应选择 LLM 智能体，在遵守时间和成本预算的同时保持任务求解质量。ProgRouter 引入了多视图任务进度评分器，将粗粒度工作流结果状态与子任务完成情况、进度趋势和工作流状态质量的细粒度信号相结合。随后，双路径任务进度预测器和自适应元门控机制评估每个候选路由 LLM 的进度增益。ProgRouter 做出在线逐步路由决策，以平衡进度增益、任务时间预算和长期运营成本效率。在 HumanEval Plus、MBPP、MATH-500 和 ASQA 上的实验涵盖了智能体代码生成、数学推理和检索增强长文本问答，结果表明 ProgRouter 在保持强劲任务求解性能的同时，相较于关键基线方法降低了运营成本。

1 引言

诸如 ChatGPT (Singh et al., 2026) 和 DeepSeek (Liu et al., 2025) 这样的大语言模型（LLM），在上下文推理和工具使用方面取得了快速进步，使得基于 LLM 的智能体能够支持开放式、多步任务规划和问题求解 (Deng et al., 2025)。多智能体 LLM 工作流 (Zhang et al., 2025; Yao et al., 2023; Fourney et al., 2024) 通过协调专业化智能体分解复杂查询，并通过迭代推理解决子任务，进一步扩展了这一能力。然而，这些工作流的运营成本高昂，因为它们需要在多个步骤中重复调用 LLM 并维护长时序任务上下文，导致高昂的 Token 消耗、计算资源使用、能源需求和延迟 (Lin et al., 2026; Xiao et al., 2026)。因此，开发可持续、成本感知的服务策略，特别是为不同的智能体和工作流步骤选择合适的 LLM，对于在保持任务求解性能的同时提高成本效率至关重要。

级联 LLM 服务 (Jiang et al., 2026; Ong et al., 2025; Chen et al., 2024) 提供了一个有前景的方向，它根据任务复杂性将用户查询路由到不同大小和能力的 LLM。现有方法 (Jiang et al., 2026; Ong et al., 2025; Chen et al., 2024; Woisetschläger et al., 2025) 将较简单的查询分配给轻量级 LLM，而将更强的 LLM 留给较难的请求，通常只会带来最小的质量下降。然而，这些一次性路由方法并不能充分支持多智能体工作流，因为后者需要的不是单一的前置决策，而是一系列关于调用哪些智能体、何时调用以及如何结合它们互补优势的协调选择，并在线适应不断演变的工作流状态。这一差距引出了一个根本问题：如何在运营成本预算下，跨工作流步骤动态路由 LLM 智能体，以保持任务求解质量？

回答这个问题具有挑战性，因为：
- 多智能体 LLM 工作流是开放式且有状态的。 每一步“正确”的智能体取决于当前的任务进度、部分解的质量以及涌现的协作需求。传统的 LLM 选择方法依赖于静态基准 (Naveed et al., 2025) 或离线人类偏好数据集 (Ong et al., 2025)，无法满足多步智能体工作流的在线、上下文路由需求。
- 有效的 LLM 智能体路由需要准确评估已取得的任务进度和剩余难度。 然而，中间工作流状态通常是嘈杂且部分解决的，关键进度因素隐藏或隐含其中 (Ma et al., 2024; Li et al., 2026)。校准不当的估计要么将运营成本预算浪费在不必要的强智能体调用上，要么过度使用弱智能体，导致不可恢复的质量下降 (Deng et al., 2025)。
- LLM 智能体路由必须尊重工作流的剩余成本预算，但未来的步骤和子任务难度是先验未知的。 总是选择最强 LLM 的贪婪策略可能会过早耗尽预算，而保守策略则会利用不足强智能体。这需要原则性的在线算法来平衡任务进度和长期运营成本。

贡献。 为了应对这些挑战，本文提出了 ProgRouter，一个在线进度引导路由框架，它在时间和成本预算下跨工作流步骤自适应选择 LLM 智能体，同时保持强劲的任务求解质量。ProgRouter 在多智能体 LLM 工作流执行时，从多样化的路由轨迹中持续学习工作流进度模式，并逐步细化其路由策略。其核心是，ProgRouter 引入了一个多视图任务进度评分器，将粗粒度工作流结果状态与子任务完成情况、任务进度趋势和工作流状态质量的细粒度信号相结合。该任务进度评分器作为一个轻量级域适配器，将可观察的工作流信号转换为统一的进度表示，而随后的双路径进度预测器设计原则和在线质量-成本感知路由算法在不同智能体领域间保持可迁移性。在此基础上，具有结构化和语义路径的双路径进度预测器以及自适应元门控机制估计每个候选路由 LLM 的进度增益。ProgRouter 做出在线逐步 LLM 智能体路由决策，平衡任务进度增益、任务时间预算和长期运营成本效率，实现质量驱动、截止时间感知和成本高效的工作流操作。

2 问题设置

2.1 协作多智能体 LLM 工作流

如图 1 所示，多智能体 LLM 工作流 $w={C,\mathcal{R},\mathcal{M}}$ 通过执行一系列 $T$ 个智能体调度步骤来解决用户任务：
- $\mathcal{R}$ 表示预定义的工作 LLM 智能体角色 $r$ 的集合（例如分析师和程序员）。
- $C$ 表示协调器 LLM 智能体，负责子任务规划、工作 LLM 智能体调度以及执行期间的工作流适配。
- $\mathcal{M}$ 表示具有不同大小和容量的可用 LLM $m$ 集合，模型从中实例化具有角色 $r\in\mathcal{R}$ 的智能体。设 $\mathcal{M}_{r}\subset\mathcal{M}$ 为有资格服务智能体角色 $r$ 的 LLM 子集。

在运行过程中，多智能体 LLM 工作流 $w$ 维护着不断演变的工作流状态 $s$，指示问题求解状态。每个智能体调度步骤 $t\in{1\cdots T}$ 调用智能体角色 $r_{t}$ 并产生更新的工作流状态 $s_{t+1}$，最终促成任务结果 $\mathcal{P}(w)\in{0,1}$（失败或成功）。

2.2 LLM 智能体编排

不同的 LLM 具有不同的优势和局限性 (Fourney et al., 2024; Zhang et al., 2025)，LLM 智能体路由的目标是利用它们的互补能力。这种异构工作流包括代码生成和数学推理等结构化任务，以及检索增强问答等开放式工作流，其中必须从中间证据综合、检索结果和答案细化中推断任务进度。例如，为代码生成子任务选择具有编程能力的 LLM，而将面向推理的 LLM 分配给更高层次的分析任务，例如动态子任务编排和对中间智能体输出的基于评论家的评估。因此，工作流 $w$ 中 LLM 智能体的有效编排取决于调度任务的领域和难度。为了实现这一点，我们采用账本驱动的协调器智能体 $C$ 进行动态任务规划和工作智能体角色调度，并采用在线进度引导 LLM 路由算法进行自适应智能体 LLM 选择。

账本驱动的协调器智能体。 协调器智能体 $C$ 由面向推理的 LLM 驱动，将高级用户目标分解为可执行的子任务，并按顺序将它们分配给专业工作角色 $r\in\mathcal{R}$。与基于静态规则的计划器不同，$C$ 维护结构化的工作流状态账本 $s_{t}$，总结任务目标、当前任务进度、中间推理轨迹和先前工作智能体的输出。这些账本能够持续监控工作流状态并检测执行失败。利用账本中记录的信息，协调器 LLM 对工作流状态进行推理，并通过子任务重新分配或协调调整动态修改执行计划。这促进了复杂、长时序工作流中的自适应规划和错误恢复。

进度引导的 LLM 路由算法。 虽然协调器智能体 $C$ 决定了下一步应该调度哪个工作智能体角色，但我们期望一个进度引导的 LLM 路由算法来决定哪个 LLM 实例应该实例化所选角色。具体而言，给定协调器账本中维护的实时工作流执行状态，在线路由算法评估子任务特征，包括调度的子任务领域、估计的子任务难度和历史执行性能，以从候选集 $\mathcal{M}_{r}\subseteq\mathcal{M}$ 中为工作智能体角色 $r$ 选择合适的 LLM。这种自适应路由策略旨在整个工作流执行过程中平衡 LLM 能力需求与时间及运营成本。我们将其实现为 ProgRouter，其详细方法如下所述。

3 ProgRouter 方法论

3.1 LLM 路由控制问题

图 2 说明了 ProgRouter 的整体流程。我们考虑一个持续服务 $W$ 个用户任务流的多智能体 LLM 工作流。对于每个用户任务 $w\in{1,\cdot,W}$，工作流执行一系列 $T_{w}$ 个智能体调度步骤。不同的用户任务表现出不同的复杂性和服务要求，导致任务时间 $\Gamma_{w}$ 和运营成本 $E_{w}$ 的约束。此外，我们施加了长期平均运营成本约束 $\widetilde{E}$，以调节多个服务任务的整体系统级成本效率。

我们寻求一种在线自适应 LLM 智能体编排策略 $\pi(s_{t},r_{t})\mapsto m_{t}$，跨越智能体调度步骤。基于当前工作流状态 $s_{t}$，每一步 $t$ 为调度的智能体角色 $r_{t}$ 选择合适的 LLM $m_{t}\in\mathcal{M}{r{t}}$。

$$
\max\limits_{\pi}\;\textstyle\frac{1}{W}\sum\limits_{w=1}^{W}\mathcal{P}\left(w\right) \quad (1a)
$$
$$
\textit{ s.t. }\;\textstyle\sum\limits_{t=1}^{T_{w}}E(m_{t})\leq E_{w},\forall\,w\in{1\cdots W}, \quad (1b)
$$
$$
\quad\;\;\;\,\textstyle\sum\limits_{t=1}^{T_{w}}\Gamma(m_{t})\leq \Gamma_{w},\forall\,w\in{1\cdots W}, \quad (1c)
$$
$$
\quad\;\;\;\textstyle\frac{1}{W}\sum\limits_{w=1}^{W}\,\sum\limits_{t=1}^{T_{w}}\;E(m_{t})\leq\widetilde{E}. \quad (1d)
$$

其中 $E(m_{t})$ 和 $\Gamma(m_{t})$ 分别表示所选 LLM $m_{t}$ 产生的运营时间和成本。形式上，$\pi(s_{t},r_{t})$ 旨在最大化工作流的任务求解性能，同时满足特定任务和长期平均运营成本约束。这将 LLM 智能体编排构建为长时序、多任务工作流执行上的在线约束优化过程。

挑战。 我们的在线控制问题具有挑战性，主要有两个原因。首先，任务求解性能 $\mathcal{P}(w)$ 通常要在整个工作流完成后才能观察到。这使得实时评估每个智能体调度步骤的 LLM 路由决策对进度的贡献变得并非易事。其次，优化系统级运营成本涉及时间平均，这很难先验估计，因为未来的用户任务和智能体调度步骤是异构的且事先未知。

3.2 多视图任务进度表示

为了实现在线、进度引导的 LLM 路由，ProgRouter 将中间工作流状态编码为多视图任务进度表示。给定当前工作流状态 $s_{t}$，多视图任务进度评分器估计一个归一化的进度分数 $g(s_{t})\in[0,1]$。它量化了当前工作流距离成功完成任务的远近。$g(s_{t})$ 值越高表示进度越大。为了在异构工作流状态下实现稳健且细粒度的进度估计，我们从多个互补角度评估工作流：
- 整体结果视图：评估当前工作流状态的整体健康度和有效性。它使用基于规则的分类器（例如决策树）将 $s_{t}$ 映射到四种粗粒度状态之一 $c_{t}\in{\textup{invalid, recoverable, partial success, complete}}$。这产生基础分数 $b(c_{t})$。
- 子任务完成视图：衡量用户的子任务、约束和其他评估标准得到满足的程度。它计算已满足要求的比例，得出子分数 $r_{t}$。
- 进度趋势视图：通过分析最近几个步骤中工作流是在改善、停滞还是倒退，捕捉短期进度动态。它由最近几步的平均进度增量计算得出，产生子分数 $d_{t}$。
- 状态质量视图：评估最新工作流状态转换的语义和结构意义。它可以包含工作流状态嵌入相似性和结构性工作流状态差异（例如新解决的子任务）等信号，得出子分数 $e_{t}$。

最后，通过分层聚合获得多视图任务进度分数 $g(s_{t})$：
$$
g(s_{t})=b(c_{t})+\alpha_{c_{t}}r_{t}+\beta_{c_{t}}d_{t}+\gamma_{c_{t}}e_{t}, \quad (2)
$$
其中 $b(c_{t})$ 是与粗粒度结果状态相关的基础分数，$\alpha_{c_{t}},\beta_{c_{t}},\gamma_{c_{t}}\geq 0$ 是权重系数。注意，该进度评分器提供了一个轻量级域适配器，将可观察的工作流里程碑映射到公共任务进度空间。对于新的智能体任务领域，只需适配可观察的里程碑定义和粗粒度结果状态。下游的在线探索与更新过程、在线预算感知 LLM 智能体路由算法在不同任务领域间保持领域无关。

关键洞察。 分层多视图评分器设计将可靠的粗粒度锚点（整体结果）与来自三个互补分析视图的细粒度、可微信号相结合，能够检测明显和微妙的任务进度。它生成密集的逐步监督信号，比稀疏的最终工作流结果更及时、信息量更大，用于指导工作流执行期间的 LLM 智能体路由。

3.3 在线任务进度预测器

ProgRouter 进一步需要一个前瞻性的进度信号，以确定接下来应调用哪个智能体 LLM 来有效推进任务完成。LLM 路由决策的进度增益不仅取决于 LLM 的大小和容量，更关键地取决于当前工作流状态和剩余任务难度。当工作流被未解决的错误阻塞时，强大的 LLM 会带来实质性的改进；然而，一旦用户任务接近完成，它提供的边际效益有限。因此，准确预测任务进度需要精确理解当前工作流状态。

双路径任务进度预测。 给定当前工作流状态 $s_{t}$ 和候选 LLM $m_{t}\in\mathcal{M}{r{t}}$，任务进度预测器学习在智能体调度步骤 $t$ 调用 $m_{t}$ 时的逐步进度增益：
$$
\hat{y}{t}=P{\Theta}(s_{t},m_{t})\textup{,} \quad (3)
$$
这促进了中间进度引导的在线 LLM 路由。为了在异构工作流状态 $s_{t}$ 下获得可靠的进度估计，我们将 $P_{\Theta}$ 实现为具有两个互补预测路径和自适应元门控机制的双路径预测器：
- 结构化路径：在表格特征向量 $x_{t}^{\mathrm{str}}=\phi_{\mathrm{str}}(s_{t},m_{t})$ 上操作，该向量编码显式工作流信号，包括当前任务进度分数、子任务完成状态、近期进度趋势、LLM 智能体调度历史和候选 LLM 路由决策 $m_{t}$。它产生进度增益估计：
$$
\hat{y}{t}^{\mathrm{str}}=P{\mathrm{str}}!\big(x_{t}^{\mathrm{str}}\big), \quad (4)
$$
其中 $P_{\mathrm{str}}$ 表示基于树的回归器（例如随机森林、XGBoost），擅长学习异构、低维表格特征。
- 语义路径：在协调器 LLM 智能体 $C$ 生成的工作流状态 $s_{t}$ 和候选路由决策 $m_{t}$ 的紧凑自然语言摘要上操作。摘要由轻量级句子嵌入模型 $\phi_{\mathrm{sem}}$（例如 MiniLM, Wang et al., 2021）编码为密集的语言嵌入向量 $x_{t}^{\mathrm{sem}}=\phi_{\mathrm{sem}}(s_{t},m_{t})$，产生进度增益估计：
$$
\hat{y}{t}^{\mathrm{sem}}=P{\mathrm{sem}}!\big(x_{t}^{\mathrm{sem}}\big), \quad (5)
$$
其中 $P_{\mathrm{sem}}$ 同样是基于树的回归器。语义路径捕捉了难以通过表格特征表达的微妙、定性工作流线索。

双路径估计 $\hat{y}{t}^{\mathrm{str}}$ 和 $\hat{y}{t}^{\mathrm{sem}}$ 最终通过基于树的元门控学习器（例如 XGBoost）组合，该学习器根据在线工作流状态 $s_{t}$ 在两个预测路径之间自适应路由信任：
$$
\hat{y}{t}=P{\mathrm{meta}}(\hat{y}{t}^{\mathrm{str}},\;\hat{y}{t}^{\mathrm{sem}})\textup{.} \quad (6)
$$

在每个智能体调度步骤 $t$，双路径预测器以可忽略的开销在线评估所有候选 LLM $m_{t}\in\mathcal{M}{r{t}}$，因为两个预测路径都依赖轻量级句子编码器和适度的基于树的回归器。由此产生的进度增益估计 $\hat{y}{t}(m{t})$ 被纳入协调器 LLM 智能体 $C$ 的路由目标中，使得工作智能体调度决策能够联合优化预测的任务进度增益与时间及运营成本。

关键洞察。 由于其元门控设计，我们的双路径任务进度预测器在不同工作流状态下自适应地结合了结构化和语义证据。当显式工作流进度信号可靠时，它可以更加重视结构化估计。另一方面，当工作流状态包含微妙的进度瓶颈和稀疏的可观察反馈时，它可以更多地依赖语义估计。

3.4 在线决策制定

在双路径任务进度预测器的基础上，ProgRouter 引入了一种在线决策算法，将预测的进度增益 $\hat{y}{t}(m{t})$ 转化为每个智能体调度步骤 $t$ 的 LLM 路由动作。

虚拟成本队列。 我们的方法受 Lyapunov 漂移加惩罚框架启发 (Neely, 2010)。我们在一个虚拟队列 $Q$ 中捕捉系统运营成本效率违规，即 $\widetilde{E}$ 的累积超支，在完成用户任务 $w$ 后进行如下更新：
$$
\textstyle Q_{w+1}=\max{0,Q_{w}+\sum\nolimits_{t=1}^{T_{w}}\;E(m_{t})-\widetilde{E}} \quad (7)
$$
其中我们初始化 $Q_{1}=0$。直观上，这捕捉了对长期平均运营成本约束 (1d) 的违反。因此，我们旨在最大化每个用户任务 $w$ 的工作流性能，同时最小化虚拟队列长度。质量-成本权衡公式如下，其中 $V$ 是权衡系数：
$$
\textstyle\max\limits_{\pi}\;V!\cdot!\mathcal{P}\left(w\right)-Q_{w}\left(\sum\limits_{t=1}^{T_{w}}\;E(m_{t})-\widetilde{E}\right) \quad (8a)
$$
$$
\textit{ s.t. Constraints (1b) and (1c).} \quad (8b)
$$

在线逐步路由决策。 在工作流 $w$ 的每个智能体步骤 $t$，ProgRouter 选择在时间和运营成本预算下最能推进任务的 LLM $m_{t}\in\mathcal{M}{r{t}}$。路由决策是立即且不可撤销地做出的，且不知道未来的智能体调度步骤或工作流演变。

进度差距感知的 LLM 路由。 我们将候选 LLM $m_{t}$ 的任务求解能力评估为：
$$
\widetilde{P}(m_{t},s_{t})=V\cdot(1-g(s_{t}))\cdot\hat{y}{t}(m{t}) \quad (9)
$$
因子 $(1-g(s_{t}))$ 捕捉了这样一种直觉：当用户任务仍远未完成时，任务进度增益 $\hat{y}{t}(m{t})$ 更有价值。它会激励 ProgRouter 在工作流还有很大进步空间时选择更强的 LLM 智能体，因为额外的进度预计会带来更大的收益。

预算感知成本惩罚。 除了系统级虚拟成本队列外，ProgRouter 还尊重特定任务的时间和运营成本预算（$\Gamma_{w}$ 和 $E_{w}$）。当工作流已经消耗了很大一部分成本预算时，路由器在选择昂贵的 LLM 时应该更加保守。我们将预算感知成本系数定义为：
$$
\textstyle c_{t}^{\Gamma}=\exp!\left(\frac{\Gamma(m_{t})+\sum_{i<t}\Gamma(m_{i})}{\Gamma_{w}}\right) \quad (10)
$$
$$
\textstyle c_{t}^{E}=\exp!\left(\frac{E(m_{t})+\sum_{i<t}E(m_{i})}{E_{w}}\right) \quad (11)
$$
这些系数随着累积时间和运营成本消耗接近其相应预算而增加。因此，如果工作流已经消耗了更多预算，同一调用的 LLM 智能体在后期阶段会受到更大的成本惩罚。这鼓励 ProgRouter 保留预算余量，避免重复选择昂贵的 LLM，除非它们预测的进度增益足够大。最终的在线 LLM 路由分数为：
$$
\displaystyle\mathrm{score}(m_{t})= \widetilde{P}(m_{t})-Q_{w}\cdot(E(m_{t})-\widetilde{E}) -c_{t}^{\Gamma}\cdot\Gamma(m_{t})-c_{t}^{E}\cdot E(m_{t}). \quad (12)
$$
在每个智能体调度步骤，ProgRouter 选择 $m_{t}^{\star}=\arg\max_{m_{t}\in\mathcal{M}{r{t}}}\mathrm{score}{t}(m{t})$。路由分数平衡了三个因素：任务进度、系统级运营成本效率压力和每个任务的时间/运营成本预算消耗。这使得 ProgRouter 能够在预期会带来有意义进度时选择更强的 LLM，同时避免在线工作流执行期间过高的时间和运营成本。

在线预测器学习。 我们的任务进度预测器 $P_{\Theta}$ 通过探索与更新过程在线学习。在每个智能体调度步骤，以概率 $\varepsilon$，ProgRouter 随机选择一个候选 LLM 以收集无偏训练样本；以概率 $1-\varepsilon$，它使用当前任务进度预测器选择等式 (12) 中路由分数最高的 LLM。在所选智能体步骤执行后，实现的进度增益计算为 $y_{t}=g(s_{t+1})-g(s_{t})$，探索样本被添加到训练缓冲区 $\mathcal{D}$ 中。一旦收集了足够的样本，预测器就会定期更新并用于指导未来的 LLM 路由决策。随着更多在线训练样本的积累，$\varepsilon$ 逐渐衰减，使路由器从探索转向预测器指导的利用。这样，ProgRouter 在没有离线训练数据的情况下自适应地改进 LLM 路由，从而实现更准确的任务进度估计和更好的整体工作流性能。

数据集和基准测试。 我们在智能体 LLM 工作流中使用四个广泛采用的基准测试评估 ProgRouter，涵盖代码生成、数学推理和检索增强长文本问答（QA）：HumanEval Plus (Liu et al., 2023)、MBPP (Austin et al., 2021)、MATH-500 (Hendrycks et al., 2021) 和 ASQA (Stelmakh et al., 2022)。值得注意的是，ASQA 评估开放式检索增强长文本 QA，其中不同的 LLM 智能体角色迭代检索证据、综合信息并产生有引用支持的答案，而没有单元测试式的反馈。我们使用 HumanEval Plus 的全部 164 个任务，以及从 MBPP 随机抽样的 200 个编码任务、从 MATH-500 抽样的 200 个数学推理问题和从 ASQA 抽样的 100 个检索增强长文本 QA 任务。对于 HumanEval Plus、MBPP 和 MATH-500，我们使用任务通过率作为任务完成指标，而 ASQA 使用引用精确度评估，因为它更适当地衡量在开放式检索增强 QA 中生成的响应是否得到相关且正确归因的证据的支持。

基线。 我们将 ProgRouter 与三个关键基线进行比较：
1. MasRouter (Yue et al., 2025)：一种查询级一次性 LLM 路由方法，在工作流执行前根据对任务复杂性的初始评估将每个用户任务分配给固定的 LLM；
2. CASCADIA (Jiang et al., 2026)：一种反应式 LLM 路由升级策略，从小型 LLM 智能体开始，当工作流的任务进度停滞时升级到更大的 LLM；
3. Educated Guessing：在线积累 LLM 路由经验，并无论实际任务进度需求如何都选择历史上表现最佳的 LLM。

模型库。 对于编码基准测试，模型库包含来自 Qwen 2.5-Coder (0.5B/7B/14B/32B) (Hui et al., 2024) 和 Qwen 3.5 (2B/4B/9B/27B/35B) (Qwen Team, 2026a) 两个系列的九个 LLM。对于数学推理基准测试 (MATH-500)，我们采用来自 Granite 4.1 (3B/8B/30B) (IBM Research, 2026) 和 Gemma 4 (2B/4B/26B/31B) (Google DeepMind, 2026) 两个系列的七个 LLM。对于检索增强长文本 QA 基准测试 (ASQA)，模型库由来自 Qwen 3.5 (2B/4B/9B/27B/35B) (Qwen Team, 2026a) 和 Qwen 3.6 (27B (Qwen Team, 2026b)/35B (Qwen Team, 2026c)) 的七个 LLM 组成。

表 1 报告了在 HumanEval Plus、MBPP、MATH-500 和 ASQA 上的主要基准测试结果，包括任务通过/精确度率、能耗、工作流执行时间以及每种方法的 LLM 路由分布。

单模型策略普遍成本不可行。 如表 1 所示，无论 LLM 规模如何，每个固定的单模型基线在所有四个基准测试中都违反了长期能源效率要求 $\widetilde{E}$。小型 LLM（如 Qwen2.5-Coder 0.5B 和 Granite 4.1 3B）由于任务求解能力弱，触发重复的智能体调度步骤以从中间故障中恢复，导致累积能耗高。相反，大型 LLM（如 Qwen 3.5 35B 和 Gemma 4 31B）由于其每次调用的能耗成本超过了 $\widetilde{E}$，其中 Gemma 4 31B 在 MATH-500 上消耗高达 26276 J。这一趋势在开放式 ASQA 设置中也成立，基于 Qwen 3.5 和 Qwen 3.6 的固定单模型策略超过了 19000 J 的能源预算，除了最小的模型配置满足预算约束但实现了较低的引用精确度。这进一步证明了在现实的运营成本约束下，总是小型或总是大型的策略都不可行，证实了 ProgRouter 的核心动机，即自适应逐步 LLM 智能体路由对于平衡任务质量和运营成本效率是必要的。

ProgRouter 在满足 $\widetilde{E}$ 的方法中实现了最佳的质量-成本权衡。 在 HumanEval Plus 上，ProgRouter 获得了 93.0% 的最高任务通过率，同时保持在 4800 J 预算内，优于 MasRouter（+2.1%）和 CASCADIA（+8.2%）。在 MBPP 上，ProgRouter 实现了最佳任务通过率（79.4%）、最低能耗（3376 J）和最短执行时间（10.3 s），在所有指标上主导了所有基线。在 MATH-500 上，ProgRouter 在满足 $\widetilde{E}$ 的方法中提供了最低能耗（6112 J）和最短执行时间（19.0 s），同时达到了 84.3% 的任务通过率，比 CASCADIA 的 87.8% 低 3.5%，但运营成本大幅降低。除了代码生成和数学推理基准测试外，ProgRouter 还推广到更开放的 ASQA 检索增强 QA 设置中，其中任务进度无法通过明确的单元测试式反馈来指定。在 ASQA 上，ProgRouter 在所有评估方法中实现了最高的引用精确度（92.1%），同时保持在 19000 J 能源预算内，比 MasRouter（89.8%）和 CASCADIA（89.8%）提高了 2.3%。图 3 可视化了这种质量-成本权衡，其中 ProgRouter 在所有基准测试中始终位于或接近帕累托前沿。这些结果验证了进度感知 LLM 路由分数（等式 12）与基于虚拟队列的预算跟踪相结合，使 ProgRouter 能够比基线更有效地导航帕累托前沿。

自适应 LLM 路由基线表现出 ProgRouter 所避免的一致失败模式。 Educated Guessing 收敛于历史上强大但与任务无关的选择（例如 MATH-500 上 98.8% 的 Granite 4.1 8B），这在 MATH-500 上违反了 $\widetilde{E}$（7023 J），并且在进度停滞未被检测到的更难问题上表现不佳。CASCADIA 的反应式路由升级在恢复之前产生了不必要的小型模型调用，导致 HumanEval Plus 上的任务通过率较低（84.8%）。MasRouter 的路由决策分配 LLM 智能体调用时没有适应不断演变的工作流状态和运营成本预算，导致 MATH-500 上的能源违规（8294 J）和较弱的 MBPP 通过率（67.8%）。在开放式 ASQA 设置中，MasRouter 也严重依赖单一主导小型模型（88.3% 的调用指向 Qwen 3.5 2B），尽管能耗较低，但其引用精确度（89.8%）低于 ProgRouter（92.1%）。ProgRouter 通过持续估计实时任务进度并根据不断演变的工作流条件调整 LLM 智能体路由决策，避免了所有这些失败模式。

LLM 智能体路由分布揭示了根据任务进度需求的自适应专业化。 如图 4 和图 5 所示，ProgRouter 根据工作流进度需求自适应分配 LLM 智能体调用。对于代码生成和数学推理任务，ProgRouter 将大多数智能体调度步骤集中在主导模型家族内的高效小型 LLM 智能体上（例如 HumanEval Plus 上 84.3% 使用 Qwen2.5-Coder 0.5B，MATH-500 上 91.0% 使用 Granite 4.1 3B），而当进度预测器预期额外的 LLM 能力会带来实质性增益时，则选择性地调用更大的 LLM 智能体。在开放式 ASQA 设置中，ProgRouter 表现出一致的专业化模式。这表明 ProgRouter 不依赖固定的模型选择策略，而是根据每个工作流的特征和不断演变的难度调整路由决策。这种自适应模式直接反映了 LLM 路由分数（等式 12）中进度差距感知项 $V\cdot(1-g(s_{t}))\cdot\hat{y}{t}(m{t})$，该项仅在工作流还有很大剩余进度可获取时才对更强的 LLM 进行加权。

5 结论

本文提出了 ProgRouter，一个在质量-成本权衡下用于多智能体 LLM 工作流的在线进度引导编排框架。通过将多视图任务进度评分与双路径进度预测相结合，ProgRouter 估计每个候选 LLM 智能体的边际进度增益，并利用它来指导成本感知、截止时间感知的 LLM 智能体路由决策。任务进度评分器充当轻量级域适配器，将可观察的工作流信号转换为统一的进度表示，而在线路由优化仍然适用于异构智能体工作流。在 HumanEval Plus、MBPP、MATH-500 和 ASQA 基准测试上的实验表明，ProgRouter 始终满足长期运营成本预算，同时实现了强劲的任务求解性能和具有竞争力的执行时间。这些结果突出了进度感知在线自适应 LLM 智能体编排对多智能体工作流的价值。

局限性

虽然 ProgRouter 展示了强劲的实证性能，但仍存在一些局限性，并指出了未来的工作方向。首先，我们的评估是在涵盖代码生成、数学推理和检索增强长文本 QA 的四个基准测试上进行的。尽管这些任务被广泛采用并跨越多个智能体领域，但 ProgRouter 对其他智能体设置（如开放式 Web 导航和工具增强 QA）的泛化能力仍有待实证验证。其次，多视图任务进度评分器需要轻量级的领域适配，其中可观察的工作流里程碑和粗粒度结果状态是根据任务特征指定的。尽管当前设计在多样化的基准测试中提供了可靠的进度信号，但以完全端到端的方式自动学习这些进度表示仍然是一个有趣的方向。

伦理考量

ProgRouter 旨在降低多智能体 LLM 工作流的能耗和运营成本，从而有助于实现更可持续的 AI 服务。由于我们的方法仅在现有 LLM 之间进行路由，不修改其底层能力，因此生成输出的质量、可靠性和潜在偏差仍取决于所选模型。标准做法（如仔细的模型选择、输出验证、检索增强任务的引用检查以及人工监督）仍然是必要的。由于 LLM 路由决策是根据任务进度调整的，从业者应监控不同任务类型的路由模式，以确保稳定的服务质量并避免意外过度依赖特定模型。我们的实验使用公共基准测试，不涉及个人数据。然而，现实世界的部署可能会在工作流状态或协调器账本中存储用户信息，因此应采取适当的数据保护措施，如访问控制和数据保留策略。通过提高智能体 LLM 工作流的运营成本效率，ProgRouter 可以帮助使多智能体 LLM 系统更加可持续和易于访问。

附录 B 数据集详细信息

我们在涵盖代码生成、数学推理和检索增强长文本问答等多样化智能体 LLM 工作流的四个代表性基准测试上评估 ProgRouter。

HumanEval Plus。 HumanEval Plus (Liu et al., 2023) 是原始 HumanEval 基准测试的增强版，用于评估 LLM 代码生成能力。每个任务包含一个编程问题描述，要求 LLM 智能体生成满足所提供提示规范的函数实现。与原始 HumanEval 相比，HumanEval Plus 引入了额外的隐藏测试用例，以提供对功能正确性的更全面评估。在我们的实验中，我们使用全部 164 个任务，并使用任务通过率评估性能，其中如果生成的解决方案通过了所有相关测试用例，则被视为成功。

MBPP。 Mostly Basic Python Problems (MBPP) 基准测试 (Austin et al., 2021) 在基本 Python 编程任务上评估 LLM 智能体。每个任务包含自然语言问题描述、参考实现和用于正确性评估的相应测试用例。MBPP 提供了比 HumanEval Plus 更广泛的编程场景，并评估生成的程序是否满足功能要求。我们从基准测试中随机抽取 200 个任务，并使用基于自动测试执行的通过率衡量任务完成情况。

MATH-500。 MATH-500 (Hendrycks et al., 2021) 是一个数学推理基准测试，包含跨越多个数学领域的具有挑战性的竞赛式问题。每个问题都需要多步推理和最终答案推导，使其适合评估智能体工作流的推理能力。我们随机抽取 200 个问题，并使用基于解决方案生成后精确答案匹配的任务通过率评估解决方案。

ASQA。 ASQA（歧义搜索问答）(Stelmakh et al., 2022) 是一个开放域检索增强长文本问答基准测试，旨在评估智能体 LLM 系统是否能为歧义问题综合准确且有证据支持的响应。与具有显式正确性检查的代码生成和数学推理基准测试不同，ASQA 需要迭代证据检索、信息综合和有引用支持的答案生成。因此，它为开放式智能体工作流提供了互补的评估设置，其中必须从中间检索和推理状态推断任务进度。我们随机抽取 100 个 ASQA 问题，并使用引用精确度评估生成的响应，该精确度衡量引用的证据是否适当地支持生成的答案。

附录 C 最先进基线描述

我们将 ProgRouter 与三个具有代表性的最先进 LLM 智能体路由基线进行比较，涵盖多智能体系统配置、基于级联的 LLM 服务和基于在线经验的路由策略。我们还额外评估了固定的单模型策略作为参考基线，以分析在任务求解质量和运营成本约束下自适应 LLM 路由的必要性。

MasRouter。 MasRouter (Yue et al., 2025) 是一个为多智能体 LLM 系统设计的基于学习的路由框架。与传统的单查询 LLM 路由方法不同，MasRouter 通过级联控制器架构联合考虑协作模式选择、智能体角色分配和 LLM 选择。它基于任务级信息学习路由决策，并构建平衡任务性能和运营成本的多智能体配置。在我们的实验中，我们使用 MasRouter 作为代表性的多智能体路由基线，它根据可用任务信息在工作流执行之前或开始时执行 LLM 选择。

CASCADIA。 CASCADIA (Jiang et al., 2026) 是一个高效的级联 LLM 服务框架，联合优化模型部署和请求路由。它将级联服务表述为约束优化问题，其中部署组件确定不同 LLM 候选者的资源分配和并行策略，而路由组件在质量和延迟要求下优化模型选择决策。CASCADIA 采用由基于 MILP 的部署求解器和切比雪夫引导的路由求解器组成的双层优化框架，以共同优化系统配置和路由策略。在我们的评估中，CASCADIA 将请求路由到较小模型以处理较简单的情况，并在需要额外能力时升级到更强模型。与 ProgRouter 基于不断演变的工作流进度执行在线逐步路由不同，CASCADIA 主要遵循反应式级联策略，当现有执行信号表明进度不足时触发更强模型。

Educated Guessing。 Educated Guessing 是一个基于在线经验的 LLM 智能体路由基线，利用历史执行结果来指导未来的 LLM 选择。它维护以前任务的路由统计信息，并偏好已展示出强劲实证性能的模型。与 ProgRouter 明确估计工作流进度和边际进度增益不同，Educated Guessing 不对不断演变的工作流状态进行建模，也不将预测的进度改进纳入智能体 LLM 路由决策。

单模型基线。 我们额外评估固定的单模型策略，其中在整个工作流执行期间为所有智能体调度步骤选择相同的 LLM。这些基线包括每个特定基准测试模型库中的轻量级和大容量模型。它们提供了评估自适应逐步 LLM 路由有效性的参考点，并量化了模型能力、任务求解性能和运营成本之间的权衡。

附录 D 补充实验设置

D.1 系统配置

我们在开源多智能体 LLM 框架 AG2 0.11.3 (Wu et al., 2023) 上实现 ProgRouter，并在 NVIDIA RTX PRO 6000 Blackwell 工作站上使用 Ollama 0.24.0 服务路由的 LLM 智能体。在所有评估的基准测试中，协调器 LLM 智能体由 Qwen3-Coder-Next 80B-A3B (Cao et al., 2026) 驱动。长期平均能源预算 $\widetilde{E}$ 为每个基准测试单独校准以反映任务复杂性，HumanEval Plus 设为 $\widetilde{E}=4,800$ J，MBPP 设为 $\widetilde{E}=4,500$ J，MATH-500 设为 $\widetilde{E}=7,000$ J，ASQA 设为 $\widetilde{E}=19,000$ J。

D.2 能耗测量方法

LLM 智能体服务的能耗使用 NVIDIA NVML 以 100 ms 的采样间隔进行测量。与基于 Token 计数或 FLOP 的代理指标不同，我们的能耗测量基于物理 GPU 功率测量。在校准期间，我们对每个执行段的活跃 GPU 功率进行积分：
$$
E=\int_{t_{\mathrm{start}}}^{t_{\mathrm{end}}}P(t)\,dt, \quad (13)
$$
其中 $P(t)$ 是 NVML 报告的 GPU 板功率。由此产生的值表示可归因于工作负载的增量 GPU 能耗。

我们分别对 LLM 模型加载、提示预填充、Token 生成、工作/协调器 LLM 智能体执行和工具执行进行性能分析。对于模型库中的每个 LLM 大小，我们校准每次调用的能耗估计器：
$$
\displaystyle E_{\mathrm{estimated}} = I_{\mathrm{load}}E_{\mathrm{load}}+E_{\mathrm{prefill}}+e_{\mathrm{decode}}N_{\mathrm{gen}}. \quad (14)
$$
其中 $I_{\mathrm{load}}$ 指示调用是否产生冷模型加载，$E_{\mathrm{prefill}}$ 根据实际上下文长度捕捉提示处理能耗，$N_{\mathrm{gen}}$ 表示生成的 Token 计数。该公式表征了提示处理和自回归 Token 生成。

报告的 GPU 能耗包括工作智能体和协调器智能体 LLM 推理，涵盖模型加载、提示预填充、上下文相关计算、Token 解码、KV 缓存活动和 GPU 运行时开销。CPU 侧编排、主机内存、存储和网络通信能耗被认为可忽略不计，不在能耗测量边界内。

D.3 在线评估协议

ProgRouter 在工作流执行期间执行在线学习，其中任务进度预测器使用从先前路由决策收集的实现任务进度反馈进行即时训练和优化。为了评估这种在线适应过程，我们将每个基准测试评估构建为顺序任务流。每个基准测试任务集使用固定的随机种子随机打乱，每个任务在结果顺序中处理一次，不进行重放。所有比较的方法使用相同的任务流构建。

在评估开始时，任务进度预测器从冷初始化开始，没有预训练参数或离线训练样本。在预热阶段，ProgRouter 使用 $\epsilon$-贪婪探索收集 LLM 智能体路由轨迹和相应的实现任务进度信号作为训练目标。在工作 LLM 执行所选工作流步骤后，生成的工作流状态由任务进度评分器评估，产生实现的进度增益：
$$
\Delta_{t}=g(s_{t+1})-g(s_{t}), \quad (15)
$$
用作优化任务进度预测器的训练目标。这些探索过程是在线执行的，在执行之前不可用。

任务进度预测器的训练集缓冲区、学习参数和虚拟队列状态在整个任务流中持续存在。随着额外的路由轨迹可用，任务进度预测器定期更新。我们根据预测器成熟度自适应地定义稳定。具体而言，当训练缓冲区包含足够的实现进度样本且探索概率降至预定义阈值以下时，即达到稳定。稳定后，学习到的路由策略在剩余任务流上进行评估。报告的主要结果对应于稳定后的稳态评估，因此测量了自适应 LLM 智能体路由策略的性能。

附录 E 消融分析结果

我们在 HumanEval Plus 基准测试上进行了额外的消融研究，以分析 ProgRouter 中各个组件的贡献。消融分别检查了两个方面：(1) 双路径进度预测器的内部设计，包括结构化路径、语义路径和自适应元学习器；(2) 在线路由组件，包括多视图进度评分器、预算感知路由目标和虚拟队列机制。所有在线路由消融都采用相同的模型库、工作流配置、能源预算和评估协议（附录 D.3）。

E.1 进度预测组件的消融

双路径任务进度预测器旨在从结构化执行特征和语义工作流状态中捕捉互补的工作流信息。我们首先通过离线预测精度分析评估每个预测组件。表 3 报告了不同预测器变体的预测误差。

表 3：HumanEval Plus 上进度预测器组件的离线消融。较低的 MAE 表示更准确的进度预测。
预测器变体 | MAE | $\Delta$ MAE
---|---|---
仅结构化路径 | 0.0967 | +0.0247
仅语义路径 | 0.0788 | +0.0068
双路径，均值组合 | 0.0843 | +0.0123
双路径 + 元学习器 | 0.0720 | 0

结果表明，两条预测路径都提供了互补信息。移除任一路径都会增加预测误差，表明结构化工作流信号和语义状态表示捕捉了任务演变的不同方面。语义路径单独实现的误差低于仅使用结构化路径，表明中间工作流描述包含超出显式执行统计信息的宝贵信息。然而，简单平均两条预测路径不如自适应元学习器，证明每条路径的贡献在不同工作流状态下有所不同。元学习器动态结合结构化和语义预测，以实现最佳的任务进度估计精度。

E.2 在线路由组件的消融

我们进一步评估各个路由组件如何对端到端工作流性能做出贡献。表 4 报告了在相同长期能源约束下 HumanEval Plus 的在线评估结果。

表 4：HumanEval Plus 上在线路由组件的消融。
配置 | Pass (%) | Energy (J)
---|---|---
完整 ProgRouter | 93.0 | 4796
无预测器 | 89.0 | 4785
仅结构化路径 | 90.9 | 4400
仅语义路径 | 87.2 | 4784
无多视图评分器 | 90.2 | 4486

移除进度预测器将通过率从 93.0% 降低到 89.0%，表明估计未来进度增益对于选择合适的 LLM 智能体很重要。仅使用一条预测路径也会降低性能，这与离线预测结果一致。特别是，仅语义变体遭受更大的退化，因为它缺乏显式的结构化工作流信号。

多视图任务进度评分器也对 LLM 智能体路由有效性有贡献。仅用测试通过率视图替换它将通过率降低到 90.2%，表明子任务完成、进度趋势和工作流状态质量等中间信号提供了超出最终结果估计的有用信息。

预算感知惩罚在平衡任务进度和运营成本方面起着重要作用。移除该组件将性能降低到 87.8%，尽管降低了能耗，因为 LLM 智能体路由器在选择候选 LLM 时不再能有效考虑异构模型的运营成本。虚拟队列机制对这个有限评估流的影响较小（92.7% 对 93.0%），这与其控制长期预算偏差而非提高单个任务性能的预期目的一致。

E.3 仅进度信号是不够的

为了区分完整路由目标与任务进度预测器本身的贡献，我们额外评估了朴素的任务进度-成本路由策略。该基线使用与 ProgRouter 相同的预测进度增益，但贪婪地选择每单位归一化成本预测进度改进最大的模型，而不考虑剩余进度差距、累积预算偏差或长期路由后果。

朴素策略仅实现了 17.7% 的通过率，同时消耗了 7797 J，大大低于完整的 ProgRouter 系统（93.0% 通过率和 4796 J）。失败的发生是因为立即进度-成本优化偏向于便宜但能力不足的 LLM，导致工作流停滞和重复的恢复尝试。这些结果表明，仅靠准确的进度预测是不够的；有效的 LLM 智能体路由需要联合考虑预测的进度增益、剩余任务难度和长期预算约束。

总体而言，上述消融结果证实 ProgRouter 的进步源于多个算法组件的交互。双路径任务进度预测器提供准确的进度估计；多视图任务进度评分器捕捉工作流演变；预算感知在线 LLM 智能体路由目标将这些信号转化为有效的 LLM 智能体选择决策。
