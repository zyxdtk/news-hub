中文摘要： 本文提出EnvOpt，一种LLM智能体静态环境的自动化端到端优化方法，作为参数调优与框架优化之外的第三条优化路径。该方法利用无验证器的训练任务，由编码智能体自动优化环境表示（如重组文件结构、建立索引、构建数据库、制作速查表等）。在5个基准测试中，EnvOpt平均降低智能体成本48%（最高88%），同时保持或提升通过率；优化后的环境可迁移至不同模型与框架，节省成本超过自身运行成本的10倍。

EnvOpt：智能体环境的自动化优化

Alex Dimakis

摘要

LLM 智能体的成本和成功率取决于其模型、框架和环境。除了已被广泛研究的参数调优和框架优化方向之外，我们提出第三个方向：对静态环境的优化。智能体通常部署在由许多任务共享的丰富环境中，例如公司的 Slack 工作区，或由数据源、文档或工单组成的复杂集合。我们将这类环境称为静态环境。我们提出了 EnvOpt，这是一种针对任意给定模型和框架的静态环境自动化端到端优化方法，使用真实或合成任务，无需任何评分器或参考答案。在 AutomationBench 上，EnvOpt 将 Claude Haiku 4.5 的成本降低了 72.7%，并将其通过率提高了 14.34%。同一环境可迁移到 Opus 5，将其成本降低 68.1%，同时通过率提升 1.34%。在 Meta-Harness 为 Haiku 4.5 优化的框架之上叠加使用时，成本进一步降低 83.4%，准确率比单独使用 Meta-Harness 提高 11.17%。在 5 个基准测试中，EnvOpt 显著降低了智能体的成本，同时提高或保持了通过率，并且可迁移到不同的模型和不同的框架。我们还讨论了自动化优化过程中常见的成功和被拒绝的环境优化策略。更广泛地说，我们的结果表明，信息呈现给智能体的方式决定了其成本和成功，因此除了参数和框架之外，环境也值得优化。

1 引言

LLM 智能体的成本和成功率取决于三个因素：模型参数、框架，以及它所交互环境的结构。前两者已通过参数调优和框架优化得到积极优化（Lee 等，2026；Agrawal 等，2026b），而环境通常被视为不可变的。然而，同样的信息可以以非常不同的形式提供给智能体。例如，公司的 Slack 历史记录既可以存放在远程服务器上并通过 MCP 访问，也可以导出为纯文本文件，使用 grep 等终端工具进行读取和搜索。仅这一选择就能显著影响智能体解决任务所需执行的工作量（Mak 等，2026）。在本文中，我们提出将静态环境优化作为改进 LLM 智能体的第三个维度，与模型参数调优和框架优化并列。静态环境是指包含大量工件集合的环境，这些工件在许多任务中保持相同或相似。例如，银行智能体在大量查询中使用相同的企业平台和数据库；公司 Slack 助手的许多任务依赖于同一个 Slack 工作区；工具包的功能请求可以依赖于同一个代码仓库。我们旨在优化静态环境如何组织和呈现给智能体。

图 1：AutomationBench 上的 EnvOpt。左图：EnvOpt 对 AutomationBench 中的静态环境进行离线优化的成本约为 150 美元，可节省运行 Claude Opus 4.8 成本的 77.5%，轻松节省多倍于运行 EnvOpt 的成本。曲线通过对运行测试集任务的实际成本进行随机采样得出。右图：EnvOpt 中离线优化工作原理的示意图。在固定模型和框架的情况下，EnvOpt 在每一步使用互不相交的训练任务集（无验证器）来优化环境。每一步之后，优化后的环境会在单独的验证集上进行测试，以确定整个过程何时停止。

尽管环境尚未得到与模型参数和框架同等的系统优化，但先前的工作已表明，改进智能体与环境的交互可以提高智能体性能。SWE-agent（Yang 等，2024）及后续工作（Xu 等，2026）表明，当为模型提供更好的仓库接口时，同一模型可以用更少的步骤修复更多问题（Xu 等，2026），但这些接口是手动设计的。后来的工作重塑环境以为强化学习（RL）创造更多训练信号（Lu 等，2026；Huang 等，2026），但这些修改旨在改进模型训练，而非已部署智能体的执行效率。PREPING 和 corpus2skill 主要关注将环境中的信息提炼为可复用的智能体记忆和技能，而不是直接优化静态环境本身的组织和表示方式（Choi 等，2026；Sun 等，2026）。总之，社区已经探索了如何在 RL 期间利用环境、优化环境的工具接口，或针对特定用例改进环境，但环境优化本身作为智能体优化的第三个方向仍未得到充分探索。

我们提出了 EnvOpt，这是一个针对任意智能体和任意静态环境进行环境优化的自动化流水线。使用无验证器的训练任务，我们让一个编码智能体（配备在静态环境上运行目标智能体的权限和预算）为目标智能体优化环境表示。优化目标包括环境所包含的内容（例如向环境添加数据库或重构环境）以及环境暴露给目标智能体的方式（例如新的 API 端点）。优化后的环境通过带验证器的验证集进行监控，以跟踪成本和通过率，并在保留的测试集上进行测试。

在涵盖工作区任务、数据工程任务和软件工程任务的五个基准测试中（见第 3 节），EnvOpt 将目标智能体在未见测试集上的成本平均降低 48%，同时通过率更高或相近。在 AutomationBench（Shepard 和 Salimans，2026）上，EnvOpt 以仅 15% 的成本实现了比 Meta-Harness（Lee 等，2026）高 9.67% 的通过率。我们还从两个方面表明 EnvOpt 构成了与框架优化和参数调优正交的优化方向：(1) 为目标智能体优化的环境可以迁移到其他智能体，甚至迁移到具有不同框架的智能体以及比提出优化的模型更强的模型；(2) 我们将 EnvOpt 的环境应用于 Meta-Harness 之上，观察到类似的成本降低和 16% 的通过率提升，优于单独使用 Meta-Harness 或 EnvOpt。

我们的贡献如下：

  • 我们将静态环境上的环境优化定义为改进 LLM 智能体的新正交方向。我们的方法可以与参数调优和框架优化相结合。
  • 我们开发了 EnvOpt，一个用于环境优化的自动化流水线，并表明在 3 类任务的 5 个基准测试中，它可以显著降低智能体在未见任务上的运行成本，同时提高或保持通过率。
  • 我们通过展示环境优化对不同前沿模型和框架的强迁移性，证明 EnvOpt 确实与参数调优和框架优化正交，并且 EnvOpt 与 Meta-Harness 结合可以进一步提升结果。
  • 我们系统地讨论了运行 EnvOpt 期间被接受和被拒绝的设计选择，这些可用于未来环境优化的研究工作。

2 方法

EnvOpt 是一个自动化研究流水线，使用 Codex 等编码智能体作为研究智能体 R，在共享静态环境的任务上自动为另一个目标智能体 T 优化环境表示。

我们将静态环境表示为 E(I)，其中 I 是环境底层的信息，例如 Slack 频道中的对话；E 是该信息以特定格式的表示，例如可通过 MCP 工具访问的官方 Slack 工作区，或存储所有对话的 Markdown 文件。我们的前提是，对于任务所需的固定 I，更好的表示 E(I) 可以显著提高智能体在任务上的 token 效率，在某些情况下还能提高准确性。给定初始静态环境 E₀(I) 上的任务实例 X_train、X_val、X_test ~ 𝒳，EnvOpt 的目标是找到最小化目标智能体 T 在 𝒳 上成本的 E：

E* = arg min_E 𝔼_{x~𝒳}[cost(T, E(I), x)]. (1)

环境演化

如算法 1 所示，EnvOpt 在 N 步中对 E(I) 进行优化。在第 k 步，研究智能体 R 在沙箱中被启动，并获得一组训练任务 X_k ⊂ X_train、来自第 k−1 步的静态环境 E_{k−1}(I)、运行目标智能体 T 的权限以及设定的预算。我们只提供 X_train 的一个子集，因为已有研究表明过多的上下文对基于 LLM 的优化有害（Li 等，2026）。我们为每一步提供互不相交的任务集以防止过拟合。研究智能体被指示在 E_{k−1}(I) 上运行 T，分析轨迹，并将 E_{k−1}(I) 作为其文件系统中的一个目录进行编辑，以降低 T 在 X_k 上的成本而不损害通过率（由于如下文所述训练任务不提供验证器，研究智能体通过代理指标或答案一致性自行判断）。例如，如果 E_{k−1}(I) 是一个没有结构的大型文件目录，E_k(I) 可以被编辑为每个领域有单独的目录、制作如何访问内容的速查表、构建一个小型数据库、为更好的工具调用创建新的工具端点等。在环境高度相似但任务间不完全相同的情况下，可以编写程序自动转换新环境（见 ）。在实现中，我们使用前沿智能体作为研究智能体，并给予其选择任何设计决策的自由。研究智能体在第 k 步的训练任务上进行内部迭代，并在该步骤结束时交付它能找到的最佳 E_k(I)。值得注意的是，我们不允许研究智能体修改 T 的框架（任何更改，尽管在我们的实验中未观察到，都将在该步骤结束时被丢弃）。这使得我们的环境演化成为与框架优化正交的方向，并且一个好的环境即使对于不同的智能体也能显示出显著的成本降低（ ）。

算法 1 环境演化

输入：初始环境 E₀(I)、目标智能体 T、研究智能体 R、训练任务 X_train（无验证器）、验证任务 X_val（带验证器）、步数 N、每步预算 B、准确率容差 δ

将 X_train 划分为互不相交的子集 X₁, …, X_N
c₀ ← cost(T, E₀(I), X_val)
a₀ ← acc(T, E₀(I), X_val)
for k = 1 to N do
　在沙箱中启动 R，配备 X_k、E_{k−1}(I)、运行 T 的权限和预算 B
　Ẽ ← E_{k−1}(I)
　τ ← T 使用 Ẽ 在 X_k 上的轨迹
repeat
　　R 分析 τ 并将 Ẽ 编辑为候选 E′
　　τ′ ← T 使用 E′ 在 X_k 上的轨迹
if τ′ 的成本低于 τ 且 R 判断准确率保持（代理指标/答案一致性）then
　　　Ẽ ← E′，τ ← τ′
else
　　　丢弃 E′
end if
until 预算 B 耗尽或 R 终止
　E_k(I) ← Ẽ；丢弃对 T 框架的任何更改
　c_k ← cost(T, E_k(I), X_val)
　a_k ← acc(T, E_k(I), X_val)
if c_k > c_{k−1} 或 a_k < a_{k−1} − δ then
return E_{k−1}(I)
end if
end for
return E_N(I)

无验证器训练

为了防止研究智能体在训练步骤中进行奖励作弊（例如直接写下训练任务的答案以降低成本），我们对训练中使用的任务隐藏所有验证器。这也缓解了某些静态环境高质量任务稀缺的问题，因为我们可以合成分布内的查询（无需合成验证器）用于训练（见第 3 节）。我们保留一个带验证器的单独验证集 X_val，并在每个训练步骤 k 结束时用 E_k(I) 在其上运行目标智能体，以决定何时停止环境演化。具体而言，如果 cost(T, E_k(I), X_val) > cost(T, E_{k−1}(I), X_val)，或者验证集上的通过率比第 k−1 步显著变差，我们就停止演化并使用 E_{k−1} 作为最终优化后的环境。

3 实验

我们在 3 类任务的 5 个基准测试上评估 EnvOpt：工作区任务（AutomationBench（Shepard 和 Salimans，2026）、Workspace-Bench（Tang 等，2026））、数据工程任务（Data-Eng-Bench（Snowflake Inc.，2026））以及软件工程任务（gskill 中使用的 Bleve 仓库任务（Agrawal 等，2026a）和 advisor models 中使用的 SWE Agent Efficiency 任务（Asawa 等，2026））。与基线相比，我们观察到高达 88% 的显著成本降低，同时智能体成功率更高或相近。我们还表明，在所有测试场景中，优化后的环境也能大幅提高不同框架和不同模型的 token 效率和通过率，包括比目标智能体更强的智能体，展示了强大的迁移能力。值得注意的是，EnvOpt 还可以构建在 Meta-Harness 等框架优化方法之上，进一步推进帕累托前沿。

AutomationBench 包含工作区任务，要求智能体在企业环境中回答问题或完成工作，通常涵盖 Slack、GitHub、Gmail、Salesforce 等多个平台。在 600 个公开可用的任务中，我们随机抽取 200 个任务作为 X_test，96 个作为 X_val，其余用于训练任务池。训练每步进行 20 个任务，并在第 5 步停止，此时 X_val 上的结果开始饱和。我们使用 Claude Code（Anthropic，2025a）搭配 Claude Opus 4.8（Anthropic，2026b）作为研究智能体，使用 Claude Code 搭配 Claude Haiku 4.5（Anthropic，2025b）作为目标智能体。

如 所示，我们观察到目标智能体的 token 效率和通过率显著提升，最终成本降低 72.7%，通过率提高 14.3%。我们在 中展示了每一步的性能。我们还使用相同的训练任务池、相同的研究智能体或提议者、相同的目标智能体运行 GEPA（Agrawal 等，2026b）和 Meta-Harness（Lee 等，2026），并在相同的 X_test 上进行评估。EnvOpt 产生的环境在成本和通过率上都取得了显著更好的结果，即使训练任务没有验证器。

我们还考察了优化后的环境在不同框架和模型间的迁移能力，平均成本降低 75.7%，通过率普遍更高。值得注意的是，使用 Claude Code 和 Opus 4.8 作为研究智能体的 EnvOpt 能够迁移到使用 Opus 5 的 Claude Code（Anthropic，2026c）。使用 EnvOpt 的 Haiku 5.5（Anthropic，2026a）实现了高于 Opus 4.8 甚至接近 Opus 5 的通过率。

此外，EnvOpt 可以应用于 Meta-Harness 之上，进一步提高智能体的 token 效率和通过率。使用为 Haiku 4.5 优化的框架，EnvOpt 可以进一步推进 Haiku 4.5 的帕累托前沿。在迁移到 Opus 5 时，虽然单独使用 Meta-Harness 在通过率上没有显示增益，但在 Meta-Harness 之上的 EnvOpt 仍然以更低的成本提高了通过率。

Workspace-Bench 在工作者的个人工作区上评估智能体，包括研究人员、工程师、产品经理等。我们使用官方排行榜所用的 100 个任务的公开集合，划分为 80 个任务作为 X_test，20 个作为 X_val。由于我们的训练步骤不需要验证器，且该基准的任务数量稀少，我们直接使用 Claude Code 和 Claude Opus 5 合成无验证器的查询作为训练任务。我们每步提供 20 个不同的训练任务，并使用 Claude Code 搭配 Opus 4.8 作为研究智能体，Codex（OpenAI，2025）搭配 GPT-5.4-mini（OpenAI，2026b）作为目标智能体。Claude Code 搭配 Sonnet 5 用作在 X_test 和 X_val 上进行评估的裁判智能体。我们在 中展示结果。我们观察到目标智能体的成本降低 47.65%，通过率提高 3.3%。在向非目标智能体的迁移方面，我们在 Codex 搭配 GPT-5.6-Sol（OpenAI，2026a）和 Claude Code 搭配 Opus 5 上进行评估，与基线相比观察到平均 56.7% 的成本降低和稳定的通过率。

Data-Eng-Bench 在 dbt 数据工程任务上评估智能体。我们使用 73 个任务作为 X_test，19 个作为 X_val。同样，由于现有任务稀缺，我们合成了无验证器的查询用于训练，每步 20 个不同的任务。我们使用 Codex 搭配 GPT-5.6-Sol 作为研究智能体，Codex 搭配 GPT-5.6-luna 作为目标智能体，在不损害性能的情况下将成本降低了 53.44%。在非目标智能体上，我们观察到平均 53.54% 的成本降低（见 ）。

软件工程任务

我们采用先前工作中改进智能体在 SWE-Bench 风格任务上 token 效率的两个基准，其中智能体被要求在给定的代码仓库中修复 bug，所有任务共享同一个代码库。gskill 使用来自同一代码库的带验证器任务优化编码智能体的技能，并在 Bleve 搜索库上报告了更高的通过率和更快的完成时间。Advisor models（Asawa 等，2026）使用强化学习训练一个向编码智能体提供建议的顾问模型。在基于 tenacity 库的 SWE Agent Efficiency 基准上，advisor models 在使用显著更少步骤的同时保持了与基线相同的通过率。我们使用 gskill 和 advisor models 提供的相同 X_train、X_test 和 X_val 运行 EnvOpt，并使用相同的目标智能体。如图 2 所示，在 Bleve 仓库上，EnvOpt 仅用 gskill 56.9% 的完成时间就保持了接近满分的成绩。在 tenacity 仓库上，EnvOpt 以更少的步骤实现了比 Advisor Models 高 8.9% 的通过率。这些结果表明，即使在软件工程任务上，EnvOpt 也显著优于其他改进智能体 token 效率的方法。

4 讨论

4.1 环境优化示例

准备文件内容

在 AutomationBench 上，研究智能体构建了一个程序，直接检索 Gmail 信息并以纯文本形式呈现给目标智能体，涵盖发件人、主题、邮件 ID 和邮件内容块。这样目标智能体可以直接读取文本，而无需在大量工具调用上花费 token。在 Workspace-Bench 上，不同格式的文件（如 .xlsx）被转换为 .txt 文件，使目标智能体更容易读取文件，无需进行进一步的解析。

制作速查表

在训练期间会创建存储未来任务重要信息的速查表。例如，AutomationBench 的一个速查表存储了智能体创建 Jira 问题、在 Slack 上发消息、记录 Xero 付款等所需的所有 API 端点，因此它无需调用 api_search 或 api_fetch 来获取端点。对于 Bleve 仓库的 bug 修复，构建了一个存储复杂工具调用模板命令的速查表，因此智能体无需从头组合搜索命令。

建立索引

对于 Workspace-Bench，智能体部署时带有模拟企业员工计算机的大量文件。因此，研究智能体构建了一个作为单个文本文件的索引映射，存储所有所需文件的路径、大小和类型，这样智能体只需在索引文件上搜索，而无需在庞大的文件系统上花费 token 和时间。

构建数据库

在 Data-Eng-Bench 上，研究智能体构建了一个 SQLite 数据库，存储表的位置、每个代码脚本写入哪些文件、每个表中存储的信息类型等。目标智能体可以快速定位所需信息，而无需浏览数千个文件。

构建文件优先级排序程序

对于 Bleve 仓库，研究智能体构建了一个程序，接收任何 bug 报告并基于关键词匹配输出最可能受影响的 8 个 .go 文件。目标智能体可以快速定位其可能需要调查以修复 bug 的文件。

编辑的自动化测试

对于 Tenacity 仓库，构建了一个 validate_tenacity.py，用于自动获取目标智能体所做的代码更改、搜索相关测试文件、运行测试并返回判定结果。这可以快速验证候选编辑，无需额外 token 成本，并加快了目标智能体的整个 bug 修复工作周期。

4.2 被拒绝的环境优化

我们总结了在训练期间或在 X_val 上运行后被丢弃的环境优化：

在单个文件中存储过多信息导致更多探索

对于 Data-Eng-Bench，研究智能体试图创建一个大文件来存储数据库中所有列的所有可能值。虽然这旨在帮助智能体用更少的 token 检索正确的信息，但将所有内容放入一个大文件反而鼓励智能体进行更多工具调用来探索这些值，因为一个工具结果向智能体揭示了还有许多它尚未探索的信息，最终增加了成本。

构建返回过多文件的搜索工具导致更多读取

对于 Workspace-Bench，构建了一个搜索工具来帮助智能体定位任务需要读取的文件。虽然该工具成功减少了搜索所需文件的 token 成本，但它经常在搜索结果中包含不必要的文件，这促使智能体读取更多文件，从而增加了成本。

添加仅适合部分训练任务的测试

在 Bleve 仓库上 EnvOpt 的第 2 步中，向仓库中的一个测试脚本添加了一个检查，该检查扫描特定的 bug 修复代码片段，如果该片段存在则直接使测试失败。这旨在节省修复 bug 所需的时间，并且在 X₂ 上运行良好。然而，对于 X₃，一些正确的 bug 修复被这个额外的检查拒绝，智能体需要花费更多时间来绕过该检查。

4.3 成本降低分析

为了说明 EnvOpt 的成本降低来自哪里，我们将输入 token 和输出 token 分解为多个类别，包括不同类型的工具调用、工具执行结果（环境反馈）、思考 token、智能体历史等。我们比较了基线环境和 EnvOpt 环境之间每个类别的 token 数量，并在 中展示结果。我们观察到，最显著的 token 成本降低来自输入 token 的环境反馈类别。输出 token 方面的工具调用类别也有显著的节省。这些结果与我们的动机一致，即优化环境以实现更好的智能体交互。

4.4 消融实验：仅工具优化

在环境优化过程中，EnvOpt 还可以优化访问新环境的方式，包括新工具。我们研究了仅使用新工具的有效性。在 AutomationBench 上，我们在原始环境 E₀ 上使用来自 E₅ 的工具测试 Claude Code 搭配 Haiku 4.5。如 所示，我们发现仅工具优化就可以在 token 效率和通过率上带来改进，但显著低于同时优化工具和环境的效果。由于工具优化可能已被框架工程覆盖，这一消融实验表明，除了框架工程之外，EnvOpt 带来了显著更多的优化空间。

4.5 训练成本和时间

我们在 中展示了所有 5 个基准的总训练成本（包括研究智能体启动的目标智能体运行的成本）和时钟时间。在 中，我们假设有 1000 个此类任务，比较了累计训练成本与在不同智能体上运行未见任务所节省的成本。我们表明，对于大规模部署的前沿智能体，我们可以轻松节省超过 EnvOpt 运行成本 10 倍的费用。

4.6 研究智能体行为

在这里，我们展示了从研究智能体中观察到的一些有趣行为，包括但不限于失败模式，以及训练期间的行为如何与 EnvOpt 在保留任务上的性能相关。

使用不可靠的验证代理

由于我们不提供训练任务的验证器，Workspace-Bench 的研究智能体偶尔在训练步骤中使用答案长度和关键词匹配等代理来确认答案质量。这通常被证明会损害在保留任务上的性能。在观察验证集后，我们更新了研究智能体的指令以防止这种行为（见附录 A）。

使用研究智能体行为预测验证性能

我们发现，对于 AutomationBench，验证集上的成本降低与每一步训练期间工具调用模式的变化程度相关，该变化通过步骤前后训练运行之间每任务工具调用次数的差异来衡量，Pearson 相关系数为 0.75。或者，通过查看每一步中获得超过 30% 成本降低的训练任务比例，其与验证集成本降低的 Pearson 相关系数在 AutomationBench 上为 0.82，Workspace-Bench 上为 0.70，Data-Eng-Bench 上为 0.56。

未能遵循指令

尽管被告知不要触碰与模型或框架相关的任何内容，Workspace-Bench 中的研究智能体在其第 6 步期间仍试图更改 Codex 的推理努力程度。这一更改在保留任务上无效，因为我们只保留研究智能体沙箱中的环境目录并丢弃其他工件。然而，在训练步骤早期的这种行为可能会显著影响研究智能体在该步骤期间的优化，从而可能损害性能。

没有验证集我们能走多远

从测试的五个基准来看，我们观察到即使不运行验证任务，运行 EnvOpt 3 个训练步骤通常是安全的。然而，我们注意到这只是一个经验性的结论，带有真实验证器的验证集对于可审计的环境优化仍然很重要。

优化中的早期缺陷可能在后续许多步骤中仍未被发现

在 Data-Eng-Bench 中，研究智能体在第 1 步引入了一个基于分号解析的 SQL 语句分割器。但如果分号出现在引号文本中，该分割器就会失败。第 1 步优化中的这个 bug 直到第 5 步才被发现。这在所有 4 个步骤中都增加了成本，因为目标智能体无法判断是分割器损坏了它的查询，所以它将失败归因于自己的模型，并花费 token 重新构建查询。

5 结论

我们将静态环境上的优化表述为智能体优化的第三个方向，与框架优化和参数调优并列。本工作引入了 EnvOpt，一个用于端到端环境优化的自动化研究流水线，并表明它在五个基准上显著降低了智能体成本，同时保持或提高了成功率。EnvOpt 在不同模型和框架之间有效迁移，优于先前的智能体优化方法，包括 GEPA、Meta-Harness、gskill 和 advisor models。此外，EnvOpt 可以构建在 Meta-Harness 之上，进一步推进帕累托前沿。我们的分析表明，EnvOpt 显著优于仅工具优化，并且节省的成本超过运行 EnvOpt 本身成本的 10 倍。最后，我们详细介绍了成功和被拒绝的环境优化的关键示例，作为定性参考，并为未来研究提供设计经验。

A.1 AutomationBench

你的工作方式（本会话完全自动化）

没有人在监视你，你也不会得到任何进一步的指令——所以不要提前停止，不要请求确认，也不要等待。全程持续工作。

  • 进行多轮循环：更改访问层 → 在训练任务上运行目标智能体 → 读取其成本和它做了什么 → 保留有帮助的部分 → 尝试下一个想法。把"我做了一个改进"当作开始，而不是结束。
  • 当你真正用尽了想法或达到支出预算（见下文）时，在 /work 中留下一个简短的 REPORT.md：你尝试了什么，什么有帮助，什么没有，前后的成本和行为，以及你接下来会尝试什么。该报告是终点线。

你是无头且非交互式的。没有人会重新调用你，也没有唤醒/通知/等待机制——它们在这里不会触发。如果你结束你的回合，会话将永久结束，未完成的工作将丢失。

永远不要结束你的回合去"等待"。基准运行需要几分钟——在前台运行并让它完成，或者在同一回合中用阻塞循环轮询（until [ -f /work/out/run.json ]; do sleep 5; done）。保持你的回合活跃。

你没有网络访问权限。你需要的一切都在这里。

你的任务

一个固定的 AI 助手在约 47 个模拟 SaaS 应用（Gmail、Salesforce、Slack、Google Sheets、QuickBooks、Zendesk 等）中完成业务工作流任务。它仅通过一个小的工具层接触那个世界。它的模型和智能体是固定的——不是你可以触碰的。

属于你的是那个访问层：它可以调用的工具、工具返回什么、世界的数据在到达助手之前如何组织/呈现，以及告诉它如何工作的指令。

通过给这个助手一个更好的访问层，让它更好且更便宜地完成任务——同时推进两个方面：更少的 token/工具调用，以及更频繁地真正完成任务。

你正在优化助手工作所通过的世界抽象——塑造它，使正确的操作容易且低成本地到达。

有两个杠杆，第一个最重要：

  1. 提前组织/预加载世界。
    每个任务从一个完全填充的世界开始。让访问层在任务开始时通过基础工具预取它，然后反规范化/解析引用/布局它，并交给助手一个紧凑的块——这样它读取所需的内容，而不是通过对噪声填充数据的多次 list/get/query 调用来发现它。
    这是更大的杠杆——在这里要大胆，甚至激进。
    重塑世界的表示；不要只是把更好的探照灯指向同一堆原始数据。
    注意——"重塑环境状态"在这里如何工作：与具有共享文件的工作区不同，每个任务都有自己的全新世界，助手没有文件系统——只有这些工具。所以你不能预先构建一个静态摘要或交给它文件。相反，你的访问层代码在任务开始时自动地、逐任务地进行重塑。
  2. 工具 + 指南。
    更好的工具（合并往返调用，返回反规范化的结果）和一个始终开启的指南，教会助手高效、正确的模式。

你编辑的访问层

你的访问层是位于 /work/layer 的 Python 包。这是交付物——就地编辑它。

先阅读它：它可能已经带有前一轮的改进——在这些改进的基础上构建，而不是从头开始。如果它仍然是原始基线（三个普通工具，没有预加载任何内容——在其上运行与原始基准相同），则从那里开始构建。

该包如何接入目标智能体的运行：

  • LAYER_TOOLS（一个列表）——助手看到的工具。每个工具以 base 作为其第一个参数，加上助手传递的参数。base 是通往世界的唯一门户，对助手的工具规范隐藏：
  • base.search(query, top_k)——发现端点（原始 api_search）
  • base.fetch(method, url, params, body)——调用端点（原始 api_fetch）
  • base.encode(text)——用于 Gmail 正文的 base64url（原始 base64_encode）

工具的主体在你的容器中运行；它仅通过 base 接触世界。所以你可以制作一个链接多个 base.fetch 并返回一个反规范化结果的工具。

  • inject_context(state, base)（可选——添加它以进行预加载）——在任务开始时、助手行动之前调用一次。通过 base 预取世界，构建一个紧凑的概览，并将其作为单个系统消息前置：state["prompt"].insert(0, {"role": "system", "content": ...})。这是杠杆 1——而且因为它是代码而不是助手 token，预取在助手成本方面是便宜的。

你可以添加工具、重写它们的返回内容、添加 inject_context、添加辅助模块/速查表——任何东西，只要工具仅通过 base 接触世界。

你如何测试它——以及你如何判断

你自己用 evolve-run 运行目标（它通过你的层在训练任务上运行助手，并写入每个任务的成本和完整轨迹）：

evolve-run \
  --model claude-haiku-4-5-20251001 \
  --base-url https://api.anthropic.com/v1 \
  --api-key-var ANTHROPIC_API_KEY \
  --reasoning-effort high \
  --layer-dir /work/layer \
  --prompts /work/prompts.json \
  --max-concurrent 4 \
  --export-json /work/out/run.json

没有答案钥匙，也没有评分——你不会看到。

像你判断任何智能体一样判断助手做得如何：对照任务提示阅读它的轨迹和最终行动——它是否找到了正确的记录，执行了任务要求的操作，然后停止了？所以循环是：更改层 → evolve-run → 查看它花费了多少以及它是否仍然完成了任务 → 保留有帮助的，丢弃没有帮助的。

始终在完整训练集上测量（每次前后对比），并运行比较 2–3 次（成本因运行而异）。

--max-concurrent 4 以加快迭代速度（不要超过 4）。

probe tasks

你这一步的预算

这一步你最多可以花费 30 美元运行目标智能体（将你运行的 total_cost 相加）。
