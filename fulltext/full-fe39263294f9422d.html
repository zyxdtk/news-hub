摘要

诸如 VerilogEval 之类的基准测试一直支持着大语言模型（LLM）在硬件描述语言（HDL）生成方面的快速进步。然而，近期的 HDL 生成系统在 VerilogEval 上的通过率已超过 90%，留给揭示进一步进步的空间十分有限。为了在一个具有实际重要性的硬件开发任务上为进一步进展提供具有挑战性的目标，我们引入了 CPU-Eval——一个由六款 CPU 构建的、包含 339 个 HDL 生成问题的基准测试。这些问题源自实用的 CPU 设计（包括已流片的 CPU 系列），涵盖从小型嵌入式核心到支持 Linux 的乱序核心，并覆盖以 SystemVerilog、Chisel 和 SpinalHDL 编写的多样化 CPU 功能。在每个问题中，LLM 执行生成 HDL 这一真实的 CPU 开发任务。在七个最先进的 LLM 上，CPU-Eval 的平均 pass@1 比 VerilogEval v2 Spec-to-RTL 低 45.14 个百分点，揭示了被 VerilogEval 高通过率所掩盖的能力差异。CPU-Eval 揭示了源代码行数更多的子模块的 pass@1 更低，这促使人们为 LLM 辅助硬件生成采用细粒度的模块化设计。我们还表明，以使用较少的 HDL 编写的 CPU 的 pass@1 更低，这促使设计者在部署之前验证 LLM 是否足够熟练地生成他们所用 HDL 的代码。

I 引言

图 1： 339 个 CPU-Eval 问题之一的生成与评估流程： CPU-Eval 向 LLM 提供 Ibex CPU 算术逻辑单元（ALU）的提示词； LLM 生成 ibex_alu，CPU-Eval 将其集成到 Ibex 中； CPU-Eval 执行测试程序； 轨迹比较定位功能错误。

诸如 VerilogEval [1, 2] 之类的基准测试一直支持着大语言模型（LLM）在硬件描述语言（HDL）生成方面的快速进步。基准测试使研究人员能够评估新的 LLM 和生成方法是否产生功能更正确的 HDL，而编译和功能测试失败则为改进模型和开发生成技术提供了具体反馈。在训练阶段，VeriReason 通过推理步骤和测试平台扩展了 RTLCoder 数据集，将测试平台结果用作强化学习的奖励，并使用 VerilogEval 证明所得到的模型生成了功能更正确的 RTL [3, 4]。在推理阶段，RTLFixer 利用 VerilogEval 问题的编译器错误迭代修复语法错误 [5]，而 VerilogCoder 则利用 VerilogEval 测试平台失败和波形追踪来定位并修复功能错误 [6]。因此，基准测试为分析失败和开发模型与生成方法提供了共同基础，而不仅仅是简单地比较它们。

为了使这一研究循环得以持续，基准测试必须能够揭示 HDL 生成方法之间可衡量的差异，并为失败分析和修复提供具有挑战性的案例。然而，近期的系统已在多个 VerilogEval 问题集上实现了超过 90% 的通过率 [7, 8, 9]，留给进一步研究的未解决案例越来越少。一些基准测试通过从开源硬件设计中提取具有挑战性的问题来解决这一问题 [10, 11]。例如，RealBench 要求 LLM 从四个开源硬件 IP 生成模块，并报告 o1-preview 的 pass@1 为 13.3%，而其在 VerilogEval v2 Spec-to-RTL（S2R）上为 70.5% [10]。尽管如此，现有基准测试并未充分衡量 LLM 在完整 CPU 中实现子模块的能力，因为它们仅覆盖有限范围的 CPU 设计，并且没有将生成的子模块作为这些 CPU 的一部分进行评估。

为了弥补这一差距，我们引入了 CPU-Eval，这是一个在六款完整、实用的 CPU 中生成子模块的 339 问题基准测试。得益于其广泛的 CPU 覆盖范围，CPU-Eval 为 LLM 辅助处理器设计提供了实用见解，详见第 III 节。CPU-Eval 的任务反映了设计者通常在现有 CPU 的基础上进行构建，仅设计特定目的所需的额外子模块，而不是从头设计整个 CPU 的做法 [12, 13]。

我们做出以下贡献：

  1. 我们从六款实用的 CPU 实现中构建了 339 个 HDL 生成问题，包括已流片的 CPU 系列。这些问题涵盖从小型嵌入式核心到支持 Linux 的乱序核心，覆盖数据通路和复杂控制逻辑中的多样化 CPU 功能。CPU-Eval¹ 覆盖三种 HDL：RTL 层面的 SystemVerilog 以及更高层的硬件构建语言 Chisel 和 SpinalHDL。

¹CPU-Eval 可在 https://github.com/next-edge-ai-ishihara/cpu-eval 获取。

  1. 我们为 LLM 定义了一个基准测试任务，该任务将子模块级 HDL 生成与 CPU 级功能评估相结合，且不依赖商业 EDA 工具。CPU-Eval 将每个生成的子模块集成到其 CPU 中，在该 CPU 上执行测试程序，并将 CPU 的执行轨迹与参考 ISA 轨迹进行比较，以检测与预期 CPU 行为的偏差。

  2. 我们通过在 CPU-Eval 上评估七个最先进的 LLM，揭示了被 VerilogEval 高通过率所掩盖的模型能力差异，其平均 pass@1 比 VerilogEval v2 S2R 低 45.14 个百分点。CPU-Eval 表明，源代码行数更多的子模块的 pass@1 会下降，且以使用较少的 HDL 编写的 CPU 的 pass@1 更低。

我们的发现对 LLM 辅助硬件设计有两个启示。首先，源代码长度趋势促使人们为 LLM 采用具有更小子模块的细粒度模块化设计。其次，HDL 之间的差异促使设计者使用诸如 CPU-Eval 之类的实用基准测试，在部署之前验证 LLM 是否足够熟练地生成他们所用 HDL 的代码。

II CPU-Eval 基准测试设计

II-A HDL 生成与评估的示例

每个 CPU-Eval 问题将指定一个 CPU 子模块的提示词与对生成实现的功能测试配对。CPU-Eval 衡量 LLM 生成的 HDL 是否在完整 CPU 中正确运行，如果不正确，则记录程序执行在何处偏离参考 ISA 模型。图 1 展示了 LLM 如何求解以及 CPU-Eval 如何评估这 339 个问题之一。图 1(a) 中的提示词指定了 Ibex CPU 的算术逻辑单元（ALU），LLM Gemma 4 31B 生成了图 1(b) 所示的 ibex_alu 子模块。生成的 HDL 在计算除法器使用的结果之前，错误地丢弃了每个除法器操作数的最高有效位。在每个除法步骤中，Ibex 使用该结果来决定是否减去除数并设置相应的商位，因此截断其操作数可能会改变商。CPU-Eval 将此 HDL 集成到 Ibex 中并构建 RTL 模型。然后，它在 CPU 的 RTL 模型和 Spike ISA 模型上运行图 1(c) 所示的测试程序 busy_work.S。图 1(d) 比较了两条执行轨迹。在 div 指令之前，两条轨迹都显示 x28 包含 0x77ab6f90（2,007,723,920），x7 包含 0xef56df20（−279,519,456），因此正确的有符号商为 0xfffffff9（−7）。随后 Spike 将该值写入 x29，而操作数截断使 RTL 模型写入 0xfffffffa（−6）。因此，这些轨迹识别出了暴露功能错误的指令和架构状态更新，而不是仅仅报告生成的 HDL 失败。研究人员可以分析此类具体失败以改进 LLM 和 HDL 生成方法。

CPU-Eval 包含来自六款 RISC-V CPU 的 339 个 HDL 生成问题，涵盖广泛的 CPU 设计范围。我们从 RISC-V International 维护的 RISC-V Exchange 的 Core(s) 类别中 [14, 15]，选择了具有可再分发 HDL 和不使用商业 EDA 工具的文档化验证流程的 CPU。如表 I 所总结，这些 CPU 涵盖从小型嵌入式核心到支持 Linux 的乱序核心，其硬件源代码以 SystemVerilog、Chisel 和 SpinalHDL 编写。CPU-Eval 针对用于构建物理处理器的实用 CPU 系列，而不是仅为基准测试练习而创建的设计。例如，Ibex 已经历多次流片 [16]，CVA6 的前身 Ariane 采用 22 纳米 FDSOI 工艺制造 [17]，一款基于 BOOM 的核心采用 28 纳米 CMOS 工艺制造 [18]，而 VexRiscv 被用于已流片的 Baochip 1x [19]。CPU-Eval 公开可用，使研究人员无需访问商业 EDA 工具即可评估和开发 HDL 生成方法。

II-D 问题质量检查

仅凭低通过率并不能证明一个 HDL 生成问题是困难的，因为不完整的提示词和有缺陷的测试也可能导致生成的 HDL 失败。例如，RTL-BenchMT 发现 VerilogEval 中存在省略测试所需寄存器初始化的提示词 [24]。STG 发现，有缺陷的 VerilogEval 测试平台可能会拒绝正确的 HDL [25]。因此，在将 LLM 失败解读为问题难度的证据之前，我们会检查每个 CPU-Eval 提示词是否缺少需求，以及每个测试是否存在错误判定。

II-D 1 检查提示词是否缺少规范

为防止规范不完整，我们通过检查子模块的源代码以及 CPU 与其连接的位置，枚举每个问题中子模块的接口和外部所需行为。然后，我们将每一项映射到设计文档、指令集和接口规范或周围 HDL 的逐字摘录。最终的提示词提供了人类开发者实现该子模块时会使用的设计信息。

II-D 2 检查测试判定

作为功能评估的可靠起点，CPU-Eval 使用 CPU 开发者运行以验证其完整 CPU 的测试程序。对于 CVA6，CPU-Eval 使用 RISC-V 架构测试，该测试检查 RISC-V 规范的实现，CVA6 开发者将其包含在回归测试中 [26, 27]。VeeR EL2 评估使用由 Linux 基金会托管的 CHIPS Alliance 维护并由 CPU 开发者在持续集成中运行的 riscv-dv 回归测试 [28, 29, 30]。Rift2Core 和 BOOM 使用两个项目都使用的 riscv-tests 处理器测试套件进行测试 [31, 32, 33]。VexRiscv 测试程序来自该项目的 TestIndividualFeatures 回归套件 [34]。对于 Ibex，CPU-Eval 使用 Ibex 项目在持续集成中运行的 simple_system 程序 [16]。

我们不假设重用这些测试程序能保证每个 CPU-Eval 问题的判定正确。在纳入问题之前，我们首先确认其测试接受 CPU 存储库中该子模块的源代码。然后，我们准备若干 HDL 实现，每个实现包含不同的功能错误，但仍能成功构建和仿真。测试必须拒绝每个实现，因为其执行与预期的 CPU 行为不同。如果错误的实现通过了，我们会确定是程序未能触发该错误还是比较遗漏了其影响，并相应地加强程序或比较。每次更改后我们都会重复这些检查。

例如，在 CVA6 的 store_unit 问题中，一个为每个存储写入零的实现最初通过了，因为比较记录了指令和寄存器更新，但遗漏了内存更新。因此，我们扩展了比较以包含内存写入信息，例如地址和数据值。扩展后的比较既拒绝了为每个存储写入零的实现，也拒绝了抑制每次内存写入的另一个实现，同时继续接受 CVA6 存储库中的 store_unit 源代码。通过这种方式，我们提高了 CPU-Eval 测试的可靠性。

III 实验

III-A 实验设置

为了揭示 LLM 辅助处理器设计的实用见解，我们在 CPU-Eval 的 339 个问题和 VerilogEval v2 S2R 上评估了七个最先进的 LLM。我们评估了由 Ollama Cloud 提供服务的五个开放权重 LLM：Gemma 4 31B、gpt-oss-120B、Qwen3.5-397B、DeepSeek-V4.1-Flash 和 Kimi K2.7 Code。我们还评估了两款旗舰商业 LLM：GPT-5.6 Sol 和 Claude Opus 5。对于每个问题，我们向每个 LLM 提供提示词，并独立采样 10 个 HDL 实现。对于五个 Ollama Cloud 模型，我们将温度设置为 0.8，top-p 设置为 0.95，与 VerilogEval 的采样设置相匹配 [1]。对于这五个模型，我们设置了 65,536 个 token 的限制，该限制仍然足以生成每个 CPU-Eval 问题所需的 HDL，同时阻止无限重复输出的有缺陷生成。我们将 gpt-oss-120B 的 think 设置为 low，将其他四个开放权重模型的 think 设置为 false，并将 GPT-5.6 Sol 和 Claude Opus 5 的推理努力设置为 low。

我们报告 k ∈ {1, 10} 的 pass@k。pass@k 衡量某个问题的 k 个生成的 HDL 实现中至少有一个通过的概率。遵循 Chen 等人 [35] 和 VerilogEval [1]，我们从为每个问题生成的 n = 10 个 HDL 实现中估计 pass@k：

pass@k = (1/|P|) Σ_{p∈P} (1 − C(n−c_p, k) / C(n, k))

其中 P 是问题集，c_p 是问题 p 通过的生成 HDL 实现数量。

III-B CPU-Eval 揭示的能力差异

如表 IV 所示，七个 LLM 在 CPU-Eval 上的平均 pass@1 比 VerilogEval v2 S2R 低 45.14 个百分点。Claude Opus 5 在 VerilogEval v2 S2R 上实现了 92.69% 的 pass@1，但在 CPU-Eval 上仅为 62.86%，这表明 VerilogEval 的高通过率并不意味着能够为实用 CPU 中的子模块生成 HDL 的可比能力。CPU-Eval 揭示了被 VerilogEval 高通过率所掩盖的模式，如下所述。

III-B 1 对源代码长度的敏感性

图 2：按源代码长度划分的平均 pass@1。 突出显示两个商业模型在 VerilogEval v2 S2R 上的接近饱和的平均值。 说明随着 CPU-Eval 中 SystemVerilog 子模块变长，各模型的 pass@1 如何下降。 和 突出显示五个开放权重模型与两个商业模型在 Chisel 和 SpinalHDL 子模块上的平均 pass@1 差异。

VerilogEval v2 S2R 上接近饱和的分数掩盖了 pass@1 如何随源代码长度变化。如图 2(a) 所示，尽管源代码长度增加，两个商业模型的平均 pass@1 从 1–20 行的 89.74% 上升到 21–50 行的 94.66%。两个分数都接近饱和，1–20 行范围内的大多数剩余失败源于第 II-D 节讨论的那种有缺陷的提示词或测试。因此，这种明显的反转几乎不能提供有关模型对源代码长度敏感性的信息。

图 2(b) 和 (c) 显示，随着源代码长度增加，CPU-Eval 的 SystemVerilog 和 Chisel 子模块的平均 pass@1 呈整体下降趋势。图 2(b) 中 500 行以上的范围包括 CPU-Eval 最长的子模块（3,176 行），而 VerilogEval v2 S2R 问题提供的最长解决方案仅包含 78 行。在两个面板中，每个序列在其最长有数据的范围内都显著低于其最短有数据的范围。

图 2(b) 揭示了随着 SystemVerilog 子模块中源代码行数的增加，各模型的 pass@1 下降程度不同。五个开放权重模型的平均值从 1–20 行范围内的 94.55% 几乎崩溃至 500 行以上的 1.38%，下降了 93.17 个百分点。GPT-5.6 Sol 和 Claude Opus 5 的下降幅度较小，分别为 79.79 和 55.55 个百分点，在 500 行以上仍保持 20.21% 和 43.54% 的 pass@1。因此，CPU-Eval 不仅通过整体 pass@1 区分模型，还通过它们生成具有更多源代码行数的子模块的能力来区分模型。

ChipVerilog 报告，随着源代码长度的增加，LLM 在来自多个硬件设计（包括两款小型 CPU）的模块中生成功能正确的 HDL 的频率降低 [22]。CPU-Eval 在仅从六款完整 CPU 中提取的子模块中显示出相同的总体趋势，并进一步揭示了下降幅度在 LLM 和 HDL 之间存在差异。

这种对源代码长度的敏感性对 LLM 辅助硬件设计具有启示意义。模块化设计通过将复杂系统分解为可以独立开发和测试的更小组件，使人类开发者更易于管理复杂系统 [36]。我们的结果表明，细粒度模块化设计的较小子模块同样可以使硬件生成任务对 LLM 更易于处理。

III-B 2 HDL 之间的差异

图 2(b)–(d) 揭示了即使按源代码长度对子模块进行分组，以不同 HDL 编写的 CPU 之间仍存在显著差异。在所有三种 HDL 共享的每个源代码长度范围内，七模型平均 pass@1 在 SystemVerilog CPU 上最高，在 Chisel 和 SpinalHDL CPU 上显著较低。例如，在包含 51–100 行的子模块中，两个商业模型在 SystemVerilog CPU 上的平均值为 80.31%，在 Chisel CPU 上为 44.83%，在 SpinalHDL CPU 上为 6.67%。因此，在 SystemVerilog 子模块上的成功并不能表征模型为以 Chisel 或 SpinalHDL 编写的 CPU 生成子模块的能力。

图 2(c) 和 (d) 还表明，这种难度在不同模型之间存在显著差异。对于包含 1–20 行的 Chisel 子模块，两个商业模型比五个开放权重模型高出 55 个百分点。对于包含 21–50 行的 SpinalHDL 子模块，差异为 51 个百分点。

一种假设是模型受益于有关 HDL 的公开信息。截至 2026 年 9 月 19 日，面向程序员的公开问答网站 Stack Overflow 包含 3,672 个标记为 system-verilog 的问题、695 个标记为 chisel 的问题和 13 个标记为 spinalhdl 的问题。这些问题数量的顺序与图 2(b)–(d) 中三种 HDL 的整体平均 pass@1 的顺序相同。

这些结果表明，使用较少的 HDL 对 LLM 辅助硬件设计构成了采用障碍。LLM 可以克服这一障碍：商业模型在 Chisel 和 SpinalHDL 上都显著优于开放权重模型。

III-B 3 以相同 HDL 编写的 CPU 之间的差异

图 3：按源代码长度划分的 BOOM 和 Rift2Core 结果。 显示每个范围内问题的比例。–(d) 显示每个范围内的平均 pass@1，水平线标记每款 CPU 所有问题的 pass@1。

图 3 比较了 BOOM 和 Rift2Core，两款以 Chisel 编写的乱序 CPU。图 3(a) 显示，BOOM 在 50 行以上的问题比例大于 Rift2Core，而包含 1–20 行的问题比例小于 Rift2Core。对于图 3(b) 中的五个开放权重模型，两款 CPU 在每个源代码长度范围内的差异最多为 3 个百分点，但 BOOM 的整体 pass@1 低 6.15 个百分点。因此，BOOM 中较长问题（pass@1 较低）的比例较大，导致了这一整体差异。

图 3(c) 和 (d) 显示了两个商业模型的不同模式。与五个开放权重模型一样，GPT-5.6 Sol 在 BOOM 上的整体 pass@1 低于 Rift2Core。Claude Opus 5 则不同：其在每个源代码长度范围内 BOOM 上的 pass@1 都更高，且其在两款 CPU 上的整体 pass@1 几乎相等。截至 2026 年 9 月 19 日，BOOM 拥有 2,238 个 GitHub 星标和 529 个分叉，而 Rift2Core 为 41 个星标和 14 个分叉。因此，Claude Opus 5 可能接触过更多 BOOM 特定的代码，这可以解释其在每个范围内 BOOM 上更高的 pass@1。

IV 结论

本文提出了 CPU-Eval，它通过将每个生成的子模块集成到其 CPU 中并执行软件，来评估来自六款实用 CPU 的 339 个 HDL 生成问题。在七个 LLM 上，CPU-Eval 的平均 pass@1 比 VerilogEval v2 S2R 低 45.14 个百分点，揭示了被 VerilogEval 高通过率所掩盖的能力差异。我们的评估揭示了随着子模块中源代码行数的增加，pass@1 会下降，这促使使用较小的子模块作为 LLM 生成单元。HDL 之间的比较还揭示了以使用较少的 HDL 编写的 CPU 的 pass@1 更低。这一结果强调需要诸如 CPU-Eval 之类的实用硬件代码生成基准测试，以在部署之前评估 LLM 在设计者所使用的 HDL 中生成代码的熟练程度。
