摘要
现代 Intel AI PC 配备了强大的集成 GPU 和 NPU，拥有 16+ GB 的统一内存，并且它们有大量时间处于闲置状态。但这点内存不足以容纳诸如 70B 参数 LLM 这样的大模型。我们展示了将几台这样的机器通过普通网络协同工作，可以提供超越任何单机能力的模型服务。我们的系统使用流水线并行：模型按层切分为不同阶段的分片，每个分片预编译为 INT4 OpenVINO 图，使得每台机器运行一个分片并将激活值传递给下一台。三项技术使其速度足以实用。首先，我们恢复了未切分模型的速度：朴素的逐阶段导出运行速度远低于单体推理，因为它错过了 OpenVINO GPU 优化，而在每个分片中注入 beam_idx Gather 会触发该优化（IndirectKVCache 融合）并使分片达到同等水平。其次，我们使投机解码在有状态的 OpenVINO 模型上产生回报，这些模型缺乏标准实现所假设的分页注意力 API：我们不是从 KV 缓存中物理修剪被拒绝的草稿 token，而是通过现有的 attention_mask 输入将它们掩盖，这在本质上零成本的情况下与物理修剪在位级上完全相同。第三，流水线通过在各个阶段交错处理多个用户的请求（每个请求携带自己的缓存，即微批处理）来同时为多个用户服务。综合来看，双节点 Llama 3.1 8B INT4 流水线在相同硬件上以单用户吞吐量的 1.79 倍为两个并发用户提供服务，并且在模拟的广域网延迟下差距进一步扩大。相同的设计可扩展到任何单个集群成员都无法容纳的 70B 模型：在 Intel Tiber Cloud 上的四节点 Lunar Lake AI PC 部署以交互式速度为单个用户提供服务，其输出与不带投机解码的相同四节点流水线解码在 token 级别完全一致。代码、原始基准测试日志和复现脚本作为独立包发布在 https://github.com/labscommunity/pipeline-sharded-inference-paper （在顶层 reproduction/ 目录中）。

1  引言
现代 AI PC 配备了集成 GPU、NPU 和 16+ GB 的统一内存，并且它们有大量时间处于闲置状态。单台 Intel AI PC 运行 Llama 3.1 8B [6] 的速度为每秒几十个 token。通过标准办公网络协调的一组 PC 集群可以在没有云依赖的情况下提供 LLM 推理——边际成本为零，且具备完全的数据本地性。

障碍在于软件，而非硬件。标准的模型导出工具（torch.export、torch.onnx.export）在现代 Transformer 注意力机制上会失败，因为旋转位置编码和 KV 缓存管理中存在动态控制流。单体编译模型如果不进行侵入式图修改，就无法在层边界进行切分。为训练吞吐量而开发的流水线并行 [7, 14] 在消费级硬件上的自回归推理中评估有限——当各个阶段分布在真实网络上时，每个 token 的 TCP 往返成为主要成本。投机解码 [12, 3] 是自然的解决方案（将网络往返分摊到每个目标前向传播发射的多个 token 上），但标准的规范实现依赖于有状态 OpenVINO 模型上不可用的分页注意力或专用回退 API。

我们构建了一个分布式推理栈，填补了这三个空白，这种组合产生了令人惊讶的强劲结果：两台消费级 Intel AI PC 组成的集群在相同硬件上以单用户单体基线 1.79 倍的吞吐量为两个并发用户提供服务，并且在 100 ms/跳的模拟广域网下，相同配置仍保持可用，而朴素的流水线并行解码则降至交互底线以下。

我们做出三项贡献：
1.
一个逐阶段导出流水线，生成与单体性能持平的 INT4 OpenVINO IR 分片。
从带有预计算旋转编码的 torch.jit.trace（§3.2）开始，添加导出后的 beam_idx Parameter + Gather(ReadValue, beam_idx, axis=0) 注入，解锁 OpenVINO GPU 插件的 IndirectKVCache 转换（§4），生成的分片达到 openvino_genai.LLMPipeline 单体推理 4% 的差距范围内。如果没有 beam_idx 注入，相同的分片运行速度会慢 13–23%（切分为更多阶段会扩大差距）；融合解锁是流水线中不平凡的部分，我们记录了发现它的过程。
2.
基于掩码的 KV 缓存回退，用于有状态模型上的投机解码。
在 OpenVINO 有状态目标上进行投机解码需要从 KV 缓存中拒绝投机草稿 token。自然路径——query_state()/set_state() 物理修剪——在具有 72 个 token 缓存的 Arc B390 iGPU 上每次调用耗时约 48 ms（已测量；每步一次修剪，分摊该步中被拒绝的草稿），这足以使投机解码在盈亏平衡接受率下成为净损失。对于被拒绝的草稿缓存位置设置 attention_mask[j] = 0 在本质上零成本的情况下与物理修剪在位级上完全一致，并在八种提示类型中实现了 1.33 倍的平均单节点加速，在 2048 个 token 生成时上升至约 1.6 倍（§5）。我们在随附的代码库中将其记录为发现 #20。
3.
通过独立的有状态 InferRequests 进行流水线微批处理，乘法组合成一个分布式栈，超越单体单用户吞吐量并在广域网延迟下优雅降级。
每个 InferRequest 携带自己的 KV 缓存，因此在流水线阶段之间交错来自不同用户请求的解码步骤，在我们的 v5_beam Llama 8B 分片上产生了 1.80 倍的系统吞吐量扩展，通过每流 compile_model 隔离流（§7）。叠加在前两项贡献之上，这种组合是经验性的：双节点集群在局域网下达到 43.97 tok/s（单用户的 1.79 倍），在 100 ms/跳的模拟广域网下保持交互性，并在三节点测试床上以 3 流扩展至 64.67 tok/s（§6）。在 Intel Tiber Cloud 上的 4 阶段 Llama 3.1 70B INT4 部署表明，该流水线可扩展到任何单个集群成员都无法容纳的模型大小（§6.11）。Top-1 logits 压缩恢复了中继广域网路径上的交互式吞吐量（§6.7）。

该系统在三台通过 WiFi 连接的 Intel AI PC（两台配备 Lunar Lake 的 ASUS Zenbook S 14，一台配备 Panther Lake 的 HP OmniBook X 16）上进行评估。结果可复现：下方的每一行表格数据都有配套代码库（见第 9 节）reproduction/ 目录下的已提交基准测试脚本和原始日志支持。

2  背景与相关工作
2.1  推理的流水线并行
流水线并行将模型的层跨设备分区。GPipe [7] 和 PipeDream [14] 为训练确立了这一点，其中微批次使所有阶段保持忙碌。自回归推理则不同：每个 token 依赖于前一个，在解码期间产生严格的顺序依赖。
Petals [2] 演示了通过互联网在志愿者 GPU 上进行去中心化流水线推理，通过基于 DHT 的路由以大约每秒一个解码步骤的速度运行 BLOOM-176B。Parallax [17] 在去中心化、地理分散的消费级 GPU 上调度流水线 LLM 推理，与去中心化服务基线相比，将 p99 延迟降低了 2.6 倍。MDI-LLM [13] 提出了用于边缘设备的循环流水线并行，在三板 Jetson TX2 测试床上随着每个节点的增加提高生成速率。
我们的工作在三个方面有所不同。我们通过 beam_idx-Gather 图修改过程预编译 OpenVINO IR 分片，解锁 IndirectKVCache GPU 融合，生成与单体性能持平的逐阶段分片，而不是在运行时进行带有图开销的模型分区。我们通过 OpenVINO 针对 Intel AI PC 集成 GPU，而不是 NVIDIA 或 Apple 硬件。并且我们引入了基于掩码的投机解码回退（§5）——这是一种使投机解码 [12, 3] 在没有分页注意力的有状态 OpenVINO 上产生回报的技术——它与微批处理叠加，产生了本文所构建的多用户吞吐量优势。
我们不与 Petals、Parallax 或其他分布式推理系统进行基准比较，因为硬件目标不重叠：Petals 和 Parallax 在 NVIDIA GPU 上运行，MDI-LLM 在 Jetson 板上运行，而我们的系统通过 OpenVINO 在 Intel iGPU 上运行。跨系统比较会将硬件差异与软件差异混淆。相反，我们在相同硬件上与单体 openvino_genai.LLMPipeline 进行比较——这是我们目标平台上可用的最强单节点基线——并始终报告绝对吞吐量，以便拥有其他系统的读者可以进行自己的比较。

2.2  模型编译与导出
从 PyTorch 到编译推理图的标准路径依赖于抽象张量形状传播（torch.export、torch.onnx.export），这在现代旋转位置编码内的重塑和转置操作上会失败。当给定 nn.Module 时，OpenVINO 的 ov.convert_model 继承了这些失败。
optimum-intel 库通过 OVModelForCausalLM 导出整个模型，但生成的是没有逐层切分机制的单体图。KTransformers [4] 编译单个 MoE 专家用于 CPU/GPU 混合推理，但不处理密集模型的逐层范围导出。
我们的流水线使用带有真实张量的 torch.jit.trace——完全避免了抽象形状传播——并在外部预计算旋转编码，将它们作为扁平输入传递。这避开了跟踪失败，同时生成了 OpenVINO 编译器独立优化的逐阶段图。

2.3  服务系统与吞吐量优化
vLLM [11] 引入了用于 GPU KV 缓存管理的 PagedAttention。Sarathi-Serve [1] 提出了带有无停顿调度的分块预填充。TD-Pipe [20] 在时间上解耦预填充和解码阶段，实现了高达 1.91 倍的吞吐量。Splitwise [15] 将这些阶段拆分到专用硬件上。
这些系统针对的是数据中心 GPU 集群。我们的微批处理更简单：每个 OpenVINO InferRequest 通过编译图中的 ReadValue/Assign 操作携带独立的 KV 缓存状态，因此请求的时间交错不需要框架更改，也不需要超出 OpenVINO 已提供的内存管理。运行时还支持连续批处理 [19]，结果表未使用它：OpenVINO 的 ContinuousBatchingPipeline 在 CPU 和 GPU 上提供该功能，而我们自己的一种打包多槽方案在 NPU 上提供该功能，其编译器根本不接受批处理图（§8.6）。
一条互补的工作线是缩小 KV 缓存本身，而不是围绕它进行调度。GEAR [10] 通过将均匀量化与残差的低秩近似和异常值的稀疏校正配对，将近无损地将缓存条目压缩为 4 位；SkipKV [16] 直接跳过长推理跟踪中语义冗余跨度的 KV 生成和存储。这种缓存占用空间的减少与分片是正交的，并且可以与之组合，因为每个阶段只拥有自己层的缓存：KV 增长是侵蚀我们 70B 部署长上下文吞吐量的原因（§6.11），而每槽缓存容量是打包 NPU 服务模式中的约束资源（§8.6）。我们没有评估这两种技术；我们测试过的一个缓存精度旋钮——OpenVINO 的统一 INT8 KV 缓存提示——在 Arc iGPU 上运行比默认情况慢（§8.8）。

图 1：系统架构和逐步解码流程。
离线状态下，导出流水线（§3.2）将 HuggingFace 检查点转换为 N 个独立的 INT4 OpenVINO IR 分片，每个节点一个。
在线状态下，每个解码步骤如下进行：
1 协调器在其本地 iGPU 上运行阶段 0 分片；
2 在投机解码（§5）下，本地草稿模型提议 K 个 token，因此流水线每次遍历验证 K+1 个位置；
3 隐藏状态通过持久 TCP 连接跨越到下一阶段（§3.3），每跳每个 token 约 16 KB；
4 中间阶段向下游转发；
5 最终阶段应用 LM head，采样的 token（或 top-1 logits，§6.7）逐跳中继回协调器，协调器将其附加并重复。在微批处理（§7）下，2–3 个用户流通过相同的链交错，每个流在每个阶段都有自己的 KV 状态。
协调器放置。
协调器不是一台单独的编排机器：它本身就是一个集群成员（图 1 中的节点 0），托管分词器、生成循环、阶段 0 分片，以及——当启用投机解码时——草稿模型，后两者在其本地 iGPU 上。本文中的每个多节点结果都以这种方式运行协调器。阶段 0 设备是可配置的：CPU 托管的阶段 0 可以工作并已针对 Gemma 4 进行测量（表 16，CPU→GPU 为 9.87 tok/s，而 GPU→GPU 为 10.40），但所有主要配置都将每个阶段（包括草稿模型）放置在集成 GPU 上。
每个工作节点加载一个分片并暴露一个 TCP 端点。在每个解码步骤中，协调器在本地运行阶段 0 并将生成的隐藏状态发送到下一个节点；每个中间阶段将其输出向下游转发；最终阶段应用 LM head 并返回下一个 token，该 token 逐跳中继回协调器。

3.2  逐阶段导出流水线
该流水线将 HuggingFace Transformer 转换为 N 个独立的 OpenVINO IR 分片，每个分片覆盖连续的层范围，加上（对于第一个）嵌入层和（对于最后一个）输出头。
第 1 步：选择性层加载。
解码器层通过模型无关的结构映射（Llama、Mistral、Qwen、Phi、Gemma）从 safetensors 加载。每个阶段只获取其分配的层。内存使用量随层数扩展，而不是模型大小。
第 2 步：注意力重写。
HuggingFace 的 DynamicCache（Python 列表操作）和 LlamaRotaryEmbedding（torch.autocast 守卫）都无法跟踪。我们用手动注意力实现替换它们，该实现采用预计算的 cos/sin 张量和显式 KV 张量作为输入。已验证数值等价性：与 HuggingFace 原生前向传播的最大差异 < 5×10^-7。
第 3 步：跟踪和转换。
每个阶段使用带有真实张量（批次大小 1，代表性序列长度）的 torch.jit.trace 进行跟踪。跟踪的图通过 ov.convert_model 转换为 OpenVINO IR。KV 缓存张量通过 make_stateful_transformation 成为有状态的 ReadValue/Assign 对。
第 4 步：INT4 压缩。
通过 NNCF [8] 进行 INT4 对称权重压缩，组大小 128。每个分片是一个独立的 IR（XML + BIN），输入 token ID 或隐藏状态，输出隐藏状态或 logits。

3.3  TCP 激活中继
激活值通过普通操作系统 TCP 套接字在节点之间传输。路径中没有点对点网络框架、DHT 或中继基础设施：诸如 Petals [2] 之类的去中心化系统通过 libp2p 路由阶段，libp2p 在多种传输之间进行协商，但处于一个管理域下的集群既不需要对等发现，也不需要 NAT 遍历或传输协商，当整个 token 预算约为 60 ms 时，从每个 token 路径中移除的每一层都很重要。
连接建立。
每个工作器监听配置的 host:port。启动时，协调器拨号阶段 1，每个阶段 i 拨号阶段 i+1，重试直到下游工作器启动，因此启动顺序无关紧要。结果是一个持久 TCP 连接的静态菊花链，每对相邻阶段一个，为整个会话保持打开状态：没有每个 token 或每个请求的连接设置，解码路径上也没有握手。最终阶段发出的 token 通过相同的套接字逐跳返回协调器（图 1）。
线路格式。
每条消息是一个 20 字节的头部（有效载荷长度、数据类型、三个形状维度），后跟原始张量字节。KV 缓存解码发送 [1, 1, 4096] float32 张量：每跳 16 KB。在每个套接字上设置 TCP_NODELAY，以便内核不会缓冲小的每 token 写入（否则 Nagle 算法会将它们延迟多达一个往返）。该协议是故意最小化的——旨在不触及系统其余部分的情况下替换为 QUIC、RDMA、压缩或其他传输；§6.4 讨论了传输替换能带来什么和不能带来什么。

3.4  有状态 KV 缓存推理
每个分片的编译图包含实现 KV 缓存的 ReadValue/Assign 操作。预填充在一遍中处理完整的提示；解码每步处理一个 token，读取缓存的上下文并附加新的 KV 对。协调器为最大序列长度预计算旋转 cos/sin 张量，并每步切分适当的范围。
对于具有跨层 KV 共享的模型（Gemma 4 通过 DynamicCache 在层之间共享 K/V），共享张量作为额外的阶段输出/输入通过 TCP 传输，并进行 4D→3D 重塑以适应 3 维头部协议。

3.5  操作场景与贡献映射
运行时组合成三种操作场景，按机制复杂度递增顺序排列：
(a) PP：单独的流水线并行解码——一个用户，每次遍历阶段链一个 token。
(b) PP+SD：带有投机解码的流水线并行——协调器本地的草稿模型提议 K 个 token，流水线在一次遍历中验证所有 K+1 个位置（§5）。
(c) PP+SD+MB：场景 加上多用户微批处理——多个并发用户流在相同阶段之间交错，每个流具有独立的 KV 状态（§7）。

束搜索不是一种操作模式。
本文中的所有解码都是贪婪的（argmax）；我们从不运行束搜索。§4 的 beam_idx 输入纯粹作为编译时图模式存在：OpenVINO GPU 插件的 IndirectKVCache 融合仅在 每个 KV ReadValue 流经由 beam_idx Parameter 索引的 Gather 时触发。在运行时，每个阶段接收常量 beam_idx = [0]，使 Gather 成为批次 1 缓存的恒等重排序。特别是，在场景 / 中 beam_idx 和草稿模型之间没有交互：缓存重排序（常量恒等，由 beam_idx 驱动）和草稿拒绝回退（由 attention_mask 驱动，§5）作用于不相交的模型输入，因此不会出现 beam_idx 冲突。在投机解码之上运行实际的束搜索将需要每个束的草稿状态和候选树验证步骤，我们尚未构建；导出的图已经包含缓存重排机制，因此分片端已为此做好准备。

4  达到单体性能持平：beam_idx Gather 注入
对 §3.2 导出流水线的朴素解读给出了可行但缺乏竞争力的结果：在 Llama 3.1 8B INT4 上，1 阶段分片（一个图中包含所有 32 层，权重与单体模型相同，仅导出路径不同）在稳定状态下运行速度比 openvino_genai.LLMPipeline 慢 13–23%。切分为更多阶段会使情况变得更糟。原因是 OpenVINO GPU 插件包含一个插件内部转换 IndirectKVCache，它将 ReadValue→Concat→Assign 模式重写为融合的 IndirectSDPA 操作——但该转换取决于特定模式的存在：每个 KV ReadValue 的输出必须流经由 beam_idx Parameter 索引的 Gather（在单体 LLMPipeline 路径中由束搜索使用）。我们最初的导出不包含该模式，因此 GPU 插件静默回退到具有可测量的较低 XVE 占用率的通用 KVCacheFusion 路径。
修复方法是导出后图修改：在 apply_make_stateful_transformation 之后，遍历图，添加一个 beam_idx: [-1] i32 Parameter，并为每个 KV ReadValue 在 ReadValue 输出及其下游消费者之间插入一个 Gather(ReadValue, beam_idx, axis=0)。这正是 optimum-intel 内部的 fuse_cache_reorder 过程为单体导出所做的，我们将其提取出来应用于我们的逐阶段导出。我们将生成的分片称为 v5_beam。明确地说：注入仅是编译时模式。在运行时，每个阶段接收常量 beam_idx = [0]，Gather 是恒等重排，本文中任何地方都不执行束搜索（§3.5）。

5  通过基于掩码的 KV 回退进行投机解码
投机解码 [12, 3] 将目标模型前向传播分摊到多个发射的 token 上：较小的草稿模型提议 K 个 token，目标在一次前向传播中验证所有 K 个，接受的 前缀一起发射。在分布式流水线上，这具有双重吸引力——它不仅分摊目标计算，还分摊网络往返。在单个节点上，该技术的每步成本结构决定了它是否真的有回报。

5.1  修剪问题
标准投机解码拒绝预测与目标不匹配的草稿 token。在 OpenVINO 有状态模型上，拒绝 token 意味着在下一次目标前向传播之前从 KV 缓存中移除它们的 K 和 V 贡献。用于此的自然 API 是 InferRequest.query_state()（返回每层状态张量的列表），然后通过 sv.state = ov.Tensor(sliced_np) 将切片张量分配回每个状态。我们在 Arc B390 上的 Llama 3.1 8B INT4 上测量了这一点：

5.2  基于掩码的回退
我们的替代方案完全避免了状态操作。OpenVINO 有状态模型将 attention_mask 作为形状为 [batch, past_len + input_len] 的每次前向传播输入，其中 mask[j]=0 意味着“在注意力中忽略缓存位置 j”。如果被拒绝的草稿 token 物理上保留在缓存中，但它们的位置在随后的每次前向传播中被掩盖，则注意力结果与物理修剪的缓存完全相同。未来 token 的键和值张量附加在下一个缓存索引处，RoPE 从调用者提供的 position_ids 计算；只要 position_ids 跟踪逻辑序列长度（回退前的计数）而不是物理缓存长度，旋转旋转就是连贯的。
我们验证了这与物理修剪在位级上完全一致。在相同的目标–提示–草稿–校正序列上并排运行两条路径（reproduction/scripts/bench/mask_trim_test.py），校正后 logits 的最大绝对差异为 0.0000（fp32 等于机器精度）。
成本仅限于 CPU：每次前向传播通过将跟踪的 valid_mask 前缀与新 token 的 1 拼接来重建 [1, past_len + input_len] 掩码。测量值：在 K=3 时占每步挂钟时间的 < 1%。内存成本是被拒绝的草稿 K 和 V 条目保留在缓存中，在生成过程中膨胀缓存大小。在 K=3 的 2048 token 生成中，缓存膨胀达到逻辑长度的 1.02 倍（大多数被拒绝的草稿开销被活 token 计数分摊），因此对于现实中的单轮长度不需要定期压缩。对于累积上下文接近模型窗口的多轮对话，需要定期压缩（物理修剪缓存以移除所有被掩盖的位置）；当生成结束时缓存状态被序列化时，被掩盖的位置被压缩掉（§8.4），但生成中的压缩仍未实现和测量。掩码原语也不特定于草稿拒绝：在生成过程中丢弃低效用位置的缓存减少策略——例如 SkipKV [16]，它跳过推理跟踪中语义冗余句子的存储——预设了可以廉价地移除任意缓存位置，这正是表 4 中约 48 ms 的状态往返拒绝有状态 OpenVINO 模型所做的。相反，掩盖这些位置以零设备成本产生相同的注意力结果，因此这里构建的机制也将支持此类策略。
范围：仅限贪婪解码。
本文中的所有结果都使用贪婪解码（argmax token 选择）。基于掩码的回退对于贪婪是正确的，因为接受检查是简单的 token-id 比较，并且无论回退方法如何，存活的缓存都是相同的。扩展到基于温度的采样将需要 [12] 和 [3] 的拒绝采样校正，它根据草稿概率调整目标分布；基于掩码的回退原则上与此校正组合（无论哪种方式缓存状态都相同），但我们没有经验验证它。束搜索在本文中任何地方也没有使用；§3.5 解释了为什么 beam_idx 输入仍然出现在每个分片图中。

在千兆 WiFi 下，16 KB 传输时间不到 0.2 ms。约 6.5 ms 的每跳延迟是 TCP 内核调度和往返时间，而不是带宽。将有效载荷减半没有任何好处。4096 维隐藏状态的 INT8 对称量化破坏了生成——“法国的首都是什么？”产生“1. 巴黎 2. 伦敦 3. 柏林 4. 罗马”。逐通道或分组量化可能会保持质量，但未进行测试。激活压缩仅在带宽受限的广域网条件下才有意义。
