AI Training Manager: Bounded Closed-Loop Control of Adaptive Training Recipes Anjali Rao Nikhil Kamalkumar Advani Abstract We present the AI Training Manager, a bounded LLM-based supervisory controller for adaptive machine learning training. Standard training pipelines often rely on fixed recipes or single-axis schedulers, which can struggle with mid-run failures such as severe overfitting, loss imbalance, over-regularization, exploration collapse, or unsafe exploration. Rather than replacing mathematical optimizers or acting as an unconstrained coding agent, the manager operates through a schema-conditioned interface: it reads structured telemetry snapshots from an active run, audits a constrained action space, and returns validated updates to training parameters such as learning rate, regularization strength, loss-weight coefficients, and exploration settings. We evaluate this architecture across supervised language modeling and reinforcement learning. On TinyStories, the manager detects and corrects overfitting, achieving a validation loss 60% lower than the baseline while producing auditable intervention logs. In this supervised setting, we additionally show that manager inference does not need to block the training loop: training can continue while a manager response is pending, and validated updates can be applied asynchronously once available. In a robotic manipulation reinforcement-learning task, we use the same bounded decision interface in an episodic closed-loop se

tting, where manager updates are applied at evaluation or checkpoint boundaries. The manager mitigates both conservative and unsafe exploration regimes. In the cautious regime, the manager rescues a failed run from 0.0 to 0.94 rollout safe success. In the reckless regime, where the fixed recipe eventually succeeds but only after the full budget and with high fluctuation, the manager reaches comparable safe success roughly 4x earlier by reducing excessive exploration.These results suggest that schema-conditioned LLMs can serve as bounded supervisory managers for live training runs, complementing conventional optimizers and schedulers with interpretable, multi-axis intervention capabilities. I Introduction Modern AI training systems are not completely open-loop. Learning-rate schedulers, early stopping rules, adaptive loss weighting methods, curriculum schedules, and population-based training all adjust training behavior based on feedback. These mechanisms are useful and widely adopted, but they are usually specialized: they monitor a limited set of signals, control a limited set of knobs, or operate across multiple runs rather than as an auditable supervisor inside a single active training run. At the same time, training runs produce rich telemetry. A supervised run may expose training loss, validation loss, generalization gap, gradient norms, and auxiliary losses. A reinforcement-learning run may expose success rate, collision rate, reward components, action magnitudes, entro

py, and safety metrics. Human practitioners often inspect these signals to decide how the next experimental trial should be modified. Recently, outer-loop automated research agents have begun to mimic this workflow by using LLMs to parse final metrics, rewrite training scripts, and launch subsequent runs. However, this supervisory reasoning remains largely external to the active optimization process. The question we study is whether such reasoning can be moved closer to the live training loop while keeping the system bounded, auditable, and constrained to safe interventions. We present the AI Training Manager, an LLM-based supervisor for closed-loop control of the training recipe. Here, “training recipe” refers to the configurable settings surrounding the optimizer and objective, including learning-rate policy, objective weights, regularization strength, exploration settings, and reward or penalty coefficients. The manager does not update model parameters directly. It does not rewrite code, change architectures, or design new experiments. Instead, it reads a structured snapshot of the active run and selects from a predefined set of bounded interventions. A central design goal is to make manager decisions compatible with live training rather than treating the LLM as an external offline analyst. In supervised learning, we implement this through an asynchronous application protocol. A simple implementation would pause training, call the LLM, wait for a response, and then continu

e. We avoid this because LLM inference latency should not determine the critical path of the gradient loop. Instead, the primary training loop continues while a manager request is pending. Each request is tied to a telemetry snapshot and versioned configuration. When the response arrives, the system validates the JSON, checks action bounds, verifies that the decision is still relevant, and applies it only at the next safe intervention boundary. Stale or invalid decisions are logged and converted to safe no-ops. In reinforcement learning, where asynchronous mid-update interventions were not stable in our setting, we use the same bounded decision interface but apply manager updates at episode or checkpoint boundaries. This paper evaluates the manager on controlled failure modes where the desired intervention is interpretable. In TinyStories language-model training, we evaluate recovery from overfitting, and auxiliary-loss imbalance, demonstrating that the manager can improve best validation loss from 0.852 to 0.770 and final validation loss from 2.09 to 0.800 in the small-data overfitting stress test. In a two-link robotic-arm environment, we test a cautious ’Scared Arm’ regime that avoids collision but fails to reach the target, and a ’Reckless Arm’ regime that explores unsafely. The manager selects bounded updates during training, yielding a [Y.Y]x improvement in safe success rates. The contributions of this workshop paper are threefold: 1. We describe a bounded manager inter

face that exposes telemetry, current settings, prior decisions, and action limits to an LLM supervisor. 2. We introduce an asynchronous application protocol for supervised training that prevents manager latency from blocking live gradient updates, while safely rejecting stale or invalid decisions. 3. We provide empirical evidence that a unified, schema-conditioned manager can select meaningful, multi-axis interventions across controlled failure modes in both supervised language modeling and reinforcement learning. II Related Work II-A Inner-Loop Heuristics and Adaptive Training Methods Modern training pipelines already contain several forms of feedback control. Learning-rate schedules, early stopping rules, curriculum schedules [ 2 ] , and exploration-decay mechanisms in reinforcement learning all adjust training behavior based on observed progress. Adaptive loss-balancing methods similarly modify the relative weights of multiple losses using task-specific signals such as learned uncertainty [ 3 ] or gradient magnitudes [ 4 ] . These methods are practical and widely used, but they are typically specialized: each mechanism observes a narrow signal family and controls a narrow set of knobs. Our goal is not to replace these established mechanisms. Instead, we study whether an LLM can act as a reusable supervisory layer over several bounded controls simultaneously. For example, in our auxiliary-head experiments, the manager can adjust the auxiliary loss coefficient, but the same

interface also exposes learning-rate changes, regularization changes, and rollback/no-op decisions. The distinction is therefore not feedback versus no feedback, but specialized hand-designed feedback rules versus a schema-conditioned supervisor that reasons over heterogeneous telemetry and a constrained action space. II-B Hyperparameter Optimization, AutoML, and Population-Based Training Hyperparameter optimization and AutoML methods search for effective training configurations across evaluations. Bayesian optimization [ 5 ] , resource-allocation methods such as Hyperband [ 6 ] , and related AutoML systems have shown that systematic search can outperform manual tuning. Population-Based Training (PBT) goes further by training a population of models concurrently, periodically exploiting stronger runs and perturbing hyperparameters to discover training schedules rather than a single fixed configuration [ 7 ] . Our setting differs in both authority and execution model. The AI Training Manager does not launch a population, copy model weights, mutate competing runs, or select among parallel trials. It supervises a single active run and proposes bounded updates to the live training recipe based on telemetry from that run. This makes the intervention trace auditable at the level of individual decisions: each manager action is tied to a snapshot, validated against an explicit schema, and applied only at safe intervention boundaries. II-C Dynamic Algorithm Configuration and Parameter

Control The closest classical framing to our work is dynamic algorithm configuration (DAC) and parameter control. DAC studies policies that adapt algorithm parameters during execution rather than selecting a static configuration before the run [ 8 ] . This perspective is highly relevant to machine learning training, where the best learning rate, regularization strength, exploration pressure, or loss coefficient may change over time. Recent DAC benchmarks and AutoRL studies further show that dynamic control policies can be studied in controlled settings where the desired adaptation is interpretable [ 24 , 10 ] . The AI Training Manager can be viewed as a language-model-based, schema-conditioned instance of this broader idea. However, unlike learned DAC policies trained offline over many problem instances, our manager uses an instruction-following LLM at run time, constrained by an explicit action schema and validation layer. This trades optimality guarantees for generality, interpretability, and ease of reuse across heterogeneous training failures. II-D Automated Reinforcement Learning and Safe RL Reinforcement learning is particularly sensitive to training-recipe choices. Exploration settings, entropy pressure, reward penalties, and safety-related coefficients can determine whether a policy learns, collapses, or exhibits undesirable behavior. AutoRL methods attempt to automate parts of this pipeline, including hyperparameter selection, architecture choices, reward design, and

algorithm configuration [ 9 ] . However, many AutoRL approaches still evaluate candidate configurations across runs or require substantial search budgets. Our reinforcement-learning experiments focus on bounded mid-training recipe interventions in a single robotic-arm task. We do not claim to solve safe reinforcement learning or constrained policy optimization, which aim to provide stronger guarantees about constraint satisfaction during learning or deployment [ 11 , 12 ] . Instead, we use safety-related telemetry, such as collision rate and safe success rate, as observable signals that the manager can use to adjust bounded exploration and penalty coefficients. II-E Learned Optimizers and Meta-Learning Learned optimizers and learning-to-optimize methods attempt to replace or augment hand-designed optimization algorithms with learned update rules [ 13 , 14 , 15 ] . Recent work has studied learned optimization specifically for reinforcement learning, where nonstationarity, high-variance gradients, and agent-environment interactions make the problem especially difficult [ 16 , 17 ] . The AI Training Manager adopts a lower-authority design. It does not replace PPO, Adam, AdamW, or the core parameter-update equations. Instead, it supervises the configurable recipe surrounding those optimizers: objective weights, regularization, exploration pressure, reward penalties, and learning-rate settings. This design intentionally preserves conventional optimizers as the mechanism for param

eter updates while using the LLM only for bounded supervisory decisions. II-F LLMs for Optimization, Hyperparameter Tuning, and Research Agents Recent work has explored LLMs as optimizers and hyperparameter-tuning agents. OPRO frames optimization as a prompting problem in which an LLM proposes candidate solutions from prior evaluations [ 18 ] . Other work uses LLMs to suggest hyperparameter configurations from dataset and model descriptions, iteratively refine candidates based on performance, or combine LLM proposals with classical HPO machinery [ 25 , 19 , 20 ] . Recent systems also investigate whether smaller LLMs can perform hyperparameter tuning when paired with deterministic expert blocks that summarize optimization trajectories [ 21 ] . These approaches demonstrate that LLMs can use training feedback to make optimization-relevant decisions. Our framework differs in three ways. First, the manager acts within an active training run rather than only proposing the next trial. Second, its agency is explicitly bounded: the LLM cannot rewrite code, alter the architecture, or invent new actions outside the schema. Third, each decision is validated before application, checked against action limits, and recorded as an auditable trace. This places the work between classical dynamic parameter control and recent LLM-based research agents, which can autonomously write code, launch experiments, and iterate over external research loops [ 22 , 23 ] . III-D Structured Output and Verification The manager must return structured JSON rather than free-form advice because the training system consumes the decision programmatically. Each response contains a diagnosis, a control audit, a selected action, expected outcomes, and watch items for the next interval. The selected action may update one or more exposed recipe settings, or it may explicitly choose no-op. The diagnosis summarizes the current training state, such as overfitting, over-regularization, auxiliary-objective imbalance, cautious exploration, unsafe exploration, or healthy/no-action. The control audit evaluates the relevant exposed controls and indicates which are selected, rejected, or deferred. The selected-action field specifies the proposed bounded relative update. The expected-outcome field states what should improve during the next interval, and the watch-items field lists the metrics that should be inspected to judge whether the intervention helped, hurt, or remains inconclusive. After recei

ving the response, the deterministic verifier performs syntactic and semantic checks. It verifies that the response is valid JSON, that all required fields are present, that selected actions are part of the exposed action surface, and that proposed updates satisfy the allowed ranges and relative step limits. The verifier does not attempt to prove that the manager’s diagnosis is correct. It only determines whether the response is admissible under the interface contract. If verification succeeds, the decision is queued for application at the next safe intervention boundary. If verification fails, the response is logged but discarded, and the active training recipe remains unchanged. In this sense, the LLM never receives direct write access to the training loop. It proposes candidate decisions, while the deterministic shell decides whether those candidates are admissible. III-E Application Protocols The same bounded manager interface can be used with different application timing depending on the training domain. In supervised training, we use an asynchronous protocol so that LLM latency does not block the gradient loop. At an evaluation boundary, the training loop creates a telemetry snapshot and sends a manager request. Training then continues with the current recipe while the request is pending. Each asynchronous request is tied to a snapshot interval and a versioned recipe configuration. When the response arrives, the system checks whether it is still valid for the current ru

n state. A decision may become stale if training has advanced too far, if another decision has already changed the recipe, or if the current telemetry no longer matches the snapshot that triggered the request. A valid and still-relevant decision is queued for the next safe intervention boundary. A stale, invalid, or incompatible decision is logged and discarded. In reinforcement learning, we do not apply asynchronous mid-update interventions. In our setting, such interventions were less stable because rollout collection, policy updates, and evaluation phases have different semantics. We therefore use a boundary-synchronous protocol for the robotic-arm experiments. The manager is queried at rollout, update, evaluation, or checkpoint boundaries, and any verified decision is applied before the next control interval begins. This preserves the same prompt structure, action surface, verifier, and decision trace while avoiding recipe changes in the middle of a rollout or policy-update phase. III-F Decision Logging Every manager request produces a decision trace. The trace records the prompt version, telemetry snapshot, current recipe, candidate response, diagnosis, control audit, selected update, expected outcome, verification status, application status, and subsequent outcome. For asynchronous supervised runs, the trace also records the snapshot interval, recipe version, response latency, whether the decision was stale, and whether it was applied. These logs serve two purposes. Fir

首先，它们使系统具备可审计性：研究人员可以检查管理器为何更改某项设置、拒绝了哪些备选方案、预期会有何种结果，以及下一个时间间隔的数据是否支持该决策。其次，它们提供了结构化的事后分析数据，可用于指导后续的实验设计。例如，反复增加正则化可能表明默认配方的正则化不足，而反复降低辅助损失权重则可能表明目标函数存在不平衡。我们将这些轨迹视为结构化的决策记录，而非隐藏的推理过程。

This experiment should be interpreted as a controlled demonstration of bounded multi-loss recipe control, not as a definitive result on dynamic loss balancing. The dialogue-detection task is relatively easy: its loss collapses quickly, leaving little long-term tension between the auxiliary objective and the main objective. Nevertheless, this experiment demonstrates that the same manager interface can adjust both ordinary regularization controls and an auxiliary-objective weight within one validated action surface. Overall, the TinyStories experiments show that the manager is most useful when a fixed recipe enters a regime where the apparent optimization signal becomes misleading. In the healthy 20k-story baseline, standard cosine annealing already works well. In the 2k-story overfitting regime, however, the fixed recipe continues to reduce training loss while validation loss deteriorates. The manager responds by increasing regularization and, in the auxiliary-head setting, reducing the weight of a solved auxiliary objective. These interventions produce worse training loss but substantially better validation behavior, which is precisely the desired behavior for a training-time supervisor. V Discussion and Limitations The experiments support a narrow but useful claim: a schema-conditioned LLM can act as a bounded supervisory layer for controlled training failures. The mana

ger is not optimizing model parameters directly, searching over architectures, or launching new experiments. Instead, it reads structured telemetry, selects from an explicit action surface, and proposes bounded relative updates that are verified before application. This framing is important because the observed gains do not require treating the LLM as an unconstrained autonomous agent. The LLM supplies diagnostic and control-selection behavior, while the deterministic shell enforces the interface contract. The strongest TinyStories result is the overfitting stress test. In the fixed cosine recipe, train loss continues to improve while validation loss degrades sharply. The manager responds by increasing regularization and sacrificing training-set fit to preserve validation performance. This is precisely the kind of intervention a training supervisor should make: it should not blindly optimize the most immediately improving scalar, but should recognize when that scalar has become misleading. The auxiliary-head experiment extends this behavior to a multi-loss setting, where the manager reduces the weight of an auxiliary dialogue-detection objective that saturates early while preserving language-model validation performance. The reinforcement-learning results show a complementary behavior. The same task prompt and action surface are used for both the scared and reckless arm settings, and the manager is not told which failure mode is present. In the scared setting, it increases ac

tion noise to enable exploration; in the reckless setting, it decreases action noise to reduce excessive exploration. This is the clearest evidence that the manager is not simply applying a fixed rule such as ‘increase exploration” or ‘decrease exploration.” It selects opposite bounded updates from the same action surface based on telemetry. A central design choice is that the manager’s authority is intentionally limited. This has two advantages. First, invalid or out-of-scope responses can be rejected without affecting training. Second, the resulting decision traces are auditable: each intervention can be inspected in terms of the telemetry snapshot, diagnosis, selected control, expected outcome, and subsequent behavior. This makes the manager closer to a bounded control layer than to an open-ended code-writing agent. There are several limitations. First, our experiments are controlled failure-mode studies rather than broad AutoML benchmarks. The tasks were selected because the failure mechanisms are interpretable, not because they exhaust the space of possible training failures. Second, the experiments use relatively small models and compact environments. Larger models, longer runs, and more realistic reinforcement-learning tasks may expose different failure dynamics. Third, the manager receives structured decision/outcome context that fixed baselines do not receive, although scheduler baselines condition on their own metric histories by design. Future comparisons should mo

re systematically separate the value of LLM reasoning from the value of structured memory. Fourth, the auxiliary dialogue-detection task is an intentionally simple multi-loss test. Because the auxiliary objective saturates quickly, the manager mostly learns to reduce its weight rather than negotiating a persistent tradeoff between two difficult objectives. Stronger future tests should use auxiliary objectives that remain informative throughout training, such as entity consistency, event ordering, factual consistency, or style control. Fifth, asynchronous application worked naturally for supervised training but did not transfer directly to reinforcement learning in our setting. For the robotic-arm experiments, we therefore used boundary-synchronous updates at rollout, update, evaluation, or checkpoint boundaries. This suggests that the manager interface can generalize across domains, but the application timing must respect the semantics of each training loop. Finally, the manager does not provide formal optimality or safety guarantees. In reinforcement learning, safety-related quantities such as collision rate and safe success rate are used as telemetry for bounded recipe updates; the method is not a substitute for constrained policy optimization or formally safe RL. Similarly, in supervised learning, the manager improves validation behavior in the studied stress tests, but it does not guarantee better generalization across all datasets, architectures, or training regimes. uage-model validation behavior. In reinforcement learning, it applies opposite action-noise updates for scared and reckless exploration regimes under the same prompt and action surface. These results suggest that schema-conditioned LLMs can serve as useful training-time supervisors when embedded inside a deterministic control shell. The manager should not be viewed as a replacement for optimizers, schedulers, or systematic hyperparameter search. Rather, it provides a reusable supervisory layer that can read richer telemetry than ordinary single-axis rules, select among multiple bounded controls, and leave behind an auditable trace of its decisions.
