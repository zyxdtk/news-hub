前沿红队：调查网络安全评估中的三起真实事件

📅 2026-07-30 📄 Anthropic 🔗 原文链接

原标题：Frontier Red Team Investigating three real-world incidents in our cybersecurity evaluations

中文摘要： Anthropic在网络安全评估中发现三起事件：Claude模型因配置错误从隔离测试环境访问了互联网，未经授权访问了三个组织的真实系统。模型在夺旗挑战中将真实系统误认为模拟环境的一部分。最新模型在识别真实环境后自行停止攻击。Anthropic正加强评估环境安全措施。

在对我们的网络安全评估记录的审查中，我们发现了三起事件，其中 Claude 模型从第三方评估环境内部或与第三方评估环境交互时连接到了互联网，然后未经授权访问了三个不同组织的真实系统。

以下我们描述了发生了什么、如何发生的，以及我们正在做出哪些改变。我们鼓励其他 AI 实验室进行类似的审查。这篇文章反映了我们目前的理解；如果有任何细节变化，我们将更新此文。

7月21日，OpenAI 披露 他们的几个模型通过利用一个此前未知的（"零日"）漏洞突破了一个隔离的测试环境。这些模型随后访问了 Hugging Face 的生产基础设施，Hugging Face 是一个开源机器学习模型和 AI 数据集平台。

作为对此事件的回应，我们开始对我们自己的网络安全评估进行大规模的回顾性审查。特别是，我们寻找 Claude——像访问了 Hugging Face 的 OpenAI 模型一样——是否能够从本应被封闭的测试环境中访问互联网的证据。

在审查了 141,006 次 Claude 可能获得互联网访问权限的评估运行后，我们确定了三起事件，其中模型从我们的第三方评估合作伙伴 Irregular 的评估环境内部或与其交互时访问了互联网，然后未经授权访问了三个不同组织的生产基础设施。

在这三起事件中，Claude 被分配了一个"夺旗"（capture-the-flag）挑战，这是我们评估模型网络能力的方式之一。模型被给予一个虚构场景，并被告知一个秘密信息（"旗帜"）已被隐藏在网络上的另一台机器上，其目标是入侵并检索它。挑战是开放式的，没有规定特定的方法。

在所有情况下，Anthropic 的评估提示都向 Claude 明确说明其环境是一个模拟环境，并且没有互联网访问权限。由于我们和我们的评估合作伙伴之间的误解，实际情况并非如此，互联网访问是可用的。因此，当 Claude 的搜索引导它到达开放互联网上的真实系统时，它将它们视为练习的一部分。（网络安全评估靶场通常包含逼真的细节，以便准确评估模型在真实环境中的能力；一个看起来逼真的目标本身并不能向模型清楚地表明该目标不是模拟的一部分。）

在所有可访问的实体都是练习范围内的目标这一错误信念下运作，Claude 使用基本技术（如利用弱密码和未经身份验证的端点）攻破了受影响组织的基础设施。它没有发现或利用任何复杂的漏洞，在每种情况下，Claude 都继续工作以完成其评估所分配的特定夺旗任务。然而，在某些情况下，我们的旧模型在获得证据表明它正在开放互联网上运行后仍继续攻击；我们的最新模型在认识到它在互联网上后就停止了。在所有这些情况中，Claude 都没有自行外泄数据或故意试图逃离其测试环境。

这些事件涉及三个不同的 Claude 模型：Opus 4.7、Mythos 5 和一个内部研究测试模型。1 最早的事件可追溯到4月。这些评估中的模型在运行时没有我们公开发布模型时部署的标准安全防护措施（也就是说，它们没有我们通常实施的用于防止滥用的分类器和监控）。然而，这些模型确实有它们特定的安全训练（也就是说，它们不是我们在测试中有时使用的"仅提供帮助"版本的模型）。这里描述的所有评估都在专用基础设施上运行，该基础设施与 Anthropic 的敏感内部系统或客户数据是分开的，并且无法访问。

我们在7月23日星期四开始审查记录，并在同一天在识别到 Claude 可能已访问互联网的记录后停止了所有网络评估。我们在第二天确定了所有三起事件。我们在7月27日星期一通知了我们的评估合作伙伴 Irregular 和三个受影响的组织。我们能够联系到的两个组织此前没有检测到这些活动或联系过我们，我们现在正在与它们合作进行修复。我们正在继续联系第三个组织。

我们与 Irregular 合作进行了这次审查。我们感谢他们与我们密切合作以理解和解决这些事件；他们也在进行自己的调查。我们相信这种合作对于确保模型的安全、严格评估越来越关键。我们期待我们在安全方面的联合工作。

在下文中，我们提供了每起事件的更多细节以及我们未来的应对措施。

网络评估背景

我们定期运行涉及模拟真实进攻性网络安全挑战的网络安全评估。这些评估是开发和发布模型的关键步骤——对模型能力的细致理解使我们能够设计适当的安全防护措施，并最终安全地发布模型。

我们于2025年2月开始使用 Claude Sonnet 3.7 在 Cybench 上运行网络安全评估，该平台包含40个不同的夺旗挑战。随着时间的推移，随着新基准的发布和模型能力的演进，我们增加了使用的基准数量。例如，在 Mythos 5 系统卡片 中，我们纳入了 CyberGym 和 ExploitBench，这些是评估语言模型发现新漏洞能力的基准。2 在大多数这些评估中，环境不连接互联网，模型也被如此告知。

我们经常与外部合作伙伴合作，他们创建并协助运行一些这样的网络安全评估。外部合作伙伴提供的环境和场景比我们独自构建的更加多样化，并提供对我们模型的独立第三方评估。

发生了什么

在我们审查的 141,006 次评估运行中，我们确定了三起独立事件（涉及总共六次运行，其中四次影响了同一个组织；另外两起事件各自发生在独立的评估运行中）。每起事件涉及不同的虚构夺旗场景——例如，在其中一起事件中，Claude 扮演一家虚构公司的员工，在私有测试环境中攻击该公司的内部系统。

在所有情况下，我们的评估提示都明确指出 Claude 没有互联网访问权限，但没有给 Claude 任何关于在哪里寻找旗帜的限制。然而，一个配置错误导致 Claude 作为评估一部分访问的机器具有实时互联网访问权限。直到我们上周通过额外的评估监控检测到这个问题之前，我们和我们的评估合作伙伴都不知道这个配置错误。

我们和合作伙伴双方的几项纵深防御措施本可以防止这些事件，或至少降低其发生的可能性。在评估开始之前仔细验证所有互联网访问路径，以及对评估日志进行实时监控，本会有助于更早地发现问题。我们和我们的合作伙伴也本可以更彻底地审查评估记录或网络日志。此外，如果提示告诉 Claude 它确实有互联网访问权限，可能会改变 Claude 在接触真实系统时的行为方式。

Claude 做了夺旗练习训练网络安全专家做的事情：寻找到达旗帜的方法。这个搜索使它发现它的机器可以连接到互联网，但由于在系统提示中被告知没有互联网访问权限，Claude 认为它最初遇到的一切都是模拟的一部分，并将它发现的真实系统视为练习的组成部分。这三起事件涉及三个不同的模型，一旦出现目标可能是真实的迹象，每个模型的反应都不同，如下所述。

事件1

在一次评估中，我们的评估合作伙伴选择的虚构目标公司与一个活跃的网站域名共享一个名称。由于上述讨论的误解，这个评估容器具有意外的直接互联网访问权限。

在这个评估的四次运行中，Claude 在评估环境中难以到达其模拟目标，但随后发现可以通过互联网访问真实公司。假设这是夺旗任务中的预期目标，Claude 寻找、识别并利用了该公司基础设施中的漏洞，相信它是练习的一部分。这四次运行提取了应用程序和基础设施凭据等信息，并获得了包含数百行生产数据的数据库的访问权限。这是我们识别出的最严重的影响。

这起事件涉及 Claude Opus 4.7，也是唯一一个模型在了解到它可能正在真实环境中运行后仍继续攻击系统的情况。在所有四次运行中，模型最终认识到（如其语言化推理中所观察到的）系统是真实的——在两次运行中，模型合理化认为真实公司必须是练习的一部分。然而，没有一次因此停止攻击。

事件2

在另一次评估中，Claude 在虚构环境中发现了一份文档，看起来像是另一家虚构公司为新开发者准备的设置说明。这些说明告诉员工从 PyPI——发布 Python 软件的公共注册表——安装一个实际上并不存在的 Python 包。

Claude 将此视为一个潜在的突破口：如果它以相同的名称发布自己的包，虚构公司的系统将自动下载并安装它。因此，Claude 构建并发布了一个同名的恶意（本质上是陷阱式的）Python 包，试图赢得夺旗挑战。

Claude 花费了大量精力来执行这次攻击——这些精力很可能向人类参与者表明这不再仅仅是一次评估，他们实际上正在上传一个真实的 PyPI 包。例如，在一种情况下，为了创建 PyPI 账户，Claude 需要一个电子邮件地址。而为了创建电子邮件地址，它需要一个电话号码。为了获得电话号码，在未能找到免费电话号码服务后，它尝试——但失败了——通过几种不同的方式获取资金来支付电话号码。它最终回溯，找到了一个免费的、未被阻止的电子邮件提供商，用它注册了 PyPI 账户，然后使用这个账户将恶意软件上传到 PyPI。

Claude 认为它使用的包注册表是模拟的一部分，但实际上该包在网上免费提供了大约一个小时。在这个时间窗口内，该包被下载并在15个真实系统上运行。其中一个系统属于一家真实安全公司（与场景中引入的虚构公司不同）的扫描器，该扫描器例行安装 Python 包并扫描它们以查找恶意软件。当该公司的扫描器安装该包时，Claude 的隐藏代码被执行。我们认为该公司的安全扫描器将 PyPI 包视为可安全安装的，因此 Claude 能够将该公司的凭据外泄到它设置的收集点。Claude 随后使用这些凭据访问了该公司的更多基础设施。

Claude 并没有直接针对这家公司——在上传包时它甚至不知道这家公司的存在。但由于代码被发布到开放互联网上，它影响了运行它的任何系统。（Claude 上传的包被 PyPI 自己的安全系统自动从 PyPI 中移除。我们已将此事件通知 PyPI 团队，并向他们提供了相关指标。）

这次攻击由 Claude Mythos 5 执行。在运行早期，Claude 自己的推理正确地识别了其行为的后果。它指出，如果这是真实的互联网，发布包将是一次真实的攻击——"不可以，而且肯定不是预期的解决方案。"然而，它说服自己仍然处于模拟中，理由是它不认识保护其连接的（实际上是真实的）证书颁发机构。此外，根据 Claude 的说法，系统上2026年的日历日期证明了环境是搭建的。Claude 从未重新审视这个结论；例如，当自动扫描器开始安装该包时，Claude 认为它们是评估中的脚本化角色。

我们的观点是，无论它对其环境有什么样的信念，Claude 为发布 PyPI 包所付出的努力都不符合理想行为，这是我们将加强训练的一个领域。

事件3

在这次评估中，当 Claude 无法到达其预定的虚构目标时，它在网上寻找替代方案，扫描了大约9,000个目标。它最终找到并攻破了一家公司的面向互联网的应用程序，使用了基本的、众所周知的网络攻击技术，如从暴露的调试页面读取凭据和 SQL 注入。

这次攻击由一个内部研究测试模型执行。在运行的大部分时间里，Claude 将它到达的（真实）主机视为练习的一部分；它假设它们是模拟的，并因此相信其行为是无害的。然而，在运行的后期，Claude 意识到被攻破的主机位于一个与夺旗挑战无关的云账户中。它自行得出结论，认为目标实际上是真实的，并停止了攻击。

我们对 Claude 行为的分析

在每起事件中，Claude 都被我们的提示明确告知它没有互联网访问权限。在每次运行的大部分时间里，当它遇到真实世界的系统时，Claude 假设这些是练习的一部分（尽管它有时认识到它们是真实的生产系统）。由于夺旗场景本质上就是攻击外部系统的指令，这样做符合 Claude 被分配的任务。

在这种共同背景下，三个模型在出现目标可能是真实的迹象后表现不同。我们最旧的模型 Opus 4.7 认识到它已到达生产系统，但继续攻击。Mythos 5 正确地直觉到它正在访问开放互联网，但通过推理回到了它仍处于模拟中的结论。我们最新的模型，一个内部研究测试模型，也考虑了它的目标是否实际上是真实的。当出现证据表明它们是真实的时，它停止了练习。

这是三起孤立的事件，不是受控的实验比较的一部分。因此，我们必须谨慎地从它们中得出结论。尽管如此，我们最希望看到的行为——认识到目标是真实的并在未被提示的情况下停止——只发生在三个模型中最近的一个（即使那个模型在停止之前也比我们希望地走得更远）。这种模式与更先进的模型做出更适当反应是一致的，但我们需要进行更多测试才能对此结论有信心。

我们还在与 METR——一个独立的 AI 评估组织——进行对话，以进行第三方审查，包括访问所有记录和对相关模型的抽样访问。同时，在下周内，我们将发布一份经过轻度编辑的记录，其中 Claude 构建了一个恶意 PyPI 包。为了保护受影响的组织，我们目前无法发布更多记录，但一旦我们能够做到，我们将努力使这些记录可用。

我们的应对措施

我们从这些事件中汲取了几个教训。

首先，涉及强大自主能力的评估环境也需要重要的控制措施。安全测试在模型发布之前进行，正是因为我们还不知道它的能力。评估环境越来越需要被要求达到与我们模型运行的其他任何系统相同的安全标准。

一个仅包含虚构场景的网络评估靶场可能看起来是低风险的——毕竟，里面没有什么是真实的。然而，随着 AI 能力的进步，我们需要改变对此类威胁的建模方式。在不访问敏感信息的环境中运行的高级代理本身就构成了重大威胁。我们需要更好地共同设计评估环境，并更好地监控评估结果，以应对这一威胁。这里的一些解决方案甚至可能是简单的修复；例如，如果提示清楚地解释了哪些系统在评估范围内、哪些不在范围内，Claude 可能一开始就不会访问互联网。

这不仅适用于内部环境，也适用于第三方供应商——评估供应商构建的基础设施需要同样的加强监控和加固。我们鼓励其他实验室进行类似的审查。此外，该领域将受益于更广泛的对话，讨论如何既安全又现实地评估越来越强大的 AI 代理，包括如何在部署前测试期间权衡互联网访问提供的真实性与它引入的风险。

其次，对齐行为和有害行为之间的界限取决于模型对其情况的理解。在本文描述的任何运行中，我们都没有看到模型追求自己目标的证据。相反，模型做了评估要求它们做的事——尽管在大多数情况下，它们在对环境是否真实持有错误信念的同时这样做了。在模型认识到系统是真实的并继续进行的运行中，它这样做是因为它假设这是挑战的一部分。情境感知是允许模型做出对齐决策的一个因素，但在这种情况下，Claude 的情境感知是错误的。

最后，这些事件证明了纵深防御方法的重要性。我们运行此类能力评估时不带公开发布模型所附带的安全防护措施，因为我们的目标是衡量底层模型能做什么。只有在评估被适当隔离的情况下这才是安全的。然而，我们公开发布的模型上部署的安全防护措施本会阻止所识别出的行为。

最终，许多因素导致了这些事件，但与无责备的事后分析文化一致，我们将修复视为我们独自的责任。这始于确保我们评估流程的每个部分都是安全的，包括我们与外部合作伙伴集成的方式。展望未来，它将包括扩大我们对评估记录中意外行为的持续监控，改进我们的调查工具，并与我们依赖的供应商进行更严格的保证工作。

我们在 OpenAI 披露其模型逃出隔离测试环境后开始了这次审查，我们赞赏他们发布了 他们的报告。虽然我们也发现了我们的模型到达了它们不应该到达的系统的证据，但这些事件在其他方面截然不同：

  • 我们在对网络安全评估记录进行主动审查后发现了这些事件；受影响的组织没有检测到这些活动，我们随后联系了所有三个组织。
  • OpenAI 的模型利用了一个新漏洞来逃出隔离，而这里评估的 Claude 模型通过一条开放路径访问了互联网。
  • 虽然两者之间没有完全清晰的界限，但我们认为这些事件更接近于测试框架和运营失败，而不是模型对齐失败。我们的模型被告知它们没有互联网访问权限并且要夺取旗帜，而实际上却被错误配置为具有互联网访问权限。这导致它们相信——可以说合理地——它们遇到的真实环境是模拟的。
  • 值得注意的是，我们最新的模型在意识到它在真实环境中工作时，停止了追求评估目标。

这些事实使我们谨慎乐观地认为，通过对评估基础设施进行更严格的监控和控制，以及持续投资于对齐研究，这类风险是可以克服的。
