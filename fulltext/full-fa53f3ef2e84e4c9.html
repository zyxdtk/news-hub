## 摘要

现代车辆安全依赖于有效的网络威胁情报（CTI）综合分析，但当前自动化工具在处理非结构化数据和汽车特定架构细节方面存在困难。为弥合这一差距，我们提出了GARAGE——一个基于RAG的框架，能够将碎片化的CTI转化为可用于自动化攻击图生成的、面向特定领域的知识库。GARAGE将12,786个CVE和140份事件报告合成为符合STIX 2.1和Auto-ISAC ATM标准的知识库。通过细粒度杀伤链分析将战术模式级场景形式化，GARAGE实现了威胁生成能力。我们的320次留一法（Leave-One-Out）实验表明，该框架能够准确地将安全知识迁移到完全未见的车辆架构上。此外，我们将GARAGE定位为人机协同工作流中的可扩展TARA支持工具，提供了全面的成本性能分析以指导其在不同LLM层级间的部署。

**关键词：** 攻击图生成 ⋅ 大语言模型 ⋅ 检索增强生成 ⋅ 车辆安全 ⋅ 网络安全

## 1 引言

虽然大语言模型（LLM）在自动化安全分析方面具有巨大潜力，但其在汽车行业的应用面临独特挑战。网络安全分析所需的大部分知识仍然是私有的、碎片化的，且难以跨组织共享。

LLM克服这一限制的一个有前景的应用是生成车辆级攻击图。传统的威胁分析与风险评估（TARA）通常局限于单个电子控制单元（ECU）。然而在实践中，安全关键型攻击很少局限于单个ECU。相反，它们利用跨多个组件和架构层的链式漏洞，包括车载网络（如CAN/以太网）、操作系统和硬件接口。构建和验证此类端到端攻击路径需要跨越网络、操作系统内核和硬件的跨领域专业知识，这对人类分析师来说难以获取和系统应用。LLM可以通过聚合分布式技术知识来弥合这一差距，支持多层安全推理。

生成攻击图需要对资产、漏洞和攻击动作（如渗透、利用）之间的关系进行建模。基于图的方法提供了显式结构，但往往无法捕获嵌入在非结构化报告中的语义上下文。基于向量的检索捕获了语义相似性，但往往无法保留因果的、逐步的链式关系。在本工作中，我们采用混合检索增强生成（Hybrid RAG [sarmah2024hybridrag]）方法，联合利用基于图的结构知识和基于向量的语义检索来构建攻击图。

当前TARA实践的人工性质 [wang2024proactive] 进一步加剧了这一挑战，这延长了评估周期并阻碍了快速演变的非结构化网络威胁情报（CTI）的及时纳入。为解决这一问题，LLM可以作为自动化分析师，直接生成攻击图并推断漏洞链式关系，以支持可操作的车辆级安全评估 [pham2021survey]。

在本文中，我们提出了GARAGE（**G**enerative **A**I with **R**AG-based **A**ttack **G**raph **E**ngine），一个端到端框架，将公开可用的汽车CTI转化为特定领域的知识库（KB），并通过基于RAG的推理自动生成车辆级攻击图。我们的主要贡献如下：

- 我们从12,786个CVE和140份安全事件文档中构建了汽车网络安全知识库，与STIX 2.1和Auto-ISAC汽车威胁矩阵（ATM）对齐。基于LLM的流水线提取安全相关的实体、关系和事件，以填充知识图谱（KG）和向量存储。我们公开发布此知识库以支持可复现性和未来研究。¹

¹ https://anonymous.4open.science/r/GARAGE-dataset-4265/

- 我们设计了一个双指标评估框架（实际可行性和知识重构），分别评估攻击路径可行性和安全知识深度，实现对LLM能力的逐维度评估。

- 通过在四个真实世界攻击和八个LLM上进行320次留一法（LOO）实验，我们基于**知识粒度**经验性地确立了**自动化边界**。具体而言，LLM能够生成高层战术威胁场景，而低层实现细节则需要人类专家介入。

- 我们通过跨专有和开放权重模型层级的成本性能权衡分析提供了量化部署指导，展示了GARAGE作为人机协同工作流中实用TARA支持工具的效用。

## 2 方法论

**图1：** 提出的GARAGE系统架构和数据流。该系统将基于图的结构检索与基于向量的语义检索集成，以提高攻击图生成质量。

### 2.1 流水线概述

GARAGE是一个基于检索增强生成（RAG）的系统，可自动生成车辆级攻击图。输入包括非结构化CTI文本、CVE描述、ATM技术定义和（可选的）目标车辆架构规范。输出是结构化JSON格式的攻击图，捕获逐步的漏洞链式关系，并由从向量存储和知识图谱中检索到的证据支持。

该流水线结合了两个互补的数据库。LLM从CTI文本中提取安全相关的实体、关系和事件，并将其存储在知识图谱和向量存储中。通过整合向量存储中的语义相似性与知识图谱中存储的跨ECU、组件和漏洞的显式结构连接性，GARAGE同时捕获了语义上下文和结构链式关系。

在推理阶段（图1），GARAGE (i) 制定ATM引导的查询并执行向量检索以收集相关CTI证据，(ii) 遍历知识图谱以获取围绕目标资产/ECU的高置信度结构证据，(iii) 使用LLM将两种证据源综合为攻击路径。为减轻幻觉，LLM的输出被约束为与检索到的实体/关系保持一致，并由底层文本证据支持。

### 2.2 数据集

CTI数据集来源于AutoSec-Timeline仓库（截至2025年12月17日）[autosec_timeline]，包含**12,786个CVE**和**140个安全事件**。

#### 2.2.1 漏洞数据

为筛选与汽车软件相关的CVE，我们从三个OEM（现代MOBIS [hd]、大众 [vw_oss]、起亚 [kia_oss]）的开源许可证声明中收集了软件名称和版本，这些OEM因其详细软件披露的公开可用性而被选中。使用这些数据，我们应用基于正则表达式的过滤来识别相关漏洞。选定的漏洞描述存储在向量存储中，提取的实体被导入知识图谱（见第2.3节）。

#### 2.2.2 安全事件数据

原始文本数据从各种来源手动整理，包括技术博客、报告和演示文稿。为保持格式一致性，PDF和PPT文档使用pymupdf4llm库转换为文本，而YouTube内容通过转录提取进行处理。对于基于图像的材料，我们提供了手动编写的自然语言描述。最初收集了164个案例，其中24个因来源不可访问（如404错误、无法访问的Tor隐藏服务）或缺乏技术细节而被排除。这一精炼过程产生了140份文档，其事件描述随后被嵌入并索引到向量存储中。

### 2.3 知识库构建

所有知识库构建阶段（实体、关系、事件提取和重写）均由相同的四个LLM独立执行：**Gemini 3.0 Flash、GPT-5.2、Claude 4.5 Sonnet和DeepSeek-V3.2**。目标是 (i) 比较安全分析任务中模型特定的**知识**和**推理**特征，以及 (ii) 评估RAG的证据锚定如何增强跨模型层级的推理。

#### 2.3.1 实体提取

我们设计了一个实体提取流水线，用于从汽车CTI来源中识别网络安全元素。作为输入，我们使用过滤后的CVE描述字段和以chunk_size=500和chunk_overlap=150分段的CTI文档。每个块独立处理，同一文档的结果在文档级别合并。

每个模型在12种预定义类型（表1）下提取实体提及。结果以结构化JSON存储，并作为规范化实体集（$E_{extracted}$）提供，以约束关系提取的候选空间。

**表1：汽车CTI的实体类型**

| 类型 | 定义 | |------|------| | component | 车辆内的硬件/软件模块 | | target_ecu | 攻击中明确针对的ECU | | vulnerability | 已识别的安全缺陷（含CWE） | | network_domain | 车辆网络段或逻辑域 | | network_protocol | 攻击中使用的通信协议 | | attack_vector | 攻击传递方法 | | supplier | 组件供应商/制造商 | | researcher | 报告漏洞的研究员/组织 | | cve | CVE标识符 | | cwe | CWE标识符 | | asset | 受影响的安全关键功能/系统 | | tool | 用于执行攻击的硬件/软件工具 |

我们特定领域的实体模式解决了通用STIX对象（如Device）的语义歧义，这些对象无法区分汽车特定组件。通过显式分离IVI和网关ECU等实体，它实现了精确的特定领域关系，如(target_ecu)--[BELONGS_TO]--(network_domain)。

所有LLM引擎共享一个标准化提示框架，包含三个核心指令：(1) **逐字提取**以防止幻觉；(2) **负面指令**以禁止生成未提及的实体；(3) **结构指导**提供清晰定义以确保一致分类（完整提示模板见附录A.2）。

#### 2.3.2 实体规范化

为消除语义冗余，我们应用基于嵌入的规范化。原始实体与CVE产品名称、描述和CWE信息整合，然后使用OpenAI的text-embedding-3-large进行嵌入（$\phi:E_{raw}\rightarrow\mathbb{R}^{d}$）。

我们执行具有平均链接和余弦距离阈值$\tau=0.3$的凝聚层次聚类，该阈值经经验调整以平衡欠聚类（如未能合并'CAN'和'Controller Area Network'）与不同实体的过聚类。

选择每个聚类中最短的字符串作为规范代表（$canonical(e)=\arg\min_{e^{\prime}\in cluster(e)}|e^{\prime}|$），优先选择标准领域缩写。在Neo4j中，我们采用**规范节点**架构：创建代表节点（如CanonicalComponent）并通过SAME_AS关系从单个实体链接，将重复条目整合为规范表示。

#### 2.3.3 关系提取

为识别提取实体之间的语义关联，我们从CTI语料库$D$中提取主-谓-宾（SPO）三元组$T=(e_{s},r,e_{o})$。相同的四个LLM独立执行关系提取，每个模型接收原始文本和规范化实体列表（$E_{extracted}$）。

**表2：三元组提取的预定义关系类型**

| 关系类型 | 定义 | |----------|------| | HAS_VULNERABILITY | 组件/ECU包含漏洞 | | IDENTIFIED_BY | 漏洞与CVE关联 | | CONNECTED_TO | 组件/ECU连接到网络域 | | USES_PROTOCOL | 组件/ECU/工具使用网络协议 | | DELIVERED_VIA | 漏洞通过攻击向量触发 | | PROVIDED_BY | 供应商提供组件/ECU | | REPORTED_BY | 研究员/组织报告了漏洞 | | AFFECTS_ASSET | 漏洞影响特定资产 | | USED_AGAINST | 工具用于攻击目标 |

所有提示强制执行五个核心约束：(1) **实体约束**（$e_{s},e_{o}\in E_{extracted}$）；(2) **关系约束**，将$r$限制为9种预定义类型（表2）；(3) **逐字一致性**；(4) **负面指令**以抑制幻觉；(5) 通过严格JSON模式进行**结构强制**。由此产生的知识图谱（四个模型平均值）包含约**8,824个唯一实体节点**和**9,265条关系边**。

#### 2.3.4 事件提取

为建模动态因果关系和行为模式，我们使用相同的四个LLM从非结构化文本中提取安全事件。每个模型识别安全事件并将其转化为结构化事件节点，包含**行为者**、**动作**、**目标**和**前/后置条件**。

每个提取的事件随后通过微调分类模型（详见第2.3.6节）映射到特定的ATM技术，该模型分配相应的technique_id（如ATM-T0059）并通过CLASSIFIED_AS关系进行链接。这种层次结构允许追踪特定组件上的单个动作如何映射到更广泛的攻击战术。

#### 2.3.5 重写

重写阶段将结构化实体和关系转换回自然语言，以提高检索质量。四个LLM各自独立地从已验证的事实三元组中综合事实摘要，排除原始CTI文本中的噪声。生成的摘要存储在向量存储中，引导RAG系统检索精炼的事实信息而非嘈杂的非结构化数据（附录A.2）。

#### 2.3.6 技术提取

为分类ATM技术，我们基于GPT-4.1-2025-04-14通过监督微调（SFT）开发了一个微调模型。零样本提示在细粒度技术分类方面显示出高成本和有限精度，因此需要SFT方法。训练数据集由最新的ATM数据和以五种叙事风格（研究报告、安全公告、新闻稿、论坛帖子和培训材料；附录A.2）合成的虚拟事件报告构建。

三项措施确保训练稳健性：(1) **标签泄露预防**，将技术名称和ID从生成的叙事中列入黑名单；(2) 通过字符级噪声注入和随机截断进行**数据增强**；(3) **语义一致性验证**，每个增强样本由单独的LLM重新分类以过滤不一致的示例。此外，还纳入了从非安全上下文（如车辆维护日志）中提取的负样本以抑制误报。

### 2.4 使用混合RAG生成攻击图

#### 2.4.1 上下文感知向量检索

为在检索过程中反映特定车辆规格，我们采用三阶段检索流水线。(1) **动态查询生成**：系统分析车辆规格以识别ECU和协议等实体。(2) **ATM引导的查询制定**：通过连接每个ATM技术的标题和描述来构建查询，使检索与操作上下文对齐。(3) **交叉编码器重排序**：使用交叉编码器（ms-marco-MiniLM-L-6-v2）对初始候选进行重排序，该编码器同时评估查询-文档对以选择前10个文档作为最终上下文。

#### 2.4.2 结构化知识图谱遍历

为用显式组件连接性补充非结构化文本，我们采用基于Neo4j的知识图谱。车辆规格中的ECU ID和协议名称被映射为**种子节点**，遍历被严格过滤为仅遵循安全关键关系（HAS_VULNERABILITY、DELIVERED_VIA、EXPLOITS），最大深度为2跳。此约束有效捕获核心因果链，如"ECU→组件→漏洞"，避免穷举式图遍历。

对于密集连接的节点，原始SPO三元组被LLM生成的安全摘要替代，该摘要编译了实体关联的漏洞和攻击向量，遵循GraphRAG [edge2024local]的社区摘要原则。这减少了提示令牌消耗，同时保留了基本的安全语义。

#### 2.4.3 混合上下文集成与攻击图生成

从向量存储检索的相似攻击案例和从知识图谱遍历的组件-漏洞关系被集成到统一提示中。当两个来源冲突时，采用保守方法：知识图谱中记录的漏洞默认假定存在。向量存储证据（如补丁说明）仅在明确引用目标车辆的制造商、型号和年份时才覆盖此假设，在这种情况下，相应攻击路径的可行性被降低或排除。然后LLM使用此混合上下文连同目标车辆的网络拓扑来推断多阶段攻击路径，输出结果为结构化攻击图。

## 3 实验

我们围绕三个研究问题设计实验，以评估GARAGE的有效性、可靠性和实用性。

- **RQ1：对未知威胁的推理能力。** 评估当缺乏目标攻击的直接知识时，框架是否能仅从车辆架构规范推断潜在攻击路径。

- **RQ2：作为专家助手的可靠性。** 确定框架在重复试验中是否保持一致结果，确保自动化专家助手所需的稳定性。

- **RQ3：成本性能效率。** 调查开放权重模型是否在保持足够分析深度的同时，提供专有模型的可行、经济高效替代方案。

### 3.1 评估基准

我们选择了四个记录详尽的汽车网络安全事件（$C_{1}$–$C_{4}$），代表不同的架构和攻击向量：

- **$C_{1}$**：Jeep Cherokee [jeep_hacking] — 通过蜂窝网络远程利用，针对Uconnect和网关（V850）以控制CAN总线。验证传统架构中的攻击路径。

- **$C_{2}$**：Mercedes-Benz W177 [mercedes_hacking] — 利用车机-后端通信和WebKit缺陷。评估联网汽车分析。

- **$C_{3}$**：Nissan Leaf [nissan_hacking] — 通过免提配置文件（HFP）的蓝牙栈缓冲区溢出实现IVI上的远程代码执行。测试短距离无线漏洞检测。

- **$C_{4}$**：BMW i3 [bmw_hacking] — 多向量攻击（GSM、蓝牙、USB）危害HU和TCU，通过UDS诊断消息绕过网关。

**基准真值与控制。** 我们从详细技术白皮书手动重建攻击场景，参考$C_{1}$和$C_{4}$的ATM事件示例 [autoisac_atm]。基准真值通过将攻击路径映射到ATM战术和技术来建立。

执行了两个严格控制：(1) LOO策略，从知识库中排除目标事件数据；(2) **实体匿名化**，以防止参数记忆回忆并强制架构推理。我们从查询中省略了车辆品牌和型号名称，并严格过滤了向量存储和知识图谱中包含目标特定关键词的检索结果（如$C_{1}$的jeep、uconnect；$C_{4}$的bmw、connecteddrive）。通用技术术语（如SPI、CAN、蓝牙）被有意保留为跨车辆共享的领域通用知识。

### 3.2 实验环境

#### 3.2.1 知识库配置

### 3.3 评估方法：LLM作为评判者

单一指标无法同时捕获攻击路径可行性和知识准确性；双指标设计实现了分别分析——例如，高KR但低PF表示强大的领域知识但路径一致性差，这是开放权重模型中常见的结果。

#### 3.3.1 实际可行性（PF）

PF从红队视角评估攻击路径可行性，强制执行**级联失败**原则：如果步骤$k$无效，则所有后续步骤（$i\geq k$）被评分为失败。PF包含三个组成部分：

**(1) 链完整性（最高60分）**：在第一个无效点$k$之前连续有效步骤的比率。每个步骤$s_{i}$被评分为VALID（1.0）、PARTIAL（0.5）或BROKEN（0.0）：

$$Score_{PF\text{-}Comp}=\frac{\sum_{i=1}^{N}s_{i}}{N}\times 60\quad\text{其中 }s_{i}=0\text{ 当 }i\geq k$$

**(2) 攻击可行性（最高30分）**：相邻步骤之间的逻辑转换有效性，评分为FEASIBLE（1.0）、QUESTIONABLE（0.5）或INFEASIBLE（0.0）：

$$Score_{PF\text{-}Feas}=\frac{\sum_{j=1}^{k-1}t_{j}}{N-1}\times 30$$

**(3) 严重违规（最多-20分）**：对物理/逻辑不可能性的惩罚（如信任边界跨越-10分，协议不匹配-5分）。不与已评分为0的元素重复扣分。

#### 3.3.2 知识重构（KR）

与PF不同，KR独立于逻辑链完整性来衡量安全知识深度——即使前一步骤被遗漏，准确识别后续步骤仍可获得分数。

**(1) 实体与步骤识别（最高50分）**：5级语义匹配量表（$m_{i}$）：FULL（1.0）、SEMANTIC（0.75）、PARTIAL（0.5）、WEAK（0.25）或NONE（0.0）：

$$Score_{KR\text{-}Iden}=\frac{\sum_{i=1}^{N}m_{i}}{N}\times 50$$

**(2) 结构知识（最高30分）**：转换连接性分类为CONNECTED（1.0）、IMPLIED（0.5）或DISCONNECTED（0.0）：

$$Score_{KR\text{-}Struct}=\frac{\sum_{j=1}^{N-1}c_{j}}{N-1}\times 30$$

**(3) 知识精确度（最高20分）**：基线10分；准确细节加分（如精确CVE），仅对幻觉扣分（如虚构ECU）。有效的替代攻击路径不扣分。

**评估设置。** 我们采用LLM-as-a-Judge方法，最近的研究表明在结构化评分标准的指导下，该方法与人类专家评分具有高度一致性 [zheng2023judging]。为减轻自我评估偏差，我们使用Claude 4.5 Sonnet（temperature=0.3）作为独立评判者。我们PF/KR评估方案中的固定评分类别和显式标准进一步约束了主观变异。评估涵盖320个实例（8个模型 × 4个场景 × 10次迭代），产生640个评估配置（每个实例PF + KR）。

这一模式展示了自动化知识迁移的局限性。对于依赖于目标特定固件或软件内部的步骤，仅依靠知识检索是不够的，通过人机协同验证进行逆向工程或动态分析仍然是必要的。

**RQ1结论：** GARAGE证明，在LOO条件下，它可以通过从其他车辆攻击案例和CTI迁移知识来重建有效攻击路径（专有模型平均PF 59.0/100）。性能取决于四个关键因素：知识粒度、结构复杂性、组合推理和RAG增强范围。GARAGE对**战术模式级威胁建模**最为有效；实现细节存在需要人机协同方法的基本限制。

## 5 讨论与局限

### 5.1 讨论

**关键发现。** 我们在四个真实世界汽车攻击和八个LLM上进行的320次LOO实验揭示了三个关键发现。

**第一**，**基于知识迁移的未知威胁推理在实践中是可行的**：即使移除了所有直接攻击知识，专有模型仍以59.0/100的平均PF重建了有效攻击路径。这种迁移通过两条互补路径发生——从特定领域知识库的显式检索和从LLM参数化知识的隐式回忆。虽然我们的消融研究表明两条路径都达到了可比的PF分数，但只有基于知识库的路径提供了正式的证据可追溯性，这是法规合规性的先决条件（见**检索模式的作用**）。

**第二**，**性能受知识粒度的结构性约束**：知识库匹配率与PF之间的强相关性（BMW 88.8%→66.4 vs. Jeep 38.8%→33.9）表明，威胁定义的抽象水平设定了自动化推理的上限。无论模型能力如何，这一约束都持续存在。战术模式级威胁非常适合自动化推理，而实现细节级威胁则建立了知识迁移的结构性边界。

**第三**，**模型选择的影响高度依赖于上下文**：最佳-最差性能差距（Claude 64.8 vs. GPT-OSS-20B 29.8）远超95% CI（±5.9），但这一方差在以低知识粒度和高结构复杂性为特征的场景中被放大。这表明模型选择必须根据威胁类型的具体特征进行定制。

**实践意义。** 作为支持UN R155和ISO/SAE 21434下TARA合规性的自动化工具，GARAGE可以系统地生成初始威胁场景候选。如第4.1.2节报告的，初始访问（95.0%）和影响车辆功能（98.8%）的高杀伤链覆盖率表明，系统可以覆盖分析师可能遗漏的入口点和影响场景。相反，执行（15.0%）和C2（32.5%）的较低覆盖率确认GARAGE作为人机协同工作流中的**专家助手**最为有效，自动化初始威胁探索，同时将技术验证和优先级排序留给领域专家。

在ISO/SAE 21434 TARA工作流的背景下，这一自动化边界直接映射到特定流程阶段：GARAGE促进**威胁场景枚举**和**初始攻击路径生成**，对应高覆盖率战术。然而，**攻击可行性验证**需要目标系统的实现级知识（涉及执行和C2等低覆盖率战术），因此仍然是手动专家任务。

对于部署，我们的RQ3结果提供了模型选择的量化标准：Claude 4.5 Sonnet（PF 64.8）适用于精度关键的法规合规性；Gemini 3.0 Flash以极低成本达到了Claude 87%的性能（PF 56.3 vs. 64.8），使其适用于大规模分析；Qwen3-Coder是气隙本地环境的替代方案，但应考虑API定价之外的总拥有成本（GPU基础设施）。

**检索模式的作用。** 比较仅图、仅向量、无RAG条件与完整混合配置的消融研究显示PF变化可忽略（所有条件下$\Delta$PF < 1.2）。这表明**知识粒度——底层知识库的质量和覆盖——是决定推理性能的主导因素**，而非特定的检索模式。知识库提供了所有检索策略所依赖的基础知识；因此，本工作的核心贡献是特定领域的知识库构建流水线、双指标评估框架以及关于知识迁移边界的经验发现。

尽管如此，特定领域知识库和RAG流水线对于实际部署是不可或缺的。虽然无RAG条件通过依赖参数化记忆达到了可比的PF分数，但其输出缺乏**正式证据可追溯性**——将每个攻击步骤追溯回特定CVE、CTI报告或知识图谱节点的能力。在UN R155和ISO/SAE 21434下，没有正式锚定的输出不能作为可审计的合规证据。通过设计，基于RAG的架构将生成的攻击路径锚定在检索到的源产物中，从而提供了法规标准所要求的可追溯性。量化每个生成步骤的锚定率仍是未来工作。

### 5.2 局限

**L1：有限的基准真值规模和主观性。** 评估依赖于四个公开的汽车攻击案例，这些案例是汽车网络安全中记录最详尽的。然而，小样本量限制了统计泛化性。因为基准真值构建不可避免地涉及研究者解释，三位领域专家独立重建了每个基准真值，参考ATM官方示例（$C_{1}$、$C_{4}$）或技术白皮书（$C_{2}$、$C_{3}$），通过共识解决任何分歧。我们通过评估结构连贯性和实际可行性而非要求精确匹配来进一步减轻主观偏差，从而接受语义等价的替代路径。

**L2：LLM作为评判者的偏差。** 使用Claude 4.5 Sonnet同时作为目标模型和评估者引入了潜在的模型家族偏差。为减轻这一风险，我们实施了四项不同的保障措施： 生成和评估阶段之间的完全会话隔离；(ii) 双独立指标（PF/KR）；(iii) 所有测试模型的统一评估标准；(iv) 要求所有模型以相同JSON模式生成攻击图的结构化输出格式，消除了风格偏好作为混淆因素。经验上，未观察到系统性偏差；例如，在Jeep案例中Gemini（64.0）优于Claude（59.0）。

为进一步验证评判者可靠性，我们在两个案例（$C_{1}$、$C_{4}$；$N$=160）上使用GPT-5.2和Gemini 3.0 Flash进行了交叉评判评估。如表10详述，成对Spearman相关系数表明强一致性（$\rho$=0.74–0.84，$p<0.001$），确认无论使用哪个评判模型，模型排名都保持一致。

**L3：LLM幻觉。** 在所有320次实验中，76.9%的生成攻击图包含至少一个幻觉元素（平均每次实验1.74个），幻觉率从52.5%（GPT 5.2）到95.0%（Qwen3-Coder）不等。常见幻觉类型包括虚构的CVE标识符、不存在的协议名称以及未锚定于输入车辆规格的通用网络细节。20分中平均9.81的知识精确度分数表明，约一半的生成知识元素缺乏与检索上下文的直接可追溯性。这一结果支持了人机协同工作流的必要性：虽然GARAGE有效地生成候选攻击路径，但在操作使用前仍需专家审查以过滤幻觉产物。

**L4：LOO与真正的零日漏洞。** LOO实验设计通过系统性地排除目标案例来模拟未知威胁；然而，真正的零日场景可能涉及完全新颖的攻击面，这些攻击面在知识库中本质上缺乏任何可迁移的参考。因为我们的LOO条件确保至少有三个其他权威车辆攻击案例的可用性，它代表了对知识迁移能力的受控评估，而非严格的最坏情况评估。

**L5：车辆架构输入要求。** 我们的实验从公开可用的技术报告和白皮书重建车辆架构规范，代表了从开源可恢复的最大细节。在实践中，OEM很少披露完整的E/E架构细节或SBOM，限制了外部分析师的规格保真度。此外，验证可操作性可利用性需要物理测试台访问。因此，GARAGE被设计为生成TARA优先级排序的**合理威胁场景**，而非确认的利用链。

**L6：跨架构的泛化性。** 我们的评估基于2014-2018年时代的车辆架构。现代软件定义车辆纳入了更强的安全控制（如HSM、SecOC和汽车以太网），可能表现出不同的可迁移性特征。然而，该框架可以通过更新知识库和威胁分类法扩展到更新的架构。

## 6 相关工作

**攻击图与汽车领域应用。** 攻击图是建模多步骤攻击路径的关键工具。早期的基于逻辑的框架如MulVAL [ou2005mulval]从形式化的漏洞和配置输入中推断攻击路径。然而，这些方法依赖于预定义的静态规则，产生了知识获取瓶颈，限制了非结构化威胁情报的整合。将攻击图应用于汽车领域的研究主要集中在自动化ISO/SAE 21434标准要求的TARA流程上。早期研究如Salfer等人 [salfer2024automotive]和GAPP [saulaiman2025graph]使用攻击图分析车载网络的架构漏洞。后续工具如ThreatGet [chlup2022threatget]通过自动化资产驱动的攻击树分析支持ISO/SAE 21434合规性。另外，基于本体推理的动态攻击图生成算法被提出用于车联网环境。然而，这些方法通常关注车辆级评估，在解决ISO/SAE 21434要求的"功能级"TARA方面存在局限。此外，车辆独特的协议（如CAN、V2X）和架构创造了通用IT工具无法捕获的领域知识差距。为解决这一问题，引入了特定领域的知识库，如CAKG [yang2023cakg]（车辆特定网络安全知识图谱）和Acti数据集（手动标注的汽车CTI报告）[wang2025dataset]。尽管有这些贡献，它们没有提供将此知识自动链接到TARA攻击图生成的端到端解决方案。

**基于CTI的知识图谱构建与LLM。** 从非结构化CTI中提取结构化知识已被广泛研究。标准化本体如UCO [syed2016uco]提供了知识表示的模式。早期基于NLP的研究，如Open-CyKG [injy2021open]和AttacKG [li2022attackg]使用专门训练的神经模型从CTI报告中提取实体和关系。然而，这些方法不够灵活，过拟合于特定数据集和模式，且适应新威胁时产生高再训练成本。LLM的最新进展提供了灵活的替代方案。LLM使用预训练知识解析复杂的CTI文本，无需任务特定的微调。LLM-TIKG [hu2024llm]和CTINexus [cheng2025ctinexus]提出了使用LLM上下文学习（ICL）的灵活且适应性强的CTI到知识图谱流水线。此外，CTIKG [huang2024ctikg]引入了多智能体和双记忆架构来减轻LLM幻觉。总之，这些研究表明LLM可以减少CTI分析中的知识获取瓶颈。CTI-HAL [della2025cti]等基准进一步实现了系统性的性能验证。

**LLM驱动的攻击图自动化。** 最近的工作将LLM直接集成到攻击图生成逻辑中，超越了CTI到知识图谱的预处理。AttacKG+ [zhang2025attackg+]通过利用LLM推断攻击节点之间的依赖关系来增强攻击图构建。这一趋势导致了多模态方法的出现，如MM-AttacKG [zhang2025mm]，它分析CTI报告中的文本和图像（如威胁图、截图）。尽管有这些进展，这些基于LLM的方法与汽车领域特定TARA要求之间仍存在关键差距。

具体而言，最新的LLM-攻击图框架是领域无关的。它们缺乏建模汽车E/E架构独特约束或CAN总线特定漏洞所需的内置知识。相反，汽车领域特定研究，如CAKG [yang2023cakg]和Acti数据集 [wang2025dataset]，主要关注构建基础知识库，但未扩展到端到端攻击图生成。

总之，没有现有框架有效地将LLM的解析灵活性与汽车特定CTI处理相结合以自动生成TARA就绪的攻击图。本文提出GARAGE来填补这一差距。GARAGE是一个端到端框架，使用基于LLM的CTI提取、特定领域的汽车网络安全知识库和基于RAG的推理来生成车辆级攻击图。我们通过跨八个LLM的经验分析使用双指标方法评估此框架。

## 7 结论

本文提出了GARAGE，一个端到端框架，将公开可用的汽车CTI转化为特定领域知识库，并通过基于RAG的推理自动生成车辆级攻击图。该知识库包含12,786个CVE和140个安全事件，按照STIX 2.1和ATM结构化。我们使用双指标框架（PF和KR）评估了生成的攻击图。

通过在四个真实世界攻击案例和八个LLM上进行320次LOO实验，我们展示了向未见架构的跨车辆知识迁移。具体而言，即使没有目标攻击的直接知识，专有模型仍以59.0的平均PF重建了有效攻击路径。基于杀伤链分析和**知识粒度**，我们识别了清晰的自动化边界：自动化生成对战术模式级威胁场景有效，而实现细节级阶段需要人类专家介入。消融研究确认，知识库质量和覆盖（而非检索模式）是主导性能因素，强调了知识库构建流水线的核心地位。因此，我们的主要贡献是特定领域的知识库构建流水线、评估方法论以及关于自动化边界的经验发现。

这些结果表明GARAGE作为人机协同工作流中的实用TARA支持工具。此外，我们的发现为部署各种LLM层级提供了成本性能指导。未来工作将把评估扩展到软件定义车辆架构，并探索与实时CTI源的集成。

``` You are an expert automotive cybersecurity analyst specializing in extracting structured information from technical texts, incident reports, and vulnerability descriptions.

### Additional Instructions for Accuracy: - Grounding: Ensure all identified entities are derived explicitly from the input text. Do not hallucinate entities not present in the text. - Standardization: If an entity is referred to multiple times with slight variations, always standardize to the exact same name. - Coreference Resolution: If a pronoun is used, replace it with the specific entity name it refers to. Do NOT extract pronouns as entities. - Conciseness: Entities must be specific noun phrases (typically 1-5 words). Do NOT extract full sentences or descriptions of actions.
