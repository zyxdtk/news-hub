引言
仓库级代码翻译——即将整个代码库从一种编程语言转换为另一种编程语言的过程

语言（PL）之间的转换对于提高软件的可靠性与安全性、减少技术债务至关重要（Jamshidi 等，2013；Jain 和 Chana，2015；Khadka 等，2014；Nisar，2022）。早期工作开发了基于规则的方法（Immunant，2024；Transpile，2024；Project，2026；Irwin，2026），例如 C2Rust，其中所有翻译规则均由人工编写。后续工作发展了神经符号技术（Cai 等，2025；Luo 等，2025；Nitin 等，2025；Wang 等，2025e；Zhou 等，2025；Dehghan 等，2025；Ibrahimzada 等，2025；Zhang 等，2025；Shetty 等，2024；Wang 等，2025a, c；Yuan 等，2025），将大型语言模型（LLMs）与（符号化）程序分析和测试相结合。最近，还评估了基于代理的方法（Khatry 等，2025；Guan 等，2025；Li 等，2025；Sim 等，2025），其中一个或多个 LLM 代理协同工作，以在特定的源-目标编程语言（PL）之间进行代码转换。

先前的基于规则和神经符号的翻译技术仅在单一源-目标编程语言对上进行评估（Immunant，2024；Ibrahimzada 等，2025；Wang 等，2025a；Zhang 等，2025；Nitin 等，2025；Shetty 等，2024；Dehghan 等，2025；Xue 等，2025；Yang 等，2024c）。这是由于将一种编程语言作为源语言或目标语言支持所需的巨大工程工作量。规则的实现

基于模型的工具可以处理超过 100K 行代码（LoC）的项目，例如 C2Rust（Immunant, 2024）（100K+ LoC）；而神经符号工具则可以处理超过 10K 行代码的项目，例如 AlphaTrans（Ibrahimzada et al., 2025）（11K LoC）、Oxidizer（Zhang et al., 2025）（19K LoC）和 Skel（Wang et al., 2025a）（4K LoC）。然而，这些工具仅支持单一源-目标编程语言（PL）对。考虑到编程语言对的数量呈二次方增长，将这些技术扩展到多个 PL 对是不切实际的。一种与编程语言无关（PL-agnostic）的方法可以在无需复杂工程和外部第三方依赖的情况下，实现跨多个 PL 对的代码翻译和验证。

理论上，智能体（agents）可以实现与编程语言无关的代码翻译。然而，构建端到端的智能体代码翻译和验证流水线仍面临以下挑战：

(1) 真正的编程语言无关性。
现有的智能体框架基于迭代的“推理-行动-观察”原则（Yao et al., 2022）。通过工具使用执行的“行动”是实现智能体自主性的关键组成部分。在代码翻译和验证的上下文中，工具可以帮助智能体探索和分析代码库、确定翻译单元，并验证翻译结果。现有的智能体代码翻译技术要么仅使用基础、简单的工具来探索代码库（Khatry et al., 2025），要么使用特定于编程语言的工具（Li et al., 2025）。

(2) 在仓库级别代码翻译和验证中的幻觉问题。
在翻译包含数十万行代码的大规模代码仓库时，智能体容易产生幻觉（hallucination），即生成不准确或虚构的翻译结果。

或数百个文件，尤其是在翻译与验证集成的情况下，是一项长期任务（Erdogan 等，2025；Chen 等，2025；Sun 等，2025），其中幻觉（hallucination）是代理在此任务中的主要挑战。在代码翻译的背景下，这包括对类/文件/方法/变量名称的幻觉、寻找匹配的库，或翻译测试断言。
如果不考虑轨迹上下文和幻觉问题，代理式的代码翻译与验证可能会生成无法编译或无法保留原始功能的代码。
(3) 测试翻译的二元对立。
先翻译再验证的方法在大规模仓库级翻译中行不通，因为存在长调用链和测试耦合效应（Ibrahimzada 等，2025）。此类系统通常使用现有的开发者编写的测试来验证功能等价性，要么通过测试翻译和执行，要么通过语言互操作性。鉴于任意编程语言对之间可能不存在语言互操作性，一种与编程语言无关的方法可能需要基于现有测试的翻译以及额外的测试生成。总体而言，代码生成和验证是两个相互冲突的目标，不应由同一个代理完成（Lin 等，2025；McAleese 等，2024；Huang 等，2023；Qian 等，2024；Dong 等，2024；Islam 等，2024）；否则，代理可能会修改测试而非

将错误的代码翻译视为成功，例如通过删除或放宽断言。同时，已知在真实场景中进行测试翻译比代码翻译更具挑战性（Abid 等，2024；Pan 等，2024），需要将代码作为上下文以理解复杂对象的结构。因此，简单地将代理分离为一个用于翻译、一个用于验证的方式可能行不通。

(4) 透明且以流程为中心的评估。
现有的代理技术很少讨论代理式代码翻译工作流的原理性设计空间（Li 等，2025；Guan 等，2025；Khatry 等，2025）。它们并未评估架构选择如何影响最终翻译质量。尽管它们都通过测试执行来验证翻译结果，但关于测试翻译局限性的讨论却很少（Ibrahimzada 等，2025），例如在测试翻译过程中删除断言语句、生成新测试时缺乏或质量低下的断言，以及由于相应误报而导致研究结果有效性受到威胁（Ke 等，2025）。此外，成本报告缺乏透明度，也无人尝试分析超出最终翻译结果之外的执行轨迹。

ReCodeAgent 利用一组模型上下文协议（MCP）工具，提供静态分析能力，并促进代理与代码库的有效交互。MCP 是一个开源协议，允许大语言模型（LLM）无缝连接外部数据、工具和软件系统。我们实现了自定义工具，并通过 MCP 将其暴露给 ReCodeAgent 中的每个代理。这些工具使代理能够以与编程语言无关的方式获取详细的项目信息、修改代码以及检索文档。

3.1.1. 语言服务器协议（LSP）工具

LSP 是一种基于 JSON-RPC 的开放协议，用于源代码编辑器或集成开发环境（IDE）与提供语言智能功能的服务器之间通信：包括特定编程语言的功能，如代码补全、语法高亮、警告和错误标记，以及重构操作（Agrawal 等，2023）。该协议的目标是允许编程语言支持的实现和分发。

独立于任何特定的 IDE 进行分发。我们使用来自六种编程语言（Team, 2026i, d, c, k, j, b）的语言服务器协议（LSPs）作为一组工具，使智能体能够以语义级别与代码库进行交互，而无需依赖底层编程语言。扩展对更多编程语言的支持仅需安装其语言服务器，这些服务器通常由维护者在线提供（Microsoft, 2026），无需编写任何额外代码。

我们实现的 LSP 功能包括：

(1) definition：以符号名称作为输入，从代码库中检索完整的实现（例如函数、类）以及文件路径和行号，使智能体能够理解并提取源代码片段以进行翻译。

(2) diagnostics：为指定文件提供诊断信息，如错误和警告，帮助智能体识别源代码和翻译后代码中的潜在问题。IDE 通常在代码编辑器中通过红色和黄色下划线标示错误和警告。

(3) edit_file：原子性地对文件应用一组文本修改，支持翻译项目的增量构建和优化。当需要应用大量修改时，该工具非常有用，避免了为每次修改都调用智能体的 Edit 工具。

(4) hover：返回代码中指定位置符号的文档信息，包括文档字符串和代码弃用详情。图 3 展示了普通 IDE 中的 hover 功能，而相同功能在我们的系统中也得以实现。

(5) references：在代码库中定位符号的所有出现位置和用法，对于代理进行大规模代码重构至关重要。该工具返回每个用法的确切行号，便于代理后续引用。

(6) rename_symbol：在指定位置重命名符号，并更新项目中所有相应的引用。该工具有助于在代码库中进行一致性的修改，无需额外的手动编辑。

3.3.1. 片段提取
代理首先从源代码和测试文件中提取所有翻译单元——包括函数、方法和类。片段提取使用 get_file_structure 工具完成，同时保持严格的“验证循环”过程。为进行验证，代理生成可执行脚本，以验证每个提取的片段是否存在于源代码库中，且没有遗漏任何文件。此验证步骤可缓解代理“幻觉”问题，即代理错误地认为任务已完成而实际上并未完成。该阶段最终生成一个提取片段的文档，每个片段以 file_name:fragment_name 的格式记录。
3.3.2. 名称映射
为确保一对一翻译和命名一致性，代理构建从源片段到目标片段的映射关系。

rget 对应项，严格保留符号名称（例如，camelCase、snake_case），以保持项目中功能的一致性。该映射随后在骨架生成过程中使用，以在目标编程语言中生成准确的方法签名，防止 LLM 随意重命名方法和类，从而阻碍翻译追踪。

3.3.3. 骨架生成

代理随后构建目标项目的目录结构，并用骨架文件填充。这些骨架文件包含类声明和方法签名，但不包含具体实现。这种方法提供了一个可编译的框架，其结构与源项目一致，使得翻译过程可以逐步进行。

3.3.4. 实现计划

实现计划是一个结构化的文档，分为源代码翻译（Part A）和测试代码翻译与验证（Part B）两部分。该计划遵循自底向上的顺序，确保在依赖模块之前先实现其依赖项。例如，Part A 中的一个示例步骤可以是：“翻译 HelpFormatter.py 并验证其语法正确性”。计划中的每一步都应生成可编译的代码，并为 Translator（§3.4）和 Validator（§3.5）代理提供明确的检查清单以执行。

3.5. Validator Agent

Validator Agent 验证翻译后项目的功能正确性（算法 1，第 14–21 行）。给定由 Translator Agent 生成的翻译项目（包括翻译后的测试），该代理执行测试、进行覆盖率缺口分析，并生成验证报告，反馈给 Translator Agent 以便在下一轮迭代中进行修复。

3.5.1. 验证与失败报告

该代理在目标环境中执行翻译后的测试套件，并检查所有测试是否通过。如果出现失败（例如编译错误或断言失败），代理将诊断信息（包括堆栈跟踪和失败的测试用例）整合成结构化的验证报告。该报告标识出失败的函数，并为 Translator Agent 在下一轮迭代中的修复步骤提供可操作的反馈。

3.5.2. 基于覆盖率的测试生成

为了全面验证翻译后的模块，代理通过将已执行的测试与规划阶段识别出的完整函数列表进行对比，执行覆盖率缺口分析。如果仍有未覆盖的函数，它将在源语言和目标语言中生成额外的测试用例，以覆盖这些未覆盖的函数，并将它们添加到翻译后的项目中。生成的测试用例将在两种语言中执行，以确保行为一致。随后，代理重新执行验证，更新验证报告，确保覆盖完整。

Nitin et al. (2024) 从源代码中提取自然语言规范以指导翻译过程，而 Yang 等人 (Yang et al., 2024c) 利用测试用例来支持该过程。

LLM Agents
基于代理的框架的兴起 (Liu et al., 2024; Xi et al., 2025) 引发了大量研究和工业界对将这些架构应用于各种软件工程挑战的兴趣 (Jimenez et al., 2024; Yang et al., 2025; Chowdhury et al., 2024)。
SWE-agent (Yang et al., 2024b) 引入了一种专用的代理-计算机接口（ACI），使代理能够通过读取、编辑文件以及执行 bash 命令与代码仓库进行交互。
AutoCodeRover (Zhang et al., 2024) 为 LLM 代理配备了 de

专用的代码搜索 API，支持迭代检索和定位与软件缺陷相关的代码片段。在此基础上，SpecRover（Ruan 等，2025）扩展了 AutoCodeRover，专注于规范推断、生成函数摘要，并在代理工作流的关键节点提供有针对性的反馈。Agentless（Xia 等，2025）表明，即使是最简单的 LLM 代理，也无需复杂的工具链或对环境行为进行复杂建模，即可解决现实世界中的缺陷。除了这些领先的框架外，开源（Wei 等，2025；Ouyang 等，2025；Bouzenia 等，2024）和商业解决方案（Wang 等，2025b）中也提供了多种基于代理的方法。

6. 有效性威胁

与先前的技术类似，ReCodeAgent 也存在一些局限性和有效性威胁。本节中，我们讨论了如何缓解这些威胁。

内部有效性

一个主要的内部威胁是我们每次实验仅运行一次。由于 LLM 具有非确定性，重复运行可能会产生不同的单个测试结果。然而，考虑到我们评估的规模（118 个项目），聚合指标不太可能显著变化。

外部有效性

主要的外部威胁涉及可推广性。为缓解这一问题，ReCodeAgent 被设计为与编程语言无关（PL-agnostic），只需极少的工程工作即可扩展到新的编程语言对。我们的初始实现支持六种编程语言，涵盖四种编程语言对。次要威胁

是数据污染，因为我们的基准程序很可能包含在 Claude 的预训练数据中，从而可能夸大了其表现。

构念效度。

  1. 结论
    在本研究中，我们提出了 ReCodeAgent，一个语言无关的仓库级代码翻译与验证框架，该框架集成了四个专用的 LLM 代理，以实现高质量的翻译，并通过开发者编写的测试和代理生成的测试进行验证。
