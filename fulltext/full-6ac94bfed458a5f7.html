摘要
程序化生成器能够大规模生成有用的可验证推理问题，但作为补全监督微调的数据受到的关注较少。我们引入了 Reasoning Core，这是一个包含 50 个生成器的集合，涵盖数学、逻辑、规划、状态跟踪、形式语言、结构化数据、游戏、因果和代码，并配备了语义评分器、难度控制和任务评估器。在匹配的补全监督协议下，我们在四种基础模型设置和多种训练时长下，将 Reasoning Core 与 Procedural Warmup、Reasoning Gym 和 SynLogic 进行了比较。在主要的 3B 模型对比中，Reasoning Core 在 DROP、LogiQA 和 ARC-Challenge 上取得了最高平均分，超越了无程序化数据的基线以及所有三个替代程序化数据集。任务级分析表明，仅语义有效性并不能保证训练效用，突出了紧凑目标和校准难度作为重要设计因素。我们进行了结合模型辅助审查、人工裁定和回归测试的审计。这些审计贯穿 Reasoning Core 的开发过程并应用于其他数据集，揭示了生成、渲染、目标和评分之间的细微不匹配，提醒我们仅靠程序化生成并不能保证正确性。该库、生成的数据集和审计材料已公开可用¹。

1 引言
语言模型的推理能力是由其在训练期间遇到的问题塑造的。程序化生成器对训练分布提供了强大的控制：它们可以按需生成新样本，计算或验证其目标，并直接改变结构和难度。这种方法在训练的不同阶段都得到了探索。Jiang 等人（2026）表明，在抽象程序化序列上进行简短的预热可以改善后续的语言模型训练，而 Reasoning Gym 和 SynLogic 则提供了广泛的可验证推理环境集合，主要用于带有结果奖励的强化学习（Stojanovski 等人，2025；Liu 等人，2025；Guo 等人，2025）。

与此同时，迅速增长的文献开始质疑推理强化学习在 RL 之前建立的能力和表征之上创造了多少东西，并强调了监督或早期训练分布的重要性（Zhang 等人，2025；Akter 等人，2025；Yue 等人，2025；Yuan 等人，2025；Matsutani 等人，2025）。这些结果共同促使我们直接研究监督数据层：广泛的程序化集合能否加强后续训练所依赖的起点？

这留下了一个基本的数据设计问题：如何设计和表示广泛的可验证推理样本集合，使其成为有效的监督微调（SFT）数据？可验证的生成问题并不自动是有用的监督数据。它们的价值取决于渲染的实例是否决定了预期的答案、答案的表示方式、哪个难度范围提供了可学习的信号，以及任务在异构混合中是否仍然有用。这些选择共同决定了如何有效地将固定的 token 预算转化为有用的训练信号。

我们引入了 Reasoning Core，这是一个包含 50 个程序化生成器的集合，专为广泛的补全监督训练而设计，同时保留与可验证 RL 的直接兼容性。这些任务涵盖不同的领域（见表 1）。它们共享一个任务接口、紧凑的目标约定、语义评分、难度控制和通用的诊断套件，而不强迫每个任务使用单一的生成模板。

我们区分了语义有效性（渲染的实例是否具有正确且可识别的目标）和训练效用（在指定的模型、目标、剂量和混合下，接触该实例是否能提高下游性能）。我们通过对四个程序化集合在四种基础模型设置和几种训练时长下的控制比较来研究这两者，并辅以自由生成、保留和仓库审计诊断。

我们的贡献是：
• 一个广泛、可复现的资源。Reasoning Core 提供了 50 个带有语义评分器、难度控制的生成器，以及一个用于 SFT、评估和 RL 的接口。此次发布包括生成的数据集、版本化清单、缓存、行为哈希、任务级测量和审计材料。
• 受控的集合比较。我们在四种基础模型设置和几种训练时长下比较了四个程序化集合，并进行了完整的留出评估。
• 仓库规模的语义审计。模型辅助审查、基于 API 的采样、人工裁定和回归测试揭示了 Reasoning Gym 和 SynLogic 中生成器、目标和评分器的细微失败。

2 相关工作
可验证环境与 RL。程序化内容生成长期以来一直支持强化学习中的泛化研究（Cobbe 等人，2020；Risi 和 Togelius，2020）。对于语言模型，Reasoning Gym 提供了大量算法评分的环境集合（Stojanovski 等人，2025），而 SynLogic 开发了用于带有可验证奖励的 RL 的可扩展逻辑游戏（Liu 等人，2025）。相关工作在游戏、定理证明、逻辑、数学和代码中构建可验证任务（Paglieri 等人，2025；Lin 等人，2025；Xin 等人，2024；Xu 等人，2025）。我们的研究在补全监督目标下评估广泛的程序化集合，而不是它们原生的 RL 配方，尽管 Reasoning Core 的评分器仍然可以用作结果奖励。

RL 之前的程序化监督。形式语言、生成的符号序列和抽象算法任务长期以来一直被用于研究结构化合成监督如何塑造学习到的表征和后续的语言模型训练（Wu 等人，2022；Hu 等人，2025；Allen-Zhu 和 Li，2023）。Procedural Warmup 将以前提出的任务族（包括 Dyck 任务等形式语言问题）整合为一个用于补全监督训练的广泛公开集合（Jiang 等人，2026）。这种既定方法在更广泛的语言训练之前，对紧凑的、合成的程序化补全进行训练。Reasoning Core 将该设置扩展到更异构的集合，并在匹配的训练干预下评估生成器级设计。

精选指令和推理监督。精选的非程序化数据集仍然是数学、逻辑、对话和逐步推理监督的强大来源。DOLCI 是一个公开的指令微调套件，包含用于逐步推理的人工和模型生成数据（包括源自 GSM8K 和 MATH 的数学监督）、代码、精确指令遵循、工具使用和高质量对话（Olmo 等人，2025）。此类资源组装了广泛的指令微调混合，而不是从显式过程中生成结构化任务分布。

任务效用估计和数据选择。先前的工作估计了单个样本对目标指令微调的影响，包括使用较小的模型为较大的模型选择数据（Xia 等人，2024），或者从小规模的监督微调实验中拟合源级混合权重（Li 等人，2025）。我们在生成器级别采取了刻意更简单的方法：在较小模型上进行简短、孤立的 SFT 干预，然后直接测量更大规模下的任务排名一致性。我们将其用作低成本的开发诊断，而不是一种独立于模型的估值方法或优化训练混合的算法。

3.1 设计程序化训练数据
广泛、结构化的问题分布。由于 SFT 对每个样本使用单次教师强制补全，在固定的计算预算下，它可以比基于展开的 RL 覆盖更多不同的问题。我们寻求广泛的问题分布，改变的是语义结构而不仅仅是表面形式。在适当的情况下，特定任务的递归或基于语法的生成器会改变表达式树、逻辑形式、程序结构和形式语言系统。对于规划和通用游戏，我们同时对问题实例和底层领域进行采样，包括规划的动作模式和转换规则，以及对抗游戏的规则系统和初始状态。因此，生成器不需要重复实例化像 Blocksworld 或井字棋这样的固定环境。

难度控制和强制采样。生成器公开了适合任务的控件，如推导深度、规划长度、变量计数、分支因子或符号结构的大小。全局难度旋钮通过一个可覆盖的函数将标量级别映射到这些参数，而不是一组固定的预设，从而实现外推。高级别可能会变得计算昂贵，但经过校准，按照约定，每个生成器的级别最高到 5 仍然保持实用。

渲染和提示效率。我们将问题元数据与提示渲染分开，使格式化成为一个灵活的选择。此处使用的 Reasoning Core 提示提供了零样本指令，没有少样本演示，从而为独立采样的问题保留了更多的上下文和 token 预算。对于外部集合，我们保留了原始渲染，即使它们的任务可能具有更复杂的答案格式，并且不是为 SFT 设计的。

SFT 感知的答案设计和语义评分。语义有效的答案不一定是有效的监督目标。我们为自回归目标设计答案序列化，在合适的情况下分配确定性的规范补全。这避免了导致不兼容但同样有效的后缀的任意早期选择，特别是在规划、证明构建和程序合成中。例如，字典序可以将作为集合的答案规范化。我们还倾向于紧凑的答案，如数字、标签、集合、表达式、证明行索引、规划或短程序，而不是生成的解释。在固定的 token 预算下，这使模型接触到更多独立采样的问题，并减少了用于偶然排序或格式的监督。

评分仍然比监督参考更广泛：集合是顺序不变的，lambda 项在变量重命名下进行比较，规划被执行，证明候选被编译，生成的程序被测试。因此，训练使用规范目标，而评估接受任何语义有效的答案。

外部工具和可复现性。外部求解器扩大了可检查语义的范围，但引入了超时、版本漂移、格式错误的中间表示、不安全的执行和特定于主机的不兼容性。我们为所需的求解器和运行时提供了一个通用的集成层和 Docker 镜像。我们固定依赖项，隔离可执行任务，缓存接受的实例，并将验证器失败与不正确的模型答案分开。生成器和评分器被独立测试，以便验证器失败不会产生奖励。

3.2 任务覆盖范围和接口
Reasoning Core 包含 50 个生成器，分为九个大组（表 1）。这些组是描述性的，而不是对独立认知技能的声明。每个任务将种子和难度配置映射到提示、结构化参考答案、元数据和语义评分函数。这些评分器支持生成器开发、数据集验证、自由生成评估和在线奖励。该接口还支持 Reasoning Gym 和 SynLogic，从而实现跨集合的匹配训练和评估。大多数生成器可以产生实际上无限的变化；实验清单记录了确切的样本和行为哈希以供复现。

3.3 生成器诊断
仓库测试在已知情况下建立了预期行为，但它们没有表征生成的训练分布。因此，我们使用一组互补的诊断（附录表 4）来区分实现缺陷、不可学习的难度范围、捷径解决方案、格式化成本、混合冗余和特定于模型的效果。这些测量指导生成器的更改和任务分析；它们不定义通用的自动选择规则。

3.4 仓库规模的语义验证
广泛的程序化仓库需要超越普通单元测试的语义审查。在整个 Reasoning Core 开发过程中，使用 GPT-5.5 High 和后来的 GPT-5.6 High 进行的反复模型辅助审查检查了源代码、生成的提示、参考目标和评分器。单独的基于 API 的过程使用 Claude Haiku 4.5 在最低任务难度设置（0 和 1）下在没有推理的情况下采样了渲染样本，这是特意选择的，以使错误易于识别和隔离。获得非 1 奖励的情况被标记以进行裁定，最初使用 Claude Opus 4.6，后来使用 Claude Opus 4.7，随后进行人工审查。确认的失败被手动复现，简化为最小示例，并由回归测试覆盖。模型判断从未被视为基本事实。

对我们任务的初步审查发现了细微的失败，包括传统数学符号与 Python 算术语义之间的差异，或逻辑任务中模糊的边缘情况。我们迭代地纠正任务，直到在最终审查中没有发现进一步的实质性缺陷。为了测试该程序是否能暴露后果严重的语义失败，而不仅仅是确认我们自己的实现，我们对实验中使用的其他外部集合应用了相同的审计。

在保守的标准下，我们确认了 105 个 Reasoning Gym 任务中的 13 个和 9 个原生 SynLogic 生成器存在实质性默认路径缺陷。例子包括 Reasoning Gym 的一个评分器对任何非空答案给予满分，以及 SynLogic 的一个生成器其显示的约束与其存储的解决方案相矛盾。附录 F 和 G 记录了审计范围和确认的案例。

这些发现不是对任何一个库的总体判断。比较必然是不对称的：Reasoning Core 在开发过程中被迭代纠正，而外部审计是回顾性的，既不独立也不盲法。我们使用外部审计来证明验证程序可以暴露的失败类型，而不是建立质量排名。结果挑战了程序化数据在构造上是正确的假设：生成、渲染、目标和评分必须在整个仓库中保持一致。

4 实验设置
4.1 集合和训练协议
在将所有四个集合转换为使用相同补全监督目标训练的提示-答案样本后，我们将 Reasoning Core 与 Procedural Warmup、Reasoning Gym 和 SynLogic 进行了比较。我们重新实现了 Procedural Warmup，排除了元胞自动机任务，这是一个纯粹的延续任务。

我们使用四个预训练基础模型，这些模型具有公开记录的训练语料库：SmolLM2-135M、SmolLM2-360M、OLMo-1B 和 SmolLM3-3B-Base。主数据流将 FineWeb-Edu（Penedo 等人，2024）文本与 DOLCI 指令和对话数据平均混合。DOLCI 包括逐步推理、工具使用和对话监督（Olmo 等人，2025）；仅主数据的条件是一个精选的 SFT 基线，而不是原始文本基线。程序化集合替换了一部分提示加答案 token，而更新总数保持固定。我们将 20% 的提示加答案 token 分配给辅助数据²。我们设置最大序列长度为 1,024，并在每个种子内使用具有共享数据顺序的配对种子。我们评估从 300 到 2,400 次更新的多种时长。所有辅助条件和仅主数据基线共享相同的种子和优化配置。报告的效果是配对差异，因此研究隔离了辅助数据的边际效应。学习率是在初步的 Reasoning Gym 运行中选择的，然后在所有集合中固定；没有针对每个集合进行调优。附录表 9 报告了完整的配置。任务在支持的级别上均匀采样，样本被去重。超长行被丢弃而不是被截断，因为从末尾截断会删除监督答案。

² 我们在 Reasoning Gym 上验证了这个比例，在 2400 步时使用 BBH 验证集 NLL 对 10%、20% 和 40% 进行了扫描。

4.2 留出下游评估
我们的主要衡量标准是添加辅助集合 A 后留出答案负对数似然的相对减少：
Δ_NLL(A; E) ≔ 100 (1 - NLL_E(M_main+A) / NLL_E(M_main))。
正值表示添加 A 降低了匹配的仅主数据延续在评估分布 E 上的留出答案 NLL。

主要行为比较使用两个复合指标。Reasoning 是 DROP、LogiQA、ARC-Challenge 和 BBH-test 的平均值。Retention 是 MMLU-other 和 DOLCI 的平均值，并刻意远离形式领域进行加权：MMLU-other 是在排除了数学、形式逻辑和计算机科学后对 47 个 MMLU 学科的宏观平均，而 DOLCI 测量模型已经在训练的精选指令分布上的 NLL。因此，Retention 询问程序化监督的获得是否以更广泛的能力为代价。图 1 报告了在训练时长内这两个复合指标作为相对答案 NLL 减少的情况。

在大多数报告的设置中，准确率被强烈量化：在较小规模下，精确匹配接近底线，而多选评估接近随机，通常只移动 1-2 个百分点。因此，我们在所有留出分数都记录的地方使用 NLL，并在 3B（表 2）报告准确率和 F1，因为在那里它们变得具有区分度。NLL 是配对的，对小规模的部分概率偏移很敏感。我们还运行了任务原生的自由生成评分和零样本评估。

5 结果
5.1 下游任务的集合比较
在 3B 和 2,400 次更新时，Reasoning Core 改善了所有推理指标，超过了配对的仅主数据延续。在跨模型和时长中，每个程序化集合至少在某些设置中产生了积极的推理迁移，但它们的相对顺序有所不同。图 1 显示了训练时长内的推理和保留轨迹。附录表 5 报告了单独的 NLL 减少。我们还评估了由 BBH 开发 NLL 选择并均匀采样的 50 个任务的 Reasoning Gym 子集。该子集改善了 LogiQA，但相对于完整集合降低了大多数其他指标，这表明 BBH 开发效用并没有均匀地跨评估迁移，并且缩小任务混合可以减少总体迁移。表 2 报告了在单个数据集上的比较，并确认 NLL 的增加转化为准确率的提高。附录表 6 报告了所有四个集合的集合顺序一致性。

5.2.2 可学习性、格式和迁移
我们接下来观察性地分析孤立任务运行，将任务属性与迁移相关联；Reasoning Gym 提供了最大的此类面板，并跨越了非常不同的学习状态。在 300 次更新后，SmolLM2-360M 在 95 个任务中的 6 个上达到至少 .90 的原生奖励，包括 graph_color 和 propositional_logic，而 45 个仍处于或低于 .05；count_primes 保持为零。原生奖励提供信息但不完整。进展甚微的任务通常在 BBH 上表现不佳，而奖励增益比初始奖励提供更多信息。在 Reasoning Gym 内，中等最终奖励显示出最强的留出迁移，而完全饱和的任务并不能更好地迁移。饱和可能反映了对狭窄输出空间的掌握，而不是广泛有用的学习。

网格和棋盘任务形成了一个明显的负面集群。它们通常将长状态描述与短决策或完全序列化的解决方案配对。在 FineWeb 上，它们明显的惩罚主要由提示和答案长度解释。长输入决策仍然可以帮助 BBH，同时损害保留，而全状态重建倾向于损害两者。一些约束网格，包括数独和 futoshiki，在控制长度后在 BBH 上仍然表现不佳，这表明是特定于任务的不匹配，而不是空间推理的一般失败。Token 匹配将这种长度效应与辅助剂量分开。在 18 个配对的 OLMo-1B 任务中，它在每种情况下都改善了 BBH，但使样本长度和 FineWeb 保留之间的关系保持不变。因此，即使在控制辅助 token 预算时，长样本仍然代价高昂。完整的任务级估计和控制单独报告（附录 D.4）。

5.2.3 关于逐步推理目标的负面结果
我们还测试了包括解析和图寻路在内的任务的逐步目标。对于解析，目标重现了 Earley 图表解析器的连续操作。对于图寻路，它们追踪了无权图上的广度优先搜索和加权图上的 Dijkstra 算法，包括边界扩展、距离更新和前驱选择。这些推理在语义上是正确的，但它们在 BBH 开发和 FineWeb NLL 上的表现始终不如紧凑答案监督。在匹配训练预算和没有预算匹配的情况下，相同的排序都成立，并且使追踪更短、更节省 token 并没有逆转它。在这些任务中，更可迁移的技能可能是学习问题的格式塔：看到字符串如何在语法下组合在一起，或者可行的路线如何在图中形成，而不是一次一个操作地重现求解器的记录。结果并不意味着推理监督通常是有害的。然而，它确实表明，正确算法的忠实记录可能比它计算的答案更糟糕的训练目标。

5.3 零样本可解性
训练效用和初始可解性是不同的轴。前沿模型已经解决的任务可能对评估仍然有用，但提供的提升空间很小，而低零样本奖励可能表明有用的教师强制信号、格式错误的数据或过高的难度。因此，我们在多个难度级别运行任务原生的自由生成评估。附录图 3 评估了在 Instant 和 High 推理模式下的约 300B 参数 DeepSeek V4 Flash 以及在 Instant 模式下的约 1.6T 参数 DeepSeek V4 Pro。Flash Instant → High 探测在固定模型下的推理时间推理扩展，而 Flash → Pro 探测参数扩展。这些评估未用于生成器或任务选择。在增加推理努力下的高准确率并不会使任务在补全监督训练中变得多余，因为其样本可能仍然改善直接预测或支持更长推理的表征。Flash High 在 18/50 评估任务上保持低于 0.75 的奖励，在 32/50 上低于 0.90。在 Flash High 达到至少 0.90 的 18 个任务中，Flash Instant 和 Pro Instant 的平均奖励分别为 0.61 和 0.62。因此，无论是 300B Flash 还是 1.6T Pro 配置都无法零样本完全解决该集合。增加的推理时间推理解决了更多任务，而两种 Instant 配置都保留了大量的提升空间。Flash High 接近饱和的几个任务对两种 Instant 配置仍然困难。模型内的 Instant 到 High 的对比比 Instant 模式下模型之间的对比更一致地积极。

5.4 使用 Reasoning Core 的验证器支持 RL
我们在匹配的、单种子的 GRPO 运行中比较了 Reasoning Core 和 Reasoning Gym，在 Qwen2.5-3B-Instruct 上遵循 Stojanovski 等人（2025）。两种条件都使用相同的优化器、采样配置、有效批量大小和 20 万样本预算；只有训练集合和验证器不同。图 2 报告了每 500 步直到第 6,000 步的 BBH-test 和 MMLU 准确率。在最终检查点，Reasoning Core 在 BBH-test 上达到 38.6%，而对比为 23.1%，在 MMLU 上达到 62.5%，而对比为 43.2%。然而，Reasoning Gym 运行使 MMLU 退化到低于基础模型，这表明是运行特定的不稳定性，而不是可靠的集合级差异。因此，我们将差距视为仅作说明。更狭义的结论是 Reasoning Core 可以支持验证器支持的 RL。

6 讨论
程序化集合并不与单一的训练目标绑定。Reasoning Gym 和 SynLogic 主要作为可验证的 RL 环境开发，但在我们的协议下，两者都提供了有用的补全监督训练数据，其中 Reasoning Gym 表现尤为突出。相反，Reasoning Core 是围绕补全监督数据效用设计的，但也支持有效的验证器支持 RL。然而，明确面向补全目标的设计选择会带来更好的整体 SFT 结果。补全监督训练直接消耗生成的问题，而不是为每个提示生成和评分多个在线展开，因此可以在固定的计算预算下使模型接触到更多独立采样的问题。我们的实验分别评估补全监督和 RL；相同的程序化集合是否应该重用于顺序 SFT 和 RL 仍然悬而未决。

任务效用取决于训练上下文。生成器没有单一的独立于模型的值。其测量效果取决于基础模型、目标表示、训练剂量、主分布和相邻任务。因此，孤立任务干预对于在与测量时接近的设置下诊断和修改生成器最有用。集合级比较回答了一个不同的问题：在结合了特定任务的效果和相互作用后，完整的程序化混合是否提供了有用的边际监督。

7 结论
Reasoning Core 在通用接口下为监督训练、评估和 RL 提供了 50 个可验证的生成器。在主要的 3B 比较中，Reasoning Core 改善了所有报告的推理指标，超过了共享的仅主数据延续；在跨模型和时长中，每个程序化集合至少在某些设置中产生了积极的推理迁移，而相对顺序在不同指标、模型家族和训练时长中有所不同。目标设计与任务语义同样重要：紧凑的规范答案优于正确算法的忠实逐步追踪，审计确认仅靠程序化生成并不能保证正确性。我们在宽松许可下发布了大约 100 亿个生成的 token（附录 E.3）；发布的诊断使这些结论在生成器级别可检查，并支持未来的 SFT-RL 比较。

局限性
尽管集合级迁移在所研究的模型大小中似乎没有恶化，但我们的证据止于 3B 参数，因此这些趋势在更大规模下是否持续仍然未知；模型家族覆盖也有限。评估强调形式化和封闭答案推理；它没有确立在开放式、多模态或现实世界代理任务上的改进。尽管共享的 DOLCI 基线已经提供了精选的推理监督，但我们没有与其单独的人工精选组件（如 GSM8K 或 MATH）的匹配混合进行比较，也没有评估超出此处使用的 MMLU 和 BBH 分数的形式逻辑基准。我们将补全监督训练和验证器支持的 RL 评估为单独的干预。我们没有在同一程序化集合上测试顺序 SFT 后接 RL，因此实验没有确定程序化 SFT 如何改变后续 RL，或者在这两个阶段重用同一集合是否有益。匹配的 RL 比较使用单个种子，应被解释为可行性的证明，而不是集合级差距的精确估计。
