## 带实时语音问答的预演多智能体实时产品演示

Rahul Khedar\*, Mayank Malhotra\* Avinash Karn, Mouli V, Prakhar Mehrotra PayPal AI

### 摘要

现场产品演示是软件组织中一项反复出现的高成本活动：人类演示者必须选择功能、在运行的应用程序上执行相应的交互、连贯地进行解说，并实时回答问题。现有的自动化技术仅解决了部分问题——通用浏览器代理以指令条件下的任务完成为目标，而演示视频工具生成固定的 MP4 产物，无法接受提问，且在界面漂移时会静默失效。我们提出了 Rhetor，一个多智能体系统，它以一个运行中的 Web 应用程序及其源代码仓库作为输入，生成带有分段同步解说和实时语音问答的预演现场演示。其架构贡献包括：将 UI 探索与源代码分析融合为带有离散焦点层级标记的特征的跨模态特征表示；一个受限于探索期间观察到的 UI 元素并通过多策略语义定位器分发的基于事实的脚本生成器；一个具有显式收敛和优雅降级为纯解说段的演示前预演循环；以及一个将每个浏览器操作绑定到其解说段音频结束事件的运行时同步不变量。在四个已部署应用程序（包括公共领域的白板应用 Excalidraw）上的六次流水线会话中，预演器的内部定位器触发率 σ̄ 在 147 个脚本操作上跨越 0.31–1.00；在较大工作负载（53 个操作，完整层级分化）上，σ̄ ≈ 0.92；在公共领域参考点上，定位器修复步骤驱动收敛至第 2 次迭代时 σ̄ = 1.00。我们还定义了一个涵盖六个应用类别的十项指标基准协议，以在案例研究之外确立每个设计选择是否做出了积极贡献。

### 1 引言

现场产品演示是软件组织中跨销售工程、开发者关系、客户成功和工程入职培训等领域的反复出现的活动。该活动在结构上受到约束：在有限的时间窗口内，人类演示者从应用程序中选择一部分功能，在运行的产品上执行相应的交互，连贯地解说这些交互，并回答观众的提问，这些问题涵盖面向用户的行为和架构细节。人力成本高昂，该活动在不同观众轮次中无限重复，且产生的产物——接收者内化状态的实例——会被下一次界面变更所失效。

两类自动化技术解决了该问题的子集。通用浏览器代理 [1, 2, 3, 4, 6, 5] 以指令条件下的任务完成为目标：给定一个自然语言目标，代理尝试在真实网站上完成任务，以结果衡量成功。演示问题在两个方面有所不同：系统必须**选择**要演示哪些功能而非被告知，且它必须**口头表达**正在做什么而非仅执行它。第二类工具 [10, 11, 12, 13] 组合视觉 LLM、浏览器自动化库和文本转语音模型，从目标 URL 渲染带解说的 MP4 视频。视频格式产生固定产物：它无法接受运行时提问，无法适应用户节奏，且当底层界面已偏离渲染时状态时会静默失败。Vardanyan [7] 报告了一年的生产浏览器代理运营情况，认为支配实际部署的主导因素是架构性的而非模型能力驱动的；我们采用这一观察作为工作前提。

我们提出 Rhetor，一个用于在实时运行条件下对 Web 应用程序进行预演产品演示的多智能体系统。以运行中的应用程序及其源代码仓库作为输入，Rhetor 执行五阶段流水线——探索、代码阅读、理解、脚本编写、预演——并输出一个预演演示，通过嵌入用户浏览器中的同源反向代理提供给客户端浏览器，音频解说通过逐段握手与浏览器操作同步，用户语音桥接到以生成的知识文档为基础的实时语音到语音端点。

**贡献。** (i) 我们形式化了一种跨模态特征表示，其中 UI 探索和源代码分析被联合融合为带有离散焦点层级 𝒯 = {hero, supp, mention} 和连续演示优先级 ρ ∈ [1, 10] 的特征；焦点层级将下游阶段强制执行的叙事注意力预算操作化。(ii) 我们约束脚本生成器将每个操作基于探索期间观察到的元素；每个操作通过一个有序定位器元组 ℒ = (ℓ₁, …, ℓ₆) 分发，策略包括 role+name、text、label、placeholder、test-id 和 CSS，按固定优先级顺序尝试。(iii) 我们引入了一个具有显式收敛和降级的先预演后演示循环：脚本在真实无头浏览器中执行，LLM 为失败操作提出定位器替代方案，定位器列表通过左前缀追加更新 L_{i+1}(a) ← R_i(a) ⊕ L_i(a)，在 σ_i < τ 时继续迭代直到固定上限 I_max，循环无法验证的任何操作被转换为纯解说段而非删除，保持运行时轨迹的终止性。(iv) 我们指定了一个运行时同步不变量：创作单位是解说段 σ = ⟨text, action?⟩，运行时通过服务器-客户端握手保证 t_action(σ) = t_audio_end(σ)，消除了在可变提供商延迟下 TTS 对齐自动化特有的字偏移漂移。

除四项核心贡献外，本文还指定了一条实时语音问答路径，将浏览器 PCM 桥接到服务器端 VAD 语音到语音端点，并将生成的知识文档作为会话指令注入；同时提出了涵盖六个应用类别的十项指标基准协议。第 11 节报告了在四个已部署应用程序上进行的初步案例研究，涉及多种预演机制。

本文其余部分组织如下。第 2 节回顾先前工作。第 3 节固定符号。第 4 至 8 节描述五个阶段和运行时。第 9 节报告实现细节。第 10 节定义基准协议。第 11 节报告案例研究。第 12 和 13 节讨论局限性和设计启示。

### 2 相关工作

**通用浏览器代理。** WebArena [2] 提供可复现的 Docker 沙箱化 Web 应用程序和基于结果的评估；VisualWebArena [3] 增加了视觉维度。Mind2Web [1] 贡献了跨 137 个网站的 2,350 个任务，具有跨任务、跨网站和跨领域划分。WebVoyager [4] 报告了一个端到端多模态代理和同名基准。最近的工作 [5] 在 Online-Mind2Web 上重新评估了最先进的代理，报告的数字远低于标题分数所暗示的。开放权重的 MolmoWeb [6] 发布了一个视觉 Web 代理，附带完整的训练和评估工具。这些系统追求指令下的任务完成；Rhetor 追求叙事选择和展示。动作选择发生在**创作时**（预演）而非**运行时**，因此实时运行时消费的是经过验证的轨迹而非在不确定性下行动。

**生产浏览器代理报告。** Vardanyan [7] 报告了一年的浏览器代理生产运营，得出结论：混合无障碍树加视觉上下文、专业化优于通用自主性、以及程序化安全边界比 LLM 规模更能决定可靠性。我们采用这一立场，并贡献了**先预演后演示**的额外模式：将代理的失败面重新定位到具有定义降级规则的受控离线阶段。

**自动化演示视频。** 最近一类工具 [10, 11, 12, 13] 通过以下模式将 URL 或 YAML 规范映射为带解说的 MP4：捕获页面 → 视觉 LLM 分析 → 脚本 → 录制浏览器 → TTS → ffmpeg 合并。Rhetor 在三个方面不同：输出是通过同源反向代理提供的在目标应用程序中的实时交互式演示，而非预渲染视频；规划同时消费 UI 和源代码信号，因此架构内容（集成、可扩展性、数据模型）成为可寻址的演示材料；演示前预演阶段在部署到实际环境之前将尽力而为的脚本转换为经过验证的脚本。

**语音到语音运行时。** 实时音频 API [9] 通过 WebSocket 暴露服务器端语音活动检测和直接语音到语音生成，消除了转录-思考-合成的往返。我们使用这样的端点作为实时语音问答的载体，将生成的知识文档作为会话指令注入，以将响应基于所演示的应用程序。

**基于状态的多智能体生成。** Khedar 等人 [8] 在合成数据生成场景中引入了一个权威状态对象，约束多角色生成循环中的 LLM 输出。我们在不同场景中采用相同原则：一个非 LLM 数据结构——合并的 SiteMap 和 CodeAnalysis——约束流水线各阶段的 LLM 输出。

### 3 预备知识和符号

我们固定全文使用的符号。

**应用界面。** 设 G = (V, E) 表示目标应用程序的导航图，其中 V 是探索发现的页面集合，E ⊆ V × V 是页面间链接集合。每个页面 v ∈ V 携带元组 ⟨path, title, type, summary, ℰ_v, ℱ_v, ℳ_v⟩，其中 ℰ_v 是观察到的交互元素集合，ℱ_v 是表单集合，ℳ_v 是模态框集合。元素 e ∈ ℰ_v 具有结构化签名 ⟨role, text, aria, label, placeholder, testid, bbox⟩。

**代码界面。** 设 ℛ 表示从仓库提取的路由集合，𝒟 表示数据模型集合，ℱ_rw 表示推断的 Web 框架。CodeAnalysis 对象为 𝒞 = ⟨ℛ, 𝒟, ℱ_rw, α⟩，其中 α 是自由文本架构摘要。

**特征和层级。** 特征 f ∈ ℱ 是元组 ⟨name, P_f, K_f, τ_f, ρ_f, θ_f⟩，其中 P_f ⊆ V 是 f 跨越的页面，K_f ⊆ ⋃_{v∈P_f} ℰ_v 是关键元素集合，τ_f ∈ 𝒯 = {hero, supp, mention} 是焦点层级，ρ_f ∈ [1, 10] 是演示优先级，θ_f 是可选的架构级注释。

**定位器。** 定位器策略是函数 ℓ: (page, element) ↦ {handle, ∅}，返回 Playwright 元素句柄或失败。我们固定一个优先级排序的策略元组 ℒ = (ℓ₁, …, ℓ₆)，总结在表 1 中。对于操作目标 t，获胜定位器为

ℓ\*(t) = ℓ_{i\*}(t), i\* = min{i : ℓ_i(t) ≠ ∅}, (1)

如果没有策略匹配则为未定义。

| i | 策略 ℓ_i | 选择器模式 | |---|---------|-----------| | 1 | role+name | getByRole(role,{name}) | | 2 | text | 可见文本内容 | | 3 | label | 关联的 `<label>` | | 4 | placeholder | 输入 placeholder 属性 | | 5 | test-id | [data-testid="..."] | | 6 | CSS | 原始 CSS 选择器（回退） |

**表 1：** 定位器策略元组 ℒ。策略按优先级顺序尝试；第一个匹配成为 ℓ⋆(t)。排序偏好语义角色和基于文本的策略，它们对偶然的 DOM 变更具有鲁棒性，而非 CSS，后者耦合到内部结构。

**脚本。** 演示脚本 S 是场景序列 S = (s₁, …, s_n)。每个场景 s 包含一个动作 act(s) ∈ {hook, journey, hood, close}、一个入口路径和一个解说段序列 Σ(s) = (σ₁^s, …, σ_{m_s}^s)。每个段是对 σ = ⟨text, action?⟩，其中操作是可选的（允许纯解说）。

**已验证操作。** 预演后，每个操作 a 被标注状态 ϕ(a) ∈ {verified, failed, narration_only}、获胜定位器 ℓ\*(a) 和持续时间。场景成功率为

σ(s) = |{a ∈ 𝒜(s) : ϕ(a) = verified}| / |𝒜(s)|, (2)

其中 𝒜(s) = {a : ∃σ ∈ Σ(s), action(σ) = a}。脚本的整体成功率是大小加权均值 σ̄ = ∑_s |𝒜(s)| σ(s) / ∑_s |𝒜(s)|。

**目标。** 系统输入是应用程序 URL 和仓库 URL 的对 (U_app, U_repo)。系统输出是元组 ⟨S\*, Φ\*, K\*, U_app⟩，其中 S\* 是预演脚本，Φ\* 是已验证操作标注，K\* 是 Markdown 知识文档，U_app 是同一应用程序 URL，以实时方式提供给客户端浏览器，文本和语音问答均基于 K\*。

### 4 阶段 1：探索和代码阅读

阶段 1a 和 1b 并发运行。阶段 1a 通过对运行中的应用程序进行有界广度优先爬取构建 G；阶段 1b 从源代码仓库构建 𝒞。两个阶段不共享状态，其挂钟时间成本在量级上不同，因此端到端阶段 1 延迟为

T₁ = max(T_{1a}, T_{1b}) ≤ T_{1a} + T_{1b}. (3)

#### 4.1 UI 探索

爬取受 |V| ≤ κ_p 和 depth(v) ≤ κ_d 约束，默认 κ_p = 30 和 κ_d = 4。页面感知是混合的：在页面上下文中执行的确定性 JavaScript 通过选择器联合（a, button, [role], [data-testid]、标题、表单控件、标记输入）提取 ℰ_v，限制在可见视口内；然后多模态 LLM 调用从其 1280×720 PNG 截图总结页面，产生结构化三元组 ⟨type, summary, name⟩。页面就绪结合 Playwright 的 network-idle 信号和以 250 ms 间隔轮询的 JavaScript 加载指示器检测器。

三种行为扩展了基本爬取。

**模态探测** 在全新上下文中每页点击最多五个候选触发器，以发现静态爬取中缺失的对话框。

**视觉辅助登录** 在没有配置凭据的情况下解决认证墙，通过发出视觉 LLM 调用来识别公共区域点击目标，之后 JavaScript 树遍历器执行点击；同一组件识别 SSO 入口点（OAuth、SAML、Auth0、Okta）和企业 SaaS 部署特有的角色卡片登录流程，这些不被通用密码字段启发式处理。

**应用类型分类** 通过 URL 模式启发式将应用程序标记为 SPA、MPA 或混合型；运行时反向代理使用此标签。

#### 4.2 代码阅读

当配置了 GitHub 访问令牌时，系统通过 REST API 获取仓库：单个递归树请求列出所有 blob，按扩展名和目录拒绝列表过滤文件，由大小为 10 的工作线程池并行获取内容。不执行克隆，不将源代码写入磁盘。没有令牌时，使用浅克隆（--depth 50）作为回退。

获取的文件由具有字节预算 B ≈ 60 KB 的路径感知批处理器按目录分批。每批由 LLM 在结构化输出提示下分析，每批结果通过以 method:path 为键的路由去重合并。两次额外的一次性调用分别从目录树产生框架标签 ℱ_rw 和架构摘要 α。

### 5 阶段 2：跨模态理解

合并 Ψ: (G, 𝒞) ↦ (ℱ, K) 是在结构化输出提示下的单次 LLM 调用；提示接收导航图的序列化形式（带摘要和关键元素的页面）和代码分析（路由、模型、框架）。其输出是特征集 ℱ（为每个 f 填充 τ_f, ρ_f, K_f, P_f, θ_f）和产生 Markdown 知识文档 K 的第二次调用的提示，K 具有规定章节：Product Overview、Features、Architecture、Common Q&A、Talking Points。Common Q&A 章节是预期性生成的：模型被提示枚举十到十五个合理的观众问题，并在生成时（而非运行时）产生基于 ℱ 和 𝒞 的参考答案。问题集的预计算是相对于人类演示者的结构性优势，后者通常是被动地准备答案。

**焦点层级作为注意力预算。** 设 w(σ) ∈ ℕ 表示段 σ 的字数。系统在解说时强制执行层级条件边界：

w(σ) ∈ { [100, 140] 如果 τ_{f(σ)} = hero; [80, 110] 如果 τ_{f(σ)} = supp; [40, 65] 如果 τ_{f(σ)} = mention } (4)

其中 f(σ) 是通过其场景与 σ 关联的特征。层级是一个粗粒度的、提示可强制的信号，防止 LLM 脚本生成器产生平坦的、等权重的 walkthrough。

**知识索引。** K 按二级标题拆分为章节 {c₁, …, c_N}。每个章节通过 OpenAI 兼容的嵌入端点嵌入一次。查询时检索使用余弦相似度

s(q, c) = e_q · e_c / (‖e_q‖₂ ‖e_c‖₂), (5)

在嵌入端点不可用时使用关键词重叠回退。查询 q 的检索上下文为

ℛ(q) = arg max_{C ⊆ Top_k(q), ‖C‖ ≤ B_q} ∑_{c ∈ C} s(q, c), (6)

其中 B_q 是字符预算（默认 4000），‖C‖ 是所选章节的总字符长度。

### 7 阶段 4：带 LLM 定位器修复的预演

**迭代。** 在第 i 次迭代中，S 中的每个操作 a 在真实的无头 Chromium 浏览器中分发；执行器按优先级顺序尝试 ℒ 中的策略并返回 ℓ\*(a) 或 ∅。每个 a 被标注 ϕ_i(a) ∈ {verified, failed}、获胜定位器、操作后边界框、持续时间以及错误消息（如有）。设 σ_i = σ̄ 为第 i 次迭代后的整体成功率。

**修复。** 对于每个 ϕ_i(a) = failed 的 a，在结构化输出提示下的 LLM 调用提出新的定位器策略 R_i(a)。操作的定位器列表通过左前缀追加更新

L_{i+1}(a) ← R_i(a) ⊕ L_i(a), (9)

ϕ(a) := narration_only 对于所有 ϕ_{i\*}(a) = failed 的 a (11)

### 8 阶段 5：现场演示运行时

运行时将预演演示作为交互体验提供。服务器端状态由每个会话的 DemoSession 持有，包含 ⟨S\*, Φ\*, K\*, U_app⟩ 和 DemoDriver 状态机；反向代理在同源路径下提供原始目标应用程序，使其可以嵌入 iframe 并从浏览器 DOM 使用预演器验证的相同定位器策略进行分发。

#### 8.1 同步不变量

对于每个段 σ = ⟨text, a⟩（a ≠ ∅），设 t_audio_end(σ) 表示段解说音频完成的挂钟时间，t_action(σ) 表示操作在 iframe 中分发的挂钟时间。运行时保持：

**不变量 1（段同步）。** 对于每个具有非空操作的段 σ，t_action(σ) = t_audio_end(σ)。

该不变量通过段完成握手（图 3）维护。服务器发出解说事件并清除内部 narration_event。客户端开始 TTS 播放，同时服务器阻塞在 narration_event.wait(Δ_max)。客户端音频 onended 触发 narration_done 消息释放等待，服务器随后发出操作事件。只要 Δ_max 超过最大允许音频长度，该不变量在可变 TTS 延迟、网络抖动和韵律引起的长度变化下成立，在任意段数上产生零字偏移漂移。

**图 3：** 段完成握手。服务器发出解说事件，阻塞直到客户端播放 TTS 音频完成并回传信号，然后才发出操作事件。该协议编码了不变量 1：操作分发锚定到音频结束信号而非预测时间戳。

#### 8.2 三级 TTS 回退

解说音频路径使用三级回退链，在提供商可变性下保持不变量 1。设 𝒮₁ 表示通过 OpenAI 兼容 /audio/speech 端点的流式 TTS，𝒮₂ 表示通过同一端点的非流式 TTS，𝒮₃ 表示浏览器原生 speechSynthesis。运行时选择发出 onended 事件的最低索引源；握手协议在三者中完全相同。这将同步论证与任何特定 TTS 提供商解耦。

#### 8.3 实时语音问答

用户语音通过 WebSocket 中继从浏览器麦克风桥接到服务器端 VAD 语音到语音端点。客户端打开到服务器的控制通道；服务器检索有界长度的知识切片 K_q\* ⊆ K\* 并建立到语音到语音端点的第二个 WebSocket，会话配置为 PCM16 输入和输出、文本和音频模态、具有固定阈值和静默持续时间参数的服务器端语音活动检测、输入转录模型、配置的语音以及指令字符串 I = I₀ ∥ K_q\*，其中 I₀ 是通用角色前导。浏览器捕获的音频帧作为追加缓冲区事件转发；流式音频响应被中继回浏览器播放。

**轮次延迟。** 每个观众轮次，

T_turn = T_up + T_vad + T_stream + T_down, (13)

其中 T_up 是语音结束到服务器 VAD 接受，T_vad 是配置的静默填充，T_stream 是 LLM 到首音频延迟，T_down 是音频流播放开始。与转录-思考-合成 REST 管道相比，此路径消除了两次完整网络往返和一次音频重新编码。

**基于事实。** 因为 K\* 由 G 和 𝒞 共同构建，关于面向用户行为和架构细节的观众问题从同一检索基底回答。设 Q 表示演示会话期间发出的问题集合。我们将 Q 划分为基于 UI 的子集 Q_u（可从 G 回答的问题）和基于代码的子集 Q_c（只能从 𝒞 回答的问题）；严格子集 Q_{u∩c} 需要两者。跨模态合并是 Q_c 和 Q_{u∩c} 上任何基于事实答案的前提条件。

**多语言交互。** Realtime 端点通过配置的输入转录模型接受任意输入语言并以同一语言产生输出；解说生成在 LLM 接口处是语言无关的。因此运行时在系统层面是多语言的；本地化到特定语言需要每语言语音和提示选择但不需要架构变更。

#### 8.4 iframe 和反向代理

运行时通过 HTTP 反向代理将 U_app 挂载在与演示客户端相同的源下，该代理从代理响应中剥离 X-Frame-Options 和 CSP 头，并将 Location 重定向重写为同主机路径。同源嵌入允许使用预演期间验证的定位器策略直接向 iframe 分发 DOM。

#### 8.5 录制演示包

实现支持用于异步查看的离线包格式：通过相同 TTS 链渲染的每场景 MP3 音频、预演的截图帧，以及将帧与解说段对齐的 JSON 元数据。录制路径在结构上不同于实时运行时；它保留叙事内容但丢失对话，这是区分现场演示和视频的属性。

### 9 实现

系统以约 6,000 行 Python 实现，具有 Flask Web 层和用于浏览器控制的 Playwright，以及一个轻量级的浏览器端客户端。代理层在通用契约下结构化：每个代理扩展基类返回 AgentResult，包含成功、类型化载荷、错误、经过的毫秒数和元数据字典；每阶段挂钟延迟由计时包装器捕获，令牌使用字段保留用于 LLM 客户端边界处的成本核算。

**提供商无关的 LLM 客户端。** LLM 客户端是 OpenAI 兼容 HTTP 接口（/chat/completions、/audio/speech、/audio/transcriptions、/embeddings）加 Realtime WebSocket 之上的轻量适配器。端点基础 URL 和承载密钥由环境驱动；客户端支持标准聊天参数和推理模型参数，通过模型名称自动切换；可配置的 TLS 验证标志适应内部网关。部署可以将每个 LLM 调用路由到其首选提供商（直接 OpenAI、自托管推理或路由到 Claude、Gemini 或开放权重模型的多提供商网关），而无需修改任何代理。

**应用程序 D**（Excalidraw）是公共领域参考点，也是预演修复循环被观察到贡献于收敛的唯一会话。该会话在画布渲染的单页界面上产生了 7 场景脚本（1 hook + 4 journey + 1 hood + 1 close），填充了所有三个层级（3 hero + 3 supp + 1 mention）和 14 个脚本操作。第 1 次迭代未在 τ 处收敛；定位器修复步骤提出替代方案，第 2 次迭代达到 σ̄ = 1.00，所有 14 个操作已验证。在画布密集 SPA 上的连贯演示结构、尽管单 URL 爬取的完整层级分化，以及修复循环驱动收敛的直接证据，使这成为最强的单次会话。

**应用程序 C** 是最强的大工作负载会话：在内部 AI 平台治理工具上的单次运行产生了 11 场景脚本，具有 53 个脚本操作和适当的四幕分布（2 hook + 7 journey + 1 hood + 1 close）以及适当的层级分化（6 hero + 2 supp + 3 mention）。在 53 个操作中，49 个已验证，4 个根据第 7 节的规则降级，产生内部定位器触发率 σ̄ ≈ 0.92 和就绪标志 0.92。该会话是案例研究中最重大的工作负载，在非平凡操作数上接近收敛阈值 τ = 0.95。

**应用程序 A** 包括在内部 HR/人才管理工具上当前实现的三次会话，以不同爬取参数运行。在这些会话中，流水线分别达到 1、4 和 29 个页面，产生 7、9 和 11 个场景，分别有 16、22 和 20 个操作，记录的 σ̄ 值为 0.31、0.41 和 0.55。所有三次会话在 I_max 处退出，未在 τ 处收敛，进入第 7 节的降级路径。1 页会话反映了单页应用爬取到达一个 URL，其元素驱动了脚本；我们注意到这一点，因为当应用程序是 SPA 时，页面数本身不是探索失败。4 页会话产生了 125 个章节的知识文档，每爬取页面约 31 个章节的比例表明 K\* 超出了探索直接基于事实的内容；这是一个开放的经验问题，定义 10 会回答，也是协议旨在揭示的行为类型。

**应用程序 B** 包括在合成数据生成研究仪表板上当前实现的一次会话。爬取到达公共界面的 2 个页面；脚本包含 8 个场景（1 hook + 5 journey + 1 hood + 1 close），在小界面下缺乏特征分化时全部标记为 hero；所有 22 个脚本操作在第 1 次迭代已验证（σ̄ = 1.00），因此修复循环和降级规则在此次运行中未被行使。该会话被解释为小公共界面简单案例，而非可靠收敛的证据。

#### 11.2 操作延迟

在 6 次会话和 147 个脚本操作中，经验操作持续时间分布是双峰的：短操作（wait、scroll、DOM 内 click）在毫秒内完成，而慢页面上的 navigate 和 fill 操作占据延伸到执行超时的长尾。每会话预演挂钟时间：应用程序 A 为 10–41 秒，应用程序 B 约 24 秒，应用程序 D 两次迭代约 36 秒，主要由浏览器操作延迟而非 LLM 修复调用主导。

#### 11.3 已验证部署

除上述报告的运行外，同一架构的早期集成作为应用程序 B 的 Web 层的树内组件运行。该集成提供与独立系统相同的运行时界面——脚本检索、解说、文本和语音问答、文本转语音和转录——连同实时语音到语音路径，可通过顶级导航链接从应用程序主页访问。该部署服务于一个 1,440 行、分为 19 个章节的已创作知识文档，并在应用程序 B 上的重复演示会话中得到了行使，其中语音查询通过第 8.1 节的段完成同步协议和第 8.3 节的语音到语音路径处理。本文描述的独立系统是该集成的应用程序无关泛化，共享相同的数据结构、相同的定位器优先级 ℒ 和相同的同步不变量。

#### 11.4 此案例研究确立了什么

案例研究支持四个狭窄的主张。第一，流水线在四个在框架、交互界面和认证机制上不同的已部署应用程序上端到端执行，无需操作员干预，包括公共领域画布渲染参考点（应用程序 D，Excalidraw）。第二，在重大工作负载上（应用程序 C，53 个操作，完整层级分化），达到内部定位器触发率 σ̄ ≈ 0.92，残余由降级规则处理。第三，定位器修复步骤在至少一次观察到的运行中经验性地驱动收敛：应用程序 D 在第 1 次迭代未收敛，修复步骤提出替代方案，第 2 次迭代达到 σ̄ = 1.00。第四，预演的挂钟成本主要由浏览器操作延迟而非 LLM 成本主导：操作持续时间是双峰的，每会话总计应用程序 A 为 10–41 秒，应用程序 B 约 24 秒，应用程序 D 两次迭代约 36 秒。

#### 11.5 此案例研究未确立什么

案例研究未验证个别设计贡献；我们对每个差距都是明确的，因为每个映射到第 10 节协议中的特定项目。

**修复循环贡献部分测量。** 应用程序 D 确立了一个观察到的修复步骤驱动收敛的实例（第 1 次迭代低于 τ，第 2 次迭代 σ̄ = 1.00）。然而，案例研究会话未保留每迭代 Succ_i 轨迹，因此每迭代修复回报 RoI(i → i+1)（定义 5）未在此报告，也未报告预演开 vs 关比较（消融 A1）。应用程序 A 的三次会话在 I_max 处终止未收敛，确立修复未在这些工作负载上达到 τ，但未区分"每迭代无改进"和"迭代不足"。应用程序 B 在第 1 次迭代收敛（未行使修复），应用程序 C 在 I_max 处终止，σ̄ ≈ 0.92。量化修复贡献的大小及其对应用程序复杂度的依赖性需要第 10.5 节中指定的运行。

**跨模态贡献未测量。** 消融 A2（完整流水线 vs 移除阶段 1b）是将源代码分析对特征提取和基于代码问答准确率贡献隔离的实验。我们尚未运行它。因此案例研究未证明跨模态合并优于仅 UI 基线。

**输出质量未测量。** σ̄ 测量预演器的定位器是否触发；它不测量脚本是否以正确的顺序和适当的解说展示正确的特征。特征提取精确率和召回率（定义 3）需要人工参考 ℱ\*，我们尚未标注。演示连贯性和覆盖率未测量。在良好覆盖爬取上低 σ̄ 的会话和单页爬取上高 σ̄ 的会话原则上可能被此处报告的指标和下游质量度量以相反方向排名；案例研究无法区分这些。

**问答基于事实准确率未测量。** 语音和文本问答路径从生成的知识文档 K\* 检索，但案例研究未测量检索到的答案是否在 ℱ 和 𝒞 中有事实依据。定义 10 指定了协议；我们尚未策划问题集 Q 或评分答案。运行 A.3 的高章节数（4 个爬取页面产生 125 个章节）是此未来工作的标志：它表明 K\* 可能超出探索直接基于事实的内容，这正是定义 10 会捕获的。

**收敛机制行为仅在两次会话中观察到。** 应用程序 B 在小公共界面上达到 σ̄ = 1.00，应用程序 C 在重大界面上达到 σ̄ ≈ 0.92。这些是令人鼓舞的单次会话观察，而非跨应用程序收敛可靠的证据；需要第 10 节的协议来表征语料上的收敛率及其对应用程序复杂度的依赖。

**总结。** 案例研究证明流水线运行并产生第 3、4、5、6 和 7 节中描述的产物。产生的产物是否是好的演示、每个设计选择是否做出积极贡献、以及报告的 σ̄ 是否预测下游质量仍然是开放的，需要第 10 节的协议。我们承诺在后续修订中运行并报告该协议。

### 12 局限性

**爬取预算。** 默认 κ_p = 30、κ_d = 4 针对代表性 Web 应用程序界面校准。具有许多门控工作流的深度企业应用程序在没有每应用程序调优的情况下被系统性欠探索。

**认证。** 视觉辅助登录解决未认证的公共区域探索。认证演示需要注入会话 cookie、脚本化凭据或承载令牌；每个都需要操作员设置。

**画布渲染界面。** 主要交互界面是 HTML5 画布（图表编辑器、设计工具）的应用程序是困难的：DOM 不暴露交互元素，ℒ 中的定位器优先级顺序无信息。仅视觉定位器是一个单独的研究方向。

**部分可观测性下的修复。** 当前定位器修复 LLM 调用传递目标元数据和错误消息，但不传递失败后的 DOM。以结构化 DOM 提取为条件修复提示是一个低成本扩展，预计会实质性地改善修复 RoI。

**单次理解。** 阶段 2 是单次非迭代 LLM 调用，没有模式验证重提示。格式错误或规格不足的输出优雅地降级为缺失演示内容，而非作为显式错误呈现。

**多语言界面面积。** 语音问答路径端到端是多语言的，解说生成在模型接口处是语言无关的。剩余的英语特定界面——REST 转录路径的默认语言和默认解说提示——可按请求重新配置，但完全本地化的演示界面（每语言语音预设、区域特定叙事模式）是部署任务。

**泛化。** 流水线假设可通过 URL 访问的服务器渲染或 SPA Web 应用程序，具有并行的公共源代码仓库。移动、原生桌面和闭源 SaaS 目标不在范围内；每个都是同一多阶段模式的单独适配。

**安全、隐私和同意。** 爬取目标应用程序并阅读其源代码的演示代理引起类似于 [7] 中讨论的同意和数据外泄担忧。该系统旨在用于操作员自己产品的第一方使用；托管的多租户部署需要额外的信任层，我们不涉及。

### 13 讨论

**先预演后演示作为设计模式。** 阶段 4 的架构贡献是将代理的失败面从运行时重新定位到受控的离线阶段。运行时消费经过验证的轨迹，辅以预演循环无法验证的任何操作的显式降级回退。该模式超越演示泛化到运行时失败边际成本超过离线重试边际成本的任何浏览器代理设置：计划的客户 walkthrough、培训环境脚本课程和面向审查者的高管演示是直接示例。该模式不需要新的学习算法；实现成本简化为预飞行执行阶段和类型化降级规则。

**段作为同步单位。** 字偏移同步在可变 TTS 延迟和韵律驱动的偏离底层文本下失败。第 8.1 节的段完成不变量用离散服务器-客户端握手替换了连续时间戳估计问题，其正确性源自创作单位而非实时信号估计。该不变量独立于特定 TTS 提供商（第 8.2 节），适用于口语解说与可控界面上离散操作配对的任何系统。

**用于叙事规划的跨模态基于事实。** 先前将代码分析与 UI 信号结合的工作是在任务时间执行时进行的。Rhetor 在上游、在规划时使用相同的组合，以确定演示哪些特征、第三幕中突出哪些架构内容，以及从合并的知识文档中可回答 Q_c ∪ Q_{u∩c} 中的哪些观众问题。贡献是将合并放置在规划阶段而非执行阶段。

**知识文档作为共享检索基底。** 解说生成（第 6 节）和运行时问答（第 8.3 至 8 节）都从同一 Markdown 文档 K\* 检索。这种共享是运行时口语响应与脚本一致的结构性原因：代理从其展示的同一表示中回答。语音路径通过将用户侧交互模型从被动播放转换为基于事实的中断，使运行时区别于视频播放器。

### 14 结论

Rhetor 是一个用于 Web 应用程序预演现场演示的端到端系统。流水线并行执行 UI 探索和源代码分析，将两种信号融合为带有离散焦点层级标记的特征，生成其操作引用观察到的 UI 元素的四幕叙事，并在部署前在真实无头浏览器中验证每个操作。在运行时，预演脚本通过嵌入用户浏览器的同源反向代理提供；解说音频通过逐段握手与浏览器操作同步；用户语音被路由到以生成的知识文档为基础的服务器端 VAD 语音到语音端点。本文形式化了四个设计选择——跨模态特征表示、带语义定位器的基于事实脚本编写、具有显式收敛和降级的先预演后演示，以及段完成同步不变量——并提出了涵盖六个应用类别的十项指标基准协议。跨越四个已部署应用程序的六次会话案例研究涉及多种预演机制，支持了该设计在收敛阈值上保持运行时完整性的主张。
