摘要

智能体应用日益普及，但针对智能体的特定攻击对其构成了现实威胁。发生安全事件后，组织会进行回溯以识别入侵入口点（CEP），修复损害并防止其再次发生。可用于回溯的主要制品是记录智能体功能的轨迹日志和源代码；应用特定的函数调用日志通常相当有限。然而，轨迹日志位于智能体功能抽象层，而 CEP 候选是应用代码执行层的函数调用。由于这种语义鸿沟，分析人员需要手动检查每个 CEP 候选的相关代码，以推断其对应的智能体功能。在本工作中，我们提出了 Origin，这是一种回溯工具，允许分析人员提交少量查询来识别现有工具无法提供的 CEP。我们的方法面临两个挑战：（1）定义捕获两个语义层之间映射关系的中间抽象；（2）确定区域到变量的映射，以构建中间抽象中定义的跨层图。每个区域是一组特定的智能体功能。Origin 通过以下方式应对这些挑战：（1）跨层依赖图（CLDG），它将语义层的区域推断函数连接到低层污点传播子图中的变量，以及相关的查询语言；（2）区域推断算法。对五个流行智能体应用和八个攻击事件的案例研究表明，使用 Origin 的分析人员正确识别了所有 CEP。

关键词： 回溯、智能体应用、中间抽象、间接提示注入、记忆投毒

1. 引言

由大语言模型（LLM）驱动的智能体应用已被广泛部署。例如，开源智能体应用 GPT-Researcher 发布后已积累了超过 24,000 个 GitHub 星标（GPT, 2025）。此外，根据 Gartner 最近的预测，企业智能体应用可能从 2025 年的不到 5% 增长到 2026 年底的约 40%（Gartner, 2025）。与此同时，此类智能体应用正面临新兴的智能体特定攻击的威胁，其中间接提示注入（IPI）（Greshake et al., 2023; Zhan et al., 2024; Debenedetti et al., 2024; Liu et al., 2024b）和记忆与上下文投毒（MC-Poison）（Chen et al., 2024; Wang et al., 2024; Zou et al., 2025）是 OWASP 智能体应用十大威胁中最普遍的两种（OWASP GenAI Security Project, 2025）。例如，多个商业智能体应用中已报告了多个 IPI CVE（Cur, 2025; 5ir, 2025; Neu, 2025; Rehberger, wunderwuzzi）和基于 MC-Poison 的红队测试（Rehberger, wunderwuzzi; Lyons, 2025; Goodin, 2025）。

当已部署的智能体应用中发生安全事件时，组织会回溯该事件，以识别入侵入口点（CEP）、修复损害并防止其再次发生。可用于回溯的主要制品有：（1）轨迹日志，记录映射到智能体功能的智能体观察和动作序列（Zhu et al., 2025），例如规划、通过调用工具执行行动以及从记忆中回忆信息（Liu et al., 2025）；（2）被入侵应用的源代码。值得注意的是，应用特定的函数调用日志通常相当有限：开发人员可能无法预见哪些调用与新兴的智能体特定攻击具有诊断相关性，因此省略了相应的日志打印语句（Yuan et al., 2012a），或者由于开销阈值和隐私考虑，完整日志记录被禁用（Zhao et al., 2017; Yuan et al., 2012b）。

激励性示例。 考虑 GPT-Researcher 上的一起 MC-Poison 安全事件，分析人员收到了应用用户/受害者的事件报告（第 3.1 节）。涉及三方利益相关者：分析人员、补救管理员（通常是用户）和开发人员。分析人员的目标是回溯事件以识别 CEP，即首次将恶意内容引入应用的函数调用（第 4.3 节）。当 CEP 函数调用的相应输入参数已被记录时，分析人员可以（1）为补救管理员提供具体、可操作的补救措施，例如从可能包含数百个各种格式文档的知识库中删除确切的中毒文件；当相应的函数调用日志条目缺失时，分析人员可以（2）向开发人员提供 CEP 函数调用周围的日志打印语句放置建议，实现更高效的日志记录，使应用在未来的事件中可诊断。

识别 CEP 需要分析人员付出大量手动工作。分析人员首先对轨迹日志进行分类和检查，将可疑原因缩小到特定的智能体功能（即知识库检索）。然而，仅基于智能体功能识别 CEP 仍然困难，因为一个智能体功能通常对应许多函数调用，且没有轨迹日志记录具体的函数调用（清单 1）。从根本上说，轨迹日志位于智能体功能抽象层，而函数调用位于较低层（即应用代码执行层）。对应用源代码的静态分析可以通过变量级污点分析精确定位 CEP，从而补充基于轨迹日志的智能体功能级诊断。然而，分析受到大量 CEP 候选的阻碍：只有一小部分与可疑的初始入侵相关。经过基于日志的剪枝后，GPT-Researcher 源代码中仍有 1,518 个候选；为了推断候选是否属于可疑的初始入侵，分析人员花费数小时进行手动代码检查，详见第 3.1 节。主要原因是候选周围的代码几乎没有智能体功能语义，分析人员需要在做出推断之前沿相应的代码路径收集足够的证据。

现有方法均无法为利益相关者提供激励性示例中提到的两个"可提供"益处，因为基于轨迹日志的故障诊断（Zhu et al., 2025; Ma et al., 2025; Zhang et al., 2025b）、基于检测的故障归因（Kim et al., 2025; Zhang et al., 2026; Chocron et al., 2026）和预防性信息流控制（Debenedetti et al., 2025）不会为分析人员提供 CEP，而是提供错误的智能体执行状态（Zhu et al., 2025; Ma et al., 2025; Zhang et al., 2026）、错误的智能体（Zhang et al., 2025b）或智能体所有者（Chocron et al., 2026），以及 LLM 工具调用（而非源代码级别的函数调用）（Kim et al., 2025; Debenedetti et al., 2025）。

我们的方法可以为利益相关者提供这两个益处，因为它回溯了安全事件。如激励性示例所述，在回溯过程中缩小 CEP 范围需要大量手动工作，因为分析人员需要进行代码检查以从程序源代码中恢复智能体功能语义。我们的洞察是引入一种新的中间抽象（第 4.4 节），使分析人员能够在智能体功能级别编写少量查询，并且查询处理输出可以直接排除不相关的 CEP 候选。然而，识别哪些 CEP 候选在语义上对应特定的智能体功能是困难的，因为程序结构和实现各不相同，难以泛化如何识别映射关系。幸运的是，我们观察到智能体功能可以根据它们与之交互的信息源类型（第 2 节）分组为少量区域。每个区域是一组实现同一组智能体功能的程序变量。接收 CEP 候选返回值的变量也包括在内。基于这一洞察，我们构建了一个名为 Origin 的工具，将这种抽象实现为跨两层的图。Origin 以智能体应用的源代码和一小组开发人员提供的标签作为输入，生成跨层图，分析人员可以在安全事件调查期间使用查询语言对其进行查询： 在区域级别/层缩小候选范围； 在变量级别识别 CEP。

挑战。 我们的方法面临两个挑战。首先，定义捕获两个语义层之间映射关系的中间抽象：智能体功能层与应用代码执行层。由于不同智能体应用对同一智能体功能的实现各不相同（例如函数/变量命名、使用的智能体框架），我们认为这样的中间抽象可以为分析人员在回溯不同应用的安全事件时提供相同的接口。其次，构建跨层图（在中间抽象中定义）需要确定每个变量属于哪个区域。这是因为变量的区域由其数据来自或流入哪个信息源决定，但变量的名称、类型或所在函数不携带这些语义。

解决方案。 对于第一个挑战，我们设计了跨层依赖图（CLDG）（第 5 节），通过跨平面边将区域推断函数连接到污点图中的底层变量。我们还设计了相关的查询语言。与 BackTracker（King and Chen, 2003）一样，回溯的本质是依赖分析。由于智能体应用 CEP 是特定的函数调用，静态污点分析适用于识别回溯工具可以依赖的两类依赖：变量级数据依赖和函数级数据依赖。对于第二个挑战，我们设计了区域推断（第 6.3 节），它通过规则模拟分析人员的代码检查过程，只需要一小组开发人员提供的标签，并自动推断变量的区域。

贡献。 我们做出以下贡献。

  • 我们设计了 CLDG 及相关的查询语言，这是一种新的中间抽象，弥合了智能体功能级推理与程序变量级应用代码执行之间的语义鸿沟。
  • 我们设计了区域推断，这是一种通过规则引导的标签信息传播，沿污点程序路径将程序变量映射到相关区域的技术。
  • 我们在五个真实世界智能体应用和八个攻击事件上构建并评估了 Origin。Origin 在每个事件中以单一候选正确识别每个 CEP，与完整污点图相比，将分析人员的检查范围减少了 64–94%，并用区域引导的诊断取代了详尽的源代码检查。

为促进该主题的研究，我们将把 Origin 的源代码发布到 GitHub。

2. 背景

智能体应用。 LLM 驱动的智能体应用与多样化的信息源交互，以实现各种智能体功能（例如感知用户指令、规划、通过调用工具执行行动以及从记忆中回忆信息）（Liu et al., 2025）。此类应用生成轨迹日志，记录具体执行期间智能体功能的调用（Zhu et al., 2025; Ma et al., 2025）。两类信息源是：（1）应用外部的外部信息源，包括但不限于用户输入、与人类或智能体的交互、传感器读数、网络可访问内容（例如网页和电子邮件）以及 LLM 生成的内容；（2）应用内部的内部信息源，例如知识库和记忆。记忆存储用户与智能体之间的多轮交互，以原始或摘要形式持久化在磁盘上，以便智能体可以跨会话回忆先前的上下文（Liu et al., 2025）。

针对智能体应用的攻击。 诸如 IPI（Greshake et al., 2023; Zhan et al., 2024; Liu et al., 2024b）和 MC-Poison（OWASP GenAI Security Project, 2025; Chen et al., 2024; Zou et al., 2025）之类的智能体特定攻击通过向应用的合法信息源注入被操纵的内容来入侵智能体应用。MC-Poison 攻击通常涉及在单独执行中发生的两个阶段：投毒阶段，其中恶意数据被写入内部信息源；利用阶段，其中存储的数据被检索并造成危害。在某些事件中，投毒发生在应用之外（例如攻击者直接修改知识库文档），只有利用阶段是可观察的。

静态污点分析器。 现有的污点分析框架，如 Joern（Joe, 2025）、Pysa（Pys, 2026）和 CodeQL（Cod, 2025b），已经可以计算程序变量和表达式上的传播路径。这些能力可以被重新用于回溯智能体应用安全事件。然而，它们只暴露程序代码级语义，不提供与智能体功能对齐的抽象。

3. 动机

3.1. 激励性示例

安全事件。 考虑 GPT-Researcher，一个为用户进行研究并生成综合内容的智能体应用（GPT, 2025）。安全分析人员收到应用用户的事件报告。报告指出，该应用在一个特定研究任务中产生了包含错误信息的研究综合，而其他任务均正确完成。报告包括：应用使用方式的描述、研究综合的 PDF、应用的轨迹日志（清单 1）以及应用的源代码。根据用户描述，该应用在此失败任务中同时使用了知识库和网络数据。分析人员列出了三个可能的事故原因：LLM 产生幻觉、抓取的网页被操纵，或知识库被投毒，其中后两者是面向安全的。

三方利益相关者。 事件中有三方利益相关者：分析人员、补救管理员（通常是用户）和开发人员。补救管理员需要针对损害的具体、可操作的补救措施，例如从包含数百个文档的知识库中删除确切的中毒文件；开发人员需要日志打印语句放置建议，使应用在未来的事件中更易于诊断，例如在对应于初始入侵的函数调用之前立即记录其参数值（清单 2，第 83 行）。为了向两方利益相关者提供这两个益处，分析人员的目标是识别 CEP，即首次将恶意内容引入应用的函数调用（第 4.3 节）。

日志分类。 为了识别事件的 CEP，分析人员首先对轨迹日志（清单 1）进行分类，该日志记录了用户任务、应用的研究计划、抓取网页的链接以及对 LLM 提供商的 HTTP 请求。这些粗粒度的痕迹足以排除 LLM 幻觉和网页被操纵的可能性，剩下知识库投毒作为剩余的可疑原因。然而，日志无法帮助识别哪个函数调用对初始入侵负责（即从知识库检索中毒内容），因为轨迹日志没有记录具体的函数调用。从根本上说，轨迹日志位于智能体功能抽象层，而函数调用位于应用代码执行层。

3.2. 现有方法的局限性

现有的分析和防御智能体应用的方法无法为利益相关者提供上述两个益处。主要原因是基于轨迹日志的故障诊断（Zhu et al., 2025; Ma et al., 2025; Zhang et al., 2025b）、基于检测的故障归因（Kim et al., 2025; Zhang et al., 2026; Chocron et al., 2026）和预防性信息流控制（Debenedetti et al., 2025）不会为分析人员提供 CEP。它们反而为分析人员提供错误的智能体执行状态（Zhu et al., 2025; Ma et al., 2025; Zhang et al., 2026）（例如智能体形成错误计划）、错误的智能体（Zhang et al., 2025b）或智能体所有者（Chocron et al., 2026），以及 LLM 工具调用（而非源代码级别的函数调用）（Kim et al., 2025; Debenedetti et al., 2025）。

4. 方法概述

4.1. 范围

现有智能体应用可分为两类：预定义工作流（C1），其中应用源代码而非 LLM 决定智能体功能之间的控制流；类 OpenClaw 智能体（Ope, 2026; Her, 2026; Aut, 2025）（C2），其中 LLM 在运行时决定接下来调用哪个智能体功能。C2 智能体最近才出现；然而，大多数现有应用属于 C1。我们的方法直接针对 C1，而非 C2。因此，本工作的范围是 C1；C2 和智能体库框架（Lan, 2025; Wu et al., 2024; Smo, 2025）不在范围内，仍是未来研究的领域。

4.2. 威胁模型

我们假设攻击者可以通过现有工作中提出的方法发起两类智能体特定攻击：IPI（Greshake et al., 2023）和 MC-Poison（Dong et al., 2025; Chen et al., 2024）。这两类攻击是 OWASP 智能体应用十大威胁中最普遍的，可以覆盖报告中针对应用智能体功能的所有风险类别（OWASP GenAI Security Project, 2025）。其余类别要么是从传统软件安全继承的风险（即远程代码执行、权限提升和供应链完整性），要么是位于应用之外的风险（即智能体间通信协议、社会工程和内部威胁）。注意：不安全的智能体间通信风险类别的非协议部分可能由 IPI 和 MC-Poison 引起。此类攻击事件在第 9.3 节中进行了调查。

4.3. 入侵入口点

第 4.2 节中的智能体特定攻击类别具有一个共同特征：恶意数据通过 API 调用的返回值进入应用，并通过数据流传播造成危害。我们基于该特征和标准静态污点跟踪（Yin et al., 2007）定义入侵入口点（CEP）。给定智能体应用中的安全事件，CEP 由以下要素识别： API 调用的名称，其返回值包含恶意数据； 相应源代码程序文件的名称； 调用点的行号。我们还为分析人员提供一组污点传播路径，其中每条路径从接收 CEP 函数调用返回值的变量开始，到捕获攻击效果的变量结束。路径中的每个变量都恰好包含在一个函数中。将每个变量映射到其所在函数可得到函数级路径：数据从入口到效果所经过的函数序列。

4.4. 问题陈述

我们的洞察：需要中间抽象。 正如激励性示例所示，分析人员对从轨迹日志中观察到的已执行智能体功能进行推理（例如"哪段代码从知识库检索？"），而静态污点分析在程序变量级别操作。然而，没有现有的静态分析技术能够确定哪些程序变量在语义上对应哪些特定的智能体功能，因为程序结构和命名约定在不同应用之间各不相同，难以泛化这种映射。幸运的是，我们观察到智能体功能可以根据它们与之交互的信息源类型（第 2 节）分组为少量组。例如，从知识库检索和回忆记忆是不同的功能，但两者都与内部信息源交互；因此，它们属于同一组。我们将这样的组称为区域：一组共同实现同一组智能体功能的程序变量。分析人员可以在区域级别查询（例如"哪个区域用于从知识库检索内容？"）；查询处理输出可以直接排除不相关的 CEP 候选，无需手动代码检查。

具体而言，中间抽象由四个元素组成：（1）区域集，将智能体功能划分为有限组；（2）区域到变量的映射，将每个区域与实现它的程序变量关联；（3）区域级查询接口（包括查询语言），分析人员通过它以区域而非变量的方式表达诊断查询；（4）区域到变量的查询映射，将区域级查询转换为变量级查询，由现有静态分析基础设施支持。本工作的目标是设计一个实现这种新抽象的工具。

4.5. 挑战

挑战 1： 定义捕获两个语义层之间映射关系的中间抽象：智能体功能层与应用代码执行层。不同智能体应用对同一智能体功能的实现各不相同（例如函数/变量命名、使用的智能体框架）。我们认为需要这样的中间抽象，以便分析人员可以对不同应用的安全事件使用相同的接口进行回溯。

挑战 2： 构建区域到变量的映射。该抽象需要从区域到程序变量的具体映射（元素 2）。没有现有的静态分析技术可以从程序源代码推断智能体功能。如第 3.1 节所示，变量名称（如函数 _load_document 中的 ret_data、loader_dict 和 loader）不携带它们用于从知识库检索的提示。因此，很难确定它们属于哪个区域。

  • 函数平面。 V_fn ⊆ ℱ 是 P 中通过污点传播可从所有 API 调用到达的函数集合。λ: V_fn → ℛ ∪ {UNK} 为每个函数节点分配其推断的区域。
  • 变量平面。 V_var 是 P 中通过污点传播可从所有 API 调用到达的程序变量集合，E_var ⊆ V_var × V_var 是它们之间的污点边集合。不同代码语句中的同一变量在变量平面中被视为不同的节点（具有不同的标识符）。
  • 跨平面边。 E_cross ⊆ V_fn × V_var 将每个函数节点 f 连接到 f 中定义/使用的每个程序变量。

只要提供了映射关系，区域集 ℛ 可以由安全分析人员确定。我们的设计适用于任何分析人员定义的区域集。一旦采用了特定的区域集，Origin 需要智能体应用开发人员提供相应的函数到信息源的映射表（第 6.1 节）。此外，变量平面中的每个跨函数污点边自然映射到连接两个函数的边。这样的边出现在第 4.3 节中提到的函数级路径上。

6. CLDG 构建

构建 CLDG 涉及两个步骤：（1）污点传播以构建其变量平面（第 6.2 节）和（2）推断平面中节点的区域（第 6.3 节）。步骤（2）需要开发人员知识作为输入（第 6.1 节）。

6.1. 开发人员知识收集

有了开发人员标签，Origin 构建图。变量平面（V_var, E_var）通过从每个 API 调用的返回值执行上下文敏感、流敏感、字段敏感的前向污点传播来生成（实现见第 8 节）。由于传播从所有 API 调用开始，任何符合第 4.3 节定义的 CEP 函数调用都位于变量平面中的路径上，并且可以通过对 CLDG 的查询来定位。V_fn 和 E_cross 从变量平面导出：如果函数的任何变量出现在 V_var 中，则 f ∈ V_fn；E_cross 将每个函数连接到其变量。

6.3. 区域推断

区域推断算法实现了抽象中的区域到变量映射元素（第 4.4 节）。目标是将 CLDG 函数平面中的函数分类到附录 A 中详述的五个区域。我们观察到，朴素的基于特征的聚类方法，即按函数名称、API 名称或程序代码语法特征聚类，不适合此任务： 同名函数/API 在不同的智能体应用中可能实现完全不同的智能体功能，因此属于不同的区域。例如，两个名为 load 的函数可能读取网页（属于 PA 区域）或从知识库读取文件（属于 RR 区域）。类似地， 语法上相似的字符串操作，例如 x.format(y)，可能用于提示组装或非智能体功能，例如组合错误消息。

幸运的是，我们发现完全了解五个区域语义的分析人员通常在代码检查期间收集证据来回答四个问题，答案的融合可以确定函数属于哪个区域： 函数是否与信息源交互？ 函数是从信息源读取还是写入信息源，或两者兼有？ 如果函数与多个信息源交互，哪种类型的信息源占主导地位（第 2 节）？ 函数是否主要组装提示以出现在 LLM 上下文窗口中？

Origin 使用两类规则来模拟上述分析人员在代码检查期间的推理过程进行区域推断：

标签传播规则（共 3 条）模拟收集证据以回答关于函数的四个问题的过程。两条规则（沿污点路径）传播与信息源交互的 API 调用的标签。具体而言，这两条规则是： 如果 API 调用读取信息源，则向前传播标签； 如果 API 调用写入信息源，则向后传播标签。我们还有一条规则用于传播组装提示而非与信息源交互的函数调用的特殊标签。与提示组装相关的函数调用被分配这样的标签（例如像 format 这样的文本组合函数；函数名称或参数包含"prompt"的特殊名称）。此规则仅在函数内传播标签，因为我们观察到提示组装是局限于离散函数的智能体功能。

7. 查询处理

给定构建好的 CLDG，分析人员通过使用查询语言对其发出查询来调查安全事件。

7.1. 查询语言

查询语言实现了抽象中的区域级查询接口元素（第 4.4 节）。完整的语法在附录 B 中提供。每个查询以关键字 CHECK 开始，后跟由逻辑连接词连接的一个或多个原子公式。原子公式由谓词 DEPENDS_ON 组成，它断言两个项之间的污点数据流。项可以是区域名称或程序变量标识符，允许在区域级别或变量级别进行查询。逻辑连接词包括 AND 和 OR。例如，CHECK (PK DEPENDS_ON PA) AND (PA DEPENDS_ON PK) 是分析人员用于回溯 IPI 事件的常用区域级查询（表 5）。原子 PK DEPENDS_ON PA 询问来自 PA 区域的数据（例如抓取的网页）是否可以流入 PK 区域（例如组装提示）。类似地，原子 PA DEPENDS_ON PK 询问 PK 区域中的数据（例如组装的提示）是否可以流回 PA 区域（例如 LLM 将提示作为输入，生成的内容流向写入文档）。该语言还提供了链接运算符 →：→ 之后的公式针对前一个公式返回的子图进行评估，允许分析人员逐步缩小变量级结果。例如，在编写上述区域级查询之后，分析人员可以编写 →，后跟第二个区域/变量级查询。Origin 首先评估第一个查询；如果结果不为空，则继续针对第一个查询的结果评估第二个查询（第 7.2 节）。

7.2. 查询评估

本小节实现了抽象的区域到变量查询映射元素（第 4.4 节）。

区域级查询评估。 区域级查询（例如 CHECK PA DEPENDS_ON RR）通过两个步骤返回函数节点上的数据依赖图： 使用 λ 和 E_cross 识别 R_src 函数中的变量和 R_sink 函数中的变量； 在变量平面中计算从 R_src 变量的前向可达性和从 R_sink 变量的后向可达性，产生两组可达变量节点。这两组的交集包含位于从 R_src 到 R_sink 的某条污点路径上的所有变量。如果 E_var 中的污点边在此交集中将 f₁ 中的变量连接到 f₂ 中的变量，则边（f₁, f₂）出现在结果中。当查询包含逻辑连接词时，AND 和 OR 分别通过节点和边集的交集和并集组合结果图。

变量级查询评估。 在变量级查询中，源和汇由它们在变量平面中的节点标识符指定（当分析人员在区域级查询结果中检查函数的变量时可见）。例如，CHECK node.5110 DEPENDS_ON node.4216 查询是否存在从变量 4216 到变量 5110 的污点路径。为了评估变量级查询，对 CLDG 变量平面的朴素图切片可能包括在任何实际执行中都不可行的路径。Origin 使用在 CLDG 构建期间构建的应用调用图和控制流图，仅枚举源和汇变量之间控制流可行的污点路径。返回的路径是变量级污点路径。如第 4.3 节所述，污点路径可以自然地映射到相应的函数级路径。

8. 实现

我们在 Joern（v4.0.360）（Cod, 2025a）之上将 Origin 实现为 Python 程序（约 16 KLoC），并通过 Pyrefly（v0.45.0）（Fac, 2026）增强类型推断。我们解决了 Joern 导致污点传播中漏报的三个限制。首先，Joern 不解析生成器表达式；我们在分析之前将 yield 和 yield from 重写为 return。其次，存储在类实例变量（例如 self.x）中的污点不会跨函数跟踪；我们通过控制流图可达性显式传播它。第三，Joern 的调用图在动态分派下不完整。我们首先通过修补 Pyrefly（Fac, 2026）引入类型知情的间接调用解析；然后我们遵循 Xia et al.（Xia et al., 2024）和 Liu et al.（Liu et al., 2024a）的方法推断间接调用的目标，并进行了两项增强：用上下文敏感的类型链跟踪代替全局类型链映射，以及用值集分析代替完整数据流分析。

9.1. 共享回溯工作流程

尽管攻击类别和入口点多样，分析人员在所调查事件中的回溯工作流程是相似的。具体而言，分析人员 从轨迹日志中识别可疑的智能体功能， 提交区域级查询， 检查结果图以识别变量级污点源/汇候选， 选择源/汇以提交变量级查询，以及 识别 CEP 和相应的路径。通常，CEP 识别需要两个查询（表 3）：一个区域级查询缩小范围，一个变量级查询精确定位 CEP。我们在第 9.2 节中展示，检查区域级查询的结果图通常将变量级查询的源/汇候选分别缩小到一两个。凭借从轨迹日志中获得的知识，分析人员可以对源和汇候选进行可疑排序（详见附录 C）。在我们的案例研究中，这些帮助分析人员以最少的尝试提交正确的变量级查询。此外，对于在单独执行中跨越多个阶段的攻击事件（例如 Quivr MC-Poison（M）），分析人员在识别 CEP 之前对每个阶段重复步骤–。

9.3. 各个应用的值得注意的发现

我们报告案例研究中的其他值得注意的观察。

执行中的智能体循环不会阻止 Origin 识别 CEP，只要 CEP 和对应于攻击效果的函数调用都位于循环之外。例如，在 SWE-agent IPI 事件中，攻击执行中智能体循环的每次迭代都会查询 LLM 下一个要调用的工具，执行该工具，并将结果反馈。然而，由于循环在返回的污点路径中间作为传递函数出现，且静态污点分析跟踪源代码中变量的数据流，从源到汇的污点传播保持完整，Origin 正确识别了 CEP。

当源和汇函数是应用中两个或多个智能体功能共享的通用实用程序时，指定中间变量作为路标有助于将返回的路径约束到与事件相关的子集。在 aider 和 MetaGPT 中，一对文件读/写函数（aider 中的 read_text/write_text；MetaGPT 中的 aread/awrite）作为整个代码库的主要文件 I/O 接口。这些函数之间的标准源到汇查询返回应用中文件读取和文件写入之间的大量污点路径，其中大多数与事件无关。我们观察到获得更多事件相关结果的良好做法，即从区域级查询结果中识别中间函数，并将其中的变量指定为路标。这些函数是可识别的，因为轨迹日志记录了语义上有意义的步骤（例如命名命令和任务级操作），这些步骤直接映射到 CLDG 中的函数平面节点。

Origin 可以处理源于智能体间通信操纵的攻击事件。在 MetaGPT 中，识别的 CEP（aread）读取上游架构师智能体计划并写入磁盘的规范文件（该文件被攻击者入侵）；下游工程师智能体读取恶意数据并根据被操纵的任务生成代码。智能体之间的协调机制（即磁盘上的共享文件）完全按设计运行。然而，由于缺乏对先前执行产生的工件的验证，IPI 通过应用的正常协调机制跨智能体边界发生。

11. 讨论

框架引起的间接调用解析。 我们的静态分析无法解析框架引起的间接调用目标（例如 LangChain（Lan, 2025）工具分派）。这导致相应的污点传播路径在 CLDG 中缺失。解决此限制需要框架特定的建模或动态分析，这是未来的工作。

具有 LLM 驱动的智能体循环的智能体。 诸如 OpenClaw（Ope, 2026）和 Hermes（Her, 2026）之类的自主智能体由智能体循环驱动，其中每次迭代中 LLM 在运行时决定接下来调用哪个智能体功能。对于此类智能体，仅静态分析无法确定 CEP 函数调用（例如哪个工具引入了恶意数据），第 9.3 节发现 中讨论的情况除外。这仍然是未来研究的领域。

12. 相关工作

软件系统的根本原因分析。 诊断软件系统中漏洞和故障的根本原因是修复程序的第一步。大多数现有工作基于回溯（Xu et al., 2017; Cui et al., 2016; Xu et al., 2016; Chang et al., 2025）、重建（Cui et al., 2018; Ge et al., 2020; Yagemann et al., 2021; He et al., 2022）或统计分析（Blazytko et al., 2020; Xu et al., 2024; Park et al., 2024; Kasikci et al., 2015; Kasikci et al., 2017）。这些方法专注于诊断触发内存安全违规（Xu et al., 2017; Cui et al., 2016; Xu et al., 2016; Chang et al., 2025; Cui et al., 2018; Yagemann et al., 2021; He et al., 2022; Blazytko et al., 2020; Xu et al., 2024; Park et al., 2024）和数据竞争（Kasikci et al., 2015; Kasikci et al., 2017）的错误代码位置。然而，在智能体应用安全事件中，应用代码本身在条件表达式和语句顺序方面并没有错误。问题在于应用在不可信外部信息源与应用之间的边界缺乏验证或清理。因此，攻击者控制的数据通过合法的 API 调用进入，并无阻碍地通过管道传播。

APT 攻击的因果分析。 大量工作通过从操作系统级审计日志构建攻击溯源图来调查 APT 攻击（King and Chen, 2003; Milajerdi et al., 2019; Gao et al., 2018; Goyal et al., 2024）。后续工作通过将长时间运行的进程划分为更细的执行单元（Ma et al., 2016; Ma et al., 2017; Ji et al., 2017），或通过将应用层日志与系统审计数据融合以恢复应用语义（Hassan et al., 2020）来细化日志粒度。这些系统中使用的日志和审计数据足以分析传统的 APT 攻击。然而，在智能体应用中，分析人员依赖轨迹日志和对程序代码的静态分析。轨迹日志在智能体功能抽象层记录智能体行为，但缺少精确定位 CEP 函数调用所需的应用特定函数调用日志。静态分析不提供分析人员推理所需的智能体功能语义。由于语义鸿沟，智能体功能与程序代码之间的桥接是困难的。我们的工作通过实现连接它们的中间抽象来解决这一问题。

智能体应用攻击与防御。 智能体攻击已针对广泛的商业和开源智能体（Rehberger, 2024），最显著的是 IPI 攻击（Greshake et al., 2023; Zhan et al., 2024; Debenedetti et al., 2024; Liu et al., 2024b）和 MC-Poison 攻击（Chen et al., 2024; Wang et al., 2024）。在真实世界环境中，攻击者通常采用在智能体执行的不同阶段结合两种方法的复合攻击（Zhang et al., 2025a）。防御已在多个层面提出：基于数据-指令分离的 LLM 加固（Chen et al., 2025a; Chen et al., 2025b; Wallace et al., 2024）和针对 IPI 攻击的提示加固（Hines et al., 2024）、针对 MC-Poison 攻击的记忆写入/检索阶段过滤（Xiang et al., 2024; Wei et al., 2025; Sunil et al., 2026），以及运行时的应用级污点跟踪和策略执行（Debenedetti et al., 2025; Wu et al., 2025; Costa et al., 2025; Shi et al., 2025; Ji et al., 2026）。然而，所有这些防御本质上都是预防性的，仍然可能被绕过。当攻击确实成功时，我们仍然需要回溯事件的初始入侵。此外，IPI 攻击和 MC-Poison 攻击的检测已分别在（Kim et al., 2025; Zhang et al., 2026）和（Tan et al., 2025; Wei et al., 2025）中进行了研究。然而，检测和诊断（通过回溯）是两个不同的问题。

13. 结论

我们提出了 Origin，一个用于智能体应用安全事件的回溯工具。Origin 将新的中间抽象实现为 CLDG，它将区域推断函数与变量级污点子图连接起来，并提供相关的查询语言，允许分析人员通过少量查询识别 CEP。Origin 通过规则引导的区域推断构建 CLDG 中的区域到变量映射，这只需要一小组开发人员提供的标签。对五个应用和八个不同攻击事件的案例研究表明，使用 Origin 的分析人员可以正确识别所有事件的 CEP。
