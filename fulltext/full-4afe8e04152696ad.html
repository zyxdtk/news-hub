摘要

内存安全问题使 Rust 成为现代化遗留 C/C++ 系统的一个颇具吸引力的目标，但项目级 C++ 迁移必须在语义保真与面向 Rust 的重构之间取得平衡。保持源结构的迁移能够追踪底层行为，但也可能将源语言的组织方式、不安全惯用法和项目假设带入 Rust。直接基于智能体的翻译赋予模型更大的自由度来构建 Rust 项目，但语义覆盖取决于模型能否识别出必须保留的源行为。这一问题在 C++ 中尤为突出，因为源行为往往隐藏在对象模型、析构函数驱动的生命周期协议以及其他难以定位的 C++ 语义之中。

本文提出 Req2Rust，这是首个项目级、基于 LLM 的 C++ 到 Rust 迁移框架。Req2Rust 首先推导出有据可依的迁移需求规范（MRS），记录必须保留的行为和约束；随后综合出 Rust 设计规范（RDS），并将其落地为初始 Rust 项目。由于真实项目包含只有在构建和验证过程中才会显现的实现细节与惯用法，Req2Rust 将初始 Rust 项目视为一个可执行的重构状态。编译器、语义和不安全缩减三类验证器生成验证报告，用于改进可构建性、行为一致性和不安全使用情况。我们在通用 C++ 项目以及大规模 OpenHarmony 代码库的模块上，以 ClaudeCode 为基线对 Req2Rust 进行了评估。Req2Rust 在两种设置下均能生成可构建的 Rust crate，并将通用项目的测试通过率从 69.5% 提升至 91.9%，将 OpenHarmony 模块的测试通过率从 45.4% 提升至 87.9%。

索引词：C++ 到 Rust 迁移、代码翻译、需求工程、LLM、智能体框架

I 引言

内存安全漏洞始终是系统软件故障的一个持续性来源，因为它们源于内存不安全语言中常见的实现模式。越界访问和释放后使用等错误可以通过静态分析、消毒器和加固技术加以缓解，但这些方法仍然运行在允许不安全内存行为的语言之内。Rust 已成为一种有前景的替代方案，因为其所有权与借用系统在编译时即强制执行内存安全，这使其成为现代化遗留 C/C++ 系统的日益受到青睐的目标 [18, 19, 3, 15, 14]。

然而，将 C/C++ 系统迁移到 Rust 不仅仅是一个翻译问题，而是一个项目级重设计问题。开发者必须在围绕 Rust 的所有权模型、模块结构和生态系统惯例重组软件的同时，恢复其预期行为 [25, 6]。这在“保持语义保真”与“支持面向 Rust 的重构”之间造成了根本性的张力。

大量先前工作研究了 C 到 Rust 的迁移，主要采用基于规则的翻译和基于精化的方法。这些系统表明，C 程序可以在保留底层行为的同时被系统地转换为 Rust，从而实现可追溯性和增量式的安全改进 [9, 6, 34, 5, 10]。然而，这些方法主要是为 C 语言设计的，而 C 的程序结构和语义相对显式且以过程方式组织。

相比之下，由于 C++ 的语义更为丰富且更加隐式，C++ 到 Rust 的迁移明显更具挑战性，也较少被探索。C++ 将程序行为绑定于对象模型、构造函数与析构函数生命周期、模板实例化、重载解析、回调、资源所有权协议以及构建时约定。这些语义往往分布在多个文件中，只有通过跨模块交互和编译行为才能被观察到。因此，项目级迁移不能仅依赖局部翻译，而必须全局地推理哪些行为必须保留、哪些行为可以在 Rust 中被重构 [25, 30]。

随着 LLM 的兴起，近期工作为自动化程序迁移和代码翻译引入了新的可能性 [32, 7]。基于 LLM 的方法在局部代码转换和迭代修复方面表现出色，而编码智能体系统进一步通过执行驱动的反馈回路扩展了这一能力。然而，专门针对 C++ 到 Rust 的 LLM 工作仍然稀少，现有研究主要在代码片段、特性或翻译单元层面运作，而非项目级重构 [22, 30]。这些系统还依赖于对语义保留的隐式推断，而非对迁移意图的显式建模。这一局限在 C++ 到 Rust 迁移中尤为严重，因为关键行为往往是非局部的，只有在项目层面才能被观察到。

这揭示了现有方法的一个关键局限：若缺乏一种显式机制来区分“必须保留什么”与“目标系统应如何重构”，基于 LLM 的迁移系统就难以可靠地支持项目级 C++ 到 Rust 迁移。

Req2Rust 通过一个三阶段的需求中介流水线来弥补这一差距。首先，它将保留决策从模型的隐式上下文中移出，放入 MRS——一种介于 C++ 证据与 Rust 实现之间的语言中立中间表示。MRS 将外部可见行为、依赖假设、状态与资源效应以及安全约束记录为保留义务。通过将“必须保留什么”与“Rust 将如何实现”分离，MRS 有助于在做出 Rust 特定设计选择之前弥合源语言与目标语言之间的鸿沟。

其次，需求引导的重构从 MRS 综合出 RDS，并将其落地为初始 Rust 项目。第三，智能体框架精化将该项目视为一个可执行状态。编译器、语义和不安全缩减验证器为精化智能体生成验证报告，后者迭代地修复编译失败、行为风险和可缩减的不安全使用。这在需求引导的项目重构与验证器引导的精化之间形成了一个闭环 [20]。

我们在七个通用 C++ 项目和五个 OpenHarmony 模块上，以 ClaudeCode 为对照对 Req2Rust 进行了评估。Req2Rust 在两种设置下均能生成可构建的 Rust crate，并将通用项目的测试通过率从 69.5% 提升至 91.9%，将 OpenHarmony 模块的测试通过率从 45.4% 提升至 87.9%。消融研究表明，语义验证带来了大部分行为增益，而不安全缩减在不降低所观察到的测试通过率的情况下降低了不安全使用。

本文做出以下贡献：

（1）我们提出 MRS，一种面向项目级 C++ 到 Rust 迁移的、以保留为导向的中间表示。

（2）我们设计了一条需求引导的重构流水线，它综合出 RDS 并将其落地为初始 Rust 项目，随后在验证报告下进行智能体框架精化。

（3）我们在通用 C++ 项目和 OpenHarmony 模块上评估了 Req2Rust，消融研究证明了其生成可构建 Rust crate 的能力，同时具有更强的行为保留和更低的不安全使用。

II 方法

Req2Rust 将项目级 C++ 到 Rust 迁移表述为一个需求中介的过程。输入是一个 C++ 项目或模块及其源代码、接口和构建证据，输出是一个可在验证报告下编译、检查和精化的 Rust crate。核心设计选择是将保留义务与目标侧实现分离：MRS 记录外部可见行为、依赖假设、状态与资源效应以及安全相关约束，而 Rust 项目重构则决定这些义务应如何组织为一个 Rust crate。图 1 展示了这一工作流程：Req2Rust 首先将保留义务建模为 MRS，然后从 MRS 综合出 RDS 并落地为初始 Rust 项目，最后通过验证器引导的智能体动作精化可执行的项目状态。

图 1：Req2Rust 的总体工作流程。该框架首先从源证据推导 MRS，从 MRS 综合 RDS，落地为初始 Rust 项目，然后通过来自编译器、语义和不安全缩减验证器的验证报告精化该项目。

II-A 面向迁移的需求建模

Req2Rust 首先从源项目构建 MRS。该阶段将异构的源代码、接口和构建证据转化为供后续重构和验证使用的保留目标。MRS 从迁移视角总结源模块：它为初始 Rust 项目记录项目级义务，并将源语言语法从主要生成目标中移除。

MRS 将迁移相关信息分为若干类别。它记录外部可观察的接口，包括公共 API 标识、所有权、可调用形态、参数、返回行为和可见性。它记录行为事实，包括正常行为、输入与输出约束、失败行为、状态效应和依赖效应。它还记录外部依赖和暴露的符号，以便后续阶段能够区分由源项目实现的行为与委托给外部库或平台 API 的行为。对于跨越多个函数的项目级行为，MRS 捕获状态与资源事实、跨 API 关系以及需要后续验证的开放迁移项。由此产生的工件显式地区分了“必须保留什么”与“Rust 项目将如何实现它”。

II-B 需求引导的 Rust 项目重构

Req2Rust 随后从 MRS 重构 Rust 项目。该阶段回答需求所遗留的目标侧问题：哪些文件、模块、公共项、辅助函数和实现单元应当承载每项义务？它包含两个子阶段：需求驱动的 Rust 设计综合和设计引导的项目落地。

II-B1 需求驱动的 Rust 设计综合

需求驱动的 Rust 设计综合将保留义务转换为 RDS。RDS 规定用于落地的项目组织方式，包括 Rust 文件、文件职责、模块依赖、拥有的符号、面向公共的表面，以及分配给每个文件的实现单元。

RDS 还携带全局设计约束。这些约束描述了应跨文件使用的共享 Rust 模型，例如通用数据结构、错误处理约定、资源所有权、序列化或格式化路径，以及其他跨文件行为。这可以防止后续的单元构建将每个源片段当作孤立的翻译任务。

在每个文件内部，Req2Rust 进一步将设计分解为实现单元。一个单元对应一个 Rust 项，例如函数、类型、trait、实现块、常量或辅助函数。每个单元记录其预期签名、职责、调用关系，以及它预期满足的 MRS 条目。因此，RDS 在需求与项目落地之间架起桥梁：MRS 定义源侧义务，而 RDS 将其转换为目标侧结构。

图 2 概括了这两个结构化工件的模式。MRS 记录源侧保留义务，而 RDS 将这些义务组织为 Rust 项目设计决策。

图 2：MRS 与 RDS 工件的模式。MRS 记录源侧保留义务，而 RDS 将这些义务组织为 Rust 项目设计决策。

II-B2 设计引导的项目落地

设计引导的项目落地将 RDS 物化为初始 Rust 项目。落地规划器首先根据实现单元的文件目标和调用依赖对其进行排序，并将其分组为若干构建批次。随后，渲染器创建一个基于标记的 Rust 骨架：源文件、crate 结构、模块声明，以及稍后可被生成单元体替换的占位区域。

接着，Req2Rust 在 RDS 和 MRS 提供的约束下翻译各单元体。单元体应用步骤将生成的单元体写回基于标记的骨架。Rust crate 组装步骤则补全普通 Rust 工具链所需的 crate 根、清单、模块导出和依赖骨架。

初始 Rust 项目被视为一个可精化的项目工件。它为下一阶段中验证器和精化智能体所检查与修改的具体源文件。MRS 和 RDS 恢复主要的保留目标，而初始 Rust 项目则将剩余的实现细节带入可执行精化阶段。

II-C 智能体框架精化

最后一个阶段通过智能体框架来精化初始 Rust 项目。该阶段之所以存在，是因为项目重构可能产生一个结构连贯的 crate，但仍然缺失只有在编译、语义检查或不安全使用分析中才会显现的细节。该框架维护当前项目状态，调用验证器，收集验证报告，并将这些报告反馈给精化智能体。精化智能体更新现有的 Rust 项目，并保留累积的验证上下文。

Req2Rust 使用三个翻译框架验证器。编译器验证器检查当前 Rust 项目是否可构建，并定位编译失败、缺失项以及类型或 API 不匹配。语义验证器通过可观察契约——正常行为、边界与错误行为、状态与资源效应以及面向公共的覆盖——将当前 Rust 项目与 MRS 和源证据进行比较。其验证报告将潜在偏差与相关的保留义务、Rust 位置、源证据和修复理由关联起来。不安全缩减验证器以同样的保留导向视角分析不安全使用。它区分保护迁移边界的不安全代码与可以在 Rust 实现内部缩减的不安全代码。当边界不安全是 ABI 兼容、布局保留、外部调用、资源、回调或跨迁移接口的所有权转移所必需时，边界不安全会被保留。当等效的可观察行为可以通过安全的 Rust 抽象或更小的不安全包装器来表达时，可缩减的不安全会被报告。

这些验证器返回验证报告，作为精化智能体的编辑目标。每份报告包含可操作的发现，包括编译错误、语义不匹配、不安全缩减机会，以及指向相关保留义务的链接。精化智能体根据这些报告编辑 Rust 项目，然后 Req2Rust 再次验证更新后的项目。当各项发现相互独立时，Req2Rust 可以将其分配给并行的精化智能体，并在下一轮验证之前合并更改。当满足配置的接受标准或精化预算耗尽时，循环终止。

面板 A 追踪消息模型。源声明和构造函数体表明，消息必须保留主题/载荷构造、从现有 C MQTT 消息重建、QoS 与保留状态设置器以及属性更新。MRS 将这些事实转化为命名的保留目标，RDS 将该目标分配给 src/message.rs。初始生成的代码创建了一个看似合理的 Message 结构体，但缺失了 from_c_message 和若干设置器行为；修复任务将修复定位到消息模型，最终代码恢复了缺失的重建与设置器路径。

面板 B 追踪客户端发布。源证据将公共 publish API 与消息创建、交付令牌注册、MQTTAsync_sendMessage 调用、成功记录以及失败时的令牌清理关联起来。MRS 将这些记录为发布、缓冲区、用户上下文和监听器义务，RDS 将其路由到 src/client.rs，并依赖于消息、令牌、选项、错误和线程模块。初始生成的代码仍使用占位符发送结果和不完整的回调/消费者路径；修复任务跨越面向客户端的多个文件，恢复了发布路径、回调分发、消费者事件和令牌移除行为。

这两条追踪表明，源代码片段并非被孤立地翻译。它们首先被转换为命名义务，被分配到 Rust 文件和单元，然后被用于限定验证报告的范围，使精化框架能够修复具体的行为缺口，同时不丢失解释这些缺口为何重要的源证据。

III 评估设置

III-A 实验对象与设置

Req2Rust 面向项目级迁移，因此基准测试必须呈现的不仅仅是孤立的函数体。为此，我们纳入了具有构建上下文和多样化 C++ 特性的多文件项目。第一组实验对象由通用 C++ 项目组成，它们具有可用的测试、多样的领域、不同的代码规模以及 C++ 语言特性的不同组合。第二组实验对象由 OpenHarmony 模块组成，用于在大型真实代码库中检验迁移 [23]。

对于 OpenHarmony 设置，增量迁移意味着用 Rust crate 替换选定的 C++ 模块，而代码库的其余部分保持原位。翻译后的 crate 必须保留面向源的接口、平台调用、资源与回调边界，以及周围代码库所需的构建假设。这不同于独立的 Rust 重写，因为某些不安全代码可能代表必要的 ABI、FFI 或平台资源边界。

III-B 特性表征

III-C 基线

我们将 Req2Rust 与 ClaudeCode 基线进行比较。ClaudeCode 是最先进的通用智能体编码系统，能够读取代码库、编辑文件、运行测试并针对失败进行迭代 [1]。这使其成为直接基于智能体的项目迁移的强基线。Req2Rust 和 ClaudeCode 基线均使用 DeepSeek-V4-Pro 作为底层语言模型。我们不使用 Cpp2Rust 作为基线，因为它目前仅支持 C++ 语言特性的一个子集 [25]。该子集无法覆盖我们基准中的所有实验对象，也无法为我们的设置提供通用的端到端项目迁移基线。

IV-A3 项目级 Rust 重构

除单个函数之外，RQ1 还揭示了一个更大的优势：Req2Rust 更能将源级子系统边界带入自然的 Rust crate 结构之中。我们以 fkYAML 为代表性示例，因为两个系统都编译了该项目并达到了较高的测试通过率，但生成的 crate 呈现出不同的架构。源项目不仅仅是一个 YAML 节点类型；它包含解析与序列化入口点、值转换 trait、输入处理、标签与锚点机制以及 UTF 编码工具。图 6 将这些源义务与两个生成的 Rust crate 进行了比较。

图 6：fkYAML 上的项目级代码比较。源码暴露了解析、序列化、转换、标签、锚点和编码义务。Req2Rust 将这些义务映射到公共 Rust 模块并重新导出，而 ClaudeCode 将 crate 中心放在 YamlNode 上，将解析器和序列化器模块保持为内部实现，并留下一条未实现的公共序列迭代路径。

这个例子说明了为什么即使直接迁移已经能够编译，Req2Rust 仍能产生更自然的 Rust 项目。Req2Rust 的 RDS 在项目落地之前将源义务显式化，因此 Rust crate 中包含 parse、serialize、convert、io、tag、anchor 和 encoding 的独立模块，并重新导出相应的公共 API。这些边界为每个迁移需求提供了稳定的实现位置，并使验证报告局部化到相关子系统。相比之下，ClaudeCode 暴露了一个以 YamlNode 为中心的较小公共表面，解析器和序列化器作为 crate 私有实现细节保留，转换、锚点、标签、输入抽象或编码没有一流的公共边界。其公共迭代器中残留的 unimplemented! 进一步说明了在没有首先重构这些 API 所必须支持的项目级义务的情况下翻译局部 API 的风险。因此，Req2Rust 在 RQ1 中的收益不仅在于更高的测试准确性；它还将源项目重构为模块与原始库职责相对应的 Rust crate。

总体而言，RQ1 表明 Req2Rust 的收益来自在 Rust 重构之前保留项目特定的源行为。汇总结果显示通用实验对象上的测试通过率更高，而 paho.mqtt.cpp 和 HFSM2 案例展示了显式需求如何保留面向迁移的 API 和源特定的工具。fkYAML 案例在项目结构层面展示了相同的机制，源职责成为公共 Rust 模块和重新导出。ClaudeCode 在 uriparser 上的较好结果表明，直接基于智能体的迁移在紧凑的面向解析的行为上仍然具有竞争力。

IV-B3 增量迁移中的平台边界保留

RQ2 还改变了对不安全使用的解读方式。在独立的 Rust 重写中，较低的不安全使用通常更为可取。然而，在 OpenHarmony 增量迁移中，翻译后的 Rust 模块仍须调用 C/C++ 平台服务、窗口令牌、RenderService 操作、SQLite API 和操作系统辅助功能。某些不安全代码是 Rust 复用周围系统的必要边界，而非用孤立模型取而代之。

图 8 以 wmserver 为例说明了这一点。C++ 源码调用 RenderService 和窗口令牌 API，例如表面边界更新、事务刷新、焦点应用注册和缩放变换传播。ClaudeCode 主要将相应的状态建模为 Rust 字段和局部方法。Req2Rust 则将这些调用隔离在显式的 Rust 适配器模块中，例如 rs_adapter.rs 和 token_adapter.rs，其不安全块包装了 FFI 调用。因此不安全率更高，但它反映了增量 OpenHarmony 替换所需的保留平台边界。

图 8：OpenHarmony wmserver 的增量迁移边界示例。源码依赖 RenderService 和窗口令牌调用。Req2Rust 将这些平台调用保留在显式的 Rust 适配器之后，而 ClaudeCode 主要重建局部 Rust 状态，没有同样的外部调用边界。

总之，RQ2 的示例表明，Req2Rust 在增量 OpenHarmony 设置中既保留了源可观察行为，又保留了显式的平台调用边界，同时仍能生成具有更高平均通过率的可编译 Rust crate。

总体而言，消融结果表明 Req2Rust 的收益来自互补的组件。语义验证在可编译性之外驱动行为保留，而不安全缩减在不降低所观察到的测试通过率的情况下改善了安全状况。完整框架将这些效果结合在一起，生成具有高测试通过率和较低不安全使用的可构建 Rust crate。

V 有效性威胁

行为预言机： 我们的测试和探针源自可用的项目测试、源证据和 OpenHarmony gtest 用例，但它们并不能证明完全的语义等价。它们主要检验公共 API 以及选定的状态、错误、回调和边界行为。未测试的路径、罕见输入、时间敏感的行为以及跨模块交互仍可能被遗漏。

基准覆盖： 我们的基准覆盖了多个 C++ 特性类别、项目规模、通用项目和 OpenHarmony 模块。对于具有特殊构建系统、更强平台耦合、更大规模的模板密集表面或我们的实验对象未涵盖的罕见语言特性的项目，泛化能力可能有所不同。我们报告了项目特征和特性覆盖，以使评估范围明确。

智能体可变性： Req2Rust 和 ClaudeCode 基线均使用 DeepSeek-V4-Pro，但智能体翻译仍然对模型行为、提示措辞、工具轨迹和运行时决策敏感。不同的模型、ClaudeCode 版本或采样配置可能会改变绝对结果。

VI 相关工作

VI-A 保持源结构的 Rust 迁移

自动迁移到 Rust 通常从保持源结构的表示开始。C2Rust 提供了一个实用的 C 到 Rust 源到源翻译基线 [9]，后续工作通过不安全缩减、所有权推断、别名分析、类型迁移、输出参数重写、联合体翻译和 I/O API 迁移来改进翻译后的程序 [16, 6, 34, 5, 12, 10, 11, 13, 29]。保留声明、控制流和底层操作使源行为可追溯，同时后续分析可以恢复更多面向 Rust 的类型和 API。

近期的系统将 LLM、静态分析、依赖恢复、FFI 验证、历史检索和编译器反馈修复引入保持源或骨架的迁移 [35, 21, 17, 8, 36, 37, 2, 27, 28, 33, 4]。它们提升了规模和构建恢复能力，但仍与源结构、生成的骨架或保持依赖的分解方式绑定；超越源对齐翻译的目标侧重构仍然不是核心。

VI-B C++ 到 Rust 翻译

C++ 到 Rust 翻译不如 C 到 Rust 迁移成熟，因为许多 C++ 义务难以直接从源结构中提取。类、重载、模板、RAII 与析构函数协议、回调以及资源所有权模式可以跨文件和 API 边界定义行为。Cpp2Rust 演示了从受支持的 C++ 子集到安全 Rust 的自动翻译 [25]。基于 LLM/RAG 的工作为单元级或片段级 C++ 到 Rust 翻译检索文档和示例 [22]，实证研究则识别了由语言特性和源-目标语义差距引起的 C++ 特定 LLM 失败 [30]。

这些研究确立了可行性，但仅靠特性支持并不能定义项目级迁移。现实的 C++ 项目将行为分布在类不变量、生命周期协议、模板工具、回调、资源和依赖构建的依赖项之中。因此，任务在于恢复哪些跨文件行为和项目假设应当在 Rust 重构中得以保留。更广泛地说，基于 LLM 的代码翻译研究报告了反复出现的语义错误、类型不匹配、API 不匹配和源-目标语义差距 [24, 32, 7]。

VI-C 智能体精化与验证反馈

智能体编码系统将代码视为可检查、修改和复查的可执行状态 [20]。迁移系统通过编译反馈、测试、FFI 验证、静态分析或等价性检查来改进生成的 Rust [8, 36, 26, 37, 31]。此类反馈暴露了许多只有在生成项目被构建或运行之后才会显现的错误。

验证和精化是对保持源结构迁移和基于 LLM 翻译的补充：构建反馈暴露缺失项和类型不匹配，测试暴露行为失败，FFI 检查比较源与翻译后的行为，静态或验证反馈可以减少不安全使用或检查等价性。然而，修复仍然受其证据的约束；即使生成项目可以执行，未测试或隐式的源义务仍可能不可见。

VII 结论

本文提出了 Req2Rust，一个项目级、基于 LLM 的 C++ 到 Rust 迁移框架。它在 MRS 中记录保留义务，综合 RDS 以指导 Rust 重构，然后通过编译器、语义和不安全缩减验证器精化初始 Rust 项目。我们在通用 C++ 项目和 OpenHarmony 模块上的评估表明，Req2Rust 在两种设置下均能生成可构建的 Rust crate，并将通用项目的测试通过率从 69.5% 提升至 91.9%，将 OpenHarmony 模块的测试通过率从 45.4% 提升至 87.9%。消融研究进一步表明，语义验证带来了大部分行为增益，而不安全缩减在不降低所观察到的测试通过率的情况下降低了不安全使用。
