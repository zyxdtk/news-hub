原标题：Meta returns to open source with Muse Glimmer, an Apache 2.0 licensed 30B parameter AI model optimized for agents — available now

中文摘要： Meta 发布了 300 亿参数的开源 AI 模型 Muse Glimmer，采用 Apache 2.0 许可证，专为在消费级硬件上运行自主 AI 智能体而优化。该模型支持本地部署，无需依赖云端，有效保护数据隐私并降低 API 成本。通过 4 位量化技术，Glimmer 可在 24GB 显存的设备上运行，并利用 DFlash 推测解码大幅提升推理速度。它在多项智能体基准测试中表现优异，标志着 Meta 重返完全开源领域，与 Google 和阿里等竞争对手展开激烈竞争。

Markdown Content:
Meta 今天发布了 Muse Glimmer，一个 300 亿参数的开放权重模型，旨在直接在消费级硬件上运行自主 AI 智能体——将通常依赖云基础设施的智能体工作负载转移到了高端 Mac 和 PC 上。

与该模型的功能同样引人注目的是它的许可方式。Glimmer 采用宽松的、行业标准的 Apache 2.0 开源许可证发布——这是该公司自 4 月份以专有的 Muse Spark 取代开放权重的 Llama 系列以来，首次进行完全开放的发布。

事实上，Muse Glimmer 今天发布时携带的许可证比 Llama 以往任何时候都要宽松。Llama 定制的社区许可证因其 7 亿月活用户的限制等条款而招致了多年的批评；而 Apache 2.0 没有此类附加条件，允许无限制的商业使用、修改和再分发。

权重现已在 Hugging Face 上可用。Wang 表示，本周将通过 Ollama、LM Studio、vLLM、SGLang、Together AI、Fireworks AI 和 OpenRouter 推出支持，未来几天内将落地优化的 llama.cpp、MLX 和 ExecuTorch 集成；Meta 的博客文章还指定 Unsloth 为本地运行时合作伙伴，并指向 PyTorch 的 TorchTitan 进行微调。该公司表示正在与 AMD、Arm、Dell、Intel 和 Nvidia 合作优化跨设备性能，并发布了涵盖自定义智能体脚手架的开发者文档。

“今天我们也在开放 Muse Glimmer 的权重，这是一个出色的 30B 参数稠密模型，可以在本地运行，”Meta 联合创始人兼首席执行官马克·扎克伯格在 X 上的一篇帖子中（使用他长期以来的账号 @finkd）写道。“很快我们还将发布 Muse Spark 1.2 的权重，这是我们最新的基础模型。Meta 是开源的坚定支持者，我为这些发布感到自豪。”

承诺发布的 Muse Spark 1.2 将是一个更大的转变：它是 Meta 仅在五天前推出的终端编码智能体 Muse Code 背后的前沿模型，直到今天，整个 Muse 系列都是专有的。扎克伯格在那次发布会上曾暗示，关于开源他“很快会有更多分享”。现在我们知道他的意思了。

对于开发者和企业来说，本地推理的实际意义远超计算发生的位置。处理文件、屏幕截图、开发环境和其他敏感上下文的智能体可以执行这些工作流，而无需不断将该信息发送到远程推理服务。本地部署还从推理循环中移除了网络可用性和按 Token 计算的 API 费用——尽管组织仍需承担硬件、电力、部署和管理成本。

围绕智能体循环构建的 30B 模型

Meta 并未主要将 Glimmer 定位为通用聊天机器人，而是围绕自主智能体执行的操作序列对其进行训练：制定计划、调用工具、解释结果、继续工作，以及在出现问题时进行恢复。

“就像大得多的模型一样，muse glimmer 可以通过规划、工具调用、检查自身结果和故障恢复，作为一个功能完备的智能体运行，”Meta 首席 AI 官 Alexandr Wang 在宣布发布的 X 上的一个帖子中写道，并补充说该模型“可以在 24GB VRAM 上运行，而不会丧失智能体的可靠性。”

根据 Hugging Face 上的模型卡，Glimmer 是一个稠密因果 Transformer，在 52 层中拥有约 296 亿个总参数，包括一个专门的约 18 亿参数的 ViT-G/14 感知编码器。它接受交错的文本和图像，生成文本，支持 100 多种语言，声明的上下文长度为 131,072 个 Token 或更多，知识截止日期为 2026 年 1 月 4 日。

这种组合旨在让智能体在推理文本和调用外部工具的同时，解释屏幕截图、图表和文档。Glimmer 提供低、中、高和超高推理设置——通过系统提示设置——因此应用程序可以根据任务调高或调低推理力度，Meta 表示它适用于包括 OpenClaw 和 Hermes Agent 在内的智能体脚手架。

该模型是 Meta 更大旗舰模型的蒸馏版：根据该公司的技术博客文章，Glimmer 使用 logit 蒸馏在 Muse Spark 的输出上进行了预训练，在具有更丰富推理轨迹的更长上下文、智能体密集型数据上进行了中期训练，然后在通用、推理、编码和智能体领域通过监督微调、策略内蒸馏和强化学习进行了后训练。

Meta 通过本地 Home Assistant 工作流演示了这一结果：在一段演示视频中，Glimmer 通过工具调用自主发现网络上的 Home Assistant 实例，查询设备 API，从头编写响应式 HTML/CSS/JavaScript 仪表板，并部署本地服务器以验证自己的工作。这比独立的问答基准测试更接近企业智能体部署的运营现实——模型必须在与外部系统交互时保持计划，然后检查其行动是否产生了预期结果。

将智能体压缩到 24GB

硬件故事是本次发布的核心。

Meta 表示，在全精度下，30B 模型需要超过 55GB 的内存——超出了任何单张消费级 GPU 的能力。

因此，该公司开发了约 4 位量化版本，将语言模型权重压缩到 20GB 以下，为运行中的智能体在内存中所需的其他部分留出了余量：KV 缓存、感知编码器和配套的推测解码模型，所有这些都可容纳在 24GB 或 32GB 的空间内。

实际上，这意味着量化版本可以在消费级机器上运行——尽管是其中高端的机器。针对 24GB 目标的 K-Quant-17GB 配置可安装在单张高端消费级显卡上，例如 Nvidia 的 RTX 3090 或 RTX 4090（两者均有 24GB VRAM），而针对 32GB 目标的 K-Quant-Dynamic 版本则与较新的 RTX 5090 的 32GB 相匹配。在 Mac 方面，Apple Silicon 的统一内存扮演了 VRAM 的角色，因此具有 32GB 或更多内存的 MacBook Pro 或 Mac Studio 可以容纳完整堆栈——Meta 在 M4 Max 和 M5 Max MacBook Pro 上运行了自己的速度测试。然而，典型的 8GB 或 16GB 笔记本电脑仍然无法胜任，而 Meta 标定为 64GB 的全精度 BF16 版本则仍属于数据中心 GPU 和顶配 Mac Studio 配置的领地。

Meta 报告称，其针对 32GB 硬件的 K-Quant-Dynamic 版本在 15 项基准测试中的平均准确率下降仅为 0.2%，针对 24GB 硬件的 K-Quant-17GB 配置为 1%。这些数据是 Meta 自己的测量结果，而非独立评估。

Meta 还使用 DFlash 推测解码来解决本地智能体的另一个大问题：延迟。较小的 DFlash“草稿”模型不再按顺序生成每个 Token，而是提出由 16 个 Token 组成的块，由主模型并行验证，从而更快地产生相同的输出。

Meta 报告称，这将 Nvidia RTX 5090 上的平均生成速度从每秒 74.9 个 Token 提高到了 233.4 个——提升了 3.1 倍。Apple M5 Max 从每秒 26.6 个提高到 50.2 个（1.8 倍），M4 Max 从 23.7 个提高到 37.8 个（1.5 倍）。测试使用批量大小为 1 和贪婪解码，Apple 系统通过 ExecuTorch 测量，RTX 5090 通过 llama.cpp 测量。

对于智能体应用而言，这些倍数比聊天应用更重要：单个用户请求可能会触发多次模型轮次、工具调用和验证步骤，在每个阶段累积的延迟会很快使原本能干的智能体变得不切实际。

Glimmer 进入竞争日益激烈的本地模型市场

Meta 并非进入一片空白的领域。开发者已经拥有此规模级别的能力强大的开放权重模型，最著名的是 Google 的 Gemma 4 系列和阿里巴巴的 Qwen3.6-27B——两者都围绕推理、多模态理解和智能体工作负载进行定位。Meta 自己的基准测试表直接与两者进行了比较。


Muse Glimmer 基准测试比较图。图片来源：Meta

Glimmer 在多项智能体测试的三方比较中领先，包括 MCP Atlas（75.5）、DeepSearch QA（74.6）、τ³-Banking（23.5）、WildClawBench（47.6）和 GAIA2（43.3）。在 Meta 的评估中，它在 SWE-Bench Pro 上得分为 51.2，而 Gemma4-31B 为 36.9，Qwen3.6-27B 为 50.2。

但 Glimmer 并没有横扫全场。Qwen 在 OSWorld-Verified（75.6 对 Glimmer 的 65.9）、TerminalBench 2.1（60.7 对 51.7）、SkillsBench、GDPval-AA（1141 对 953）以及大多数多模态基准测试上领先于 Meta 自己的比较。在 SWE-Bench Verified 上，Glimmer 的 76.0 略低于 Qwen 的 77.2。Gemma 在 GPQA Diamond 和 Humanity's Last Exam 上领先。

客观地看，这些数字使 Glimmer 作为一个专门的本地智能体模型比作为全面性能领先的证据更有趣。对于企业开发者来说，实际问题是其智能体可靠性、量化质量、工具兼容性和解码速度的组合是否能从基准测试转化为持续的真实世界工作流。

Meta Glimmer 增加了美国公司仍然数量稀少的真正开放的前沿级模型阵容。

在过去的两年里，中国公司设定了开源 AI 的步伐，DeepSeek、阿里巴巴的 Qwen 团队、Moonshot AI 的 Kimi、智谱的 GLM 和 MiniMax 以西方实验室无法匹敌的节奏在 MIT 和 Apache 2.0 许可证下发布前沿级开放模型。

使用数据反映了这一点：到 2026 年 5 月，中国开放权重模型占 OpenRouter 上消耗的所有 Token 的约 61%，使用量排名前五的模型中有四个来自中国实验室——而 Meta 的 Llama，之前的开放权重领导者，则完全跌出了排行榜。

美国的反例仍然屈指可数：OpenAI 的 gpt-oss-120b 和 gpt-oss-20b，于 2025 年 8 月在 Apache 2.0 下发布，是该公司自 GPT-2 以来的首个开放权重；Google 的 Gemma 系列，虽然是开放权重，但在 Google 自己更严格的自定义许可下发布，而不是 OSI 批准的许可；以及 Thinking Machines 的 Inkling。

Glimmer 引发了与 gpt-oss 最直接的比较：两者都是 Apache 2.0，都提供可调的推理力度，并且都针对自托管部署。

但 gpt-oss 模型是纯文本的稀疏混合专家设计，主要为推理和工具使用而构建——gpt-oss-20b 可容纳在约 16GB 内存中，而 gpt-oss-120b 则针对单张 80GB 数据中心 GPU。

Glimmer 划定了不同的领域：一个具有原生视觉输入的稠密模型，围绕智能体循环进行端到端训练，附带为 24GB 消费级机器调整的量化变体和推测解码草稿模型。

如果扎克伯格兑现开放 Muse Spark 1.2 权重的承诺，Meta 将把一个真正的美国旗舰前沿模型投入开放流通——这是任何美国实验室在该层级上都没有做过的事情。

安全仍然是部署架构的一部分

赋予本地模型访问工具的权限会产生与部署本地聊天机器人不同的安全问题——而 Meta 自己的安全数据显示，Glimmer 并非在所有方面都比其同行更强。

在 CI Memories（违规率越低越好的隐私基准测试）上，Glimmer 记录为 26.4，而 Gemma 为 12.1，Qwen 为 53.4。在 Siren AgentDojo（提示注入测试）上，Glimmer 显示出 28.4% 的攻击成功率，而 Gemma 为 25.6%，Qwen 为 40.3%——同时在这三者中发布了最高的实用性分数 94.2。

Meta 表示，它在其高级 AI 扩展框架下对 Glimmer 进行了评估，并确定该模型不符合该框架对“前沿 AI”的定义，因为它通常不如 Muse Spark 强大。其防范团队在化学/生物、网络和失控类别中将 Glimmer 评估为中等或更低风险——后两者是根据 Glimmer 总体上弱于 Muse Spark 1.0 这一事实推断出来的，后者获得了相同的评级。

尽管如此，该公司仍建议将 Glimmer 作为带有护栏的更广泛系统的一部分进行部署，包括对不可逆操作的人在回路确认。这一警告对于本地智能体尤为重要：将数据保留在设备上可减少对云基础设施的暴露，但本地执行本身并不能解决提示注入、过度权限或智能体采取意外行动的问题。

Apache 2.0 权重和快速增长的运行时生态系统

Meta 正在发布全精度 BF16 权重、两个 4 位量化变体、DFlash 草稿模型和感知编码器——全部在 Apache 2.0 下。可下载的模型没有附带 Meta API 价格，这使得总成本取决于本地硬件或开发者选择的任何第三方托管。采购团队需要注意的一个细微差别是：与大多数“开源”模型发布一样，开放的是权重——Meta 并未发布训练数据或训练代码。

更广泛的影响是，Meta 将开发者工作站视为自主智能体的可靠部署目标，而不仅仅是试验较小语言模型的地方。Glimmer 的 30B 大小和 24GB 目标使这一主张在高端消费级硬件上触手可及，而 Apache 2.0 许可证赋予开发者——及其法务部门——修改和部署它的非凡自由。

下一个测试是它的基准测试优势能否在更混乱的真实软件存储库、企业工具和长时间运行的智能体会话条件下存活下来。如果能，Glimmer 最重要的部分可能不是另一组基准测试分数——而是一类以前预期存在于云 API 之后的智能体，可以越来越多地生活在开发者办公桌下的机器上，并在那里工作。
