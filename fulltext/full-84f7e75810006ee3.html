Across both, context length, multimodal-input support, and structured-output reliability vary by family and model size, and the model landsc

ape evolves on a fast timescale of months. The frontier models share a common three-stage training pipeline: self-supervised pretraining on raw text, supervised fine-tuning on instruction-response data, and preference-based alignment. In the pretraining stage , the model learns broad statistical patterns of language by minimizing the next-token loss in ( 2 ) over a large unlabeled corpus. This gives general linguistic competence and world knowledge but targets no specific task or instruction format, so a pretrained-only model continues text fluently yet may not reliably follow instructions, answer in the expected format, or refuse unsafe requests. Supervised fine-tuning (SFT) then adapts the pretrained model to instruction following using curated prompt-response demonstrations [ 75 ] , updating the parameters by minimizing the token-level cross-entropy between predicted and target responses. SFT lets LLMs give structured, formatted answers and is a prerequisite for the tool calling, structured outputs, and conversational behavior agentic systems rely on. A final alignment stage optimizes the SFT model with human preference feedback so responses better match expectations for helpfulness, safety, and reliability [ 62 ] . The most common implementation is reinforcement learning from human feedback (RLHF) , where a reward model trained on human preference comparisons is used to optimize the LLM through reinforcement learning. A related approach, reinforcement learning from verifi

able rewards (RLVR) , replaces the learned reward model with an automatic verifier that scores each response against a ground-truth criterion [ 39 ] . Note that alignment improves how the model behaves, but does not by itself ensure numerical correctness or constraint satisfaction, so in smart grid workflows it should be treated as a behavior layer on top of trusted solver and verification components. 2.3 The Solver-grounded Design Rule The central design rule of this paper is that LLMs and agents should not be treated as sources of numerical truth in smart grid applications. Instead they act as interfaces, task planners, and orchestrators around trusted computational tools. These tools are central to safety-critical power systems practice, such as operating and planning studies already rely on power-flow solvers, OPF solvers, economic-dispatch optimizers, forecasting models, and simulators to enforce physical laws, operational limits, and feasibility. In current workflows, engineers configure cases, run these tools, inspect convergence and constraint violations, iterate across scenarios, and translate the outputs into operational reports. LLMs fit tool calling naturally because they can map natural language requests into structured tool inputs, select and sequence the right solver or data API, interpret logs and outputs, and explain results while leaving numerical computation to verified softwares. This is the boundary of the solver-grounded regime rather than an exception: absent a trusted tool, the system should report predictions with their validation evidence and uncertainty, not as solver-verified quantities. 2.4 Where LLMs and Agents Add the Most Value The solver-grounded rule of Section 2.3 guardrails what LLMs should not do in smart grid tasks. In practice, there are several recurring bottlenecks in solver-grounded smart grid workflows: data preparation, model specification, tool-run configuration, failure detection, scenario iteration, and technical reporting and interpretation. We do not propose these as a formal taxonomy but as a high-level synthesis of workflow patterns that motivate the observations and case studies in Section 6 . First, bottlenecks live around rather than inside the solver. Data preparation, model setup, iteration, and reporting consume most expert time per scenario, while the solver call i

s fast. This supports positioning the LLM as an interface and orchestration layer rather than a numerical engine. The PFAgent case study (Section 6.3 ) shows the split: PandaPower’s Newton-Raphson solver computes the operating point, while the LLM parses multi-step queries, selects and sequences tools, tracks network state across turns, and synthesizes outputs into operator-readable responses. Second, iteration cost compounds with case complexity. As grid studies grow from one case to many scenarios, contingencies, assets, and operating conditions, the burden shifts from solving one well-posed problem to repeatedly specifying tasks, selecting tools, checking inputs, interpreting outputs, and revising the workflow. Here LLMs and agents add value as planners and orchestrators, since they decompose a request into subtasks, identify the required data and tools, sequence tool calls, and adapt to intermediate results, leaving numerical computation to trusted solvers. The GridDebugAgent case study (Section 6.4 ) shows this by automating the diagnose-act-verify loop while preserving solver-grounded correctness. Third, verification itself is a bottleneck. The final output often combines numerical results, explanations, diagnostics, and recommendations. Even when the solver call is correct, the agent can misreport a value, omit a violation, or overstate a result’s validity. A solver-grounded design therefore separates three functions: i). the LLM interprets, plans, orchestrates, and ex

plains, ii). trusted tools produce the numerical evidence, and iii). a verification gate decides whether the final answer is safe to communicate. the model to produce intermediate reasoning steps before the final answer [ 76 ] . Because generation is sequential, the steps it writes become context for the final answer, so it decomposes a multi-step problem into sub-steps and builds the answer on its own reasoning. Making the steps explicit lets a reader follow how the answer was reached and improves quality on multi-step tasks. Fig. 4 illustrates CoT prompting on a power flow over-voltage diagnosis. In smart grid applications, CoT helps when the LLM explains solver outputs or supports human review. For a bus over-voltage, a CoT response can identify the violated limit, locate the affected bus, connect it to causes such as excessive local generation, and suggest actions such as adjusting inverter setpoints or transformer taps. Like the other techniques, CoT does not guarantee correct reasoning. It can produce plausible reasoning while making an arithmetic error or recommending an infeasible action, so the final response must still be checked against trusted computations and constraints. In power systems, CoT has been used within LLM assistants for dispatch operations [ 12 ] . The pattern fits workflows that split into many independent subtasks whose results combine into one answer. In smart grids, N − 1 N{-}1 contingency screening is a natural example. It should be treated as a structured system component, not just a longer conversation history [ 70 , 64 , 63 ] . It includes short-term memory , holding state within a single trajectory, and long-term memory , which carries across trajectories and holds episodic and semantic memories. Short-term memory holds the working state within a single task: a scratchpad recording the current goal, steps taken, tool outputs received, and intermediate conclusions. Each reasoning step reads from it and writes back new information. Because it persists only for one trajectory, it is most exposed to context-window pressure: when the working state grows too large, items can be dropped or paraphrased, silently corrupting the reasoning [ 63 ] . In smart grid workflows, it keeps operational details such as the active network case and the latest solver output accessible across steps within a task. Long-term memory carries state across tasks, typically as an external store [ 63 ] , with two subtypes. Episodic memory is the agent’s logbook of past runs, storing the task, tool calls, observations, failures, and the final verified outcome of each [ 70 ] . Semantic memory stores patterns and rules distilled from many runs: reusable guidance (“always verify solver

status before reporting”), report templates, common causes of non-convergence, and standard corrective actions [ 64 ] . It gives consistency across tasks, but a faulty rule generalized from one episode propagates to every later run, so updates must be cautious. Verification status is an important filter: values from runs that failed verification should never be promoted to semantic memory as ground truth. 4.5 Frameworks and Tools for Building Agents Frameworks for agentic AI provide the engineering layer for defining agents, registering tools, managing memory, and deploying workflows.
