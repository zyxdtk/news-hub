MCP 已四次收紧认证规则，旧服务器恐难跟上

📅 2025-03-26 📄 VentureBeat AI 🔗 原文链接

原标题：MCP has tightened its authentication rules four times. Older servers may not have kept up.

中文摘要： MCP 协议自发布以来已四次收紧认证规则：从最初无认证要求，到引入 OAuth 2.1 框架、将服务器定义为 OAuth 资源服务器、新增 CIMD 注册方式，再到 2026 年 7 月正式弃用 DCR。OWASP 与 NSA 警告令牌管理和身份验证是重大盲区，Unit 42 测试显示五个互联 MCP 服务器的攻击成功率达 78.3%。文章建议采用身份感知网关、短时效最小权限令牌与集中治理，并按规范演进方向而非当前快照进行构建。

Gartner 预测，到 2026 年底，40% 的企业应用将包含面向特定任务的 AI 智能体，而 1 月份这一比例还不到 5%。该公司将智能体 AI 监管列为 2026 年首要网络安全趋势，并指出机器行为体的身份注册和基于策略的授权是企业准备不足的具体领域。

这正是每位 CTO 目前做出 Model Context Protocol（MCP）部署决策的背景。这种将智能体连接到真实系统的协议，其认证故事仍在书写之中，以每隔几个月发布一次的规范修订形式呈现。

MCP 认证模型的实际演进

官方 MCP 规范变更日志显示了五个不同的阶段，而非一次性的大型安全修复：

版本 认证方面的变化
2024-11-05（发布） 没有授权框架。认证完全留给实现者自行处理。
添加了基于 OAuth 2.1 的全面授权框架。
2025-06-18 将 MCP 服务器归类为正式的 OAuth 资源服务器；要求使用资源指示器（RFC 8707），防止恶意服务器获取本应发给其他服务的令牌。
2025-11-25 添加 OAuth 客户端 ID 元数据文档（CIMD）作为推荐的注册方法，与动态客户端注册（DCR）并行。
2026-07-28 弃用 DCR，转而支持 CIMD；要求客户端验证 iss 参数（RFC 9207）；被称为发布以来最大的一次修订。

MCP 发布时没有任何认证要求，此后的每一次修订都在逐步补回严谨性。任何在第一年构建的服务器很可能仍带着规范早已摒弃的假设。方向是一致的：趋向正式的 OAuth 模式，远离轻量级、由实现者自行选择的注册方式。

OWASP 和 NSA 的警告

OWASP MCP Top 10 将令牌管理不当和密钥暴露列为最高优先级类别：硬编码的凭据和存储在模型内存中的密钥可能暴露整个互联环境，且通常可以通过提示注入检索到。

NSA 2026 年 5 月的指南提出了一个值得深思的观点（与 OWASP 清单对照来看）：OWASP 的十个风险类别中，只有两个存在于智能体读取并执行的文本中。其余八个——包括凭据、范围和身份——都位于协议完全没有内置约束的基础设施中。MCP 标准化了智能体如何发现和调用工具，但从未标准化如何证明调用者是谁，或他们被允许接触什么。

影响范围真实存在

Palo Alto Networks 的 Unit 42 在现实规模下测量了实际发生的情况：在他们的测试中，将五个 MCP 服务器连接到单个 AI 智能体产生了 78.3% 的攻击成功率。五个互联服务器并非边缘案例，对于任何已超越单一概念验证阶段的团队来说，这是再平常不过的一周。

其机制是级联信任。一旦智能体将某个服务器的输出视为可信上下文，被攻破的服务器就可以注入指令，这些指令会随之传播到之后的每一次工具调用中，包括调用那些本身从未被攻破的服务器。

两种部署场景，两种不同姿态

防火墙后的内部工具。 暴露风险较低，但并非为零。微软在其 Inside Track 博客中描述的内部 MCP 治理，即使对仅限内部的流量也颁发短时效、最小权限的令牌，理由是“内部”不等于“可信”。

向客户暴露端点的远程服务器或多租户 SaaS。 风险最高。微软的 Azure 指南建议使用身份感知网关，拒绝任何缺少有效的、绑定受众令牌的调用，外加一个固定工具定义的注册表，这样“rug pull”（受信任的依赖项悄然改变行为）就能被漂移检测捕获，而不是在生产环境中才被发现。

应做与不应做

应做：
- 将每个 MCP 服务器视为验证令牌的 OAuth 资源服务器，这是规范自 2025 年 6 月以来的自身方向
- 严格限定令牌范围并保持短时效；微软的指南特别警告不要“在只读权限就够用的情况下授予完整邮箱访问权限”
- 现在就验证 iss 参数，抢在其成为强制要求之前

不应做：
- 假设 DCR 是安全的长期选择；它已于 2026 年 7 月被正式弃用
- 在服务器启动时缓存凭据，而不是在调用时获取；存在于进程内存中的令牌无法被有效撤销
- 在未将新 MCP 服务器注册到可治理之处的情况下就将其接入

集中式还是逐服务器：执行层面的问题

逐服务器执行 身份感知网关
跨服务器一致性 取决于每个开发者 天然统一
检测被攻破的服务器 仅当该服务器日志记录良好时才行 网关可固定工具定义并在漂移时告警
最佳适用场景 单一内部工具 超过少数几个服务器的任何部署

微软和 NSA 各自独立地得出了相同的答案：将身份、范围和审计日志推送到每个服务器前面的一个层，而不是单独信任每个服务器。

为方向而构建，而非为快照

MCP 授权模型自发布以来在每次修订中都有变化，且更多强化措施已有信号。稳定的是方向：正式的资源服务器模式、明确的颁发者验证，以及集中治理优于临时信任。对于正在决定如何接入下一个 MCP 集成的 CTO 来说，部署速度与身份治理之间的差距才是真正的项目本身，而不是它的脚注。
