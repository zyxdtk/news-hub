KVM编码代理：资源受限下的隔离与用户控制

Yutaka Nagashima
捷克科学院计算机科学研究所

摘要

编码代理通常需要广泛的权限才能进行高效的开发工作，但授予这些权限可能会暴露用户的数据和基础设施。现成的云工作区可以帮助限制代理活动，但依赖特定提供商的平台可能导致供应商锁定并降低用户控制力。研究人员和工程师因此必须在可用的财务、计算和人力资源范围内，平衡代理自主性、强制隔离与用户控制。我们分析了这些权衡，并提出了 KVM-Agent——一个自动化大多数设置和配置步骤的开源实现。它在可替换的 Ubuntu 虚拟机（VM）内部赋予代理广泛的权限，同时将主机管理保留在这些虚拟机之外，并支持多种编码代理应用、模型服务和远程任务委派。该方法保留了熟悉的工作流程和用户选择，其代价是虚拟机资源、维护，以及来自虚拟机内可访问的密钥和被允许的网络访问的残余风险。

I 引言

在理想的世界中，每个人都能使用安全、经济实惠、开源、易用且高效的编码代理，同时不会失去对自己数据和计算基础设施的控制。在实践中，这些目标涉及权衡。广泛的权限使开发工作成为可能，但增加了错误或被攻陷可能造成的损害。云工具和模型服务可以减少本地运营需求并提供可扩展性，但引入了外部依赖。熟悉的开发环境支持现有工具和工作流程，但在用户控制的基础设施上部署和维护它们需要计算资源和人力。

代理可能需要安装编译器、构建一个不熟悉的代码仓库，或修复依赖项。编码代理通过代理-计算机接口 [1] 执行此类操作，对执行环境行使权限。错误、恶意依赖项和间接提示注入 [2] 可能重定向这种权限。在普通工作站账户中运行这些操作，会使该账户可访问的文件和会话暴露在外；而要求对每条命令进行人工批准，则会使进度依赖于用户的反复干预。与此同时，需要大量安全管理、特定商业服务或专用新硬件的部署方案，对于资源紧张的小型研究团队而言可能并不现实。

在本文中，我们介绍 KVM-Agent 以解决以下问题：

研究人员和工程师如何在保留工具和基础设施选择权、控制运营成本的同时，赋予编码代理开发工作所需的权限？

KVM-Agent 是现有编码代理应用的一个操作层包装。它配置一个图形化的 Ubuntu 虚拟机（VM）。我们将虚拟机内的操作系统（OS）称为客户机，将运行虚拟机的操作系统称为主机。代理在客户机内使用具有无密码 sudo 权限的账户。用户则保留主机虚拟化控制和专用的恢复密钥。该设计还支持编码代理应用和大语言模型（LLM）服务提供商的自主选择、远程操作，以及可选的向另一台机器委派任务。

我们的贡献包括：对在资源限制下部署编码代理的这些权衡的分析（第 II 节），以及由此产生设计的开源参考实现（第 III 节）。该实现自动化了大多数设置和配置步骤，仅在需要用户特定选择、凭据或信任决策时才需要手动输入。

II-A 自主性与隔离

我们的目标是在可替换的项目专属环境中授予广泛权限，同时限制对可能包含管理凭据及其他与项目无关数据的主机资源的访问。虚拟机内的无密码 sudo 允许系统级安装和修复；我们接受客户机被攻陷时会暴露项目的代码、数据、会话及所提供凭据这一事实。为限制影响范围，我们的预期部署方式是为每个项目专门分配一个或多个虚拟机，尽管实现本身并不强制执行此约定。这种权衡适合源代码保密性并非主要要求的研究项目。

便利的交互会带来额外通道：主机-客户机剪贴板共享、导出的文件、远程编辑器转发和工作节点访问，都会使数据或权限跨越边界。这些通道在提升便利性的同时也增加了暴露面。因此，该设计区分了在客户机之外强制执行的限制与客户机本地的默认设置及明确的用户实践。相关考量包括网络可达性、凭据的存放位置、输出审查、用户对外部操作的控制，以及隔离机制的选择。

II-B 提供商依赖与用户主权

我们旨在帮助用户保留主权：即实际选择和管理执行基础设施、编码代理应用、LLM 服务及数据目的地的能力。开源虚拟化栈可在用户控制的硬件上运行，客户机既可容纳专有应用，也可容纳开源替代方案。开放权重推理是一种选项，而非要求，也不保证同等能力。使用托管 LLM 服务可以减少本地计算和维护需求，但会将提示和上下文发送给提供商，并可能产生服务费用。在本地运行模型则将计算和维护负担置于用户身上；有限的硬件可能制约模型选择，进而影响任务质量。支持多种应用保留了选择权，但可能增加维护工作量，尤其是当它们的软件依赖或配置要求不同时。

II-C 功能性与运营成本

我们旨在保持设置和日常操作的可管理性，同时支持标准开发工具、远程访问和工作节点委派。这些功能带来不同的成本：完整的 Ubuntu 客户机需要计算资源和软件维护，而委派则增加了需要管理的机器和访问权限。该设计接受这些成本，以适应项目特定的软件并利用现有机器上的计算能力。为限制管理工作量，重复性的设置和配置步骤应实现自动化，操作和恢复流程应明确化。用户特定配置、身份验证和信任决策仍需手动输入。

II-D 部署方案比较

表 I 将各种替代方案与上述目标进行了比较。专用裸机消除了客户机到主机的逃逸路径并避免了虚拟化开销，但恢复操作必须在被攻陷的操作系统之外进行。当有备用硬件可用时，它仍是一个可行的选择，尽管物理隔离并不限制网络行为，也无法保护所提供的凭据。

专用 Linux 账户以独立的用户身份运行代理，文件访问由 Unix 权限 [3] 约束。它共享主机内核；不授予 sudo 会限制自主的系统级安装和修复，而授予无限制的 sudo 则会使基于账户的隔离失效。

容器在共享主机内核的同时增加了命名空间和资源控制 [4, 5]。Docker 和 Podman 都支持 rootless 操作；Podman 的常规 CLI 是无守护进程的 [6, 7]。

我们选择 KVM/QEMU 主要是为了解决自主性与隔离的矛盾（第 II-A 节）。KVM [8] 在 Linux 内核中提供硬件辅助虚拟化，QEMU [9] 提供虚拟硬件，libvirt [10] 管理虚拟机配置、生命周期、存储和网络。代理可以在客户机内管理完整的开发操作系统，而用户在其外部保留主机管理、恢复和资源控制。与为每个项目分配一台物理机相比，独立的虚拟机让用户能够跨项目共享硬件，并在项目环境之间切换。受信任的主机保留对资源分配和替换被攻陷虚拟机的控制。主机管理的网络可以将物理网络凭据（如 Wi-Fi 密码）保留在虚拟机之外。这些好处的代价是虚拟化开销和主机软件栈的维护。

开源虚拟化栈还通过使执行环境独立于特定编码代理应用或模型提供商，支持用户主权（第 II-B 节）。在功能性与运营成本方面（第 II-C 节），完整的客户机 OS 兼容现有开发工具，而我们的设置自动化和恢复流程旨在使部署和管理在现有硬件上保持可管理。

III-A 自主性与隔离

III-A1 威胁假设与风险覆盖

对于自主性目标（第 II-A 节），虚拟机边界将客户机权限与主机 OS 资源及无关的文件和凭据分离。我们假定存在任意的客户机命令（包括以 root 身份执行）；客户机内的项目、会话和所提供的凭据均处于暴露状态。用户、物理机器、固件、主机内核、KVM、QEMU、libvirt 和管理工具构成受信任基础。OpenAI 和 Anthropic 提供操作系统强制的沙箱，其覆盖范围取决于应用、配置和集成路径 [12, 13, 14]。对于主机隔离，我们依赖 KVM/QEMU 而非这些特定应用的沙箱，使隔离机制独立于所选的编码代理应用（第 II-B 节）。

我们默认保留互联网访问，以便代理能够获取软件、依赖项和数据。默认情况下，客户机防火墙通过阻止私有和链路本地 IP 地址范围来限制对本地设备和服务的访问。在客户机内拥有 root 权限的代理可以更改或禁用这些规则。模型提供商和编码代理应用开发者提供的安全保障可对代理行为形成补充性检查。旨在抵御客户机被完全攻陷的网络限制需要在客户机之外强制执行，且策略需适应部署的网络拓扑结构以及代理需要访问的服务。用户可以配置主机强制执行的出口策略，或在任务允许时从主机禁用客户机网络。

表 II 总结了威胁场景、相应的控制措施和用户实践，以及残余暴露。虽然虚拟化漏洞利用和侧信道攻击仍是残余风险，但我们省略了主机目录共享、主机容器套接字和物理设备直通，以限制通往主机权限的路径 [15]。

III-A2 交互与外部权限

如前所述，我们假定客户机虚拟机可能被完全攻陷；然而，代理仍需访问在线服务（包括付费服务）。因此，我们将客户机服务访问与账户管理及恢复相分离。GitHub、OpenAI 和 Anthropic 的账户密码、通行密钥、恢复密钥和管理浏览器会话保留在受信任的主机或远程控制器上（图 2）。在支持的情况下，跨设备授权在用户于受信任设备上登录的同时授予客户机服务访问权；Codex 需要启用设备代码身份验证 [16, 17, 18]。然而，客户机会接收访问/会话令牌（可能是刷新令牌）或任务 API 密钥；在客户机内拥有 root 权限的攻击者可以窃取并使用它们。在支持的情况下，应向客户机提供作用域狭窄、可撤销、生命周期短的任务凭据。对于 OpenAI 和 Anthropic 服务，可以通过无付费超额的订阅式访问，或在可用时受提供商强制支出上限约束的 API 访问来降低财务风险。仅靠预算警报无法阻止使用，且上限的强制执行因产品和套餐而异 [19, 20, 21]。用户应从受信任设备管理计费、权限和使用限额；客户机凭据不得拥有更改这些设置的权限。在"每个虚拟机一个项目"的约定下，GitHub 细粒度令牌可限定于该项目的代码仓库和所需权限，并设置有效期 [22]。分支保护和人工审查提供额外控制。剪贴板共享支持将提供商登录 URL 传输至受信任浏览器的常见工作流程，但也可能将主机剪贴板内容暴露给客户机。根据我们的经验，这种便利性证明了保留剪贴板共享的合理性。

III-B 提供商依赖与用户主权

对于主权目标（第 II-B 节），独立于编码代理应用来配置执行环境保留了应用和提供商的选择权。默认情况下，安装程序会安装 Codex、Claude Code、OpenCode、Aider、GitHub CLI 和 Ollama。一些服务将特定功能保留给付费套餐，但预装的替代方案使切换应用或提供商更加容易，并降低了对任何单一供应商的依赖。对于拥有充足计算资源的用户，Ollama 支持在客户机内进行模型推理，使推理输入保持本地化，避免对外部 LLM 服务的依赖。参考实现支持无 GPU 直通的 CPU 推理。使用托管模型则会将计算转移到别处，并将配置的项目上下文发送给该服务。

III-C 功能性与运营成本

为解决运营目标（第 II-C 节），KVM-Agent 自动化了大多数设置和配置步骤，并提供用于恢复、远程访问和在工作者虚拟机上运行作业的工具。用户特定选择、凭据和信任决策仍需手动输入。

III-C1 配置与恢复

安装程序根据 Ubuntu 的签名校验和验证 Ubuntu 镜像，创建带有包含初始配置的临时磁盘的虚拟机 [23]，并安装桌面和开发工具。主机会检查配置和所需的重启是否完成，删除缓存的设置数据，并在删除前确认配置磁盘已断开连接。版本记录有助于诊断，但上游安装程序的更新使逐字节复现无法实现。恢复访问使用每个虚拟机专用的 SSH 密钥，私钥保留在主机上。用户在替换虚拟机之前应审查并导出所需结果。在怀疑被攻陷后，用户应使用受信任的主机或控制器撤销或轮换在客户机内使用的服务凭据；删除虚拟机并不会撤销被盗的令牌。

III-C2 远程访问与持久会话

基本设置在单台计算机上运行；远程访问为可选项。对于拥有多台计算机的用户，笔记本电脑可作为控制器，控制运行在性能更强的台式机上的虚拟机（图 2）。客户机内置 tmux，可在远程连接中断时保持终端会话运行，允许用户重新连接到正在进行的工作 [24]。若客户机重启，这些会话将终止。OpenSSH 提供经过身份验证的远程终端访问，而 Tailscale 通过加密的专用网络连接控制器和客户机 [25]。物理虚拟机主机保留在该专用网络之外。与上述在线服务类似，用户通过在受信任主机或控制器上的浏览器中打开客户机的 Tailscale 登录 URL 来授权客户机，将账户凭据和管理浏览器会话保留在客户机之外。Tailscale 简化了连接设置，但引入了对其托管协调服务的依赖。自管理的 WireGuard 是一种需要更多设置工作的替代方案 [26]。用户授权设备并配置访问规则，允许控制器连接到客户机，同时阻止客户机向控制器和无关设备发起连接 [27]。用户必须将默认的"允许所有"策略替换为由接收方设备独立于客户机设置强制执行的规则；安装程序不会配置此策略。这些规则仅管理专用网络；通过其他网络的访问需要单独的控制。KVM-Agent 包含一个将 macOS 计算机用作受信任远程控制器的设置脚本。我们已测试过此配置。

III-C3 管理器-工作者执行

拥有备用计算机的用户可能希望卸载长时间运行的构建或测试，同时在主虚拟机中继续开发。在这种可选安排中，主虚拟机充当管理器，通过 OpenSSH 向其他机器上的工作者虚拟机提交作业（图 2）。在我们的部署中，我们配置管理器访问工作者虚拟机内具有无密码 sudo 的账户，用于软件安装、依赖修复和以客户机 root 身份执行作业。用户保留对物理主机的管理权，并将恢复密钥保留在这些主机上。对于构建和测试作业，模型服务令牌可保留在管理器上，而主账户凭据保留在受信任的主机或控制器上。专用网络的访问规则应允许管理器连接到工作者并接收回复，同时阻止工作者向管理器、控制器或无关设备发起连接。由于被攻陷的管理器也可以控制其授权的工作者，用户应将管理器及其工作者专用于同一项目。为加速 KVM-Agent 下一版本的开发，我们使用此管理器-工作者设置，在托管于较旧实验室计算机上的三个虚拟机中并行运行独立的开发和测试任务。

图 2 架构要素说明： Tailscale 专用网络；受信任的远程控制器（浏览器登录；SSH 密钥；macOS）；基于 Tailscale 的 OpenSSH；WireGuard 传输；虚拟机主机位于专用网络之外；管理器 VM（代理+工作者；SSH 密钥；具有无密码 sudo 的账户）；工作者 VM（远程工作；构建和测试；具有无密码 sudo 的账户）；作业/查询；状态/日志和结果；主机 A（KVM/libvirt 控制；恢复密钥保留在主机上）；主机 B（KVM/libvirt 控制；恢复密钥保留在主机上）；用户配置的策略阻止反向连接发起；每个物理主机保留独立的恢复访问。

图 2：远程控制与委派。实线箭头表示 SSH 发起；虚线箭头表示回复。控制器和客户机加入使用 Tailscale 建立的专用网络；物理虚拟机主机不加入。提供商账户管理和控制器密钥保留在控制器上；恢复密钥保留在各主机上。管理器持有工作者访问密钥。

IV 相关工作

SWE-agent 研究代理-计算机接口 [1]；OpenHands 集成了代理开发与沙箱执行 [28]。Firecracker 面向无服务器工作负载 [29]，而 Docker Sandboxes 为编码代理提供 microVM 内的 sudo 以及主机端的网络和凭据控制 [30]。Anthropic 也描述了 Cowork 的基于虚拟机的代码执行 [31]。KVM-Agent 建立在现有虚拟化技术之上，自动化了用户管理的图形化 Linux 工作流程，支持编码代理应用、模型服务和可选远程执行的多种选择。Nitro 隔离引擎为指定的虚拟机管理机制提供形式化保证 [32]；seL4 在明确假设下具有机器检验的内核证明 [33, 34]。Agentic-seL4 提出了具有动态权限和信息流控制的代理沙箱 [35]；其规划的保证与已确立的内核结果有所不同。这些关于更强隔离保证的工作与我们对部署、提供商选择和运营成本的关注形成互补。

KVM/QEMU 在 KVM-Agent 中引入的性能开销是一个潜在的关注点。独立研究报告 KVM 在 Linux 内核编译方面达到裸机性能的 95.9% [36]，SPEC ACCEL 1.2 OpenMP 工作负载的开销为 6% [37]。虽然这些研究并未评估 KVM-Agent 本身，但其结果表明虚拟机隔离对此类工作负载可能仅带来适度的执行开销。

V 讨论与结论

本文研究了部署编码代理中的三个权衡：代理自主性与隔离、提供商依赖与用户主权，以及功能性与运营成本。我们提出了 KVM-Agent 作为由此产生设计的开源参考实现。代理管理可替换的项目虚拟机，而用户保留主机管理、恢复和账户控制。该实现保留了编码代理应用和模型服务之间的选择，支持熟悉的开发工具和可选的远程执行，并自动化了大多数设置和配置步骤。这种平衡仍需要虚拟机资源、软件维护以及用户对凭据和网络访问的决策。然而在实践中，我们发现这些需求对于我们的小型研究团队而言是可管理的。我们已在四个项目中使用了 KVM-Agent：ProofStudio [38]、AbductionProver 的神经化改造 [39]、一个跨证明器的证明自动化工具，以及 KVM-Agent 本身的下一个版本。在这些项目中，我们使用商业 LLM 服务，同时将代理对我们机器的权限限制在项目特定的虚拟机中。我们保留了切换到托管在捷克学术基础设施（e-INFRA CZ [40]）上的模型的选项，以减少对商业提供商的依赖。

未来的工作将评估设置和恢复的工作量、执行性能，以及切换编码代理应用或模型提供商所需的成本。还将评估在客户机被完全攻陷情况下的主机和网络控制。这些评估将有助于完善 KVM-Agent 中所体现的设计选择——它提供了一种高度自动化的方式来部署自主编码代理，同时在资源受限条件下保留用户控制。
