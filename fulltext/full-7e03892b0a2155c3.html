At each decoding round the drafter proposes a sequence (or, in tree-based methods, a small tree) of candidate continuation tokens; the target model then scores every candidate position in a single parallel forward pass and accepts the longest prefix (or root-to-leaf path, for a tree) whose tokens match what the target model itself would have sampled. Because the accepted tokens are guaranteed to come from the target model’s own distribution, speculative decoding is lossless up to floating-point tie-breaking : it changes only the number of target-model forward passes needed to produce a given output, not the output distribution itself. Tree-attention verification (Section 3.5 ) reorders bf16 reductions relative to token-serial decoding, which could in principle add further divergence; Section 4.5 shows it does not, at the same benign tie-level rate as chain-style verification, which is what substantiates the losslessness claim for trees specifically. st heap over factorized marginals DDTree (Ringel and Romano, 2026 ) builds a draft tree directly on top of a block-diffusion drafter’s per-position marginals. Under a fixed node budget n n , DDTree maintains a max-priority queue (heap) keyed by cumulative path log-probability: starting from the root’s children, it repeatedly pops the globally highest-cumulative-log-probability unexpanded leaf, adds it to the tree, and pushes its own children (again scored by the drafter’s per-position marginal at the child’s depth) onto the heap, until the node budget is exhausted. Because DDTree’s per-depth distributions are read directly from the drafter’s marginals L i base L_{i}^{\text{base}} , this scoring is path-independent : two different candidate ancestors at the same depth would offer the identical menu of children and child scores, since the marginal drafter never conditions on which tokens are actually chosen along the path. The resulting tree is prefix-closed by construction (every node’s parent appears earlier in the pop order) and is verified in a single target-model forward pass using an ancestor-only causal attention mask — the standard tree-attention verification mechanism used by DDTree and SpecInfer (Miao et al., 2024 ) alike, which we reuse unmodified (Section 3.5 ). 2.5 CaDDTree: cost-aware adaptive budget DDTree’s node budget n n is a fixed hyperparameter, chosen offline per task. Batching nodes into one launch, the obvious fix, backfires: best-first exists to grow the tree deep along the single highest-scoring path, whereas a batched depth level spends the fixed node budget on shallow breadth before best-first order can choose what to extend — forfeiting the depth the conditional score depends on (its advantage comes from conditioning on the realized path, which only a deep path exercises). Speculative decoding was introduced by Leviathan et al. ( 2023 ) and Chen et al. ( 2023 ) . SpecInfer (Miao et al., 2024 ) generalized single-chain verification to tree-structured candidates, verifying an entire token tree in one target-model forward pass via an ancestor-only attention mask — the verification mechanism this paper reuses unmodified (Section 3.5 ). Autoregressive tree drafters: EAGLE. The EAGLE line (Li et al., 2024a , b , 2025 ) builds high-quality draft trees on top of an autoregressive drafter, culminating in EAGLE-3’s (Li et al., 2025 ) training-time-test procedure. Because an autoregressive drafter’s hidden state

at position i i genuinely depends on the realized tokens at all earlier positions, branching an EAGLE-style tree requires re-running the (small, but nontrivial) draft model per branch — there is no shared, precomputed representation across branches the way there is for a block-diffusion backbone. Domino, and by extension our tree, avoid this cost by keeping the expensive backbone pass parallel and shared, and branching only the cheap sequential correction (Section 2.3 , Structural Fact B) — a different point on the cost/branching trade-off than the EAGLE line occupies. Block-diffusion drafting: DFlash. DFlash (Chen et al., 2026 ) is the parallel drafter backbone Domino, and therefore this paper, builds on (Section 2.2 ). DFlash itself drafts a single chain per round from its marginal per-position distributions; it does not build trees. Marginal draft trees: DDTree. DDTree (Ringel and Romano, 2026 ) is the direct algorithmic ancestor of the tree-construction mechanism used in this paper: a best-first heap over a block-diffusion drafter’s per-position marginals, verified with an ancestor-only attention mask (Section 2.4 ). Our conditional tree uses the identical heap mechanism; the entire technical contribution of this paper is a node-scoring function — Domino’s GRU-corrected, path-dependent conditional log-probability — that DDTree’s factorized formulation cannot express, because DDTree only ever consults per-position marginals that do not depend on which tokens are realized a

long a candidate’s own path (Section 3.1 ). Cost-aware budgets: CaDDTree. CaDDTree (Zhang et al., 2026 ) replaces DDTree’s fixed, offline-tuned node budget with a per-round greedy stopping rule, proved optimal under a convexity assumption on verification cost, for the factorized case (Section 2.5 ). CondAdaptive (Section 3.4 ) inlines the same rule into our conditional tree’s pop loop; the optimality framework plausibly carries over, but the corrected drafter’s path-probabilities are miscalibrated as target-acceptance estimates, so the resulting budget gives no gain over a fixed one (Section B.3 ). Closest related work: JetSpec. JetSpec (Hu et al., 2026 ) is, to our knowledge, the closest published method to our goal: it builds a causal draft tree directly on top of a parallel drafter, combining one-forward-pass drafting efficiency with branch-wise causal conditioning, by training a new causal parallel draft head aligned with the target model’s own factorization. The honest distinction is that JetSpec trains a new draft head end-to-end for tree-structured causal conditioning, whereas our method is training-free: it reuses Domino’s released, off-the-shelf correction head, adding no new parameters and requiring no additional training data or compute. We flag plainly that this is a narrow niche: if a future revision of JetSpec is shown to be training-free as well, or if it adds a per-round adaptive budget we could not get CondAdaptive to deliver (Section B.3 ), the distinction w

e claim narrows substantially, since a purpose-trained causal head is a strictly more expressive mechanism than reusing a GRU correction that was not trained with tree branching in mind. 6 Limitations and Future Work We state the current scope limits plainly rather than deferring them to a closing paragraph. GPU-native builder: scope. DominoTree’s default builder is GPU-resident: heap management is left to Python, but per-node correction executes via CUDA-graph capture/replay rather than a per-node round-trip through eager PyTorch, analogous to Domino’s own CUDA-graphed chain correction (Section 3.3 ). What remains future work is extending this pattern beyond a single-stream research harness: a multi-request, batched, or serving-integrated (e.g. SGLang/vLLM) version of the same graph-capture idea. A6000 and 5080 throughput are not directly comparable. This matters for the Qwen3-8B grid (Table 1 ), collected on a single RTX A6000 rather than the two RTX 5080s used for the Qwen3-4B grid this paper headlines. Microbenchmarking indicates the A6000’s verification-forward latency in this setup is both higher and noisier than the 5080’s, consistent with clock- or attention-kernel-throttling rather than the 5080’s cleaner memory-bandwidth-bound profile, so absolute tokens-per-second numbers from the two GPUs should not be compared directly. Only same-GPU relative comparisons — a tree method vs. its own chain baseline, or own-AR-normalized speedups — carry across the two grids. If any

thing, the GPU-native builder matters more at 8B than at 4B: the heavier Domino drafter makes tree construction costlier, so the builder’s per-round saving grows to 11.52 11.52 ms and is what converts DominoTree’s accepted-length lead into its 8B throughput win (Section 4.3 ). T > 0 T{>}0 draft convention. At T > 0 T{>}0 DominoTree drafts deterministically (best-first) and samples the target, accepting a draft token iff it equals the sampled target token, so the committed output is the target’s own temperature-sampled sequence (lossless). We verified from source that the reference DFlash/DDTree/CaDDTree implementation uses this identical convention, so that cross-harness comparison is convention-matched at every temperature; the released Domino baseline samples its own draft, as published. Draft-side sampling is a separate axis, ablated in Table 10 . Adaptive budgeting remains open. DominoTree ships a fixed node budget. CondAdaptive — our attempt to transfer CaDDTree’s cost-aware adaptive budget to this non-factorized setting — does not improve over it: the corrected drafter’s cumulative path-probabilities over-credit acceptance, so the adaptive rule saturates at its cap (Sections 3.4 , B.3 ). A calibrated per-round adaptive budget is left to future work. Prototype, not a serving system. All results are produced by a single-stream, batch-size-1 research harness built on Hugging Face Transformers, not by an integration into a production serving stack (e.g. SGLang or vLLM). The
