摘要

在受监管行业部署大语言模型，需要的不仅仅是挑选最快的推理引擎：还需要证据，证明某个配置在服务任何客户请求之前就满足合同与法律义务。我们介绍了 Runway，这是 MasterControl 内部构建的验证工具，围绕 NVIDIA AIPerf 构建受治理的决策流水线。其关键洞察在于关注点分离：AIPerf 提供可信的测量，而 Runway 提供测量之前的实验设计以及测量之后的合规、成本和审计决策。我们描述了使缓存与审计成为同一机制的架构和存储模型。我们报告了 Runway 扫描的三项发现：TensorRT-LLM 与 vLLM 的排名随并发数反转；更新、更昂贵的 GPU 实例在单请求成本上可能更便宜；投机解码在高负载下在不同引擎间表现迥异，因此引擎配置的重要性可能超过引擎选择。

1 引言

部署大语言模型的标准做法将推理引擎选择视为一次性决策：在合成负载下对候选方案进行基准测试，选择吞吐量最高的配置，仅在性能退化时才重新审视。这种方法假设越快越好、选择标准是隐含的。在受监管行业（制药制造、医疗器械、金融合规）中，这两个假设都不成立。

MasterControl 运营着一个质量管理平台，被生命科学及其他受监管行业的 1,200 多家公司使用 [1]，需遵守 21 CFR Part 11 [2] 等法规。对推理引擎、GPU 实例类型或模型版本的每一次变更，都是对已验证生产系统的变更。监管机构不接受"供应商说它更快"作为理由；他们期望有客观的、有文档记录的证据，证明该变更在部署前已根据明确的验收标准进行过评估 [2, 3]。

本文介绍了 Runway，一个将"此配置是否真正满足我们的要求？"这一问题转化为可重复、有版本、可审计答案的内部工具。核心设计决策是不构建基准测试引擎。NVIDIA 的 AIPerf [4] 已经存在、开源，并且由构建我们所部署的 GPU 和推理运行时的同一组织维护。相反，Runway 围绕未经修改的 AIPerf 构建受治理的决策流水线：它设计实验，调用 AIPerf 进行测量，并将结果转化为日后能够辩护的发布决策。

我们做出两项贡献：

C1. 受治理推理验证的参考架构。 前—测—后模式、缓存与审计合一的存储布局，以及将决策问题转化为可审查产物的活动（§3–§5）。

C2. 关于配置选择的实证发现。 引擎排名随并发数反转；更昂贵的 GPU 实例在单请求成本上胜出；投机解码在高负载下使引擎分化（§6）。

2 背景：测量问题

2.1 为什么 LLM 推理验证与众不同

LLM 推理的三个特性广为人知：性能取决于 token 形状，因为延迟随输出长度增长、首 token 时间随输入长度增长 [5]；即使在温度为零时输出也是非确定性的，因此重复运行并非相同的工作负载 [6]；速度不等于质量，因为量化模型可以在平均准确率上持平却翻转个别答案 [7]。质量评估不在本文范围内；性能门控是必要条件但非充分条件。另外两个特性塑造了 Runway 的设计。

合成负载不是真实负载。 生产流量具有特定的提示类型、上下文长度和输出期望分布。微妙的细节很重要：引擎仅对完全相同的提示前缀重用缓存的注意力状态 [8, 9]，因此系统提示放在最前面可以启用前缀缓存，而相同内容放在每请求字段之后会使缓存失效，极大改变首 token 时间。验证必须使用尽可能匹配生产的数据，或明确承认其未覆盖的内容。

结果必须可追溯。 当被问及"为什么部署引擎 X 而不是引擎 Y"时，答案必须是可检索的产物，展示比较过程、验收标准和通过/失败判定。Part 11 本身就要求经过验证的系统和安全的、带时间戳的审计跟踪 [2]。

2.2 NVIDIA AIPerf

NVIDIA AIPerf [4] 是 GenAI-Perf 的继任者，是一个面向大语言模型推理的开源基准测试工具。它针对 OpenAI 兼容端点生成负载，测量首 token 时间、token 间延迟和端到端请求延迟的多个百分位数，以每秒请求数和 token 数报告吞吐量，并同时采样 GPU 遥测数据 [10, 11]。NVIDIA 推荐将其用于生成式 AI 推理基准测试，并在其自己的 NIM 基准测试指南中使用它 [12]。

虽然 AIPerf 负责测量，但受监管部署在测量之外增加的是流程：决定测试哪些配置、判断结果是否通过、保持证据可检索。该流程正是 Runway 所提供的。

3 架构：前、测、后

Runway 是一个围绕三个阶段组织的 Python CLI（图 1）：运行之前，扫描扩展和缓存查找；测量，完全委托给 AIPerf；运行之后，存储、SLA 评估和成本建模。这种分离意味着测量来自 NVIDIA 自己的工具（我们没有构建负载生成器，因此不必向审计人员为其辩护），而决策逻辑由我们自行更改而无需修改上游代码。

图 1：Runway 系统概览。每个阶段是一个独立的层；AIPerf 是唯一接触被测引擎的组件。缓存命中则完全跳过测量。

3.1 前：实验设计

扫描以每个轴的值列表声明：

清单 1：声明扫描

runway benchmark --model Qwen/Qwen3-8B-FP8 \
  --engines vllm,tensorrt-llm@1.2.1 \
  --instance-type g6e.xlarge --deployment argo \
  --input-tokens 128,512,1024 --output-tokens 128,512,1024,2048 \
  --concurrency 1,5,10,50,100 \
  --gpu-telemetry pynvml --sla sla/production.yaml

BenchmarkRunner 将其扩展为单元格网格（2 个引擎 × 3 种输入长度 × 4 种输出长度 × 5 个并发级别 = 120 个单元格），并询问 CacheManager 哪些单元格已被测量（§5）。仅运行缺失的单元格。

3.2 测：AIPerf，未经修改

BenchmarkExecutor 通过相同的固定生命周期（模板方法）运行每个单元格：设置部署、启动引擎并等待健康检查、预热、运行、保存、拆除。因此结果在构造上即可比。对于每个单元格，它作为子进程调用 AIPerf；下面的命令是 Runway 为 §6 中某个单元格记录的命令：

清单 2：为某个单元格记录的 AIPerf 调用

aiperf profile --model 'Qwen/Qwen3-8B-FP8' --url 'http://vllm-benchmark:8000' \
  --endpoint-type 'chat' --streaming --concurrency 1 \
  --isl 1024 --osl 1024 --tokenizer 'Qwen/Qwen3-8B-FP8' \
  --gpu-telemetry 'pynvml' --artifact-dir '/workspace/artifacts/result_i1024_o1024_c1'

Runway 直接读取 AIPerf 的 profile_export_aiperf.json，不做任何重新计算。SLA 门控、成本模型和比较表都完全使用 AIPerf 报告的内容。引擎（TensorRT-LLM、vLLM 或远程端点）和部署目标都是各自统一接口背后的适配器，因此两个引擎在相同的负载配置下进行基准测试。启用 GPU 遥测 [11] 时，它还会记录设备名称，这就是下面的结果与特定硬件关联的方式。

在 EKS 上的 Argo Workflows [13] 上（图 2），init 容器暂存模型权重，引擎作为 sidecar 在 pod 的共享网络上运行，Runway 和 AIPerf 在主容器中针对 localhost 运行，被测对象与测量对象之间没有网络跳转。引擎作为顺序步骤运行，因此它们永远不会争用 GPU，并且每个单元格完成后立即上传，因此被中断的扫描会保留其已完成的单元格。

图 2：Argo Workflows 执行。引擎和 AIPerf 共享 pod，因此负载通过 localhost 生成。

3.3 后：SLA 评估与成本

结果根据声明式、有版本的 SLA 文件进行评估：

清单 3：SLA 定义（节选）

name: production
version: 1.2.0
thresholds:
  - metric: request_latency_p95
    operator: "&lt;="
    value: 2.5
    severity: critical
  - metric: ttft_p50
    operator: "&lt;="
    value: 150.0
    severity: warning

每个阈值指定一个 AIPerf 指标和统计量、一个比较运算符和一个严重性级别（critical、warning 或 info）。运行汇总为通过、部分通过（无严重违规，但违反了警告或缺少指标）或失败。成本模型根据实时 AWS 价格为运行定价。每次运行的 report.json 记录 SLA 名称、版本和判定结果以及成本和引擎配置，因此"我们发布时生效的阈值是什么"有存储的答案。

对于跨运行的决策，runway compare 变化一个维度（模型、引擎、实例类型或实验）并按指标标记胜者。它首先列出结果路径，仅加载匹配的单元格，因此对数百个单元格的比较不需要 GPU 且只需几秒钟。

4 配置与活动

引擎设置存在于每个引擎和模型对应的一个 YAML 文件中，原样传递给 trtllm-serve 或 vllm serve。模型规范（model spec）将重复扫描捆绑到一个文件中，并可以直接传递 AIPerf 选项（例如，token 长度分布而非固定长度）。单个 versions.yaml 固定引擎镜像和 AIPerf 版本；版本是每个结果路径的一部分，因此不同版本的结果永远不会混合。工作负载是由 AIPerf 生成的合成 token 形状或上传的提示集，单轮或多轮；数据集名称是第一个路径段，报告仅通过名称引用数据集，因此可以在不包含提示的情况下共享报告。

单次扫描回答"有多快？"。活动回答决策问题，例如"投机解码对此工作负载是否划算？"，并保存为可审查文本的目录：

  • manifest.yaml：契约，包含问题、模型、引擎版本、扫描设置、带有实测输入/输出长度的数据集以及比较结构。一个 leg（分支）固定一种硬件、数据集和缓存机制；每个 arm（臂）是其中的一个引擎配置，具有自己的来源信息。
  • configs/：完全按提交时的引擎配置。
  • run.sh：如何复现；FINDINGS.md：数字、建议、注意事项。

验证器拒绝任何两个 arm 会写入相同结果前缀的清单，这种冲突否则会静默地用一个 arm 覆盖另一个。§6.3 中的发现来自两个这样的活动。

5 结果存储与缓存

每个单元格的结果落在确定性路径上（图 3）。路径回答测量了什么：数据集、实例、模型、引擎、版本、可选的实验名称，以及单元格的输入长度、输出长度和并发数。AIPerf 输出旁边的第二个文件 benchmark_config.json 记录如何测量：流式传输、额外的 AIPerf 参数、持续时间、数据集格式、预热和引擎配置。

s3://&lt;bucket&gt;/runway/
  benchmarks/&lt;dataset&gt;/&lt;instance&gt;/&lt;model&gt;/&lt;engine&gt;/&lt;version&gt;/[&lt;experiment&gt;/]
    result_i&lt;I&gt;_o&lt;O&gt;_c&lt;C&gt;/            . 一个扫描单元格
      profile_export_aiperf.json      . AIPerf 输出，未修改
      benchmark_config.json           . 缓存指纹
  reports/&lt;instance&gt;/&lt;org&gt;/&lt;model&gt;/&lt;engine&gt;/&lt;timestamp&gt;/report.json  . SLA + 成本判定
  datasets/&lt;name&gt;/dataset.txt         . 上传的提示集
  campaigns/&lt;id&gt;/results/             . 规范化的活动快照

图 3：产物存储布局。路径编码测量了什么；指纹文件记录如何测量。合成扫描使用 synthetic 作为数据集段。

相同的布局使缓存和审计成为同一机制。在部署任何内容之前，CacheManager 检查每个单元格（图 4）：结果必须存在且其指纹必须与请求的运行匹配。指纹比较会改变 AIPerf 测量内容的设置（streaming、aiperf_extra_args、benchmark_duration、custom_dataset_type）。引擎配置被记录但不比较；具有不同引擎配置的运行使用 --experiment 名称，这会添加一个路径段，从而产生新的缓存槽。该规则可以推广：任何改变结果的内容都必须改变其路径或其指纹。

图 4：每个单元格的缓存决策。--only-cache 将任何未命中变为错误，这使得可以在没有 GPU 的机器上重新生成报告。

完全命中可以在没有 GPU 的情况下复现报告。代价是相同配置的重复运行返回存储的数字而不是新的测量，因此每个单元格只有一个独立的测量，除非使用 --no-cache（§7）。

6 发现

我们报告 Runway 扫描的三项发现。所有数字来自存储的单元格；每个单元格是单次测量（§5），因此小差异应被视为指示性的而非显著的。

6.1 引擎排名随并发数反转

设置。 vLLM 0.19.1 和 TensorRT-LLM 1.2.1 在 Qwen3-8B-FP8 [14] 上使用默认设置，60 个匹配单元格：12 种 token 形状（输入 ∈ {128,512,1024}，输出 ∈ {128,512,1024,2048}）× 5 个并发级别（1、5、10、50、100），在 g6e.xlarge（NVIDIA L40S，48 GB [15]）上，AIPerf 0.7.0。

并发数 吞吐量胜者 p95 延迟胜者
1 TensorRT-LLM（+35%） TensorRT-LLM（12/12）
5 TensorRT-LLM（+13%） TensorRT-LLM（12/12）
10 TensorRT-LLM（+10%） TensorRT-LLM（12/12）
50 vLLM（+3%） TensorRT-LLM（7/12）
100 vLLM（+19%） vLLM（12/12）

表 1：跨并发级别的引擎比较。吞吐量优势是胜者在 12 种 token 形状上的平均吞吐量比率；延迟胜者统计 12 种形状中的胜出次数。

交叉点出现在并发数 10 和 50 之间。两个引擎都实现了分页 KV 缓存和连续（在途）批处理 [16, 17]，因此我们将其解读为默认调度器设置而非架构差异，尽管这些扫描没有隔离原因。在低并发下，TensorRT-LLM 的每 token 速度占主导。在高并发下，其默认调度器策略 GUARANTEED_NO_EVICT 保守地使用 KV 缓存，保证已启动的请求永远不会被暂停，因此同时接纳的请求更少 [18]。§6.3 展示了不同策略在多大程度上改变局面。

因此，单并发基准测试可以根据所选级别选出任一引擎；引擎选择应遵循部署的并发特征，比较应测试多个级别，正如 NVIDIA 的 NIM 基准测试指南已经建议的那样 [5]。

6.2 更贵的实例单请求成本更低

设置。 相同模型在 vLLM 0.19.1 上，80 个匹配单元格（16 种 token 形状，输入最长 4,096，× 5 个并发级别），在 g6e.xlarge（NVIDIA L40S）和 g7e.2xlarge（NVIDIA RTX PRO 6000 Blackwell Server Edition，96 GB [19]）上。成本模型将其定价为每小时 $1.861 和 $3.363（us-west-2，Linux 按需，截至 2026-09 [20]），g7e 的溢价为 1.81 倍。

并发数 吞吐量 p50 延迟 单请求成本
1 2.13× 0.47× 0.85×
5 1.82× 0.55× 0.99×
10 1.85× 0.54× 0.98×
50 1.94× 0.52× 0.93×
100 2.04× 0.49× 0.88×

表 2：g7e.2xlarge 相对于 g6e.xlarge，16 种 token 形状的中位数。单请求成本是价格比率除以吞吐量比率。

Blackwell 在每个并发级别下大约使吞吐量翻倍、延迟减半，与 AWS 自己给出的高达 G6e 推理性能 2.3 倍的数据一致 [19]，这足以补偿其价格：单请求成本中位数低 1–15%（表 2）。这是"后"阶段在起作用。每小时成本视图会选择更便宜的实例，而实测的单请求成本会选择另一个。一个单元格（输入和输出均为 128，并发数 1）出现反转，g7e 更慢；由于每个单元格只有单次测量，我们还无法判断这是否真实。

6.3 投机解码：配置可能比引擎选择更重要

设置。 在 Qwen3.5-9B [21] 上使用一块 NVIDIA H100（p5.4xlarge，80 GB [22]）进行两项活动（§4）：具有共享前缀的内部实体提取提示集（约 3,300 输入和 200 输出 token），60 秒单元格，缓存禁用。TensorRT-LLM 1.3.0rc23（预发布版本；固定的 1.2.1 不支持该模型的多 token 预测）对阵 vLLM 0.19.1，两者都经过调优。每个都在启用和不启用多 token 预测（MTP）[23] 的情况下运行，MTP 是投机解码 [24] 的一种形式，使用模型自己的 MTP 头来起草 token [25, 26]，起草 token 数为五。模型卡建议 vLLM 使用两个起草 token [21]，因此更长的起草可能在负载下影响 vLLM 的结果。

并发数 vLLM：MTP / 基线 TensorRT-LLM：MTP / 基线
1 2.16× 2.57×
16 1.11× 1.69×
32 0.92× 1.32×
64 0.80× 1.45×

表 3：启用 MTP 的吞吐量相对于同一引擎不启用时的比率。

MTP 将 TensorRT-LLM 在并发数 1 时的中位 token 间延迟从 6.65 ms 降至 2.18 ms，每 token 提速 3 倍。当小批量使 GPU 利用不足时，投机的收益最大 [26]，因此两者的收益都随负载而缩小，但引擎在缩小程度上存在分歧（表 3）。vLLM 的 MTP 在大约并发数 16 以上变成净成本，而 TensorRT-LLM 的在每个级别都保持正收益。因此每个引擎的最佳配置在性质上不同：vLLM 不启用 MTP 时表现最佳，TensorRT-LLM 启用时表现最佳。在并发数 64 时，vLLM 的最佳结果仍然领先，20.9 对 19.3 req/s。它凭借默认设置达到这一水平，而 TensorRT-LLM 需要非默认的调度器策略（MAX_UTILIZATION 而非 GUARANTEED_NO_EVICT [18]）。活动笔记将 2.55 倍的吞吐量增益归因于这一个设置。对表 1 中比较的启示是，该结论在默认设置下成立：单个引擎设置对吞吐量的影响可能超过引擎之间的差距。

7 讨论与局限

自定义负载生成器的成本。 在采用 AIPerf 之前，我们原型化了一个内部基准测试工具。达到与 AIPerf 的功能对等花了三个工程师周，而且其正确性在验证期间仍需要独立论证。采用未经修改的 AIPerf 将这部分工作从测量转移到了围绕它的决策流水线。

缓存与方差。 指纹缓存使报告可复现并避免重新测量已知单元格，但这也意味着每个单元格只有一个测量，因此 §6 中的结果都没有置信区间。计划提供一个故意绕过缓存的复制选项（--replicate=N），但在这些扫描中尚不可用。

合成工作负载。 表 1 和表 2 中的发现使用生成的 token 形状，而不是回放的生产流量，且生产 token 分布尚未测量。它们确立了引擎和实例的相对行为，而不是在任何特定 MasterControl 工作负载上的性能。

8 结论

受监管的 AI 部署需要证据，而不是直觉。我们介绍了 Runway，这是一个验证工具，通过在测量之前设计实验、在测量之后应用声明式 SLA 和成本门控，并将每个结果存储在说明其测量内容的路径上，围绕 NVIDIA AIPerf 构建受治理的决策流水线。关键设计洞察是测量和决策是不同所有者的不同问题：AIPerf 提供可信的测量，Runway 提供围绕它的流程。

这些发现从数据中得出了相同的观点。引擎排名随并发数反转，更昂贵的实例在单请求成本上可能更便宜，单个引擎设置的重要性可能超过引擎选择。这些对单点基准测试不可见，而在受治理的扫描中一目了然。

Runway 是 MasterControl 的内部工具，目前未开源。我们欢迎在受监管环境中构建类似工具的从业者咨询。
