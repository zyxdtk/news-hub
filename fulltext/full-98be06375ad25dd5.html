摘要

LLM 智能体越来越多地被用于仓库级软件工程任务。这些任务要求智能体在推理或编辑之前先检索到正确的代码上下文。然而，大多数智能体仍然通过原始文件、词法搜索和 shell 命令来访问仓库，主要将代码视为文本。本文将基于地图的代码表示工作流作为智能体软件工程中的一个设计变量进行研究，考察不同的仓库视图如何改变智能体的检索行为、任务成功率、token 使用量和延迟。

本文研究了五种代码表示工作流：抽象语法树、调用图、模块依赖、文档增强搜索，以及结合以上视图的混合工作流。每种工作流都提供一个按需的仓库地图，供智能体在任务执行过程中查询。我们在四个仓库级任务上评估了使用 Haiku 4.5 的 Claude Code 与原始工具基线的对比：基于 LinuxFLBench 的故障定位、基于 SWE-bench Pro 的仓库级代码生成与修复、基于 SWT-bench 的测试生成，以及基于 SecBench 的安全补丁。我们同时测量了任务成功率、表示工具使用情况、原生工具使用情况、token 消耗和挂钟时间。

结果表明，当定位是瓶颈时，表示工作流最有价值的用途是节省 token；而当决定性步骤是补丁或测试编写时，其成功率增益会收窄。在 LinuxFLBench 上，所有五种工作流均提升了 recall@10（0.757–0.829 对比 0.717），并将 token 使用量降低 25–39%，但也增加了挂钟时间。在 SWE-bench Pro 上，解决率保持接近基线（44.3–50.6% 对比 49.0%），而 token 使用量下降 17–26%。在 SecBench 上，Callgraph 在本样本中具有最高的补丁解决率（34.3% 对比 28.9%）且使用更少 token，但所有工作流都增加了延迟。在 SWT-bench 上，Hybrid 和 Docs 在本样本中具有最高的复现测试率（47.8% 和 47.2% 对比 44.7%），但所有工作流都使用更多 token 且耗时更长。总体而言，基于地图的工作流既改变了智能体检查的内容，也改变了其开销，但其收益取决于任务类型而非普遍适用。

I 引言

LLM 智能体越来越多地被用于仓库级软件工程（SE）任务，例如故障定位、问题解决、测试生成和安全补丁 [1, 2, 3]。在这些任务中，生成代码只是流程的一部分。智能体首先需要确定相关行为在何处实现、哪些文件和函数与之相关，以及在进行预测或编辑之前应检查哪些证据。如果这一定位步骤薄弱，智能体可能会将大部分预算耗费在阅读无关文件或编辑仅与任务存在词法关联的代码上。

当前的编码智能体，包括 Claude Code [4]、SWE-agent [5]、Agentless [6] 和 OpenHands [7]，通常通过词法文件搜索和基于 shell 的探索命令与仓库交互。这种接口很灵活，但提供给智能体的仓库结构化信息很少。例如，智能体可能需要反复搜索和读取文件才能确定某个符号在何处定义、哪些函数调用它、哪些模块依赖它，或者哪些文档解释了其预期行为。这些操作主要用于重建 SE 任务所需的上下文。

代码表示能够自然地呈现这种上下文。除源代码文本外，仓库还可以通过抽象语法树、调用图、依赖图、与程序符号关联的文档或这些视图的组合来查看。每种视图强调不同的关系：抽象语法树呈现定义与包含关系；调用图呈现过程间关系；依赖图呈现模块级耦合；文档则将自然语言描述与代码意图联系起来。这些视图在程序分析和代码智能领域已被广泛使用 [8, 9, 10, 11, 12]，但它们在 LLM 智能体工作流中的作用仍知之甚少。

先前关于 SE 智能体的研究表明，仓库导航和上下文选择会影响性能 [5, 13, 14, 15, 16, 17]。然而，表示往往与智能体脚手架、检索方法或修复循环捆绑在一起。这使得我们难以判断性能提升究竟来自模型、提示词、智能体策略，还是提供给智能体的代码视图。因此，我们缺乏对“哪些表示能帮助智能体、适用于哪些任务、代价如何”的系统性比较。

为弥合这一差距，本文研究智能体在执行仓库级软件工程任务时应如何访问代码表示。图 1 展示了本研究的概览。我们研究了四种对仓库理解要求不同的仓库级软件工程任务：故障定位（根据错误报告找到负责的文件或符号）、程序修复（跨仓库编辑代码以修复报告的问题）、安全补丁（定位并修复导致漏洞的代码）和测试生成（理解待测试的行为并编写能捕获该行为的测试）。我们使用成熟的仓库级基准来实例化这些任务：LinuxFLBench [18]、SWE-bench Pro [19]、SecBench [20] 和 SWT-bench [21]。这些任务分别考验不同的瓶颈：不进行编辑的情况下定位相关代码、编辑并验证功能性修复、修复触发漏洞的行为，以及编写能暴露缺陷的测试。

我们考察四种表示类别：抽象语法树（AST）、调用图（CG）、依赖图和文档增强搜索。我们还研究了一个混合工作流，将这四种视图合并到单一仓库地图中。在评估中，我们测量任务成功率、工具调用行为、token 使用量、挂钟时间以及逐实例轨迹。

我们的核心发现是：当任务瓶颈在于查找相关代码时，基于地图的表示工作流最为有用。在故障定位任务（本质是代码搜索）中，它们在削减 token 使用量的同时提升了召回率，尽管会增加延迟。在程序修复中，瓶颈部分已越过定位阶段，因此它们在保持解决率的同时，通过替代仓库浏览减少了 token。在安全补丁中，本样本中最强的信号来自 Callgraph，它与以堆栈为中心的提示相匹配，能以更低的 token 成本（但更高延迟）呈现调用者/被调用者上下文。在测试生成中，决定性步骤是编写具有区分性的断言，成功率变化很小，且若干工作流增加了 token 开销。因此，结果支持“工作流应依任务而定”的主张，而非“某种固定表示普遍更优”的主张。

本工作的贡献如下：

• 据我们所知，我们首次对智能体软件工程中的五种代码数据表示进行了受控比较，在相同的智能体技术栈下，跨四个仓库级任务评估了 AST、调用图、依赖、文档增强和混合视图。

• 我们在固定的智能体技术栈下比较了 AST、调用图、依赖、文档增强和混合仓库视图，同时报告了任务成功率、token 使用量、挂钟时间和工具调用行为。

• 我们表明，当仓库定位是主要瓶颈时，表示工作流能提供最强且最一致的收益，主要通过减少高 token 消耗的浏览。

• 我们提供了轨迹级证据，解释不同仓库视图何时有帮助、何时增加开销、何时无法影响最终的补丁或测试生成步骤。

II 相关工作

II-A 仓库级智能体软件工程

仓库级 SE 智能体通常在整个项目中搜索、编辑、执行和验证代码。SWE-bench [22] 通过需要跨文件推理的真实 GitHub 问题确立了这一任务设定，而 SWE-agent [5] 表明仓库接口会影响智能体读取文件、编辑代码和运行命令的方式。AutoCodeRover [13] 通过结构感知的代码实体搜索强调“先定位后修复”。总之，这些研究表明仓库导航本身就是任务的一部分，而不仅仅是预处理步骤。

近期系统通过修改智能体工作流来改进智能体软件工程。Agentless [6] 将问题解决分解为定位、修复和验证，表明在精心选择上下文的情况下简单脚手架即可有效。OrcaLoca [14] 通过动作调度、分解和上下文剪枝改进问题定位，而 ARISE [23] 则暴露仓库图和切片工具用于定位与修复。这些工作启发了我们的研究，但它们主要评估完整系统或特定表示设计；相比之下，我们保持智能体框架固定，将表示作为实验变量进行比较。

II-B 面向结构与意图的代码表示

代码智能研究长期以来一直在使用超越局部词元的程序视图。TBCNN [8] 用 AST 建模语法结构，Allamanis 等人 [9] 将程序表示为带语义关系的图，GraphCodeBERT [10] 将数据流纳入预训练。文档提供了关于意图和 API 使用的补充性自然语言视图：DocPrompting [11] 为代码生成检索文档，RepoRepair [24] 利用层次化文档进行仓库级修复。总之，这些研究表明语法、程序关系和文档各自能呈现原始源代码词元可能无法显式表达的上下文。

我们在不同的设定下研究这些表示。我们不是将它们嵌入模型、检索器或修复系统内部，而是在智能体轨迹执行过程中将 AST、调用图、依赖、文档和混合视图作为 MCP 工具暴露。这使我们能够在共享接口和固定智能体框架下比较哪种视图对哪种仓库级任务有帮助。

II-C 仓库级上下文检索

仓库级编码需要在生成之前选择上下文。RepoBench [25] 和 CrossCodeEval [26] 评估上下文跨文件的补全，而 RepoCoder [27] 使用迭代式检索与生成。Repoformer [15] 表明更多上下文并不总是更好，RepoQA [28] 表明长上下文模型仍需将自然语言查询与分散的代码证据关联起来。

基于图的检索提供了组织仓库上下文的另一种方式。GraphCoder [16]、RepoGraph [17]、LocAgent [29] 和 CodeGraph [30] 暴露仓库图或图引导的搜索工具用于代码导航和定位。这些系统展示了交互式图上下文的价值，但每个都绑定于一种图设计和检索策略；我们的研究则保持智能体固定，将代码视图视为受控变量，在同一接口下比较 AST、调用图、依赖、文档和混合地图。

我们考察五种不同的代码表示，每种捕获仓库结构和意图的不同视图。各表示的细节描述如下。

AST

抽象语法树捕获代码的结构组织：存在哪些定义（函数、方法、类、结构体、变量）以及它们之间的嵌套关系，与运行时行为无关。AST 服务器的地图以这些定义为节点，以语法包含为边（文件 → 顶层定义 → 嵌套定义），因此整个仓库成为以文件为根的包含树森林。这告诉智能体代码位于何处以及如何分组。其 explore/node 工具对按结构相关性对定义排序，并返回定义的源代码及其外层作用域和嵌套成员；附加工具（表 I）提供文件骨架和精确的 tree-sitter 查询。实际上，AST 使代码的结构骨架可直接寻址，无需智能体重新解析源代码。

Callgraph（CG）

调用图捕获行为结构：不是代码在何处定义，而是控制流如何在定义之间流动，因此当不同文件中的函数相互调用时它们相邻。CG 地图以函数和方法为节点，以解析后的调用（调用者 → 被调用者）为边，形成有向的“谁调用谁”图。其 explore/node 工具对按调用连通性对函数排序，并返回函数的源代码及其调用者和被调用者；更多工具（表 I）返回直接调用者/被调用者和具体调用路径。此视图适用于需要沿调用边将一个函数中的症状追溯到另一个函数中的根因的任务。

Deps

依赖图以更粗的粒度捕获结构：不是定义如何嵌套或相互调用，而是整个文件和模块如何相互依赖，因此当一个文件导入另一个文件时它们相邻。deps 服务器的地图以文件为节点（附带其定义，使探索呈现真实代码而非裸文件名），以导入（文件 → 被导入文件）为边。其 explore/node 工具对按与查询的导入距离对代码排序，并返回文件的相关代码及其导入和被导入的文件；更多工具（表 I）报告文件的入站/出站依赖、两个模块之间的导入链、其架构层以及导入环。这使智能体能直接从导入图读取仓库组织，而无需通过大量搜索重建它。

Docs

文档视图捕获其他三种视图无法捕获的内容：代码背后的意图及其问题域的词汇，来源于附加在每个符号上的文档字符串、注释和签名。这使其成为以人类术语而非符号名称表述的查询的天然视图。由于文档没有固有的图结构，docs 服务器没有可遍历的边：它不扩展邻域并按中心性排序，而是直接按全文相关性对其解析后的文档注释和签名排序文档化符号节点。其 explore/node 工具对返回文档与自然语言查询最匹配的符号；更多工具（表 I）提供模块级和仓库级的文档化概览。因此，docs 视图让以通俗词语表达的查询能找到实现它的代码，即使智能体不知道确切的符号名称。

Hybrid

混合视图不是一种新结构，而是其他视图的融合，将它们合并为单一地图，使智能体能够同时基于多种关系进行推理。它将调用图和依赖图合并为一个图，其节点既包括函数也包括文件，其边包括调用、导入和包含（文件 → 定义）；包含边承载 AST 骨架，因此单一地图同时容纳包含关系、调用关系和模块依赖。其 explore/node 工具对按调用和导入连通性联合排序代码，并返回符号的组合邻域；更多工具（表 I）估计某项更改的传递影响范围并提供文档化的仓库概览。

III-B 代码表示的实现

我们通过将每种表示暴露为专用的模型上下文协议（MCP）[31] 工具服务器，来研究不同代码表示如何影响智能体行为。一次智能体运行由如下元组参数化：⟨智能体, 模型, 表示, 基准任务⟩。其中，“智能体”指编码智能体框架，“模型”指该框架使用的 LLM 快照。表示决定挂载哪个 MCP 服务器（若有），基准任务提供输入提示和评分信号。在比较表示时，我们保持智能体框架、模型和基准任务固定。

我们实现了五个表示服务器：AST、调用图、依赖图、文档和组合前四者的 Hybrid。在每次智能体运行之前，所选服务器对目标仓库建立索引，并将提取的信息存储为可搜索的仓库地图。所有服务器使用 tree-sitter 解析源文件，并为每种语言采用相应语法。对于 Python，调用关系使用 jedi 解析，导入依赖从 import 和 from 语句中提取，文档字符串使用 griffe 加载。对于 C/C++ 仓库（jedi 和 griffe 不适用），调用通过将调用名称与仓库级定义匹配来解析，依赖从 #include 指令中提取，文档取自紧邻每个定义之前的注释块。

五个受控服务器都暴露相同的核心导航工具对 <rep>_explore 和 <rep>_node，外加表示特定的实用工具。这为智能体在各工作流之间提供了可比的入口点，同时仍允许每种表示暴露关系特定的操作。地图是一个图，其节点表示代码单元（如函数、文件或文档化符号），其边编码该表示所使用的关系（如文件到定义的包含、调用或导入）。

所有服务器使用相同的基本查询流程。首先，服务器在基于 BM25 [32] 排序的 SQLite FTS5 索引上进行全文搜索以找到相关种子节点。符号名称中的匹配比签名、文档或代码体中的匹配权重更高。对于结构化服务器，这些种子节点随后通过服务器的图关系进行扩展：AST 的包含关系、调用图的调用边、依赖的导入边以及 Hybrid 的所有合并边类型。扩展后的图邻域使用带重启的随机游走中心性 [33] 从种子节点出发进行排序，排名最高的源代码片段按文件分组返回。文档服务器则不同，因为它没有结构边：它跳过图扩展，直接返回按 BM25 排序的文档化符号。这保持了各服务器检索入口点的可比性，同时改变了每个地图提供的主要信息。表 I 总结了各工具，图 2 展示了同一段代码在不同表示下的呈现形式。

IV-C 智能体技术栈

智能体无关：同一表示服务器无需修改即可在 Claude Code、Codex [35] 或任何未来兼容 MCP 的宿主上评估。

V-B3 性能收益的根本原因

将上述协议应用于性能轴得到以下类别，我们按基准报告：

故障定位的性能

表 VIII 第一块显示，故障定位的收益取决于表示是否暴露了缺陷所需的关系。对 AST 而言，所有获胜案例都是报告命名的文件内缺陷：报告命名或暗示了缺陷函数，AST 的包含边将该符号映射到其文件（17/17）。其主要失败类别是症状≠根因文件：报告描述的是症状，但真正的缺陷位于包含关系无法触及的结构上遥远的兄弟文件中（7/11）。对 callgraph 而言，所有获胜案例都是调用可达的跨文件缺陷：修复位于报告符号的调用者或被调用者中，通常在另一个文件里。其失败为邻居漂移（调用边停留在错误的症状文件附近）和排名稀释（缺陷出现在图中但被埋在高连接度的辅助函数之下）。对 deps 而言，大多数获胜是报告命名 API 型缺陷，报告命名了函数或调用点，依赖地图检索到相关文件（13/17）；其主要失败是导入集群之外的架构文件，架构或协议特定文件无法从通用集群通过导入到达（9/11）。对 docs 而言，所有获胜都是术语匹配注释：报告术语与缺陷文件中的注释或标识符匹配。其主要失败是仅有症状崩溃、无术语：报告只给出 panic/崩溃症状，文本搜索漂移到词法相似的错误文件（7/9）。最后，Hybrid 是安全的默认选择：它既赢得报告命名的单文件缺陷（11/17），也赢得跨子系统的症状到缺陷案例（6/17），并且零失败，因为它组合了所有关系类型。总体而言，单一关系地图各自帮助一种特定的缺陷形态，并在该关系缺失时失效，而 Hybrid 通过组合所有线索覆盖最广的范围。图 V-B3 用来自同一表示的已验证赢/输对说明这种匹配，并与同一实例上的基线进行对比。

Callgraph 获胜：调用可达的跨文件缺陷（LinuxFLBench 14053）
缺陷：内核在向 NFS 挂载执行 rsync 期间冻结；缺陷位于症状之下两层，在 RPC 客户端 net/sunrpc/clnt.c 中。沿 RPC 调用链，callgraph 将 clnt.c 拉入其地图并排在第 9 位；而 AST 和 deps 的关系停留在 fs/nfs/* 症状目录内，从未呈现该文件，基线在 42 次操作后也未能找到。
只有调用关系能跨越症状与缺陷之间的 NFS→RPC 层。

当缺陷是症状不调用的兄弟模块时，调用地图会漂移到错误的邻居。

程序修复的性能

在 SWE-bench Pro 上（表 VIII 第二块），每种表示仍能在基线失败的真实问题上获胜（20–28 个实例），获胜类别反映了各地图的定位强度。对 AST，主要获胜是报告命名的文件内缺陷（18/28）：问题命名了缺陷符号，包含边直接呈现其实现。对 callgraph，是调用可达的跨文件缺陷（11/20）：所需修复位于报告符号的调用者或被调用者中，调用边暴露了平面搜索可能遗漏的耦合函数。对 deps，是单模块转储（17/21）：一次依赖地图调用返回目标模块及其测试，在编辑前就给智能体提供了相关脚手架。对 docs，是跨文件共享符号缺陷（20/21）：共享符号、标志或 API 契约将受影响的文件联系起来，全文搜索一并返回相关源码。对 hybrid，主要获胜是命中单一目标文件（14/24）：合并地图将报告术语解析到问题文件，而基线放弃或落在他处。失败则更为一致。对每种表示，主要的失败模式都是定位正确、补丁错误（16–23 次失败）：地图找到了标准补丁文件，智能体也编辑了它们，但生成的修复在逻辑上是错误的。因此，与 LinuxFLBench 不同，SWE-bench Pro 的失败往往不是导航失败。解决率保持接近基线（表 IV 中 44.3–50.6% 对比 49.0%），表明许多输赢反映的是单次补丁的方差而非稳定的表示效应。其余与表示无关的失败是任何源码符号地图都难以捕获的任务形态：全树查找替换（索引给出定义但非所有引用点）、新文件创建（没有可检索的现有文件）以及非 Python 修复点（如 YAML 或 docker-compose）。这些情况击败了所有地图，因此属于任务设定的限制而非某一种表示的限制。图 V-B3 给出了来自 deps 表示的已验证赢/输对，均与基线对比。

图 5：SWE-bench Pro 上一对匹配的 deps 赢/输案例

Deps 获胜：命名目标上的单模块转储（SWE-bench Pro，ansible-3889ddeb）
任务：向单个 Ansible 模块添加参数。对命名文件的一次 deps_node 调用预先转储了整个目标模块及其测试，交给智能体完整的参数规范脚手架，因此它直接编辑唯一的实现文件。基线则通过漫长的 grep/Read 过程重建相同上下文（约 80 轮对比 deps 的 18 轮）。

任务：修复一个依赖算法/环境的缺陷。deps_explore 在几次调用内到达确切的缺陷文件（定位毫无悬念），但 k=1 的单次补丁尝试是错误的，运行在导入地图无法裁决的修复逻辑上失败。到达同一文件的基线碰巧在其一次尝试中得到了通过的补丁。
地图找到了正确的文件；失败在于编辑，且每实例一次运行下这是修复方差，而非定位失败。

安全补丁的性能

SecBench 不应被视为编辑受限任务，因为其输入信号以堆栈为中心：提示通常暴露崩溃堆栈帧，成功取决于沿堆栈追踪到编辑位置和执行上下文。这解释了为什么 Callgraph 表现最佳。其主要获胜类别是流定位（9/18）：callgraph 查询或所选节点与崩溃堆栈函数或最终编辑文件重叠，帮助智能体从崩溃帧移动到拥有漏洞不变量的调用者/被调用者上下文，最常见于解析器、解复用器、解压缩和运行时路径。与同样包含调用边的 Hybrid 的比较表明，优势不仅在于更多信息，而在于更显著的执行关系：在 Callgraph 解决而 Hybrid 未解决的 18 个实例中，Hybrid 在 14 个案例中编辑了与 Callgraph 相同的文件，但未能产出成功的补丁。这表明到达相关文件并不足够，Hybrid 中的额外上下文可能淡化了执行流信息的显著性。AST 通常过于局限于崩溃函数，而 Deps 和 Docs 仅在名称或注释暴露漏洞路径时有所帮助。SecBench 偏向 Callgraph，因为许多修复需要从堆栈帧跟随调用者/被调用者上下文，但这并不意味着 Callgraph 普遍最优。图 V-B3 给出了来自 callgraph 表示的已验证赢/输对。

Callgraph 获胜：从堆栈路径到修复点（SecBench gpac.cve-2023-4682）
漏洞：AVI 解复用溢出，其 sanitizer 堆栈命名为 avi_read / AVI_read_frame。Callgraph 的首次查询使用了 AVI_read_frame avi_read avidmx_process，将崩溃辅助函数与解复用路径关联。基线在 src/media_tools/avilib.c 中添加了大小上限，但 sanitizer 仍然触发。Callgraph 转而在 src/filters/dmx_avi.c 中产出了单行状态修复，在读取帧之前设置 AVI 视频位置，补丁得以解决。

漏洞：FAAD2 堆溢出，堆栈根位于 libfaad/lt_predict.c 的 lt_prediction。Callgraph 查询了该汇聚点并编辑了同一文件，对计算索引进行钳制；补丁可以编译，但 sanitizer 仍然触发。基线转而修补 libfaad/syntax.c，传播 ltp_data 的返回值，使无效的长期预测元数据在预测之前被拒绝。
这就是失败模式：当真正的修复是调用方侧的格式不变量时，以调用为中心的视图可能使崩溃辅助函数过于显著。

测试生成的性能

SWT-bench 则不同。其每种表示的主要获胜和失败类别相同：运行在与基线相同或相邻的测试目标中编写测试，k=1 生成的测试碰巧复现或未复现缺陷。因此 SWT-bench 的准确率净值小而混合（-11 到 +5），因为决定性步骤是编写有区分度的断言，而非找到仓库邻域。因此，一般性教训比“编辑受限任务是噪声”更窄：表示仅在其关系匹配任务当前瓶颈时有所帮助，一旦瓶颈转移到补丁不变量或测试断言，地图上下文可以改变轨迹，但往往成为开销。

V-B4 token 收益的根本原因

将相同协议应用于 token 轴，更少 token 的运行由一种机制主导。在这些实例上，表示主要通过读取替代发挥作用：地图内联返回相关代码体，智能体将其视为已读取，从而避免大量源文件读取。在 LinuxFLBench 上，读取替代占每种表示更少 token 运行的大多数（AST 79/111、callgraph 109/109、deps 72/115、docs 93/115、hybrid 85/117）。在 SWE-bench Pro 上，它再次是最大的单一原因（读取替代解释了每种表示 181–197 次更少 token 运行中的 115–188 次）。在 SecBench 和 SWT-bench 上，天平向另一侧倾斜：除 SWT-bench 上的 callgraph 外，每种表示使用更多 token 的实例都多于更少的（表 VII），因为在找到崩溃帧或测试目标后，智能体仍必须读取和编辑，地图上下文叠加在原生浏览之上。

当表示比基线使用更多 token 时，超支来自少数几种反复出现的模式。地图开销是简单故障定位案例中的主要成本：基线已廉价解决任务，表示为相同答案增加了额外的地图调用（例如 AST 占 LinuxFLBench 更多 token 运行的 30/41）。其余更多 token 的运行是混合型的，结合了找到相关文件后的冗余重新探索（docs 最常见）、单次合并地图查询返回的大量逐字源码载荷（hybrid 常见），以及通用符号名称拉入的噪声导入（deps 常见）。因此，成本要么来自简单案例上不可避免的地图开销，要么来自过多、过大或过噪的地图调用。图 V-B4 展示了一对已验证的 Docs 更少 token/更多 token 案例。

图 7：LinuxFLBench 上的 Docs token 对比

Docs 更少 token 运行：读取替代（LinuxFLBench 16043）
缺陷：注释/术语丰富的故障定位，docs 仅凭全文地图即可作答。docs_explore 逐字返回缺陷文件的源码（“视为已读取”），智能体几乎零源码读取即正确排序该文件，而基线需读取 70–114 KB 才能到达相同答案。

缺陷：报告直接命名了文件，基线用少量廉价操作即可定位。Docs 廉价的逐字源码查询反而引发了对已找到文件的冗余细化和大结果钻取：答案是对的，但探索在普通搜索本可完成的基础上叠加进行，token 膨胀至基线的 27.7 倍。
当文件被轻易命名时，地图的廉价探索循环成为纯粹的开销。

RQ2 要点。总体而言，表示在其关系匹配任务瓶颈时有所帮助。它们在定位瓶颈下分化最大：AST 帮助命名的文件内缺陷，callgraph 帮助调用可达的修复，deps 帮助导入/API 集群，docs 帮助术语丰富的缺陷，hybrid 帮助组合线索；对于地图之外的工作（如出现次数枚举、新文件创建和配置编辑），基线仍然更强。一旦瓶颈越过查找代码阶段——在修复、安全补丁和测试生成中——只有暴露所需编辑或测试的关系仍有帮助，许多剩余差异是单次补丁/测试方差。token 成本遵循相同模式：当地图替代定位读取时节省 token，当智能体仍需读取和编辑时增加成本。

VI 效度威胁

若干威胁限定了我们的发现。

内部效度方面，智能体运行并非完全确定性，相同的模型和提示可能采取不同路径或产出不同补丁。我们通过在各工作流间固定智能体技术栈、模型、effort 设置、提示和任务 ID，并将基础设施故障与表示内容效应分离来缓解此问题。然而，表示工作流还增加了使用引导，且在修复任务上增加了在原生读取之前强制执行一次地图查询的工具前使用钩子；因此，所测量的处理组合了表示内容、可用性和地图优先工作流，诸如原生读取减少之类的行为变化并非数据结构本身的效应。

外部效度方面，我们使用一个主要智能体技术栈和四个仓库级基准，因此结果可能因其他模型、智能体、语言或仓库而异，我们的结论针对这些任务类别而非全部软件工程。

构念效度方面，我们的指标近似于所关注的概念：基准成功率不能完全反映补丁质量或对开发者的有用性，token 和工具计数忽略了人力和一次性基础设施成本（地图构建、本地计算、克隆/Docker 设置、评分），且定性归因需要人工判断，因此我们仅在具备直接轨迹证据时才归因表示效应。

统计方面，我们以 95% 置信水平和 5% 误差幅度采样，并在各工作流间使用相同任务 ID，但每个实例在每个工作流下仅运行一次（k=1），而非采用 pass@k [37] 之类的多样本协议。较小的成功率差异（尤其是在 SWT-bench 和 SecBench 上）可能反映单次补丁或测试生成的方差；因此我们强调大而一致的效应和轨迹证据，而非微小的排名变化，并将接近的解决率视为描述性结果。

VII 结论

我们研究了代码表示如何影响智能体软件工程任务。我们将 AST、调用图、依赖、文档和混合仓库视图作为 MCP 工具暴露，并在故障定位、程序修复、测试生成和安全补丁任务上将其与非结构化仓库访问进行比较。

结果表明收益取决于任务。当定位是瓶颈时，代码表示帮助最大：它们改善故障定位，减少 token 使用量，并在不实质性改变解决率的情况下降低程序修复中的浏览工作量。当任务需要超出定位的能力时，权衡各有不同。Callgraph 改善安全补丁并减少 token 使用量，但所有表示工作流都增加了时间成本。对于测试生成，增益适中，而 token 和时间成本增加。

总体而言，软件工程智能体应根据任务瓶颈选择代码表示，而非采用固定的表示策略。原始搜索对精确字符串和非代码工件仍然有用，而结构化视图在代码关系引导定位时最为有用。
