基于LLM引擎集成的O-RAN高级AI服务供给

📅 2026-05-22 📄 arxiv 🔗 原文链接

原标题：Advanced AI Service Provisioning in O-RAN through LLM Engine Integration

中文摘要： 本文提出了一种用于O-RAN的“双脑”架构，将大语言模型（LLM）的编排能力与专用机器学习引擎的数值精度相结合，以自动化AI服务的配置生命周期。LLM编排器负责意图解析、数据管理和代码合成，而NeuralSmith引擎则训练轻量级、确定性的分类器。基于容器化O-RAN 5G SA测试台的实验表明，该架构实现了384毫秒的稳态编排延迟，并满足近实时RIC的亚10毫秒推理约束，为6G网络中的自动化AI服务交付提供了可行路径。

基于LLM引擎集成的O-RAN高级AI服务供给
Seyed Bagher Hashemi Natanzi, Pranshav Gajjar, Bo Tang, 和 Vijay K. Shah

摘要
开放无线接入网（O-RAN）架构允许通过模块化的 xApp 和 rApp 将 AI 直接嵌入到 RAN 中，然而创建这些应用——收集数据、训练模型、编写代码并安全部署——仍然缓慢且主要依赖人工。大语言模型（LLM）提供了强大的推理和代码生成能力，但不适合实时 RAN 控制中所需的快速、确定性推理。我们提出了一个概念验证的“双脑”架构，结合了双方的优势：基于 LLM 的编排器将运营商意图转换为数据收集策略和部署代码，而自动化 ML 引擎 NeuralSmith 则通过 API 按需训练轻量级分类器。我们描述了该架构和供给工作流，分享了来自容器化 O-RAN 5G SA 测试台的实用见解，并讨论了开放的研究方向。

I 引言
蜂窝网络已演变为软件定义的、日益智能的系统，人工智能（AI）被期望存在于部署和运营的每一层[13]。开放无线接入网（O-RAN）[12]架构是实现这一愿景的关键推动力：通过解耦基站并引入智能控制器，O-RAN 允许第三方 AI 应用程序（xApp 和 rApp）直接部署到 RAN 中。

然而，虽然部署 AI 应用正变得越来越容易，但创建它们仍然是一个重大瓶颈。供给一个新的 xApp 涉及网络工程师、数据科学家、软件工程师和部署工程师之间的一系列人工交接，通常需要数天到数周的时间——这对于需要响应快速变化的网络条件的运营商来说太慢了。

大语言模型（LLM）的快速发展促使业界发问：LLM 能否作为 O-RAN 内部的 AI 引擎？答案是微妙的。LLM 擅长理解意图、对系统进行推理和生成代码，但它们不适合实时数值推理：它们的延迟违反了近实时 RIC 的 10 毫秒预算，其输出是不确定的，并且其模型大小使得每个 xApp 的部署变得不切实际。

最近的工作已开始将 LLM 集成到电信和 O-RAN 的多个层中。早期研究探索了电信领域的生成式 AI[2]，而 NetLLM[14]则将 LLM 适应于视口预测和比特率自适应等网络任务。更接近我们领域的是，ORAN-Bench-13K[4]和 ORANSight-2.0[5]对 O-RAN 知识的 LLM 进行了基准测试和微调，揭示了通用 LLM 与 RIC 中所需的领域推理之间的差距。在系统层面，Hermes[1]提出了用于自主网络建模的链式 LLM 代理，LLM-xApp[15]将近实时 RIC xApp 内直接部署了 LLM，而最近的愿景工作则主张在 6G AI-RAN 中用代理编排器取代狭义的预测性 AI[6]。

本文的关键见解是，LLM 不应取代经典机器学习，而应编排它。我们提出了一种双脑架构，将基于 LLM 的零接触编排代理与专用 ML 引擎 NeuralSmith[7]配对。与先前的工作不同，我们的架构将编排与实时执行解耦：LLM 在非实时 RIC 层处理语义任务（意图解析、代码合成），而专用分类器在近实时 RIC 处理 10 毫秒以下的控制决策。与自由形式的代码生成不同，我们的模板约束合成消除了部署控制逻辑中的幻觉风险。本文描述了该架构，详细介绍了供给工作流，分享了来自容器化 O-RAN 5G SA 测试台的实用见解，并讨论了开放的研究方向。

II O-RAN 背景
我们简要回顾 O-RAN 架构以建立背景。已经熟悉 O-RAN 的读者可以跳至第 III 节。

II-A 架构概述
O-RAN 将基站解耦为 O-CU、O-DU 和 O-RU，通过开放接口连接[9]。两个智能控制器实现闭环网络管理。近实时 RIC 部署在网络边缘，运行在 10 毫秒到 1 秒之间，并托管 xApp 微服务，这些微服务通过 E2SM-Key Performance Measurement (KPM) 收集 RAN 数据，并通过 E2SM-RC 发出控制动作。非实时 RIC 运行在 1 秒以上，并托管 rApp 用于策略指导和生命周期管理，通过 A1 接口与近实时 RIC 通信。

O-RAN 中的传统 AI 部署涵盖监督学习（例如，流量预测）、无监督学习（例如，异常检测）和强化学习（例如，动态资源分配），每种通常作为分类器或策略嵌入在近实时 RIC 中。本工作的贡献不是 RIC 内部的另一个分类器，而是非实时 RIC 层的编排器，它通过 LLM 驱动的意图转换、数据管理和 xApp 代码合成，自动化此类分类器的创建和部署。

正如最后一行所强调的，本工作的贡献不是 RIC 内部的另一个分类器，而是一个自动化此类分类器创建和部署的编排器。

II-B 供给差距
WG2 规范定义了概念性的 AI/ML 工作流，但将实现留作开放。在实践中，供给新的 xApp 涉及一系列人工交接：网络工程师提取 KPM，数据科学家训练模型，软件工程师编写 xApp，部署工程师将其推出。每次交接都会引入延迟和错误风险。这种碎片化的过程可能需要数小时到数天——这对于需要响应快速变化的网络条件的运营商来说太慢了。

III 双脑架构
为了弥合这一差距，我们提出了一种双脑架构（图 1），基于一个简单的原则：让 LLM 思考，让 ML 引擎计算。

图 1：双脑架构。ZTO-Agent（LLM 编排器，非实时 RIC rApp）解析意图、管理数据并合成 xApp 代码。NeuralSmith（ML 引擎）训练轻量级分类器并通过 API 返回 ONNX 模型。训练后的模型被注入到预验证的 xApp 模板中并部署到近实时 RIC。

III-A 大脑 1：LLM 编排器（ZTO-Agent）
ZTO-Agent 是非实时 RIC 中的一个 rApp，由基础模型（在我们的原型中是 Llama-3.1-8B，但该架构与 LLM 无关）驱动。它处理三个任务：
1. 意图转换：运营商用纯语言提交目标（例如，“预测小区边缘拥塞并预留物理资源块（PRB）”）。ZTO-Agent 生成结构化规范：收集哪些指标，以何种粒度，如何标记数据，以及需要什么模型特征。
2. 数据管理：ZTO-Agent 从 gNB 收集 MAC 层遥测数据——包括每个 UE 的物理资源块（PRB）分配和信道质量指示符——并应用自动标记。对于拥塞预测，聚合小区 PRB 利用率超过饱和阈值（例如，总容量的 80%）的时间间隔被标记为拥塞。
3. 代码合成：在从 NeuralSmith 接收到训练好的模型后，ZTO-Agent 将 ONNX 制品注入到预验证的 Jinja2 xApp 模板中，该模板包含 E2SM-RC 控制逻辑和 ONNX Runtime 推理调用。因为 LLM 只填充模板变量——而不是任意代码——xApp 继承了模板的正确性保证。然后容器被注册到近实时 RIC。

III-B 大脑 2：ML 引擎（NeuralSmith）
NeuralSmith 是一个专用的 ML 引擎平台，可自动化完整的模型构建工作流[7]。在接收到来自 ZTO-Agent 的管理数据集和延迟预算后，它运行特征工程、超参数优化的模型选择（随机森林、XGBoost、LightGBM、紧凑型 MLP）、5 折交叉验证，并将获胜模型导出为带有验证报告的 ONNX 制品。

III-C 部署灵活性
运营商关注的一个关键问题是数据主权。NeuralSmith 支持灵活部署：完全本地部署（遥测数据永远不会离开运营商的边界）或私有云部署，具体取决于合同要求。ZTO-Agent 和 NeuralSmith 都可以在同一个计算集群上运行，使整个管道保持在运营商的信任边界内。

IV 供给工作流
完整的生命周期分为四个阶段（图 2）：

图 2：四阶段供给工作流：(1) 意图和遥测订阅，(2) 管理数据发送到 NeuralSmith API，(3) 返回训练好的 ONNX 模型，(4) xApp 模板渲染并部署。
注意：虽然该图反映了 633 毫秒的初始冷启动编排延迟，但系统在操作部署中实现了 384 毫秒的优化稳态（热）延迟。

阶段 1（意图 → 数据）。ZTO-Agent 解析运营商的自然语言目标，从 gNB 收集 MAC 层遥测数据（每个 UE 的 PRB 分配和 SNR），并自动标记聚合小区资源利用率超过饱和度的时间间隔。

阶段 2（数据 → NeuralSmith）。标记的数据集与任务类型和延迟预算一起传递给 NeuralSmith 的 API；NeuralSmith 训练、验证并导出 ONNX 分类器，如果超出延迟预算，ZTO-Agent 会以更严格的约束重新提交。

阶段 3（模型 → 实时 xApp）。ZTO-Agent 使用模型路径和动作参数渲染 Jinja2 模板，将其容器化，并在 FlexRIC 中注册；xApp 开始在近实时 RIC 的控制循环内执行。

在稳态条件下，在 Ollama 提供服务的 Llama-3.1-8B 端点上，端到端编排开销为 384 毫秒，完全在非实时 RIC 的 1 秒预算内，并且可以在专用 GPU 基础设施上进一步减少。

V 实现与实用见解
我们不是展示详尽的实验结果，而是分享在容器化 O-RAN 5G SA 测试台上构建和运行双脑架构所获得的实用见解。我们的设置使用 Docker 容器化的 OpenAirInterface (OAI) 组件[8]与 rfsimulator，三个模拟 UE 使用 iperf3 流量生成，以及 FlexRIC[10]提供 E2 接口连接。遥测数据从 gNB 的 MAC 层调度器日志中提取，这些日志以亚秒粒度提供每个 UE 的 PRB 分配、BLER 和 SNR 测量。尽管我们在这种最小拓扑上评估系统以隔离核心行为，但将 ZTO-Agent 和 NeuralSmith 容器化为微服务确保了该架构本质上可以扩展到多小区、多供应商部署。

V-A 效果良好的方面
关注点分离。在我们开发的早期，我们尝试使用 LLM 同时进行编排和推理，提示它从原始遥测值对拥塞状态进行分类。结果很差：延迟令人无法接受，相同输入的输出不一致，并且模型偶尔会幻觉出不存在的拥塞状态。将 LLM（思考）与 ML 引擎（计算）分离立即解决了所有三个问题。

基于模板的代码合成。通过限制 LLM 填充预验证的 Jinja2 模板而不是生成任意 xApp 代码，我们消除了基于 LLM 的代码生成最危险的故障模式：幻觉控制逻辑到达实时网络。我们的管道生成的每个 xApp 都继承了模板经过测试的正确性。这种方法直接满足了行业对健壮 AI 代理工具包的要求；通过将 LLM 的输出限制在预定义的参数空间内，我们的架构实施了结构性护栏，确保自主代码生成遵循标准化的信令流和安全协议。

rfsimulator 对编排基准测试的充分性。因为双脑管道完全在物理层之上运行，消耗 MAC 层遥测数据并发出 E2 控制动作，所以软件模拟的 RF 信道忠实地测试了系统使用的每个接口。确定性信道也使实验可重现，这对于迭代开发很有价值。

延迟约束的训练。在 NeuralSmith 的训练请求中指定推理延迟预算可确保返回的模型始终与近实时 RIC 的时间约束兼容。否则，自动化管道可能会生成准确但太慢的模型。

V-B 具有挑战性的方面
自动标记阈值敏感性。ZTO-Agent 的自动标记（将聚合小区 PRB 利用率超过 80% 容量的间隔标记为拥塞）在我们的场景中效果良好，但阈值的选择显著影响模型质量。在实践中，更细致的任务可能需要自适应或多阈值标记策略。

意图歧义。运营商的意图如“保护小区边缘用户”是有歧义的：保护免受什么？拥塞？干扰？切换失败？ZTO-Agent 有时会误解模糊的意图。带有澄清提示的结构化意图模板显著提高了可靠性。

依赖于部署的 LLM 延迟。通过 Ollama 提供服务的 Llama-3.1-8B 的 384 毫秒稳态编排时间完全在非实时 RIC 的时间预算内。然而，对于需要多步推理的复杂意图，较小的模型或仅 CPU 的部署可能难以满足 1 秒的阈值。使用三个额外的基础模型（Qwen-2.5-Coder-7B、Gemma4-26B 和 Llama-3.3-70B）重复管道在每种情况下产生了相同的 xApp——在生成的 Jinja2 模板参数和由此产生的 E2SM-RC 动作配置方面相同。如图 4 所比较，较大模型的较高延迟源于未优化的本地服务而不是结构性限制，确认该架构在适当托管时保持与 LLM 无关。

V-C 拥塞管理演示
为了演示提议的双脑架构管道，我们部署了一个预测性拥塞管理 xApp。
在此场景中，两个中心 UE 在 20 分钟内的六个开关周期中通过 iperf3 各自生成 20 Mbps 的突发 UDP 流量，而第三个小区边缘 UE 保持低速率后台会话。运营商输入意图：“预测拥塞并为边缘用户预留 20% PRB。”ZTO-Agent 收集 MAC 层遥测数据（每个 UE 的 PRB 分配和 SNR），将聚合小区 PRB 利用率超过 80% 容量的间隔标记为拥塞，并将管理的数据集分派给 NeuralSmith。

NeuralSmith 返回一个 LightGBM 分类器（ONNX，49 kB），实现了 97.7% 的准确率（F1：0.975），在 CPU 上的推理延迟低于 1 毫秒——完全在近实时 RIC 的 10 毫秒预算内。ZTO-Agent 随后使用训练好的模型渲染 xApp 模板并将其部署到 FlexRIC。尽管 rfsimulator 的确定性 AWGN 信道限制了原始特征多样性（SNR 和误块率 (BLER) 几乎恒定），但通过 PRB 分配上的滑动窗口聚合进行的时间特征工程使 NeuralSmith 能够高保真地学习拥塞发生模式。图 3 按阶段分解了编排延迟，确认意图解析主导了管道，而下游合成和部署增加了最少的开销。表 II 总结了完整的测量管道指标集，包括我们测试的四个基础模型的编排延迟和 NeuralSmith 分类器性能。

为了评估自动化 ML 相对手工编码启发式方法的价值，我们将 NeuralSmith 的 LightGBM 输出与一个简单的阈值规则进行了比较，该规则每当瞬时 PRB 利用率超过 80% 时就标记拥塞。阈值规则在相同测试集上实现了 84% 的准确率，但仅对已经发生的饱和做出反应。相比之下，LightGBM 分类器使用时间特征（例如滑动窗口上的 PRB 利用率均值和斜率），提前 2-3 个测量间隔预测拥塞的发生，展示了双脑管道中自动化特征工程的价值。

VI 研究方向
双脑架构为未来的研究开辟了几条途径，我们将其分为四个主题，我们认为这些主题对于将 LLM 编排的 O-RAN 供给扩展到生产部署最为重要。

从模拟到真实部署。我们的原型在软件模拟的 RF 信道上运行，它忠实地测试了编排接口，但掩盖了真实无线环境的可变性。弥合这一差距提出了两个耦合问题：如何通过域随机化和在线适应等技术使 NeuralSmith 训练的分类器对信道衰落、干扰和硬件损伤具有鲁棒性；以及如何克服当前阻止在一个站点训练的模型泛化到另一个站点的元数据碎片化。社区将从标准化的参考数据集中受益匪浅——实际上是无线领域的 MNIST——这些数据集捕获遥测和环境上下文，从而实现可重现的模拟到真实迁移以及自主供给的 xApp 的跨供应商可移植性。

安全性、信任和生命周期管理。自主生成的 xApp 引入了经典手工制作控制逻辑所没有的安全问题。三个方向显得尤为紧迫。首先，自主合成的 xApp 在部署前必须经过系统的正确性、鲁棒性和对抗性测试，将先前的 O-RAN AI 测试框架[11]扩展到 LLM 编排的领域。其次，当多个自主供给的 xApp 共存时，它们的控制动作可能会冲突；例如，一个提升吞吐量的 xApp 与一个节能 xApp 竞争相同的 PRB 池。部署前冲突检测——可能通过渲染模板的静态分析或共享参数的保护带强制执行——是重要的保障。第三，运营商和监管机构需要了解每个自动生成的 xApp 做了什么以及为什么；集成可解释性报告，显示分类器所依赖的特征以及 LLM 在合成期间做出的决策，对于生产采用至关重要。

闭环、置信度感知的编排。当前的管道是基于触发的：运营商提交意图，构建并部署 xApp，系统等待下一个意图。两个扩展将把这转变为一个持续学习循环。ZTO-Agent 可以监控实时 xApp KPI，并在检测到性能漂移时重新触发 NeuralSmith，从而在没有运营商干预的情况下实现自我修复的 AI 服务。与此同时，编排层本身将受益于校准的不确定性估计。ZTO-Agent 核心的 LLM 在模糊的网络条件下可能产生过度自信的输出，而最近关于基于 LLM 的自主控制的保形预测[3]的工作提供了一种原则性的方法，将可靠性保证附加到意图解析和自动标记决策上。低置信度的情况随后可以被标记供人工审查，弥合完全自主和运营商信任之间的差距。

高效且可移植的 LLM 后端。两个实际问题决定了双脑架构可以广泛部署的程度。第一个是计算成本：虽然 8B 参数的 LLM 可以在配备 GPU 的非实时 RIC 基础设施上舒适运行，但较小的小区站点和边缘部署将需要更轻量级的后端。针对电信专用小语言模型、参数高效微调以及针对编排提示的结构化特性调整的推测解码的研究，可以大大降低这一障碍。第二个是可移植性：跨供应商特定 E2 实现泛化 xApp 模板需要更深入地标准化 xApp 打包和 E2SM 配置文件协商，以便相同的意图可靠地生成可互操作的 xApp，而不管底层的 RIC 平台如何。

VII 结论
在 O-RAN 中创建和部署 AI 服务的过程仍然主要是手动的。本文提出了一种双脑架构，将 LLM 的编排能力与专用 ML 引擎的数值精度相结合，以自动化整个供给生命周期。基于 LLM 的编排器处理意图转换、数据管理和代码合成；而 ML 引擎 NeuralSmith 则通过简单的 API 训练轻量级、确定性的分类器。我们在容器化 O-RAN 测试台上构建系统的经验表明，该方法是实用的，实现了 384 毫秒的稳态编排延迟，同时满足近实时 RIC 的亚 10 毫秒推理约束。虽然我们的原型在单个下游任务上端到端地演示了管道，但在空中部署和额外用例中的验证仍然是重要的未来工作。该架构与 LLM 无关，保留了数据主权，并为 6G 网络中的自动化 AI 服务交付提供了一条可重现的路径。
