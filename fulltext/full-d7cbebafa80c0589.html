摘要。
Python 是一种广泛采用的编程语言，因其简单性和灵活性而备受青睐。然而，Python 的自动化重构仍然充满挑战，尽管重构是软件演进中的一项基本实践，旨在改善内部代码结构而不改变外部行为。了解在重构过程中是如何引入行为变更的至关重要，因为这些问题会损害软件的可靠性并降低开发者的生产力。我们提出了一种基于基础模型预言机的方法，该方法通过分析 git 风格的 diff 来识别 Python 重构引入的行为变更。我们在 Rope 重构实现上评估了我们的技术，复用了先前研究中的 1,152 次重构尝试，并用预言机分析了 217 个生成的转换对。我们基于模型的分析在所研究的七种重构类型中发现了 13 个不同的 bug。所有报告的 bug 都已提交给相应的开发者，根据问题追踪器的证据，13 份问题报告中有 12 份被接受。这些结果凸显了需要提高当前 Python 重构工具的鲁棒性，以确保自动化代码转换的正确性并支持可靠的软件维护。

3.
检测重构中的行为变更
本节详细说明了我们如何使用 git 风格 diff 和基础模型预言机扩展 SafeRefactorPy，以检测 Python 重构引起的行为变更。
3.1.
概述和重构应用
概述。我们的技术以 Python 程序、被测的重构实现、目标位置和任何所需参数作为输入（步骤 1）。如果转换成功，它会计算原始程序和重构程序之间的 git 风格 diff（步骤 2），并将该 diff 提交给基础模型预言机，由其决定该实例是否保留可观察行为（步骤 3）。在分析了所有实例之后，分类算法汇总结果，识别重复的失败模式，并为专家检查组装 bug 报告（步骤 4）。如果重构工具抛出异常，此结果将直接记录在 bug 报告中。图 1 提供了行为变更检测流水线的概述。

3.2.
Diff 生成
在应用重构之后，我们的技术计算程序的原始版本和重构版本之间的 git 风格 diff。此 diff 用作行为变更检测阶段的输入。预言机只接收此 diff；它不接收完整的源文件或完整的项目。清单 2 显示了一个典型的 git 风格 diff。我们使用 git 风格 diff 作为预言机输入有三个原因。首先，diff 提供了转换的紧凑表示，这有助于解决基础模型的上下文窗口和推理成本限制。将整个项目提供给模型对于现实世界的代码库可能是不切实际的，而 diff 暴露了重构引入的具体编辑。其次，diff 将预言机集中在转换本身上，减少了不相关的项目上下文，使分析更接近开发者在代码审查中检查重构变更的方式。第三，该格式与工具无关：任何产生原始程序和生成程序的重构引擎都可以通过生成相应的 diff 来集成。这种设计对于 Python 重构特别有用，因为行为保留违规可能源于涉及特殊方法、动态分派、名称解析、导入或缩进敏感作用域的小编辑。通过向模型展示精确的修改集合，SafeRefactorPy 优先检测可能被传统前置条件检查或仅仅通过观察转换成功完成而遗漏的行为变更。这种选择也是一种方法论上的权衡：使用 diff 提高了可扩展性、成本和可移植性，但它可能会遗漏依赖于 diff 中不可见的项目上下文的影响，例如外部调用者、子类交互或导入时依赖项。

我们使用以下提示：
你是一名专门从事重构的编码助手。
你将收到一个统一 diff（git 风格），它将初始程序转换为生成程序。仅使用 diff 中的信息和一般语言语义来判断一个条件：
1) 行为：初始程序和生成程序具有相同的可观察行为（相同的输出、异常、外部可见状态、时序/同步）。
假设（严格应用）：
- diff 中未显示的代码保持不变。
- 如果一个符号被重命名，并且所有受 diff 影响的引用都被一致地更新，则假设其他调用点（未显示）也被更新，除非 diff 提供相反的具体证据（例如，移动/重命名而未更新同一文件中的引用）。
- 忽略仅注释和仅空格的更改。
- 将添加的日志记录/打印、同步、异常类型更改、常量值更改和评估顺序更改视为可能改变行为。
- 不要发明缺失的文件或符号；根据 diff 显示的内容加上语言规则（例如，方法重写规则、访问修饰符、包/模块可见性、泛型边界、受检异常）得出结论。
分析步骤：

误报
我们将预言机预测为行为变更而专家识别转换为保留行为的任何情况称为误报。相反，当预言机预测行为保留而专家识别出行为变更时，就会发生漏报。更一般地，预言机和专家之间的任何不匹配都构成分歧。这种差异的一个重复出现的原因是 Python 使用缩进来定义类和函数作用域的方式。这种语法特性使得我们基于 git 风格 diff 进行推理的预言机特别难以正确解释某些转换。在 Python 中，声明的作用域取决于其前面的空格字符（空格或制表符）的确切数量和类型。对于底层的基础模型，这需要正确解析和语义解释 diff 中的空格，而不是仅仅依赖更显著的词法标记。相比之下，人类专家可以通过视觉检查代码的缩进结构快速推断作用域。

5.
有效性威胁
我们的评估涉及一些有效性威胁。首先，行为等价基线来自单个专家的手动判断，随后对预言机答案的检查以及将失败执行合并为不同的 bug 报告也需要手动判断。这些步骤可能会引入主观性或偶尔的错误分类，特别是在边缘案例中。我们通过要求为专家标签提供书面理由、将每个报告的问题缩减为最小重现程序以及将生成的 bug 报告提交给工具维护者进行外部检查来减轻这种威胁。尽管如此，维护者反馈仅验证了报告的 bug 候选，而不是全套专家标签。因为精确率、召回率、准确率和 F1 分数是针对此专家基线计算的，所以基线中的任何歧义或错误都可能直接影响报告的指标。因此，未来的复制应该包括多个独立评估者、分歧裁决和评估者间一致性度量。
其次，我们的研究基于单个真实的 Python 项目 TextBlob，以及 Rope 支持的重构类型子集。尽管 TextBlob 提供了大量的语法多样性，并且这些重构在实践中被广泛使用
(Murphy-Hill et al
.,
2012
)
，但结果可能无法推广到所有 Python 代码库、语言特性或重构操作。此外，217 个分析的转换对支持了一项专注于 bug 发现和预言机评估的研究，但它们不支持关于 Python 重构 bug 的广泛普遍性声明。行为变更实例在内联方法中的集中也意味着汇总指标可能更多地反映了此重构类型的特征，而不是其他重构类型的特征。此外，我们在其他 IDE 中的手动验证是探索性的，而不是系统性的，因此不应将其解释为全面的比较评估。额外的项目、工具、IDE 和重构类型是我们未来工作的一部分。
第三，预言机是有意限定在 diff 范围内的：模型和人类基线都仅对 diff 中显示的已编辑代码进行推理，将未见的代码视为未更改。这种选择提高了在真实世界项目上的可行性，但它可能会遗漏依赖于 diff 之外的外部调用者、子类层次结构或导入时交互的项目范围影响。同样，Python 对缩进敏感的语法使得某些转换难以仅从 diff 中解释，这导致了一些误报和漏报。因此，我们的结果表征了 diff 局部的行为变更检测，而不是完整的项目感知的语义等价。项目感知的基线，或丰富了选定项目上下文的 diff，可能会改变涉及公共 API、子类或导入的边缘案例的分类。
最后，我们的构建和结论效度受到主要评估中使用单个基础模型的限制，我们的方法仅针对行为变更而不是所有类别的重构 bug 的事实，以及每种重构类型有限的数据集大小的限制。因此，结果可能反映了 gpt-oss-20b 的特征，以及对类别不平衡和观察值之间依赖关系的敏感性。补充性的 GPT-5.2 分析是探索性的，不应被解释为受控的模型比较。我们也没有将预言机与 TextBlob 的测试套件、静态分析或基于字节码的检查进行比较，因此我们的评估没有确定这些替代方法可以发现多少检测到的行为变更。我们的技术应被视为测试套件和其他验证技术的补充，而不是完全替代。未来的工作应该调查其他模型、更广泛的 bug 类别、更多的项目/工具以及更强的统计报告，例如置信区间。

结论
我们扩展了 SafeRefactorPy，使用一种基于模型的方法来检测 Python 重构引入的行为变更。通过分析 217 个转换，SafeRefactorPy 在所研究的 7 种重构中识别出 13 个不同的 bug。这些转换表面上看起来是成功的，这使得检测到的 bug 非常相关，因为它们没有被显式的工具失败或先前的问题指示所暴露。报告的 13 个 bug 中有 12 个被开发者接受。这些结果表明，基于 diff 的基础模型预言机可以以良好的准确率暴露 Python 中的行为变更失败。对于开发者来说，这强化了验证重构结果的需要，而不是完全依赖工具自动化。对于工具构建者来说，它突出了对更强前置条件和验证机制的需求，特别是在 Python 等动态语言中，该语言具有动态分派、数据模型方法、名称解析和继承契约等具有挑战性的机制。我们的结果表明，基础模型可以成为传统重构验证技术的宝贵补充，在传统技术中，行为变更难以表达为静态规则或难以通过现有检查检测到。此外，观察到的可变性、成本和 diff 范围限制表明，这些模型最好用作额外的验证层，而不是作为静态和动态分析技术的替代品。因此，SafeRefactorPy 应被解释为用于可疑重构转换的实用 bug 发现辅助工具，而不是一个完整的正确性预言机。我们的方法受益于 git 风格 diff 的紧凑性，这使得无需将完整项目作为输入即可进行大模型分析，但它仍然受到模型成本和基于 diff 的推理范围的限制。未来的工作包括评估额外的重构工具、涵盖更多的重构类型，以及探索用于验证和修复的多模型或代理配置。
