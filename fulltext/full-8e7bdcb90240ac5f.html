原标题：Made by VentureBeat with Gemini

中文摘要： 随着 AI 智能体接管代码编写工作，软件工程师的角色正发生深刻转变。文章借用热力学、无限猴子定理和三体问题，指出智能体在复杂企业系统中容易产生“操作熵”并陷入混沌。工程师的新使命不再是编写微逻辑，而是“设计平衡”：通过构建数据契约、语义层和确定性边界，为智能体创造可信任的生成环境，将系统运动转化为有用功。

Ananth Packkildurai
太平洋时间 2026 年 8 月 31 日 上午 11:52
由 VentureBeat 携手 Gemini 创作

如果你查看现代数据平台的提交历史，会发现过去两年间发生了一些深刻的变化。编写语法的摩擦已经消除。随着 Cursor、Claude Code 和智能体工作流如今驻留在我们的 Docker 容器和 IDE 中，生成分布式流处理管道或复杂 API 集成的初始实现不再是核心瓶颈。

智能体可以浏览代码库、编写测试覆盖、检查堆栈跟踪并提出重构建议。用通俗的英语描述一个从 Kafka 到 Iceberg 的接收器映射，智能体就能在工程师打开所有相关文件之前，产出一个可靠的起点。

这改变了软件工程师面临的问题。

如果智能体正在成为本地系统逻辑的主要编写者，那么工程师还剩下什么工作要做？我们是否正走向一个由审查者机械地批准源源不断、看似合理的拉取请求的行业？还是说工作已经从构建逻辑转向了更抽象的东西？

为了回答这个问题，借鉴热力学的视角会有所帮助，它为我们提供了一种关于有向功、反馈、损耗以及保持复杂系统连贯性的边界的语言。

作为热机的智能体

当我们剥离 AI 拟人化的错觉后，剩下的就是一个计算引擎。它接收指令并将其转化为行动。

位于数据中心的 LLM 拥有巨大的容量，但在被赋予意图之前，它不会做任何有用的工作。一个提示词、一项业务需求、一条系统指令或一个失败的测试，都为智能体指明了方向。它将这种方向转化为代码、工具调用、查询、测试以及对运行系统的更改。

每个引擎都有损耗。每个智能体循环也是如此。

任何让智能体在复杂的代码库上持续运行过的人都会看到这一点。它从一个清晰的任务开始。然后它遵循一个过时的假设，治标不治本，把旧的迁移当作当前行为，并开始积累自己的历史。几次工具调用之后，上下文中就充满了看似合理但相互冲突的细节，以至于下一步比第一步更加不确定。

将此称为“操作熵”：在仍然试图向前推进的循环中，过时的假设、分支上下文和未解决的依赖关系的不断积累。

人类干预之所以有帮助，是因为它引入了新信息。失败的测试、精确的数据契约、确定性工具或能准确告诉智能体哪里错了的评估，也同样有效。没有这种信号，智能体会不断产生输出，同时却离正确的结果越来越远。

智能体显然产生了运动。真正的问题是它们周围的系统是否将这种运动转化为有用功。

无限猴子与不断加速的搜索空间

无限猴子定理为我们描绘了一幅有用的后续图景：反复尝试、有限约束和反馈。

该定理指出，一只猴子随机敲击键盘无限长时间，几乎肯定能打出莎士比亚的全集。现代智能体是更聪明的猴子。它们有编译器、工具、代码库、测试套件和反馈循环。它们的工作不是随机的——反馈引导着下一次尝试——但这种动态机制很熟悉：提出、执行、观察、纠正，然后再试一次。

在有边界的任务中，这个循环非常有效。

给智能体一个已知的输入模式、一个已知的目标模式、一个小型代码库以及能捕获相关故障的测试。它可以检查代码、进行更改、运行测试、吸收结果并重试。“完成”的定义是可见的。搜索空间很窄。循环有机会收敛。

但企业系统很少提供这种静止状态。一个实时定价引擎可能依赖于可变的操作状态、第三方 API、迟到的事件、区域政策以及部分存在于代码中、部分存在于某人头脑中的业务规则。一个数据湖仓在物理上可能是一致的，但在语义上却是错误的。一个管道可以通过测试，但仍然产生财务部门无法识别的数字。

环境在猴子打字时正在发生变化。

企业逻辑的三体问题

这就是为什么三体问题对企业软件来说是如此有用的形象比喻。

对于两个天体——一颗行星和一颗恒星——你可以用简洁的数学描述来预测其运动。加入第三个天体，问题就变得难以解决。没有通用的封闭形式解，某些配置会表现出混沌行为。一个地方的微小变化会在另一个地方产生截然不同的轨迹。

现代数据平台具有相同的形态。点击流数据随着产品行为而变化。操作数据库在客户活动下发生突变。API 施加速率限制并更改版本。模式不断演进。安全策略发生转变。遗留系统带着没人写下来的规则，因为它们多年来一直被埋没在异常处理中。

每个系统都对其他系统施加压力。一个地方的改变会改变另一个地方的含义或行为。一开始作为局部功能请求的东西，最终会牵动整个系统。

考虑一个假设：智能体被要求向收入模型中添加一个 customer_tier 字段。它在操作数据库中找到一个名为 status 的字段，将其映射到转换中，并通过了现有的类型和可空性测试。代码很干净。管道亮绿灯。但答案仍然是错的。

语义数据契约规定，customer_tier 源自过去十二个月的消费额，有指定的业务负责人，并且不能从账户状态中填充。契约在更改到达仪表板之前就拒绝了它。工程师的贡献不在于转换逻辑——而在于建立边界，使得智能体的错误变得可见、具体且可恢复。

新使命：设计平衡

软件工程师的工作不再是编写每一块微逻辑。智能体将越来越多地承担这项工作，而且通常更快。新的使命——设计平衡——就是创造可以信任生成逻辑的条件。

当业务需求的变化速度快于智能体吸收反馈的速度时，工程师必须构建“遏制场”。严格的语义层、不可变的事件日志、数据契约、幂等 API 和确定性状态机不仅仅是良好的平台规范。它们减少了智能体一次必须做出的假设数量。

它们将一个耦合问题转化为具有清晰输入、明确规则和可靠反馈的有界领域。

一旦这个领域存在，智能体就会变得真正强大。它可以编写转换、执行测试、修复故障并交付更改，而无需推断每个表和服务背后未写明的历史。

随着代码生成成本的降低，软件工程的价值并没有消失——它变得更加明显，这才是真正重要的转变。

自治系统将越来越多地生成软件。但是，决定这些软件是成功还是陷入混乱的契约、反馈循环和边界，仍将由软件工程师来设计。
