大规模运行 AI 智能体的企业团队发现，单一模型很难妥善处理所有任务——要么对于简单问题来说模型太贵，要么对于复杂问题来说能力不足。模型路由可以自动为每个任务选择合适的模型，正成为解决这一问题的方案。

Snowflake 的 Cortex AI Gateway 现在提供了动态模型路由来解决这一问题：企业可以选择“自动”而不是固定模型，系统会将每个任务路由到能提供最佳质量与成本组合的模型上。Snowflake 表示，该功能可以在某些工作负载上将 token 成本降低多达 3 倍——这一数据来自公司内部的测试——此前他们发现，简单问题往往由其最强大的模型来处理，导致响应比必要的更昂贵、更慢。

此举正值行业向自动化模型路由进行更广泛转型之际。Databricks、AWS、Google Cloud 和 Nvidia 都已宣布了某种形式的模型路由技术。Snowflake 认为，模型路由不仅仅是价格和性能的问题，还涉及治理和上下文。

Snowflake 人工智能副总裁 Baris Gultekin 告诉 VentureBeat：“要构建高质量的企业级智能体，正确处理上下文和治理至关重要。上下文、信任和模型选择是相辅相成的。”

两种机制决定任务去向

该功能基于 Cortex AI Gateway 构建，Snowflake 于 2026 年 7 月推出了该网关，作为智能体和模型流量的治理层。Gultekin 表示，在动态路由之前，模型选择是基于每个任务的静态列表，而不是真正的回退系统。

Gultekin 表示，动态路由本身依靠两种机制运行。

先尝试小模型。
在 Snowflake 所称的“顾问模式”下，较小的模型会首先尝试执行任务。如果它无法完成工作，它会调用较大的模型作为工具并从那里继续。

分类器根据任务历史进行排序。
一个基于过去查询训练的独立分类器，会自动将简单直接的问题路由到更简单的模型。

客户仍然可以固定模型。
自动路由是可选的。客户可以将路由限制在一个模型或一组指定的模型上，系统只会在该范围内进行路由。

没有单独的费用。
Snowflake 的 AI 定价纯粹基于 token 使用量。路由到更便宜的模型会产生更低的账单，路由决策本身不收取额外费用。

访问控制跟随任务，而不仅仅是数据

Snowflake 将路由与其已用于数据治理的访问控制绑定在一起。

治理从数据级别的基于角色的访问控制开始。接着它扩展到模型，客户的角色映射到已批准的模型集合。然后它再次扩展到智能体，智能体可以被限制为比调用它的用户拥有更窄的权限。

开放模型可以在客户自己的区域运行，以满足数据驻留要求。Gultekin 表示，所有的推理，无论是开放的还是专有的，都留在 Snowflake 的安全边界内，而不是路由到外部提供商。这种区域和边界设置对于源自非美国的开放模型尤为重要，包括在中国开发的 DeepSeek-V4-Flash 和 GLM-5.3。

Snowflake 最近对 Natoma 的收购增加了另一层保障。这笔交易带来了 100 多个具有范围限制和受治理访问权限的 MCP 连接器。例如，智能体可以获得对电子邮件等连接工具的只读访问权限，而不是更广泛的权限。

上下文让更便宜的模型完成工作

Snowflake 最近宣布了其 Horizon Context 和 Cortex Sense 工具，提供上下文能力。

如果没有良好的上下文，模型必须自己进行探索性工作，编写和测试 SQL，搜索数据并在出现问题时重试。Gultekin 解释说，这个过程很昂贵，而且要正确完成通常需要能力更强的模型。提前打包上下文可以消除这一探索步骤，这意味着一个更简单、更便宜的模型通常可以处理相同的任务。

Snowflake 还将智能体记忆构建到该上下文中。随着智能体被重复使用，它的记忆会更新并融入到未来的查询中。系统不会每次都从头重新解决相同的问题。记忆成为传递给模型的上下文的一部分。

OpenRouter、Databricks 和 Nvidia 正在追逐同一问题

模型路由领域并不缺乏技术。OpenRouter 是最广为人知的选项之一，它提供了一个平台，使组织能够基于成本和性能进行路由。Nvidia 在 8 月 11 日宣布了 Switchyard 作为帮助路由 AI 模型选择的技术层。Databricks 也为其 Unity AI Gateway 提供了 Smart Routing 产品。

SanjMo 负责人兼创始人 Sanjeev Mohan 告诉 VentureBeat：“有趣的部分在于它说明了差异化已经转移到了哪里。Snowflake 并不是真的在卖路由，它卖的是从不离开受治理数据边界的路由，并且已经附带了访问控制、标签和成本归因。”

Mohan 补充说，对于一家数据和合规已经以 Snowflake 为中心的公司来说，保持数据原位并按团队归因支出的路由是解决该问题的真正杠杆。对于没有这个重心的公司来说，中立的网关可能会以更少的摩擦跨更多模型进行路由。

Mohan 将市场划分为三个截然不同的阵营，而不是一个竞争领域。Databricks 从数据工程和机器学习血缘的角度切入治理。其 Unity Catalog 为构建和训练模型的团队治理数据、模型和管道。Snowflake 从分析和访问控制的角度切入治理，治理谁可以接触哪些数据，并跨业务部门归因使用情况。第三个阵营包括中立的网关，如 OpenRouter、LiteLLM、Portkey 以及超大规模云厂商的路由器（如 Azure AI Foundry）。它们在模型广度和避免锁定方面展开竞争，而不是在深度治理上。

选择路由器意味着选择治理模型

模型路由现在已成为企业的基本要求。重要的决定是哪种治理模型已经适合其数据和团队的组织方式，而不是哪家供应商的路由器最快或最便宜。

在智能体规模下，手动模型选择正成为成本负担。
当团队运行少数几个智能体时行之有效的方法，在规模扩大时会失效。数百个智能体进行常规模型调用，如果没有自动化的成本检查，费用会迅速增加。

评估治理模型，而不是路由器的功能列表。
Mohan 认为，真正的问题是哪种治理模型与现有的数据资产相匹配，以及哪一种能提供避免不愉快惊喜所需的成本可见性。

正确的起点取决于企业数据已经存放在哪里。
Mohan 表示，一个以 Snowflake 为核心的平台从尊重其现有访问模型并将费用计回成本中心的平台内路由中获得的价值，比从原始的模型广度中获得的更多。一个以 Databricks 为中心、担心跨训练和部署血缘的团队，更适合使用围绕相同血缘构建的网关。一个多平台或模型优先、希望以最小锁定获得最大选择的团队，更适合中立的网关，这也是 OpenRouter 估值背后的卖点。

Mohan 说：“对于从业者来说，不要从路由器开始，而要从受治理数据和平台承诺已经存在的地方开始，以及从你的利润率受推理成本影响的程度开始。”
