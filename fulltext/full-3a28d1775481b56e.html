摘要

机器学习代码应当运行在研究者选择的地方，而不是它最初被编写的地方。如今，机器学习代码主要存在于两个生态系统中：NVIDIA GPU 上的 PyTorch 和 Google TPU 上的 JAX。在两者之间迁移仓库意味着跨框架和跨硬件进行构建与测试。这种迁移（1）是一种实际需求，因为它为研究者解锁了不同的硬件；（2）也是一个天然的基准测试：它涉及不同的框架和硬件，覆盖整个仓库，且是长时程、具有挑战性的。我们提出 XStack，一个评估智能体在这两个生态系统之间迁移机器学习仓库能力的基准。每个智能体接收一个 PyTorch 仓库和一台干净的 TPU 机器，必须交付一个 JAX 仓库。其输出若满足我们的评分标准即为通过，该标准基于源仓库已发表的结果，并经我们认证和校准。智能体的迁移仍然不可靠：Claude Opus 5 通过 75%，GPT-5.6-sol 通过 45%，其他所有智能体至多 40%。XStack 是将机器学习代码从其生态系统中解放出来的一步。我们发布 XStack，以使跨框架和硬件的可靠迁移的进展可衡量。

1 引言

假设你找到了一个恰好满足你需求的仓库。它的论文报告了强劲的结果，代码是公开的，实验也已被证明可行。只有一个问题：它是为错误的机器构建的。你的实验室有 TPU，但该仓库假设使用 GPU 和 PyTorch。虽然原则上科学思想并不依赖于这一选择，但实际上你被困住了。使用它意味着用 JAX 重写模型、优化器、数据管道和评估（因为那是 TPU 所运行的技术栈），然后让一切在不同的编译器、内存层次结构和分布式执行模型下正常工作。看似实现细节的东西变成了复用科学的障碍。一个团队碰巧拥有的硬件可以决定它能基于哪些已发表的思想进行构建。

这正是编码智能体应当消除的障碍。大量已发表的机器学习代码是为 GPU 上的 PyTorch 编写的，而人们也使用 TPU，后者通常通过 JAX 编程。JAX 是 Google 的 Python 数组计算库；它用 XLA 编译器编译 NumPy 风格的代码以在 TPU 和 GPU 上运行。到 2025 年底，TPU 占全球 AI 算力的近五分之一（18.2%）：2093 万 H100 等效算力中的 381 万。然而，2024 年随机器学习论文发布的基于框架的代码中只有 4.2% 使用 JAX。这创造了将可工作的系统跨软件和硬件栈迁移的日益增长的需求，这是研究者关心的现实任务，因为它解锁了对不同硬件的访问。这样做意味着不仅跨越代码级框架边界，还要跨越机器级差异。这正是我们希望智能体解决的问题；我们希望将纯粹的科学还给研究者，并为此进展提供度量。

迁移既改变硬件也改变代码，所以智能体必须做的不仅是翻译代码。

我们直接提出以下问题：

智能体能否正确地将一个可工作的机器学习仓库迁移到新框架和新硬件？

现有基准并不能很好地测试这一点。问题解决类基准从损坏的代码开始，要求智能体修复它；而转换类基准在同一台机器上比较翻译后的代码与原始代码。在我们的场景中，仓库已经在原始机器上正常工作。挑战在于在将整个系统迁移到原始代码不支持的硬件上时保持该行为。我们提出 XStack（XStack 代表 Cross-Stack Benchmark，跨栈基准）来直接测试这一点。每个任务给智能体一个可工作的 PyTorch 仓库和一台干净的 TPU 机器，然后要求它在 TPU 上用 JAX 重建代码，并使一个原始实验端到端运行并达到其已发表的结果。

上述问题的答案目前是否定的：智能体在此任务上并不完全可靠。我们的结果表明这一障碍开始瓦解，但尚未消失。最强的智能体成功迁移了 20 个仓库中的 15 个。因此智能体已经能够在仓库规模上跨越框架和硬件边界迁移一些机器学习系统。然而这种能力在智能体和仓库之间远不可靠。智能体开始松动科学代码与其编写时所针对的技术栈之间的联系，但我们仍未达到研究者可以随意在任何地方运行已发表工作的程度。

从失败中浮现出一个更广泛的模式：智能体可以编写大量代码，但它们在验证所构建的东西是否忠实、完整且在真实环境中实际可用方面仍然可靠性低得多。这在各模型中表现为遗漏评估、保真度差距、崩溃，甚至在卡住时试图绕过任务。

总体而言，我们的贡献是：

  • 我们提出 XStack，一个包含 20 个真实仓库的基准，用于测试智能体能否跨框架和硬件迁移可工作的机器学习系统。
  • 我们在真实 TPU 上评估了七个编码智能体，并发布评分标准和完整的智能体轨迹，使这一能力的进展可衡量。
  • 我们发现智能体有时可以完成这些迁移，但仍难以可靠地验证所构建的东西是否忠实、完整且端到端实际可用。我们还观察到通过率随智能体成本的对数线性增长（图 6）。

2 XStack 基准

图 2：XStack 流程。上：智能体将 PyTorch 仓库迁移到裸 TPU 上的 JAX。下：我们在全新 TPU 上重新运行输出，将其数字与源的结果以及两个模型裁判进行核对。如果失败，对齐步骤（阶段 2，粉色）向智能体给出主实验的配方，只允许它更改入口脚本，并重新评分结果。通过还需要权重能加载到原始 PyTorch 模型中。

XStack 中的每个任务是一个已经正常工作并报告结果的 PyTorch 仓库（图 2）。智能体将其迁移到裸 TPU 机器上的 JAX，我们在全新机器上重新运行迁移后的代码以检查其是否满足我们的评分标准。为公平起见，评分分为两个阶段：如果第一次尝试失败，第二阶段告诉智能体我们评分哪个实验，这样正确的迁移不会仅仅因为运行了不同的实验而被判失败（2.2 节）。数值目标保持隐藏，只有入口脚本可以更改；所有其他代码和设置保持冻结。2.1 节定义任务，2.2 节解释我们如何评分，2.3 节描述我们的仓库和智能体。

2.1 任务表述

输入。智能体接收仓库（固定到一个 git 提交，使每个智能体看到相同的代码）和一台 TPU 机器。一个对所有仓库相同的提示模板要求它将整个仓库迁移到 JAX（模型用 Flax，优化器用 Optax），并按源运行实验的方式全规模运行它。对于四个源提供多种配置的仓库，一两行额外的文字命名评分配置或评分器使用的标志，使每个智能体知道它必须做什么而不了解评分目标（附录 B）。

机器设置。机器上没有机器学习软件；设置它是任务的一部分：智能体安装每个包，获取数据并决定如何使用其主机。它在我们集群的沙箱中工作，通过 SSH 连接到机器，在产出输出期间没有时间限制（附录 C）。

输出。智能体交付带有三个脚本的迁移仓库。setup_env.sh 准备一台干净的机器，入口脚本 run_train.py 训练、评估并写入指标，export_torch.py 以源的参数名称保存权重。在阶段 1 中，智能体不会被告知我们评分哪个数字、要达到什么值或是否通过（表 2），所以它必须迁移整个仓库，而不是单个实验。

2.2 迁移评分

达到评分目标。我们将迁移后的仓库（不含其 git 历史）复制到一台新擦除的机器上，运行 setup_env.sh 和 run_train.py 一次（图 2 的紫色阶段）。一个脚本（评分器）将评分数字与评分目标（通常是源发布的数字）进行比较，带有容差（附录 A）。每个评分目标遵循源已发表的结果，我们针对固定提交的源进行了认证；对于 3 个仓库，我们从自己运行未修改源的结果中设定目标，对于 minGPT 则按规则设定（2.3 节）。忠实的迁移通过复现仓库达到评分目标，而无需知道目标。在预期运行时间十倍内未写入指标的运行判为失败。

裁判。一个数字也可能因错误的原因达到评分目标，例如较小的变体或另一次运行的文件。因此两个模型裁判（均为 GPT-5.6-sol）审查每个达到评分目标的结果（图 2 的验证者）。正确性裁判检查数字是否来自本次运行的主实验训练，作弊裁判检查智能体是否通过作弊达到目标，例如钳制指标或使用另一次运行的文件。结果只有在达到评分目标、两个裁判都接受且其权重能加载到源模型中时才通过。

两个阶段。在标准隐藏的情况下，智能体可以正确迁移代码但运行我们不评分的实验，例如 AST 的 ESC-50 配方而不是 Speech Commands。将其评为失败会惩罚任务从未指定的选择。阶段 2 在不使任务更容易的情况下消除了这种不公平：在阶段 1 失败后，一条消息（图 2 的对齐步骤）冻结除入口脚本之外的一切，并给出主实验的配方，但不给出评分目标（表 2）。更改任何其他文件会因违反冻结而使阶段 2 失败，裁判会拒绝入口脚本重建冻结代码的通过（破坏冻结）。我们报告阶段 2 后的通过率作为主要结果。

2.3 仓库和智能体

图 3：XStack 的仓库。行将 20 个仓库分为三个任务族。每个名称旁边的数字是一次评分运行的预期持续时间（小时），该运行以源的完整规模训练模型。

仓库。XStack 包含来自十四个领域的 20 个仓库（图 3；表 A1 给出每个评分目标）。七个是语言模型：minGPT、nanoGPT、makemore、llama2.c、modded-nanoGPT、nanochat 和 x-transformers。其余是 LoRA、SimCSE、airbench、AST、S4、HSTU、TD-MPC2、TensoRF、nanoVLM、deepspeech、TGN、PatchTST 和 TabR。我们从 200 多个 PyTorch 仓库中挑选它们，大多数因已发表的数字问题而被拒绝。

评分目标。对于 15 个仓库，评分目标是 README 或论文报告的数字，我们针对固定提交的源进行了认证；deepspeech 的来自其发布说明。公平的目标必须是原始代码本身能达到的，我们的实验确认这些目标中的每一个都可以达到。对于另外 3 个仓库，我们从自己在 GPU 上运行未修改源的结果中设定目标。例如，makemore README 报告损失约 1.92，但我们在 GPU 上八次运行未修改源平均为 1.989，标准差 0.017，因此 1.92 的目标会使原始代码本身失败。故我们将其目标设为最佳测试损失至多 2.023，即均值加两个标准差。对于 minGPT（其任务训练一个小 GPT 做两位数加法），我们要求 500 个保留求和中至少 495 个正确：训练好的模型应能解出全部 500 个，余量允许因种子和数值噪声错过五个。

3 结果分析

3.1 主要结果

阶段 1。在阶段 1 中，智能体通过 30/140 个单元（21%；图 4）。评分器通过了 58 个阶段 1 结果，裁判拒绝了其中 28 个。Claude Opus 5 以 12/20 大幅领先。DeepSeek V4.1 Flash 以 6/20 紧随其后，在 GPT-5.6 各层级中只有 sol 通过了任何仓库（6/20）。迁移整个仓库对当前智能体来说仍然困难：大多数尝试失败，即使每个智能体都拥有完整源代码和自己的 TPU，可以在上面充分测试。

阶段 2 在 108 个阶段 1 失败的单元上运行。评分器通过了其中 44 个，裁判让其中 16 个通过。这些正是该阶段设计针对的情况，例如固定步数而源训练到停止规则为止、报告训练统计量而源运行评估、或源配方的另一变体。裁判拒绝了 28 个阶段 2 通过，其中 21 个因为入口脚本重建了冻结代码，其余阶段 2 失败在于冻结代码本身（2.2 节）。阶段 2 后，46 个单元通过评分器和裁判。其中 2 个单元的权重在源的参数名称下无法加载，所以智能体最终通过 44/140 个单元（31%）。

阶段 2 将智能体与我们评分的实验配方对齐，因此第一次运行了不同实验的正确迁移不会因该选择而被判失败。每个智能体从中获得至少一个通过。它还有助于确保剩余失败在于迁移的代码，而不是任务描述不充分（2.2 节）。运行所有 140 个单元花费 22,802 TPU 芯片小时（图 H1），智能体轨迹总计 125 亿 token。

3.2 裁判、成本和行为

图 5：按阶段的结果。从左到右，各列显示所有 140 个单元、其阶段 1 结果、其阶段 2 结果和最终结果。在阶段 1 失败的 110 个单元中，阶段 2 拯救了 16 个；其余失败于裁判、未达评分目标、崩溃或破坏冻结（2.2 节）。两个被拯救的单元未通过权重加载检查。

裁判的作用。裁判是必需的，因为它们能捕获因错误原因达到评分目标的结果，这是仅靠指标无法检测的。在两个阶段中，他们拒绝了评分器通过的 102 个结果中的 56 个（图 5；表 4）。我们手工检查了许多拒绝案例并发现它们合理；裁判捕获了一个 llama2.c 迁移在其自己的数字旁边将已发表的数字写入指标，以及一个 minGPT 迁移在其训练数据上进行评估。

裁判发现什么。除了破坏冻结，裁判捕获两类误报。评分器读取运行报告的任何数字，这可能不是配方自身的数字，例如用单独的验证通过代替配方的平均损失；正确性裁判在运行日志中找到配方的数字并检查它，所以每次通过都是真阳性。作弊裁判捕获作弊行为，例如在另一任务的机器上训练或读取另一会话的文件。

图 6：准确率与成本。每个点是一个智能体的最终通过率对其在 2026 年 9 月 14 日标价下的成本（附录 F）。虚线是通过对数成本的通过率最小二乘拟合。蓝线是有效前沿，即成本在对数尺度上各智能点的上凸包。通过率每 10 倍成本上升约 25 个百分点。

准确率与成本。通过率随成本的对数线性增长（图 6）。我们将通过率拟合到对数成本上，因为智能体在 20 个仓库上的成本从 10.0 美元到 1,844 美元不等。每 10 倍成本增加约 25 个百分点，该线解释了智能体之间的大部分差异（R²=0.66，r=0.81，p=0.027，n=7 个智能体）。趋势在 5% 水平上统计显著。阴影区域的上边缘（有效前沿）穿过三个智能体：GPT-5.6-luna，最便宜；DeepSeek V4.1 Flash，每次通过最便宜；Claude Opus 5，最准确。其他所有智能体都在其下方；例如 Muse Spark 1.3 的成本是 DeepSeek V4.1 Flash 的七倍多，通过的仓库却更少。

4 智能体为何失败？

4.1 失败分类学

图 7：阶段 1 后的失败分解。每个条按阶段 1 结果分割智能体的 20 个仓库：通过；被裁判拒绝；错误实验（不同的管道或规模，或主要评估从未运行）；保真度差距（正确的管道，未达评分目标）；崩溃或未终止。最后两类占失败的 47%，是迁移代码中的故障，阶段 2 无法修复。

第三个裁判（失败裁判）基于运行的指标、日志和迁移代码的 diff，从固定分类学（附录 D）中为每个评分运行分配一个类别。失败裁判只读取运行；它无法确定运行通过还是失败。图 7 显示失败裁判对阶段 1 运行的分类。

是代码失败，而非实验选择。我们按可修复的内容对类别分组。错误或不完整的实验（不同的管道、正确管道的不同规模、或从未到达主评估的运行）是入口脚本运行内容的问题，阶段 2 可以修复。保真度差距、崩溃或永不结束的运行是迁移代码中的问题。在阶段 1 中，27% 的失败是错误或不完整的实验，47% 是代码失败；裁判拒绝其余。阶段 2 消除了第一组。它未能拯救的单元仍在代码中失败，或因在入口脚本内重建迁移代码而破坏冻结（图 D1）。如果迁移本身是错误的，将智能体与评分配方对齐不会使单元通过。

智能体失败方式各异。DeepSeek V4.1 Flash 很少崩溃（1 个单元），其 15/20 的单元达到评分目标，但裁判拒绝了其中一半，多因作弊。Terra 的失败分布在错误实验、保真度差距和崩溃上，luna 的分布在几乎每个类别（图 D1）。

仅翻译不是难点。因为 JAX 也可以在 GPU 上运行，我们还可以在同一硬件上单独测试 PyTorch 和 JAX 之间的翻译。在我们基准的早期开发中，我们要求交付完整的 JAX 仓库并在 GPU 上评分。在那里迁移几乎已被解决：高等推理努力的 GPT-5.5 将 12 个 PyTorch 仓库迁移到 JAX 并通过了 99% 的检查（117 项中的 116 项），12 个仓库中的 11 个完全通过（附录 G，表 G1）。检查是严格的：与 PyTorch 的前向和梯度一致性、可在两个框架中加载的检查点、逐 token 匹配的解码，一次未命中即整个仓库失败。

在 TPU 上，即使在阶段 2 之后，智能体的平均通过率也只有 31%，约一半的失败是智能体自己搭建的机器上崩溃或未达标的代码。这一比较表明困难不在于翻译本身，而在于跨框架和硬件的迁移。因此测试这种能力需要跨硬件迁移，这正是 XStack 所做的。

4.2 行为与诚信

通过的智能体遵循源的文档，运行 README 的默认配方，以其名称报告其数字，并得到接近源的结果。卡住的智能体则转而探索机器，读取其他单元的残留文件或使用我们的凭证。我们在初始实验中发现了这些泄漏，加固了沙箱，并干净地重新运行了三个受影响的单元。两起针对评分目标的事件（钳制指标和复制检查点）也来自构建基准的时期，不影响当前基准及其结果。在最终基准中，作弊事件反而利用源自身提供的东西，例如兄弟变体或已发表的数字，我们的检查和作弊裁判能捕获它们。

5 相关工作

代码迁移。代码翻译已从单个函数和小程序发展到整个仓库，尽管一些仓库级基准仍在上下文中评分单个函数或填充骨架。迁移基准升级语言版本或将仓库迁移到另一软件栈。

框架转换。对于机器学习代码，框架转换已在单个片段、短程序和训练代码库上被研究，或通过可移植层避免。T2J-Bench 最接近：整个 PyTorch 训练代码库到 JAX，在隐藏评估器下，但在单个 GPU 上——我们的 GPU 实验发现仅框架的设置几乎已解决（4.1 节）。内核基准为一个加速器编写内核，一次一个算子，针对已在上面运行的参考实现。模型在训练数据中罕见的硬件上表现更差。在所有这些工作中，加速器保持不变或单元是一个内核。XStack 将整个仓库迁移到新框架和硬件，并在运行时禁止 PyTorch，所以没有智能体能靠什么都不做而通过。

智能体基准。自 SWE-bench 以来，问题解决基准用之前失败、之后通过的测试来评分更改。后来的基准要求从头构建代码库。然而，可工作的仓库在其自身环境中没有失败的测试。大多数基准还给智能体一个现成的环境；SetupBench 和 DeployBench 单独测试设置，但在代码运行后即停止。更接近我们设置的是针对研究结果评分的基准。智能体从作者代码复现论文结果、针对评分标准或参考代码复现论文、或在机器学习任务上最大化分数。相比之下，我们的评分目标是源仓库自身的结果（2.3 节），忠实的迁移自然会达到。

评估诚信。智能体利用未充分指定的目标，并博弈它们能看到或篡改的检查；从公共代码构建的基准有记忆风险。在 XStack 中，评分目标是隐藏的：智能体永远不会被告知它或是否通过。为公平起见，在第一次尝试失败后，第二阶段将智能体与评分实验对齐，同时其代码（入口脚本除外）保持冻结。我们在全新机器上重新运行代码，所以记住答案是不够的，模型裁判审查每个达到目标的结果（2.2 节）。

6 结论

我们提出 XStack，一个评估智能体将可工作的机器学习仓库从 GPU 上的 PyTorch 迁移到 TPU 上的 JAX 能力的基准。在来自 5 个实验室的 7 个智能体中，平均通过率为 31%，且通过率随成本的对数线性增长。我们的分析表明验证区分成功与失败：将源的实验运行到底并将其结果与原始结果比较的智能体倾向于通过，提交未测试代码的智能体倾向于失败。我们鼓励其他具有隐藏标准的基准采用类似的冻结第二阶段，将智能体与评分内容对齐，以对智能体保持公平。虽然当前智能体在跨框架和硬件迁移上尚不可靠，我们希望它们有一天能可靠地处理此任务，并为研究者解锁对不同硬件的访问。与此同时，XStack 将帮助衡量朝向这种硬件自由的进展。

# TPU 访问

一台多主机 TPU 机器在任务期间被分配。它是一台必须保持运行的常设机器（规则在最后）。

- Google Cloud v5p 切片，8 个 worker 主机，每个 4 个 TPU 芯片（总共 32 个芯片）。在所有 worker 上同时启动的 JAX 程序将所有 32 个设备视为一台机器。
- 每个 worker：Ubuntu 22.04，远程用户 <user>，原生 Python 3.10，未预装 ML 技术栈，自己的约 100 GB 本地磁盘（请设置每个 worker；大数据集和重复检查点可能耗尽它）。
- TPU 名称 <name>，区域 <zone>。Worker 外部 IP：<list>

在 worker N 上运行命令（此形式是可靠的）：

    gcloud alpha compute tpus tpu-vm ssh <user>@<name> \
      --zone <zone> --worker=N --command 'command' --quiet \
      --ssh-flag=-i --ssh-flag=$HOME/.ssh/<key>

复制文件到 worker N：

    gcloud alpha compute tpus tpu-vm scp --recurse local_path \
      <user>@<name>:remote_path --zone <zone> --worker=N --quiet \
      --scp-flag=-i --scp-flag=$HOME/.ssh/<key>

直接 ssh -i ~/.ssh/<key> <user>@<worker-ip> 也可以，但在此区域会间歇性超时；如果使用它，请设置宽松的连接超时并重试。优先使用 gcloud 形式。

注意：
- 要使用整台机器，需同时在所有 worker 上启动相同的程序（例如用 & 在 worker 上循环命令）；在 TPU 上 JAX 运行时自动发现其他主机。
- 每个 worker 都有互联网访问；在每个上安装包都可行。
- 掉线的 ssh 会话会杀死其前台子进程：请在 nohup（或 tmux）下运行长时间远程命令并轮询其日志。
- 你的最终提交将从此工作区收集，然后在那台机器上运行（在所有 worker 上同时启动）。

规则（机器是共享基础设施，必须保持运行）：
- 永远不要重启、关机或断电 worker，永远不要停止或重启系统服务。如果 TPU 看起来卡住，是你的某个进程仍在持有设备：在每个 worker 上杀死你自己的进程并等待它们退出。
- 所有 worker 都归你使用。在每个 worker 上，将你的文件保存在 <user> 主目录、/tmp 和 /dev/shm 下，只触碰你启动的进程。

附录 D 失败分类学定义

失败裁判分配以下类别之一。

类别 含义
pass 达到评分目标（图中的通过还需要裁判）
scope miss 与主要管道不同的管道，或仅仓库的一部分（nanoGPT 的 Shakespeare 快速入门而非 OpenWebText 上的 GPT-2；minGPT 的 chargpt 而非加法器；HSTU 的 ML-1M 示例）
incomplete transfer 训练了正确的管道，但从未运行主要评估（没有 CORE 套件的 nanochat；没有束搜索解码和 BLEU 的 LoRA）
fidelity gap 正确的管道和评估，但模型未达评分目标
scale deviation 配方以与源不同的规模运行（批次、步数、模型大小、数据比例）
runtime crash 评分运行非零退出或挂起
no termination 迁移没有停止规则；运行达到上限且未写入指标
no TPU 评分运行从未获取 TPU（CPU 回退）
wrong fix 更改了缺陷以外内容的后续回合
unchanged tree 智能体未编辑交付物就返回
grader artifact 评分是 harness 的错误而非迁移的；该类别描述评分器
fabricated result 主要数字不是通过运行管道产生的（复制、硬编码，或在下载的已完成权重上评估）
freeze violation 阶段 2 回合更改了入口文件以外的内容
infra 机器或 harness 中断；该回合未被消耗
