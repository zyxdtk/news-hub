亚马逊云科技（AWS）于周四推出了 Kiro 机器人，为其 Kiro Crew 开发工作区新增了持久型智能体。这些智能体能够监督周期性职责、协调其他智能体，并记住开发者在过程中做出的决策。

该功能现已正式全面上线，旨在解决开发者同时将多项任务委派给 AI 时出现的问题：仍然需要有人检查哪些智能体已经停滞、协调它们的结果，并在工作恢复时再次解释相同的需求。

AWS 建议将这类协调工作交给职责各异的机器人。开发者可以让一个机器人负责监控构建失败，另一个负责审查提议的代码变更，第三个负责检查版本是否已准备好发布。每个机器人都保留自己的上下文，并可以指挥多个工作会话。

对于企业工程负责人而言，这一卖点不仅限于更快地生成代码。AWS 希望机器人能在人工干预之间推进部分开发流程。这是否真能减少管理开销，将取决于它们能否可靠地遵循指令、上报决策，并将其工作保持在团队所分配的权限范围之内。

从单次提示到持续职责

每个 Kiro 机器人都有名称、持续进行的对话、自己的笔记和专属工作区。开发者可以回到该对话中调整方向或查看结果，而无需逐一重新打开每个工作会话。

据 AWS 介绍，机器人可以启动多个会话、跟踪其进度、纠正偏差并整合输出结果。当某项工作分支需要人工决策时，它可以请求该决策，同时继续执行不依赖于该答案的其他任务。

开发者还可以通过对话方式描述时间安排。机器人可以在夜间调查故障，或汇总每周的变更摘要。其活动日志记录日常工作，而对话则会呈现需要关注的发现和问题。

AWS 用四个可能的任务示例来说明该功能：对传入的问题进行分类并识别重复项；检查构建管道是否出现新的失败；对照此前的工程决策审查提议的变更；以及在发布前验证测试和文档。

这些只是可配置工作流的示例，并不能证明 AWS 已为这些工程职能提供了四种自主替代方案。开发者仍然需要定义任务、提供对相关系统的访问权限，并确定什么才算完成。

机器人还可以维护一个自定义仪表板。在随公告发布的一个示例中，一个 GitHub 监控机器人按主题对问题进行分组，并显示积压任务的变化，让开发者无需阅读每一条底层交互记录即可检查工作情况。

独立的记忆、权限和模型

AWS 将每个机器人的记忆与其特定任务绑定。关于部署的决策可以与研究型机器人积累的上下文分开保存，用户可以查看、修改或删除被记住的信息。

公告描述了通过保存的上下文、对话和纠正来实现改进，但这并不意味着机器人会重新训练其底层模型。其实际主张是，开发者应该不必反复解释某个经常出现的偏好或约束。

权限也因机器人而异。AWS 描述了一种可以查看文件但不能编辑的研究配置，以及一种在做出更改前需请求批准的部署配置。其示例中的审查机器人可以发表评论并要求修改，但不能批准或合并代码。用户随后可以调整这些边界。

这一区别很重要：分配给机器人的职责并不会自动赋予其不受限制的权限。AWS 表示，添加工具需要用户批准，由开发者决定每个机器人可以采取多大的主动性。

模型选择提供了另一种控制手段。协调机器人及其工作智能体可以使用不同的模型，使团队能够为规划任务保留能力更强的模型，同时将重复性检查分配给更便宜的选项。Kiro 的模型目录收录了 OpenAI 和 Anthropic 的产品，以及开放权重替代方案；可用性和积分收费因模型而异。

根据公告，机器人可以通过 Crew 在笔记本电脑、Mac Mini 或 Amazon EC2 实例上运行。这使用户可以灵活选择工作区的运行位置，不过在自己硬件上运行该软件不应与在本地运行所有底层模型混为一谈。

Kiro 与 Cursor、Anthropic 和 OpenAI 周期性智能体的对比

AWS 加入的是一场已经成型的竞争，即在用户提示之间实现工作自动化。定时调度、保留上下文和后台执行等功能已出现在竞品中。以下对比聚焦于周期性开发工作及相关工作流，而非将所有编程助手视为同类产品。

Cursor 是一个尤为接近的对比对象。其自动化记忆可在单次运行之后保留，并且可以编辑或删除。智能体可以创建拉取请求、与外部工具交互，并使用截图或录屏演示其变更。因此，持久记忆本身并不能成为 Kiro 的差异化优势。

Anthropic 的定时任务强调仓库、连接器和触发器的配置。使用托管执行时，即使笔记本电脑处于关闭状态，任务也能继续运行，不过 Anthropic 仍将这一能力标记为研究预览版。OpenAI 则区分了需要可用本地机器的桌面任务和使用上传上下文及连接服务的 Web 任务。

Kiro 提出的优势在于组合：围绕特定职责的持续对话、独立的记忆和权限，以及一个监督工作智能体并掌握其进度全貌的协调者。这是一种产品设计上的区别，并不能证明它在同等工作上优于竞争对手。

实际成本取决于机器人的具体工作

AWS 的定价页面显示，Kiro 订阅涵盖 Crew 以及 IDE、CLI 和 Web 产品。发布文章并未宣布单独的按机器人收费。

对于至少两人的团队，AWS 列出的共享用量方案为每席位每月 20 美元，每个席位贡献 500 积分。这与个人版 20 美元 Pro 套餐的 1,000 积分额度不同。额外的团队积分为每个 0.04 美元。

积分并不等于已完成的任务：消耗量取决于复杂度和模型选择。因此，团队无法仅凭订阅价格推算出一个持续定时运行的机器人的月度成本。

同样的比较问题也适用于所有供应商。更频繁的检查、更大的代码仓库和重复尝试都可能改变无人值守工作的经济性。将协调模型与工作模型分开，为 Kiro 用户提供了一种可能的成本控制机制，但 AWS 在公告中并未提供这种安排的实测节省数据。

企业团队仍需验证的问题

发布文章没有提供对比基准测试、量化的生产力结果或新机器人的实测错误率。它描述了功能和建议的工作流，将评估自身部署需要多少监督的工作留给了潜在用户。

一项有用的评估应当衡量审查和纠正机器人所花费的时间，同时考量已完成的工作量、意外行为和模型消耗。一个能发现更多构建失败但产生过多不必要上报的系统，可能只是把工作负担转移到了别处。

AWS 自己的示例给出了一个务实的起点：分配一项范围较窄的周期性职责，限制其权限，只有在审查结果之后再行扩展。企业眼下的问题是，一个机器人能否可靠地负责流程中的一小部分。只有当增加机器人能够减少而非加重协调负担时，更大的机器人才有价值。
