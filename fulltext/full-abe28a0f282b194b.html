摘要

网络靶场与夺旗（CTF）场景的构建仍然是一项劳动密集型工作，因为作者必须协调基础设施、脆弱服务、攻击路径、制品和成功条件。大语言模型（LLM）可以提出详细的演习方案，但看似合理的描述并不能保证可部署的软件或可验证的目标。我们提出 ScenarioForge，它将高层需求转化为资源落地的拓扑、服务、流量、分段和挑战链，然后在通用开放研究仿真器（CORE）中实例化并验证它们。ScenarioForge 执行数据集包含 226 个物化场景，覆盖 294 个 Vulhub 镜像以及通过我们的 AI 辅助脚手架开发的全部 85 个定制挑战资源生成器。全部 226 个场景通过了构建、预览、排序、部署、严格运行时验证和实时制品检查；其 867 个步骤——每个都是可单独验证的挑战目标——由 457 个漏洞支撑实例和 410 个生成资源支撑实例组成。在一项独立的 50 提示匹配基准中，ScenarioForge+Qwen3.8 和 ScenarioForge+GPT5.6 均实现了 50/50（100%）的拓扑/构建成功率和 160/160 的意图字段；直接前沿生成仅在完整累积脚手架（结构、词汇、策略和容器镜像指导）下才达到 41/50 的构建和 147/160 的字段。该测试尚未涵盖 ScenarioForge 的下游挑战资源生成、依赖/flag 排序、部署和实时验证。这些制品为训练与评估提供了操作丰富且可复现的演习。

I 引言

网络靶场再现网络化系统、漏洞和对抗活动，用于受控的训练与评估。有效的演习需要的不仅仅是叙事：作者必须协调基础设施、脆弱组件、网络依赖、参与者行动和成功条件。这种领域专业知识与详细配置的结合使场景构建成本高昂；自动化可以提高多样性和适应性 [1, 2]。

LLM 可以生成攻击叙事和演习设计，近期工作利用多模型角色和检索增强来提高其细节和真实性 [3]。网络靶场研究分别提供了可执行规范（如 VSDL [2]）和仿真平台（如 CORE [4]）。

尚未解决的问题是描述与执行之间的边界。LLM 可能提出不可用的实现、不兼容的版本、无效的配置或不受支持的目标。对合理性、真实性、创造性或可用性的评估并不能确定场景可以被实例化和运行 [3, 5, 6]。因此，模型表达的知识必须与靶场的可执行资源相协调。

我们提出 ScenarioForge（图 1），这是一个将 LLM 输出视为提案而非成品环境的框架。类型化的持久表示将生成式创作与确定性落地和执行分离：模型提出场景意图和关系，而后端组件决定哪些已安装资产可以实现它们并记录生成的绑定。解析后的规范随后在 CORE 中实例化，并使用来自已部署环境的观察进行评判。这种划分建立了明确的信任边界——看似合理的生成内容绝不会被当作可用资源、运行服务或受支持目标的证据。

图 1： ScenarioForge 工作流与信任边界。规范 XML 在通过 CORE gRPC 和 SSH/SFTP 路径编排之前，先经过合格目录的细化和落地。随后 ScenarioForge 验证观察到的运行时状态和挑战结果，生成经过验证的演习和可移植的证据包；参与者或测试主机在配置后通过 HITL 接入。

我们的贡献是：

  • 自动化、资源落地的构建： ScenarioForge 将拓扑、服务、分段、流量、制品和挑战链落地到可部署资源中。它支持 Vulhub 环境和用户开发的漏洞、服务和制品，并内置使用本地或云端 LLM 的自动化资源构建。
  • 基于执行的验证与基础设施： 目录预检、预览、排序、部署、运行时验证和实时制品检查产生运行证据。我们的评估工具链和加固的 CORE 9.2 虚拟机/分支使这些检查对于容器支撑的靶场可重复。
  • 匹配的 AI 创作基准： 在 50 个独立基准提示中，ScenarioForge+Qwen3.8 和 ScenarioForge+GPT5.6 均实现了 50/50（100%）的拓扑/构建成功率和 160/160 的请求意图字段。因此，相对较小的开放权重 Qwen3.8 模型在 ScenarioForge 内部比肩前沿模型，且框架辅助条件优于直接前沿生成——后者尽管有累积脚手架，也仅达到 41/50 的构建和 147/160 的字段。我们发布了复现该比较所需的冻结提示与期望、保留的输出、评分记录和分析脚本。
  • 可复现的执行数据集： 我们发布 ScenarioForge 执行数据集：226 个固定场景，覆盖 294 个 Vulhub 镜像、全部 85 个定制挑战资源生成器，以及跨越多样拓扑、服务、策略、流量、制品和依赖的 867 个挑战步骤。

两者结合，匹配基准隔离了从描述到可构建定义的转换，而执行数据集则将固定的落地定义贯穿排序、部署和实时证据。这种从提案到证据的设计使贡献超越了一个提示或生成器。它将失败定位到创作、解析、编译、部署、运行时状态或制品验证；记录的阶段计时表征了在所述环境中的复现成本。

II 相关工作

网络靶场自动化涵盖可复用基础设施、随机化生成、模型驱动的演习执行和声明式场景语言 [7, 8, 9, 10, 2, 11]。CRACK 类似地验证人工编写的 TOSCA 蓝图，并将虚拟机和网络实现委托给外部 ARIA/OpenStack 技术栈，但其发布的模型不涵盖容器化漏洞目录或 CTF 特有的制品和跳板依赖 [12]。SecGen 根据人工编写的约束配置随机化的脆弱虚拟机和带生成提示的 CTF 挑战 [13]。当目标基于已知机制定义时，自动化攻击执行同样提供了强有力的证据 [14]。

AI 辅助工作通过信息抽取、多智能体提示和检索增强生成演习内容 [15, 3]。ASCERT 评估交互式 LLM 生成场景的事件保真度和可重复性，而 Hasegawa 和 Takakura 从真实攻击数据生成组织特定的演习 [5, 6]。这些系统拓宽了语义创作，但其报告的评估集中于生成内容而非相应资源的部署。

ScenarioForge 为生成、落地和执行分配了不同的职责：LLM 提出拓扑和演习逻辑；目录将提案绑定到实现；CORE 和 Docker 将靶场物化；后端观察评判受支持的目标。与 CRACK 的外部实现虚拟机模型不同，此路径可原生运行或使用独立的 CORE 虚拟机，且不需要 OpenStack。容器化服务与路由仿真共存，同时 flag、提示、解答、类型化制品前提和访问约束保留在可执行模型中。

III 方法论

III-A 系统概述

如图 1 所示，ScenarioForge 将基于 LLM 的综合与确定性落地、执行和验证相结合。输入范围可以从宽泛的目标到明确的拓扑、服务、漏洞、路由、分段、访问和挑战约束。

规范场景 XML 贯穿整个工作流持久存在。落地将网络元素映射到 CORE 配置，将脆弱服务映射到 Docker 支撑的资源，将 CTF 目标映射到已安装的挑战资源生成器。解析后的场景可原生运行或在通过 gRPC 和 SSH 控制的 CORE 9.2 虚拟机中运行；参与者可以通过硬件在环（HITL）网络接入。运行时检查涵盖节点、容器、服务、端口、注入、分段、流量和制品。解题脚本遍历挑战序列并记录通过、失败、不确定或跳过。XML、日志、摘要和报告保存证据。

III-B 场景规范与中间表示

ScenarioForge 在创作、预览、排序和执行过程中使用一份 XML 文档；被调用时，LLM 对其进行细化，但绝不调用 CORE、Docker 或远程 shell。该表示记录基础设施、节点和资源配置、挑战状态和依赖、参与者连接以及执行元数据。部分指定的场景保留用户约束，同时由模型填充缺失字段，且每个生成的值必须解析到目录条目或后端能力。嵌入的 PlanPreview 和排序状态使预览的拓扑和挑战结构成为部署输入，而非单独的计划。

III-C LLM 引导的场景综合

LLM 提取约束，将请求分解为基础设施和演习组件，补全未指定的角色和关系，并将结果序列化为受约束的 XML。显式约束保持权威性，因此固定的漏洞、节点数或挑战顺序得以保留，而周围的拓扑和服务可以被生成。

WebUI 将模型引导的创作与保留显式请求的拓扑意图编译器相结合。其内置的 AI 辅助生成器构建器使用本地或云端 LLM 为用户开发的漏洞和挑战资源搭建脚手架或进行细化，实现为 flag-generator 或 flag-node-generator，对其进行契约测试，并在安装前修复故障。该工作流产生了此处评估的 85 个定制挑战资源生成器；已安装的生成器确定性地执行。

由于服务、版本、生成器或攻击步骤可能不可用或不兼容，初始输出仍是一个提案。确定性解析确定哪些具体资产和参数可以实现它，在不将部署决策委托给模型的情况下保留灵活的创作。

当请求混合精确和开放式需求时，这种混合路径非常重要。意图编译器将显式计数和命名服务转换为类型化约束，而模型调用填充关系结构和未指定的值。解析可以添加放置所选容器所需的主机，在拓扑编辑后协调标识符，并拒绝其架构或运行时前提与执行端点不匹配的目录选择。验证和修复在持久表示上进行，因此修正后的草稿会针对相同约束重新检查，而不是从无约束的对话中重新生成。

III-D 在可执行网络安全资源中落地

落地仅在元素映射到可执行资产或受支持的确定性配置时才保留该元素。脆弱服务解析到已编目的 Docker Compose 环境、端口、启动流程和注入计划，包括用户开发的资源和可复现的 Vulhub 环境 [16]。挑战资源生成器产生制品、flag、部署说明和解答；网络和参与者资源编译为 CORE、HITL 或 Proxmox 支持的配置。因此，仅有服务名称而没有兼容的版本和运行时定义是不够的，且只有当已安装的生成器同时提供制品和验证流程时，目标才被接受。静态预检在执行前拒绝无效的目录或注入接线。

当前活跃的挑战资源生成器目录涵盖二进制制品（如固件和数据包捕获）、凭据和签名、JSON/YAML/INI 配置、编码载荷，以及文本证据（如聊天导出、工单、运维记录和备份）。每个条目记录其生产者、放置位置、预期输出和解答流程。这使得目录状态（而非模型的记忆）成为靶场可以部署和验证内容的权威。

算法 1 形式化了核心确定性流水线。它将 LLM 输出视为提案，当组件或依赖无法实现时返回类型化失败，并且仅在部署和目标验证成功后才产生执行证据。用户对持久预览的编辑会在解析步骤重新进入流水线，以便修订后的 XML 在相同规则下接受检查。

算法 1 资源落地的执行与验证

1:  输入：场景 XML X，目录 C，执行后端 B
2:  输出：证据记录 E 或类型化失败 F
3:  Q ← ParseAndPreserveConstraints(X)
4:  for all 组件 q ∈ Q do
5:      A_q ← CompatibleAssets(q, C, B)
6:      if A_q = ∅ then
7:          return GroundingFailure(q)
8:      end if
9:      a_q ← Select(A_q)
10:     X ← Bind(X, q, a_q)
11: end for
12: G ← DependencyGraph(X)
13: if G 有环或存在未解析的前提 then
14:     return DependencyFailure(G)
15: end if
16: T ← CompileTopology(X, B)
17: if ¬Preflight(X, T, C) then
18:     return PreflightFailure(X, T)
19: end if
20: X ← PersistPreview(X, T, G)
21: O ← TopologicalOrder(G)
22: D ← Deploy(T, O, B)
23: if ¬D.ok then
24:     return DeploymentFailure(D)
25: end if
26: V ← RuntimeValidate(D, X)
27: S ← VerifyObjectives(D, G)
28: if ¬V.ok ∨ ¬S.ok then
29:     return VerificationFailure(V, S)
30: end if
31: return E ← (X, D, V, S)

对于 n 个组件、c 个目录条目、e 条依赖边、t 条编译记录和 p 个探针，算法 1 使用 O(|X|+nc+e+t+p) 的最坏情况时间和 O(n+e+t) 的空间；索引可将时间降低至接近 O(|X|+n+e+t+p)。该界限不包括 LLM 推理，并将后端请求视为单位成本操作。

三个不变量将该算法与实现联系起来。第一，每个选定的资源都由目录键标识并复制到解析后的规范中，使模型输出不足以构成绑定。第二，所有依赖端点必须在拓扑排序之前命名持久化的步骤或类型化制品。第三，部署和验证使用与预览相同的解析后 XML 和稳定节点标识符。这些不变量防止看似合理但不可用的组件、孤立的前提或仅在预览中的修复悄然进入执行。因此，失败具有类型化的位置：落地、依赖分析、预检、部署、运行时验证或目标验证。

III-E 拓扑与演习构建

落地后，ScenarioForge 将主机、路由器、链路、寻址、路由、服务放置、流量、分段和制品编译为 CORE 操作。构建遵循依赖顺序：网络先于服务，目标先于注入，制品跟随活跃目的地。来自执行 XML 的预览在部署前展示确切的拓扑、角色、漏洞和依赖。

III-F 依赖感知的挑战构建

ScenarioForge 将每个演习表示为依赖图。步骤是绑定到落地服务、文件、凭据或挑战节点及预期结果的一个可验证挑战目标。框架将需求连接到前驱输出，拒绝未解析或循环的图，并记录目标、flag 和解答动作。Sequence 构建有效顺序，Resolve 选择资源和参数；两者更新同一份 XML。

排序持久化的不仅仅是有序列表。每个分配记录目标节点和服务、实现目标的资源、前提访问事实、先前步骤产生的类型化输入、预期输出和验证策略。拓扑排序随后产生可部署的 Flow，其中生成的文件、凭据、端点和访问能力成为显式边，而非仅存在于教官头脑中的假设。持久化的排序 JSON 和更新后的 XML 被执行、解题脚本和制品验证共同使用，因此三者观察同一个解析后的依赖图。

部署后，解题脚本遍历图并记录通过、失败、不确定或跳过。受支持的 HTTP、SSH 和 TCP 挑战节点策略是自动的；漏洞主机和仅制品步骤保留 flag、提示、解答和接口，供参与者或漏洞利用工具链交互。中间输出仅到达依赖步骤，而严格验证在整个解析图中确立部署和制品就绪。

III-G 分段与跳板约束

跳板是从提供者 H_p 到目标 H_t 的依赖边：前驱产生对 H_p 的访问，而依赖步骤在针对 H_t 之前需要它。提供者可以是脆弱主机、生成的挑战节点或受支持的 SSH 回退。

图必须将需求链接到提供者；策略必须允许来自 H_p 的服务并拒绝未授权来源；探针要求从 H_p 成功且从代表性禁止来源失败。这种正负测试避免将允许列表成员资格视为隔离的证明。

每个依赖步骤携带其提供者-目标对，因此多个或非相邻的跳板不会覆盖全局上下文。路径被独立探测并通过通用验证记录报告。

III-H 人机回环场景细化

用户可以提供宽泛的目标或详细的需求，或完全绕过 AI 直接在 WebUI 中构建场景。共享 XML 在部署前展示解析后的预览。编辑触发重新解析，允许不受支持的资源、放置、顺序或连接发生更改，而无需重新开始创作。使用时，模型提出意图；落地限制实现，用户保留最终控制权。

III-I 网络靶场实例化

在拓扑、资源和依赖固定后，ScenarioForge 原生执行或将应用程序、CORE 9.2 和参与者角色分离到不同主机。CORE gRPC 管理会话拓扑和生命周期；SSH 处理放置、Docker、服务、注入和检查。执行创建拓扑和策略，部署服务，应用注入和制品，然后激活流量和 HITL 接入。Web 和 CLI 工作流共享此后端，请求标识符让重试的客户端重新连接到长时间操作。

III-J 多阶段验证与确认

验证区分三类失败。目录预检检查部署元数据、服务和注入接线。运行时验证检查活跃 CORE 会话中的预期节点、容器、端口、注入、输出、流量和策略行为。挑战确认遍历解析后的序列，自动执行受支持的策略，并为每个步骤记录通过、失败、不确定或跳过。Web 和 check-artifacts CLI 路径返回结构化的 validation_summary；严格成功要求其 ok 字段为真且所有相关问题计数器清零。通过一个阶段并不意味着后续阶段的成功。

特别是，严格验证要求零缺失节点、零停止的 Docker 服务、零缺失注入、零缺失生成器输出和零缺失生成器注入。正负可达性探针检查分段，而制品检查检查的是已部署环境而非仅仅生成的计划。按问题的日志保留导致失败的观察，维护目录资格、组合运行时状态和目标完成之间的边界。

IV ScenarioForge 执行数据集

IV-A 构建与预期配置

ScenarioForge 执行数据集包含 226 个固定的物化规范，每个规范保留其创作输入、种子、目录选择、权威 XML、预览、挑战顺序、执行证据和派生组合。对于每个案例，ScenarioForge 从解析后的挑战图生成并持久化 Flow 顺序、挑战依赖和 flag 放置；随后全部 226 个案例完成了部署、严格运行时验证和实时制品检查。预期配置与执行日志分开保存，因此成功并不定义预期内容。该集合使用一个经过验证的目录快照，涵盖 294 个已启用、自包含的 Vulhub 镜像和完整的 85 个已启用定制挑战资源生成器集合；需要外部在线服务的十个导入条目被排除。该数据集与第 V 节中的 50 提示匹配 AI 创作基准相互独立。

三十个源规范定义了以漏洞为中心、以制品为中心、混合、规模和分段族。评估工具链在执行前将其迭代次数和种子扩展为 226 个解析后的规范，冻结有界拓扑选择、资源分配、策略和流量设置以及验证要求。这种两级组织既保留了可复用的族定义，又保留了运行的确切案例。它还允许未来的目录或后端修订重放相同的解析案例，或有意重新物化某个族并报告该区别。

IV-C 预期用途与覆盖

固定的输入和绑定支持回归测试、受控的智能体或参与者比较以及组合分析，而无需从日志重建意图。数据集的精心组合将完整的已启用目录覆盖与多样的族规模、链长、拓扑规模、访问模式、分段策略和可复现流量配置文件相结合。

V 实验评估

V-A 实验问题与证据边界

实验使用独立的输入。EQ1 询问全部 226 个固定执行数据集场景是否都能完成 XML 构建、预览、排序、部署、严格运行时验证和实时制品检查。EQ2 询问在独立的 50 提示基准中，资源落地创作是否比直接前沿生成产生更好的 CORE 可构建拓扑并更好地保留请求的意图。EQ2 通过安全的 CORE 构建测量由 AI 生成器控制的面向拓扑的项目。ScenarioForge 的下游排序阶段从落地的拓扑和目录元数据中派生 Flow 顺序、挑战依赖和 flag 序列；EQ1 评估这些阶段。一项单独的无 Flow 审计启动框架辅助的输出。

V-B 评估基础设施与全流水线研究

我们构建了 scenarioforge-eval 以对每个固定规范执行一次。它解析 YAML，持久化种子和 XML，调用预览、排序、执行和制品检查，序列化共享 CORE 虚拟机的阶段，并保留输入、日志、指标和复现包。严格成功要求正常进程退出、validation_summary.ok、零问题计数器，以及观察到预期的容器、服务、端口、注入、策略、流量和访问路径。其 WebUI 控制运行并索引结果、计时、失败位置、拓扑、组合和证据。

该工具链提供独立的执行和分析视图。执行视图选择规范集、ScenarioForge 检出、输出目录、阶段边界和重放模式；它流式传输有界日志，并支持停止、恢复或重新运行所选阶段。分析视图索引结果树并按运行元数据过滤，然后呈现拓扑、组合、计时、阶段结果、制品和验证证据。该界面支持研究期间的实时诊断，而保留的 JSON 和 CSV 记录仍是报告测量的来源。

评估虚拟机打包了我们定制的 CORE 9.2 分支。我们修复了容器初始化竞态、Docker/Podman 节点和接口在 gRPC/XML 间的持久性、陈旧接口、可能导致冲突或空卷的 Compose 项目与会话隔离，以及容器 shell/环境发现。这些是可重复性和运行时基础设施方面的贡献，而非 AI 生成器的输出。

批处理使用 16 核、48 GB 的 Apple M4 Max 主机和本地 8 GB VMware 虚拟机中的 CORE 9.2。我们将镜像已缓存的 194 次运行与观察到镜像拉取的 32 次运行分开报告，在每个计时范围旁展示缓存状态。

在此基础设施下，全部 226 次执行完成了 XML 构建、预览、排序、部署、严格验证和实时制品检查，无阶段失败。规范确立预期成员资格；保留的批处理记录确立结果并按阶段定位未来失败。

最小-最大时间（预缓存，n=194 / 观察到拉取，n=32；秒）为：XML，0.003-0.994 / 0.298-0.830；预览，0.443-0.703 / 0.456-0.846；排序，14.9-74.3 / 15.9-58.3；执行，56.4-657.2 / 70.8-486.8；总计，73.7-727.0 / 87.7-550.0。这些观察到的复现成本包括组合、镜像构建、服务启动、网络收敛和验证。

V-C 匹配的 AI 创作基准

匹配 AI 创作基准包含跨五个复杂度层级的 50 个组别中立请求，从路由网络逐步发展到服务、分段、脆弱容器和综合压力案例。我们使用 gpt-5.6-sol 通过以下指令生成初始套件：

“生成 50 个简洁的、组别中立的网络靶场请求，分为五个递增复杂度层级，分别包含 12、12、10、10 和 6 个案例。从路由主机网络逐步发展到服务、防火墙/NAT 分段、脆弱容器和综合压力案例。变化路由器和主机数量；不要提及 ScenarioForge、其模式、目录名称或工具。对于每个请求，返回机器可读的预期路由器、主机、服务、分段、漏洞和流量字段。”

生成的请求和期望在任何评估条件运行之前被冻结。

评分器解析每个条件的原生输出；缺失或不可读的输出仍保留在分母中。七个条件在 50 个提示上产生 350 个保留的原生创作制品——100 个框架辅助的 ScenarioForge 定义和 250 个直接响应/XML 记录——以及 1,120 个意图字段判定（每个条件 160 个）。框架运行器仅允许在提供者超时后重试一次；报告的令牌数和计时值使用保留的成功尝试。

在冻结的套件中，每个条件接收的请求总计 462 个拓扑节点实例：128 个路由器（均值 2.56；范围 1-5）和 334 个主机（均值 6.68；范围 2-15）。每个提示都指定这两个计数。24 个提示请求 38 个命名服务（15 个 SSH、15 个 HTTP 和 8 个 HTTPS）；18 个请求 24 个分段实例（14 个防火墙和 10 个 NAT）；15 个请求 29 个脆弱服务放置；3 个请求背景流量。特定层级的功能总数从 T1 的无到 T2 的 19 个服务；T3 的 3 个服务和 12 条策略；T4 的 3 个服务、2 条策略和 18 个漏洞；以及 T5 的 13 个服务、10 条策略、11 个漏洞和全部三个流量请求。这六种字段类型产生每个条件 160 个意图判定。每请求的期望和详细的层级组合在数据集仓库的 frontier-comparison/specifications/ 下发布。

框架辅助组仅通过 ScenarioForge 的 AI 生成器发送描述。我们将开放权重 Qwen3.8-27B-NVFP4 条件记为 ScenarioForge+Qwen3.8，将前沿 gpt-5.6-sol 条件记为 ScenarioForge+GPT5.6；两者接收相同的模式、编译器、目录、验证和修复路径。直接组将相同的描述发送给不带 ScenarioForge 的 gpt-5.6-sol。其五个累积脚手架级别（或阶梯）从 CORE XML 请求（R1）逐步发展到结构示例（R2）、节点/服务词汇（R3）、分段词汇（R4）和容器镜像指导（R5）。累积设计测量直接生成在接近框架辅助条件之前需要多少表示知识，而两个 AI 生成器条件揭示在不改变框架的情况下更换底层模型的效果。

每个阶梯保留相同的用户请求和所有先前的指令，因此 R1-R5 之间的差异反映的是增加的表示指导，而非任务内容的变化。R1 要求可加载的 CORE XML 制品。R2 演示文档结构，R3 枚举允许的节点和服务术语，R4 添加防火墙和 NAT 请求所需的策略词汇，R5 提供脆弱服务的容器镜像约定。直接模型不接收 ScenarioForge 的目录查找、编译器、验证工具或修复循环。相反，框架条件不接收特定阶梯的直接脚手架：它们使用受测试的普通 AI 生成器路径。

EQ2 排除 Flow/挑战链结果，因为顺序、依赖和 flag 序列由下游排序而非 AI 生成器派生。对它们评分会错误归因框架决策。使用 ScenarioForge 的 AI 辅助创作/脚手架工具创建的 226 个固定 EQ1 场景集体锻炼了链、挑战资源、制品依赖、访问控制的跳板、分段、流量、部署和实时验证。

意图准确率是解析每个原生表示后匹配的请求字段的比例。主机计数在两组中使用相同的拓扑级定义：所有物化的非路由器主机，包括承载脆弱服务的主机。可构建性是从条件的原生制品成功构建非空 CORE 9.2 会话。评分器调用 open_xml(start=False)，使 CORE 解析并实例化拓扑定义，同时保持节点、容器和物理接口不活动。每案例和摘要记录均被保留。配套的鲁棒性审计启动框架辅助的输出，运行执行后验证，并在禁用 Flow 的情况下调用实时制品检查。

评分器首先提取每个条件的原生 XML，然后在不通过 ScenarioForge 规范化制品的情况下派生观察到的拓扑和资源字段。这避免了在评分前悄然修复直接输出。构建和意图分开报告：结构有效的会话可能遗漏请求的内容，而文本上看似合理的制品可能保留计数却未能通过 CORE 构建。将缺失输出和缺失字段保留在分母中防止了对可解析案例的选择性报告。

V-D 匹配基准结果

表 III 回答了 EQ2。两个框架条件均达到了可构建性上限，而直接前沿生成在各级阶梯上有所改善，但在 R5 仍差九次构建。失败检查在聚合之外增加了细节：在 R1，35 个制品加载后无节点，10 个被拒绝；全部九次 R5 失败均为 CORE 拒绝。Qwen 和 GPT 在框架内打平，表明在共享的模式、目录、编译器、验证和修复路径下，模型规模并非决定性因素。

意图准确率遵循相同的模式：两个框架条件均达到上限，而直接 R5 仍差 13 个字段，在 50 个请求中的 38 个中满足了每个字段。表 III 还报告了打平的框架结果之间的成本和延迟差异，将创作质量与提供者工作量分开。

表 III 中的阶梯轨迹显示，结构示例产生了最大的增益；节点/服务词汇主要改善了可构建性，分段词汇在不改变可构建性的情况下改善了意图，镜像指导产生了较小的最终增益。因此，越来越明确的语法和词汇缩小但未消除差距。框架条件在不向用户暴露这种累积表示脚手架的情况下达到了两个上限。

全部 100 个框架生成的场景（每个模型 50 个）在 ARM CORE 虚拟机上运行，禁用了 Flow 挑战排序；60 秒后，应用了运行时和实时制品检查。使用原始资源，ScenarioForge+Qwen3.8 通过了 46/50，ScenarioForge+GPT5.6 通过了 47/50。诊断性重放恢复了其余案例：一个 GPT 案例在瞬时 CORE 故障后未做更改即通过，而两个 GPT 和四个 Qwen 案例在记录在案的替换（在同一 ARM 端点上先前成功执行）后通过。合格的重放使每个框架条件达到 50/50；首次通过和修复结果保持分开报告。

100% 构建与较低的首次通过运行时/制品成功之间的差距确定了剩余的失败层：CORE 拓扑可以在架构不兼容的容器或瞬时守护进程事件中断启动之前完成构建。独立报告原始资源选择和修复后的重放，将拓扑质量与端点兼容性和瞬时基础设施行为区分开来。

V-E 解释与测量范围

如表 III 所示，同一前沿模型仅在 ScenarioForge 内部达到了两个测量上限；ScenarioForge+Qwen3.8 也达到了它们。因此，模式、目录、编译、验证和修复实质性地改变了生成的意图是否成为可用的 CORE 定义。EQ1 和 EQ2 测试信任边界的互补侧面——分别是描述到定义和固定定义到已验证演习——两者互不替代。

我们使用 gpt-5.6-sol 生成组别中立的请求套件，并在评估前冻结所有请求和预期字段。意图评分涵盖六种可观察的拓扑和资源字段类型，而提供者报告的令牌计数和延迟表征保留的创作调用。结合每案例的原生制品和 CORE 结果，这些测量揭示了语义保留和可执行结构质量。

VII 发布与复现

226 条执行数据集记录中的每一条都包括解析后的 YAML 和种子、权威 XML、执行证据、指标以及可移植的 scenarioforge-reproduction.zip 包；聚合文件将报告的值追溯到这些记录。

发布分为 scenarioforge（https://anonymous.4open.science/r/scenarioforge-479A ，创作、落地和执行）、flag-generators（https://anonymous.4open.science/r/flag-generators-E148/ ，挑战和 Vulhub 目录）、scenarioforge-eval（https://anonymous.4open.science/r/scenarioforge-eval-E1D7/ ，批处理、验证和分析）和 scenarioforge-dataset（https://anonymous.4open.science/r/scenarioforge-dataset-6015/ ）。数据集仓库包含 226 条执行数据集记录和独立的 frontier-comparison/ 集合的 50 个请求、七个条件的输出、评分记录、指标和分析脚本；比较提示不对 226 个案例做出贡献。

复现支持交互式和集合工作流。对于个人创作，用户通过 AI 生成器或直接在 WebUI 中工作，审查或编辑落地预览，并从同一界面启动排序、执行、验证和导出。对于集合，.spec.yaml 文件通过迭代次数、种子策略、固定或有界的拓扑和资源选择、Flow 设置、分段、流量、访问和验证策略定义可复用的场景族。物化为每次迭代冻结一个解析后的规范，让用户重新生成某个族以探索多样性，或重放权威 XML 和种子以精确复现记录的案例。

命令 scenarioforge-eval --sf-path SPEC_PATH --execute --out OUTPUT_PATH 复现规范集合。重放可以从规范和种子或权威 XML 开始，绕过模型变化。复现 ZIP 包含权威 XML、带哈希的清单和物化的制品源；WebUI 导入重建记录的配置和制品状态以进行重放，或从保存的解析输入确定性地重新生成制品。它必须受到保护，因为它可能包含凭据、flag 和生成的秘密。解题脚本、HITL 和漏洞利用工具链接口支持参与者和自动化演习交互。

在数据集仓库中，源规范捕获可复用的族，解析后的规范冻结随机选择，结果目录保留权威 XML 和观察到的运行证据。比较子树同样保留每个原生响应和评分记录，而非仅保留聚合百分比。清单提供文件哈希，随附的分析脚本从每案例记录重新计算面向论文的表格。连接凭据和提供者秘密已被编辑；复现必须在归档之外提供自己的 CORE 连接设置。

发布支持聚合、每案例和原始证据审计。规范确立 EQ1 的预期组合；原生制品和请求标识符追溯 EQ2 的结果。原始 XML、日志和报告在成功示例之外保留否定和中间证据。

图 3： dataset-segmented-enterprise-pivots_run01 中的源访问和制品依赖。虚线边显示已验证的访问前提；绿色边显示类型化制品依赖。橙色节点为漏洞支撑；蓝色节点使用生成资源。

VIII 结论

ScenarioForge 将提案与落地、部署和验证的演习分离。全部 226 个执行数据集场景完成了完整流水线。在独立的 50 提示基准中，两个框架条件均实现了 50/50 的拓扑/构建成功和 160/160 的意图字段；直接前沿生成最高达到 41/50 和 147/160。较小的开放权重模型在 ScenarioForge 内部比肩前沿模型。这些互补研究评估了拓扑创作和全流水线执行；发布的制品支持复现以及未来的跨模型、参与者和智能体研究。
