TideCache：基于透明缓存管理与逐层流式传输的高效混合LLM服务系统

Jinbin Luo¹, Xiaozhe Yao², Shang Yang¹, Zhijian Liu³, Song Han¹, Qinghao Hu¹

¹麻省理工学院 ²苏黎世联邦理工学院 ³加州大学圣地亚哥分校

摘要

混合架构已成为开放权重语言模型的主流。其全局注意力层和有界状态层维护着异构缓存，这些缓存的需求随上下文长度和并发度而变化。我们提出 TideCache，一个在 CPU-GPU 超级芯片上运行的服务系统，包含三个组件，用于在各缓存间分配 GPU 内存并管理它们在 GPU 和主机内存间的驻留。透明缓存池（Transparent Cache Pool）在固定虚拟地址后面对缓存组件间重新分配物理页，保持缓存布局和后端接口不变。缓存流式传输器（Cache Streamer）利用有界状态层提供的计算间隔，将下一个全局注意力层的前缀预取到全局注意力层间共享的 GPU 槽位中，在减少 GPU 驻留的同时将逐层传输与计算重叠。生成的 KV 保持驻留。请求调度器（Request Scheduler）根据请求大小和队列状态选择驻留或流式执行，并触发容量调整。三者协同工作，使流式传输释放的 HBM 可以容纳其他缓存组件和更多请求。TideCache 在 SGLang 中实现，并在 GB300 和 GH200 上跨七种模型/平台配置进行评估，与使用 HiCache 的 SGLang 相比，TideCache 最多可完成 2.04 倍的智能体轮次，将整体 P50 每 token 延迟降低 20-59%，并将智能体 P50 TTFT 提升 1.40-3.05 倍。

1 引言

混合架构已成为开放权重语言模型的主流。Kimi K3、Ring-2.6、GLM-5.3-Flash、Qwen3.8 和 GPT-OSS 每隔几层仅保留一个全局注意力层，其余层使用滑动窗口注意力或循环层（如 Mamba、Gated DeltaNet 和 Kimi Delta Attention）。我们将后者称为有界状态层，因为它们每请求的缓存内存与上下文长度无关。这些模型服务于日常聊天、编码智能体、文档分析和自动数据标注等应用。这些应用在上下文重用、交互结构、到达模式和并发度方面各不相同。编码智能体跨轮次积累工具输出，文档分析保留参考资料，聊天或标注服务可能处理许多独立请求。这些行为对全局注意力 KV、窗口缓存和循环状态产生不同需求；仅凭应用标签无法确定哪个组件限制了服务容量。

CPU-GPU 超级芯片通过高带宽互连将 GPU 内存与主机内存耦合，为这些工作负载提供了更大的内存层次结构。该链路的带宽在五年内增长了一个数量级（表 1）：从 A100 上 PCIe 4.0 的 64 GB/s 到 Grace Hopper 上 NVLink-C2C 的 900 GB/s，以及 Vera Rubin 上的 1.8 TB/s。这使得 GPU 可以通过直接内存访问和显式传输两种方式访问主机驻留数据。主机内存因此为混合模型维护的不同缓存组件提供了额外的层级。

现有系统通过缓存分配来改善混合模型的内存利用率。静态分区为每个组件预留固定预算，可能导致一个池未充分利用而另一个池空间不足（图 1a）。动态共享方案，如 SGLang 的统一内存池和 vLLM 的混合 KV 缓存管理器，减少了这种不平衡。然而，在缓存布局间共享一个 arena 可能需要更改索引和内存访问，使与注意力后端和其他服务功能的集成变得复杂。

一条互补的研究路线使用卸载来减少 GPU 内存驻留。HiCache 在分层缓存中保留可重用上下文，并在后续执行时恢复它们，减少重复预填充计算。然而，恢复的前缀在后续解码期间仍保持 GPU 驻留。HiSparse 通过在解码期间获取选定的 KV 条目来减少活跃请求的 GPU 占用，但专门针对稀疏注意力。FlexGen 和 Pie 等通用卸载系统通过张量放置和传输调度支持更大的推理批次，但未利用混合模型的缓存访问模式。

为此，我们提出 TideCache，一个包含三个组件的混合模型服务系统：透明缓存池、缓存流式传输器和请求调度器。我们的关键观察是，有界状态层创建了计算间隔，在此期间下一个全局注意力层的历史 KV 尚未被需要。缓存流式传输器利用解码期间的空闲 CPU-GPU 带宽，将主机驻留前缀预取到全局注意力层间共享的 GPU 槽位中（图 1b）。将这些传输与计算重叠可以扩展有效全局 KV 容量：具有可重用主机驻留前缀的请求缩小其 GPU 占用，而新生成的 KV 保持驻留。为使释放的容量对其他缓存组件可用，透明缓存在混合子池的保留虚拟地址后面重新分配物理页。透明缓存池透明地支持现有的缓存布局和注意力后端接口，无需对任何一方进行更改。两种内存机制协同工作：逐层 KV 流式传输释放的 HBM 可以容纳额外请求的窗口缓存和循环状态，更大的解码批次提供更多计算来重叠后续传输。请求调度器协调这些机制，根据请求和队列条件选择驻留或流式执行，并触发子池容量调整。

我们在 SGLang 中实现 TideCache，并在 GB300 和 GH200 超级芯片上评估七种模型/平台配置，无需模型特定的内核更改。在聊天和编码智能体流量混合中，与使用 HiCache 的 SGLang 相比，TideCache 最多可完成 2.04 倍的智能体轮次，将整体 P50 每 token 延迟降低 20-59%，并将智能体 P50 TTFT 提升 1.40-3.05 倍。透明缓存池在每个固定负载下达到两个手动调优分区中较好者的 96.3-113.6% 的轮次；在 GH200 上的变化工作负载下，完整系统相比使用 HiCache 的 SGLang 完成 59% 更多的智能体轮次，并将智能体 P50 TTFT 降低 78%。在相同批次大小下，系统对解码步延迟最多增加 6.3%。

本文做出三项贡献：
- 我们识别出混合服务中的空闲分区容量和空闲解码时 CPU-GPU 带宽这两个机会。
- 我们设计了透明缓存池、缓存流式传输器和请求调度器，并在 SGLang 中在固定虚拟地址后面构建它们。
- 我们在两个超级芯片平台上跨不同工作负载评估七种模型/平台配置。

2 背景

2.1 混合模型推理

自回归模型运行预填充阶段（为输入构建逐层状态）和解码阶段（每步每请求产生一个 token 并更新该状态）。状态是什么取决于层（图 2）。全局注意力层让每个 token 关注所有较早位置，因此其键值（KV）缓存随上下文增长。有界状态层保持大小与上下文无关的状态：滑动窗口层保留最近窗口的 KV，循环层（如 Mamba、Gated DeltaNet 或 Kimi Delta Attention）保持固定大小的状态并就地更新。模型重复堆叠图 2 中的混合块，每隔几个有界状态层放置一个全局注意力层。我们将每种层类型保持的数据称为缓存组件：全局 KV、窗口 KV 和循环状态；在不区分的情况下，我们将两个有界组件统称为状态。对于 TP4 下的 Ring-2.6-1T（BF16 缓存），67K token 上下文每 GPU 使用约 0.72 GiB 的全局 KV，而一个循环状态槽位占用 35 MiB。评估的 SGLang 配置为每个运行请求的准入预算五个这样的槽位（175 MiB 或 0.17 GiB），与上下文长度无关。

2.2 混合缓存管理

服务系统重用前缀的缓存状态以避免再次预填充。在混合模型中，仅全局 KV 命中是不够的：有界状态层只能从匹配位置的检查点恢复，因此每个组件必须在同一边界处保持一致。SGLang 的统一基数缓存在一个前缀树下协调所有组件的匹配、插入和逐出，其内存池拥有张量并决定每个组件获得多少 GPU 内存，要么通过启动时固定的分区，要么通过运行时边界可移动的统一池。HiCache 将树扩展到主机内存：被逐出的前缀和检查点在那里备份，并在会话下一轮运行前加载回来。TideCache 仅替换内存池层，继承基数缓存和 HiCache。

2.3 CPU-GPU 超级芯片上的卸载

在 Grace 超级芯片上，GPU 通过 NVLink-C2C 访问主机内存；一个 GB300 GPU 以实测 211 GB/s 的速度读取固定主机内存，四个 GPU 并发读取时每个达到 182-192 GB/s。使用此路径的两种方式在 GPU 上保留的内容不同。

请求级恢复在轮次运行前一次性复制会话前缀；前缀在整个轮次中保持驻留。

逐层加载仅在 GPU 上保留即将执行的层，并在每个解码步中再次传输其余层；只有当每层的复制在该层开始前完成时才能隐藏，这取决于需要数据的层之间有多少计算。

3 动机

3.1 缓存需求取决于工作负载

不同工作负载对混合模型缓存的不同部分施加压力。繁忙的聊天或数据标注服务可能同时有许多活跃请求，每个请求需要自己的窗口 KV 或循环状态。编码智能体或文档分析可能保留大量上下文，增加每请求的全局 KV 占用。这些例子描述的是需求模式，而非固定的应用类别。对于 N 个运行请求和平均上下文 c̄，全局 KV 需求随 N·c̄ 增长，而有界状态需求仅随 N 增长。固定分区可能耗尽一个组件而使另一个组件未充分利用。图 3 使用 SGLang 默认分区下的 Ring-2.6-1T 说明这种不平衡。状态池将并发限制为 61 个请求，即使大部分全局 KV 未被使用。相反，在每请求 64K token 时，全局 KV 仅容纳 17 个请求，而大部分状态池未被使用。不同的分区会移动这些限制但保留权衡：给一个组件更多内存意味着给其他组件更少。在混合工作负载中，需求随每个请求源的到达率变化，因此为一种混合调优的分区可能成为另一种混合的瓶颈。重新分区不能增加 GPU 的总缓存预算：当合并需求超过 HBM 容量时，它只改变哪些请求等待。

3.2 解码期间 CPU-GPU 链路空闲

HiCache 在轮次间使用主机内存：会话的前缀在其下一轮被准入前完整恢复，并保持驻留直到轮次结束。在解码期间（占轮次的主要部分），主机到设备链路几乎不传输任何内容。其容量很大：GB300 GPU 以 211 GB/s 读取主机内存，因此 Ring-2.6-1T 在第 5 节负载下的一个 57 ms 解码步在该带宽下每 GPU 可以移动约 12 GB。混合模型可以利用这个容量，因为只有其全局注意力层读取前缀。在两个全局注意力层之间，Ring-2.6 的 7 个有界状态层在不需要任何全局 KV 的情况下计算，因此下一层的前缀可以在该间隔中传输，前一层的前缀可以被丢弃。以这种方式服务的请求一次只需要几个全局注意力层的设备内存，而不是所有层。每个解码步更多的计算允许更多的传输重叠。多样化的工作负载可以创造这种机会：并发请求扩大解码批次，而其他请求保留可重用的主机驻留前缀。相关属性是批次计算和缓存需求，而非应用身份。

4 设计

受第 3 节观察的启发，我们构建了 TideCache，一个包含三个组件的服务系统。透明缓存池（TCP，第 4.1 节）通过将物理页移动到阻塞准入的缓存组件来在运行时重新分区 GPU 内存。缓存流式传输器（第 4.2 节）通过在该层运行前将每个全局注意力层的前缀复制到共享槽位中来服务流式请求。请求调度器（第 4.3 节）决定 SGLang 等待队列中的第一个请求（头请求）是以其前缀驻留在 GPU 上运行还是从主机内存流式传输，以及如果两者都不适合，哪个缓存组件阻塞它。三者操作一个内存布局，其定义属性是每个缓存组件保持固定的虚拟地址：注意力后端、页表、CUDA 图和 HiCache 像往常一样寻址缓存，TideCache 仅更改哪些物理页支持一个地址以及哪些主机行在一个步骤中出现在一个地址。

图 4 展示了 TideCache 的架构。请求调度器控制驻留和流式区域的准入（由其两个标记箭头所示），并将准入的请求分派到推理引擎。数据平面暴露虚拟缓存布局、物理 GPU 内存和主机缓存。透明缓存池管理 GPU 页的共享 arena，随着需求变化在缓存组件间重新分区。对于头请求，调度器选择驻留或流式执行，或向透明缓存池报告阻塞的缓存组件以在前向传播间增长。在每个前向传播之前，缓存流式传输器为批次的流式前缀分配槽位行并准备其复制，而 HiCache 像以前一样恢复驻留前缀和备份完成的轮次。

4.1 透明缓存池

如第 3.1 节所示，固定分区即使在另一个缓存组件有未使用容量时也可能阻塞请求。透明缓存池通过在全局 KV、窗口 KV 和循环状态之间动态重新分区共享的 GPU 物理页 arena 来解决这种不平衡。每个缓存组件有一个子池：一个由可变数量物理页支持的固定虚拟地址范围。要增长一个子池，透明缓存池将额外的 arena 页映射到其虚拟范围；要收缩一个子池，它取消映射没有活跃请求使用的页，使其对另一个子池可用。这在不迁移活跃数据或更改其虚拟地址的情况下调整容量。

物理 arena 通过 CUDA 虚拟内存 API 以 2 MiB 页一次性分配。每个子池保留比它将接收的任何物理份额更多的虚拟地址空间，其张量跨越此保留。分配器仅使用其支持页已映射的行。行保留 SGLang 的索引寻址，因此前向传播与物理页位置无关。

透明动态共享。 表 2 对比了动态共享如何影响现有缓存接口。SGLang 的统一内存池（UMP）从原始 uint8 缓冲区的两端分配全局 KV 和有界状态。它将一个页的所有层 KV 打包到一个页信封中；回收碎片空间可能需要复制活跃信封和更新地址映射。这种页主布局需要步长兼容的注意力后端和逻辑到物理的索引转换。在此修订版本中，UMP 拒绝 HiCache 和 LMCache：主机池未初始化，主机卸载缺少逻辑到物理的槽位转换。vLLM 的混合 KV 缓存管理器在缓存组间共享统一大小的页而不迁移活跃块。KV 传输连接器必须实现 SupportsHMA 来处理每组块列表及其异步释放。

这些设计将池特定的布局或分组暴露给缓存消费者。TCP 将重新分区限制在物理页映射中。 它保持逐层张量、虚拟地址和缓存索引，实现无复制的重新分区，无需注意力后端或 HiCache 的池特定适配。相同的虚拟布局原生支持逐层流式传输的别名映射（第 4.2 节），保持现有缓存接口。

移动协议。 透明缓存池每 E=8 个前向传播的周期重新平衡一次容量，最多一个移动在飞行中（图 5）。它规划接收者、数量和捐赠者，并通过从分配器的空闲列表中移除捐赠者行来驻留它们；使用中的行从不被触碰。步骤栅栏等待在驻留之前发出的每个前向传播完成。工作线程然后对驻留的页调用 cuMemUnmap，调用 cuMemMap 来支持接收者的最低驻留行，随后调用 cuMemSetAccess；这些驱动程序调用不等待 GPU，仅触碰没有批次可能使用的内存，因此前向传播继续。池管理器在每个周期轮询工作线程，并在每个 rank 的工作线程完成的第一个周期中应用移动，取消驻留接收者的行。每个周期以一个忙碌标志的全归约开始，因此所有 rank 在相同的前向传播之前应用相同的移动并构建相同的批次。

策略。 透明缓存池采用失败驱动的重新分区策略，将容量引导到阻塞准入的组件，同时限制缓存逐出。当请求调度器因为子池缺乏容量而无法准入头请求时，它请求透明缓存池增长该子池。该子池是接收者；页来自以下来源，按回收成本递增排序：

(1) 空闲页，未分配给任何子池。
(2) 其他子池中的空闲容量，通过取消映射未使用行的页来回收。这些子池作为捐赠者，随着接收者增长而收缩。
(3) 捐赠者子池中的冷缓存前缀，定义为 τ 秒未被触碰的前缀。逐出冷前缀及其检查点释放其缓存行。

透明缓存池在进入下一个来源之前耗尽每个来源。如果增长可以在不逐出的情况下资助，其大小按等待队列长度缩放（上限为 k），以避免每个多周期移动仅准入一个请求。如果需要逐出，增长限制为头请求的需求，以避免丢弃比必要更多的缓存数据。热缓存前缀不被回收为捐赠者，因为丢弃在工具间隔后重用的前缀可能强制重新计算。子池仅收缩以供给接收者。在准入失败之前，TCP 还可以从其他子池的空闲容量或冷缓存中以一个小步骤增长一个空闲空间不足的子池，使热前缀免于后续逐出。

4.2 缓存流式传输器

在每个解码步流式传输每个请求的上下文可能超出链路的传输预算。例如，GPT-OSS-120B 消融（第 5.3 节）在 GH200 上维持 29 个请求的批次，上下文为 8K token。它们的 BF16 全局 KV 在 18 个全局注意力层间占用 8.76 GB。以 400 GB/s 传输整个批次每步需要 21.9 ms，超过选择性流式传输实测的 19.7 ms 解码步。仅靠逐层流水线因此无法在此操作点隐藏全批次传输。缓存流式传输器仅流式传输请求调度器选择的请求子集，保持其余驻留。这引出三个问题：如何仅减少这些请求的物理占用，如何在不破坏解码图的情况下移动它们变化的 KV 地址，以及多少传输可以被隐藏。

选定的请求如何使用更少的 GPU 内存？ 全局 KV 子池将驻留和流式区域分离，同时保持相同的逐层张量接口（图 6）。驻留区域为每层有独立的支持页，由 TCP 管理。它保存无流式服务请求的前缀和所有请求新生成的 KV。仅主机内存中已有的历史前缀被流式传输；生成的 KV 在轮次结束时由 HiCache 备份。

在启动时，L 个全局注意力层的流式区域虚拟范围映射到 M=2 个物理槽位，层 ℓ 使用槽位 (ℓ-1) mod M。这些别名映射让不同的层通过其原始逐层张量寻址相同的物理页。流式前缀在 GPU 上仅占用其全层全局 KV 占用的 M/L。其行一次保存一层的前缀；生成的 token 保留在单独的驻留行中。槽位容量在启动时使用公式 1 中的界限设置，别名映射在执行期间保持固定。TCP 可以在不更改这些映射的情况下重新分区驻留支持。

这些槽位支持图 7 中的双缓冲重叠流水线。单个 H2D 流填充一个槽位而 GPU 读取另一个，使用有界状态计算和全局注意力来隐藏传输。例如，在注意力完成从槽位 B 读取 KV2 后，复制流可以在计算继续通过 KV3 和中间有界状态层时用 KV4 覆盖它。实现此调度需要在不中断解码图的情况下协调槽位重用和 KV 可用性。

选择性 KV 传输如何保持低启动开销？ 流水线必须仅传输批次中流式的前缀，其主机地址、目标行和长度每步可能变化。然而，CUDA 图捕获固定的操作和依赖集。困难是双向的：传输必须等待前一个读取者释放其槽位，同一解码步中的后续注意力操作必须等待该传输。图 8 比较了选择性 KV 传输和低启动开销的三种设计。

图分段（图 8a）将解码图划分为段，并在段启动之间提交动态复制及其依赖。边界让主机在入队消费者的等待之前提交复制及其完成记录。这支持选择性 KV 传输，但重复的图启动和主机协调可能暴露提交气泡。

固定范围传输（图 8b）在计算旁边捕获固定主机范围的复制到槽位中，通过完整的解码图保持低启动开销。然而，复制也移动非活跃行和未使用的容量，浪费链路带宽并在额外传输超过可用重叠时延迟注意力。

我们的图兼容握手（图 8c）保持两个属性：低启动开销和选择性 KV 传输。在重放之前，缓存流式传输器将批次的流式前缀分配给连续的槽位行，更新其页表条目，并将相邻的主机行合并为源-目标复制运行。此准备仅更改元数据；不添加 KV 暂存复制。缓存流式传输器在 H2D 流上使用 cudaMemcpyBatchAsync 提交这些运行，直接从主机缓存复制到槽位中，不传输批次外请求的 KV。

两个持久标志协调每层对槽位的使用。在复制流上，传输等待并清除前一个读取者的 Free，复制选定的行，并发布 Ready。在图内部，小内核在层首次 KV 访问前等待并清除 Ready，并在最终读取后发布 Free。图 8c 中的箭头说明了两种依赖：完成 KV1 的读取允许 KV3 的传输，其完成允许 KV3 的读取。每个标志在被消耗时清除，防止前一步的信号满足当前等待。槽位的首次使用等待其在前一步的最后一个读取者；两个槽位初始空闲。

主机提交到每个槽位的第一次传输，启动完整的解码图一次，然后提交剩余的传输。执行时标志检查让图等待这些传输，即使它们的提交在其启动之后。因此 DMA 地址和长度可以变化，而图节点和标志地址保持固定。主机不需要等待单个层，迟到的传输阻塞其消费者直到 KV 就绪。每个辅助内核使用一个 warp 并在图内重放，无需单独的主机启动。这在不碎片化解码图的情况下保持选择性传输效率；组合实现开销在第 5.3 节中评估。

流式传输可以扩展多少有效全局 KV 容量？ 对于固定的 GPU 缓存预算，有用的扩展受限于每个解码步内可以交付多少主机驻留 KV。有 L 个全局注意力层、每行和层 b 字节、计算时间 T 和持续链路带宽 BW，流式传输 A 行每步传输 L·A·b 字节。为隐藏这些传输，我们要求 L·A·b ≤ η·BW·T，其中 η < 1 留出调度余量。得到的隐藏界限 C 限制准入（第 4.3 节）。有 M=2 个流式槽位，界限和相对容量增益为

C = η·BW·T / (L·b), r = C(1 - M/L) / D (1)

其中 D 是相同 GPU 预算下完全驻留的全局 KV 池的容量（以行为单位）。C 个流式行的槽位消耗相当于 M·C/L 个驻留行，净增益为 C(1-M/L)。忽略页舍入，有效容量因此达到 (1+r)·D，前提是槽位适合 GPU 预算。这是聚合带宽界限；传输还必须满足每层的截止时间。

在 GPT-OSS-120B 消融（第 5.3 节）中，L=18，b=2 KiB，M=2，D=147,648。尺寸校准（T=13.16 ms，BW=400 GB/s，η=0.9）给出 C≈128.5K 和 77% 容量增益。配置的 126,976 个流式行加上 133,056 个驻留行在页舍入后产生 260,032 个 token——原始容量的 1.76 倍。

对于固定模型和槽位数量，更多带宽或更长的计算增加扩展；更大的每 token KV 占用或原始驻留容量减少相对增益。我们使用预期批次下的离线解码校准来调整 C 的大小。额外容量服务于主机驻留的历史前缀；新生成的 KV 保持驻留。当全局 KV 容量限制准入且其他缓存组件有空间时，更高的并发随之而来。

4.3 请求调度器

请求调度器协调 TCP 和缓存流式传输器，在可用 GPU 容量和传输预算内准入更多请求。对于头请求 r，它考虑其状态槽位 nₛ、未缓存的全局 KV 行 n_f 和主机缓存前缀长度 h。驻留轮次持有 n_f + h 个驻留行。流式轮次保持 n_f 行驻留并使用 h 个流式槽位行，每步每层传输 h·b 字节；总流式行必须保持在 C 内（第 4.2 节）。如果容量不足，TCP 可以使用空闲页、空闲容量或冷缓存增长阻塞的子池。算法 1 给出决策顺序。

仅当驻留区域竞争时请求才被流式传输：Pressure 从等待请求需要的行、N 个运行请求在平均输出长度 ℓ̄ 上的解码增长以及该轮次期间的到达（每步 λ 个，提示长度 p̄，缓存未命中比例 φ）投影该区域的需求，所有这些都是每个 rank 观察到的事件的基于计数的运行平均值。被选择流式传输的请求如果槽位已满则跳过此迭代，允许需要其他资源的请求继续。room(G) 计算驻留区域的空闲行和有主机副本的缓存行，减去为进行中预填充的保留；h_min 是值得流式传输的最小前缀大小。

5 评估

5.1 实验设置

实现。 TideCache 在 SGLang 中增加了约 9K 行代码，主要在内存池包中。它支持多头、潜在和稀疏索引全局注意力、滑动窗口缓存和循环状态，同时保持注意力后端和 CUDA 图运行器。

测试平台。 我们使用两个超级芯片平台。GB300 节点有四个 NVIDIA GB300 GPU，每个有 288 GB HBM3e，通过 NVLink 连接，以及两个 72 核 Grace CPU 和 960 GB LPDDR5X 主机内存；每个 GPU 通过 NVLink-C2C 以实测 211 GB/s 的主机到设备速度访问主机内存。GH200 超级芯片将一个 72 核 Grace CPU 与 480 GB LPDDR5X 和一个通过 NVLink-C2C 连接的 96 GB HBM3 的 H100 GPU 配对。

模型。 表 3 列出了七种模型/平台配置，覆盖三种循环层和滑动窗口注意力上的潜在、分组查询和稀疏索引全局注意力。Kimi K3 和 Qwen3.8-2.4T 使用其前 48 和 36 层以适应 HBM，保持每层的缓存几何。SGLang 的内存比例保持正常部署值（0.80-0.95）。

工作负载和指标。 我们从 ShareGPT 请求轨迹和 SemiAnalysis 发布的多轮 Claude Code 轨迹构建合成混合。前者平均有 896-1152 个输入 token 和 703 个输出 token，作为开环泊松过程到达。后者有 40K-110K token 上下文和 8-28 轮；闭环重放保留工具间隔并将输出馈入后续轮次。两个源共享一个先来先服务队列，不向调度器提供应用标签或优先级。我们改变独立请求到达率和并发会话数；配置标签使用 req/s × sessions。预热后（GB300 上 360 秒；GH200 上至少 600 秒），测量窗口为 600 秒，变化工作负载为 900 秒。Turns/s 是窗口内完成的智能体会话轮次数除以窗口持续时间。P50 每 token 延迟是窗口内提交的所有请求的端到端请求延迟除以实际输出 token 数的中位数。P50 TTFT 是该窗口内提交的会话请求的提交到首 token 延迟的中位数。Turns/s 和 TTFT 因此描述智能体会话，而每 token 延迟覆盖完整混合；两个延迟都包括预填充和排队，并计算提交队列在窗口后的完成。

5.2 端到端性能

我们在七种配置下评估内存压力下的性能，然后检查对执行期间需求变化的工作负载的适应性。

内存压力下的性能。 图 9 对每个配置使用一个负载点，其中会话前缀超过驻留全局 KV 容量。没有 HiCache，重复的前缀计算占用 GPU 并延迟后续请求。HiCache 避免了大部分这种重新计算，但每个恢复的前缀在其整个轮次中保持在 GPU 内存中，限制了可以并发进行的会话。TideCache 通过在全局注意力层间重用 GPU 内存来缓解这种容量约束。相对于 SGLang w/ HiCache（调优），它最多完成 2.04 倍的轮次，将整体 P50 每 token 延迟降低 20-59%，并将智能体 P50 TTFT 提升 1.40-3.05 倍。TideCache 通过缓解内存压力和缩短服务会话前缀的等待来降低 TTFT。轮次增益在 GH200 上达到 2.04 倍，在 GB300 上达到 1.44 倍，与 HBM 较少时全局 KV 的更大容量收益一致。第 5.3 节检查基线分区调优的效果。

对工作负载变化的适应性。 图 10 在 900 秒预热后在 GH200 上运行 Qwen3.8-27B。900 秒测量包括三个 300 秒阶段：独立请求到达从 0.05 上升到 1.6 req/s，然后回到 0.05 req/s。十个智能体工作器在突发前后重放十个会话；突发期间新智能体轮次暂停，而进行中的请求完成。这在全局 KV 和有界状态之间转换需求。静态基线保持 1.0 的状态：全局 KV 比率，而两个 TideCache 变体从 0.6 开始并在线适应。SGLang、SGLang w/ HiCache、TideCache w/o streaming 和 TideCache 分别完成 57、115、174 和 183 个智能体轮次。相对于 HiCache，TideCache 完成 59% 更多的轮次，将整体 P50 每 token 延迟从 63.4 降低到 39.3 ms（38%），并将智能体 P50 TTFT 从 25.70 降低到 5.68 s（78%）。

时间线暴露了固定和自适应分配之间的差异。HiCache 的池容量在工作负载变化时保持不变。TCP 在突发期间将 TideCache 的有界状态分配从约 5.6 增长到 17.6 GiB，然后在智能体活动恢复时将其返回到约 6.0 GiB。大约一半的 GPU 缓存预算更换了所有者，使容量可用于受压的组件。静态基线达到其原生的 32 请求运行限制；HiCache 的突发队列峰值达到 74 个请求，而 TideCache 为 15 个。流式传输进一步扩展了会话前缀的有效全局 KV 容量：相对于无流式变体，它将完成的轮次从 174 增加到 183，并将智能体 P50 TTFT 从 8.13 降低到 5.68 s（30%）。

5.3 消融研究

我们在消融中检查透明缓存池、对分割比率的敏感性和实现开销。

独立 TCP 性能。 图 11 通过禁用主机缓存和逐层流式传输来隔离 TCP，将其与固定分区和 UMP 进行比较。TCP 和 UMP 都动态共享 GPU 容量；我们测试 TCP 是否在保持现有缓存接口的同时匹配 UMP 的吞吐量。UMP 的 HiCache 集成在评估的修订版本中不完整，因此我们仅在此仅 GPU 比较中包含它。每个模型使用三种混合，Kimi K3 的大/小固定状态：全局 KV 比率约为 1.3/0.26，GLM-5.3-Flash 为 2.8/0.85。TCP 从每个模型的一个分配开始并在线适应。在六个点上，它达到较好固定分区 turns/s 的 96.3-113.6%，无需按混合调优。它在 Kimi K3 上匹配 UMP，turns/s 高 0-3.7%。N/A 表示 GLM 的 DSA 后端，UMP 修订版本 25ce8063 不支持；TCP 支持其现有布局。

对分割比率的敏感性。 图 12 说明了图 9 中使用的基线调优，在 Kimi K3 上将分割比率从 2 扫描到 6。SGLang w/ HiCache 在比率 3 处达到峰值 67 个完成轮次（用于主比较的设置），而其他测试比率为 44-59：给状态分配太少内存限制准入，而给全局 KV 分配太少限制驻留前缀。TideCache 参考完成 94 个轮次，比最佳测试基线高 40%，在该起始比率下整体 P50 每 token 延低 29.5%。因此，调优基线的固定分区不能缩小差距。

系统开销。 图 13 比较了三次运行的每个批次大小的中位数解码吞吐量，具有相同的 GPU 缓存预算和 SWA：全局 KV 分割。测量包括此路径上的组合实现：传输提交、页表更新和 CUDA 图协调。在两个系统都能维持的批次大小下，TideCache 的解码步时间与 SGLang w/ HiCache 相差 -1.1% 到 +6.3%。增加的容量补偿了这一成本：有效全局 KV 容量从 148K 上升到 260K token，最大持续批次从 16 增长到 29。峰值解码吞吐量从 1.19K 上升到 1.47K tokens/s，增益 24%。

6 相关工作

混合缓存管理。 静态分区在启动时固定每个缓存组件的 GPU 预算。SGLang 的统一内存池在子池间共享字节缓冲区并通过复制压缩活跃槽位；vLLM 的混合 KV 缓存管理器动态分配共享块到缓存组。Jenga 在两级分配器中使用 LCM 大小的父页用于异构缓存。这些设计通过软件级缓存布局和映射实现共享。vAttention 首先通过 CUDA 虚拟内存 API 用物理页按需支持连续虚拟 KV 缓存，Prism 在共享 GPU 的模型间重新映射物理页。TideCache 将相同的原语应用于一个混合模型的缓存组件间，添加一个由所有全局注意力层共享页的区域，并从准入队列驱动重新映射。

KV 缓存卸载。 FlexGen 在 GPU、CPU 和磁盘间调度权重、激活和 KV；ZeRO-Inference 从 CPU 或 NVMe 流式传输层权重以支持大推理批次。Pie 在主机和设备间交换 transformer 层的 KV，使活跃集超过 GPU 内存；InfiniGen 和 HiSparse 仅获取注意力实际会读取的 KV；SuperInfer 在超级芯片上轮转请求通过 GPU 并使用两个传输方向保持延迟有界。TideCache 利用混合结构：只有全局注意力层持有与上下文成比例的数据，而有界状态计算提供时间重叠其传输。这使得在解码提供足够计算时，每步流式传输变得可行。

7 结论

我们提出了 TideCache：透明缓存池透明地重新分区 HBM，缓存流式传输器将逐层传输与计算重叠，请求调度器协调准入。在 GB300 和 GH200 上的七种模型/平台配置中，它比使用 HiCache 的 SGLang 最多完成 2.04 倍的智能体轮次，将整体 P50 每 token 延迟降低 20-59%，并将智能体 P50 TTFT 提升 1.40-3.05 倍。
