摘要
诸如 Lean 4 之类的证明助手承诺了形式化验证数学的范式，但大规模形式化项目一直面临着重大准入门槛，包括需要形式验证（以及底层数学）的专业知识，以及编写形式化证明所需的大量时间。AI 编码智能体极大地降低了这些门槛；人类用户现在可以使用自然语言提示智能体在 Lean 中编写复杂的证明。这开启了一种引人入胜的可能性，即涉及人类和 AI 智能体的互联网规模数学协作，其中正确性由机器检查。

为了实现这一可能性，我们引入了 Prove2Me，一个用于形式化数学的开放协作平台。用户发起形式化“任务”，AI 智能体为此贡献形式化证明以完成任务。我们在 Prove2Me 中设计了机制和专用框架，以实现大规模协作，使得智能体能够基于彼此的工作并自由重用现有结果。
在此过程中，Prove2Me 旨在将数学形式化转变为一种可扩展的、众包的努力，对任何拥有智能体的人开放。

1 引言
完全形式化数学语料库的梦想——即每个定理都由机器检查且每个证明步骤都可验证——长期以来一直受制于所需的大量人力。菲尔兹奖得主 Peter Scholze 的“液态张量实验”需要大约十八个月的持续社区努力 (Commelin et al., 2022)，而正在进行的费马大定理形式化项目获得了五年的资助，其负责人 Kevin Buzzard 承认他“无法独自完成形式化” (Buzzard, 2024)。在这些情况下，形式化一直局限于一个小型专家社区，他们必须同时是数学和证明助手工程方面的专家。

然而，AI 驱动的定理证明的最新进展提供了一个转折点。AI 系统在形式化数学方面正在迅速改进 (Yang et al., 2023; Yang et al., 2024; Hubert et al., 2026; Song et al., 2024; Achim et al., 2025)，并且越来越多的工作利用 AI 智能体来形式化研究论文 (Garg, 2026; Ren et al., 2026; Bei et al., 2026) 和教科书 (Gloeckle et al., 2026; Rammal et al., 2026; Wang et al., 2026; Urban, 2026)。这些努力提供了一个有希望的信号，即通过多个 AI 智能体协同工作，以前需要数月甚至数年的形式化任务可以得到大幅加速。

然而，现有的努力仍面临以下障碍。第一个是审计：尽管有 LLM 辅助的方法 (Wang et al., 2026; Garg, 2026)，但要确定形式化是否忠实地捕捉了其预期含义仍然需要人类专业知识，这无法扩展到可能包含数十万个定理的 AI 生成项目 (Gloeckle et al., 2026; Urban, 2026)。第二个是可重用性：先前的 Lean 形式化通常作为紧密相互依赖的定理托管在 GitHub 上，这使得难以孤立地提取、重用或导入单个结果。第三个是规模：尽管成千上万的智能体群已经能够产生令人印象深刻的结果 (Gloeckle et al., 2026; Rammal et al., 2026)，但它们依赖于单一组织的内部计算资源。原则上，任何拥有 AI 智能体的人现在都应该能够做出贡献。有了正确的协作协议和激励机制，形式化可以 tapping 广大公众的集体 token 预算。

为了充分释放和扩展 AI 在形式验证中的力量，我们引入了 Prove2Me，一个大规模数学形式化的开源协作平台，其中 AI 智能体作为一等参与者。Prove2Me 的贡献有四个方面：(1) 低准入门槛：配备了 AI 智能体，任何人都可以贡献 Lean 证明，而无需具备 Lean 甚至底层数学的专业知识；(2) 基于任务的设计，将人类审计限制在一个经过精心挑选的核心陈述中，让 AI 智能体自由地大规模生成中间定理；(3) 协作机制，能够将复杂证明分解为原子化任务，以便智能体自然地基于彼此的工作进行构建；(4) 可重用库，随着完成的证明成为可引用的构建块且未解决的子问题作为新挑战出现，该库有机地增长。

我们对 Prove2Me 的愿景是利用 AI 智能体的众包努力来大规模形式化数学项目。本文的其余部分组织如下。第 2 节回顾了相关工作。第 3 节介绍了在 Prove2Me 上提交和解决问题的基本工作流程，以及我们基于类型的验证设计。第 4 节介绍了证明草图，这是实现将困难定理分解为原子化子问题并允许跨智能体协作和重用的关键机制。第 5 节报告了社区在该平台上完成的任务。第 6 节提供了一个关于为 Prove2Me 做贡献的教程，这不需要 Lean 甚至底层数学的专业知识。

2 相关工作
用于定理证明的 AI。自从 GPT-f 首次将机器生成的证明贡献给形式化库以来 (Polu and Sutskever, 2020)，快速的进展（包括检索增强证明器 (Yang et al., 2023)、在 miniF2F 上达到 88.9% 的 DeepSeek-Prover 系列 (Xin et al., 2024; Xin et al., 2025; Ren et al., 2025)、AlphaProof 的国际数学奥林匹克银牌表现 (Hubert et al., 2026)、诸如 Aristotle 的 IMO 级别系统 (Achim et al., 2025) 以及工作流集成的策略建议 (Song et al., 2024)）表明，AI 智能体越来越有能力生成形式化证明脚本；我们建议读者参阅 Yang et al. (2024) 的综合调查。然而，这些能力仍然孤立于各个研究流程中，没有共享的场所让智能体和人类协作攻克开放的形式化挑战。

AI 辅助的形式化。在这些证明器的基础上，最近的一波工作应用 AI 智能体端到端地形式化现有语料库。一条路线针对教科书和基础理论：一个单一的编码智能体用大约 13 万行 Lean 形式化了点集拓扑 (Urban, 2026)，而多智能体群进一步扩展，在大约一周内形式化了一本 500 页的研究生组合学教科书 (Gloeckle et al., 2026)，并组装了跨越数十本教科书的库 (Rammal et al., 2026; Wang et al., 2026)。另一条路线针对个别研究论文，从经济学和计算 (Garg, 2026; Bei et al., 2026) 到量子计算 (Ren et al., 2026) 和物理学 (Meadows et al., 2026)。尽管 AI 生成 Lean 证明的速度令人鼓舞，但这些努力仍然存在以下局限性，这也激发了 Prove2Me 的诞生。

审计。证明内核证明了一个证明属于某个陈述，但不能证明该陈述忠实地捕捉了预期的主张；AI 生成的陈述可能是空洞的、遗漏了假设或在语义上发生了漂移，但仍然被“证明”了 (Gloeckle et al., 2026)。由于自动化的忠实性检查仍然不完善（最近的一项 Lean 作为评判者的审计发现只有大约 43% 的已证明陈述是忠实的 (Bourigault et al., 2026)），一种常见且有效的缓解措施是缩小人类审计范围，仅审查定义和顶层陈述，而不是证明 (Gloeckle et al., 2026; Garg, 2026)。Prove2Me 通过提前固定审计范围进一步推进了这一原则：人类审查任务的核心部分，即其目标陈述、它所依赖的定义，以及构建其证明的里程碑引理，而智能体则自由地引入其余的中间定理。

可重用性和成本。现有的形式化通常作为紧密相互依赖的定理的整体 Git 存储库发布。因为每当模块发生变化时，即使是仅针对证明的编辑，Lean 也会重新编译整个下游依赖树，所以集成是通过单个合并队列串行化的，这成为了大型智能体群的经验瓶颈 (Gloeckle et al., 2026; Rammal et al., 2026)；相应地，单个结果很难脱离上下文进行提取和重用。最后，这些智能体群在单一组织的内部计算资源上运行，每个项目有数万个智能体和五位数的预算 (Gloeckle et al., 2026; Rammal et al., 2026)，使得更广泛社区的集体资源未被利用。在这项工作中，我们设计了一个框架和机制，能够在平台上平滑地重用已证明的结果，并展示了用甚至几个智能体就能完成的类似形式化项目的案例研究。

3 Prove2Me 的基本设计
Prove2Me 旨在托管既高效又可扩展的验证。其基本设计决策是将定理的陈述与其证明分开：每个定理都是一个独立的、不可变的对象，只陈述一次，并且可能有多个证明，可能由不同的智能体完成。这种分离是本文其余部分描述的每个功能的基础。我们从平台上的两个基本操作开始，提交定理（第 3.1 节）和提交证明（第 3.2 节），然后介绍审计任务（第 3.3 节），这是保持智能体生成的库值得信赖的机制。

3.1 提交定理
作为一个运行示例，我们采用下面这个来自著名的灵敏度猜想证明 (Huang, 2019) 的引理，并从其自然语言形式追踪到平台上托管的定理。
引理 3.1。假设 $H$ 是一个具有 $m$ 个顶点的无向图，$A$ 是一个对称邻接矩阵，其元素在 ${-1,0,1}$ 中。那么 $H$ 的矩阵度满足 $\Delta(H)\geq\lambda_{1}:=\lambda_{1}(A)$。

在 Prove2Me 上，这个引理在 Lean 4 中被形式化并存储为 max_degree_ge_lambda_max，其定理卡片包含以下字段：
• 描述：对陈述背后的数学的自然语言说明，类似于引理 3.1。还鼓励智能体详细说明预期的表述。
• 前言：导入部分，如图 1 的上半部分所示。通常，此字段不仅可以包含来自 Mathlib 的导入，还可以包含来自 Prove2Me 上托管的其他定义文件的导入。
• 形式化陈述：在 Lean 4 中形式化的目标陈述本身，如图 1 的下半部分所示，要求以 := by sorry 占位符结尾。

⬇
-- 前言
import Mathlib.Analysis.Matrix.Spectrum
import Mathlib.LinearAlgebra.Matrix.Hermitian
import Mathlib.Data.Fintype.Basic
import Mathlib.Data.Real.Star

-- 形式化陈述
theorem max_degree_ge_lambda_max
{V : Type*}
[Fintype V]
[DecidableEq V]
{A : Matrix V V ℝ}
(hA : A.IsHermitian)
(h_entries : ∀ u v : V, A u v = -1 ∨ A u v = 0 ∨ A u v = 1)
(adj : V → V → Prop)
[DecidableRel adj]
(h_zero : ∀ u v : V, ¬adj u v → A u v = 0)
[Nonempty V] :
∃ v : V, hA.eigenvalues 0 ⟨0, Fintype.card_pos⟩ ≤ ((Finset.univ : Finset V).filter fun u => adj u v).card := by
sorry

图 1：定理卡片 max_degree_ge_lambda_max（引理 3.1 的 Lean 4 形式化）的前言和形式化陈述字段。该陈述是针对纯粹的邻接谓词 adj 而不是 SimpleGraph 提出的，这使得它可以直接应用于灵敏度证明所需的超立方体子集；这种选择正是描述字段所记录的内容，也是审计（第 3.3 节）所检查的内容。

一个完整的提交还可以包含一个来源字段（指向原始论文或教科书的链接）以及将该定理归入某个学科分类的标签。引理 3.1 的完整定理卡片可以在其定理链接中找到。最后，Prove2Me 支持多个验证环境，每个环境都固定到特定的 Mathlib 和工具链版本，提交智能体选择目标环境。一旦定理在相应的后端编译通过，它就会被接受。环境之间是完全隔离的，因此结果总是带有重现它所需的精确上下文。

3.2 提交证明
因为陈述和证明是独立的对象，一个定理可能有多个独立的证明。为了根据陈述检查证明，Prove2Me 依赖于 Lean 4 核心的 Curry-Howard 对应关系 (Wadler, 2015)：一个命题的证明是一个类型为该命题的项。具体来说，一个证明提交是一个 Lean 文件，它声明了一个名为 solution 的定理，其类型与目标定理的类型完全匹配，并且不包含 sorry 或任何其他新公理。

⬇
import Mathlib.Data.Matrix.Mul
open Matrix

/-!
max_degree_ge_lambda_max 的完整证明。
一个标准的“最大坐标”Perron 风格论证。
-/

theorem solution
{V : Type*}
[Fintype V]
[DecidableEq V]
{A : Matrix V V ℝ}
(hA : A.IsHermitian)
(h_entries : ∀ u v : V, A u v = -1 ∨ A u v = 0 ∨ A u v = 1)
(adj : V → V → Prop)
[DecidableRel adj]
(h_zero : ∀ u v : V, ¬adj u v → A u v = 0)
[Nonempty V] :
∃ v : V, hA.eigenvalues 0 ⟨0, Fintype.card_pos⟩ ≤ ((Finset.univ : Finset V).filter fun u => adj u v).card := by
-- 将 eigenvalues 0 ⟨0, _⟩ 连接到某个 j : V 的 eigenvalues j。
set i0 : Fin (Fintype.card V) := ⟨0, Fintype.card_pos⟩
set j : V := (Fintype.equivOfCardEq (Fintype.card_fin _)) i0 with hj_def
-- ... 剩余证明，无 sorry。

图 2：引理 3.1 最大度界限的证明提交（节选）。该文件声明了 theorem solution，其类型与目标 max_degree_ge_lambda_max 完全相同，并在没有 sorry 的情况下闭合了它。

图 2 说明了图 1 中的定理 max_degree_ge_lambda_max：提交原样重用了目标的类型，并提供了一个属于该类型的项。然后，平台在与目标定理相同的环境中编译提交，并检查 solution 的类型是否与目标陈述的类型匹配，从而使得两者作为 Lean 项是可以互换的。对称地，智能体可以通过提供一个类型为 ¬(目标陈述) 的 theorem solution 来提交定理的反证，即原定理的否定。除了证明文件外，智能体还需要上传对证明思路的详细自然语言解释，该解释链接到证明，以造福人类读者和其他智能体。

3.3 审计任务
因为任何拥有 AI 智能体的人都可以提交定理，所以陈述可能是错误的、定义不明确的或幻觉产生的。这对于内容主要由智能体生成的平台来说尤其是一个风险。最近的工作尝试对形式化陈述进行自动审计 (Wang et al., 2026; Garg, 2026; Gloeckle et al., 2026; Ren et al., 2026)，但要提供形式化忠实捕捉其预期含义的强有力保证，通常仍然需要人工审计。

然而，人工审计无法扩展，而我们的目标是让智能体生成越来越多的内容。Prove2Me 通过任务解决了这一矛盾。一个任务由一个标题目标（例如，项目、论文或书籍章节的主要定理）、它所依赖的定义以及构建其证明的里程碑引理（第 4.4 节）组成。人类在任务发布前审计这个核心部分，检查其每个形式化陈述是否忠实地捕捉了预期的数学内容，并且除此之外不审计任何东西。然后，智能体通过自由引入未经审计的中间引理来提供剩余的证明细节。这是合理的，因为受信任的对象不是智能体选择的分解方式，而是 Lean 内核对已审计陈述证明的接受。中间引理只有在帮助闭合已审计目标时才重要。因此，人工审计受任务核心的限制，而开放式证明细化则随智能体的努力而扩展，这与最近的 AI 辅助形式化实践相一致 (Gloeckle et al., 2026; Garg, 2026)。

领导任务。任务由船长创建，即提出该任务的人类贡献者。船长不需要编写 Lean：船长的智能体会起草任务提案，这是一个包含目标定理、其定义和里程碑引理（第 4.4 节）的私有包。任务提案保持可变状态，因此在正式发布到平台之前，仍然可以修复形式化不当的陈述。船长不能委派的是审计：人类需要单独点击每个陈述来确认它，确保没有未经阅读的陈述进入审计核心。确认的草稿随后被编译并发布为不可变的定理，平台版主在任务上线前对其进行审查。

子智能体回读。审计忠实性通常需要阅读 Lean，这将参与限制在形式化专家中。Prove2Me 通过子智能体回读步骤降低了这一门槛。对于每个候选陈述，一个独立的审计智能体会获得 Lean 声明及其依赖定义，但没有原始来源参考。智能体将 Lean 代码翻译回普通的 LaTeX 数学，明确绑定器和假设，并在需要时展开非标准定义。然后，人类审计员比较两个数学陈述：源 LaTeX 陈述和智能体从 Lean 回读的陈述。忠实性是通过这两个陈述是否匹配来判断的，而不是要求审计员直接检查 Lean。Garg (2026) 应用了相关的回译检查。图 3 显示了在关于 Erdős 问题 390 的任务中起草的陈述的回读。

图 3：起草陈述的回读。审计智能体只看到 Lean 代码（顶部），并呈现它字面断言的内容（底部），展开了两个特定于问题的定义，并考虑了每个绑定器和假设，包括源陈述会隐含的那些：两个有限集是独立量化的，空乘积为 1，以及假设仅为 $n<M$。人类审计员将此证词与源陈述进行比较。

一个任务通常涉及数百甚至数千个支持定理和引理。因此，这种设计保持了审计核心以及任务的标题目标值得信赖，同时充分释放了 AI 智能体大规模生成内容的能力。

4 多智能体协作
Prove2Me 的一个核心目标是让每个拥有 AI 智能体的人都能为数学形式化做出贡献。实现这一目标需要协调许多去中心化智能体的工作，使它们各自的贡献组合成一个连贯的整体。在第 3 节描述了平台的基本机制之后，我们现在转向使这种协调成为可能的设计。我们首先解释为什么显而易见的方法——要求智能体填充 sorry 占位符——无法扩展（第 4.1 节）；然后我们介绍证明草图，它将困难定理分解为原子化的、可独立解决的子问题（第 4.2 节）；我们展示相同的导入机制如何将已证明的定理转变为可搜索、可重用的语料库（第 4.3 节）；我们描述里程碑，即保持这些子问题与源对齐的精选目标（第 4.4 节）；最后，我们描述建立在这种分解之上的协作机制（第 4.5 节）。

4.1 朴素的 sorry 填充无法扩展
一种自然的首选方法是要求智能体直接填充大型证明中的 sorry 占位符，每个智能体编辑一组共享文件。这无法扩展，原因有二。首先，它在计算上很昂贵：每当下游引理发生变化时，每个依赖于它的上游文件都必须重新编译，而从头编译像 Mathlib 这样的大型库是出了名的慢 (The mathlib Community, 2020)。其次，更根本的是，工作难以原子化。当几个智能体编辑同一个文件或目录时，它们的贡献通常是相互依赖和相互干扰的，因此努力无法在智能体之间干净地分配。

一些现有的大规模 Lean 项目通过 Git 工作流缓解了这些问题 (Rammal et al., 2026; Gloeckle et al., 2026)，但这是以中心化为代价的：拉取请求必须由人类维护者或编排智能体审查和合并，对于像 Prove2Me 这样的去中心化平台来说，这个瓶颈变得极其昂贵。而且因为底层定理仍然相互依赖且非原子化，在它们的原始上下文之外重用它们仍然很困难。

4.2 通过证明草图进行证明分解
我们的解决方案是让证明导入平台上已有的其他定理，包括尚未证明的开放定理。我们将导入其他定理的证明称为证明草图：它基于导入的陈述建立目标，将它们的证明推迟到单独的提交中。我们用 Huang (2019) 的灵敏度猜想来说明。

定理 4.1（Huang 的灵敏度猜想）。对于每个整数 $n\geq 1$，设 $H$ 为 $n$ 维超立方体图 $Q^{n}$ 的任意 $(2^{n-1}+1)$ 顶点导出子图，并用 $\Delta(H)$ 表示 $H$ 的最大度。那么 $\Delta(H)\geq\sqrt{n}$。

按照 Huang (2019) 中的证明，定理 4.1 归约为上一节的引理 3.1 以及下面的另外两个引理。

引理 4.2（柯西交错定理）。设 $A$ 为对称 $n\times n$ 矩阵，$B$ 为 $A$ 的 $m\times m$ 主子矩阵，其中 $m<n$。如果 $A$ 的特征值为 $\lambda_{1}\geq\lambda_{2}\geq\cdots\geq\lambda_{n}$，$B$ 的特征值为 $\mu_{1}\geq\mu_{2}\geq\cdots\geq\mu_{m}$，那么对于所有 $1\leq i\leq m$，有 $\lambda_{i}\geq\mu_{i}\geq\lambda_{i+n-m}$。

引理 4.3。我们迭代地定义对称方阵序列如下，
$A_{1}=\begin{bmatrix}0&1\ 1&0\end{bmatrix},\qquad A_{n}=\begin{bmatrix}A_{n-1}&I\ I&-A_{n-1}\end{bmatrix}.$
那么 $A_{n}$ 是一个 $2^{n}\times 2^{n}$ 矩阵，其特征值为重数为 $2^{n-1}$ 的 $\sqrt{n}$，以及重数为 $2^{n-1}$ 的 $-\sqrt{n}$。

因此，定理 4.1 的证明草图是一个单一的、无 sorry 的 Lean 证明，它导入了这些子引理，如图 4 所示。回顾上一节，Prove2Me 将陈述与证明分开。根据 Curry-Howard 对应关系，导入另一个定理或引理等价于假设一个类型为该陈述的项，对于开放定理，该项仍然以 sorry 结尾。此外，Prove2Me 保证了不可变性：Prove2Me 上的每个陈述和证明草图都是持久的，一旦提交就无法编辑。因此，一旦无 sorry 的证明草图被接受，它就建立了一个永久的逻辑保证。形式上，我们有以下属性。

4.3 Formalpedia：可重用定理的可搜索语料库
证明草图可以导入开放定理或已证明的定理。上一节使用了第一种情况，即导入将工作推迟到子问题；第二种情况是最纯粹的重用。因为每个陈述都是原子化和不可变的，带有自行编译所需的所有上下文，所以任何已证明的定理都可以作为任何后续证明草图（在任何任务中）的构建块。因此，Prove2Me 有机地发展成为一个跨任务积累的形式化数学共享库。我们将这个库命名为 Formalpedia，与 Prove2Me 构建形式化数学百科全书的愿景保持一致。

Formalpedia 建立在 Mathlib、CSLib 和 PhysLib 等精选基础库之上 (The mathlib Community, 2020; Barrett et al., 2026; community, 2024)，而不是与它们竞争：它专注于应用层，其中的结果是一次性的且相互独立的。我们也希望平台上积累的一些内容最终能被贡献回这些库。Formalpedia 还分享了 Palomar 和 TheoremDB 等 Lean 验证结果注册表的开放精神，但在两个方面更进一步：每个陈述都是可单独导入的，因此可以在别人的证明中轻松重用；并且附带的框架将形式化工作本身开放给更广泛的社区。

Prove2Me 还提供了对该语料库的搜索 API。该框架要求每个智能体在其 Lean 陈述（第 3.1 节）旁边提交详细的、标准化的自然语言描述，这正是搜索 API 索引的内容。还指示智能体在提交之前进行搜索：在存在现有定理的地方重用它，只有在没有时才引入新陈述。

最后，重用在 Prove2Me 上也会得到奖励。贡献者不仅因为闭合开放定理而获得荣誉，还因为提出后来被其他证明导入的陈述而获得荣誉，这是该平台引用的形式。因此，激励与机制指向相同的方向：一个定理被构建得越多，它就越有价值。

4.4 里程碑：精选任务检查点
证明草图让智能体分解定理，但仅靠分解并不能使去中心化的工作组合起来。多智能体协作的另一个障碍是达成共识，这可能在两个方面失败。首先，没有共享目标，几个智能体会以互不兼容的方式独立形式化同一个引理；因为结果陈述不能相互导入，平行的努力是重复的而不是累积的。其次，默默偏离源的形式化会污染其上方的所有内容，因为每个导入有缺陷陈述的证明草图都会继承其错误。因此，去中心化智能体需要一个引理级别的目标，它既是幂等的，以便独立的尝试收敛到一个规范陈述，又是权威的，以便下游证明可以在不重新审计的情况下基于它构建。Prove2Me 正是通过里程碑来提供这一点的，里程碑是由任务船长（第 3.3 节）精选的引理级别子目标。

里程碑由权威的自然语言陈述（通常从源论文或教科书逐字转录）以及一旦船长证明一个定理后指向其规范形式化的定理链接组成。里程碑是有序的，因为后面的里程碑通常依赖于前面的。图 6 显示了灵敏度猜想任务的里程碑列表。

图 6：灵敏度猜想任务的里程碑列表。每个里程碑将一个从源证明转录的权威陈述与船长证明为其规范形式化的平台定理配对。所示的两个里程碑正是第 4.2 节中的柯西交错定理和 $A_{n}$ 的谱，这里链接到已证明的定理 cauchy_interlacing_sorted 和 huang_matrix_spectrum_sorted。标题跟踪已达到的里程碑数量以及任务中已证明的定理数量。

因为列表是权威的，它成为任务的入口点，而不是原始的分解图。智能体针对里程碑的陈述进行形式化，而不是发明自己的重述，并重用其链接定理已被证明的里程碑，而不是重新证明它。

因此，里程碑起着类似于检查点的作用。它们防止并发智能体产生同一引理的冲突形式化。它还提供了中间立足点，因此没有智能体必须从头开始攻击大型任务。一旦每个里程碑都被证明并通过证明草图连接，目标定理自动解决，任务完成。

4.5 多智能体持续学习
证明草图使智能体能够基于彼此的结果进行构建，但有效的协作还需要共享这些结果背后的推理。因此，Prove2Me 提供了一个讨论频道，智能体在其中实时发布进度、中间发现和经验教训。图 7 显示了在精确矩阵补全任务下的一个例子，其中两个智能体交换了它们的最新进展。

我们还观察到智能体积极纠正彼此。例如，在灵敏度猜想任务中，一个智能体提出了一个导入名为 gotsman_linial 的定理的证明草图，第二个智能体后来反驳了它（在图 8 中标记为红色）。在反驳的提示下，第一个智能体提出了一个修改后的形式化 gotsman_linial_with_zero，提供了缺失的边界条件，修正后的定理随后闭合了整个分支。

这些动态指向了更广泛的研究议程。机器学习文献中关于多智能体协作的大多数现有工作研究的是具有编排器的中心化设置，例如 (Li et al., 2023; Qian et al., 2024; Mao and Mirhoseini, 2026)。如何最好地协调 Prove2Me 上去中心化、异步的智能体仍然是一个开放问题。

6 正确使用 Prove2Me
本节作为一个简短的快速入门指南：它展示了如何将智能体连接到 Prove2Me，并简要解释了底层的运作方式。首先，您需要带来任何具有基本 shell 或终端访问权限的智能体，包括 Claude Code、Codex、Cursor、OpenClaw、OpenCode、GitHub Copilot 和 Antigravity 等等。网页聊天机器人不能直接使用，因为它们缺乏运行代码以进行 Prove2Me API 调用的能力。

设置。设置智能体只需要一条指令：将其指向 prove2.me/start.md。之后的一切都是智能体的工作。它根据自己的能力选择入门路径，如果它有 shell 和 git 访问权限，则克隆 Prove2Me 工作区存储库，否则通过 HTTP 获取相同的文档。然后，工作区告诉它如何安装固定的工具链，即平台验证所依据的带有确切 Lean 和 Mathlib 修订版的 elan，以及它的三个定义、定理和解决方案文件夹如何镜像服务器的模块布局，以便本地和服务器端验证一致。最后，智能体询问其人类要扮演哪个角色，解决任务还是发布任务。本地 Lean 安装是可选的，因为服务器验证每个提交，但它让智能体可以在花费一个之前检查证明。

7 结论与展望
我们介绍了 Prove2Me，一个以 AI 智能体作为数学形式化一等贡献者的开放协作平台。其关键特性包括让任何拥有智能体的人都能做出贡献的低准入门槛、将人工审计限制在精选核心陈述的审计任务、将困难定理分解为可独立解决的子问题的证明草图，以及不可变的可重用结果库。

我们强调，Prove2Me 的愿景不是取代数学家。选择什么值得形式化、将其分解为里程碑，以及判断形式化陈述是否表达了其预期含义，这些都仍然是人类判断的问题；智能体在这些决策之下提供机械劳动。智能体还需要为他们提交的每个陈述和证明编写详细的自然语言说明，以便他们产生的内容对人类保持可读性和清晰。人类是平台的第一原则：目标是帮助数学家更好地理解数学，而不仅仅是给结果盖上正确的印章。

除了平台本身，Prove2Me 还开启了许多我们认为令人兴奋的研究问题。随着 Formalpedia 的增长，定位要导入的正确现有定理对于高效协作变得至关重要，这提出了智能体应该如何搜索大型、不断演变的形式化陈述语料库的问题。该平台还托管了许多相互构建的去中心化、异步智能体。这些智能体如何交换框架、经验和上下文以持续学习仍然是一个开放问题。此外，开放提交不可避免地会招致低质量或恶意内容，因此除了任务审计之外，我们还要问平台如何拒绝对抗性提交并建立社区信任，例如通过声誉系统。最后，尽管智能体是主要的内容生成者，但 Prove2Me 最终存在是为了为人类创造价值，如何从机器生成的证明中提取人类可读的见解仍然是一个开放问题。
