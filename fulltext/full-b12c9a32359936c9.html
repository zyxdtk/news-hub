摘要：LLM智能体几乎所有时间都在等待模型。在Amazon Bedrock AgentCore上，我们的智能体每次等待模型回复的中位时间为2.7秒，随后进行估计5至40毫秒的计算。AgentCore在等待期间不对CPU收费。但它为每个对话保留一个独立的环境——一个拥有自己内存的虚拟机——并保持保留状态直到对话关闭。因此，1,000个对话保留1,000个环境来完成2至15个处理器核心的工作量。服务在处理能力耗尽之前很久就会耗尽环境。

这种短缺有两个原因，各有解决办法。环境在对话结束后仍保持保留：在我们运行的客服基准测试中，对话平均持续33秒，但其环境会被多持有15分钟，除非客户端将其关闭。而一个环境只服务一个对话，而对话大部分时间在等待：在我们的模拟中，64个对话共享一个环境所需的环境数量减少59倍，且每100个回复中有99个最多延迟40毫秒。

毫秒数是估计值，因为它们难以测量：存根化的模型、模型调用周围的计时器，以及背靠背运行的步骤，各自都给出了貌似合理但过低的数字。我们展示了如何避免这三种错误。在这两个修复方案中，关闭会话只需要客户端。共享环境则需要平台，而在我们调查的智能体运行时中，只有一个部分允许这样做。这些运行时将对话彼此隔离，因为智能体会运行由模型选择的工具，有时甚至是代码。开放问题在于如何在不为每个等待中的会话保留环境的情况下保持这种隔离。

  1. 引言

无服务器平台只在代码运行时收费。LLM智能体与该模式契合不佳。智能体会话几乎全部时间都在等待模型，但它在等待期间持有执行环境。会话按步骤进行，每一步是一次模型调用加上围绕它的框架工作。在我们的部署中，一步在模型上等待的中位时间为2.7秒，计算时间估计为5至40毫秒。

在过去两年中专门为智能体构建的平台之一，Amazon Bedrock AgentCore Runtime，在会话等待I/O时停止对CPU计费（Amazon Web Services, 2026a）。这解决了等待的成本问题，而这本来就是小头：按公布的价格，我们计算出计算费用只占模型token账单的百分之几（第5节）。然而，它并不改变等待中的会话所持有的东西。智能体运行时为每个会话在其整个生命周期内提供专用的、隔离的环境（Amazon Web Services, 2026n；Microsoft, 2026b），并且无论忙碌还是空闲都将其计入会话配额（Amazon Web Services, 2026i）。因此，在这些运行时上，限制智能体工作负载的不是它为处理器时间支付的费用，而是它持有多少隔离环境以及持有多长时间。

本文表征了无服务器和智能体运行时上的智能体步骤，并测量了该容量。它做出四项贡献。

智能体运行时的表征（第4、5和6节）。首先，我们观察了部署在AgentCore上和自托管的LangGraph和Strands智能体服务公共基准的3,549个步骤。其次，我们在AgentCore和AWS Lambda内部、在平台自己的处理器上运行了我们自己的CPU基准测试。在已部署智能体步骤所花费的时间中，只有0.2%至1.5%是计算；其余是等待模型。为每个会话提供自己环境的平台在整个等待期间持有该环境。那么在任何时刻，每1,000个持有的环境中只有2至15个在使用处理器，因此平台每完成一个核心的工作大约持有70至600个环境。最多400个并发会话的直接测量验证了这一计算。对九个平台公开文档的调查（第6节）显示了该比例适用的范围：AWS和Microsoft的智能体运行时为每个会话专用一个环境，Google的只在智能体代码为异步时才共享环境，而每个默认共享环境的运行时都是通用运行时（Amazon Web Services, 2026n；Microsoft, 2026b；Google Cloud, 2026a；Google Cloud, 2026b；Amazon Web Services, 2026j）。

隔离的代价，以及最便宜的修复（第7节）。在由已部署工作负载驱动的模拟中，每个环境共享64个会话比隔离每个会话少持有59倍的环境，在第99百分位每步最多增加40毫秒延迟，相比之下模型调用为2.7秒。该修复需要平台改变；下一个修复只需要客户端。留给默认15分钟空闲超时的会话，而不是在对话结束时关闭，会在整个超时期间保持其环境，相同流量随后比及时关闭会话时多持有28倍的环境。该倍数就是未关闭会话被持有的时间除以关闭会话被持有的时间，对于我们33秒的对话即为933/33=28，但它是客户端可控的最大因素。

一种测量方法，以及三种出错方式（第3节）。为了在不支付数千次模型调用费用的情况下测量框架每步的CPU，并使每次运行重放相同的对话而没有围绕每毫秒计算的网络等待秒数，必须用假的东西替换模型。如何替换决定了测量的是什么。三种错误各自给出貌似合理但错误的数字。（1）用存根替换模型对象跳过了序列化不断增长的对话的工作，因此框架CPU随对话增长看起来是平的；只伪造网络套接字则保留了该工作。（2）在已部署的智能体中对"模型调用"计时会将客户端自己的序列化和解析计为模型时间；根据我们的估计，这在我们的部署数据中隐藏了框架的大部分CPU。（3）背靠背地对步骤进行基准测试低估了CPU：在我们的台式机上，在部署长度的等待之后运行的步骤成本为1.9至4.7倍。使用套接字模拟测量，两个框架和我们测量的每种处理器上，每步框架CPU与对话大小呈线性关系，尽管其常数变化超过五倍。

平台构建者的开放问题（第8节）。主要问题是如何保持每个会话的隔离——正如今天的智能体运行时通过给每个会话自己的环境所做的那样——而不在会话等待模型时让该环境处于保留状态。今天的平台提供其中之一，至少在我们调查的九个平台中是如此：智能体运行时将每个会话隔离在自己的环境中，而共享环境的运行时按租户而不是按会话隔离。隔离区和每工具沙箱指向中间地带（第8节）。

两个范围声明构成了以下所有内容的框架。首先，我们报告的倍数计算的是客户持有和支付的东西：环境、配额槽和计费内存。它们不是提供商的成本。提供商可以将许多空闲的微虚拟机打包到一台机器上，因此一千个持有的环境对它的成本远低于一千台机器的价值；具体多少，我们无法从外部看到。我们的主张是关于客户方面的。其次，我们不认为每会话隔离是一个错误。智能体运行由模型代表用户选择的工具，有时是代码，隔离每个会话有真正的价值。我们测量其价格。

  1. 背景

术语。 LLM智能体运行一个循环。每次循环是一次步骤：智能体用到目前为止的对话调用模型，模型要么回答，要么请求一个或多个工具调用，这些调用被执行并附加到对话中。一轮是从用户消息到智能体回复的循环的一次运行；通常需要几个步骤。会话是共享一个对话状态的轮次序列。步骤的挂钟时间分为在远程服务（模型或工具）上阻塞的时间和在运行循环的框架中计算的时间。本文测量每步的两者，并询问当前者占主导时托管平台保留了什么。

功能平台假设什么。 功能即服务是为跨租户多路复用的、短的、主要是CPU绑定的请求处理而设计的。由此产生了几个设计决策，每个对该工作负载都是合理的（Hellerstein et al., 2019；Jonas et al., 2019）。一个请求占用一个执行环境，这使得隔离简单且资源使用易于归因（Amazon Web Services, 2026m）。计费按环境生命周期的毫秒计算，假设持有的环境正在被使用（Amazon Web Services, 2026c）。容量通过计算并发环境来限制。三者都将调用视为工作单元。对于智能体步骤，调用主要是等待单元。

智能体运行时改变了什么。 由主要云提供商在过去两年引入的托管智能体运行时以两种方式使该模型适应智能体。首先，预留单元变为会话：客户端选择的会话标识符将对话的每个请求固定到相同的环境，该环境保持到客户端关闭它、空闲超时通过或达到最大生命周期（Amazon Web Services, 2026n；Microsoft, 2026b）。其次，计费区分活动时间和阻塞时间：例如，AgentCore在会话等待I/O时停止对CPU收费（Amazon Web Services, 2026a）。第6节检查这些改变做了什么和没有改变什么。第一个将预留从一个请求延长到整个对话。第二个消除了等待的大部分账单，但没有消除预留本身。

先前工作与差距。 无服务器平台为阻塞在I/O上的函数预留容量已是确立的结论（Stojkovic et al., 2023；Liu et al., 2025）。尚未测量的是在为此构建的平台上的智能体案例：智能体步骤有多少是等待，每会话运行时在该等待期间持有什么，以及客户能做什么（第10节回顾相关工作）。

3.1. 每步框架CPU：伪造网络，而不是模型

测量框架在模型调用周围做什么需要在没有真实模型的情况下运行智能体，原因有三。成本：每个40步的运行进行41次模型调用，而我们在机器和平台上进行超过2,500次运行。可重复性：真实模型的回复因运行而异，因此没有两次运行会携带相同的对话，我们回归所用的请求大小会不同。隔离：使用真实模型时，每毫秒的框架工作位于秒的网络等待之间，两者必须分开才能测量前者。

如何移除模型决定了测量的是什么。我们的第一次尝试用返回脚本化工具调用的存根替换框架内的模型对象，随着对话增长，每步CPU看起来是平的：存根恰好跳过了增长的工作——将历史转换为提供商的线格式、序列化和编码请求，以及将回复解析回消息对象。

因此我们保留模型客户端，以便存根跳过的序列化工作被执行和计数，只伪造其下的层，即网络。两个框架都通过适用于Python的AWS SDK到达Amazon Bedrock，该SDK允许程序在其before-send事件上注册处理程序。SDK在"操作已完全序列化、签名并准备好通过线发送时"调用该处理程序，如果处理程序返回响应，该响应即"满足请求"（Amazon Web Services, 2026d）。我们的处理程序以Bedrock自己的线格式返回脚本化回复（40步的工具调用，然后是最终答案），因此请求构建、签名和响应解析的每个字节都执行，只有套接字不存在。每次扫描之前，测试工具会检查此设计所依赖的一件事，即序列化的请求随对话增长而增长，否则中止。在每次运行中，它从第一步的1.1 KB增长到第四十步的19.6 KB。

两个框架。 我们测量LangGraph（LangChain, Inc., 2026a）（版本0.6.11），它通过LangChain的ChatBedrockConverse客户端调用Bedrock，以及Strands（Amazon Web Services, 2026k）（1.55.0），AWS的智能体SDK，它自带Bedrock客户端。我们选择它们是因为它们在谁拥有智能体循环上采取相反的立场（LangGraph让开发者定义它；Strands运行它），并且因为它们是第3.3节部署研究中的两个框架。为了使它们的测量可比，两个智能体注册相同的三个工具，具有相同的名称、参数模式和返回值，不使用系统提示，并保留整个对话。Strands默认只保留最近消息的滑动窗口，这会阻止请求增长；我们用保留所有内容的管理器替换它。每次运行驱动智能体通过40步，每步一次模型调用和一次工具调用。四十步将请求带到19.6 KB（LangGraph为19,617字节，Strands为19,627字节，在每台机器和平台上），是已部署智能体发送大小的低端（第3.3节）。有效载荷如此接近，CPU差异就是代码差异。

两个时钟。 CPU时间是操作系统在线程或进程于处理器上运行时向其收取的时间；阻塞所花费的时间不计费。我们通过Python的time.thread_time和time.process_time读取它，它们返回当前线程或进程的"系统和用户CPU时间之和"，并且"不包括睡眠期间经过的时间"（Python Software Foundation, 0000）。读取哪个时钟取决于框架将其工作放在哪里。

LangGraph在调用线程上运行模型路径，但通过工作线程池调度工具，因此我们读取每线程CPU并显式添加工作线程的CPU。Strands在工作线程上运行SDK调用并在其事件循环线程上处理回复，将一次模型调用拆分到两个线程（其Bedrock模型类将SDK调用交给工作线程并将每个回复事件发布回循环（Amazon Web Services, 2026l）），因此每线程CPU会错过其中一部分；我们改为在Strands自己的模型调用前后钩子之间的间隔内读取进程范围的CPU。其循环严格顺序，因此该间隔内没有其他东西运行。所有运行都是同步的，因为在Python的asyncio下，挂起的协程会将其线程交给另一个协程，每线程归因不再有意义。

扫描设计。 扫描是在一台机器或平台配置上的120次运行，每次40步，共4,800步。重复的运行平均掉调度器和分配器噪声，跨运行的每步中位数是第4节拟合所用的。对于LangGraph，120次运行被分割为三组各40次，跨其检查点器的三种配置——检查点器是在每步之后持久化图状态以便稍后可以恢复运行的组件：无、内存中和SQLite。三者形成一个每次添加一个成本的阶梯，将框架自身的成本与持久化状态的成本分开。Strands没有这样的检查点器；其对应物是可选的会话管理器，在添加每条消息时保存它（Amazon Web Services, 0000），没有它的智能体（默认）不持久化任何东西。我们只在默认情况下测量了Strands，这匹配LangGraph的无配置，因此其所有120次运行都在一个配置中。

机器和平台。 在一台机器上测量的常数对另一台机器说明很少，因此我们在几台机器上测量，并且在本文所涉及的平台内部。LangGraph在Apple M5笔记本电脑（CPython 3.9.6）上运行，两个框架在Intel Core i5-8500T台式机（CPython 3.14.4）上运行。然后我们在Amazon Bedrock AgentCore Runtime内部运行相同的传输模拟扫描，作为代码包部署（Amazon Web Services, 2026f）到运行时为每个会话提供的微虚拟机中（Amazon Web Services, 2026n），以及在AWS Lambda内部的两种处理器架构arm64和x86-64上。Lambda按内存比例分配CPU，在1,769 MB时有一个完整vCPU（Amazon Web Services, 2026e），因此在Lambda上我们还扫描了内存（512、1,024、1,769和3,008 MB），以查看较小的函数是改变步骤使用的CPU还是只改变所需时间。在两个平台上，我们为四组各30个重复强制一个新环境，以便结果跨越多个主机，并且我们记录了每个主机的处理器；平台将我们放在几个主机上。库版本在任何地方都相同地固定。解释器不是（平台上是CPython 3.12），因此机器之间常数的差异包括解释器的差异。套接字在那里也被伪造，因此云运行花费几美元且没有token。

3.2. 阻塞时间：校准延迟

第3.1节的传输模拟在移除网络的情况下测量CPU，因此它移除的等待必须单独测量。我们于2026年9月3日记录了50次对Amazon Bedrock的模型调用（Anthropic的Claude Haiku 4.5，通过Bedrock的Converse API，在us-east-1区域），来自距离端点约200毫秒往返的客户端。模型延迟由生成的token数而不是消耗的token数决定（Kwon et al., 2023；Zhong et al., 2024），因此我们对每次调用的max_tokens在48到1,536之间进行对数均匀抽取，这给短回复和长回复相同的权重，并记录每个延迟对应的实际输出长度。我们还记录了30次对两个公共HTTP端点的调用作为替代工具；此处工具调用唯一重要的属性是它阻塞。对每个端点的一次预热调用被丢弃，以排除连接和TLS设置。中位数为每次模型调用4.23秒和每次工具调用0.97秒。这些等待定义了第5节中的实验室场景；第4节显示已部署智能体的等待更短。

3.3. 部署锚点，以及它看不到的

上述仪器分别测量c和w：c在笔记本电脑、台式机和AgentCore与Lambda内部测量，总是伪造模型；w在真实调用上测量，周围没有智能体。第5节通过计算组合它们。为了检查该计算，我们使用2026年9月为单独研究收集的数据集：相同的两个框架服务τ²-bench（Barres et al., 2025），一个公共基准，其中模拟用户和智能体通过工具完成零售客服任务，针对Claude Sonnet 4.5，以三种方式部署。LangGraph在自托管容器和AgentCore Runtime中运行；Strands在AgentCore Runtime上运行。数据集包含384个会话，7到19步。我们使用其3,549个热步骤，即由已在运行的进程服务的步骤，因为冷步骤的服务器时间包括进程启动，与此处测量的每步成本是不同的量。

每个已部署的步骤记录服务器时间、模型时间及其差异，该研究称之为开销。此拆分的一个属性很重要。模型时间是围绕模型客户端调用测量的：围绕LangGraph的litellm.completion，其部署的智能体通过LiteLLM（BerriAI, 2026）到达Bedrock，这是一个在模型API之间转换的库，以及Strands的模型调用钩子之间。该间隔包含客户端自己的请求序列化和响应解析，这正是第3.1节测量为框架CPU的工作。已部署的开销因此只覆盖模型客户端之外的框架和服务器工作。它省略了客户端序列化，并且它是挂钟时间而不是CPU。它在两个方向上都不约束已部署的CPU。

因此我们对已部署的每步CPU进行区间估计而不是声称测量它。低端是客户端之外测量的开销。高端加上同一框架的传输模拟拟合在同一平台上测量的、在已部署请求大小下预测的客户端序列化：已部署请求携带中位数6.9k输入token，按假设每token 3到5字节计算为20到34 KB。第4节报告该区间。教训是对"模型调用"计时悄悄隐藏了客户端自己的工作。

  1. 步骤的成本

第3节构建了仪器；本节报告它们读取的内容：等待w、每台机器和平台上的框架CPU c、检查点器的额外CPU，以及由于已部署的每步CPU无法直接测量，第5节所依赖的低和高估计。

4.1. 等待跟踪答案的长度，而不是对话的

智能体等待模型多长时间取决于模型答案多长，而不是对话增长多长。在每一步，智能体将到目前为止的整个对话作为输入发送，在我们的部署中为5k到10k token，并返回一个短输出，即答案：中位数99到113 token。模型调用等待的中位数LangGraph为2.74秒，Strands为2.59秒，3,549个步骤中的90%等待在1.7到6.5秒之间。

如果等待随输入增长，对话在每一步都会等待更长时间。但事实并非如此。将每步等待对两个token计数回归，分别针对三个已部署配置（第3.3节），每个额外的输出token增加19.3到19.5毫秒，而额外输入不增加任何东西（每千token -15到-51毫秒）。模型服务器解释了原因：它们在一个并行传递中读取整个输入（预填充），然后一次一个token地写出答案（解码），因此慢的部分及其等待随答案扩展（Kwon et al., 2023；Zhong et al., 2024）。我们的部署在其覆盖的5k到10k输入上与此一致。

我们的校准调用（第3.2节）等待更长时间，中位数4.23秒，尽管它们的答案大约一样长（中位数137 token）。相同的回归将差距置于每次调用的固定延迟：约3.5秒，而部署中为0.9到1.2秒。两组在模型（Haiku 4.5对Sonnet 4.5）、客户端位置和日期上不同，50次调用无法区分这些原因。因此我们在需要现实值的地方使用已部署的等待，并将校准的保留为实验室场景。

4.3. 检查点将相同的历史序列化第二次

检查点器（第3.1节）在每步之后保存图的状态。LangGraph将状态保存在命名通道中，其中之一是消息历史，并且它已经增量保存：保存器被交给新检查点以及"截至此写入的新通道版本"，内存中保存器存储恰好这些通道的序列化副本（LangChain, Inc., 2026b）。然而，在智能体循环中，每步都改变的通道是消息历史，一个保存在单个通道中的仅追加日志。它每步都有新版本，因此每步再次序列化其全部内容，该步骤将相同的增长对象序列化两次：一次进入模型请求，一次进入检查点。内存中检查点器的每步CPU（跨运行中位数）在M5上从第一步的低于0.1毫秒增长到第四十步的0.56毫秒，在台式机上从0.2到0.99毫秒。SQLite检查点器显示每步中位数为零，峰值高达1.8毫秒，这是批量写入的模式；我们没有测量刷新的工作在哪里计费，因此不报告其总数。在无服务器主机上，进程在调用之间不存活，因此生产智能体检查点到远程存储，每次写入增加网络往返：阻塞时间，即本文所涉及的量。我们的检查点数字因此是下界。

4.4. 已部署的每步CPU，区间估计

如第3.3节所解释的，已部署的数据不能直接给出每步CPU。已部署的智能体在模型客户端之外每步花费中位数4.48毫秒（AgentCore上的LangGraph）和4.49毫秒。对于LangGraph，该开销也随对话增长，大约每千输入token 0.25毫秒（R²=0.99，按千token分箱的中位数）。对于Strands则不然，因为Strands在模型调用窗口内执行其序列化，而已部署的开销排除了该窗口。

因此我们进行区间估计。低端是测量的开销，4.5毫秒。高端加上AgentCore拟合在已部署请求大小20到34 KB下预测的客户端序列化。对于LangGraph，那是表2的AgentCore行；对于Strands，它是通过两代处理器上的运行合在一起的一个拟合（1.73毫秒 + 0.41毫秒/KB）。这给出LangGraph为4.5到13.2毫秒，Strands为4.5到20.3毫秒。高端夸大了背靠背运行步骤的CPU，原因有二：开销是挂钟时间，至少是其中的CPU，而对于LangGraph，开销已经包含的消息转换被拟合再次计算。相对于2.6到2.7秒的中位数等待，计算占已部署步骤时间的0.16%（4.5/2,740）到0.8%（20.3/2,590）之间。第5节从这个区间开始，然后通过直接测量发现，在部署长度的等待之后的步骤比背靠背花费更多CPU，这将上端提高到约1.5%。

  1. 容量，而不是成本

重要的量。 第4节给出了步骤的两个持续时间，等待w和CPU c；本节将它们转化为容量。考虑一个为每个进行中的会话专用一个环境的平台。然后每个环境在处理器上的时间分数为c/(w+c)，因此根据Little定律（Little, 1961），N个持有的环境平均保持N·c/(w+c)个处理器核心忙碌。等价地，平台每执行一个核心的工作持有/w个环境。该比率是工作负载的属性：它不依赖于配额或到达率。

图2显示了为什么它对智能体如此之大。一个已部署的会话，按比例绘制，持有其环境28秒，并且最多计算其中的0.7%。

直接测量还显示每步CPU比相同测试工具中背靠背运行的相同智能体更多：LangGraph步骤为13到17毫秒而不是6.8毫秒（1.9到2.5倍），Strands步骤为16到31毫秒而不是6.4毫秒（2.4到4.7倍，随着会话添加而下降）。并发不是原因：一个会话单独在其进程中，具有相同的等待，每步花费14.8毫秒和27毫秒。垃圾收集也不是：禁用收集器后，LangGraph仍然花费16.5毫秒。剩下的是等待本身：在我们的台式机上，在几秒空闲之后运行的步骤花费背靠背运行的相同步骤CPU的1.9到4.7倍。我们没有分离原因。可能的原因是降低了时钟频率的处理器和变冷的缓存，这是每个被唤醒的线程都要付出的代价；Strands的模型调用跨越两个线程（第3.1节），这可以解释其更大的惩罚。第4节的已部署开销是在原地测量的，已经包括此效应。拟合预测的序列化不包括，这就是为什么高估计将该部分乘以2.2，即LangGraph的因子。我们也将其用于Strands。Strands自己的因子更大（27/6.4≈4.2），会将其高估计推得更高，但没有必要：直接测量下，Strands步骤最多花费31毫秒，已经低于38.9毫秒的高估计。

这些数字计算什么。 它们计算客户持有和据此规划的东西：环境、配额和计费内存。它们不计算提供商花费的东西：提供商可以超额订阅空闲的微虚拟机（Agache et al., 2020），因此空闲会话对它的成本更低，降低多少我们无法观察。

为什么计算成本是错误的视角。 智能体步骤产生两张账单：一张用于模型的token，一张用于托管智能体的计算，包括等待。按公布的价格，我们计算出在计费挂钟时间的地方（Amazon Web Services, 2026c），计算账单是token账单的百分之几，在等待CPU不计费的地方更少。因此成本是对无服务器智能体的弱论证。不对等待CPU计费，如AgentCore所做的，进一步降低该账单，但不减少持有的环境。更高的会话配额也不行，它移动限制而不改变比率；配额也是账户范围的，与所有其他工作负载共享。

比率随上下文增长而缩小。 模型等待不随上下文增长（第4节），但框架CPU增长，因此更长的对话每个忙碌核心持有更少的环境。外推AgentCore测量的CPU拟合，50k token的上下文将每个忙碌核心持有大约26到47个环境，250k token的上下文大约6到11个，较低的数字包括步骤在等待后花费的额外CPU。这些是远在我们观察到的5k到10k token之外的外推，并且它们将等待保持在其短上下文中位数，而250k token的预填充会延长它。方向是有用的发现：持有和使用之间的不匹配对短对话最大。

暂停消除了空闲时间的成本，而不是其容量。 Lambda MicroVMs为每个会话提供自己的微虚拟机，可以在空闲时暂停。暂停的MicroVM只支付快照存储，但它仍然计入内存配额，该配额覆盖"处于RUNNING或SUSPENDED状态"的MicroVM（Amazon Web Services, 2026h）。暂停也只在配置的无流量时间段之后发生，从不在请求中间，因此它不能回收步骤等待模型所花费的时间。持久函数是Lambda用于长时间运行工作流的特性，确实在等待期间释放其并发槽（Amazon Web Services, 2026b）。然而，它们所指的等待是计时器和回调；根据我们对文档的阅读，在步骤内进行的模型调用在其持续时间内持有该槽。

共享已经提供，在智能体运行时之外。 让一个环境服务多个进行中的请求消除了每会话保留。通常限制共享的是CPU争用，而等待超过98%时间的工作负载（如我们的，第5节）产生的争用很少。这一观察并不新鲜。MXFaaS（Stojkovic et al., 2023）和后来的工作（Liu et al., 2025）提出了一般观点，Cloud Run已经交付多年（Google Cloud, 2026b），并且在2025年和2026年AWS在Lambda中通过托管实例和web函数交付了它（Amazon Web Services, 2026g；Amazon Web Services, 2026j）。表5中的模式是：每个在请求之间共享环境的被调查运行时都是通用运行时，而智能体运行时按会话隔离。Vertex AI Agent Engine是部分例外：一个实例接受多个并发请求，默认九个，但只有当智能体的代码为异步时（Google Cloud, 2026a）。

每会话隔离是一个选择，它有原因。 智能体执行由模型选择的工具，有时是代码，代表一个用户。每个会话一个专用微虚拟机限制了该会话所做的任何事情。第7节询问该选择在固定流量水平下的成本，以及共享将恢复什么。

  1. 评估补救措施

第6节发现智能体运行时每个会话持有一个环境。本节将该选择量化：1,000个并发会话在隔离下持有多少环境，以及如果会话共享它们将持有多少。这里的每个结果都是模拟的，来自测量的输入。

工作负载。 我们不是运行数千个智能体，而是模拟它们，将第3.3节的已部署会话重放为事件序列：会话到达、步骤等待模型、步骤计算、会话结束（离散事件模拟）。每个模拟会话从384个已部署会话之一获取其步骤数（中位数9，范围7到19），每个步骤的等待从1,094个已部署的LangGraph模型调用之一获取（中位数2.74秒）。每步CPU在一次运行中固定为四个值之一：第4节的低和高估计，4.5和20.3毫秒；它们之间LangGraph的中点，11.7毫秒；以及第5节的最高估计，38.9毫秒。新会话随机到达，彼此独立（泊松过程），大约每秒30个；由于会话平均持续33秒，这保持大约1,000个在任何时刻进行中（30×33）。每次运行覆盖40分钟并丢弃前20分钟，以便留给15分钟空闲超时的会话有时间在我们计数之前积累。作为检查，模拟的环境计数与Little定律（Little, 1961）一致到1%以内。

策略。 在隔离下，每个会话从其第一步到结束持有自己的环境，拥有一个vCPU。我们建模两种结束方式。要么客户端在对话结束时关闭会话，要么它不关闭，平台在其空闲超时后回收环境，AgentCore上默认15分钟（Amazon Web Services, 2026n）。在多路复用下，一个2 vCPU的环境托管最多k个会话。新会话进入第一个有空闲槽的环境，只有当没有环境有空闲槽时才启动新环境。当需要CPU的步骤多于环境拥有的vCPU时，它们按到达顺序排队，因此共享的成本表现为添加到步骤的延迟。

图3. 在每种托管选择下服务1,000个并发智能体会话所需的环境，用已部署工作负载模拟。橙色：每个会话一个环境，要么在对话结束时关闭，要么留给平台的15分钟空闲超时。蓝色：会话共享2 vCPU的环境。每个条形旁边是共享在四个CPU值下最慢1%步骤中添加到步骤的额外延迟。

隔离每个会话持有一个环境；共享需要几个。 图3显示了结果。会话及时关闭时，隔离平均持有1,008个环境，每个进行中的会话一个。每个环境多路复用64个会话持有17个，少59倍（1,008/17）；每个环境256个时持有5个。这些计数在每个CPU水平上都相同，下面有一个例外。内存取决于我们只能假设的占用：每个环境0.5 GB加上每个会话10 MB，它在k=64时从514 GB下降到18.5 GB。

共享在k=64之前增加很少延迟。 每个条形旁边的延迟是共享在最慢1%步骤（第99百分位，p99）中添加到步骤的。在k=64时，在每步20.3毫秒CPU时为13毫秒，在38.9毫秒时为40毫秒，最多是2.74秒中位数模型等待的1.5%，vCPU最多35%忙碌。在k=256时，在20.3毫秒CPU时为79毫秒，vCPU 63%忙碌；在38.9毫秒时，会话请求的CPU多于两个vCPU拥有的，步骤排队数秒，需要第六个环境。在k=64之前，环境远未饱和：如第5节所发现的，几乎没有计算可共享。

未关闭的会话持有28倍的环境。 图3的顶部条形将会话留给空闲超时。然后每个会话持有其环境933秒而不是33秒，因此相同流量持有28,432个环境，28倍（933/33）。修复是客户端的一次调用。相对于AgentCore的最大默认配额5,000个会话，这是每秒约150个新对话（5,000/33）和约5个（5,000/933）之间的差异。AgentCore较新的运行时降低了空闲会话在120秒后计费的内存，但会话及其在配额中的位置保持持有直到超时（Amazon Web Services, 2026a；Amazon Web Services, 2026i）。

模拟没有显示什么。 它为隔离定价；它不认为隔离是不必要的。共享进程的会话共享其内存及其故障，运行由模型选择的工具或代码的智能体可能需要比这更多的限制。模拟在步骤之间也没有思考时间，如在自主智能体中；有人在轮次之间暂停，会话会更长，空闲超时是它们的较小倍数。它给每个隔离的会话一个完整的vCPU，因此它对隔离是慷慨的。并且它计算客户持有的东西，环境和配额槽，而不是提供商的物理成本（第5节）。

  1. 教训和开放问题

8.1. 对于部署智能体的团队

显式关闭会话。 在每会话运行时上，没有其客户端关闭会话而结束的对话保持其环境直到空闲超时。对于我们33秒的对话对15分钟默认超时，倍数是28（933/33；第7节）。这是团队可以在不改变平台的情况下移除的一个因素。

按配额而不是CPU进行容量规划。 在我们的部署中，1,000个并发会话根据我们的计算只保持1.6到15个核心忙碌，但持有1,000个环境和1,000个配额槽（第5节）。监视CPU利用率的规划因此将显示大量余量，而会话配额已经用完。改为预测并发会话：到达率乘以每个会话被持有的时间，包括它在被关闭或超时之前空闲的任何时间。

有意选择隔离。 在智能体的工具和代码不需要每会话沙箱的地方，多路复用运行时在我们的模拟中为相同流量持有少59倍的环境，延迟成本在第99百分位每步最多40毫秒（第7节）。在需要的地方，隔离的价格是已知量并且可以预算。

用伪造的套接字而不是模型进行基准测试。 用存根替换模型对象恰好移除了随对话增长的框架工作（第3.1节）。并且在已部署的智能体中对模型调用计时时，提前决定客户端自己的序列化是计为模型时间还是框架时间。在我们的已部署数据中，它被计为模型时间，根据我们的估计，这隐藏了框架每步CPU的大部分（第3.3节）。最后，用步骤之间的现实等待测量每步CPU：在我们的台式机上，跟随几秒空闲的步骤花费背靠背基准测试的相同步骤CPU的1.9到4.7倍（第5节）。

8.2. 开放问题

表6总结了哪些已确立的无服务器技术适用于智能体工作负载，以及为什么。下面的问题是它留下的空白。

没有每会话环境的隔离。 智能体运行时为每个会话专用一个环境以进行隔离；多路复用运行时共享一个以获得容量。表5中没有平台同时提供两者。候选机制存在：共享主机进程内的每会话沙箱、轻量级隔离区（一个进程内的独立沙箱，如Cloudflare Workers），以及也释放配额槽的快照和暂停。它们中哪一个能在智能体需要的隔离程度和其空闲允许的密度下保持隔离，是开放的。

阻塞工作的调度信号。 自动缩放器观察请求率、队列深度和CPU利用率，所有这些对智能体几乎没有信息量：一千个阻塞会话和一千个计算会话在请求率上看起来相同，并且两者在CPU上看起来都空闲。预测智能体工作负载持有资源的是在远程调用上阻塞的进行中会话的数量。被调查的平台都没有记录使该数量对其调度器或其租户可用。

正确单位的配额。 会话配额计算环境。智能体会话的真实需求是随时间持有的内存，几乎没有CPU。内存-时间配额，即会话持有的内存乘以其持有时间，将按每个会话实际保留的东西收费，而不是将每个会话计为一个完整的环境。

只保存改变的内容。 LangGraph在每步之后保存智能体的状态，但它将整个消息历史视为单个项目，因此每次保存再次写出整个对话，尽管只有最新消息是新的（第4节）。如果历史保持为每个步骤只追加其新消息的日志，则无论对话增长多长，每次保存都将保持小。共享日志无服务器系统已经提供了这样的日志（Jia and Witchel, 2021）。智能体框架是否可以在不改变智能体编写方式的情况下以这种方式保存状态是开放的。

  1. 有效性威胁

构造。 已部署的每步CPU是区间估计而不是测量（第3.3节）；其上端可能重复计算其两个仪器都包括的工作。

内部。 传输模拟移除网络但保留所有其他操作，我们通过要求请求随对话增长来验证。它不重现脚本化之外的响应大小，因此响应解析成本是短回复的成本。在AgentCore上，健康检查ping大约每两秒到达一次，落入Strands的进程时间窗口；每个花费微秒。

外部。 我们部署了一个工作负载τ²-bench零售，其工具由基准而不是智能体执行，因此已部署步骤不包含工具等待；运行自己工具的智能体更阻塞，而不是更少。我们使用了一个提供商的一个模型家族和固定版本的两个框架，并且只测量了最多10k token的上下文。CPU常数在我们测量的六种处理器类型上变化超过五倍，并且在一个平台内也是如此（第4节）；只有线性形式被声称可迁移。步骤在空闲等待后花费的额外CPU是在一台台式机上为两个框架测量的；我们没有分离其原因，也没有在云平台上测量它，云平台的处理器由管理程序管理。

隶属关系。 作者为Amazon Web Services工作，其平台是被测量的平台之一。所有平台事实来自截至2026年10月27日的公开文档，并且会改变。所有测量都在个人账户上以公开价格运行。

  1. 相关工作

无服务器和阻塞工作。 无服务器平台为阻塞在I/O上的函数预留容量已是确立的结论。MXFaaS观察到函数执行"大部分时间阻塞在同步等待操作上"（Stojkovic et al., 2023），并发感知编排检查并发请求应如何共享容器（Liu et al., 2025）。Hellerstein等人（Hellerstein et al., 2019）和Berkeley观点（Jonas et al., 2019）编目了无服务器在哪些方面不适合数据密集型工作；我们将这些视为给定。我们的贡献是测量智能体案例，在为其构建的平台上。

无服务器和LLM。 Samanta和Nguyen研究无服务器LLM推理服务（Samanta and Nguyen, 2025）；我们研究智能体编排，其中单元是多步骤会话，阻塞时间花在等待推理而不是执行推理。

冷启动和隔离。 快照-恢复（Du et al., 2020；Cadden et al., 2020；Ao et al., 2022）、轻量级隔离（Agache et al., 2020；Oakes et al., 2018；Shillaker and Pietzuch, 2020）以及冷启动工作的调查（Golec et al., 2025）解决了启动成本和密度。它们与第8节的开放问题——在不给每个会话自己的环境的情况下隔离会话——相关，而不是等待本身。

有状态无服务器。 Cloudburst（Sreekanti et al., 2020）、Boki（Jia and Witchel, 2021）和Beldi（Zhang et al., 2020）为函数提供持久状态和恰好一次语义；诸如Unum（Liu et al., 2023）之类的工作流系统将长时间运行的控制流外置。没有一个被应用于智能体状态，其访问模式——仅追加对话——比当前检查点器假设的键值模型更自然地适合共享日志。

  1. 结论

AgentCore是一个托管智能体运行时，在会话等待时不计费CPU。每个会话仍然在其整个生命周期内持有隔离环境、其内存和配额槽。在我们的部署中，会话在该生命周期的0.2%到1.5%之间进行计算，因此平台每执行一个核心的工作持有数十到数百个环境。这是隔离每个会话的价格。本文测量了它，其模拟表明共享环境将以毫秒级的成本恢复其大部分。共享需要平台改变。在对话结束时关闭每个会话，而不是留给平台的空闲超时，只需要客户端。

测量框架每步CPU——该价格所依赖的小数字——需要小心：存根化的模型、模型调用周围的计时器或背靠背运行的步骤各自给出了貌似合理但低估它的数字。开放问题是针对平台构建者的：像这些运行时那样隔离每个会话，而不为它等待的时间保留环境。
