原标题：SWE-Together: Evaluating Coding Agents in Interactive User Sessions

中文摘要： SWE-Together 是一个从真实用户—智能体编码会话中重构的多轮交互式基准测试，包含 109 个仓库级任务。它通过锚定的 LLM 用户模拟器重放原始用户意图，仅在触发条件满足时提供反馈。评估框架同时衡量最终仓库正确性（通过冻结的评分标准和智能体评判器）和交互质量（用户纠正次数和意图覆盖）。对七个前沿模型的实验表明，更强的智能体通常实现更高的成功率并需要更少的纠正性干预，用户纠正与性能强烈负相关。模拟器产生的轨迹在图灵测试中无法被人类标注者可靠区分于真实用户。

\contribution [*]项目共同负责人 SWE-Together：在交互式用户会话中评估编码智能体 Yifan Wu Zhuokai Zhao Songlin Li Ho Hin Lee Jiacheng Zhu Shirley Wu Tianhe Yu Serena Li Lizhu Zhang Xiangjun Fan Shengzhi Li Meta （2026年6月29日）

摘要 大多数编码智能体基准测试是静态的：智能体在开始时接收完整的任务描述，仅以其最终代码作为评判依据。真实的编码辅助是交互式的，用户会在多轮对话中澄清目标、增加约束并纠正错误。我们提出了 SWE-Together，一个从真实用户—智能体编码会话中重构的多轮基准测试。为了使真实交互可验证，我们从 11,260 个记录会话中精选了 109 个仓库级任务，选择具有可恢复仓库状态、明确用户目标和可观察结果的会话。为了在不同智能体之间重放这些交互，我们构建了一个基于 LLM 的反应式用户模拟器，该模拟器保留原始用户的意图，并在编码智能体的进展需要时提供反馈。为了将智能体作为协作者进行评估，我们同时测量最终仓库正确性和交互过程中所需的纠正性反馈轮数。对前沿编码智能体的实验表明，更强的智能体通常能实现更高的最终成功率，同时需要更少的干预，这意味着用户体验得到了改善。

1 引言 编码智能体越来越多地被用作软件工程助手，这些智能体的基准测试已成为前沿模型发布中能力衡量的重要指标。著名的例子包括 SWE-Bench 系列和 Terminal-Bench（jimenez2024swebench；openai2024sweverified；scale2025swebenchpro；merrill2026terminal）。更广泛地说，许多广泛使用的编码基准测试遵循静态协议：它们在开始时呈现完整的任务描述，并通过运行可执行测试来评估智能体提交的代码（chen2021evaluating；austin2021program；jimenez2024swebench；zhuo2025bigcodebench；datacurve2026deepswe）。这一协议推动了编码智能体开发的实质性进展。然而，随着主流编码基准测试接近饱和，并且越来越难以区分前沿模型，越来越需要能够更好地反映人类用户在真实工作流中使用编码智能体体验的评估。

基准测试与实践之间的不匹配是双重的：任务设计和评估。 首先，大多数基准测试将任务设定为固定的、单轮的指令。相比之下，真实世界的编码辅助本质上是交互式的：用户通常会在多轮对话中逐步揭示意图、澄清不完整的请求、细化需求并纠正先前的输出（zhong2025codechat；zhang2025decodingcoding）。因此，现有基准测试错过了真实使用的关键条件，即任务相关信息可能分布在多轮对话中，而初始请求可能远不如基准测试任务描述那样完整（laban2025lostmultiturn；garg2025savingswebench）。 其次，评估主要衡量最终任务的成功，但很少捕捉智能体如何有效地整合不断演变的指令以及需要多少用户努力。两个智能体可能获得相同的最终任务分数，但施加非常不同的负担：一个可能从粗略的初始请求中成功，而另一个可能需要详细的规范、反复的提醒和大量的纠正性反馈。因此，评估编码智能体需要超越最终任务正确性，考虑交互质量和成功所需的人类努力。

构建这样的评估面临一个根本性挑战：在保持真实用户交互的同时使任务可验证。真实世界的对话日志捕捉了开发者如何使用编码智能体，但原始会话通常不具备基准测试就绪性：它们可能缺乏可重现的仓库状态、可识别的用户目标或可评估成功的可观察结果。此外，原始对话不能逐字重放给新智能体：后续的用户轮次必须以被评估智能体的轨迹为条件，同时仍锚定于原始用户的意图；否则，交互可能发生漂移，使最终结果不可比较。因此，应对这一挑战既需要可验证的任务构建，又需要受控的交互重放。

为了应对这一挑战，我们提出了 SWE-Together，一个通过从真实用户—智能体对话中重构的多轮会话来评估编码智能体的基准测试。SWE-Together 通过保留具有可恢复仓库提交、明确用户意图和具体结果（如提交的代码更改）的会话，将选定的会话转换为沙箱任务。每个任务包括恢复的仓库、作为第一轮指令的用户初始请求，以及从记录会话中派生的任务特定工件，包括分解的用户意图和每个反馈轮次的触发条件。在评估期间，一个锚定的、状态条件的 LLM 用户模拟器仅当其触发条件在被评估智能体的轨迹中出现时才释放反馈，保留原始用户的目标和干预顺序，同时将反馈时机适应于每个智能体。这种设计有助于将结果差异归因于智能体而非模拟器变化。最终仓库状态使用从仓库检查和原始会话证据中派生的任务特定评分标准进行评分。除了最终正确性之外，SWE-Together 还报告用户纠正，量化模拟用户提供的纠正性引导量，以及意图覆盖，衡量模拟器是否在智能体运行中一致地传达底层用户意图。我们的贡献总结如下：

• 我们提出了 SWE-Together，一个从真实多轮用户交互编码智能体会话中重构的 109 任务基准测试，以及一个将记录会话转换为可验证任务的流水线。 • 我们开发了一个锚定的、状态条件的 LLM 用户模拟器，该模拟器保留原始用户的意图和干预顺序，同时将反馈适应于每个被评估智能体不断演变的轨迹。 • 我们设计了一个联合评估协议，使用冻结的、与实现无关的评分标准对最终仓库正确性进行评分，并通过用户纠正和意图覆盖来表征交互轨迹。

2 SWE-Together SWE-Together 将记录的多轮编码智能体会话转换为可重现的交互式软件工程任务。我们的方法包含三个组件。 首先，任务构建流水线过滤和规范化原始会话，筛选其编码目标是否可以在本地重现，并将可行的会话转换为具有固定环境、可执行检查和任务特定用户模拟提示的沙箱仓库级任务。 其次，用户模拟器以轨迹条件化的方式重放原始用户的意图，仅当从记录会话中派生的条件满足时才进行干预。 第三，评估框架分别测量智能体最终仓库状态的正确性和重放期间的用户模拟器行为。正确性由一个智能体评分标准评判器使用仓库检查和可执行证据进行评估，而用户模拟器行为通过用户纠正和意图覆盖来表征。这些组件共同实现了对智能体完成具有不断演变指令的编码任务的能力以及它从模拟器引发的纠正性引导的受控评估。

2.1 会话到任务的构建 我们从来自上游 Hugging Face 数据集的原始多轮编码会话中构建可执行任务。四个上游来源为评估套件做出了贡献：DataClaw（dataclaw2026）、Pi-staging（pistaging）、Hyperswitch（hyperswitch）和 SWE-chat（swechat），总结于表 1。

图 2：会话到任务构建流水线概览。第一阶段完全确定性，第二阶段执行可行性筛选，第三阶段在沙箱中生成可重现任务。

最终套件是原始会话中经过精心筛选的高精度子集：109/11,260 个会话通过筛选并转换为可执行任务，转换率为 0.97%。早期筛选倾向于具有多轮用户交互和具体代码更改工作的公开、足够成熟的 GitHub 仓库；后期筛选要求可恢复的更改和可在本地评估的结果。

构建流水线有三个阶段。 首先，一个确定性的基于规则的收集器过滤原始上游会话，并为每个候选发出一个规范化记录。 其次，一个 LLM 评判器确定编码工作是否可以重构为可重现和可验证的任务。 第三，一个沙箱编排器运行任务构建以产生完整的任务目录。 概览如图 2 所示。

2.1.1 步骤 1：确定性资格筛选 第一阶段使用确定性过滤构建候选会话的初始池。给定上游编码智能体会话，收集器移除缺乏足够交互、代码修改或仓库上下文以支持重放的轨迹，并为每个剩余候选发出一个规范化记录。这些标准是有意基于规则的，不需要 LLM 调用。

候选必须包含多个真实用户消息、具体的智能体操作或代码编辑，并提供足够的仓库信号以识别工作仓库。交互和编辑标准确保每个轨迹都包含多轮用户反馈和具体的代码更改工作，而不仅仅是讨论或只读探索。仓库筛选倾向于公开的、足够成熟的项目，以便下游沙箱构建可行且较少依赖私有或不稳定的代码库。我们还筛选掉最终更改主要由人类用户编写的会话。这保留了编码智能体执行实质性实现工作的轨迹。

图 3：任务构建工作流。主机编排器创建一个隔离的沙箱，提供规范化的会话和创作提示，并导出最终的任务包。在沙箱内，任务生成智能体筛选候选、识别仓库验证命令、编写测试、构建用户模拟提示，并审计生成的任务。

2.1.2 步骤 2：可行性筛选 第二阶段筛选保留会话中的实质性编码工作是否可以重构为一个独立的、本地可执行的任务。筛选器接收一个紧凑的会话摘要：仓库元数据、消息/工具/编辑计数、工具使用分布、选定的用户消息、编辑的文件路径和截断的 shell 命令。它返回会话的主要交付物以及该交付物是否可在本地基准测试环境中重现。

我们拒绝主要交付物依赖于外部状态的会话，例如拉取请求管理、问题分类、部署操作、私有凭据或实时服务状态。具有附带外部操作的会话（如最终推送或拉取请求创建步骤）在代码编辑是核心结果时仍然可行。

可行性筛选不评估正确性。保留的会话稍后被重构为原始参考补丁，并通过确定性验证器和最终仓库状态评分进行评估。

2.1.3 步骤 3：任务构建 第三阶段将每个可行会话转换为可执行的基准测试包。对于每个候选，主机编排器启动一个隔离的沙箱，提供规范化的会话和提示，并收集生成的任务目录。在沙箱内，任务生成智能体执行更严格的仓库基础筛选，在固定提交处克隆目标仓库，识别本地设置和测试命令，并编写任务工件。这种分离防止任务构建依赖于主机机器状态，如缓存的凭据、本地路径、安装的工具链或已应用的修复。

生成的包包含原始会话记录、初始用户指令、固定的执行环境、确定性验证器工件和任务特定的用户模拟提示。图 3 总结了工作流。

2.2 用户模拟器 真实的软件工程任务通常通过用户干预演变：澄清、纠正、新需求或检查外部工件的请求。我们通过将每个重构任务重放为编码智能体和用户模拟器之间的多轮交互来对此进行建模。在每个完成的智能体轮次之后，重放过程总结实时轨迹并咨询模拟器一次。然后，模拟器做出一个结构化决策：发送面向用户的消息或保持沉默。

模拟器动作空间包含 no-op、question、redirect、new-requirement 和 check-external。默认动作是 no-op，它保持模拟器沉默并让智能体继续，而不消耗原始后续消息之一。其他动作对应于常见的用户干预：请求澄清、重定向无效的轨迹、引入后续需求或请求智能体检查外部工件。

图 4：用户模拟器咨询的上下文。每个重放检查点结合了固定的会话锚点、被评估智能体最新轮次的摘要以及来自早期检查点的模拟器记忆。模拟器发出一个结构化动作：携带消息的动作作为用户轮次注入，而 no-op 让智能体继续。

模拟器遵循两个原则：干预是轨迹条件化的而非计划性的，并锚定于原始会话而非通用的。它以最近的智能体活动、智能体的最新响应、经过的时间、观察到的仓库变化以及它自己先前的决策为条件，这有助于避免重复、过早或不相关的消息。同时，每个任务特定的模拟器以从原始用户—智能体交互中重构的会话分析为条件（wu2026humanlm）。该分析指定了用户的目标、约束和基于原始后续消息的干预条件。这避免了两种失败模式：当被评估智能体遵循不同路径时，固定重放可能时机不当，而通用模拟可能偏离原始任务。在评估时，这些锚点定义了一个状态条件决策策略：当实时轨迹需要反馈时模拟器发言，否则返回 no-op。

2.3 评估方法 我们沿两个维度评估每次重放：任务正确性和用户模拟器行为。任务正确性衡量智能体的最终仓库状态是否满足编码请求，包括交互期间引入的需求。用户模拟器行为衡量产生该最终状态所需的反馈。

图 5：正确性加上交互诊断。最终正确性对提交的仓库状态进行评分，而交互诊断表征产生该状态的重放。意图覆盖衡量模拟器对原始用户范围的保真度；用户纠正衡量智能体引发的引导。

2.3.1 任务正确性 对于任务正确性，我们评分行为完整性而非与原始参考补丁的相似性。这一区别很重要，因为不同的智能体可能以不同的辅助函数、控制流或集成点满足相同的请求。

任务构建期间产生的可执行检查对于最终评分是有用但不足的。固定检查可能在两个方向上与会话意图不一致：狭窄的检查可能强制附带的实现细节，而宽泛的检查可能要求从未被请求的行为。这种失败模式并非我们设置独有：OpenAI 在发现许多剩余任务使用拒绝功能正确解决方案或要求未指定行为的测试后，停止报告 SWE-bench Verified 分数（openai2026swebench），而 DeepSWE 在 SWE-bench Pro 中报告了类似的验证器可靠性失败，包括对行为有效补丁的假阴性（datacurve2026deepswe）。仅执行评分也可能错过交互后期引入的需求，未能行使依赖于真实仓库上下文的行为，或拒绝有效的替代实现。纯静态审查有相反的弱点：相关证据可能出现在调用点、配置、生成行为或有针对性的执行结果中，而不仅仅是在本地代码片段中。

因此，我们的评估器将确定性验证器与智能体评分标准评判器相结合。确定性验证器为每个任务提供可执行证据。另外，评分标准评判器分两个阶段对任务完整性进行评分：阶段 1 每个任务运行一次以派生加权的任务评分标准，阶段 2 将相同的评分标准应用于每个候选仓库状态。我们将两个阶段分开，以便评分标准在离线时固定，在任何候选之前且独立于任何候选，防止评分标准被量身定制或受到被评估的特定解决方案的偏见，从而保持跨智能体的可比性。阶段 1 的评分标准可以咨询原始参考补丁以识别记录解决方案的行为，但由此产生的目标是行为性的，并在智能体之间不变地重用。

对于每个目标，阶段 2 返回一个二元的"满足"决策及支持证据。最终任务正确性分数从这些决策中机械地派生： score = round(∑_g w_g · 𝕀[g 满足], 2)， 其中 g 遍历任务评分标准目标，权重 w_g 归一化为总和为 1。加权提供部分学分，而在智能体之间重用相同的评分标准确保同一任务上的所有尝试都根据相同的标准进行评估。主机端验证器检查目标覆盖、权重归一化以及报告决策与结果分数之间的一致性。

2.3.2 用户模拟行为 仅正确性不能捕捉到达解决方案的交互成本。两个智能体可能以相似的仓库状态结束，但需要非常不同数量的模拟器反馈。因此，我们与任务正确性分开报告用户模拟器行为。

我们使用两个诊断。意图覆盖审计模拟器保真度：重放的模拟器消息是否保留原始用户的意图并保持在范围内。用户纠正衡量被评估智能体引发的纠正性引导，计算明确纠正和较低权重的提示。这种分离使模拟器保真度与主要结果中使用的面向智能体的交互信号保持区别。

意图覆盖。意图覆盖衡量模拟器如何忠实地保留原始会话的原始用户意图。我们分两遍计算它。首先，每个任务一次，我们将原始会话轨迹分解为一组原子原始会话意图，每个意图代表原始用户做出的一个独特请求。其次，对于每个重放的试验，我们将模拟器的消息与这些意图进行匹配，并记录每个意图被覆盖的程度以及每个模拟器消息是否保持在原始范围内。

从这种匹配中，我们派生加权意图召回 I_recall，衡量模拟器如何完整地重新表达原始请求，以及范围精度 I_precision，衡量其指导如何一致地保持在原始用户范围内。我们将它们组合如下。 IntentCoverage = round(0.70 · I_recall + 0.30 · I_precision, 2)。

我们更重地加权召回，因为省略一个原始意图可以直接改变呈现给被评估智能体的任务。单独测量意图覆盖有助于将智能体能力与模拟器引起的、在原始会话如何忠实地重构方面的变化区分开来。因此，该指标作为模拟器保真度和跨智能体可比性的诊断：分数应在模型队列之间保持广泛稳定，而显著较低的分数可能表明模拟器省略了需求、偏离了原始范围，或由于智能体的响应将交互从原始轨迹转移而难以传达剩余意图。

用户纠正。我们定义"用户纠正"来测试更强的模型需要更少干预才能达到相同性能水平的假设。为了识别纠正性干预，我们对每个模拟器消息应用一个多标签标记器。多标签是必要的，因为一条消息可能同时执行多个交际行为，例如在纠正先前错误的同时引入新请求。

该分类法分离了用户行为的三个层次。纠正层包含 correction，明确断言智能体的工作不正确、不完整或偏离轨道，以及 nudge，仅暗示怀疑或鼓励重新考虑而不断言缺陷。非纠正性请求层包含 request、question 和 verification，分别代表新需求、真正的信息寻求问题和中性检查。最后，workflow、approval 和 context 捕获机械指令、确认和背景信息。这些后面的标签不对用户纠正做出贡献。

对于每个试验，我们计算 UserCorrection = N_correction + 0.2 · N_nudge。

明确纠正获得全部权重，因为它们直接断言智能体失败或误解了请求。提示获得较小的权重，因为它们捕捉较软的纠正压力，例如作为提示提供的怀疑问题或诊断信息。用户纠正首先在每个任务内的重复中平均，然后跨任务平均，确保每个任务对模型级结果贡献相等。编码智能体之间用户纠正的变化主要取决于智能体，并作为任务正确性的伴随衡量。在我们更强的模型需要更少纠正性干预才能达到可比性能的假设下，用户纠正应与模型能力负相关。

3 实验和结果 3.1 主要结果 实验设置。我们使用通用智能体框架 opencode，在完整的 109 任务 SWE-Together 基准测试上评估七个前沿模型，每个任务 k=2 次重复。每个最终补丁从智能体评判器根据第 2.3.1 节的任务冻结评分标准获得 [0,1] 中的分数。我们使用该评判器分数，而非原始测试执行，作为主要正确性信号。

评估指标。令 j_{t,r} ∈ [0,1] 表示任务 t 的重复 r 的评判器分数，并令 s_{t,r} = 𝕀[j_{t,r} ≥ τ], j̄_t = (1/k) ∑_{r=1}^k j_{t,r}, s̄_t = (1/k) ∑_{r=1}^k s_{t,r}, 我们报告四个同等任务加权的正确性指标： pass@1 = (1/N) ∑_{t=1}^N s̄_t, SSR = (1/N) ∑_{t=1}^N 𝕀[j̄_t ≥ τ], pass² = (1/N) ∑_{t=1}^N ∏_{r=1}^2 s_{t,r}, MeanJudge = (1/N) ∑_{t=1}^N j̄_t。

这里，N=109。三个基于阈值的指标应用相同的成功阈值 τ=0.85，但以不同方式聚合 k=2 次运行。pass@1 是边际每次运行成功率，估计单次新运行解决任务的概率。稳定解决率（SSR）首先在每个任务内平均连续评判器分数，然后应用阈值，衡量模型平均而言是否可靠，同时容忍偶尔的弱或接近未中的运行。相比之下，pass² 衡量联合成功，仅当两次重复都超过阈值时才给予任务学分，提供最严格的一致性衡量，并最强烈地惩罚运行间方差。因此，pass² ≤ pass@1。MeanJudge 通过报告平均连续评判器分数而不应用阈值来补充这些二元指标。

我们另外报告用户纠正作为与智能体行为最直接相关的交互诊断。它衡量智能体引发的纠正性引导，首先在每个任务内的重复中平均，然后跨任务平均。我们单独报告意图覆盖作为模拟器保真度诊断，而非模型排名指标。我们还报告每个任务的输出加推理标记和挂钟时间。

为什么参考分数低于 100%。参考基线在 τ=0.85 阈值下，在 109 个任务中有可提取参考补丁的 93 个任务上评估，获得 0.90 的平均评判器分数和 ≈78%（73/93）的通过率，其余 16 个没有规范代码差异。在这 93 个中，57 个（61%）获得完美的 1.0，73 个（78%）通过；只有 20 个低于通过阈值，其不足有三个可识别的来源，而非任务不可解决。首先，大约 35% 的未满足目标是评分标准从记录会话继承的流程要求——在编辑前诊断根本原因、回答后续问题或向用户解释更改——最终补丁无法表达这些，因此惩罚每个提交，参考和智能体 alike。其次，一些参考补丁不完整地捕捉了最初跨越多个提交或会话的工作，这是数据流水线的提取噪声伪影。第三，一小部分残余反映了真正不完美的人类解决方案——例如，一个会话修复了几个代码路径但留下了标题错误，评判器正确识别了这一点。由于相同的冻结评分标准应用于参考补丁和每个被评估的智能体，这些共享因素在很大程度上同样影响所有提交，参考行最好被解读为我们评分标准下的同类参考点，而非可解决性的严格上限。

3.2 用户模拟器一致性分析 意图覆盖在编码智能体之间保持广泛稳定。七个模型队列中有六个获得 0.70 到 0.72 之间的总分，召回率从 0.72 到 0.74，精度从 0.66 到 0.72。这种狭窄的变化表明，尽管底层编码智能体的行为存在差异，模拟器通常保留原始用户的请求并保持在其预期范围内。因此，由此产生的评估在模型队列之间广泛可比，不太可能由模拟器保真度的系统变化驱动。

GPT-5.5 略低于这一范围，总分为 0.68（召回 0.71，精度 0.65）。差距很小，与其强大、高效的任务性能一致：更强大的智能体更经常地自行解决或重塑交互，这可能使模拟器更少有自然机会重新表达每个原始后续，而不是表明该队列的模拟器保真度降低。所有七个队列在紧凑范围内表现出一致的用户模拟器行为，支持跨智能体可比性。

3.3 用户模拟器质量研究 协议。我们评估人类标注者是否能区分模拟用户和真实用户。通过网络界面，四名标注者对配对轨迹做出强制的二选一判断，选择他们认为由真实用户产生的轨迹。我们使用 DeepSeek-V4-Pro、MiniMax-2.7 和 Claude Opus 4.6 共享的 52 个任务，产生 156 个轨迹对和 312 个判断。

我们报告图灵通过率，定义为模拟轨迹被选为真实的判断比例。50% 的通过率对应于机会水平的区分。

发现。在所有轨迹中，模拟器实现了 46% 的图灵通过率（95% CI [40.5, 51.6]%）。由于置信区间包含 50%，标注者没有表现出统计上可靠的能力来区分模拟用户和真实用户。这些结果表明，在我们的评估协议下，模拟和真实用户轨迹对人类评估者来说通常无法区分。

4 相关工作 我们区分了编码智能体的两种多轮评估形式。 智能体—环境多轮指的是智能体在解决固定用户请求时迭代地检查文件、运行命令、编辑代码和调用测试的情景。 交互式重放指的是面向用户的指令通过反馈、纠正、澄清或新需求演变的情景。 这种区分将先前的工作组织为三组： 具有真实智能体—环境交互但固定用户请求的软件工程基准测试； 具有模拟用户的交互式编码基准测试；以及 没有任务基础重放的真实编码会话数据集。 如表 3 所总结，SWE-Together 结合了仓库级智能体—环境交互、交互式用户纠正重放以及来自真实记录用户—智能体编码会话的来源。

智能体—环境多轮基准测试。SWE-bench（jimenez2024swebench）及其扩展（yang2025swesmith；zhang2025swebenchlive；liang2026swenext；pan2024swegym）是规范的仓库级软件工程基准测试。它们将任务基于真实代码库和问题，智能体可以在产生最终补丁之前采取许多环境动作。Terminal-Bench（merrill2026terminal）类似地在交互式终端环境中评估智能体。这些基准测试在智能体—环境意义上是多轮的，但用户请求是固定的：基准测试不评估智能体是否能从用户纠正中恢复或适应中间尝试后揭示的需求。SWE-Together 保持了仓库级、使用工具的设置，但增加了交互式用户纠正循环。

具有模拟用户的交互式编码基准测试。一条互补的工作线将模拟用户反馈引入编码评估。TiCoder（lahiri2022ticoder）研究在 HumanEval（chen2021evaluating）和 MBPP（austin2021program）上具有模拟用户查询的迭代代码生成。MINT（wang2024mint）和 ConvCodeWorld（han2025convcodeworld）将 LLM 驱动的反馈扩展到标准代码生成任务。而 pan2025whenbenchmarkstalk 通过模拟用户揭示隐藏信息，将静态基准测试转换为交互式评估。更近期的工作将交互式评估推向更接近软件工程：CodeAssistBench（CAB）（kim2025codeassistbench）使用 GitHub 问题任务和满意度驱动的模拟用户。SWEET-RL/ColBench（zhou2025sweetrl）、RECODE-H（miao2025recodeh）和 FronTalk（wu2026frontalk）评估后端、研究代码和前端设置中的协作细化，而 CollabLLM（wu2025collabllm）通过优化通过模拟用户估计的多轮感知奖励来训练助手作为主动协作者。这些基准测试表明用户反馈是重要的评估轴，但它们的交互循环通常是从静态任务、问题工件、精心策划的反馈策略或基准测试生成的场景中合成的（xu2025funreasonmt；zhou2026sandmle；chen2026dreamgym）。相比之下，SWE-Together 从记录的真实人类—智能体编码会话中派生任务，并将模拟纠正循环基于相应的原始会话。这一设计选择得到 suh2026simulators 的支持，他们量化了用户模拟器的效用，并发现基于真实人类行为的模拟器产生比角色扮演提示更好的下游协作助手。

真实编码会话数据。最近的数据集表明，真实用户—智能体编码交互可以大规模收集。SWE-chat（swechat）表征了真实世界的编码智能体会话，而 BigCodeArena（zhuo2025bigcodearena）和 CodeChat（zhong2025codechat）收集以代码为中心的对话，用于偏好建模、分析和助手评估。相关基准测试如 Saving SWE-Bench（garg2025savingswebench）和 EDIT-Bench（chi2025editbench）进一步强调真实的用户措辞和实际编辑指令。然而，这些工作主要是描述性的、面向偏好的或单请求评估集：它们没有将每个真实会话与可重放的仓库状态、确定性验证器和实时用户纠正循环配对以评估新智能体。

5 局限性和结论 局限性。用户模拟器不能在智能体轮次期间中断它，不能直接编辑文件，并且仅依赖于文本轨迹和工具输出，而非来自界面的视觉信息。当前设计在用户目标和约束明确定义时效果最佳，并专注于具有可衡量结果的任务，如提交的补丁。因此，它对模糊的、开放式任务和难以量化的定性用户行为的覆盖有限。

结论。这项工作提出了 SWE-Together，一个将真实多轮编码会话转换为可重现软件工程任务的基准测试，并评估最终任务正确性和交互期间所需的用户引导。在 109 个任务和七个前沿模型中，结果显示能力和可靠性方面存在实质性差异。用户纠正与性能强烈负相关，支持更强大的编码智能体需要更少用户干预的假设。此外，模拟器在模型之间保持广泛一致的意图覆盖，并产生人类标注者无法可靠区分于真实用户交互的轨迹。这些发现共同表明，评估编码智能体不仅应根据它们是否完成任务，还应根据它们引发多少纠正性引导。通过纳入真实的多轮交互和以用户为中心的诊断，SWE-Together 旨在以更接近反映实际用户体验的方式评估编码智能体。
