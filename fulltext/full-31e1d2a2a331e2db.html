智能体编程与专业知识的持续回报

📅 2026-06-16 📄 Anthropic 🔗 原文链接

原标题：Agentic coding and persistent returns to expertise

中文摘要： 本文分析了约40万个Claude Code会话，发现智能体编程中存在明确的劳动分工：人类负责规划，AI负责执行。领域专业知识而非编程熟练度是决定任务成功的关键因素，专家级用户的成功率和AI工作效率显著更高。非软件职业人员的编程成功率已接近软件工程师，表明编程背景的重要性正在降低。未来，领域专业知识将继续在人机协作中发挥核心作用。

核心发现

  • 在先前工作的基础上，我们引入了一个研究交互式智能体编程的框架，该框架基于对 2025 年 10 月至 2026 年 4 月期间约 40 万个 Claude Code 会话的隐私保护分析。我们评估了任务构成、人机协作和成功率。
  • 在典型的会话中，人们做出大部分的规划决策（做什么），而 Claude 做出大部分的执行决策（怎么做）。一个人在会话中带来的领域专业知识越丰富，Claude 每条指令完成的工作就越多。在编程任务上，每个主要职业的成功率——即完成人们设定要完成的目标，并有通过测试或提交工作等可验证的证据——平均而言与软件工程师几乎相同。
  • 一个人的领域专业知识越丰富，会话以成功告终的频率就越高——尽管中级和专家用户之间的差距不大。在我们观察的七个月中，用于调试的会话比例下降了近一半，使用方式转向了更多的端到端智能体使用：部署和运行代码、分析数据以及编写非代码文档。
  • 在这七个月中，通过与自由职业招聘信息进行比较估算，典型任务的价值在几乎所有类型的工作中都有所上升——平均约为 25%。

引言

智能体编程已经起飞。自 2025 年底以来，带有编程智能体活动的 GitHub 项目份额增加了一倍多，1 Claude Code 用户现在平均每周花费 20 小时使用该工具。2 没有正式编程经验的人能否成功指导智能体完成复杂的技术工作？这些工具的快速采用和改进对广泛的知识型工作意味着什么？虽然我们还没有这些问题的完整答案，但我们通过 Claude Code 的使用数据寻找早期信号。

随着智能体嵌入到非编程工作中，Claude Code 上发生的事情可能是知识型工作走向的预览。我们发现 Claude 正在处理更复杂、更有价值的任务。同时，智能体编程中仍然存在明确的劳动分工：人们决定构建什么，智能体决定如何构建。

我们还看到证据表明，是领域专业知识而非编程熟练度放大了该工具的有效使用。特别是，领域专家更常取得成功，并且更容易从错误和误解中恢复。然而，专家和中级用户之间的差距不大——这表明在一个领域内的熟练度足以让人几乎和那些拥有深厚掌握程度的人一样有效地使用该工具。

这些发现让我们对劳动力市场可能发生的转变有了初步了解。在我们的数据中，成功取决于一个人对他们试图解决的问题的理解程度，而不是他们是否受过编程训练。如果这些模式在整个经济中成立，这表明虽然智能体编程工具可能正在吸收一些繁重的实现工作，但它们也在奖励那些在工作中对所解决问题有坚定理解的人。编程智能体并不能替代领域专业知识——员工带给智能体的理解越多，智能体就能完成越多的优质工作。

劳动分工

人们使用 Claude Code 做什么

为了了解人们使用 Claude Code 做什么，我们将每个会话分类为九种工作模式之一——最能描述会话试图完成的单一活动。5 四种模式涉及直接编写或维护代码：构建新东西、修复损坏的东西、测试代码，以及编排其他智能体或自动化流水线。另一个类别是操作软件——部署、配置、运行流水线、监控系统。两个类别更多是关于弄清楚要做什么：理解现有系统如何工作，以及在进行更改之前规划更改。还有两个采取与代码无关的操作，或者代码对最终产品来说是附带的：分析数据，以及通过演示文稿和其他基于文本的文档进行沟通。

大约 56% 的会话由编写 (25%)、修复 (26%) 或测试和编排代码 (5%) 组成。操作软件占 17%，而 14% 的会话是规划或探索，13% 产生分析或文本（图 1）。

图 1：九种工作模式每个交互式会话都被分类为最能描述其试图完成目标的单一模式。

我们通过让模型读取其记录来对每个会话进行分类，然后使用我们的隐私保护分析工具，将它们与每个会话自动记录的遥测数据进行核对，包括是否添加或删除了任何代码行。两个来源具有很高的一致性——例如，我们的分类器标记为创建或修改代码的会话中，超过 90% 在遥测中显示了代码更改。详情请参阅附录。

谁决定什么

Claude Code 的自主性如何？能力评估表明上限很高且在上升：在 METR 的时间跨度评估等基准上，前沿模型现在可以完成需要一个人数小时才能完成的软件任务，并在此过程中自主克服障碍。但实际使用情况是怎样的呢？在这里，我们看看在真实会话中，人和 Claude 分别进行了多少指导。

我们从两个角度调查这个问题。首先，我们关注人们在多大程度上将决策委托给 Claude，其次我们关注他们给 Claude 多少操作。为了理解会话中的决策分工，我们基于会话内容构建了一个隐私保护的决策归因分类器。我们要求分类器列出会话中的所有有意义的决策。我们将这些决策分为规划（做什么、采取哪种方法、什么算完成）和执行（更改哪些文件、编写什么代码、用什么语言编写、运行哪些命令）。然后，分类器将每个决策归因于 Claude 或用户，为每个会话提供两个数字：用户的规划决策份额和用户的执行决策份额。

平均而言，人们做出大约 70% 的规划决策，但只做出 20% 的执行决策（图 2）。在实践中，智能体编程中存在明确的劳动分工——人们决定构建什么，智能体决定如何构建。

为了理解会话中操作的委托，我们查看会话的结构而不是其内容。一个 Claude Code 会话涉及 Claude 和用户来回交换提示（来自用户）和操作（由 Claude 执行）——用户写一个提示，Claude 去做一些工作，然后用户写另一个提示，依此类推。在典型的会话中，大约有四个这样的轮次。在我们 10 月到 4 月的历史数据中，用户发送的每个提示平均会引发 Claude 执行约 10 个操作的链条——有时超过 100 个。6 在每个轮次中，Claude 读取文件、编辑代码、运行命令，并平均输出 2,400 个单词。

Claude 在两次检查之间做了多少工作很大程度上取决于谁在做决策。当用户保持对执行的控制（即做出超过 80% 的执行决策）时，Claude 每个轮次采取的操作较少（约八个操作）。当 Claude 掌控规划（即做出超过 80% 的规划决策）时，它采取的操作数量最多（约 16 个）。

图 2：Claude 在规划和执行决策中的份额归因于 Claude 而非用户的规划决策（做什么）和执行决策（怎么做）份额在会话中的分布。在典型会话中，用户做出约 70% 的规划决策，而 Claude 做出约 80% 的执行决策。

专业水平

从每份记录中，Claude 在五分制上对用户在该任务中的表面专业水平进行评级，从新手到专家。专业水平分类器寻找三个信号：用户构建指令的精确度、他们要求 Claude 验证什么，以及是用户倾向于纠正 Claude 还是 Claude 倾向于纠正用户。请注意，专业水平捕捉的是与职位名称或一般能力截然不同的东西，而且至关重要的是，它是针对特定任务的。一位高级工程师第一次问 Rust 问题时，在 Rust 方面就是初学者。一位从未使用过 Python 的会计师，如果准确地告诉 Claude Python 脚本必须执行哪些对账规则，并抓住了它在月末结账时处理不当的边缘情况，那他就是该任务的专家。

下表显示了我们在分类器中如何定义每个专业水平，以及来自公共编程智能体会话数据集 SWE-chat 的示例请求。被归类为新手的对话给出的是通用指令，没有暗示特定领域的知识。专家对话则传达了对代码库和技术环境的深刻知识。

我们量化了专业水平如何与 Claude 的输出和每个提示的活动相关。在典型的新手会话中，每个提示引发大约五个 Claude 操作和大约 600 个单词的输出，而专家会话引发的操作链条是其两倍多（12 个操作），输出是其五倍（3,200 个单词）（图 3）。新手和专家会话之间的这种差距出现在每种工作和每个任务价值区间中。

谁在使用 Claude Code，以及用于什么

用户

为了了解谁在做这项工作，我们从会话记录中推断每个用户的职业，并将其映射到劳工统计局标准职业分类 (SOC) 分类法中的 23 个主要群体之一。分类器被指示仅依赖信号，例如智能体在会话开始时加载的项目上下文、其文件的名称和结构、他们引用的任何工件（例如法律文件、临床数据、财务报告、课程等）以及他们使用的词汇。7 它被明确指示不要将编程行为视为编程职业的证据。只有当有明确信号表明软件或数据工作是用户的职业时，会话才会被分类到编程 SOC 代码（计算机和数学职业）中。律师构建脚本以自动标记合同文件夹中缺失条款的会话被映射到法律职业，即使该会话的工作主要是软件。当没有关于用户职业的信号时，该会话将被保留为未分类。

我们能够在约 70% 的会话中推断出职业。在这一组中，包含大多数软件相关工作的计算机和数学职业是最大的群体，这并不令人意外。其次是商业和金融运营；艺术、设计和媒体；管理；以及生命、物理和社会科学。我们样本中增长最快的非软件职业群体是管理、销售和法律职业。

工作

2025 年 10 月至 2026 年 4 月期间，使用 Claude Code 完成的工作构成发生了重大变化。最明显的变化是用于修复损坏代码的会话份额从 33% 下降到 19%（图 4）。取而代之的是，我们看到了更大份额的围绕代码的工作。操作软件从 14% 增长到 21%。编写和数据分析几乎翻了一番，从约 10% 增长到 20%。

图 4：Claude Code 工作的构成和价值，2025 年 10 月至 2026 年 4 月七个月窗口期内每种工作模式的会话份额。修复损坏代码的会话份额从 33% 下降到 19%，而操作软件、分析数据和编写文档的份额则有所增长。

成功取决于用户带来了什么

任务的估算价值是了解 Claude Code 如何帮助人们工作的一种方式。另一个角度是看有多少会话是成功的，以及会话的哪些特征与成功相关。在我们所有的成功衡量标准中，我们看到了一个清晰的模式：一个人在会话中表现出的专业知识越多，成功的可能性就越高。大部分增益集中在专业水平量表的低端——新手会话和中级会话之间的差距大于中级和专家之间的差距。

在转向成功会话的特征之前，我们应该明确如何衡量成功。我们观察不到用户的现实世界结果，也不能直接问他们是否从 Claude 那里得到了他们想要的东西。相反，我们依赖两种互补的基于记录的衡量标准。第一种是判定成功，来自一个读取完整记录并决定此人是否成功完成了他们设定要完成的目标（选项包括：成功、部分成功、失败、无明确目标）的分类器。然后，两个配套分类器对该判断的证据强度进行评级，以确定验证成功。成功信号分类器寻找成功的可验证证据。特别是，它寻找与工作匹配的 git 活动（如提交和拉取请求），以及通过的测试套件和用户的明确肯定。它将会话从“无信号”到“弱信号”(1) 到“多个硬信号”(5) 进行评分。并行的失败信号对出错的证据进行评分——错误、测试失败、重试、用户对输出提出异议。验证成功要求会话既被判定为成功，又至少有一个硬性的可验证成功信号。在以下专注于会话中成功或失败程度的分析中，我们排除了被归类为“无明确目标”的会话，这些会话约占我们完整样本的 7.7%。

专业知识的回报

那么什么样的会话最成功呢？事实证明，上述的会话专业水平评级对会话的成功至关重要。

人们可能会担心专业知识并不是真正的驱动因素——也许专家只是选择了不同的任务，或者在其他方面有所不同。在本节中，我们通过比较做相同类型工作、具有相同估算价值、在同一个月、针对同一主题、来自相同广泛职业群体的人的会话来部分解决这种担忧，并询问结果如何因个人的评级专业水平而异。

表 2：从分类器得出的成功和失败定义这些示例改写并总结了来自公共智能体编程交互数据集 SWE-chat 的真实会话，由我们的分类器标记。

在我们所有的成功衡量标准中，一个人在会话中表现出的专业知识越多，会话成功的可能性就越大。评级为新手的会话有 15% 的时间达到我们最严格的衡量标准——验证成功，有 77% 的时间至少达到部分成功。评级为中级或以上的会话有 28-33% 的时间达到验证成功，有 91-92% 的时间达到部分成功（图 5）。

在每项衡量标准中，大部分增益来自于从新手到中级的提升；在中级和专家之间，斜率下降。在附录中，我们给出了图 5 背后回归的详细信息。

图 5：专业水平与会话如何结束按用户在任务中的评级专业水平划分的会话结果，采用从新手到专家的五分制。左图包括所有会话。中图和右图限制在遇到麻烦（失败信号 > 3）的会话，并显示最终以各种成功和失败定义结束的份额。每个点都是一个调整后的比率——我们仅通过比较共享相同工作模式、相同任务价值区间、相同月份、相同任务主题和相同类型用户（是否为软件相关职业）的会话来估计专业水平之间的差异。关于这些点背后回归的详细信息在附录中。须线是样本均值的置信区间（大多数在这个图中太小而不可见）。这些图排除了被成功结果分类器判定为无明确目标的会话。

在沿途遇到挑战的会话中也出现了类似的梯度。当失败信号记录了失败的验证证据时，我们就说一个会话遇到了麻烦。这可能是错误、测试失败、多次尝试做同一件事，或者用户表达沮丧或不满。在遇到麻烦的会话中，验证成功的份额从新手评级会话的 4% 上升到专家评级会话的 15%，这考虑了上述所有控制因素（图 5）。看看更宽松的衡量标准，我们发现新手至少部分成功的份额为 60%，而中级到专家会话为 80-81%。

我们还跟踪了反向关系——专业水平与各种失败衡量标准的关系。请注意，在此分析中，被判定为失败的会话是那些甚至没有部分成功的会话。如果一个遇到麻烦的会话被判定为失败并且编写了零行代码，我们就说它被放弃了：在用户似乎是新手的情况下，19% 的会话最终被放弃，而其他所有人则为 5-7%。换句话说，最缺乏经验的用户在努力获得他们想要的结果时更有可能放弃。专业知识的部分价值似乎在于能够将智能体引向正确的方向。9

职业的影响可能不如专业水平

从事软件相关职业的人总体上在大约 30% 的会话中达到验证成功，而来自其他职业的用户达到验证成功的比例约为 26%。在生成代码的会话（即添加或修改至少一行代码的会话）中，这两个数字分别为 34% 和 29%（图 6）。在我们更宽松的成功定义下，软件相关职业和其他职业之间的差距缩小了——这两个群体在生成代码的会话中分别有 89% 和 88% 的时间至少达到部分成功。这五个百分点的差距很小，在七个月内既没有扩大也没有缩小，即使这两个群体的成功率都有所提高。在生成代码的会话中，我们数据集中十个最大的职业在成功率方面都与软件工程师相差不到七个百分点。管理职业在验证成功方面最高，略高于软件工程职业。他们较高的验证成功率可能反映了转移到指导智能体的管理技能。但也可能部分反映了我们的衡量方式：验证部分依赖于记录中的明确确认，而管理者在得到他们要求的东西时可能更愿意沟通。10

图 6：按推断职业划分的编程会话中的验证和判定成功率在添加或更改至少一行代码的会话中，符合严格成功定义——判定成功和验证成功——的会话份额，按用户推断的职业群体划分，显示了十个最大的群体。每个群体与软件/数学用户（SOC 代码计算机和数学职业）的差距都在七个百分点以内。误差线是在不同账户上计算的 95% 置信区间。

展望未来

本报告的结果提供了一幅新兴的画面，说明智能体编程如何放大某些形式的知识和技能，同时替代其他形式。在生成代码的会话中，每个主要职业的成功率都与软件相关职业相差无几。看来编程智能体正在使编程背景与成功的编程变得不那么相关。

同时，成功的会话更有可能表现出领域专业知识。评级为专家的会话达到验证成功的频率是评级为新手的会话的两倍多，当会话遇到麻烦时，新手放弃会话的比率是其他所有人的几倍。协作的形态为这幅画面增添了更多色彩——领域专家能够指导 Claude 用他们给出的每条指令做更多的工作。因此，引导 Claude 走向成功的能力更多来自于对领域的掌控，而不是编写代码的能力。拥有这种掌控力的人，在任何领域，现在可能都能做他们以前不能做的技术工作。一个没有任何此类专业知识的人从同一工具中获得的收益要少得多。而且收益主要来自于胜任能力，而不是精通——对领域的工作性掌握能获得大部分收益，而深度专业化在此之外只增加了一点点。

这些发现是初步的。与我们的大多数研究一样，我们无法衡量现实世界的结果，例如会话中编写的代码此后是否实际被使用或丢弃，或者它是否产生了具有经济价值的工件。此外，本报告排除的非交互式使用是活动的很大一部分。开发一个衡量它的框架是未来工作的优先事项。而且我们所有的会话分类都取决于模型对记录的读取。在附录中，我们展示了我们的分类器按预期方向跟踪独立遥测数据，并在大多数会话上与强大的参考模型一致。但分类器在大规模验证方面仍然具有挑战性，而 Claude Code 会话增加了进一步的难度，因为它们可能太长太复杂，以至于人类标签无法作为基准事实。

随着模型、用户以及他们之间的劳动分工发生变化，本报告中的情况将得到更新。我们希望这些衡量标准将使我们能够跟踪正在发生的重大转变。例如，如果专业知识的回报随着时间的推移开始下降，这将表明模型开始提供用户目前带来的基本判断，并且这些工具的收益正在扩大到领域专家之外。如果软件职业之外的用户成功完成编程会话的份额继续增长，这可能表明软件生产正在成为每个领域日常工作的一部分，而不是单一职业的产物。这些转变将改变谁从智能体编程中受益以及受益多少，并将对劳动力市场中最有价值的东西产生影响。
