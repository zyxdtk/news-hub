中文摘要： 本文提出SPARTA，一种面向文本与表格的大规模树形多跳问答基准。通过统一参考事实数据库、生成可执行嵌套SQL查询及轻量人工验证，SPARTA解决了现有基准规模小、噪声高、推理浅层等问题。实验表明，SPARTA显著提升了任务难度，SOTA模型性能下降超30 F1分，暴露了跨模态推理的根本缺陷。

SPARTA：面向文本与表格的大规模可扩展、原则性树形多跳问答基准 孙成浩（Sungho Park）、金瑞俊（Jueun Kim）、韩悟新（Wook-Shin Han） 韩国浦项科技大学（POSTECH），浦项，韩国 {shpark,jekim,wshan}@dblab.postech.ac.kr 通讯作者。

摘要 现实世界的表格-文本问答（QA）任务要求模型能够跨长文本与源表格进行推理， traversing 多跳路径并执行聚合等复杂操作。然而，现有基准规模小、人工精心构建（因而易出错），且问题浅层，极少要求超过两跳或调用聚合、分组或其他自然语言查询中可表达的高级分析操作。

我们提出 SPARTA，一种端到端构建框架，可自动大规模生成表格-文本 QA 基准，并辅以轻量级人工验证，仅需 HybridQA 标注时间的四分之一。

该框架首先通过将源表格与从配套非结构化段落中自动提取的原子事实（作为元组）构成的“支撑表”进行增强，构建参考事实数据库；随后合成嵌套查询，使其嵌套谓词数量匹配目标跳数。为确保每条 SQL 语句可执行，且其自然语言化能生成流畅、自然的问题，我们提出两种新方法：基于来源的精炼（provenance-based refinement），对任何语法合法但返回空结果的查询进行重写；以及真实结构强制（realistic-structure enforcement），将生成限制在查询图的后序遍历中。最终流水线生成数千个高保真问题-答案对，涵盖聚合、分组及跨文本与表格的深度多跳推理。

在 SPARTA 上，曾在 HybridQA 上达 70+ F1 或在 OTT-QA 上达 50+ F1 的最先进模型，性能骤降超 30 F1 分，暴露出当前跨模态推理的根本性缺陷。我们的基准、构建代码及基线模型见：github.com/pshlego/SPARTA。

1 引言 表格-文本 QA 已成为构建稳健跨异构数据模态（即文本与表格）问答系统的核心挑战 [Chen et al., 2020a; b; 2021; Zhao et al., 2022; Zhu et al., 2021]。 此类任务在文本描述与表格条目源自一个或多个来源（如多个维基百科页面中的文本信息与表格）时尤为突出，需联合分析以得出正确答案。 尽管单个维基百科页面常同时包含文本与表格，但相关信息常跨多页或多文档，需跨文档检索及异构信息的有效整合。

现有表格-文本 QA 基准的一个显著局限是：其由人工标注者手动构建 [Chen et al., 2020a; b; 2021; Zhao et al., 2022; Zhu et al., 2021]，导致基准设计存在根本缺陷，阻碍系统全面评估。

（1）问题类型有限，推理浅层。 受限于人工标注的复杂性，现有表格-文本 QA 基准的问题范围狭窄且较浅层。这些问题通常仅需直接信息抽取（如定位单段文本中的事实或表格中的特定条目）。 即使对超出简单抽取的问题，推理深度仍较浅，极少要求超过两跳或涉及聚合、分组等高级分析操作——尽管这些操作在现实自然语言查询中很常见，但在基准中却严重缺失。 这阻碍了对系统深度、多步推理能力的全面评估。 此外，当前多跳问题通常遵循简单的线性链结构，而非表达性强的树形推理（如多分支路径、更长链或单模态跳转），而后者对评估系统在复杂推理任务上的能力至关重要（如图1所示）。

（2）标注噪声。 我们的质量审计揭示了大量标注错误，损害了基准的可靠性。 重新检查 HybridQA 的 100 个随机采样开发集示例，我们发现 21% 包含至少一个错误，分为三类： （1）冗余模态（52.4%）：表格与段落编码同一事实，但实例被标记为跨模态问题，而单模态已足够； （2）答案集不完整（23.8%）：多个答案正确，但仅记录一个，扭曲召回率； （3）答案错误或不可答（23.8%）：标注答案错误或无法从给定数据中推导，暴露质量控制缺失。 我们对其他基准的审计也发现了类似错误模式（见附录 A）。

（3）依赖单一、小型网络表格。 当前基准几乎全部依赖小型网络表格——通常从维基百科或公司报告中爬取——仅提供玩具级场景。如表1所示，任务要么仅涉及单表，要么在多表情况下，平均表格基数约为15行，远低于现实数据库的数千行。此简化主要出于务实考虑：在更大表格上推理会大幅增加标注员工作量与错误率 [Chen et al., 2020b]。因此，现有基准无法在现实、高复杂度场景中（需在大型异构关系数据上推理）对 QA 系统进行有意义评估。 SPARTA 将所有证据——结构化与非结构化——统一于单一关系存储中，称为参考事实数据库。 每个原始关系（如网络表格或财务账本）保持完整，称为源表。 支撑表（grounding tables）以元组形式存储原子命题，供 SQL 可寻址访问，通过两种互补方法填充（详见第3.2节）：（1）利用经验证语料库（如 ROTOWIRE [Wu et al., 2022]）；（2）采用表到文本策略，直接从结构化数据生成原子事实。 文本事实现可通过 SQL 访问，查询此组合存储可自由混合模态；无需指向原始片段，答案由查询执行直接返回。

阶段1——参考事实数据库构建：源表与支撑表合并为参考事实数据库，使所有事实可统一查询。 阶段2——查询生成：大语言模型（LLM）接收模式与样本行，生成 SQL，其嵌套谓词数量匹配目标跳数。 注意，SPARTA 合成的查询实例化了附录 B 中详述的四种代表性嵌套模式——N、A、J 和 JA 类型。 两项保障确保仅现实、可执行语句得以保留：（1）基于来源的精炼：将来源反馈（如未匹配连接或过度筛选谓词）循环反馈给 LLM，直至查询返回非空结果；（2）真实结构强制：将生成限制在查询图的后序遍历中，生成类似人类的连接顺序，并支持早期剪枝不可行子查询。 阶段3——问题自然语言化：每个经验证查询与其执行结果配对，第二个 LLM 将 SQL 重写为流畅自然语言问题，生成涵盖聚合、分组及大型表格深度多跳连接的高保真对 ⟨question, answer⟩。 此处，最终正确性（即问题-答案对的有效性）通过轻量级人工验证检查；与 HybridQA 不同，我们的流水线无需重新执行完整多跳推理，从而保持审计成本低廉（见第3.4节）。

本 SQL 中心的流水线生成了一个大规模、多样化且严格验证的基准，纠正了先前表格-文本 QA 资源在规模、噪声与逻辑浅层性方面的缺陷。 在 SPARTA 上，曾在 HybridQA 上超 70 F1 或在 OTT-QA 上超 50 F1 的最先进模型，性能下降超 30 F1 分，揭示了当前跨模态推理的根本性缺陷，并指明了未来研究方向。

2 相关工作 表格-文本 QA 基准。 HybridQA [Chen et al., 2020b] 引入该任务，OTT-QA [Chen et al., 2020a] 将其扩展至开放域设置，但二者均存在标注噪声、推理深度浅及缺乏高级分析操作支持的问题。 具体而言，二者不支持 GROUP BY 或 HAVING 子句，仅 1.1% 的问题涉及聚合。其多跳推理限于短线性链，无法捕捉树形或单模态推理路径。 其他基准——TAT-QA [Zhu et al., 2021]、FinQA [Chen et al., 2021] 和 MultiHiertt [Zhao et al., 2022]——窄化聚焦于金融语境中的数值推理，而非多跳推理，进一步限制覆盖范围 [Zhang et al., 2023]。 此外，所有现有表格-文本 QA 数据集均依赖小型、人工标注的网络表格，阻碍可扩展性与真实性。 SPARTA 通过 SQL 中心的流水线构建大规模可执行、组合式问题基准，为跨文本与表格的多跳 QA 提供原则性测试平台。

合成基准生成。 近期合成基准生成从现有来源扩展 QA 对，但多数为单模态：依赖知识图谱 [Sun et al., 2024; Omar et al., 2025; Orogat and El-Roby, 2023; 2022] 或文本语料库 [Bonifacio et al., 2022; Jeronymo et al., 2023]，忽略跨模态推理。 ERBench [Oh et al., 2024] 使用关系数据库，但其问题为二元或选择题，基于排除 GROUP BY、HAVING 和聚合等分析运算符的浅层模板；亦缺乏表格-文本互动。 类似地，TDBench [Kim et al., 2026] 利用时序数据库自动化时敏 QA，但限于结构化表格内的时序推理。 相较之下，SPARTA 生成桥接表格与段落的多跳问题，模仿复杂嵌套 SQL 模式，为表格-文本 QA 提供严格跨模态基准。

其他领域的基准施加领域特定约束：数据库性能基准 [Nambiar and Poess, 2006; Erling et al., 2015] 使用固定模式与模板进行可复现剖析；遗忘基准 [Maini et al., 2024; Zhong et al., 2024] 创建遗忘/保留分区以实现选择性遗忘；PEEL [Kim, 2024] 采用模板生成 NL-嵌套 SQL 对以保证结构复杂查询的可执行性。 SPARTA 的约束根本不同：每个合成示例必须编码树形多跳推理，以语义合理、可执行的 SQL 与自然语言问题为根基，要求分析运算符与表格-文本对齐。 我们的基于来源的精炼与真实结构强制方法解决了此问题，生成语义丰富、可执行的查询。

3.2 参考事实数据库构建 我们使用 ROTOWIRE 数据集作为参考事实数据库的一部分，其结构化表格被广泛用作文本到表格的黄金监督，并经 Wu et al. (2022) 作者验证与配套赛事报告一致。 该语料库中每场 NBA 比赛报告被分解为原子事实，存储于 G<sub>T</sub> 中，确保文本与关系数据的完美对齐。 为构建 S<sub>T</sub>，我们整合了六个公共 NBA 数据集——涵盖薪资、奖项、选秀数据及球队历史——来源为 Kaggle 和 data.world¹;²⁶;²⁸;¹³;²⁵;²⁷。 共享实体属性（如 PLAYER_NAME 与 TEAM_NAME）被强制为主-外键对，形成连通模式，使 G<sub>T</sub> 中每个元组可与 S<sub>T</sub> 中至少一张表连接。 所得数据库包含三个支撑表与六个源表（见附录 C）。 尽管构建以 NBA 数据为例，SPARTA 本质上与领域无关。 从任意关系数据库出发，可指定子集为 S<sub>T</sub>，其余为 G<sub>T</sub>。 对 G<sub>T</sub> 应用表到文本生成，可得配套文本段落集合 C<sub>P</sub>，形成参考事实数据库 D = S<sub>T</sub> ∪ G<sub>T</sub>，二者无信息重叠。 查询生成流水线保持不变，为任何含关系数据的领域构建大规模表格-文本 QA 基准提供可移植方案。 为验证，我们将流水线扩展至电影与医疗两个新领域，使用 Kaggle 数据集¹⁵;¹⁴，配置与 NBA 领域相同（见附录 E）。 对这些数据集，我们从现有结构化表格出发，用基于规则的模板将子集转换为支撑表。此表到文本转换是确定性的、模板驱动的，模板经手动设计与验证，以防止虚假事实或错误。

3.3 查询生成 对非嵌套查询，SPARTA 逐子句构建语句：LLM 按标准 SQL 顺序生成每个子句，基于模式与先前写入的子句，并立即执行部分查询。若结果为空，则将执行结果反馈，使 LLM 修订出错子句，确保每步查询可执行且语义合理。 下一步是合成作为多跳推理忠实逻辑形式的嵌套 SQL 查询。 生成查询须满足两个标准：(i) 应类似于人类分析师可能编写的查询，避免退化模板工件；(ii) 必须在 D 上无误执行并返回非空结果。 这些保障确保每个 (q<sub>NL</sub>, a) 对既自然又可答。 基于模板的生成通过填充固定槽位或添加辅助谓词保证执行，但所得 SQL 常语义不健全。 例如，SELECT birthplace FROM nba_player_information WHERE birthplace <> ‘Chicago, Illinois’ OR birthplace <> ‘Dallas, Texas’ 可无误执行，但表达空洞意图（“… 非芝加哥出生或非达拉斯出生”，匹配所有人）。 相反，单次 LLM 提示生成自然查询，但常返回空结果且多样性有限（见表4.2）。 因此，我们引入双阶段框架：(i) 真实结构强制；(ii) 基于来源的精炼。

3.3.1 真实结构强制 嵌套 SQL 查询可建模为查询图 G = (V, E)，其中每个节点 v<sub>i</sub> ∈ V 对应一个独立查询块——即每个 SELECT … FROM … WHERE … 子查询（包括最外层语句）——而每条（有向）边 e<sub>ij</sub> ∈ E 表示一个嵌套谓词，通过共享属性引用关联块 Q<sub>i</sub> 与 Q<sub>j</sub>，从而以图形式捕获原始嵌套查询的依赖结构（附录 B 提供代表性嵌套查询模式）。 基于此表示，我们以查询树中的边数衡量查询复杂度，每条边代表一个推理跳。 对嵌套查询生成，SPARTA 默认采用 Post-Order+Prov：为保持真实结构，强制 LLM 以后序构建查询树——先组合每个叶节点子查询，再逐层包裹更高层块——这正是分析师构建嵌套 SQL 的方式。 我们选择后序遍历而非广度优先或自顶向下，因后者需在内部子查询构建前验证不完整查询。相较之下，后序确保每个中间块通过先验证子查询再组合高层谓词而可执行。 在 Post-Order+Prov 中，叶节点逐子句生成。对目标问题类型，按标准顺序选取相关子句（WHERE、GROUP BY、ORDER BY…），让 LLM 使用（i）模式、（ii）先前子句及（iii）部分结果填充每个子句。若子句导致空结果，我们回滚至上一有效子查询，避免冗余 LLM 调用。内部节点通过递归封装已验证子查询产生。每步 LLM 选择子查询、选取可连接表并生成连接谓词（AND/OR 等）。空输出触发来源引导修复（§3.3.2）；否则保留谓词。循环持续至查询图增长至指定目标大小。 图3：基于来源的精炼概览。

3.3.2 基于来源的精炼 LLM 以后序构建查询图——先验证叶节点，再逐个添加外部谓词。若演化查询返回无行，则启动基于来源的精炼过程以修复查询。该过程利用“为何无结果”来源（why-not provenance），一种数据库技术，用于识别导致过滤掉预期元组的查询谓词 [Bidoit et al., 2014; Chapman and Jagadish, 2009; Lee et al., 2017]。 尽管传统为何无结果来源常依赖用户提供的缺失元组示例，我们的方法动态从中间查询结果推导预期元组。 过程分三步：首先，当查询返回空结果时，我们按逆序剥离谓词直至查询返回结果；其次，从该非空结果集采样一元组；最后，运行为何无结果来源工具 [Dietrich et al., 2022] 以识别阻断谓词，并向 LLM 提供此来源报告，指示其仅重写出错子句。 消融实验包括：(i) One-Shot–k，单次插入所有 k 个谓词，无检查；(ii) Post-Order（无来源），遵循相同构建但跳过修复循环。 图3展示了基于来源的精炼整体过程。来源反馈将谓词 salary > 800000 放宽为 salary > 600000。

3.4 问题自然语言化 对每个可执行 SQL 查询 q<sub>SQL</sub>，我们使用 AST-ICL [Al Lawati et al., 2025]（一种 SOTA LLM 基于 SQL 到文本的模型）生成对应自然语言问题 q<sub>NL</sub>。 我们采用 LLM 基于模型而非模板方法，因后者受限于僵化与对手工模板的依赖 [Iyer et al., 2016; Xu et al., 2018]。 在 AST-ICL 中，SQL 抽象语法树作为上下文示例提供，模型生成与查询语义一致的流畅问题 q<sub>NL</sub>。 在 D 上执行 q<sub>SQL</sub> 得到答案 a，完成基准对 (q<sub>NL</sub>, a)。 每个实例因此可解释、可执行，适用于探测混合（表格+文本）数据上的多跳推理。 自然语言化的问题由三名具备 SQL/模式素养的计算机科学研究生验证与修正，以确保事实性与意义性。此过程轻量，所需工作量远低于全手动标注。具体而言，验证 3,300 个查询总耗时约 1,493 分钟，而 HybridQA 创建同等数量查询需约 6,600 分钟。

4 实验 4.1 评估设置 硬件与软件设置。 实验在配备 Intel(R) Xeon(R) Gold 6230 CPU @ 2.10GHz、1.5 TB RAM、Ubuntu 22.04.4 及 4 块 RTX A6000 GPU 的机器上进行，LLM 推理通过 SGLang [Zheng et al., 2024] 推理引擎管理。 我们使用 Llama-3.1-70B-Instruct [Dubey et al., 2024] 作为 LLM。

查询生成方法。 对非嵌套查询生成，SPARTA 默认为 Execution-Guided 生成：LLM 按标准顺序编写每个子句，执行部分查询，并立即修正使结果为空的子句。 作为消融，我们还评估：(i) One-Shot，仅基于模式一次性生成整个查询；(ii) Clause，顺序构建查询但无执行反馈。 对嵌套查询生成，SPARTA 默认为 Post-Order+Prov：已验证叶节点逐谓词封装（后序）；每个新谓词立即执行，若为空则以来源反馈修复。 消融包括：(i) One-Shot–k，单次插入所有 k 个谓词，无中间检查；(ii) Post-Order（无来源），遵循相同后序构建但无来源驱动修复。 我们在 NBA 领域（配置如表10）每种方法生成 500 个非嵌套与 600 个嵌套 SQL 查询，以公平比较质量与成本。

表格-文本 QA 方法。 为评估当前 SOTA 系统在 SPARTA 更深跳数、更大表格及高级分析操作下的表现，我们评估 SOTA 表格-文本 QA 方法，包括基于 LLM 提示的方法，如 ODYSSEY [Agarwal et al., 2025] 和 HProPro [Shi et al., 2024]。 这些模型在 HybridQA 上表现强劲，其中模型对提供表格与链接文档进行推理。 ODYSSEY 构建表格与链接文档的图，使 LLM 可遍历图以获取查询答案。 HProPro 通过 LLM 生成并执行程序以产生查询响应。 因现有表格-文本 QA 方法原未设计支持单模态跳转，我们在 SPARTA 评估时施加最小扩展以启用此行为。 具体而言，对 ODYSSEY，我们通过添加共享连接关系列的匹配单元格间边来增强混合图。 对 HProPro，我们通过将输入表格替换为相关表格列表来调整提示格式。 在无任何 oracle 的全端到端场景中，我们将表格-文本 QA 方法与 HELIOS [Park et al., 2025]（OTT-QA 上的顶级检索器）配对，使模型必须同时检索证据并对其进行推理。 我们还以 GPT-5 和 GPT-3.5-turbo 为主干运行每种方法，以测试 LLM 敏感性。

5 结论 总之，我们提出 SPARTA，一种基准生成框架，通过 (i) 将异构证据统一于参考事实数据库，(ii) 生成逻辑深度高、类似人类的 SQL 嵌套查询（其跳数与分析操作通过来源引导的 LLM 流水线显式控制），及 (iii) 使用 LLM 基于 SQL 到文本模型将其自然语言化，并辅以轻量级人工验证以确保流畅性与正确性，从而纠正现有表格-文本 QA 资源的三个关键缺陷——浅层问题设计、标注噪声与玩具级表格。 在 SPARTA 上，曾在 HybridQA 上达 70+ F1 或在 OTT-QA 上达 50+ F1 的最先进模型，性能下降超 30 F1 分，暴露了当前跨模态推理的根本性缺陷。

6 局限性与未来工作 SPARTA 当前聚焦于表格-文本设置。未来工作将通过使用视觉-语言模型将视觉内容总结为原子陈述、将其规范化为支撑表并合并至现有事实数据库，将其扩展至图像与视频等多模态输入。由于这些元组遵循与 D 相同的模式，查询生成流水线（§3.3）保持不变。完整的多模态扩展（包括数据集收集、模式设计与评估）计划在未来研究中进行。

错误的数据分析。 相较先前基准，SPARTA 引入更复杂的分析要求，暴露了模型能力的局限： • 未能执行高级分析操作：模型在正确应用聚合（如 COUNT, MAX）或执行多表连接时遇到困难。这些操作需要精确对齐关系结构与逻辑，常被误处理。 • 阅读理解错误：模型错误解释文本信息，导致错误答案。例如，在问及掘金队投篮命中率的问题中，模型错误地从句子“Nuggets held Sacramento to just 37 percent from the field”中提取“37%”，并将萨克拉门托的统计数据错误归因于掘金队。详见图11的错误示例。
