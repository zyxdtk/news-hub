周一上午，Cursor 开始向付费用户推出其自有的代码托管平台 Origin。大约三个半小时后，GitHub 的状态页面亮起红灯，随后演变成一场长达 6 小时 42 分钟的全球性服务降级——根据 GitHub 的事件日志，拉取请求、问题和 API 的错误率接近 20%，存档和原始文件下载的错误率接近 50%。企业单点登录也随之瘫痪：SAML、OIDC、SCIM 配置和 Team Sync 全部失效。Copilot 也未能幸免。

开发者互联网做出了它一贯的反应。

“你现在可以在 Cursor Origin 中托管你的代码库，并通过 Cursor Origin 部署到 Vercel，而 Cursor Origin 本身就托管在 Vercel 上，”Vercel 首席执行官 Guillermo Rauch 在 X 上发帖称。“而且与 GitHub 不同，它是在线的 😁” 当被问及为何微笑时，Rauch 回答说：“想对这种情况轻松一点。我们自己现在也被 GitHub 卡住了！”

在 Cursor 工作的 Matt Palmer 引用了自己公司的推文并附上了当天最精彩的评论：“我们本来打算早点发布这个，但 GitHub 宕机了。”换句话说，GitHub 的宕机延迟了一个 GitHub 竞争对手的发布。

产品发布通常会在几周前就锁定，没有证据表明 Cursor 是故意选择这个时机的。但这个巧合给公司带来了巨大的好处，因为它戏剧化地强化了 Origin 存在的意义。十八年来，选择在哪里托管团队的源代码一直是工程组织做出的最无趣的决定。Cursor 押注 AI 智能体让这个决定再次变得有趣——对于技术决策者来说，这才是真正的新闻。不是一个新产品，而是一个伴随着治理问题的新采购问题。

Origin 内部：Cursor 的代码托管平台实际做了什么

Origin 位于 Cursor 内部一个新的“代码库”选项卡中。团队命名一个代码库，它成为其 URL 的一部分，然后通过命令行推送到该代码库。从那里，他们获得了你期望从代码托管平台得到的机制——包装 Git 并处理存储、权限、检查和合并的服务层。每个存储库都带有拉取请求：时间线、提交、检查和文件更改。审阅者可以阅读差异、留下评论并合并，而无需打开浏览器标签页。

Cursor 围绕该机制构建的部分才值得研究。智能体现在与它们正在修改的代码和拉取请求在同一个界面中运行。“你的代码、PR 和智能体现在都在同一个地方，”更新日志写道。开发者可以就屏幕上的文件提问，将评论交给智能体并让它就地修改拉取请求，或者告诉它推送一个分支——所有这些都在编写代码的编辑器中完成。

首日发布了三项集成，合作伙伴的选择很能说明问题。其开发者账号表示，Vercel 为每个拉取请求启动一个预览部署，并在合并时部署到生产环境，该功能已向 Pro 和 Enterprise 客户开放公开测试版。Depot 和 Buildkite 运行持续集成，关键是，两者都原封不动地执行现有的 GitHub Actions 工作流。Buildkite 还在此基础上添加了原生管道。

这个兼容层就是整个战略的缩影。Cursor 并没有要求团队重写他们的构建系统、重新培训工程师或拆除他们的部署管道。它只是要求他们尝试为已有的代码开一扇“第二扇窗”——这是一个更容易获得批准的请求。

该公司表示，更多的合作伙伴正在路上，而它最先敲定的那些合作伙伴，对于评估 Origin 能否承载实际工作的平台团队来说至关重要。一个没有部署和 CI 的代码托管平台只是一个代码查看器。一个能运行你现有的 Actions 工作流并将预览发布到你已经在付费的 CDN 上的托管平台，才是一个候选者。

为什么让 GitHub 继续作为事实来源是 Origin 最明智的设计选择

这是企业买家应该最仔细研究的决定，因为它决定了 Origin 能否通过安全审查。

Cursor 不要求你离开 GitHub。连接一个 GitHub 组织，选择存储库，它们就会与 Origin 原生存储库一起出现。“推送继续发送到 GitHub，GitHub 仍然是任何在那里开始的东西的事实来源，”更新日志说。访问权限镜像了 GitHub 现有的读写设置，而不是建立一个平行的系统。拉取请求的对话是双向同步的——在 Cursor 中评论，它会发布到 GitHub；在 GitHub 上回复或做出反应，它会在“几秒钟内”出现在 Cursor 中。

这是一个经典的楔子，而且执行得很好。源代码控制的“替换式”迁移是工程组织所能承担的风险最高的项目之一。它涉及持续集成、合规性证据、审计跟踪、分支保护规则、工具链中的每个集成以及每个工程师的肌肉记忆。几乎没有首席技术官会为一个处于早期测试阶段的产品批准这样做。

一个让 GitHub 保持权威的“以读为主”的镜像会自动获得批准。尝试它没有任何成本，放弃它也不会破坏任何东西，并且悄悄地转移了开发者花费工作时间的地方。如果 Cursor 的审查体验被证明更好——Cursor 花了真金白银来确保这一点——事实来源最终会跟随注意力转移。

这笔钱花在了 Graphite 身上，这是 Cursor 在 2025 年 12 月收购的代码审查初创公司，据 Axios 报道，收购价格远高于其 2.9 亿美元的 B 轮估值。Graphite 构建了堆叠式拉取请求，这种工作流允许开发者在不等待批准的情况下继续发布依赖更改。在宣布这笔交易时，Cursor 写道，“编写代码的地方和协作代码的地方之间的界限感觉越来越随意”，并承诺“还有一些我们目前还不能分享的更激进的想法”。Origin 就是这个激进的想法。Graphite 联合创始人 Tomas Reimers 在 6 月于 Cursor 首届 Compile 大会上在舞台上发布了它，并领导其开发。

AI 智能体如何将代码审查变成软件的新瓶颈

一个为智能体原生构建的代码托管平台的理由建立在一个很容易陈述、且对于这个市场来说不寻常地有充分证据支持的主张上：编写代码不再是约束条件。审查和集成代码成为了约束。

谷歌的 2025 年 DORA 报告调查了近 5,000 名技术专业人士，发现 90% 的开发者现在在工作中使用 AI，每天与它共度的时间中位数为两小时，超过 80% 的人表示它提高了他们的生产力。但 AI 的采用与软件交付吞吐量呈正相关，与交付稳定性呈负相关。产出更多，破坏也更多。报告作者将 AI 描述为“一个放大器”，“放大了高性能组织的优势和挣扎中的组织的功能失调”。

信任并没有跟上产量的步伐。Stack Overflow 的 2025 年开发者调查覆盖了 177 个国家的 49,009 名受访者，发现 84% 的人正在使用或计划使用 AI 工具，而对其准确性的信任度从一年前的 43% 下降到 33%，不信任度从 31% 上升到 46%。三分之二的人将“几乎正确但又不完全正确的 AI 解决方案”列为他们最大的挫败感。GitLab 的第九次年度 DevSecOps 调查（由 Harris 调查了 3,266 名从业者）用数字说明了运营拖累：73% 的人遇到了“凭感觉编码”输出的问题，70% 的人表示 AI 使合规管理变得更加困难，只有 37% 的人愿意在没有人工审查的情况下让 AI 处理日常任务。

无论如何，产量都在攀升。GitHub 的 Octoverse 2025 统计了 1.8 亿开发者、6.3 亿存储库和每月合并 4320 万个拉取请求，同比增长 23%。而 RuntimeWire 报道了最能解释 Origin 存在原因的内部数据：在 Cursor 内部合并的拉取请求中，有 35% 是由在云虚拟机中自主运行的智能体开启的。

一个为人类构建的代码托管平台假设拉取请求代表人类的意图，是由一个你可以询问其意图的人开启的。一旦三分之一的合并更改来自软件，队列就不再是一场对话，而变成了一个调度问题。这是一个真正的架构论点，也是 Cursor 目前拥有的最强有力的论点。

GitHub 的可靠性危机给了 Cursor 一个它不需要费力就能获得的机会

替代方案的供给侧理由更简单：GitHub 一直不可靠，而且它自己的高管也这么说过。

LeadDev 的一项分析统计了 2025 年 5 月至 2026 年 4 月期间的 257 起事件，其中 48 起是重大事件——大约每周发生一次重大中断。2 月是有记录以来最糟糕的月份，发生了 37 起。仅 GitHub Actions 在十二个月内就造成了 57 次宕机。首席技术官 Vlad Fedorov 曾表示，该平台“不是为它现在被要求处理的规模而构建的”，必须为今天负载的 30 倍进行设计。在 InfoQ 报道的一篇 4 月份的工程文章中，该公司承认其“未能达到自己的可靠性标准”，理由是快速增长、紧密的架构耦合和负载削减不足。周一的宕机是 GitHub 状态页面在十五天内的第七起事件。

疲劳感是显而易见的。“GitHub 真的不像是为智能体时代构建的，”一位开发者在 Origin 上线时在 X 上写道。“它宕机的频率太高了，但直到现在还没有太多真正的替代方案。”

在 Origin 出现之前，叛逃就已经开始了。Zig 编程语言于 2025 年 11 月迁移到 Codeberg，理由之一是 Actions 故障。4 月，Mitchell Hashimoto 宣布 Ghostty——一个拥有超过 52,000 个星标的终端模拟器——也将离开，他指出几乎每天都会发生宕机，导致审查和 CI 中断数小时。The Information 在 3 月份报道称，微软持有大量股份的 OpenAI 开始构建自己的 GitHub 替代方案，部分原因是宕机导致其工程师一次无法提交代码长达数小时，正如 Tom's Hardware 转载的那样。

微软的结构也于事无补。Thomas Dohmke 于 2025 年 8 月辞去 GitHub 首席执行官一职，且从未被替代；该部门的领导层被并入由执行副总裁 Jay Parikh 领导的微软 CoreAI 组织。在 5 月份的一份报告中，The Information 写道，Parikh 曾警告副手们，来自 Cursor 和 Anthropic 的编码工具最终可能会让 GitHub 淘汰。GitHub 自己对智能体时代的回应是 Agent HQ，它允许客户在 GitHub 内部编排来自 Anthropic、OpenAI、Google、Cognition 和 xAI 的第三方智能体——这是一个连贯的战略，让出了智能体层，但保留了底层的基石。Origin 攻击的正是那个基石。

既然 SpaceX 现在拥有了 Cursor，谁实际掌握着你的源代码？

即使按照这个周期的标准，Cursor 的崛起也是非同寻常的。由四名麻省理工学院学生于 2022 年创立的 Anysphere 于 2023 年 10 月从 OpenAI 创业基金获得了 800 万美元，据 TechCrunch 报道，随后是 25 亿美元估值的 1 亿美元、99 亿美元估值的 9 亿美元，以及去年 11 月 293 亿美元估值的 23 亿美元。5 月，彭博社报道其年化收入达到 30 亿美元，有超过 3,000 个客户每年至少支付 10 万美元。

然后，在 Origin 发布的三天前，彭博社报道 SpaceX 完成了对 Cursor 600 亿美元的全股票收购——TechCrunch 在 6 月份报道了这项协议，就在 SpaceX 创纪录的 IPO 之后几天，以及它吸收 xAI 六个月之后。Cursor 现在在一个名为 SpaceXAI 的部门内运营。上周五，要求持有你专有源代码的供应商变成了一家火箭公司的下属部门，该公司拥有自己的前沿模型部门，且其创始人并不以机构谨慎著称。

Moor Insights & Strategy 的 Jason Andersen 在 6 月份交易完成前向 Tech Times 提出了模型路由问题：“xAI 的模型和护栏处理方式与 Cursor 一直以来的立场大相径庭。”那篇文章提出了首席信息安全官现在必须回答的问题。当一家公司同时控制着智能体编写代码的编辑器、代码所在的宿主以及这些智能体运行的模型时，什么来治理它对代码的处理？

Cursor 尚未公布答案。RuntimeWire 在发布前指出，Origin 的定价、安全架构、数据处理条款和迁移工具均未公布，而周一的更新日志也没有增加任何内容。它只是说 Origin 从今天开始面向“所有付费计划用户，除非企业管理员选择退出”。是选择退出，而不是选择加入——这句话管理员应该读两遍。

还有一个过往记录需要权衡。7 月，Mindgard 的研究人员披露，当用户打开一个 Windows 项目根目录中植入的恶意 git.exe 时，Cursor 会立即执行它，且没有任何提示——这是一个他们在 2025 年 12 月首次报告的存储库投毒漏洞。The Hacker News 报道称，Cursor 拒绝修复它，称该问题在共同责任模型下超出了范围，同时承认没有“及时与研究人员闭环”。没有发布 CVE。同样的漏洞类别在 GitHub Copilot CLI、Google 的 Gemini CLI 和 OpenAI 的 Codex 中也未修复——但供应商拒绝修复的漏洞，对于一个基本宣传语是“让我们持有你的存储库”的产品来说，是一个尴尬的脚注。

工程领导者在让 Origin 进入工具链之前应该解决的问题

Origin 是一个测试版，而不是一次迁移，作为测试版，它值得评估。同步模式为平台团队提供了一种低风险的方法，以衡量原生于智能体的审查界面是否缩短了周期时间，而无需触及任何一条分支保护规则。但在任何权威性的东西转移之前，有三件事需要解决。

第一是默认设置。除非企业管理员选择退出，否则 Origin 会对付费用户开启，这意味着一个尚未就是否可以将专有代码镜像到新宿主做出明确决定的组织，实际上已经有人替它做出了决定。确认你的姿态是周一早上的任务，而不是下个季度的任务。

第二是书面文件。数据保留、驻留、训练使用、子处理器以及 Cursor 向 SpaceX 汇报后发生了什么变化，这些都未公布，而且产品页面不是合同。在这些条款以书面形式存在之前，站得住脚的立场是将 Origin 视为 GitHub 之上的便利层，而不是记录系统——巧合的是，这正是它的架构已经是的样子。

第三是退出机制。Origin 的 Actions 兼容性及其以 GitHub 为事实来源的设计是使其可以安全采用的属性。随着 Cursor 的激励转向拥有基石而不是借用基石，它们也是最有可能被侵蚀的属性。趁着镜像还是镜像的时候，问问现在的出口是什么样的。

这些都没有让 Cursor 的论点变得错误。GitHub 通过作为无聊、可靠的基础设施赢得了其 incumbency，而在过去十八个月里，它两者都不是，同时到达其前门的代码有三分之一不再由人类编写。Origin 是对一个真实问题的严肃回答，由一个购买了合适的公司来构建它的团队打造。

但 GitHub 的失败和 Cursor 的失败在性质上是不同的，企业不应将它们混淆。

周一的宕机在 UTC 时间 20:22 解决。可用性是一个工程问题，而工程问题是会闭环的。关于谁持有你的源代码、他们可能用它做什么以及他们最终向谁负责的问题，却没有这样的时间戳——而在那个问题上，周一花费时间推销信任的公司尚未公布其条款。
