直到最近，从商业文档中提取结构化数据都是由人类完成的：知识工作者阅读财务报表、保险理赔单、采购订单和政府表格，然后将相关数值键入记录系统以供下游工作流使用。这项工作通常高度手动且重复，任何错误都可能代价高昂 [18, 5]。随着大型语言模型和自主智能体的最新发展，我们看到企业对部署智能体以完成历史上由人类执行的以抽取为重点的文档工作流的需求迅速增长。

模式定义是抽取工作流的核心。一个模式定义了一个抽取任务，在同一类型的所有文档中共享。例如，一个发票模式涵盖了来自每个供应商的发票，无论每张发票的外观有多大差异。鉴于企业几乎为每个新工作流编写新模式，系统不能仅针对一个固定模板进行调优。

我们将抽取任务定义为模式引导抽取（在第 2.1 节中精确定义）：给定一个文档和用户定义的模式作为输入，智能体忠实地遵循模式以产生正确的输出以及作为溯源元数据的来源证据。

在企业面临的现实用例中，抽取工作流存在许多挑战来源和失败案例，常见的包括长列表中缺失行、选择了稀疏事实的错误出现、过度填充密集表单，以及混淆相似的日期、标识符或金额。在准确理解文档结构方面也存在特殊挑战，我们称之为感知挑战：扫描或手写噪声、分层标题、跨页延续以及大型或不规则表格。

长度造成了另一个独立的问题：系统可以正确读取局部值，但仍然会截断长附表。视觉溯源和可追溯性是使智能体驱动的抽取在企业生产规模上有效且可靠的另一个关键要素。鉴于总是存在不可避免的失败——例如，当智能体在核对基金持仓时失败，因为长附表被截断且输出中缺失了行——这需要人工介入循环，使用视觉溯源信号来快速识别和纠正问题。

此外，在生产量级下，每页的抽取成本也很重要 [23]。在海量、文档密集的企业工作流中，每页一美分的成本差异可能决定一个 AI 项目在财务上是否可行。

尽管现有的多个基准尝试应对这一挑战，但它们都有关键局限性（表 1；第 4 节和第 A.4 节给出了详细比较）。经典的信息抽取使用特定任务系统填充固定的、手工构建的模板 [16]。固定的 KIE 基准，如 SROIE [19] 和 DocILE [39]，不处理用户指定的模式。更近期的模式引导基准 [12, 4] 仅覆盖了问题的一个狭窄维度。三个最接近的基准各自覆盖了这些要求的一部分：针对企业规模模式的符合模式的 JSON [12]、合成渲染数组上的行完整性 [9]，以及长篇统计报告和报表 [26]。这三个基准都没有测量成本、对溯源进行评分，或包含扫描或手写文档。例如，Contextual AI 的 ExtractBench [12] ^1 不包含任何手写文档，也没有考虑视觉溯源或成本。

^1 Contextual AI 的不相关学术基准共享了 ExtractBench 名称 [12]；第 4 节详细说明了两者在范围上的差异。

为了弥合这一差距，我们引入了 ExtractBench，这是一个用于模式引导企业文档抽取的综合基准，它具有广泛的任务覆盖范围，评估可追溯性并测量成本。ExtractBench 包含跨越 8 个业务领域和 67 种文档类型的 370 份文档（4,869 页）。每种文档类型在其所有文档中共享一个模式。每份文档都按任务挑战、感知挑战、表格结构、领域和长度进行标记（第 2.2 节）。该基准由原生数字文档、基于真实布局的合成长列表以及带有从空白模板编写的模式的真实监管和税务表格组成。

为了大规模建立高质量的基准真值，我们设计了一个可扩展的流程：对真实文档进行独立系统提议的裁决，对合成列表在渲染前设定值，由人工验证扫描表格上的值和溯源（第 2.3 节）。我们使用对抽取 JSON 中值不敏感的顺序值 F1 来评估准确率。为了评估视觉溯源能力，我们还对具有人工验证框的字段中正确的值是否指向其来源进行评分，以便审阅者无需搜索文档即可审核答案（第 2.4 节）。

我们评估了涵盖商业 VLM、开源抽取、编码智能体和专用 API 的 14 种前沿方法。我们注意到开箱即用的前沿模型在不同挑战维度上存在显著的性能差异。例如，Gemini 3.5 Flash 的准确率从短文档的 87.9% 骤降至长文档的 27.9%（第 3 节）。LlamaExtract Agentic Plus 表现出更加一致的性能，短文档和长文档的准确率分别为 96.6% 和 94.4%。它还在成本低得多的情况下（8.1 ¢/页 vs 27.8 ¢/页）优于 Codex GPT-5.5（95.6% vs 93.6%）。此外，商业 VLM 和编码智能体不返回词级框，因此需要源证据的工作流需要专门的抽取 API（第 3.4 节）。

我们的贡献包括：
• 具有广泛覆盖范围的挑战标记基准。370 份文档和 4,869 页涵盖了 8 个业务领域和 67 种文档类型，带有任务挑战、感知挑战、表格结构、领域和长度的标签，支持逐挑战分析。
• 用于模式和基准真值整理的可扩展流程。为了在无需手动标记每个字段的情况下生成高质量、规范明确的模式-基准真值对，我们结合了用于真实文档的前沿模型集成、用于合成长列表的程序化生成以及用于扫描表格的人工验证。
• 对前沿抽取方法的广泛评估。我们比较了涵盖商业 VLM、OSS 流水线、编码智能体和专用 API 的 14 个系统，报告了准确率、溯源、成本以及质量-成本权衡。

2 ExtractBench
本节精确定义模式引导抽取，然后描述 ExtractBench 如何应用它来构建一个挑战标记的语料库。

2.1 任务定义
给定一个文档和一个模式，系统返回带有证据的结构化数据（图 1）：
f: (document, schema) ⟼ (structured data, evidence).

输入。输入是一份完整的文档（原生数字或扫描件）以及用户编写的模式。用户通过模式指定抽取任务：它列出了要抽取的字段，每个字段都有一个名称、一个类型以及关于其内容的自然语言描述。它表示为 JSON Schema，即指定结构化输出的行业标准方式，可能包含标量字段、嵌套对象、记录数组、可空字段和值约束。一个模式定义了一个抽取任务，并指导所有相同类型的文档，即使这些文档在结构、布局和样式上可能存在显著差异。例如，来自不同提供商的保险理赔单在长度和布局上差异很大。文档通常包含比模式要求更多的内容——有时则更少：文档未作回答的任何字段必须返回为 null。

输出。输出是一个模式有效的 JSON 对象，带有每个值的源页面和边界框作为证据。它必须返回正确、详尽的值（包括重复记录），对缺失信息正确使用 null，并为每个抽取的值提供溯源。第 2.4 节明确了这些期望。

2.2 分类法和覆盖范围

图 1：ExtractBench 在五个标签轴上的覆盖范围。每个条形表示 370 份文档中带有该标签的比例，文档数量显示在条形旁边。任务面板报告了三个任务挑战；一个带有某个挑战多个子标签的文档只计算一次。标签可能在面板间重叠；表 4（第 A.1 节）定义了每个标签和子标签。

现有的文档抽取基准通常在狭窄的文档类型集上报告一个总分。总分不能显示系统是漏掉了列表的三分之一还是弄错了一个标签，也无法区分困难的抽取任务和糟糕的扫描件。ExtractBench 则沿着五个独立的轴对每份文档进行标记：任务挑战（什么使抽取变得困难）、感知挑战（页面是如何被捕获的）、表格结构、长度和业务领域。由于这些轴是独立的，低分可以追溯到其实际原因。图 1 显示了语料库在这五个轴上的分布。以下段落简要解释了每个轴；第 A.1 节的表 4 给出了每个标签的额外细节和代表性文档类型。

任务挑战。任务挑战定义了抽取任务的本质及其困难之处。
• T1：长列表完整性。恢复可以跨越多页的重复结构的每一条记录。典型的失败是截断、重复或合并的行、幻觉记录以及附加到错误记录的值。
• T2：大海捞针。在长文档中寻找少量请求的事实。T2 的目标记录很少，但有很多看似合理的提及，其中只有一个是规范的；失败是遗漏目标、错误的出现以及未规范化的释义。它也是唯一一个要求远少于文档内容的任务挑战：每页中位数仅 1.6 个字段（第 A.1.1 节）。
• T3：密集文档。从充满标签、空白、复选框、手写和扫描伪影的文档中填充许多字段。特征性失败是过度抽取，即为实际上为空白的字段发明一个值，并因遗漏复选框和误标字段而加剧。密集文档还会重复相同格式的标识符、日期和金额，因此一个看似合理的值可能会落入错误的字段。密集表单是最常见的情况（T3.a）；收据、发票和监管报表也属于此类。

感知挑战。感知挑战记录了页面是如何被捕获的。标签为旋转或仅图像捕获（P1）、扫描页面图像（P2）和手写（P3）（表 4）。它们的分配独立于任务挑战，因此相同的抽取任务可以出现在多个感知挑战下。

表格结构。表格拥有一个专门的轴，原因有二。首先，企业抽取的大部分值存在于表格中，从持仓附表到发票行项目。其次，表格的失败方式是其他页面元素所没有的：一个复杂的表格可以逐值正确读取，但仍然被组装成错误的结构，这是任务和感知轴无法隔离的失败。结构标签标记了发生这种情况的布局：合并或分层标题（S1）、不位于其数据上方的标题（S2）、跨页延续的表格（S3）、超过一千行的表格（S4）以及打包在单个单元格内的表格（S5）。每种布局都有其自身的失败模式：合并标题将值附加到错误的列，透视标题转置了记录，跨页表格失去了延续性，超大表格提前停止，打包单元格作为一个字符串返回而不是其字段。

文档长度。文档分为三个长度区间：短（L1，最多 10 页），中（L2，11 至 50 页）和长（L3，超过 50 页）。长度拥有自己的轴，原因与其他轴分离相同：相同的任务挑战可以出现在任何长度，并且长度增加了自身的失败模式，因为系统可以正确读取页面上的每个值，但仍然在长附表结束前停止。

业务领域。企业抽取系统需要跨领域工作，原因有二：团队希望有一个系统，而不是每种文档类型一个单独的工具；企业通常无法控制收到的内容，必须处理客户、供应商和监管机构发送的任何内容。因此，ExtractBench 跨越了 8 个领域和 67 种文档类型（表 4）：金融和基金持仓（D1）、能源部门监管表格（D2）、政府采购和海关（D3）、汽车估值（D4）、供应链和其他交易文档（D5）、医疗保健汇款（D6）、法律和破产申请（D7）以及房地产结案披露（D8）。先前的结构化抽取基准通常覆盖较少的领域和少数真实文档类型（表 6）。

图 2：基准真值是如何构建的，每种来源类型一个条带。卡片的边框标记了谁运行该步骤（蓝色：抽取模型池；紫色：编码智能体流水线代码；琥珀色：人工）；填充的绿色卡片是生成的基准真值，橙色虚线标记了修复和分歧循环。

2.3 模式和基准真值构建
为了正确评估模式引导抽取系统，抽取任务本身需要被明确定义：每个模式必须与其适用的文档保持一致，并且每个字段都必须有一个明确的期望值。如果模式与其文档族对齐不佳，或者其指令使抽取目标模糊不清，错误将无法归因，低分可能反映的是基准的缺陷而不是被测系统的缺陷。

创建定义明确的模式以及与之对应的基准真值是劳动密集型的，特别是当文档很长且数据密集时。在这种规模下，手动检查每个字段在时间和成本上都是不可行的，而使用单个抽取器的输出作为基准真值会重复其错误并使结果偏向该抽取器。这促使我们采用一个可扩展的流水线，在无需完全手动标注的情况下生成高质量的模式和基准真值对。为此，我们结合了三种文档来源，每种来源由适合它的方法进行标注：用于真实文档的前沿模型集成、用于合成长列表的程序化生成以及用于扫描表格的人工标注器（图 2）。

真实文档提供了我们想要测试的布局、扫描噪声和领域范围，但在其每个字段上画框慢得令人望而却步。合成长列表涵盖了太大而无法手动标注的文档：数千条相似的记录标注起来很慢，而且容易误读。扫描表格是需要人工决定每个值的真实文档，因为手写不清晰，而且标记可能位于两个字段之间。来自这些来源的文档也被重新捕获为降级的扫描件，这不需要新的标注：值不会改变，因此干净文档的基准真值可以直接沿用。我们使用这种方法来构建 ExtractBench，但它很容易扩展到更大的数据集。第 A.3 节给出了完整程序。

模式。文档类型是携带相同类型信息的文档族——SEC 13F 文件、水电费账单、抵押贷款结案披露——无论其布局有多大差异。在 ExtractBench 中，每种文档类型只有一个模式，由其所有文档共享。该模式采用用户在生产环境中编写的形式：字段名称、类型和每个字段的自然语言描述（第 2.1 节）。每个模式是如何编写的取决于其来源，并在下面的每个流水线中进行了描述。每个字段的编写都是为了在文档中具有确定性的期望值，因此无论评估哪个系统，基准真值都是相同的。

真实文档。模式是从样本文档中起草的，然后来自不同模型和流水线系列的几个抽取系统针对这个候选模式运行（图 2，顶部条带）：没有单个抽取器足够可靠，且同系列系统会共享错误。所有系统都同意的值（包括缺失字段的 null）成为候选基准真值。分歧按原因分类：如果对该字段有不止一种合理的解读，则是模式的错误，我们通过别名、格式要求、位置提示和不可混淆指南来收紧其描述，直到重运行收敛；如果只有一种合理的解读，则是模型的失败，由审阅者根据页面解决有争议的单元格。

合成长列表。我们向后构建每个合成文档，先数据后文档，因此基准真值生来就是可信的，并且从未有人工标注过任何值。从真实的文件（基金附表、持仓登记表或债权人矩阵）中，我们生成记录（逐字解析或按其风格生成），以及编码智能体在研究布局的字体、列和页面外观后编写的渲染代码（图 2，中间条带）；该文档族保留真实文件的模式。该代码将记录渲染为与真实文档紧密匹配的 PDF，分页符由测量值放置。每个值在 PDF 存在之前都是已知的，其页面和词级框是从渲染中回读的，因此无论列表增长多长，基准真值都保持精确。机械检查捕获样式不匹配和裁剪，抽取系统池审计完成的文档，其分歧暴露了在文档族发布前修复的渲染代码错误。

2.4 指标
ExtractBench 测量两件事。值准确率询问系统是否返回了正确的值，并使用每份文档的统一值 F1 进行评分。溯源询问系统是否能显示每个值的来源，仅在框基准真值经过验证的文档上进行评分（第 2.3 节）。

值准确率。统一值 F1 评估抽取的值是否与期望输出匹配，在标量字段和记录数组下使用同一个定义。每个输出被展平为单元格，每个标量字段和每个对齐的记录子字段对应一个单元格，当一个单元格在规范化后与其期望的对应项匹配时，该单元格即为正确。每份文档的这些单元格计算精确率、召回率和 F1，切片报告未加权的文档均值（附录 B 给出了确切的评分规则）。
• 数组对齐。重复结构作为无序记录集进行比较：记录通过匈牙利算法进行配对以最小化不匹配的单元格，遵循先前抽取基准对齐行项目和数组的方式 [39]。未匹配的期望记录会降低召回率；额外的预测会降低精确率。
• 规范化。值在比较前进行规范化：日期转为 ISO 格式，字符串通过折叠空白字符；其他所有内容都要求精确相等，没有数值容差，也没有 LLM 裁判。少数例外列于第 B.1 节。
• 缺失值。省略的键被计分为显式的 null，因此每个标量字段都计入精确率和召回率，并且空白字段上的正确 null 会被记入（表 9 列出了所有情况）。只有重复记录会使精确率和召回率产生差异，因此它们之间的差距指向的是丢弃或额外的记录，而不是错误的值（第 D.1 节分别按系统和长度切片列出了两者）。

溯源。对于具有验证过的基准真值框的字段，ExtractBench 还报告词级溯源精确率、召回率和 F1。仅当一个字段的值正确且其预测框与该字段的接受框在固定的 0.5 IoU 阈值下重叠时，该字段才被视为已溯源：围绕错误值放置良好的框不会得分。页级溯源 F1 询问同一问题的较弱版本，仅要求正确的源页面而不是框，许多系统即使在根本不返回框的情况下也能满足这一点。第 B.4 节给出了细节。

3 实验
3.1 设置
我们评估了 14 个抽取系统 ^2，涵盖三种高级方法：
^2 模型和价格反映了截至 2026 年 7 月 1 日可用的模型和价格。

• VLMs 将抽取视为直接的多模态生成：它们接收文档和模式，并在单次模型调用中生成结构化输出。我们评估了通过受限结构化输出 API 调用的 GPT-5.4 Nano [29] 和 Google Gemini 3.5 Flash [13]；以及自托管的 Lift 9B [7]、NuExtract3 [27]、Qwen3.6 35B-A3B [34] 和 Gemma4 26B [14]。
• 编码智能体 通过迭代工具使用循环进行抽取：它们可以检查文档、编写和运行解析代码、验证结果并修改最终输出。我们评估了 Claude Code Opus 4.8 [2] 和 Codex GPT-5.5 [30]，它们接收带有文件系统和工具访问权限的文档和模式（工具配置见第 C.1 节）。
• 专用 API 提供托管的文档工作流，处理预处理、解析和模式引导抽取，有时带有源溯源。我们评估了 Reducto Deep Extract [36]、Extend Max Context [10]、Datalab Accurate Parse + Balanced Extract [6, 8] 以及三个 LlamaExtract 层级 [24]（Cost-Effective、Agentic 和 Agentic Plus）。

所有系统接收相同的文档-模式对，并在没有针对基准特定调优的情况下进行评估；所有运行均在 2026 年 6 月至 7 月进行。我们使用第 2.4 节中定义的指标，报告值 F1、词级和页级溯源 F1 以及成本的未加权文档级均值。每页成本将发布的提供商费率应用于实际的 token 或信用消耗（第 C.2 节）。由于四个自托管的 VLM 没有直接可比的 API 价格，我们在成本比较中省略了它们。

3.2 质量-成本前沿
企业抽取工作负载通常跨越数百万页，使得每页成本的差异变得巨大。在一百万页的情况下，每页每增加一美分就会增加 10,000 美元。图 3 比较了总体值 F1 与测量的每页成本。被评估的系统族占据了这种权衡的不同区域。这里评估的 VLM 占据了质量-成本权衡的低成本区域（≤ 1.0 ¢/页），但都没有超过 80% 的 F1。编码智能体达到 87-94% 的 F1，但成本超过 15 ¢/页。专用 API 跨越的范围要广得多。在该组中，LlamaExtract 描绘了质量-成本前沿：Cost-Effective 在 1.0 ¢/页时达到 86.8% 的 F1，Agentic 在 3.1 ¢/页时达到 89.5%，Agentic Plus 在 8.1 ¢/页时达到 95.6%。Agentic Plus 优于两个编码智能体，而成本不到它们的一半。这些结果表明为什么必须联合评估抽取质量和成本：更多的花费不一定会产生更高的准确率。第 D.3 节提供了商业 VLM 的更广泛比较。

3.3 跨维度结果
总体 F1 使得比较系统变得容易，但单个总分无法显示哪些文档特征驱动了它们的成功和失败。为了暴露这些失败模式，我们使用 ExtractBench 的挑战标签将性能分解到五个轴上：文档长度、任务挑战、感知挑战、表格结构和业务领域（表 2）。

文档长度。大多数系统在短文档上表现良好，超过一半的系统得分在 90% 以上，但随着文档变长，差距会扩大。在长文档上，商业 VLM 降至 40% 以下，而 Claude Code Opus 4.8（88.1%）和 Reducto Deep Extract（92.0%）保持接近其短文档的得分。LlamaExtract Agentic Plus 在所有三个长度上都是最强的，并且从未跌破 90%（96.6/93.3/94.4）。长文档的失败集中在召回率上：整个记录被丢弃而不是被误读（第 D.1 节分别报告了精确率和召回率）。我们将其归因于上下文限制：大多数系统无法在单次传递中处理完长文档，而那些没有迭代处理策略的系统会提前停止，截断剩余的记录。

任务挑战。长列表完整性（T1）和大海捞针（T2）反映了文档长度的结果：LlamaExtract Agentic Plus 和 Reducto Deep Extract 是这两个挑战上排名前二的系统。密集文档（T3）重新排列了排名。这个挑战将许多字段集中到一个大型模式中，处理此类模式较差的系统会落后：Reducto Deep Extract 降至 87.5%，Claude Code Opus 4.8 降至 82.4%，Datalab Accurate Parse + Balanced Extract 降至 54.4%。LlamaExtract Agentic Plus（95.5%）和 Codex GPT-5.5（95.4%）在该挑战上领先。第 D.2 节分别报告了每个子标签。

感知挑战。感知轴暴露了系统特定的盲点。Codex GPT-5.5 处理旋转或仅图像捕获（P1）的能力较差，从其他感知挑战上的大约 93% 降至约 80%。Reducto Deep Extract 表现出互补的弱点：它在旋转或仅图像捕获和手写（P3）上保持在 90% 以上，但在扫描页面（P2）上降至约 81%。Qwen3.6 35B-A3B 在扫描页面和手写方面比其他 VLM 更强，两者得分均在 92% 以上。LlamaExtract Agentic Plus 仍然是所有三个感知挑战中最强的系统。

表格结构。超大表格（S4，超过一千行）在表 2 中产生了最尖锐的分离。大多数系统提前停止并仅返回一小部分记录：每个 VLM 在该切片上的得分都低于 10%，Datalab Accurate Parse + Balanced Extract（32.7%）和 Extend Max Context（24.8%）也急剧下降。相比之下，LlamaExtract Agentic Plus（95.9%）、Reducto Deep Extract（95.3%）和 Claude Code Opus 4.8（87.8%）是排名前三的系统。跨页表格（S3）构成了相同失败的一个较温和版本，其困难在于在分页符处保持表格结构。透视布局（S2）是结构切片中区分度最小的，因为大多数领先的系统都能很好地处理它们。

业务领域。领域难度很大程度上反映了每个领域内任务挑战的混合（表 2）。金融（D1）和政府（D3）带有长列表（T1）和大海捞针（T2）任务；能源（D2）以扫描的密集表单（T3）为主；法律（D7）和医疗保健（D6）包含长记录列表，包括债权人矩阵、制裁名单和临床事件日志。因此，一个领域的得分主要是其任务挑战结果的重加权，我们将领域轴视为对覆盖范围的检查，而不是独立的困难来源。

3.4 溯源差距
溯源通过让审阅者将每个预测值追溯其来源，使抽取变得可审计。ExtractBench 明确测量了这种能力，而现有的模式引导抽取基准忽略了它（表 1）。我们仅当抽取的值及其引用都正确时（在页面或词级别），才认为一个字段已溯源。我们在表 3 中强调了溯源差距。
• VLMs 和编码智能体 默认不返回证据；因此它们在两个溯源级别上的得分均为零。需要可审计输出的用户必须添加一个单独的证据定位组件，或者使用内置溯源的抽取 API。
• 粒度挑战。定位确切的单词比找到正确的页面更具挑战性。LlamaExtract Agentic Plus 实现了 84.9% 的页级溯源 F1，但词级 F1 仅为 46.4%。Datalab 显示出更大的差距，为 48.5% 对比 2.0%。页面证据缩小了搜索范围，但仍然留给审阅者在相似的候选者中定位该值。
• 对长度的鲁棒性。Extend Max Context 的页级溯源 F1 从短文档的 61.7% 降至长文档的 0.0%，Datalab 也遵循相同的模式。Reducto Deep Extract 更稳定，从 72.6% 降至 67.3%，而 LlamaExtract Agentic Plus 仍然是总体上最强的系统。

即使是最好的总体词级溯源 F1 也保持在 50% 以下。系统越来越能够抽取值并经常识别其源页面，但可靠地将每个值与其确切的支撑证据连接起来仍然是一个开放问题。

4 相关工作
4.1 文档抽取基准
文档抽取基准涵盖两种主要设置：固定本体抽取（其中字段是预先定义的）和模式引导抽取（其中用户在推理时提供定义字段和输出结构的模式）。我们简要回顾这两种设置。

固定本体文档信息抽取。固定本体基准询问当文档变得更具挑战性时，系统能多可靠地恢复已知的一组字段。它们逐步将文档多样性从表单和收据扩展到多语言布局和企业领域 [21, 19, 33, 44, 42]。其他工作通过行项目、表格、长文档和不熟悉的模板增加了结构和上下文的复杂性 [43, 39, 40, 17, 20]。一些基准还额外标注了空间位置或研究定位 [39, 41]。然而，在这些设置中，目标字段仍然由基准固定：它们测试的是已知本体内部的鲁棒性，而不是系统是否能遵循用户提供的新的模式。

模式引导抽取基准。最近的文档抽取基准集中在模式引导设置上，用户在推理时指定抽取任务而无需重新训练系统 [12, 38, 22]。该设置中的工作逐步增加了任务规模和复杂性，测试了更复杂的模式、更长的文档和更大的输出。ContextualAI 的 ExtractBench [12] 强调模式复杂性，模式包含多达 369 个字段，但仅评估了五个共享模式；LongExtractBench-50 [26] 和 VAREX [4] 对每个文档使用不同的模式，因此它们不测试一个抽取任务是否能跨多样化的文档外观进行迁移。LongArray-Extract [9] 和 LongExtractBench-50 [26] 相反，强调长文档和重复记录上的完整性，尽管它们的公开测试集仅包含几十份文档。几个基准 [4, 22, 9] 使用合成构建来扩展这些评估，但生成的文档无法捕捉真实企业数据中的视觉可变性和感知挑战。这种碎片化的覆盖使得难以全面比较系统族或诊断它们失败的原因。据我们所知，ExtractBench 提供了这些维度最广泛的组合覆盖，跨越了 8 个业务领域的真实文档族和有针对性的合成压力测试（表 1）。ExtractBench 围绕大规模的生产要求设计，联合测量值准确率、源溯源和每页成本，以捕获输出是否正确、可追溯且生产经济。我们还使用挑战标签对数据集进行分层，以确保覆盖任务和感知困难，并诊断不同系统族失败的位置。

4.2 文档抽取方法
现代模式引导抽取系统分为三大类：直接生成输出的通用视觉语言模型、使用工具迭代检查文档的编码智能体，以及围绕文档处理工作流设计的专用抽取系统。这些方法在完整性、视觉鲁棒性、溯源和成本方面做出了不同的权衡。

视觉语言模型。通用视觉语言模型是接受文本和图像并生成灵活输出的多模态推理器。因此，文档抽取可以被重新表述为多模态生成：文档页面被渲染为图像，模式被表达为文本指令，模型返回抽取的值，作为提示文本或通过结构化输出 API 强制执行的符合模式的输出。该系列中的系统包括闭源通用模型 [29, 13]、通用开放权重模型 [34, 14] 以及专门针对抽取进行调优的模型 [7, 27]。这三组都接受新模式而无需特定任务的重新训练。这种直接的、单次的工作流简单高效，但可能会遗漏长重复结构中的值，并且这里评估的系统不返回源证据。

编码智能体。诸如 Codex [28, 30] 和 Claude Code [1, 2] 之类的编码智能体通过迭代工具使用循环进行抽取：给定作为文件的文档和模式，它们可以检查页面、编写解析代码、运行检查并修改最终的 JSON。这个循环比单次生成更灵活，并且有助于处理长文档或重复记录，因为智能体可以重新访问文档，而不是依赖单一的模型响应。同样的灵活性带来了成本和可靠性风险：即使是短文档也可能触发许多检查、编码、调试和验证步骤，不受约束的智能体可能在产生少量抽取之前运行许多步骤。编码智能体还需要一个具有文件系统访问权限和验证的智能体运行时，取决于文档如何渲染以及哪些工具可用，并且不是围绕抽取特定的溯源元数据设计的。

专用文档抽取器。商业平台 [36, 10, 6, 24] 将抽取作为专用 API 公开，而不是原始模型提示或编码环境。作为托管服务，它们允许用户直接上传文件，并处理格式支持、预处理、文档解析和模式引导抽取，几乎不需要配置。它们还可以公开视觉溯源和其他抽取元数据，例如源页面，在某些情况下还有词级框，使得输出比原始模型响应更容易审计。然而，专用 API 在完整性、鲁棒性、溯源质量和成本方面仍然存在很大差异。

5 结论
我们引入了 ExtractBench，这是一个挑战标记的基准，将真实模式引导抽取的核心要求整合到一个评估中：正确和完整的输出、源可追溯性、跨文档挑战的鲁棒性以及大规模的成本。通过一起测量这些维度，ExtractBench 不仅显示了哪些系统表现良好，还显示了它们在哪里以及为什么失败。直接 VLM 抽取成本低廉，但通常会截断长记录列表；编码智能体在这些工作负载上更鲁棒，但成本要高得多。专用 API 跨越了质量-成本前沿，其中 LlamaExtract Agentic Plus 以低于编码智能体的成本实现了最强的总体性能。挑战标记的结果进一步表明，系统在长文档、密集模式、扫描件、手写件和超大表格上的退化方式不同。溯源仍然是最需要改进的领域。被评估的 VLM 和编码智能体默认不返回源证据，而即使是返回框的专用系统，其词级溯源 F1 也保持在 50% 以下。总之，这些结果为可靠的抽取设定了明确的标准：完整的输出、可追溯的证据以及大规模下可持续的成本。
