摘要

大语言模型与多模态大语言模型的快速发展，催生了能够在真实世界环境中操作日常工具、辅助用户的主动式智能体。然而，现有基准难以有效评估此类智能体：它们往往依赖沙箱环境与单轮评估范式；其基于场景的任务分类将多种模型能力混在同一任务类别中，难以定位智能体失败的根因。为此，我们提出 UniClawBench——首个面向动态真实世界环境、以能力驱动的主动式智能体基准。该基准围绕五项基础模型能力构建：技能使用、探索、长上下文推理、多模态理解与跨平台协同。基于这些能力，我们设计了 400 项双语真实世界任务。与依赖静态预录答案的以往基准不同，本基准在活跃的 Docker 容器中通过细粒度、逐步完成的检查点评估智能体。此外，我们设计了由执行智能体、隐藏监督智能体与用户智能体组成的闭环评估策略，在不泄露评分标准的前提下模拟真实的多轮人类反馈。为将基础模型能力与框架级设计选择解耦，我们在多个智能体框架下评估了最先进的模型。通过跨模型与跨框架的综合比较，我们揭示了基础模型能力与智能体框架设计如何共同塑造真实世界环境中的表现。基准与代码已开源：https://github.com/HKU-MMLab/UniClawBench

图 1：UniClawBench 概览。包含 400 项跨 5 项核心能力（多模态、长上下文、技能使用、探索、跨平台）的双语真实世界任务。提出三角色闭环评估框架：执行智能体在真实环境中执行任务，监督智能体使用隐藏评分规则评估轨迹与产物，用户模拟器根据执行表现与监督信号提供自然反馈，实现多轮交互。能力级结果显示，框架选择比模型选择影响更大。

1 引言

大语言模型与多模态大语言模型已从以文本为中心的助手演变为能在真实世界环境中执行复杂多步任务的自主智能体。这一演变催生了主动式智能体，它们通过直接控制浏览器、终端等日常工具来辅助用户。OpenClaw、Nanobot 等代表性平台已超越孤立任务执行，迈向 7×24 小时个人助理，成为处理日常工作的"数字同事"。这引发了一个紧迫问题：如何系统性地衡量它们在真实世界环境中的真实能力？

现有基准存在三大结构性局限：第一，难以捕捉真实世界复杂性，往往依赖自托管网站镜像（如 WebArena）或虚拟机内缓存页面（如 OSWorld），造成沙箱表现与真实能力之间的鸿沟；第二，大多采用单轮评估范式，忽略了人机交互的闭环本质；第三，按应用场景组织任务（如"办公""研究"），混淆了根本不同的能力——当模型在"办公"任务上失败时，无法判断瓶颈在视觉感知、长上下文推理还是工具使用。

在真实世界环境中运行并融入闭环用户交互的基准面临两大挑战：一是缺乏稳定的 ground truth（如商品价格每日变化）；二是在不损害评估可靠性的前提下忠实模拟用户交互——若用户模拟器获知底层答案或评分标准，可能无意中向被测智能体泄露解决方案。

本文提出 UniClawBench，首个面向动态真实世界环境、以能力驱动的基准。它沿五项基础能力维度系统分解任务：技能使用、探索、长上下文、多模态、跨平台。我们手工设计 400 项双语任务，覆盖真实日常使用场景，所有任务运行于配备真实软件、活跃浏览器与本地文件系统的 Docker 容器中。我们引入两项新颖评估机制：(1) 针对缺乏稳定 ground truth 的动态环境，放弃预录答案，为每项任务设计细粒度逐步完成检查点；(2) 实施严格的三角色闭环评估作为信息防火墙——隐藏监督者私下检查进度，用户模拟器仅响应可见轨迹与粗粒度进度信号。

我们开展两组实验：在 OpenClaw 框架下评估多种最先进模型以隔离基础模型能力差异；在 OpenClaw、EDICT、Nanobot 三种框架下评估代表性模型以研究框架设计影响。

主要贡献：
- 提出 UniClawBench，首个在动态真实世界环境中评估主动式智能体的能力驱动基准，围绕五项基础能力手工设计 400 项双语任务以诊断失败根因。
- 提出更贴近真实人机交互的闭环评估策略，采用执行智能体、隐藏监督智能体、用户模拟器三角色设计，支持多轮反馈同时防止答案或评分标准泄露。
- 在多个智能体框架下评估最先进模型，揭示基础模型能力与框架设计如何共同影响不同能力维度的表现。

2 相关工作

作为自主智能体的大语言模型：ReAct 建立了推理-行动循环，Toolformer 展示了语言模型学习调用外部工具的能力。后续系统如 HuggingGPT、ToolLLM、Reflexion 将该范式扩展至更丰富的编排与长程问题求解。CogAgent、AppAgent 等将范式扩展至屏幕与移动界面。这些工作建立了基本智能体循环与工具使用模式，但主要面向通用自主性而非持久个人助理。

主动式智能体系统：主动式智能体区别于反应式智能体，能自主发起行动并追求目标。OpenClaw 提供了多平台集成的 hub-and-spoke 架构；Nanobot 强调超轻量、可扩展的核心；Hermes Agent 具备自主技能创建与持续自我改进的内置学习循环。

AI 智能体基准：早期基准评估 Web、OS、移动、企业环境中的 LLM 智能体，但针对孤立任务执行。近期基准分为三组：第一组在真实环境中测量端到端任务完成（如 ClawBench）；第二组研究技能使用与适应（如 SkillsBench）；第三组强调可信度与动态环境（如 ClawMark）。尽管在活跃执行方面取得进展，这些基准仍依赖静态 ground-truth 答案或单轮评估，按场景组织任务且缺乏对智能体框架的分析。UniClawBench 通过隐藏检查点评分规则与闭环多轮评估策略应对动态环境，其能力导向分类与跨框架评估明确将内在模型能力与框架级设计选择解耦。

图 2：三角色闭环评估策略。任务由执行智能体在真实世界环境中仅使用公开输入执行；产生的可观察轨迹与产物由隐藏监督者评估，应用细粒度检查点评分规则与私有参考计算结构化评估状态（通过/失败/继续）与分数；为防止评分标准泄露，仅粗粒度进度信号通过信息防火墙暴露给用户模拟器，后者仅基于可见证据生成自然语言反馈；净化后的反馈返回执行者进行迭代改进，形成多轮闭环。

3.1 能力导向的任务分类与基准构成

现有基准通常按应用领域或交互界面组织任务，这些分类对跨设置比较性能有用，但关于何种能力导致智能体失败的诊断证据有限。在真实个人工作流中，有能力的主动式智能体必须调用专门工具、调查陌生或欠规范环境、在长证据链上保持一致性、将行动基于非文本信号、跨多个应用协调状态。这促使 UniClawBench 采用能力导向分类，将任务分为五个核心维度：

  • 技能使用任务：评估智能体选择、检查、操作任务特定工具或 API 的熟练度。关键瓶颈不是发现信息位置，而是正确选择、理解并执行提供的工具接口以产生可验证产物。代表任务包括登机牌扫描 OCR、电子表格与 CSV 对账、访问日志分析、音频转录、Mermaid 图表生成、SQLite 查询、Git/Docker 审计、文档转换、API 工作流等。
  • 探索任务：刻画智能体在不完整、噪声或可能误导信息下的开放式调查能力。要求智能体逆向工程未文档化的 Web API、审计 shell 或基础设施配置、在量化约束下从固定候选集中选择最佳选项、将图像或数据点追溯至权威来源等。强调探索过程本身：检查候选来源、拒绝错误替代、记录负面证据。
  • 长上下文推理任务：评估智能体跨异构来源、长文档或扩展交互轨迹聚合与维护证据的能力。定义性困难不是单一文档长度，而是跨多段上下文保持约束、调和冲突证据、产生全局一致综合。例如跨 Bilibili 与 YouTube 比较耳机推荐并核查价格规格、在多重约束下规划订阅或旅行、将阅读材料综合为报告或幻灯片等。
  • 多模态理解任务：要求智能体从图像、视频、音频中提取、解释并生成基于非文本内容的信息。例如在学术论文中定位特定图表并重绘、重建视觉图或 SVG 对象、检查食物或产品照片、从 YouTube 视频提取证据、生成字幕或歌词等。
  • 跨平台协同任务：要求智能体跨异构应用与界面同步与编排信息。将跨平台协同视为能力而非环境标签：智能体必须跨应用边界保持状态、传递信息、验证副作用。例如读取 PDF、创建 Zotero 记录、导出 BibTeX 引用、撰写 Obsidian 文献笔记并保存截图证明使用了真实桌面应用。

UniClawBench 共含 400 项双语真实世界任务，每项能力各 40 项英文与 40 项中文任务。所有任务均基于真实用户日常场景手工构建。每项任务设计为完整任务包，包含用户指令、任务特定上下文、输入文件或 Web 资源、工具与服务、技能、预期输出与隐藏评估参考。

图 3：UniClawBench 的多样性与构成统计。热图详述了广泛的应用领域覆盖以及多样的输入输出格式，反映了真实世界智能体任务的多模态与异构特性。

3.2 三角色闭环评估策略

不同于单轮助手，主动式智能体通常通过多轮用户-智能体交互使用。UniClawBench 引入闭环评估设计，建模此交互同时保持可控、可复现的评分。核心挑战是在不暴露隐藏评估标准的前提下提供有用的后续反馈。

设计涉及三个角色：
- 执行者：被评估的智能体，仅接收公开任务指令与许可的任务包。
- 监督者：隐藏评估智能体，观察完整执行轨迹与产物，对照任务特定隐藏参考与评分规则自主分析并给出判断。
- 用户模拟器：分析可见执行轨迹与输出生成自然反馈的智能体，模拟典型终端用户行为，关注可见进度、结果质量与明显问题，而非依赖预定义参考或详细技术检查。

为防止信息泄露，UniClawBench 将监督者与用户模拟器隔离：监督者虽有完整评分标准，但仅转发有限的高层状态信号（通过/失败/可恢复）；用户模拟器仅基于此状态信号与可见轨迹生成自然反馈；反馈重写器进一步净化反馈后送达执行者。

3.3 评估系统

UniClawBench 通过主机监督、容器执行的运行时实现闭环评估。每项任务在全新 Docker 环境中启动执行者，隐藏参考与评分规则从不暴露。执行者可与浏览器、命令行、GUI 应用、本地文件、注入服务交互，并被指示将证据与最终输出保存至指定结果目录。每轮执行后，运行器收集可观察轨迹（转录、工具使用记录、运行时状态、保存产物）提供给隐藏监督者。监督者在独立工作区使用检查点评分规则评分，返回结构化评估状态：通过、失败或继续。若不完整但可恢复，用户模拟器仅接收可见轨迹与高层状态信号，生成自然后续反馈，净化后作为下一条用户消息返回执行者。循环持续至任务通过、不可恢复失败、达到后续预算或超时。

4 实验

4.1 环境设置

开展两组实验：在相同 OpenClaw 框架（v2026.3.11）下比较十个执行者模型以隔离模型级能力差异；选择三个代表性模型在 OpenClaw、Nanobot（v0.1.5.post3）、EDICT 下评估以研究框架设计影响。监督与用户模拟均使用基于 GPT-5.4 的独立 Codex 智能体（高推理努力）。为公平比较，放弃 OpenClaw 浏览器扩展，为各框架准备相同基础技能（apt 技能、DuckDuckGo 搜索、Web 搜索、Agent-Browser、Desktop Control）。实验在 Intel Core i7-13700、16GB RAM 主机上执行，每个隔离 Docker 容器分配 2GB 内存，平均每任务运行约 17.4 分钟。每项任务在初始指令后最多允许两次后续用户交互。标准任务全局超时 30 分钟、单轮超时 20 分钟；长上下文任务分别为 45 分钟与 30 分钟。报告通过率（PR）与平均分（AS）两项指标。

4.2 基准评估可靠性研究

为验证自动评估管道可靠性，随机抽取 50 条完成轨迹，请三位人类专家独立评估。自动通过/失败决策与人类多数投票达成 92.0% 一致；检查点 AS 与人类平均完成分数的 Pearson r=0.71、Spearman ρ=0.68，相关性较强。

4.3 跨模型基准结果

结果显示，尽管 Claude Opus-4.8 与 GPT-5.4 等领先闭源模型取得最高总体通过率，但绝对成功率严格低于 50%，凸显了基准的极高难度，揭示了沙箱能力与真实世界任务执行之间的深刻鸿沟。值得注意的是，开源模型正快速缩小差距：Qwen-3.5-Plus 与 Kimi-2.6 表现高度竞争，甚至超越 Gemini-3.1-pro 等闭源模型。所有评估模型普遍存在严重的"半途失败"现象——中间平均分与最终通过率之间存在显著差距，多数模型能稳定获得高检查点分数但最终无法完成整个任务。从能力角度看，模型在技能使用与探索任务上表现相对较好；长上下文、多模态、跨平台任务则困难得多，因为它们要求智能体在长轨迹中保持记忆、将决策基于非文本证据、跨多个应用协调行动。

框架架构深刻影响任务成功。OpenClaw 在所有测试模型上始终取得最高通过率，作为集中式单智能体框架，其主要优势在于最小信息损失——原始任务约束、中间工具执行证据、闭环用户反馈在统一轨迹中无缝保留。EDICT 表现出较高平均分但较低通过率，暴露了多智能体编排固有的"协调摩擦"——中央编排器基于离散状态轮询分派任务但缺乏对下游子智能体的实时监督。Nanobot 以超轻量结构实现高度优化的 token 使用，但这种极端效率与性能存在固有权衡，在需要扩展证据链与完整轨迹的严格真实世界任务中常难以产生细粒度推理步骤。

4.5 Token 使用与性能进展

在 OpenClaw 框架下，token 使用因模型而异，并在当前模型相对薄弱的能力维度（如长上下文与多模态理解）上固有增加。EDICT 总体消耗大量 token，Nanobot 保持极端 token 效率。智能体性能在交互周期中持续提升，验证多轮用户反馈对动态错误恢复至关重要，也模拟了现实生活中的用户-智能体交互。

5 结论与局限

本文提出 UniClawBench，一个面向动态真实世界环境、以能力驱动的主动式智能体评估基准。超越静态沙箱，我们将智能体评估分解为五项基础能力类别，涵盖 400 项双语真实世界任务。为在不泄露评分标准的前提下忠实捕捉多轮人机协作，我们提出由执行智能体、隐藏监督智能体、用户模拟器组成的三角色闭环框架。评估揭示当前智能体在长程记忆与跨平台协同上挣扎，框架架构常成为内在模型能力的瓶颈。局限包括：400 项手工策划任务相对较少、活跃环境执行可能的不稳定性、基于 LLM 评估可能引入的偏差。尽管如此，UniClawBench 成功定位了智能体失败的根因，为更可靠的主动式助理铺平道路。

附录 A 任务定义格式

UniClawBench 任务通常由两个文件定义：固定公开契约的 YAML 任务声明，以及指定评分规则的隐藏 eval_rule.md。执行者仅看到渲染为运行时提示的 task 字段；监督者看到两个文件并将 eval rule 视为规范评分契约。

A.1 任务 YAML 模板

任务 YAML 模板包含任务 ID、类别、智能体绑定、生命周期（超时、最大总时间、成功阈值）、任务提示、注入（源文件、技能、服务、pre_exec 脚本、参考）、监督者与用户模拟器配置等字段。

A.2 字段语义

  • 基本定义：task_id 在套件内唯一；category 为五项任务维度之一；agent_sys、agent_id、model 记录默认执行者绑定。
  • 生命周期：timeout_seconds 限定单执行周期；max_total_seconds 限定全尝试墙钟时间；success_threshold 为记录为通过的最小监督者分数。
  • 任务提示：task 为执行者接收的字面自然语言请求；task_snapshot 为可选快照版本。
  • 注入：sources 列出工作区挂载文件；skills 列出声明技能；services 为 docker-compose 式引导服务；pre_exec 脚本在服务健康后运行一次；references 为放置于监督者工作区的隐藏判断资产。
  • 监督者与用户模拟器：codex 块配置闭环交互，max_user_followups 限定后续周期数，codex.user_simulator.policy 覆盖默认用户模拟器行为策略，codex.supervisor.instructions 追加任务特定监督者指导。

A.3 评估规则格式

每项任务附带隐藏 Markdown 评分规则 references/eval_rule.md，遵循固定九节模式：§1–§4 建立契约，§5–§6 定义评分，§7–§9 涵盖生命周期策略与资产簿记。

  1. 评分哲学：陈述任务测试内容、奖励内容、不应惩罚内容。
  2. 任务契约：重述公开提示并固定交付路径，区分硬性要求与软性要求。
  3. 来源选择与目标解析规则：监督者如何将执行者产物映射到 ground-truth 实体。
  4. Ground-Truth 快照：指向 ground-truth 文件及规范实体计数。
  5. 检查点评分规则：编号评分行，权重总和为 1.00。
  6. 评分策略与分数上限：在 §5 总和后应用的硬上限。
  7. 继续 vs 失败指导：通过/继续/失败判定的分数分带。
  8. 隐藏参考资产：仅监督者可见文件清单。
  9. 动态内容说明：任务是否离线或活跃，及活跃任务的调和规则。

D.3 周期 1 – 执行者轨迹

模型探测 LOC 网站，通过切换到直接 API 与 HEAD 请求从 Cloudflare 挑战中恢复，并写入所有五个所需产物。

D.4 周期 1 – 监督者判定

监督者接收执行者完整可见轨迹加隐藏评估规则与 ground truth，发出一个结构化决策（score=0.65，verdict=continue）。

D.5 周期 1 – 用户模拟器后续

因判定为"继续"，运行器启动用户模拟器。从监督者仅接收四字段交接（判定、尝试状态、可恢复性、分数）；监督者的 rationale、missing_artifacts、guidance_tags 从不转发，隐藏评估规则不挂载到用户模拟器工作区。

D.6 周期 2 – 执行者轨迹

执行者接收用户模拟器消息作为下一用户轮次并运行周期 2。模型驱动收紧的管道，重新获取每个候选的官方项目 JSON，发现用户消息未指出的两个实质性错误，并从修正管道重新生成所有五个输出文件。

D.7 周期 2 – 监督者判定

监督者第二次决策将分数从 0.65 推至 0.96，跨越评分规则的通过带。运行器记录 finalScore = 0.96。

D.8 此轨迹所证明的内容

  1. 监督者捕捉可恢复失败模式而非直接拒绝：周期 1 有正确管道与数据，仅选择严谨性与排除文件一致性不足。在 score=0.65 返回 continue（非 fail）保留执行者进度同时标记可弥补差距。
  2. 信息防火墙是结构性的而非风格性的：监督者返回七字段决策但仅四字段传递给用户模拟器；隐藏判断资产从不挂载到用户模拟器工作区；确定性重写器进一步净化模拟器候选文本。
  3. 多轮恢复是核心能力：周期 1 的 0.65 在任何单轮范式下都会是失败；周期 2 达到 0.96 不是通过修补保存文件而是通过从项目级 JSON 重建管道，过程中发现用户消息未指出的两个额外问题。

附录 E 社会影响

本工作可通过在真实世界环境中实现更现实、更严格的 AI 智能体评估，在部署前提升其可靠性、透明度与安全性，产生积极社会影响。通过识别能力差距（如长上下文与多模态的弱点），可指导更稳健系统的开发。但也存在潜在风险：框架可能被用于过度优化智能体以追求基准表现而非真正泛化，或加速开发更强大的自主系统而部署于敏感领域却缺乏充分监督。因此，谨慎使用与负责任的评估实践对缓解这些风险至关重要。
