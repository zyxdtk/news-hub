将 AI 智能体添加到 Slack 中听起来对许多企业很有吸引力——但是，正如 VentureBeat 亲身经历的那样，现实往往比最初看起来要复杂和笨拙得多。

现在，NanoCo 公司希望让这一切变得像输入一条 Slack 消息一样简单。该公司是广受欢迎的开源、企业友好型自主 AI 智能体框架 NanoClaw（OpenClaw 的一个更加沙盒化、低代码版本）背后的团队。更进一步的是，该公司推出的全新 NanoClaw Slack 集成 允许人类用户仅通过一条 Slack 提示词，就能启动一整支拥有专业技能、工作流甚至自定义头像的智能体团队。

“在未来 12 到 18 个月内，团队中的每个人都将成为智能体的管理者，”NanoCo 首席执行官兼联合创始人 Gavriel Cohen 在接受 VentureBeat 独家专访时表示。

此外，NanoClaw 智能体可以在频道和共享的 Slack Canvas 中协同工作，甚至可以在 Slack 之外的 Telegram 或 WhatsApp 等其他平台上接收消息，让人类同事可以像 ping 人类同伴一样跨消息平台联系它们。

“我认为这是智能体首次原生融入 Slack，”Cohen 补充道。“过去，你必须做各种奇怪的操作，试图在幕后使用同一个机器人来运行多个不同的智能体。而现在，每个智能体在 Slack 中都有了自己的身份——自己的头像、面孔和名字。你可以 @ 它们，它们也可以互相 @。”

对于企业团队来说，更关键的部分在于持久性和隔离性。NanoClaw 并没有将这些额外的工作者呈现为执行完一次任务后就消失的隐形子智能体。每个智能体都可以被赋予自己的角色、记忆上下文、指令和权限，从而创建出一个更接近小型数字部门的架构，而不是一个带有冗长提示词的单一聊天机器人。

与 2026 年 1 月发布的原始开源版本 NanoClaw 一样，开发者和企业可以进一步选择他们希望的任何底层大型语言模型（LLM）来驱动其 NanoClaw 智能体，以优化性能、成本或其他因素组合。

从单一 NanoClaw Slack 智能体到完整的专业团队

对于全新安装，NanoClaw 当前的设置过程从克隆项目并运行其 nanoclaw.sh 安装程序开始，该程序将引导用户完成依赖项配置、凭据设置、构建智能体容器以及配对首个消息通道。NanoClaw 网站表示，该安装程序可以带领用户“从一台全新机器配置到可以发消息的命名智能体”，而 Slack 是受支持的通道之一。

Cohen 向 VentureBeat 描述了针对 Slack 的特定流程，称其相比构建传统的 Slack 机器人有了显著简化。他说，以前用户必须浏览 Slack 的管理和开发者界面，创建应用，收集密钥、API 密钥和令牌，然后将这些凭据移动到机器人运行的地方。

借助新的集成，NanoClaw 的设置转而提供了一个“连接 Slack”选项。用户为智能体命名、进行身份验证、选择“将 NanoClaw 添加到 Slack”选项，并完成 Slack 的安装和授权流程。一旦获得授权，第一个智能体就可以出现在 Slack 中并开始与用户交流。

重要的区别在于，这种初始授权基本上是一次性的工作区连接。Slack 应用目录列表表示，用户“只需连接一次工作区”，之后 NanoClaw 就可以将每个新增智能体配置为独立的 Slack 机器人，拥有自己的名称、生成的头像和身份。

这些智能体继续在客户的基础设施上运行，并通过 Socket Mode 连接到 Slack。NanoCo 表示它不存储智能体的 Slack 令牌；根据应用目录列表，这些令牌保留在用户的机器上。

Slack 的标准管理控制权仍然围绕该系统。组织可以对其应用审批策略应用于 NanoClaw 集成，而 NanoClaw 的应用目录列表表示，该应用的“主页”选项卡会显示工作区中已配置的智能体，并允许用户撤销单个智能体或完全断开工作区连接。

其结果与其说是对 NanoClaw 底层基础设施的一键式替代，不如说是该基础设施与 Slack 之间的一次性桥梁：用户仍然拥有并运行智能体运行时，但一旦桥梁获得授权，智能体本身就可以创建和协调新增的 Slack 原生同事，而无需每次都让用户重新进行手动应用配置。

Cohen 表示，在幕后，主智能体拥有一个模型上下文协议（MCP）工具，可以创建新智能体并定义其指令、人设、技能和工具；另一个工具则可以将它们放入共享房间。这些智能体已准备好与 Slack Canvas 协作，可以与 Slack 频道上的每个人类用户以及彼此之间进行交流。

这种交互本身被刻意设计得很简单。Cohen 表示，用户无需每次需要新角色时都打开一个单独的智能体构建器，只需告诉现有的智能体他们想要什么样的同事或团队即可。

“对于你在 Slack 中的智能体，你可以说，‘给我创建另一个智能体来处理我的代码审查。再创建一个智能体来审查投稿文章。创建一个从不同角度审查投稿文章的智能体团队。’然后你的智能体就可以创建新智能体，它们会直接出现在侧边栏中并发消息给你。”

这意味着开发者可以要求创建一个产品经理、架构师、实施智能体、代码审查员和测试智能体，然后给每个智能体不同的工具集，并让它们相互交接工作。Cohen 举例说，测试智能体可以访问测试环境，而审查智能体携带特定于代码审查的技能，产品智能体则监控用户反馈。

Cohen 认为，这种劳动分工不仅仅是表面上的角色扮演。“为不同任务赋予每个智能体特定的技能、指令和工具是有优势的，”他说。“比如，我可以有一个代码审查智能体、一个代码测试智能体、一个代码编写智能体，并且我可以让它们处于一个循环中。”他补充道，如果实施智能体遇到歧义，它可以 @ 产品或架构智能体以求澄清，而不是强迫一个通用模型在同一个上下文中承担所有责任和工具。

NanoClaw for Slack 智能体团队宣传截图。图片来源：NanoCo. AI
智能体与人类在共享 Slack Canvas 上协同工作

提供的一张演示截图显示了应用于营销领域的相同模式：一个名为 Nano 的主智能体创建了负责策略的 Atlas、负责内容的 Sage、负责社交的 Echo、负责外联的 Scout 以及负责 SEO 和分析的 Compass。这些智能体在同一个 Slack 对话中互相介绍并开始协调工作，其中 Atlas 指出它已经在 Canvas 中添加了一个项目，这样任务就不会丢失。

用户不必预先指定每一个细节。Cohen 表示，用户可以给主智能体确切的审查流程、优先级和所需工具，或者根据其现有的上下文和记忆将更多配置工作交给智能体本身。

该设计还试图避免一种常见的多智能体故障模式：机器人之间无休止地互相触发。NanoCo 表示，智能体仅在被 @ 时才回复，而在 Canvas 中对工作留下的评论可以路由回负责该部分的智能体。

而且该模型可以超越由一个人创建的特定任务机器人团队。Cohen 描述了这样一个工作场所：每个员工都有自己持久的智能体，这些智能体可以在人类定义的策略下相互交流。

“每个人都有自己的智能体，这意味着在 Slack 中我可以有我的智能体，你有你的智能体，你的智能体可以向我的智能体提问，”他说。“也许我今天不在办公室。你的智能体可以 ping 我的智能体并询问关于可用性的问题，而我可以设置一些策略，决定我的智能体是否可以回答，或者是否需要我批准。”

这将概念推向了更接近组织委派的层面：一些智能体按功能进行专业化，而另一些智能体则有效地代表个别员工及其积累的上下文。Cohen 表示，这些智能体可以配备浏览器和互联网访问权限、记忆、编码能力和其他工具，而新创建的智能体则内置了对 Canvas 工作、智能体间通信以及生成更多智能体的支持。

Slack 正在向更多第三方智能体敞开大门

Slack 底层的变化比 NanoClaw 更为广泛。

4 月，作为 Salesforce 产品的 Slack 宣布能够直接向消息平台添加外部 AI 智能体，最初指向 Vercel 和 Lovable，并表示这些集成将于 5 月下旬推出。

Slack 表示，部署机制自动化了 OAuth、清单配置和环境设置，因此外部构建的智能体无需专门为 Slack 重建即可引入工作区。

Salesforce 新发布的 Slack Code 页面现在将 NanoClaw 与 Lovable、Hyperagent、Superhuman、n8n、Vercel、ChatGPT、LangChain、Runlayer 和 Skydive 并列，并表示“添加到 Slack”可以通过几次点击将这些平台上的智能体以其自身身份引入 Slack。

Slack 中已经挤满了 AI 助手。例如，OpenAI 允许将 ChatGPT 工作区智能体部署到 Slack 频道中，它们可以在那里回答问题、通过连接的系统执行任务并输出文件。Slack 还支持 Claude 和自定义的 Agentforce 智能体。因此，NanoClaw 的差异化不仅仅在于“Slack 中的 AI”，而在于一个已经在运行的智能体能够从对话内部创建额外的、可独立寻址的队友。NanoCo 称这是 Slack 上的首创；这一特定的市场首创声明来自该公司。

“添加到 Slack 意味着只需一条消息就可以启动一整支 NanoClaw 智能体团队，在 Slack 中与人们并肩工作，”Slack 产品管理总监 Josh Milas 在提供的公告中表示。

NanoClaw 与 Slack 中的 Claude Tag、ChatGPT 智能体和 Agentforce 有何不同

在试图将 AI 从侧边栏聊天机器人转变为类似于持久的 Slack 同事方面，NanoClaw 并非孤军奋战。

Anthropic 的 Claude Tag 于 6 月开始向 Claude Team 和 Enterprise 客户推出测试版，这可能是概念上最接近的比较。

管理员可以授予 @Claude 访问选定频道、工具、数据源和代码库的权限；频道中的每个人都可以通过 @ 它来委派工作。Claude 会记住其所在频道的相关信息，可以异步工作数小时或数天，并且当管理员启用其“环境”行为时，它可以主动标记信息或恢复未解决的工作，而无需等待另一个提示词。

Anthropic 表示，独立的 Claude 身份也可以限定于不同的用例，例如，销售 Claude 不会与工程 Claude 共享其记忆或工具。

区别在于 这些数字同事是如何被配置和组织的。Claude Tag 的文档化工作流是由管理员主导的：管理员将 Claude 与 Slack 配对，决定每个 Claude 身份可以访问哪些频道、工具和信息，设置支出限制，然后将这些身份暴露给员工。

在给定频道中，Anthropic 描述了“一个与所有人互动的 Claude”。其公开文档并未描述最终用户要求该 Claude 按需创建几个新的、独立命名的 Slack 机器人。NanoClaw 的模型几乎是倒置的。

在组织将其 NanoClaw 安装一次连接到 Slack 后，NanoClaw 表示现有的智能体本身就可以根据对话请求配置额外的智能体，每个新工作者都会获得 自己的 Slack 机器人身份、名称、生成的头像和令牌，并在客户的基础设施上运行。

OpenAI 的 ChatGPT Workspace Agents 则处于该频谱上的另一个点。
Business、Edu 和 Enterprise 客户可以在 ChatGPT 中构建可重用的智能体，为它们提供指令、模型、文件、应用、自定义 MCP 连接和计划，然后将这些智能体附加到 Slack 频道。

构建者为每个智能体分配一个唯一的 Slack 句柄，并可以将其配置为仅在提及时回复，或者自动回复频道中的相关消息。

但这种构建仍然主要通过 ChatGPT 的智能体构建器进行：OpenAI 的设置文档告诉用户先创建智能体，然后将 Slack 添加为通道。在底层，Slack 句柄依赖于由 ChatGPT Agents 应用管理的 Slack 用户组，而不是 NanoClaw 的模型（在 NanoClaw 中，每个配置的智能体本身就是一个独立的 Slack 机器人）。

Salesforce 的 Agentforce 同样允许组织创建多个专业智能体，员工可以在 Slack 中私信或 @ 提及它们，并且它可以说是该群体中最传统的企业管理模型。

公司在 Agentforce Builder 中构建智能体，通常从针对客户洞察、员工帮助或入职等工作的 Slack 特定模板开始，并且可以添加子智能体和操作，让它们搜索信息、创建 Canvas 或执行其他工作。

一旦在 Salesforce 中配置并激活，管理员就会将这些智能体引入 Slack 供员工使用。这使得 Agentforce 对于已经将身份、数据和工作流集中在 Salesforce 上的组织来说非常强大，但同样是将 智能体创建置于部署之前，而不是让创建本身成为现有 Slack 智能体可以在对话期间执行的操作。

这一区别有助于澄清 NanoClaw 实际上为日益拥挤的市场带来了什么。Slack 本身现在为开发者提供了 Agent Kit，并为在外部平台上构建的智能体提供了部署标准，自动化了 OAuth、清单和环境配置等环节。Claude Tag、ChatGPT Workspace Agents 和 Agentforce 都表明，Slack 内部持久的、专业的 AI 队友本身已不再是新鲜事物。

NanoClaw 更不寻常的押注是递归配置：Slack 不仅仅成为工作者调用智能体的地方，而是成为一个现有智能体可以组装额外命名智能体、分配角色并将它们作为一个工作团队放入频道的地方。

不同的方法各有权衡。Claude Tag 带有 Anthropic 管理的模型和集中管理控制，包括特定频道的权限、审计日志和令牌支出限制，同时还提供了 NanoClaw 提供的材料中未以同样方式声称的主动“环境”行为。

ChatGPT Workspace Agents 提供了托管的智能体构建器、计划、应用连接以及组织级别的发布和访问控制。Agentforce 则将智能体与 Salesforce 权限、企业数据和预定义的业务操作紧密绑定。

而 NanoClaw 则强调 自托管、开源修改和独立的智能体身份，将更多控制权——以及更多的运营责任——转移到了运行它的组织身上。

其结果与其说是对这些系统的直接替代，不如说是对同一个新兴问题的不同回答：企业是想要少量集中配置的 AI 助手，还是想要一个环境，在这个环境中，员工和现有的智能体可以随着新工作的出现不断创建专业的数字同事。

NanoClaw 是如何走到这一步的

NanoClaw 起源于远离企业协作市场的地方。Cohen 曾是 Wix 的工程师，他于 2026 年 1 月 31 日在 MIT 许可下推出了该项目，作为 OpenClaw 的一个刻意保持小巧、专注于安全的替代方案。

最初的理念是，一个可以访问消息、文件和工具的个人智能体应该在操作系统隔离的容器中运行，而不是直接在主机上运行，并且编排层应该保持足够小，以便开发者或安全团队能够理解——初始核心大约 500 行 TypeScript 代码，设计以容器隔离和最小的单进程架构为中心。

随后，该项目稳步向企业基础设施迈进。3 月，NanoClaw 与 Docker 合作，在 Docker Sandboxes 内运行智能体，对可能安装包、修改文件和启动进程的工作负载使用更强大的 MicroVM 支持的隔离。

4 月，NanoClaw 2.0 添加了 Vercel 的 Chat SDK 和 OneCLI 的凭据网关，允许组织围绕敏感操作定义策略，并要求在为受保护请求注入凭据之前必须经过人工批准。围绕该项目成立了 NanoCo，并筹集了由 Valley Capital Partners 领投的 1200 万美元种子轮，Docker、Vercel、monday.com 等参与投资。其商业策略是保持 NanoClaw 开源，同时向企业销售托管的、全组织范围的部署和“专业助理”基础设施。该公司现在表示，NanoClaw 的下载量已超过 25 万次，在 GitHub 上获得了 3 万颗星。

随着 NanoClaw 深入工作场所基础设施，这种开源结构仍然是 Cohen 宣传的核心。

“你现在真的能够将一个完全由你控制的开源智能体集成到 Slack 中，”他说。“你可以更改所有这些配置。另外，你可以 fork NanoClaw 并完全重写或更改行为——创建你自己的记忆系统、你自己的编码框架、智能体框架。你想做什么都可以。完全自由。”

持久的智能体，但基础设施仍受用户控制

Cohen 表示，NanoClaw 仍然是自托管的：组织可以在本地机器或其自己的云 VM 上运行它，智能体数据也存储在那里。

同一个智能体也可以出现在 Slack、WhatsApp 或 Telegram 中，同时保留相同的记忆、工作区和工具，尽管每个消息界面使用独立的会话。

NanoClaw 可以跨这些会话提取最近的上下文，以便智能体能够保持连续性，而无需将每个聊天记录合并到一个流中。NanoClaw 的文档同样描述了一种多通道架构，其中同一个智能体可以保留一个工作区和记忆，同时维护每个通道独立的会话。

“这都是自托管的，”Cohen 说。“你可以在你的计算机或云中的虚拟机上运行它，数据存储在你的计算机或你的虚拟机上。这可以是一个运行在你的 Mac Mini 上的开源模型，你的数据除了你的 Mac Mini 和 Slack 之外哪里也不会去。”

跨通道的连续性也旨在让智能体感觉不那么像一个特定于 Slack 的机器人，而更像一个碰巧可以通过 Slack 联系到的持久同事。

Cohen 表示，同一个智能体可以存在于 Telegram、WhatsApp 和 Slack 中，并访问相同的记忆、文件和工具。对话仍然是独立的会话，但它们共享一个工作区和持久的上下文，因此智能体可以将知识从一个界面带到另一个界面。

当组织开始创建许多智能体时，这种架构就显得很重要了。Cohen 表示，一个智能体可以跨通道看到自己的会话，但默认情况下看不到另一个智能体的私有会话。NanoClaw 当前的文档同样描述了在各自沙箱中运行的智能体和可配置的模型提供商，默认使用 Claude Code，并可选择 Codex、OpenCode 和本地 Ollama 模型作为替代。

对于新的 Slack 流程，存在一个云依赖项。Cohen 表示，NanoCo 运营着一个小型服务，用于处理 Slack 配置请求和头像生成。他说，它不会接收用户的消息或智能体记忆。

继续致力于开源

Cohen 表示，NanoCo 不会对这项社区 Slack 功能收费，并会承担配置服务和头像生成的成本。用户仍可能产生自己的模型推理和托管费用，因此在实际操作中，这并不能使部署的智能体团队完全免费。

NanoCo 表示，该集成可通过 Slack 应用目录获得，需经过正常的工作区应用审批和治理。Slack 表示，工作区所有者和管理员可以要求应用在安装前获得批准。

Cohen 将这一决定视为 NanoCo 更广泛的开源战略的一部分，而不是一种独立的变现手段。“我们在这个项目上不赚任何钱。这个真的是为社区做的，”他说。“我们知道从长远来看，这将使 NanoCo 作为一家公司受益。随着 NanoCo 的发展和能力的扩展，这些都会回馈给开源。我认为这是开源的新模式，我们不再试图从带给社区的每一点价值中变现。”

公司能否如此迅速地达到这一目标，与其说取决于创建智能体的难易程度，不如说取决于 IT 团队能否以同样的速度管理智能体的权限、记忆、支出和故障模式。NanoClaw 押注，下一个问题将是管理一旦消除这一障碍就会出现数字同事。
