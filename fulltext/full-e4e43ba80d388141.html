如何在不拥有服务栈的情况下于生产环境运行开源模型

生产推理要求技术团队将模型、部署方式和基础设施作为一个整体来考虑——而不必为整个服务栈承担责任。

在生产环境中运行开源模型，意味着将模型选择、部署方式、容量、加速器以及服务栈所有权视为一个单一的工程问题。团队需要围绕内存需求、预期需求量、延迟和吞吐量目标，以及自己准备管理的运营边界来进行设计。

对于技术团队而言，这意味着要回答四个问题。

1. 哪种部署模式最适合您的工作负载？

按 token 付费的推理适合需要灵活消费、但不需要专用基础设施的工作负载。其他工作负载则可能受益于专用容量——当持续需求、可预测的延迟和吞吐量、GPU 可用性，或特定的开源模型与加速器配置是优先考虑事项时。

这为那些需要专用 GPU 容量、希望对模型和基础设施配置拥有更大控制权、但又不想自己构建和运营完整服务栈的团队创造了一个中间地带。Microsoft Foundry 中的托管计算正是解决这一问题的一种方式。

2. 应如何围绕容量、延迟和吞吐量进行设计？

一旦工作负载运行在专用基础设施上，容量和性能就成为了工程变量。团队需要估算需求、配置容量，并选择一个平衡延迟与吞吐量的运行点。交互式应用可能会优先考虑响应时间，而批处理或高流量工作负载则可能针对吞吐量进行优化。当 GPU 容量分配给客户而非共享时，团队就有了更清晰的依据来围绕这些变量进行设计。

经济性也会随之改变。团队不再将推理仅仅视为按 token 计费的成本，而是需要考虑已配置的 GPU 容量及其使用效率。GPU 小时成本、利用率、吞吐量和完成的工作量，都会影响每个 token 或每次推理请求的有效成本。

3. 您想管理服务栈的多少部分？

借助 Foundry 中的托管计算，客户保留直接影响工作负载的决策权，而微软则管理大部分服务环境。

您的团队控制 微软管理大部分服务环境
模型和加速器选择 运行时和容器环境
已配置的容量 基础设施调优和优化
延迟与吞吐量之间的运行点 软件和运行时更新
容量扩展 漏洞修复和安全补丁

这种从客户自管基础设施的转变，意味着平台团队可以保留对影响工作负载性能和经济性的变量的控制权，而不必维护其下的每一层。

由于托管计算是 Foundry 的一部分，开发人员还可以在各种部署类型中继续使用熟悉的推理 API、身份验证、网络、SDK 和可观测性工具。

4. 工作负载需要什么样的加速器特性？

内存容量决定了模型能否在给定配置上运行以及需要多少个 GPU：更多的内存意味着更大的模型可以在更少的 GPU 上运行，为批处理等技术留出余量；而内存带宽则影响数据在加速器中传输的效率。这些特性与服务配置共同决定了并发性、吞吐量、延迟和工作负载经济性。

AMD Instinct™ MI300X GPU 就是一个很好的例子：作为 Foundry 托管计算中的高内存选项，每个 GPU 提供 192 GB 的 HBM3 高带宽内存和高达 5.3 TB/s 的内存带宽，八 GPU 平台合计 1.5 TB。这样的容量允许更大的模型在更少的 GPU 上运行，为批处理和长上下文推理提供更多余量——在这些场景中，模型权重和键值（KV）缓存会争夺内存。

但硬件只是等式的一部分。AMD 的 ROCm 生态系统为 AMD Instinct 提供了开放软件和优化层，广泛支持开源模型和开源 AI 框架。仅这一软件层所能带来的提升幅度，在 AMD 性能实验室的测试中得到了体现：在 8× AMD Instinct MI355X 上，与 ROCm 7.0 基线相比，ROCm 10 的全栈软件优化在 GLM-5、Kimi-K2.5 和 DeepSeek-R1-0528 上平均带来了 3.3 倍的推理吞吐量提升。在托管计算中，持续优化由平台负责，而不是转嫁给客户。

GLM 5.3 Flash 展示了这些特性如何转化为部署选择。这个拥有 3200 亿参数、每 token 激活 180 亿参数的模型，提供三种针对 AMD Instinct MI300X 优化的配置，每种配置均具有 512K 上下文窗口。四 GPU 配置面向紧凑的聊天、编码和智能体工作负载，而两种八 GPU 配置则利用张量并行（TP）、数据并行（DP）和专家并行（EP），分别优先考虑并发性与首 token 时间，或为长上下文工作负载优先考虑内存余量。

同样的原则在生产规模上也可以看到。AT&T 在 Foundry 中使用托管计算运行多个开源模型和 GPU 架构，共动用约 530 个 GPU，其中包括约 430 个 AMD Instinct MI300X GPU。仅 Phi-4 每月就处理超过 7000 亿个 token，用于数据准备和合成数据生成。

配置选择同样重要。在使用对话式工作负载对 GLM 5.3 Flash 进行的测试中，八 GPU 的 TP4 + DP2 + EP 配置实现了约为四 GPU 配置 1.8 倍的输出吞吐量，同时将平均首 token 时间缩短了一半以上。其他工作负载的提升幅度则较小，这进一步说明团队需要针对自己的工作负载对每种配置进行基准测试，而不是仅凭 GPU 的标称规格做决策。

加速器基准测试几乎无法说明某个配置是否适合生产应用。团队需要的是工作负载级别的测量数据：

  • 模型需要多少个 GPU？
  • 在指定的运行点上可以提供怎样的延迟和吞吐量？
  • 在保持目标性能的同时，可以支持多少并发用户或请求？
  • 已配置的容量得到了多有效的利用？
  • GPU 小时消耗如何折算为每个 token 或每单位工作的有效成本？

生产始于模型选择结束之处

在生产环境中运行开源模型，意味着将部署模式、容量、管理边界、加速器和基准测试方法与工作负载相匹配。

对于需要专用基础设施的工作负载，关键决策在于：团队需要对模型、加速器、容量和性能拥有多大的控制权，而不必拥有服务栈的每一层。Foundry 中的托管计算提供了一种实现这种平衡的方式，而 AMD Instinct MI300X GPU 则提供了在更少 GPU 上运行大型开源模型所需的内存容量。
