摘要
开放式无线接入网（O-RAN）正朝着代理化操作演进，其中由大语言模型（LLM）驱动的 xApps/rApps 根据运营商意图生成控制提案。
然而，此类提案可能存在冲突、不可行或产生幻觉，且现有系统无法同时提供独立于提案的安全性、感知优先级的协调以及可追溯的反馈。
为此，我们在近实时（Near-RT）RAN 智能控制器中提出了一种可证明安全的仲裁器，即 xTRUCE，用于缓解 gNB 控制中的多 xApp 冲突。
我们首先开发了一个结构化的 xApp 提案接口和三层约束层级，将物理限制和运营商定义的规则置于可放宽的性能目标之上，并引入双时间尺度控制动作空间。
随后，两阶段仲裁机制根据运营商优先级顺序最小化目标缺口，在 Near-RT 延迟预算内最终确定安全的 E2 动作，同时向 xApps 和运营商返回冲突证书以供重新协商。
最后，我们在多小区 O-RAN 用例中实现了 xTRUCE，并通过基于实时 API 的 LLM xApps 仿真以及基于 OpenAirInterface/FlexRIC 的 O-RAN 协议栈空口（OTA）实验，评估了其多进程原型。
结果表明，尽管存在严重的提案幻觉，xTRUCE 仍能确保 gNB 控制安全，实现 100% 的受保护服务；在过载情况下实现与优先级一致的性能满足；通过证书高效引导 LLM 意图重新协商；并保持延迟安全的 E2 控制环路。

I 引言
开放式无线接入网（O-RAN）架构正在重塑蜂窝网络并迈向 6G，它以多供应商分解单元、开放接口和分层 RAN 智能控制器取代了封闭的单体基站 [1, 2]。
在此架构上，网络智能以可插拔的控制应用程序形式实现，其中由近实时（Near-RT，10ms–1s）RIC 托管的 xApps 直接针对实时 RAN 闭合测量、决策和动作循环 [3]。
通常，每个 xApp 运作一个管理目标，例如服务质量保证或节能，并且此类数据驱动的 xApps 已经在开放实验平台上大规模开发并得到验证 [4, 5]。
值得注意的是，这些 xApps 可能由不同的供应商开发和提供，但它们可以通过 Near-RT RIC 层的共享 E2 接口观察和引导相同的小区、用户和频谱。
与此同时，大语言模型的快速发展正使 AI 原生网络的 6G 愿景触手可及，最近的研究预计 LLMs 将承担从翻译运营商意图到直接做出 gNB 控制决策的管理职责 [6, 7, 8]。
具体而言，基于意图的网络将高层运营商目标转化为机器可执行策略 [9]，而代理化系统赋予 LLMs 自主推理能力，以解释这些策略并在 O-RAN 功能和时间尺度上生成相应的管理提案 [10, 11, 12, 13]。
融合这两种趋势，O-RAN 生态系统正朝着代理化 O-RAN 演进，其中由 LLM 驱动的非实时（Non-RT，⩾1s）rApp 代理解释运营商意图，而多个由 LLM 驱动的 Near-RT xApp 代理协作且自主地生成 gNB 控制决策提案。
尽管如此，多 xApp 提案在运行时可能表现为相互冲突、物理上不可行、格式错误或纯粹是幻觉，并且同样的担忧在脚本化、学习型和第三方 xApps 中已经出现 [14]。
事实上，在代理化演进之前，xApp 间的冲突一直是 O-RAN 中长期存在的隐患 [15]，因为封闭的单供应商协议栈在设计时会协调其控制逻辑，而由于多供应商来源，O-RAN 的 xApps 无法进行联合工程设计。
意识到这一点后，O-RAN 规范特意在 Near-RT RIC 平台内部预留了冲突缓解功能，并概述了其架构考量 [16, 17]。
然而，它们并未规定一种针对单次决策的方法，能够同时接纳冲突目标、根据运营商优先级放宽不可行目标，并对最终动作进行认证。
因此，在运行时治理此类不可信智能代理，而不是盲目信任它们，成为代理化演进能够在现实 O-RAN 中部署的前提。
最近，O-RAN 中的冲突处理引起了若干值得注意的研究努力。
Adamczyk 等人 [18] 将 xApp 间冲突分类为直接、间接和隐式类型，并为 Near-RT RIC 设计了一个以检测为中心的缓解框架。
类似地，del Prever 等人 [15] 开发了 PACIFISTA，这是一个在实验平台上分析候选 xApps 并在部署前统计评估其冲突的框架，他们最新的后续研究进一步从相同配置中预测了此类冲突对关键绩效指标的影响 [19]。
在运行时协调方面，Wadud 等人在 [20] 中开发了 QACM，根据相关 xApps 的 QoS 要求选择冲突参数的值，并在 [21] 中以相同的思路进一步缓解了节能与移动性管理之间的具体冲突。
从编排的角度来看，D’Oro 等人 [22] 提出了 OrchestRAN 来决定哪个智能体在哪里运行，从构造上防止两个模型控制同一个参数。
所有这些努力都证实了该问题的严重性和工业相关性。
与此同时，也有一些相关工作探讨了 O-RAN 中数据驱动的独立 xApps 的安全控制问题。
Nagib 等人 [23] 通过混合迁移学习，在面对未见网络条件时稳定了基于深度强化学习（DRL）的切片 xApp，其后续研究 SafeSlice [24] 进一步添加了安全层，将每个资源分配动作投影到最近的延迟安全动作上。
Hossen 等人 [25] 在数字孪生上重放闭环控制回路，使得 xApp 在接触实时 RAN 之前就能针对真实的 KPI 进行演练。
此外，Fiandrino 等人 [26] 将基于图的解释附加到 DRL xApps 的决策中，让运营商检查并引导正在运行的代理。
然而，这些安全措施仅针对单 xApp O-RAN 场景，无法在运行时仲裁来自多个 xApps 的冲突提案，更不用说处理可能产生幻觉提案的 LLM 驱动代理了。
据我们所知，目前没有现有工作提供一个统一的解决方案，能够在平衡运营商优先级和 Near-RT 延迟预算的同时，将冲突和不可行的多 xApp 提案转化为经过验证的安全 gNB 动作。
总之，在追求此类实现时，我们遇到了以下三个根本性挑战：
• 挑战 1：如何在 LLM 驱动的 xApp 代理提出任意、不可信且可能产生幻觉的提案时，保证 gNB 控制安全？
多个 xApp 提案的内容可能格式良好且经过授权，但仍然不可行或相互冲突 [20]。
因此，安全性必须在 Near-RT RIC 平台中强制执行，并且完全独立于提案内容，同时确保每个执行的 gNB 动作同时满足物理限制和运营商定义的规则。
• 挑战 2：如何根据运营商优先级协调共同不可行的 KPI 目标，并为提案重新协商提供可操作的反馈？
当多 xApp 提案发生冲突时，在当前的 RAN 容量和操作约束下，它们的 KPI 目标可能无法共同实现，因此必须根据运营商定义的优先级放宽某些目标。
特别是对于一些硬性目标，其产生的缺口和限制性约束必须以机器可读的形式报告，以指导提案重新协商。
• 挑战 3：如何在混合离散和连续动作空间中，在 Near-RT 延迟预算内发出安全的 gNB 动作？
配置 gNB 控制决策（如小区激活和用户重关联）的演进时间尺度比常规无线电资源决策慢，这使得联合优化变得具有组合性。
此外，动作仲裁的求解器可能会超出所需的延迟要求，因此必须在决策截止时间前决定一个安全动作。
图 1：启用 xTRUCE 的代理化 O-RAN 控制架构概览，及其同地部署的 OTA 测试床实现。
为了解决代理化 O-RAN 的上述挑战，我们在本文中提出了在 Near-RT RIC 中具有可证明保证的 xApp 目标在冲突下放宽与延迟安全执行，即 xTRUCE。
借助 xTRUCE，xApp 代理仅通过结构化提案影响 gNB 控制，核心仲裁器在每个决策时期计算一个安全执行动作和一个冲突证书。
在具有多个冲突 xApps 的测试中，xTRUCE 保留了所有物理和运营商定义的刚性限制，同时根据运营商优先级分配不可避免的 KPI 目标缺口。
它还引导实时 LLM xApp 代理在仅 3 轮证书反馈内成功纠正不可行意图，在仅 24–29% 的轮次中留下未满足的目标，而基准模式为 79–99%。
进一步在空口（OTA）O-RAN 测试床上，每个 100 毫秒的运行时期总是会输出一个安全动作，即使在严重幻觉提案下仲裁偶尔超过时间阈值也是如此。
简而言之，我们的主要贡献总结如下。
• 我们首先将 xTRUCE 置于 Near-RT RIC 的冲突缓解路径中，其中结构化的提案网关将每个不可信的 xApp 限制为机器可读的提案，而不是直接的 RAN 控制。
我们进一步将物理限制、运营商定义的规则和 xApps 的 KPI 目标组织成三层约束层级，其中每个执行的 gNB 动作都服从两个刚性层，只有 KPI 目标层是可放宽的。
• 然后我们开发了两阶段感知优先级的仲裁，以协调冲突的 KPI 目标。
具体而言，阶段 I 根据运营商定义的优先级顺序最小化硬目标放宽，而阶段 II 通过 E2 控制环路最终确定安全的 gNB 动作。
在这里，我们从理论上证明了这种优先级保证，并通过定理 1 表明，当所有硬目标共同可行时，阶段 I 不会引入任何放宽。
随后，产生的目标缺口和限制性约束价格被收集在机器可读的冲突证书中，并返回以指导 xApps 和运营商进行提案重新协商。
这些解决了挑战 1 和 2。
• 我们确定了双时间尺度动作规则，并设计了一种延迟安全的动作执行机制，该机制始终保留一个经过验证的动作，以在 Near-RT 延迟限制下支持慢速配置更新和快速资源控制。
因此，即使两阶段仲裁未及时完成，RAN 控制仍可使用安全动作。
我们进一步实例化了一个多小区 O-RAN 控制用例，其中通过定理 2 从理论上证明了 xTRUCE 能够提供具有精确价格的安全动作和证书。
这些解决了挑战 3。
• 为了验证 xTRUCE 的可部署性，我们在基于 Python 的仿真中评估了其多进程原型，这些仿真连接了独立的实时 ChatGPT-5.6 和 Claude-Sonnet-5 代理，并在由 OpenAirInterface (OAI) gNB 和灵活 RIC (FlexRIC) 支持的 OTA O-RAN 兼容测试床上进行了评估。
结果验证了其独立于提案的 gNB 控制安全性、与优先级一致的 KPI 满足度、证书引导的 LLM 重新协商以及 E2 接口环路中的 Near-RT 延迟安全执行。

II 代理化 O-RAN 的 xTRUCE
II-A 代理化 O-RAN 控制路径
图 1 详细说明了 xTRUCE 在代理化 O-RAN 端到端控制路径中的部署。
它始于 O-RAN 运营商通过运营商控制台以自然语言表达高层意图，该意图由服务管理和编排（SMO）框架处理。
SMO 托管 Non-RT RIC，其中包含一个意图编排 rApp，用于将此意图精确转换为指定 KPI 目标、运营商优先级和操作规则的机器可执行策略指导。
然后，有关这些策略的数据通过 A1 终止 [27] 与 Near-RT RIC 中的多个 xApps 共享。
为了实现代理化和智能化，rApp 和 xApps 采用授权的 API 访问实时 LLM 代理（例如 Claude-Sonnet-5 [28] 和 ChatGPT-5.6 [29]），它们还支持本地的脚本和基于学习的代理。
同时，Near-RT RIC 通过 E2 接口与开放中央单元（O-CU）和分布式单元（O-DU）通信，并控制开放无线电单元（O-RU）。
具体而言，进入 Near-RT RIC 的 E2 指示携带 RAN 状态的测量值，而离开它的 E2 控制通过适用的 E2 服务模型交付 gNB 控制决策 [30]。
此外，O1 接口用于管理和持久配置，NG 接口将 gNB 连接到 5G 核心网 [1]。
除了托管 xApps 之外，Near-RT RIC 平台还提供一系列共享功能，其中 O-RAN 规范明确将多 xApp 冲突缓解确定为核心平台能力，并概述了其架构考量 [16, 17]。
然而，其标准仍然没有规定哪些限制永远不会被放宽，不可行的目标如何根据运营商优先级降级，如果仲裁达到 Near-RT 延迟预算会发出什么 gNB 动作，或者应该向 xApps 报告什么。
有鉴于此，xTRUCE 正好填补了这一空白，作为在做出 E2 控制决策之前不可或缺的冲突仲裁阶段。
请注意，xTRUCE 的范围仅涵盖基于相同运营商意图的代理化 xApps 之间与 E2 控制相关的冲突，而此之外的问题（如 xApp 身份验证或多 rApp 冲突）不予考虑。
II-B xTRUCE 工作流程和设计目标
在 xTRUCE 工作之前，每个 xApp 首先对通过 A1 接收的 Non-RT 策略和通过 E2 接收的 RAN 状态进行推理，以生成针对特定 gNB 管理目标（例如 QoS 保证、节能或负载均衡 [25]）的提案。
在此，没有 xApp 直接做出任何控制决策，相反，每个 xApp 通过提案网关提交机器可读的提案，该网关本质上是一个 RIC 内部接口，不同于 A1 和 E2SM。
具体而言，提案网关检查每个 xApp 提案的身份、授权范围、模式和有效期，任何格式错误、过期或超出范围的请求将在仲裁前被丢弃。
还值得指出的是，无论通过这些检查的提案如何，它仍然保持不可信状态，必须随后通过 xTRUCE 进行仲裁，因为它可能由于代理幻觉而单独不可行、相互冲突或完全错误。
图 2：提出的 xTRUCE，用于在 Near-RT RIC 中进行安全的多 xApp 仲裁、延迟安全的 RAN 控制以及证书引导的冲突重新协商。
在 xTRUCE 的每个仲裁时期内，首先收集最新的有效 xApp 提案，然后计算一个最佳安全动作并通过 E2 发出。
同时，xTRUCE 向 xApps 和运营商返回一个结构化的冲突证书，说明哪些 KPI 目标已满足，哪些被放宽以及放宽了多少，以及哪些限制阻碍了进一步的改进。
因此，xTRUCE 工作流程中出现了两个闭环，如图 1 所示。
快速控制环路从接收 RAN 状态开始，并在每个仲裁时期以发出 gNB 控制动作为结束。
慢速重新协商环路是一个异步反馈路径，其中证书让 xApp 代理修改不切实际的目标，并向运营商提供关于持续冲突的简明说明。
出于延迟安全的考虑，接受的 xApp 提案在声明的时间窗口内保持有效，xTRUCE 始终基于最新的有效提案做出决策，并且永远不会等待延迟敏感服务的 LLM 响应。
因此，代理化 O-RAN 中 xTRUCE 的设计和开发旨在实现以下四个具体目标：
• 独立于提案的 gNB 控制安全：从仲裁器输出的每个 gNB 控制动作不得违反建模的物理限制和运营商定义的规则，且独立于所有已接纳 xApp 提案的内容。
• 与优先级一致的 KPI 满足度：当在过载情况下无法全部满足 KPI 目标时，根据运营商分配的优先级最小化其缺口，以尽可能满足高优先级性能目标。
• 多 xApp 冲突证书反馈：在每个仲裁时期，xTRUCE 必须返回一个机器可读的冲突证书以供重新协商。
当有新的仲裁结果可用时，证书报告目标放宽和限制性约束，或者在超时后指示没有新的最优性信息可用。
• Near-RT RIC 延迟安全动作执行：即使完整的仲裁未在 Near-RT 延迟预算（小于 1s）内完成，每个时期内也必须有一个经过验证的控制动作可用并发出。
III 提出的 xTRUCE 系统
本节详细介绍了图 2 中的 xTRUCE 系统设计，涵盖其控制抽象、约束层级、两阶段仲裁、证书反馈和延迟安全保证。
III-A 控制动作和结构化 xApp 提案
时间被均分为离散的连续时期 t=0,1,2,⋯，在每个时期 t，物理 RAN 状态 1 1 1 该状态包含信道增益、队列积压和流量到达等，是可以在近实时内测量的客观条件。 ，记为 s_t，通过 E2 接口对 Near-RT RIC 层是已知的。
设 𝒩={1,⋯,N} 为部署的 xApp 代理集合，其中每个代理 i∈𝒩 针对特定 KPI 运作，并在需要时生成相应的提案。
在处理有效提案后，xTRUCE 发出 gNB 控制动作，记为 a_t∈𝒜，其中 𝒜 是包含有限数量控制变量的动作空间，涵盖发射功率/频谱分配、小区开/关状态以及小区到用户的引导。
为了适应不同的控制时间尺度，我们将 a_t 拆分为 a_t=(a_t^cfg, a_t^rt)。
这里，a_t^cfg 是每 T^cfg（T^cfg>1）个时期更新一次且在此期间保持不变的慢速重配置变量集合，而 a_t^rt 代表应在每个时期 t 重新确定的变量集合。
此外，设 ℳ={1,⋯,M} 索引 O-RAN 暴露的 KPI，它们的实现值由下式给出：
ϕ(a_t,s_t)=(ϕ_1(a_t,s_t),⋯,ϕ_M(a_t,s_t))^T, (1)
其中 ϕ_m(a_t,s_t) 是在 RAN 状态 s_t 下执行动作 a_t 所产生的关于 KPI m 的性能值。
考虑在每个时期 t，每个 xApp 代理 i 仅通过以下形式的 结构化提案 提交其请求：
𝒫_i^t={(θ_i,m, type_i,m)}{m∈ℳ_i}. (2)
具体而言，ℳ_i⊆ℳ 限制了代理 i 负责的 KPI 范围，θ_i,m∈ℝ 是其对 KPI m 的请求性能目标，type_i,m∈{hard, soft} 标识硬目标或软偏好。
为了说明，设 ℛ_t 收集时期 t 有效提案涵盖的 对。
值得注意的是，除非续订，否则每个提案都会过期，任何格式错误、过期或超出范围的提案都将被提案网关丢弃，2 2 2 代理身份和授权元数据可以附加到 (2) 中并由同一网关检查 [31]。相关的代理安全研究超出了本文范围，将不作深入讨论。 如图 2 所示。
我们进一步假设运营商为每个硬 KPI 目标（即 type_i,m=hard 的 θ_i,m）分配一个固定的优先级类 ℓ_i,m∈ℒ={1,⋯,L}，其中较小的 ℓ_i,m 表示目标满足的优先级更高，且没有 xApp 可以更改此顺序。
给定时期 t 的 𝒫_i^t，xTRUCE 在当前 RAN 状态 s_t 下输出动作 a_t，从而产生性能缺口函数 g_i,m(a_t,s_t) 来衡量 KPI m 的预期与实际性能之间的差距。即，∀(i,m)∈ℛ_t，
g_i,m(a_t,s_t)=d_m(θ_i,m−ϕ_m(a_t,s_t)). (3)
这里，d_m∈{1,−1} 是偏好方向，其中 d_m=1 表示较大的 ϕ_m(a_t,s_t) 更好（例如速率），而 d_m=−1 表示相反（例如能量）。
显然，只有当满足 KPI 目标时才成立 g_i,m(a_t,s_t)⩽0，而正的 g_i,m(a_t,s_t) 等于未达到目标的缺口。
与隐式信任 xApp 代理推理的现有代理化 O-RAN 设计不同，我们的框架建立在以下假设的相反前提之上：
假设 1（不可信的代理提案）
网关接纳的 xApp 提案不受任何条件限制。
它们可能单独无法实现、相互矛盾或错误，xTRUCE 从不依赖它们的质量。
III-B 三层约束层级
xTRUCE 在时期 t 输出的动作 a_t 必须服从三层约束。
第一层包含物理 RAN 约束，例如发射功率预算，任何 xApp 或运营商意图都不能放宽。
在这种情况下，给定任何网络状态 s_t，我们将接纳的动作集合定义为：
𝒞_phys(s_t)={a_t∈𝒜 ∣ c_j(a_t,s_t)⩽0, ∀j∈𝒥_phys}, (4)
其中 𝒥_phys 索引所有预设的物理约束，c_j(a_t,s_t) 是通过将其所有项移到左侧而重写的第 j 个约束的公式，因此正的 c_j(a_t,s_t) 正好是限制 j 处的缺口。
第二层约束源自 O-RAN 维持网络可用性的刚性操作规则，例如受保护用户的保证速率，这只能由运营商修改，并可能涉及在上一时期执行的动作，记为 a{t-1}^exec。
同样，其接纳的动作集合为：
𝒞_oper(s_t,a_{t-1}^exec)={a_t∈𝒜 ∣ e_j(a_t,s_t,a_{t-1}^exec)⩽0, ∀j∈𝒥_oper}, (5)
其中 𝒥_oper 索引所有预设的操作约束，e_j(a_t,s_t,a_{t-1}^exec) 表示其第 j 个约束的缺口。
这两层刚性约束共同限定了一个安全动作集合：
ℋ_t=𝒞_phys(s_t)∩𝒞_oper(s_t,a_{t-1}^exec), (6)
使得每个动作 a_t∈ℋ_t 满足物理和运营商限制，且独立于 xApp 提案。这里，假设 ℋ_t 是紧致的。
此外，我们通过纳入 xApps 的 KPI 目标来识别第三层约束。
在假设 1 下，它们的目标不等式不需要共同可行，因此不包含在 ℋ_t 中，但将在后续处理中予以考虑。
显然，前两层决定哪些动作是可接纳的，而第三层决定哪个可接纳的动作是首选的。
为了确保每个时期都存在有效的 E2 控制动作，我们定义了一个基线动作为 a_t^base=π_base(s_t,a_{t-1}^exec)，它保留 a_{t-1}^exec 的配置组件，并在观察 s_t 时计算一个满足两个刚性层的保守实时组件 a_t^rt。
这样，a_t^base 易于获得，并在 xTRUCE 无法及时输出更好动作时作为底线动作。
此外，我们做出以下假设：
假设 2（认证的基线动作）
在每个时期 t，令 a_t^base∈ℋ_t，这也意味着 ℋ_t≠∅。
根据假设 2，物理限制和运营商规则之间的联合动作可行性得到了保证。
III-C 两阶段感知优先级的仲裁
当发生冲突时，多个 xApps 的硬目标可能不再在 ℋ_t 内共同满足，因此 xTRUCE 必须根据运营商预设的优先级决定放弃多少意图。
为此，我们设计了两阶段仲裁机制，其中阶段 I 确定从最高到最低优先级（即 ℓ_i,m）需要放宽硬目标的程度，阶段 II 最终确定要执行的安全动作。
III-C 1 阶段 I
对于每个硬目标对 (i,m)∈ℛ_t，我们首先通过 g_i,m(a_t,s_t)⩽ξ_i,m 引入一个非负松弛 ξ_i,m，因此 ξ_i,m 正好等于被迫接受的缺口。
由此，第 ℓ 个优先级类（即 ℓ_i,m=ℓ）中所有硬目标对的整体缺口现在由下式衡量：
V_ℓ(𝝃)=∑{(i,m)∈ℛ_t: ℓ_i,m=ℓ, type_i,m=hard} β_i,m ξ_i,m^2, (7)
其中 β_i,m>0 是运营商分配的目标权重，说明同一优先级类内不同目标的相对重要性。
显然，只有当类 ℓ 中的每个硬目标都满足时才成立 V_ℓ(𝝃)=0，而平方松弛的设计可以阻止将不可避免的缺口集中在一个目标上。
在每个时期 t，阶段 I 随后求解如下字典序违规优化问题：
𝐏𝟏: lex min{a_t∈ℋ_t, 𝝃⩾0} (V_1(𝝃), V_2(𝝃), ⋯, V_L(𝝃)) (8)
s.t. g_i,m(a_t,s_t)⩽ξ_i,m, ∀ hard (i,m)∈ℛ_t. (8a)
字典序最小化规定首先最小化 V_1(𝝃)，然后在保持该值的同时继续求解 V_2(𝝃)，依此类推，直到 V_L(𝝃) [32]。
在最小化 V_ℓ(𝝃) 时，每个更高优先级的 j<ℓ 受到 V_j(𝝃)⩽v_j^⋆ 的约束，并将获得的最优值记录为 v_ℓ^⋆。
注意，在上述过程中的任何时刻都不会放宽 ℋ_t，仅通过 𝝃 放宽 xApps 的 KPI 目标。
此外，求解 𝐏𝟏 并不能确保唯一的最佳动作，因为许多 a_t∈ℋ_t 可能同时达到最优，例如在所有硬目标共同适应的情况下，相应的动作产生 V_ℓ(𝝃)=0。
III-C 2 阶段 II
在此阶段，xTRUCE 将通过最小化来自 xApp 提案的所有软目标的缺口以及时期间的动作变化，从 𝐏𝟏 的动作解中选择最佳控制动作。
其优化问题变为：
𝐏𝟐: min_{a_t∈ℋ_t, 𝝃⩾0} ∑{(i,m)∈ℛ_t: type_i,m=soft} β_i,m [g_i,m(a_t,s_t)]+^2 + η D(a_t,a_{t-1}^exec) (9)
s.t. g_i,m(a_t,s_t)⩽ξ_i,m, ∀ hard (i,m)∈ℛ_t, (9a)
V_ℓ(𝝃)⩽v_ℓ^⋆+ϵ_ℓ, ∀ℓ∈ℒ. (9b)
这里，[⋅]+=max{⋅,0} 提取每个软目标对 (i,m)∈ℛ_t 的缺口，D(a_t,a{t-1}^exec)⩾0 衡量动作变化，3 3 3 D(a_t,a_{t-1}^exec) 的显式形式在不同的用例中可能有所不同，例如在以下第四节中被实例化为平方欧几里得距离。 η⩾0 是运营商分配的用于控制动作变化幅度的权重。
约束 (9a) 和 (9b) 要求每个优先级的缺口在 v_ℓ^⋆ 加上非负容差 ϵ_ℓ 内，从而保留阶段 I 的优先级排序。
在假设 2 以及 𝐏𝟏 和 𝐏𝟐 中函数在紧致集 ℋ_t 上的连续性下，两个阶段都能达到其最优，阶段 II 的动作记为 a_t^⋆。
此外，xTRUCE 在配置时期之间保持配置 a_t^cfg 不变，而在每第 T^cfg 个时期，它通过 𝐏𝟏 评估运营商规定的配置候选，并选择具有字典序最小 的那个。
然后，∀a_t∈ℋ_t，令 V_ℓ(a_t) 表示 (7)，其中 ξ_i,m 被 ξ_i,m=[g_i,m(a_t,s_t)]+ 替代。
两阶段仲裁产生的优先级行为陈述如下：
定理 1（两阶段字典序最小化）
阶段 I 的输出 是 ℋ_t 上唯一的字典序最小向量，且 ∀a_t∈ℋ_t，要么 V_ℓ(a_t)=v_ℓ^⋆, ∀ℓ，要么在它们不同的最高优先级类 ℓ 处有 V_ℓ(a_t)>v_ℓ^⋆。
此外，对于任意的 ϵ_ℓ⩾0，阶段 II 的输出满足 V_ℓ(a_t^⋆)⩽v_ℓ^⋆+ϵ_ℓ, ∀ℓ，如果所有 ϵ_ℓ=0，则等式成立。
证明：请参见附录 A。 ∎
定理 1 指出，将任何 V_ℓ 减少到低于 v_ℓ^⋆ 必然会使更高优先级类的缺口增加到其最优值之上，而阶段 II 在 (9b) 的类边界内选择最终动作。
此外，如果某些动作共同满足所有硬目标，显然我们有 v_ℓ^⋆=0。
III-D 冲突证书与延迟安全执行
如图 2 所示，在每个时期，xTRUCE 最终为 xApp 代理重新协商返回一个机器可读的冲突证书，并选择一个经过验证的 gNB 控制动作，从而确保不会执行任何延迟或未经验证的仲裁结果。
这两个结果详述如下。
III-D 1 带有价格的冲突证书
在每个时期，证书沿着慢速环路流向运营商和相关 xApps（每个只读取自身目标的条目），捕获两个关键点：每个硬目标被放宽的程度，以及 ℋ_t 的哪些限制导致了这种放宽。
前者是 𝐏𝟐 的 a_t^⋆ 处的实现缺口，记为 𝝃_t^⋆=[g_i,m(a_t^⋆,s_t)]+。
对于后者，我们将 𝐏𝟐 的每个约束与一个拉格朗日乘子相关联。
当 𝐏𝟐 是凸的并且满足如 Slater 条件 [33] 的约束规格时，最优乘子衡量由放宽其约束而引起的最优值的局部变化，这里我们将其称为价格。
这些条件与互补松弛性相结合，进一步保证了正价格能识别出紧约束。
如果没有这些条件，返回的价格仅是启发式局部诊断，没有全局保证。
通过仔细检查 𝐏𝟐，令 μ_i,m⩾0 表示约束 (9a) 的价格，μ_j⩾0, j∈𝒥_phys∪𝒥_oper 表示定义 ℋ_t 的第 j 个限制的价格，它们共同构成价格集 𝝁_t。
有了这些，冲突证书给出如下：
𝒵_t=(𝝃_t^⋆, 𝝁_t, ℱ_t, t), (10)
其中 ℱ_t 仅在每第 T^cfg 个时期产生，收集每个运营商规定候选 a_t^cfg 处的，从而解释最佳选择的原因。
时期戳 t 防止过期的证书影响后续决策。
简而言之，𝒵_t 以机器可读的形式提供了有关 xApp 或运营商关心的三个问题的信息：错过了什么，为什么，以及什么会有帮助。
证书以两种模式塑造了 II-B 节的慢速重新协商环路。
在自主模式下，它被返回给 xApp 代理以修改其未满足的目标，而在人在环模式中，它被报告给运营商以调整优先级，或者在特殊情况下调整操作限制，这是更改 𝒞_oper 的唯一途径。
值得注意的是，重新协商是否以及多快收敛取决于代理能力。
III-D 2 延迟安全动作执行
求解 𝐏𝟏 和 𝐏𝟐 可能会超出固定的每时期时间阈值，记为 τ。
为了处理这个问题，仲裁器维护一个备用动作 a_t^stb，首先用假设 2 的 a_t^base 初始化，然后在每第 T^cfg 个时期通过在 τ 之前可用的最佳配置候选相关的已验证阶段 I 动作进行更新。
结合所有潜在情况，xTRUCE 最终输出用于执行的 E2 动作（记为 a_t^exec）由下式确定：
a_t^exec = { a_t^⋆, 如果阶段 II 动作在 τ 之前可用, a_t^stb, 否则，如果在第 T^cfg 个时期更新, a_{t-1}^exec, 否则，如果 a_{t-1}^exec∈ℋ_t 仍然成立, a_t^base, 否则. } (11)
注意，(11) 选择的每个动作始终属于 ℋ_t，因为前两个是经过验证的，a_{t-1}^exec 被重新检查，而 a_t^base 满足假设 2。
最重要的是，物理和操作限制与代理的质量完全解耦，随着提案恶化或出现冲突，只有其意图的可实现性按优先级降低。
如果在 τ 之前没有可用的已验证 a_t^⋆，则将 𝝃_t^⋆ 和 𝝁_t 设为 ∅ 以指示没有新的阶段 II 最优性可用，而 ℱ_t 保留到那时为止完成的任何配置评估。

III-E 算法和复杂度分析
为了更好地展示代理化 O-RAN 的 xTRUCE 全貌，我们总结了其相关技术点并将其封装在下一页所示的算法 1 中。
关于算法 1 的计算复杂度，第 3 行在每个时期以 𝒪(NM) 时间处理最多 |ℛ_t|⩽NM 个目标，并在与 (4) 和 (5) 中限制数量成线性关系的时间内组装 ℋ_t。
主要成本在于优化调用，即第 4 行的基线求解，第 7 行或第 12 行每次求解 𝐏𝟏 背后的 L 类求解，以及第 14 行 𝐏𝟐 的单次求解，因此每个常规时期需要 (L+2) 次求解，每个配置时期需要 (CL+2) 次求解，其中 C 是配置候选集 Ω^cfg 的大小。
一旦实例化为凸规划，每次此类调用都可在多项式时间内求解到任何固定精度 [33]。
同时，在第 9、14 和 16 行中针对 ℋ_t 验证动作需要对限制和目标进行一次线性遍历，使得延迟安全规则 (11) 在任何中断时刻都是可负担的。

本节通过指定其状态、双时间尺度动作、KPI 映射、刚性约束和四个 xApp 角色来为多小区代理化 O-RAN 控制实例化我们的 xTRUCE。
IV-A 网络和 E2 控制动作
考虑由 ℬ={1,⋯,B} 索引的 B 个小区在由 𝒦={1,⋯,K} 索引的 K 个 RB 上服务由 𝒰={1,⋯,U} 索引的 U 个用户，每个 RB 带宽为 W Hz。
然后，我们将 a_t 的配置和快速组件实例化为：
a_t^cfg=({α_b(t)}{b∈ℬ}, {z_u(t)}{u∈𝒰}), (12)
a_t^rt=({x_{u,k}(t)}{u∈𝒰,k∈𝒦}, {p{u,k}(t)}{u∈𝒰,k∈𝒦}). (13)
这里，α_b(t)∈{0,1} 是小区激活/休眠状态（1 表示激活），而 z_u(t)∈ℬ 标识服务用户 u 的活动小区，其中 α{z_u(t)}(t)=1 且 𝒰_b(t)={u ∣ z_u(t)=b}。
在快速时间尺度上，x_{u,k}(t)∈[0,1] 是时期 t 中 RB k 分配给用户 u 的比例 4 4 4 这里，我们假设多个用户可以在一个时间复用一个 RB，并且一个用户使用的多个 RB 份额不需要在频率上相邻。 ，而 p_{u,k}(t)⩾0 是其平均发射功率。
值得注意的是，(12) 和 (13) 的组件是在 Near-RT RIC 侧管理的 RAN 控制，其中小区激活、小区到用户引导和 RB 份额已由现有的 E2SM 暴露 [2, 34]。
自然地，RB k 上的小区级发射功率为 P_{b,k}(t)=∑{u∈𝒰_b(t)} p{u,k}(t)。
IV-B RAN 状态和 KPI 模型
在此用例中，RAN 状态 s_t 包含时期 t 的信道增益、小区间干扰、队列积压和流量到达。
令 G_{b,u,k}(t)⩾0 表示小区 b 在 RB k 上到用户 u 的信道功率增益，并记 G_{u,k}(t)=G_{z_u(t),u,k}(t) 为服务小区增益。
然后，令 I_{u,k}(t)⩾0 为用户 u 在 RB k 上接收到的固定干扰功率（在时期 t−1 测量并视为在时期 t 已知，在时期之间更新）。
进一步，Q_u(t)⩾0 和 λ_u(t)⩾0 分别表示用户 u 的下行链路队列积压和每时期流量到达量，均以比特为单位。
同时，(1) 的 KPI 映射 ϕ 包含五个 KPI 族，包括 d_m=1 的用户速率以及 d_m=−1 的队列积压、每小区能耗、引起的干扰和负载使用。
首先，用户 u 的比特率（以 bits/s 为单位）由下式给出：
R_u(a_t,s_t)=∑{k∈𝒦} x{u,k}(t) W log_2(1 + G_{u,k}(t) p_{u,k}(t) / (x_{u,k}(t)(σ^2+I_{u,k}(t)))), (14)
其中 σ^2 是一个 RB 上的噪声功率。
注意，当 x_{u,k}(t)=0 时 R_u(a_t,s_t) 定义为零，而当用户 u 被调度时 p_{u,k}(t)/x_{u,k}(t) 是使用的发射功率。
长度为 τ 的时期内的队列更新（以比特为单位）为：
Q_u(t+1)=[Q_u(t)−τ R_u(a_t,s_t)]+ + λ_u(t). (15)
这反映了排队延迟，因为在给定到达速率下有界队列意味着由利特尔定律得出的有界延迟 [35]。
其余以 W 为单位的每小区功耗和干扰 KPI，以及无量纲的资源负载，分别为：
E_b(a_t)=P_b^cir α_b(t)+∑{k∈𝒦} P_{b,k}(t), (16)
I_b^out(a_t,s_t)=∑{k∈𝒦} ∑{u∉𝒰_b(t)} G_{b,u,k}(t) P_{b,k}(t), (17)
ρ_b(a_t)=1/K ∑{u∈𝒰_b(t)} ∑{k∈𝒦} x_{u,k}(t), (18)
其中，P_b^cir 是活动小区 b 的固定电路功率，ρ_b(a_t) 是其平均 RB 利用率。
与测量的 I_{u,k}(t) 不同，I_b^out(a_t,s_t) 取决于所选的发射功率，因此可以由 xApp 作为目标。
IV-C 物理和运营商限制
在 (12) 和 (13) 的上下文中，III-B 节的物理层由以下四个限制实例化：
{ c_1: ∑{k∈𝒦} P{b,k}(t)−α_b(t) P_b^max⩽0, c_2: ∑{u∈𝒰_b(t)} x{u,k}(t)−1⩽0, c_3: −x_{u,k}(t)⩽0, x_{u,k}(t)−1⩽0, c_4: −p_{u,k}(t)⩽0, p_{u,k}(t)−x_{u,k}(t) P^rb⩽0. (19)
这里，P_b^max 和 P^rb 分别是每小区和每 RB 的功率限制。
此外，约束 c_1–c_4 分别限制总小区功率、每个 RB 的总份额、单个 RB 份额以及分配给每个份额的发射功率。
然后，对于操作层，令 N^act(t) 和 N^str(t) 分别计算在时期 t−1 和 t 之间改变激活状态的小区和改变服务小区的用户。
同样，对于时期 t 的所有，运营商规则由以下五个限制实例化：
{ e_1: R_u^min−R_u(a_t,s_t)⩽0, ∀u∈𝒰^prot, e_2: |p_{u,k}(t)−p_{u,k}(t−1)|−Δ^p⩽0, e_3: |x_{u,k}(t)−x_{u,k}(t−1)|−Δ^x⩽0, e_4: N^act(t)−Δ^act⩽0, e_5: N^str(t)−Δ^str⩽0, (20)
其中最后两个仅在配置时期应用。
约束 e_1 为运营商指定的受保护用户组 𝒰^prot 中的每个用户强制执行承诺速率底线 R_u^min，而 e_2–e_5 分别限制功率、RB 份额、小区激活状态和小区到用户引导在连续时期的变化分别为 Δ^p、Δ^x、Δ^act 和 Δ^str。
(19) 和 (20) 共同确定了 𝒞_phys(s_t) 和 𝒞_oper(s_t,a_{t-1}^exec)，从而确定了 (6) 中的 ℋ_t。
对于阶段 II，𝐏𝟐 中的 D(a_t,a_{t-1}^exec) 由两个连续快速动作之间的平方欧几里得距离计算，给出为 D(a_t,a_{t-1}^exec)=∑{u,k} (x{u,k}(t)−x_{u,k}(t−1))^2 + ∑{u,k} ((p{u,k}(t)−p_{u,k}(t−1))/P^rb)^2，其中功率差由 P^rb 归一化。
基线动作 a_t^base 保留 a_{t-1}^exec 的配置，并从受限于 c_1–c_4 和 e_1–e_3 的最小化 ∑{u,k} p{u,k}(t) 的一次凸求解中获得。
由于只涉及一个没有任何松弛的线性目标，在每个时期求解成本低廉且快速。
IV-D 四个 xApp 代理的角色
每个代理充当在 Near-RT RIC 中运行的 xApp，由实时外部 LLM 或脚本规则赋能，在此用例中，总共有 4 个代理（即 N=4）被实例化以针对不同任务。
第一个代理，即 QoS 保证代理，仅针对 𝒰^prot 中受保护用户改进 (14) 中的速率 KPI R_u(a_t,s_t)，这被设置为优先级类为 1（即 ℓ=1）的硬目标。
至于每个非受保护用户，同一个 QoS 代理通过控制 (15) 的 R_u(a_t,s_t) 来减少 (15) 的积压 Q_u(t)，从而具有软速率目标。
除此之外，一个节能代理专注于每个小区减少 (16) 中功耗 E_b(a_t) 的软目标，而一个干扰协调代理则旨在针对 (17) 中引起的干扰 I_b^out(a_t,s_t) 的软目标。
最后，我们假设存在一个负载均衡代理，对 (18) 中负载 ρ_b(a_t) 的软目标发布每小区上限。
注意，这四个代理都没有直接命令 (12) 和 (13) 中的任何 RAN 控制动作变量，它们仅通过生成的提案影响动作结果。
IV-E xTRUCE 仲裁和精确价格
通过将 (14)–(18) 代入 (3) 的 g_i,m(a_t,s_t)，𝐏𝟏 和 𝐏𝟐 简化为关于快速变量 和松弛 𝝃 的规划，其中 a_t^cfg 在配置更新之间固定。
从 IV-D 节可以看出，硬目标仅为 ℓ=1 处的受保护速率实例，因此 𝐏𝟏 简化为仅求解 V_1(𝝃)。
在 (7) 的基础上进一步构建，𝐏𝟏 变为：
v_1^⋆ = min_{a_t^rt, 𝝃⩾0} ∑{u∈𝒰^prot} β_u ξ_u^2 (21)
s.t. θ_u−R_u(a_t,s_t)⩽ξ_u, ∀u∈𝒰^prot, (21a)
a_t=(a_t^cfg, a_t^rt)∈ℋ_t, (21b)
其中 (θ_u, β_u, ξ_u) 缩写了相应硬对 (i,m)∈ℛ_t 的请求速率目标、权重和松弛。
至于 𝐏𝟐 的实例化，四个代理的软速率、能量、干扰和负载目标通过相同的替换作为 [g_i,m(a_t,s_t)]+^2 项进入 (9)，从而给出：
min_{a_t^rt, 𝝃⩾0} ∑{u∈𝒰∖𝒰^prot} β_u [θ_u−R_u(a_t,s_t)]+^2 + η D(a_t,a_{t-1}^exec) + ∑{b∈ℬ} ( β_b^E [E_b(a_t)−θ_b^E]+^2 + β_b^I [I_b^out(a_t,s_t)−θ_b^I]+^2 OPEN + β_b^ρ [ρ_b(a_t)−θ_b^ρ]+^2 ) (22)
s.t. (21a), (21b), ∑{u∈𝒰^prot} β_u ξ_u^2⩽v_1^⋆+ϵ_1. (22a)
这里，(θ_b^E, θ_b^I, θ_b^ρ) 和 (β_b^E, β_b^I, β_b^ρ) 分别是节能、干扰协调和负载均衡代理在 (16)、(17) 和 (18) 上发布的每小区软上限及其权重。
约束 (22a) 对应于此实例下的约束 (9b)，使用 (21) 的单一输出 v_1^⋆。

对于任何给定的 s_t 和 a_t^cfg，(21) 和 (22) 关于 都是凸的。

定理 2 确保了 (21) 和 (22) 可以直接交给一些现成的凸规划工具（如 CVXPY [36]）以在多项式时间内最终确定 v_1^⋆ 和 a_t^⋆。
特别是，在每第 T^cfg 个时期，xTRUCE 在每个候选 a_t^cfg 下求解 (21)，在 ℱ_t 中记录每次完成的评估，如果所有候选都在 τ 之前完成，则在字典序最佳候选下求解一次 (22)。

需要强调的是，定理 2 仅表征了此特定用例的属性，而不是一般 O-RAN 场景的属性。
即使在非凸或延迟超时的情况下，动作仍将保持在 (11) 的验证结果上，因此仅丢失意图层最优性，而不会损害任何 gNB 控制安全。
V 实验评估
在本节中，xTRUCE 完全按照 II-B 节概述的四个设计目标进行评估：i) 独立于 xApp 提案的安全性，ii) 与优先级一致的目标满足度，iii) 证书引导的 LLM 重新协商，iv) 延迟感知的安全执行。
为此，我们在基于 OAI/FlexRIC 的 O-RAN 测试床上进行了多小区基于 Python 的仿真和 OTA 实验，使用相同的 xTRUCE 实现。

VI 结论
在本文中，我们提出了 xTRUCE 系统，这是新兴代理化 O-RAN 中多 xApp 冲突缓解功能的可证明实现。
它将不可信的 xApp 代理限制在结构化提案中，以可证明安全的方式根据运营商优先级分两阶段仲裁这些提案，并通过 E2 返回经过验证的 gNB 控制动作和用于 LLM 重新协商的精确冲突证书。
我们最终实现了其多进程原型，并通过仿真和 OTA 实验对其进行了评估。
结果展示了多种保证，涵盖在严重幻觉提案下的安全 gNB 控制、资源过载下与优先级一致的 KPI 目标满足、跨模型供应商的证书引导不可行 LLM 意图恢复，以及延迟安全的每时期执行。
这项工作可以作为探索代理化 O-RAN 安全多 xApp 控制的先驱，其中 Near-RT RIC 强制执行物理限制、运营商优先级和及时执行，而不依赖于单个 xApp 的正确性。
由于 xTRUCE 仅解决多 xApp 冲突并将上一时期测量的干扰视为常数，将其扩展到 Non-RT RIC 处 LLM 驱动的多 rApps 并纳入动态干扰漂移将是未来工作的两个有前途的方向。
