AWS 大幅简化 SageMaker 模型微调

📅 2026-10-23 📄 VentureBeat AI 🔗 原文链接

原标题：AWS just made it way easier to use SageMaker to fine-tune AI models for tool use and your firm's specific tasks

中文摘要： AWS 在 Amazon SageMaker AI 中正式推出 training sessions（训练会话）功能，开发者可通过 API 控制生成响应、计算并应用更新等训练操作，由 AWS 管理 GPU 执行，将细粒度编程控制与无服务器模式结合。该功能支持 LoRA 与完全微调，按处理 token 计费，评分期间计量暂停。初期支持 gpt-oss-20b 等四个模型，ImagineSoftware 和 Karini AI 为早期客户。但公告未提供量化投资回报数据，企业仍需自行定义并验证成功标准。

AI 智能体听起来可能很有说服力，却依然可能无法完成它被雇来要做的工作。要教会它选择正确的工具、遵循公司的工作流程并识别成功的结果，仅仅拥有一个强大的模型是不够的。对于自行定制模型的团队来说，这还可能意味着要管理每次实验背后昂贵的计算基础设施。

亚马逊云科技（AWS）正通过 training sessions（训练会话）来解决第二个问题，这是 Amazon SageMaker AI（其机器学习模型开发和部署平台）中的一项新功能。该公司于 10 月 22 日宣布正式上线，让开发者能够控制现有模型的学习方式，而由 AWS 来运营 GPU。

开发者团队/用户编写训练流程并定义如何衡量成功；SageMaker 负责分配计算资源、协调跨处理器的工作、从故障中恢复并保存训练进度。

对于开发专用智能体的企业来说，其吸引力在于灵活性与减少运营工作的结合。团队可以试验自己的反馈机制，而无需同时构建运行这些机制的基础设施。这是否能产生更好或更便宜的模型，仍然取决于任务、训练数据和评估。

与现有 SageMaker 定制功能的区别

SageMaker 多年来一直支持微调。AWS 曾于 2023 年 9 月记录了通过 JumpStart 定制 Llama 2 的方法，可使用可视化界面或其 Python SDK。

开发者还可以将自己的训练脚本带到 SageMaker Training Jobs 中。这提供了极大的灵活性，由 AWS 配置和管理机器，但客户仍需负责实例类型、训练环境和分布式训练配置等选择。因此，自定义训练逻辑本身对 SageMaker 来说并不新鲜。

AWS 于 2025 年 12 月增加了无服务器定制功能。团队可以选择支持的模型和训练技术，而由 AWS 选择计算资源。该公司表示，托管式多轮强化学习也早于今天的发布。

Training sessions 将更细粒度的编程控制与这种无服务器方法相结合。开发者通过 API 调用来指挥各个操作——生成响应、计算更新并应用更新——而由 AWS 管理 GPU 执行。他们的代码可以改变操作顺序、定义自定义学习目标并组合训练阶段。

这一进步是一种以更少基础设施配置运行自定义后训练的新方式。它扩展了 AWS 无服务器产品的灵活性；它并不是首次将微调或强化学习引入 SageMaker。

这种灵活性对于那些成功与否取决于多个操作的智能体非常重要。例如，一个内部支持智能体可能需要查阅文档、检查账户并选择升级路径。它的训练可以奖励成功解决问题的行为，同时惩罚未经授权的操作。

AWS 的公告描述了在更广泛的无服务器产品中同时支持低秩适应（LoRA，训练模型中相对较小的附加部分）和完全微调（更新模型的所有参数）。目前的 sessions cookbook 演示了 LoRA，但博客并未将这两种方法映射到每个模型。两者都是对预训练模型进行适配。

训练循环的工作原理

AWS 将工作分为客户代码和其托管服务两部分。

客户的软件负责指导实验、将智能体连接到工具或模拟环境，并对其行为进行评分。SageMaker 执行生成响应和更新模型所需的密集计算。

AWS 用组相对策略优化（GRPO）来说明这一点：模型对一个提示生成多个答案，客户的评分函数对其进行评估，训练服务利用它们的相对分数来指导更新。该过程使用修改后的模型重复进行。

AWS 的 training cookbook 解释说，模型在操作之间会保留在 GPU 内存中。开发者可以暂停以检查结果并调整流程，而强化学习实验可以在无需单独部署推理端点的情况下生成响应。

该 cookbook 提供了聊天微调、数学、编程和偏好学习的示例。AWS 还表示，它提供了智能体技能，帮助编码助手处理准备、训练、评估和部署等任务，支持 Kiro、Claude Code、Codex 和 GitHub Copilot。

这些辅助工具并不能消除对技术判断的需求。客户仍然需要决定模型应该学习什么、其奖励是否鼓励预期的行为，以及改进是否能在陌生示例的测试中保持。

早期客户聚焦理赔和工具使用

AWS 将 ImagineSoftware 和 Karini AI 列为早期采用者。

ImagineSoftware 使用该服务通过强化学习开发了一个用于分诊医疗理赔拒绝的模型。其数据科学高级副总裁 Rob Gontarek 强调了控制单个训练操作的能力。

"Training Sessions 为我们提供了向生产级性能推进的正确原语，"Gontarek 在 AWS 的公告中说。

Karini AI 使用该服务定制了 gpt-oss-20b，用于一个与 Amazon Neptune 知识图谱进行多步交互的智能体。CEO Nitin Wagh 强调了设置工作的减少以及从保存点恢复训练的能力。

"它给了我们的开发者想要的灵活性，同时减轻了他们的运营负担，"Wagh 在帖子中说。

这些例子表明了 AWS 正在追求的专用工作流程类型。它们并不能证明量化的投资回报：已发布的公告中没有包含客户在准确性、总成本或部署速度方面的对比数据。

Token 计费改变成本计算

AWS 表示，客户按处理的 token（模型处理的文本单位）付费，而不是预留 GPU 容量。当客户自己的评分代码评估一批数据时，训练会话的计量会暂停。

当评估结果在模型更新之间需要大量时间时，这一点可能很重要。然而，训练会话计量闲置并不意味着周围的应用程序是免费的：团队仍然需要为单独使用的计算、存储、评估服务和生产推理做预算。

AWS 的技术文档将计费分为输入处理、响应生成和训练三部分。因此，有意义的比较需要估算重复实验中这三项的总和。

发布帖子没有披露美元费率或具有代表性的总训练账单。AWS 引导客户查看其 SageMaker 定价页面。仅凭 token 计费并不能证明该服务比在专用基础设施上运行同等工作的成本更低。

四个发布模型，存在区域差异

AWS 已发布的公告确认支持 gpt-oss-20b、gemma-4-31B-it、Qwen3.6-27B 和 Qwen3.8-27B。

VentureBeat 查阅的公开模型表列出了前三个模型的区域，但尚未指明 Qwen3.8-27B 在哪些区域可用。

AWS 的 cookbook 指出北弗吉尼亚、俄勒冈和孟买为支持区域。模型表列出了 GPT-OSS-20B 在所有三个区域可用，而 Gemma-4-31B-it 和 Qwen-3.6-27B 在俄勒冈和孟买可用。

文档还设定了可调整的默认配额为两个同时进行的微调会话。

开发者可以使用 SageMaker Python SDK 和 cookbook 从自己的开发环境开始，或者在 SageMaker Studio 中工作。AWS 列出 SDK 路线支持 Linux 和 macOS，Python 版本为 3.10 至 3.12。

AWS 将企业基础设施带入竞争激烈的市场

AWS 正在进入一个成熟的训练服务市场，这些服务将算法设计与 GPU 管理分离。

Thinking Machines Lab 的 Tinker 提供了密切相关的方法，具有生成响应、更新模型和保存进度的接口。其公布的定价同样区分了输入处理、采样和训练。

对于已经在使用 AWS 的企业来说，潜在的优势在于训练如何融入现有的基础设施和控制体系。

AWS 表示，会话使用客户定义的访问角色，并且可以纳入客户管理的加密密钥和私有网络配置。训练数据和保存的模型检查点驻留在客户所选区域的 S3 存储中。该公司表示，它不会使用客户的数据或其定制的权重来训练另一个模型。

该帖子还指出了部署前的评估以及部署后的护栏和 CloudWatch 监控。这些是团队可以应用的控制措施，而不是定制模型自动满足其准确性或安全性要求的证据。

AWS 还表示，定制的模型可以在 SageMaker 上运行推理，而选定的模型可以导入到 Amazon Bedrock 中。这一限定很重要：该公告并未确立每个支持的模型都具有相同的部署选项。

对于买家来说，实际的测试是额外的训练控制是否能解决可衡量的业务问题。一个有用的试点项目会将定制模型与现有方法在任务完成率、失败率和总运营成本方面进行比较。

Training sessions 可以减少该实验中涉及的基础设施工作。更艰难的责任仍然在于企业：定义成功行为的样子，并证明模型已经学会了它。
