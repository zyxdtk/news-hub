📅 2026-08-11 📄 VentureBeat AI 🔗 原文链接

原标题：Four AI agents coordinating in real time outperformed Claude Opus 4.8 on enterprise coding tasks

中文摘要： Coral AI Labs等机构推出的AgentRadio异步消息传递层，解决了多智能体系统无法实时协调的缺陷。该架构允许智能体在执行任务时进行被动感知和实时通信，在SWE-Atlas QnA基准测试中，四个协作的Claude Code智能体任务准确率达62.1%，超越了更先进的单智能体模型。研究表明，合理的协调结构比单纯增加算力或扩大模型规模更有效，为企业级复杂代码库分析提供了新思路。

随着企业代码库规模的不断增长，负责分析这些代码库的 AI 智能体在面对需要多次交互和工具调用的长周期任务时显得力不从心。将工作分配给一个智能体团队似乎是显而易见的解决方案，但这引入了一个致命缺陷：大多数多智能体系统在设计上并不允许智能体在任务执行过程中进行实时的相互协调。

为了解决这个问题，Coral AI 实验室和多所大学的研究人员推出了 AgentRadio，这是一个异步消息传递层，允许智能体在执行步骤之间进行通信，而不会中断它们的主要工作。在子任务高度相互依赖的实际企业应用中，这种架构使智能体能够在中途进行纠正，而不是沿着死胡同一路走到正式审查阶段。

在生产代码库的长周期问题基准测试中，由 AgentRadio 驱动的智能体团队将四个独立工作的 Claude Code 智能体的任务准确率几乎提高了一倍。它还击败了运行在更先进模型上的单个智能体。对于 AI 从业者来说，AgentRadio 表明，正确的协调结构可以胜过单纯的算力和模型规模。

代码库理解的挑战

基于大语言模型（LLM）的智能体越来越能够处理需要与不同工具和环境交互的长周期任务。代码库理解代表了这一挑战的极端版本。它要求 AI 智能体构建软件、执行它、跨多个文件追踪执行路径，并在较长时间内综合证据。

在这些条件下，单智能体系统通常会因为“覆盖问题”而崩溃。

“单个智能体在代码库中遵循一条串行路径，”AgentRadio 论文的合著者 Xinxing Ren、Caelum Forder 和 Peter Carroll 向 VentureBeat 解释道。随着其上下文的增长，“最初的计划变得更难修改，并且在调查后期发现的线索并不总是能传递开来。” 模型通常可以执行单个步骤，但“困难的部分在于在整个漫长的调查过程中，保持每一项义务、依赖关系和矛盾证据都处于活跃状态。”

帮助衡量 AI 在大型代码库上表现的一个基准测试是 SWE-Atlas QnA。该基准测试包含针对实际生产代码库的长周期自然语言问题。这些任务无法仅通过探索代码来解决。AI 智能体必须运行软件并执行多条命令才能找到答案。

根据研究团队的实验，在 Opus 4.6 上运行的单个 Claude Code 实例仅解决了 32.3% 的这些任务。升级到像 Opus 4.8 这样更新的先进模型，成功率也仅为 57.2%。

一个自然的补救措施是将工作负载分配给多个智能体，让每个智能体处理更小、更清晰的上下文。当任务可以被干净地分解时，多智能体解决方案可以提供显著的性能提升，这意味着它们可以分别解决并在最后合并。

然而，代码库理解很少能被干净地分解。子任务是高度相互依赖的。一个智能体发现的关键配置文件或漏洞，可能会完全重写或改变另一个智能体的整个探索路径。由于这些依赖关系，智能体必须实时协调、协商并分享中间发现。


图片来源：VentureBeat 使用 Nano Banana Pro 制作

尽管有这种需求，但异步多智能体通信却很少见。研究人员指出，现有的多智能体系统通常分为三种有缺陷的模式：

  • 并行但孤立： 智能体同时运行但完全不通信。
  • 并行但回合同步： 智能体可以通信，但只能在严格的同步回合边界进行。这迫使智能体停下来等待彼此完成一个回合，然后才能辩论或交换中间发现。基于回合的系统假设重要发现可以等到下一个通信阶段，当智能体在实时系统的相互依赖部分工作时，这是一个代价高昂的假设。例如，调查 API 症状的智能体可能会发现使存储智能体当前假设无效的证据。“如果该信息等到两个智能体都完成后才共享，存储调查可能会沿着错误的路径完成，”研究人员说。
  • 相邻形式的异步： 这些系统提供有限的异步功能，例如自上而下的任务分发。它们没有智能体之间的点对点横向通道，也没有需要智能体主动暂停工作以读取更新的共享内存。

在他们的论文中，研究人员指出阻碍当前多智能体系统的主要瓶颈是“一个正在工作的智能体无法同时倾听。”

“据我们所知，目前没有系统能通过横向自然语言通道，让同时工作的智能体对彼此产生被动感知，”研究人员写道。

AgentRadio 的工作原理

为了消除工作与倾听之间的互斥性，研究人员开发了 AgentRadio，这是一个异步消息传递层，旨在直接插入现有的编码智能体外壳中。

AgentRadio 为智能体配备了三个原语：

  • create_thread 原语在参与的智能体之间开启一个对话。
  • send_message 原语将一条消息附加到线程中，并返回而不阻塞发送方智能体。
  • wait_for_mention 原语阻塞进程，直到一条提及调用者的消息到达。它传递该消息以及所有线程的完整快照，以便智能体获得即时上下文。

这三个原语使智能体能够拥有“被动感知”状态，在这种状态下，它们可以继续主要任务，同时在后台传递消息和更新知识。

AgentRadio 的代码采用 Apache 2.0 许可证在 GitHub 上开源。它被设计为轻量级，无需对 Claude Code 或 Codex CLI 等底层智能体外壳进行直接修改。


AgentRadio 架构（来源：arXiv）

该架构由两个主要部分组成：

  • 消息服务器： 一个独立进程，充当中央枢纽，为智能体组存储所有活动线程、消息和提及。
  • 外壳端集成： 智能体使用三个简单的 shell 脚本与服务器交互，每个脚本对应一个原语。

该系统工作的唯一严格要求是智能体外壳必须能够作为后台任务运行 shell 命令。智能体在其系统提示中被指示保持一个监视器运行，并通过提供的脚本发送消息。在后台运行 wait_for_mention 脚本允许智能体继续其工作并异步接收通知。

研究人员表示，要将此集成到现有技术栈中，团队仍然需要一个“轻量级适配器，用于启动工作进程、分配身份、将它们连接到共享服务器并管理最终综合”。这项工作围绕编码智能体进行，而不需要更改底层模型。

AgentRadio 实战

为了验证 AgentRadio 的实际效用，研究人员在 SWE-Atlas QnA 基准测试的 124 个任务上对该框架进行了测试。测试涵盖的系统设计、根因分析、安全和 API 集成等领域。

研究人员使用 Claude Opus 4.6 和 DeepSeek V4 Pro 作为骨干模型。对于外壳，他们评估了从单个 Claude Code 智能体 (B0) 到具有经典分工的智能体团队 (L1)，再到使用 AgentRadio 进行异步协调的智能体团队 (L3) 的配置。

实验结果表明，AgentRadio 通信架构优于简单的多智能体设置和单纯的算力扩展。

虽然使用 Opus 4.6 的单个 Claude Code 智能体仅解决了 32.3% 的任务，但完整的 AgentRadio 设置将这一指标几乎翻了一番，解决了 62.1% 的任务，并超过了运行在 Opus 4.8 上的单个智能体（后者为 57.2%）。它还将 DeepSeek V4 Pro 的结果从 29.0% 提升到了 50.8%。


AgentRadio 与单智能体系统对比（来源：arXiv）

为了理解这对企业 AI 的实际影响，论文重点介绍了一个涉及 MinIO 系统的实际任务。解决该任务需要检查每次请求的服务器日志，这是智能体在初始规划阶段未预料到的要求。

在 L2 设置中，智能体可以协作但缺乏异步通信，两个智能体在执行命令时独立意识到他们需要这些日志。由于它们无法在执行中途分享这一发现，一个智能体私下放弃了，另一个则未能将其提交给团队。在审查阶段，团队一致同意了错误的答案，漏掉了五个评分点。

激活 AgentRadio 后，智能体在执行中途发现了同样的问题，但一个智能体立即将所需的服务器端日志证据广播到了共享工作日志中。由于其他智能体在被动倾听，它们立即吸收了这一新证据。这种实时协调将一个失败的分数变成了满分 16 分。

“有用的区别在于时机，”研究人员说。“团队不需要另一个智能体或另一轮审查。它需要的是一个智能体的发现在其操作价值过期之前传达给正确的同伴。”


AI 智能体如何使用 AgentRadio 异步通信和相互引导（来源：arXiv）

研究人员指出，同样的模式也出现在企业事件处理工作中。例如，调查 API 症状的智能体可能会发现使存储智能体当前假设无效的证据。如果该信息等到两个智能体都完成后才共享，存储调查可能会沿着错误的路径完成。“被动感知让第二个智能体在其下一个工作步骤中纳入该矛盾，而不会中断已经在进行中的命令，”他们说。

协调的成本与复杂性

AgentRadio 需要固定的多智能体团队预算，这不可避免地增加了 token 成本。研究人员承认“这种代价是真实的”，并指出平均 API 支出从一个 Opus 智能体每任务 2.96 美元增加到了完整 AgentRadio 技术栈的 19.45 美元。

然而，单纯的规模并不等于性能。当研究人员通过在六次独立的 Opus 运行中花费 17.76 美元来进行计算匹配测试时，模型仅解决了 37.9% 的任务，而 AgentRadio 为 62.1%。这表明 AgentRadio 的架构是结构上的胜利，而不仅仅是暴力扩展规模的胜利。团队仍应注意智能体之间的 churn（无效周转）。“通信可以将智能体引向更好的证据，但也可能分散智能体对有效路径的注意力，”研究人员警告说。

固定的多智能体团队不应成为每个工程任务的默认响应。研究人员表示，确定是否需要多智能体设置的更有用的测试是任务是否包含“责任断点”。这些是“胜任的工程师会让另一个人参与进来的地方，因为工作跨越了所有权边界、需要独立的假设，或者具有足够的风险来证明单独验证的合理性。”

“当任务可以分解、产生的部分保持相互依赖、单智能体成功率不可靠，并且不完整的答案具有有意义的下游成本时，协调是一个非常合适的选择，”研究人员说。例子包括代码库范围的架构问题、不熟悉的遗留系统、跨服务事件调查、安全分析、依赖迁移和多模块重构。

相反，对于“有界的、局部的和可逆的工作”，单个智能体仍然是更简洁的选择，例如已知单文件更改或样板代码生成。

“只要一个上下文还能诚实地拥有这个问题，就使用一个智能体，”研究人员说。“当现有智能体否则需要压缩掉证据、跨越独立的所有权边界，或验证其自身的高影响力结论时，再引入另一个责任方。”

从研究到商业化：Coral Code

虽然 AgentRadio 作为一个使用固定四智能体团队和五阶段协议的受控研究实现，但其底层原理正被改编成一款名为 Coral Code 的商业产品。

Coral Code 不是将僵化的多智能体协议应用于每个工单，而是自下而上地工作。工程师从他们现有的编码智能体开始，只有当新出现的证据证明其合理性时，Coral 才会引入代码库范围的调查、专家责任和通信。“Coral 将工程师已使用的工具周围的操作关注点打包，在智能体外壳周围而不是内部提供代码库上下文、范围专家、通信和证据层，”研究人员说。

这种动态方法通过针对相关单元来优化成本：即完成的、可审查结果的成本。

自主软件工程的未来

虽然 AgentRadio 对智能体编排进行了重大升级，但仍有障碍需要克服。研究人员指出的一个主要瓶颈是“注意力治理和验证”。

“被动感知使通信在执行期间可用。它并不决定应该存在哪些智能体、哪个发现值得中断、谁应该接收它，或者证据何时足够强大以修改计划，”研究人员说。如果每个智能体都收到每次更新，通信层就会变成噪音。如果几个智能体共享同一个错误假设，更快的通信可能会传播错误。

例如，在论文中涉及 Grafana 平台的案例研究之一中，九个评分点中有四个需要否定性结论，例如观察到数据源选择器没有自动选择。智能体运行了相关测试，但没有一个形成缺失的否定假设。两种配置都在这四个评分点上失败了。

“被动感知可以分发某人开发的想法。它无法提供团队中从未出现过的概念，”研究人员说。

随着任务持续时间拉长，通信和协调变得至关重要。“下一代系统……需要自适应的责任分配、证据感知路由、冲突解决、明确的成本限制、权限、恢复和清晰的人工升级点，”研究人员指出。最重要的是，它需要持久的来源记录，以便工程主管可以检查哪个智能体提出了主张以及为什么接受某个操作。

“运行时间更长的智能体使通信变得更加重要。它们也使得问责制更难伪造，”他们说。
