面向LLM分析的长文档索引

原标题：Indexing Long Documents for LLM-Based Analysis

中文摘要： 本文提出一种面向长文档分析的层次化纯文本索引方法。受B+树启发，该索引由LLM自动构建，每个文档仅需编译一次，包含从根节点概述到叶节点细节的多层摘要。它克服了向量检索丢失上下文及结构化提取缺乏灵活性的问题。在NarrativeQA数据集上的实验表明，该方法准确率与最强基线DocETL相当，但回答问题的成本降低了40%。

摘要。
临床记录、法律合同和科学论文等长文档越来越多地使用大语言模型（LLM）进行分析。自然地，为每个问题将完整文档输入模型最终会变得缓慢、昂贵、容易产生幻觉，并且不会在不同问题间复用工作。我们探索了一种基于索引的文档分析解决方案，并提出了一种层次化的纯文本索引，该索引每个文档构建一次，供后续查询参考。受经典 B+ 树启发，该索引将文档组织成页面，从根节点的通用摘要排列到叶节点的具体摘要，但在三个方面有别于 B+ 树以适应 LLM 访问：内容存在于每一层；索引是纯文本而非属性值；导航遵循页面摘要间的相关性而非比较搜索键。其结构由 LLM 针对每个文档发现，而非人工设计。在 NarrativeQA 数据集上的初步评估中，该索引达到了与最强基线 DocETL 相当的准确率，而回答问题的成本低了 40%。

1.
引言
长文档分析是一项重要但昂贵的任务。临床记录、法律合同和科学论文经常需要深入检查，手工分析它们既缓慢又费时。当同一份文档必须被多次分析时，费用会进一步增加：临床医生会随着时间的推移查阅患者记录，合同会在许多事务中被重新审视，而科学论文会被用于查询许多不同的研究问题。
最近一条有前景的工作路线是使用大语言模型（LLM）自动完成这项工作，回答以前的关键词和提取工具无法回答的自由格式问题
(
Shankar et al., 2025a
;
Patel et al., 2025
)
。
当 LLM 在每个问题上被提示完整文档时，回答成本随文档大小线性增长。长上下文自身也带来了一个问题：随着输入增长，模型更频繁地捏造答案，其比率随上下文长度急剧上升，即使答案存在于文档中
(
Liu et al., 2024
)
。
DocETL
(
Shankar et al., 2025a
)
，连同诸如 Lotus
(
Patel et al., 2025
)
和 Palimpzest
(
Liu et al., 2025
)
等相关声明式管道，通过智能体查询重写和分块执行使分析更强大。这些系统是无状态的：它们在查询之间不维护状态，从头开始处理原始文档上的每个问题，这导致了两个后果。首先，优化单次处理只能提供有限的加速。其次，每个问题都会产生全部成本，因为没有任何东西在它们之间被摊销。
一个自然的优化是预计算一些中间状态一次，并在不同问题间复用它。有两类方法做到了这一点。
第一类在文档上建立向量索引。
检索增强生成
(
Lewis et al., 2020
)
将文档拆分为块并将每个块嵌入为向量；GraphRAG
(
Edge et al., 2024
)
和 LightRAG
(
Guo et al., 2025
)
在其之上为跨越整个文档的问题添加了图结构和社区摘要。共同的局限性是向量索引本身：拆分破坏了遥远段落之间的联系，而 top-k 检索只呈现少数几个，因此整个文档的问题返回不完整的上下文；固定维度的嵌入是有损的；并且索引与一个模型绑定，因此每当该模型改变时就必须重建。
第二类将选定的属性提取到结构化表中。
信息提取系统如 Evaporate
(
Arora et al., 2023
)
、Doctopus
(
Chai et al., 2025
)
和 ZenDB
(
Lin et al., 2024
)
做到了这一点；结果对于过滤式查找是精确的，但无法回答开放式的自然语言问题，并且属性必须在任何人知道将要问什么之前就被固定下来。
在本文中，我们探索了一条不同的路径。
我们回归数据库文献中的成功原则，在不扫描大量数据的情况下回答许多查询，这正是索引，特别是 B+ 树
(
Comer, 1979
;
Bayer and McCreight, 1972
)
几十年来已经解决的问题。
我们读取每个文档一次，并将其编译成一个任何 LLM 都可以直接读取的层次化纯文本索引：根节点上有一些高级摘要，其下是主题级摘要，叶节点上是详细的页面摘要。该索引每个文档构建一次，供每次后续分析参考，就像数据库索引构建一次并被每个查询复用一样。
这保持了向量索引和结构化提取共享的复用优势，同时避免了各自的弱点。像向量索引一样，它构建一次并被复用，但因为它是纯文本，所以与模型无关，并保留了分块所破坏的跨文档连接。像结构化提取一样，它对文档施加组织，但由于该组织是由 LLM 发现的而不是固定在模式中，它回答深度的、开放式的问题，而不仅仅是过滤式查找。每个节点都是一个简短的摘要，大小足以舒适地适应模型的上下文窗口。
尽管索引借用了 B+ 树的形状和页面上的层次化访问，但它在三个方面偏离了它以适应 LLM 访问。内容存在于每一层，而不仅仅在叶节点，因此许多问题从内部摘要就能回答而无需进一步下降，就像覆盖索引仅从索引回答查询而不触及基表一样
(
Graefe, 2011
)
。索引是纯文本而不是嵌入向量，因此任何模型都可以读取它，并且上下文在构造中被保留。导航是语义的：模型判断哪些摘要是相关的而不是比较搜索键，因此相同的索引服务于开放式分析，而不仅仅是精确匹配或范围查询。
在这项工作中，我们探索了这种新型索引的设计：其结构如何从语料库中发现而不是人工设计，每个文档如何被编译进其中，以及如何针对它回答问题并随着时间推移细化索引。
第 2 节更详细地检查了当前实践的局限性。第 3 节介绍了索引及其三个设计组件。第 4 节报告了在 NarrativeQA 上的初步评估，第 5 节进行总结。
2.
相关工作
我们将现有的基于 LLM 的长文档分析工作分为三类，并指出各自的局限性。
第一类通过直接阅读文档来回答每个问题，在问题之间不保留任何内容。最简单的版本将整个文本连同问题一起输入模型。更发达的管道分解工作：DocETL
(
Shankar et al., 2025a
)
将分析分解为块上的一系列操作符，并使用智能体重写来提高准确性，后续工作将这一路线扩展到交互式引导
(
Shankar et al., 2025b
)
和多目标重写
(
Wei et al., 2026
)
；相关的声明式系统如 Lotus
(
Patel et al., 2025
)
和 Palimpzest
(
Liu et al., 2025
)
优化了类似的管道。这些系统很灵活且无需设置，但在问题之间不复用任何内容，因此成本随每个问题增长，并且长上下文掩盖了相关细节，增加了长输入上的幻觉
(
Roig, 2026
)
。
第二类通过构建可复用的中间状态来避免重新处理。检索增强生成
(
Lewis et al., 2020
)
将文档拆分为块，将每个块嵌入为向量，并在查询时检索最接近问题的块。GraphRAG
(
Edge et al., 2024
)
和 LightRAG
(
Guo et al., 2025
)
在块之上添加结构——前者是带有社区摘要的实体图，后者是更轻量的双层图——用于同时利用文档许多部分的广泛问题。最接近我们设计的是 RAPTOR
(
Sarthi et al., 2024
)
，它递归地聚类和总结块成一棵摘要树，很像我们的方法。所有这些都共享两个局限性：索引与一个嵌入模型绑定，因此改变其中任何一个都会强制重建；并且分块和 top-k 检索是有损的，破坏了遥远段落之间的链接并且只返回少数块，因此整个文档的问题很容易被遗漏。RAPTOR 也不例外，因为它的树是通过聚类自底向上构建的，并通过相似性进行查询，使其节点成为检索目标，而不是可以直接读取和导航的纯文本模式。
第三类提前将选定的属性提取到结构化表中，如 Evaporate
(
Arora et al., 2023
)
、Doctopus
(
Chai et al., 2025
)
和 ZenDB
(
Lin et al., 2024
)
。然后查询是一种结构化查找，对于可以写成已知字段上的过滤或聚合的问题来说，这既快又精确。然而，有两个主要局限性：模式通常在工作负载已知之前就被固定，因此没有人预料到的属性根本不存在；并且结构化表可能不适合自由格式的问题，例如“为什么一个角色背叛了同伴”，这需要跨文档进行综合而不是简单的值查找。
3.
方法
3.1.
概述
我们提出的索引是一个每个文档编译一次的层次化纯文本结构（图 1）。在顶部，一个根节点（巨型摘要）给出了文档的概述，并指向其下方的广泛领域，称为类别。一个类别可以独立存在或拆分为子类别，因此索引具有一层或多层，具体取决于文档如何划分。在最底层之下是主题，即具体内容，例如剧本中的角色或事件，每个主题记录一小组直接从文档填写的字段（关于该特定角色或事件的细节）。每个页面，无论是根节点、类别还是主题，都是纯文本，且足够小以适应 LLM 的上下文窗口。
其余部分将贯穿三个设计问题：结构是如何决定的（第 3.2 节），文档是如何被编译进其中的（第 3.3 节），以及如何针对它回答问题（第 3.4 节）。

3.2.
发现结构
对于每个源文档，LLM 阅读它并为索引提出一个模式：类别和字段的层次结构。在顶部，一个称为巨型摘要的简短概述位于根节点。在其下，LLM 将文档组织成类别，在每个类别下，组织成具有一小组字段（关于每个条目要记录的细节类型）的主题。例如，在电影剧本上，模式可能在根节点提出一个电影范围的概述，其下有角色、事件和事实类别；角色下的主题将记录诸如角色、行动和关系等字段。我们不规定模型应该产生哪些类别或字段；两者都是由模型从它在文档中看到的内容提出的。
主题和填充其字段的值留待编译期间确定（第 3.3 节）。在当前的实现中，我们保持每个主题较小，每个字段有固定的上限。一种更原则化的机制会限制每一层的链接数量，类似于 B+ 树的扇出，因此随着索引增长，查找保持高效；设计这样的机制是我们留给未来工作的方向。
3.3.
编译文档
编译完整阅读文档并从发现中填充模式。它分三步运行：清理、提取和写入。
清理。
原始文本被去除下载伪影和标记，然后被分割成大约 30,000 个字符的块，重叠 2,000 个字符，以便一个块边缘的段落也完整地出现在下一个块中。
提取。
发现中的模式作为提取提示的一部分交给 LLM：它告诉模型要寻找哪些类别以及在每个类别下要填写哪些字段。对于每个块，模型根据此模式阅读文本并返回它找到的主题（符合每个类别的角色、事件和事实）及其字段。类别本身从不改变；只有每个类别下的主题列表会增长。例如，在剧本中，如果块 1 提到了两个事件，事件类别就获得两个主题；如果块 2 又提到了一个，它就再增加一个。我们将所有类别及其下主题的运行记录称为合并记录。对于填充字段，保留第一个非空答案；如果后面的块提供了不同的答案，两者都被保留，因此文档所说的任何内容都不会被悄悄丢失。每个提取的字段还标记有产生它的段落的源偏移量，因此主题上的任何值都可以追溯到原始文本。
写入。
写入产生每个主题一个文件，归组在其类别下，并在根节点产生一个概述文件总结模式，与图 1 中的层次结构相匹配。
3.4.
回答查询
为了回答问题，系统导航索引。每个主题带有一个简短摘要；导航根据问题对这些摘要进行评分，以决定下一步去哪里。它从巨型摘要（根节点）开始并沿着最相关的链接，下降到类别，跨越到相关主题，或者在一个区域被耗尽时退回。
下降到索引中是无界的：系统可以沿着一条有希望的路径深入到索引允许的深度，并访问相邻页面。有界的是它可以升级以重新访问更高节点然后下降到不同分支的次数，因此遍历不会在索引中无限游荡。我们目前将此分支预算设置为一个固定值，对每个问题都相同；更智能地决定它，例如根据问题的复杂性或索引的大小，留待未来工作。当到达的页面不包含答案时，系统回退到源文档中最相关的部分并从那里回答。索引在未命中时不更新；将回退结果折叠回索引是我们在第 5 节中涉及的方向。
4.
初步评估
4.1.
实验设置
我们在 NarrativeQA 数据集上进行评估
(
Kočiský et al., 2018
)
，使用十部电影剧本和与它们配对的 295 个问题；剧本长达数百页，问题是自由格式的，这接近我们目标的设置。GPT-5 作为编译器和问答模型，LLM 评委根据参考答案对答案等价性进行评分。我们与全文档基线（每个问题将整个剧本输入模型）、DocETL 管道
(
Shankar et al., 2025a
)
和三个检索基线（RAG
(
Lewis et al., 2020
)
、GraphRAG
(
Edge et al., 2024
)
和 RAPTOR
(
Sarthi et al., 2024
)
）进行比较。
我们报告两项指标。
准确率是 LLM 评委判定与参考答案等价的答案比例。
成本是系统消耗的输入 token 总数，我们将其分为一次性索引构建成本和回答每个问题的经常性成本。所有数字均来自每个系统的完整自动化运行，没有人工干预或手动调整的估计。
4.2.
结果
图 2.

图 3.
每个系统的总输入 token 成本，分为一次性构建（褪色）和每查询批次回答的经常性成本（实心），针对十部电影的 295 个问题。我们的索引支付一次性构建成本和较低的边际回答成本。
图 2 给出了准确率排名。我们的索引达到了 55.9% 的评委准确率，基本上匹配了最强基线 DocETL 的 57.3%；差距大约是一个半百分点，大约是 295 个问题中的四个。它也优于将整个剧本输入模型（52.9%）。三个检索基线落后：GraphRAG 达到 43.7%，RAPTOR 38.0%，RAG 35.4%。它们在长剧本上挣扎，因为它们只保留了文档的一小部分。RAG 的分块检索每个问题只返回少数段落，而 GraphRAG 的提取器产生一个稀疏的图（每部电影大约 63 个节点，其中 88% 是断开的），因此自由格式问题所依赖的文档部分通常缺失。对于 RAPTOR，我们应用了系统的严格规则：当检索到的节点或 top-k 块缺少答案时，它必须返回未找到，而不是从上下文中猜测，因此所有系统都在同等基础上被评判。
图 3 将每个系统的成本分为经常性每查询回答（实心）和一次性构建（褪色）。我们的索引花费 2.1M token 构建索引一次，花费 1.2M 回答所有 295 个问题，每个问题的边际成本约为 3.9K token。DocETL 和 GPT 基线不带有构建成本，但其全部 12M token 都是经常性的，DocETL 每个问题大约 41K token。因为构建成本支付一次并在随后的每个问题中摊销，我们 3.3M 的总数比 DocETL 的 12.1M 低约 73%，比全文档基线的 12.0M 低 73%。
图 4 将每个系统置于回答成本与准确率的平面上；我们在这里只计算推理 token，并排除一次性构建成本，以便每查询的经济性可以直接比较。我们的索引位于准确率范围的顶部附近，同时花费的推理 token 比任何其他系统都少：在 1.2M 时，它回答了所有 295 个问题，甚至比检索基线还要少，包括 RAPTOR 的 1.7M，同时达到了与 DocETL 几乎相同的准确率，而每问题成本只是其一小部分。

5.
结论与未来工作
我们探索了一种基于索引的长文档分析解决方案，并提出了一种编译的、层次化的纯文本索引：每个文档构建一次，像 B+ 树一样组织，但在每一层都有内容，其结构从语料库中发现而不是人工设计。在 NarrativeQA 上，该索引以低 40% 的成本匹配了最强无状态基线的准确率，同时保持与模型无关并能够回答开放式问题。这些结果是初步的，且局限于叙事文本，但它们表明该设计值得追求。
目前，我们通过固定每个页面记录多少的上限来保持页面较小，这对每个文档都是相同的，并且我们不限制页面数量或平衡层次结构。一种更原则化的方案会从单一约束中推导出这些限制，即问答模型在其准确率于长输入上下降之前能使用多少上下文
(
Liu et al., 2024
)
。
然后，索引将由单一的递归规则构建，如果可以的话，将节点的内容适应在一页上。否则，节点应拆分为子节点并对每个子节点应用相同的规则，因此深度只随内容强制而增长，而不是预先固定。这引发了我们要研究的进一步问题：给定大小的文档应该引起多少层，如何选择每个内部节点的摘要以便它指导导航而不复制其下方的页面，以及如何限制节点的子节点以便随着索引增长查找保持高效。另一个方向是索引在查询时是否应该改变：今天它一旦编译就固定了，当问题超出它时只是报告未命中，但一个更强大的系统会在未命中时重新阅读源文档，将其发现折叠回索引中，并最终朝着实际被问到的问题增长新的结构，而不会膨胀回完整文档的副本。我们接下来要进行的工作是解决这些问题，同时跨更多领域验证该方法并为每个领域重新校准评委。
