摘要。
AI 编程智能体是一类通过推理和工具使用自动化开发任务的的软件工具，它们正越来越多地通过插件市场进行扩展，然而这些新兴仓库的结构、维护和协同演化动态在实证层面上仍未被探索。
与通过源代码交付功能的传统软件包不同，智能体插件通过自然语言指令文件、脚本和配置文件的组合来交付功能，这引发了一个问题：这些插件是需要跨组件协同演化的维护工件，还是开发者编写后无需再回顾的一次性工件。
为了研究智能体插件的维护和协同演化，我们对托管 Claude Code 插件市场的 1,926 个仓库进行了实证研究，分析了 2,018 个市场中的 8,351 个插件和 77,773 次提交。
我们发现市场正在迅速扩张，在 2025 年 10 月发布后的六个月内，涉及插件的提交活动增长了 8.8 倍，而针对软件工程任务的插件占所有插件的 61.3%。
插件开发主要由功能驱动，功能提交的发生率是传统开源软件 (OSS) 的两倍多（39.6% 对 17.2%）。Claude 共同参与了 34.9% 的提交，并且四种提交类型（docs、perf、style 和 refactor）在插件仓库中的含义与传统软件大不相同。
大多数组件类型独立演化，但在 skills 目录中，自然语言指令文件和实现脚本以高于随机概率的速率协同演化，78% 的共同变更是功能耦合的，这代表了一类在传统软件工程中未观察到的新的维护依赖关系。
这些发现将 AI 原生插件仓库特征化为一类独特的软件，其开发实践和维护依赖需要专门的实证框架。

为了研究智能体插件的维护和协同演化，我们调查了以下三个研究问题 (RQs)：
RQ1：Claude Code 插件市场的结构和维护特征是什么？
智能体插件市场已成为跨团队和社区分发扩展的关键渠道。
然而，开发者构建什么类型的插件，这些市场是否显示出积极和持续维护的迹象，或者其结构与传统包生态系统相比如何，这些都尚未被理解。
我们的分析表明插件市场正在扩张，涉及插件的提交活动在六个月内增长了 8.8 倍。
市场以用于软件工程任务的插件为主，34.4% 的插件结合了多种组件类型（例如，技能与钩子或智能体配对）。
我们的研究为这类工件提供了第一个实证基准，涵盖了其结构组成、维护模式和组件演化。
RQ2：插件是如何开发和维护的？
智能体插件仓库主要由面向 LLM 的自然语言指令以及脚本和配置文件组成，这引发了这样一个问题：在插件仓库中发生的相同类型的开发活动是否与传统开源软件 (OSS) 具有相同的含义。
我们根据广泛接受的约定式提交规范 (CCS) 定义
(
Conventional Commits, 2024
)
检查了智能体插件仓库中提交的开发和维护活动。
我们的分析揭示，与传统 OSS 相比，在智能体插件仓库中，标记为文档、性能、风格和重构的提交中，实际开发和维护行为已偏离了 CCS 类别的定义。
RQ3：插件组件如何协同演化？
随着 34.4% 的插件结合了多种组件类型，这些组件在维护期间是否协同演化仍然是一个悬而未决的问题。
未能正确更新协同演化的组件会面临使组件不同步的风险，这可能会引入不一致和隐性缺陷。
我们的结果表明，大多数组件可以独立维护。
然而，我们发现 skills/ 中的 78% 的脚本-Markdown 共同变更是功能耦合的，这是由接口更改、内部逻辑更新和从脚本传播到其配对的自然语言指令文件的变量同步所驱动的。

2.2.
软件包生态系统
实证软件工程在研究软件包生态系统方面有着悠久的传统，我们将其扩展到新兴的智能体插件市场类别。
几项研究通过依赖网络的视角分析了传统软件包注册表的结构和演化。
Kikas 等人 (2017)
分析了 npm、RubyGems 和 Cargo 中的依赖网络，发现传递依赖快速增长，并且生态系统之间存在显著的结构差异。
Decan 等人 (2019)
将此比较扩展到七个打包生态系统，总共托管了超过 830,000 个包和 580 万个版本，发现所有生态系统在包数量和更新频率上都随时间持续增长。
虽然这些研究关注包之间的依赖关系，但我们研究 Claude Code 智能体插件市场作为一类新的 AI 原生软件，其中分发的工件是自然语言指令文件、脚本和配置文件，而不是编译的包。
Onagh 和 Nayebi (2025)
研究了 GitHub Marketplace 中的扩展决策，分析了来自 3,869 个提供商的 6,983 个 CI Actions，发现该市场每年增长约 41%，并且 65% 新发布的 CI Actions 在原始工具发布后的六个月内复制了现有功能。
虽然 Onagh 和 Nayebi 研究的是非 AI 代码扩展市场 (GitHub CI Actions) 中的功能复制，但我们研究的是智能体插件市场，其中的工件是自然语言指令文件，而不是可执行的操作。
Hassan 等人 (2024)
引入了 FMware 的概念，即以基础模型为核心组件的软件，并编目了当自然语言成为主要软件工件时出现的工程挑战。
Li 等人 (2026a)
在此基础上，对来自 92 个 GitHub 仓库的 24,800 个开源提示进行了实证研究，引入了 promptware 作为使用自然语言提示构建的 FMware 的特定实例。
作者发现提示主要存储在 Markdown 中 (72.8%)，其中 38.5% 表现出语义重复，80.1% 低于标准阅读易度阈值，这表明自然语言软件资产面临着与传统代码类似的维护挑战。
Claude Code 智能体插件是 promptware 的一个实例，其区别在于它与在同一仓库内协同演化的可执行脚本和配置文件共存。
几项研究对通用 AI 助手插件和扩展生态系统进行了实证分析。
Su 等人 (2025)
从 GPT Store 中挖掘了 722,349 个 GPT，大规模分析了该平台的分类系统、交互模式和用户行为。GPT 是通过自然语言指令和知识文件构建的。
Yan 等人 (2024)
对 ChatGPT 插件商店进行了首次全面特征化，使用零样本 NLI 分类将 1,038 个插件分类为 21 个功能类别。ChatGPT 插件是由 JSON 清单文件描述的 API 集成。
他们发现功能分布不均，超过一半的插件集中在五个类别中：数据与研究 (12.9%)、工具 (11.2%)、商业 (10.1%)、开发者与代码 (9.7%) 和娱乐 (6.7%)。
虽然 Su 等人和 Yan 等人研究的 AI 助手商店的工件不携带版本化的开发历史，但 Claude Code 智能体插件是结合了自然语言指令文件、可执行脚本和配置文件的 GitHub 仓库，能够对开发实践和组件协同演化进行提交级别的分析。
Ling 等人 (2026)
对来自 skills.sh 市场的 40,285 个智能体技能进行了大规模分析，发现技能高度集中在软件工程工作流中，并且存在广泛的意图级冗余。
Zhu 等人 (2026)
通过检测跨 20,000 个技能的多模态克隆关系扩展了这项工作，发现 75% 的技能至少参与一个克隆对，并且生态系统因未声明的重用而膨胀了 3.5 倍，其中 40% 的克隆对跨越了作者边界。
虽然 Ling 等人和 Zhu 等人研究的是技能工件，但我们研究的是 Claude Code 插件市场，其中技能是通过专用市场分发的结构化多组件插件系统内的一种组件类型。表 2 总结了这些研究与我们的研究之间的差异。
2.3.
提交分类和 AI 贡献
在约定式提交规范之前，研究人员提出了用于分类软件更改的手动分类法。
Swanson (1976)
引入了最早的分类法之一，区分了纠正性、适应性和完善性维护。
Hindle 等人 (2008)
通过手动分类跨九个 OSS 项目的 2,000 次大型提交扩展了这一工作，引入了包括实现、模块管理和非功能性更改在内的其他类别，并发现大型提交更多是完善性的，而小型提交更多是纠正性的。
Bhatia 等人 (2023)
进一步将 Hindle 等人的分类法扩展到 ML 研究仓库，发现 ML 特定的工件需要两个新的顶级类别（数据和依赖管理）和 16 个新的子类别，表明当主要工件偏离传统源代码时，提交分类法需要进行调整。
约定式提交规范 (CCS)
(
Conventional Commits, 2024
)
标准化了 11 种提交类型，提供了一种机器可读的模式，用于传达更改的意图，并在开源项目中得到越来越多的采用。
Zeng 等人 (2025)
研究了来自 116 个明确采用 CCS 的传统开源项目的 88,704 次提交，发现 fix 和 chore 一起占提交的 53%，并且由于类型定义重叠，开发者经常误用 CCS 标签。
虽然 Zeng 等人 (2025) 研究的是传统开源项目中 CCS 的采用，但我们研究的是插件市场中的提交类型分布，其中主要工件是自然语言指令文件而不是源代码。
Hönel 等人 (2020)
通过将提交消息关键字与源代码密度指标相结合，改进了自动提交分类。
Wan 等人 (2025)
为 CCS 提交分类和消息生成建立了一个全面的基准，为自动分类方法提供了标准化的评估框架。
Li 等人 (2025)
引入了 AIDev，一个包含来自 61,453 个仓库的 456,535 个智能体创作的拉取请求的大规模数据集，并大规模应用基于 LLM 的 CCS 标注来标记每个 PR 的目的，证明自动 CCS 分类对于大量未标记提交是可行的。
Li 等人 (2026b)
发表了一篇专门的数据集论文，包含来自 116,211 个仓库的 932,791 个智能体拉取请求，为大规模研究 AI 编程智能体行为提供了正式的基础设施。
虽然先前的工作为传统源代码仓库开发并验证了提交分类方法，但我们将提交分类应用于智能体插件市场，其中主要工件是自然语言指令文件而不是编译代码，并且在手动验证期间，我们检查了文件级别的差异以及提交消息。
研究人员研究了传统源代码仓库中的 AI 贡献。
Tufano 等人 (2024)
在开源项目中挖掘了 ChatGPT 的提及，识别了 467 个已确认的 AI 辅助贡献实例，并将它们分类为 45 个任务，涵盖文档、重构、测试生成和功能实现。
Robbes 等人 (2026)
将检测推广到显式提及之外，编目了跨一系列编程智能体的共同作者尾部、电子邮件模式和分支前缀，作为识别提交历史中智能体贡献的启发式方法。
在本文中，我们将共同作者检测启发式方法应用于插件市场。
此外，Watanabe 等人 (2026)
研究了 GitHub 上的 567 个 Claude Code 拉取请求，发现 83.8% 被项目维护者接受，确定智能体贡献的集成率与人类贡献相当。
Horikawa 等人 (2025)
表明智能体重构以低级、面向一致性的编辑为主，而不是人类重构中常见的高级设计更改。
Ouatiti 等人 (2026)
发现 AI 编程智能体记录日志的频率低于人类（58.4% 的仓库），但在记录时密度更高，其中 67% 的生成日志语句不符合项目的日志记录说明，72.5% 需要人类开发者修复。
这些研究专门针对源代码仓库进行。在我们的研究中，我们考察了这些行为模式如何在以自然语言指令文件为主要工件而非编译代码的 AI 原生市场中表现。
2.4.
软件协同演化
大量实证工作研究了协同演化，即项目内不同工件类型一起更改的趋势。这种协同演化通常表明额外的维护工作，忘记更新任何一个协同演化的工件都会增加破坏的风险。
McIntosh 等人 (2011)
首次应用关联规则来衡量十个 C 和 Java 项目中构建文件与源代码之间的协同演化，发现构建维护对生产代码开发施加了高达 27% 的开销。
Jiang 和 Adams (2015)
应用关联规则来衡量 OpenStack 项目中基础设施即代码文件与源代码之间的协同演化，发现基础设施与生产文件和测试文件之间存在紧密耦合。
Barrak 等人 (2021)
将此扩展到机器学习项目，发现 DVC 管道文件与源代码之间的中位共同变更置信度为 91.91%。
虽然 McIntosh 等人、Jiang 和 Adams 以及 Barrak 等人将关联规则框架应用于源代码仓库中定义明确的工件对（基础设施-源代码和管道-源代码），但我们将相同的框架应用于 AI 原生插件仓库，其中协同演化关系是在自然语言组件类型之间，而不是在代码及其伴随工件之间。
Zaidman 等人 (2008)
挖掘了两个开源系统的版本历史以及测试覆盖率报告，识别了生产代码和测试代码协同演化的三种增长模式：同步、时间延迟和测试积压。
Marsavina 等人 (2014)
使用 Apriori 关联规则挖掘（支持度 50%，置信度 60%）研究了五个开源系统，在类和源代码实体级别识别了六种细粒度的协同演化模式。
Fluri 等人 (2007)
检查了三个 OSS 系统（ArgoUML、Azureus 和 JDT Core），发现 97% 的注释更新发生在与相关代码更改相同的修订版中。这些研究检查了代码及其伴随工件（测试或注释）之间的协同演化。
虽然先前的研究检查了传统 OSS 中代码及其伴随工件（测试或注释）之间的协同演化，但我们检查的是 AI 原生插件仓库内实现脚本与其配对的自然语言指令文件之间的协同演化。

4.
RQ1:

Claude Code 插件市场的结构和维护特征是什么？
4.1.
动机
先前的工作表明，自然语言正成为具有独特工程挑战的主要软件工件
(
Hassan et al., 2024
;
Li et al., 2026a
)
。
Claude Code 插件代表了最早主要围绕自然语言工件构建的大规模软件生态系统之一。
这些工件从 AI 智能体在运行时读取的 Markdown 指令文件、可执行脚本和配置文件不等，然而它们的增长轨迹、插件的功能、结构组成和开发活动仍然未被研究。
了解智能体插件市场的开发活动是加速的，还是仅代表最初的爆发，可以揭示市场是否已超越初始采用阶段进入持续开发。先前关于软件生态系统的工作表明，很大一部分项目在第一年就消亡了，存活超过五年的不到一半
(
Ait et al., 2022
)
。
持续的增长促使人们了解开发者实际在构建什么，特别是这些插件的功能，以及委托给 AI 智能体的任务类型。
了解插件的作用、其内部结构（即开发者使用哪些组件类型以及这些类型如何共现），可以识别开发者在构建和维护插件时必须考虑的技术工件。
插件维护和更新模式揭示了贡献者是否随着时间的推移积极改进他们的工作，还是在初始发布后放弃了插件。
总之，这四个维度为研究人员提供了一个大规模的实证窗口，以了解开发者如何构建和维护以自然语言指令、可执行脚本和配置文件为主要交付物的软件。
4.2.
方法
为了研究智能体插件市场，我们使用第 3.2 节中描述的数据集并进行四项分析。
追踪仓库和组件创建。
我们通过 GitHub REST API 检索所有 1,926 个仓库的每个仓库的创建日期，并将其用作市场进入生态系统的日期。
为了获得更细粒度的、组件级别的视图，我们识别引入每个组件文件的最早提交：skills/ 子目录中的 SKILL.md 文件、commands/ 中的 .md 命令文件、agents/ 中的 .md 智能体定义、hooks/ 中的钩子配置文件、plugin.json 清单、marketplace.json 注册表和 .mcp.json 服务器配置。
然后，我们执行非参数 Mann-Whitney U 检验
(
Mann and Whitney, 1947
;
Wilcoxon, 1945
)
，该检验不假设正态分布，以检查发布前和发布后期间每月的仓库创建计数之间是否存在显著差异。
我们还应用 Cliff's δ
(
Cliff, 1993
)
效应大小来衡量两组观察值之间差异的量级。
我们应用 Romano 等人 (2006) 提供的 Cliff's δ 阈值：
(1)
Effect size = { negligible, if |δ| ≤ 0.147 small, if 0.147 < |δ| ≤ 0.33 medium, if 0.33 < |δ| ≤ 0.474 large, if 0.474 < |δ| ≤ 1
对插件功能进行分类。
为了了解开发者实际在构建什么以及这些插件的功能，我们将所有 8,351 个有效插件（第 3.2 节）分类为包含 6 个主要类别和 20 个子类别的两层分类法，采用了 Ling 等人 (2026) 用于智能体技能的相同分类方案。
Ling 等人 (2026) 提出的类别涵盖了软件工程、信息检索和内容创建等端到端智能体工作流。我们在应用该分类法后验证了不需要新的类别，确认它可以无需修改地转移到 Claude Code 插件。
给定插件的名称和描述，我们使用 Ling 等人 (2026) (Qwen2.5-32B-Instruct) 使用的同一 Qwen 家族的 Qwen3-Coder-Next-80B 标记插件，将插件分配给一个子类别，以插件名称和描述作为输入。
我们用于分类插件的提示模板在附录 A 中提供。
分析插件组成。
我们在第 3.2 节描述的 2,018 个市场和 8,351 个有效插件中应用了四级方法。
在市场级别，我们计算每个 marketplace.json 中声明的插件数量。
在插件级别，我们检查每个插件根目录是否包含 Claude Code 文档中定义的七种组件类型中的任何一种
(
Anthropic, 2025c
)
：commands/、agents/、skills/、hooks/、.mcp.json、.lsp.json 和 settings.json。
然后，我们构建一个共现矩阵，记录哪些组件类型在同一仓库内一起出现，并按扩展名对文件进行分组，以表征每个组件目录中每个组件使用的文件类型。
衡量提交活动增长。
为了了解插件开发和更新模式，我们计算了从 2025 年 10 月 Claude Code 插件市场正式发布到 3 月底数据截止期间，72,191 次涉及插件的提交中每月涉及插件的提交数量，使用了第 3.2 节描述的数据集中的提交时间戳。
我们执行非参数 Mann-Kendall 检验
(
Mann, 1945
;
Kendall and Gibbons, 1962
)
以确定每月提交计数中是否存在单调上升或下降趋势。
Mann-Kendall 检验的零假设 (H0) 是在我们有序的六个月提交计数序列中没有单调趋势，备择假设 (H1) 是存在单调趋势。
我们还应用 Sen 斜率
(
Sen, 1968
)
来估计如果存在统计上显著的 Mann-Kendall 相关性时的量级。
Sen 斜率是一个非参数估计量，表示每个时间步长的变化率。
遵循 Kudrjavets 等人 (2023) 使用的相同基于聚合的序列自相关缓解措施（其中连续的月度观察往往彼此相关），我们在每月聚合的提交计数而不是原始每日时间戳上计算这两个测试。

动机

)
通过研究开发者提交的更改类型（例如，功能工作、错误修复和维护）来表征开发者如何构建和维护传统软件。我们从 RQ1 的发现表明，智能体插件仓库在初始发布后不断积累提交，并且这些仓库主要由自然语言指令以及脚本和配置文件组成，而不是程序代码。由于更改下的工件不同于程序代码，插件提交背后的开发和维护活动也可能不同于传统软件报告的活动。此外，AI 编程智能体现在已广泛应用于现实世界的软件开发中

;
Li et al., 2025
)
，智能体插件开发者特别有可能将工作委托给智能体，这引发了这种开发和维护工作有多少是 AI 辅助的问题。
5.2.
方法
随着软件开发变得越来越复杂，开发者采用提交分类系统，其中约定式提交规范 (CCS) 是最广泛使用的约定之一
(
Zeng et al., 2025
)
，以增强人类和自动化工具的可读性。
因此，我们采用 CCS 分类系统并分析智能体插件仓库中的提交。
我们首先应用两阶段管道在 CCS 分类系统下为每个提交分配一个标签，以建立我们研究的基准。
然后，我们通过分析开发者在携带 CCS 标识符的提交子集上的意图，进行手动研究以理解实际的开发和维护行为。
然后，我们使用从手动研究步骤总结的评分标准，通过 LLM 重新分类提交，以识别在插件仓库中的含义偏离其在传统软件工程中原始定义的 CCS 类型。
在 CCS 类别下分类提交类型。
我们在所有 77,773 次涉及插件的提交上应用 Li 等人 (2025) 的两阶段 CCS 管道，为每个提交分配恰好一个 CCS 类型。
阶段 1 通过正则表达式匹配已经携带 CCS 样式前缀（例如，feat: 或 fix:）的提交，直接分类了 51,141 次提交 (65.7%)。
阶段 2 使用所有 11 个 CCS 定义加上一个 other 类别（用于不适合任何标准类型的提交）提示 GPT-5-mini，为剩余的 26,632 次提交（清单 B）获取预测类型和置信度分数。
我们在单独的 385 次提交随机样本上验证每个阶段（95% 置信度和 5% 的误差范围
(
Baltes and Ralph, 2022
)
），由一名评分者阅读提交消息和更改的文件手动标记。
我们应用 Landis 和 Koch (1977) 中解释一致性强度的阈值的 Cohen's Kappa，发现阶段 1 达到 92% 的一致性 (κ = 0.903)，而阶段 2 达到 76.4% (κ = 0.707)，表明高于实质性一致
(
Baltes and Ralph, 2022
)
。
为了与传统 OSS 进行比较，我们将我们的分布与 Zeng 等人 (2025) 的分布进行绘制，他们报告了来自 116 个源代码 OSS 仓库的 88,704 次提交的 CCS 类型分布。
为了检查提交工作量在插件组件中的分布情况，我们构建了一个热图，其中每个单元格显示该组件类型的提交携带每种 CCS 类型的百分比，从而能够直接比较各组件，而不管其数量如何。
通过手动研究分析提交行为。
为了理解提交的含义以及它们在内部与传统软件提交有何不同，我们从全部 77,773 次涉及插件的提交（第 3.2 节）中抽取了 700 次提交的分层随机样本，将每种 CCS 类型视为一个层，置信度为 95%，误差范围为 5%，每层至少 50 次提交
(
Baltes and Ralph, 2022
)
。
我们遵循开放编码方法
(
Lune and Berg, 2017
)
来检查和分类样本提交。
前两位作者首先共同检查来自每种 CCS 类型的样本提交子集，并根据提交内容和智能体插件上下文构建初始类别集。
然后，两位作者根据初始类别独立分类剩余的提交。
当他们遇到不属于任何现有类别的提交时，两位作者会讨论并根据需要引入新的类别。
分歧也通过讨论解决，直到两位作者对所有分类结果达成一致。
最后，两位作者检查了 700 次涉及插件的提交的整个集合，并识别了它们的实际 CCS 类别（在第 5.3 节中讨论），达到了实质性一致 (Cohen's κ = 0.671)。
重新分类标签不再匹配其功能的提交类型。
我们首先基于 700 次手动检查的插件提交，识别在插件仓库中的含义偏离其传统软件工程定义的 CCS 类型。
然后，我们将属于显示定义偏移的 CCS 类型的所有提交重新分类为适当的 CCS 类型。
与在 CCS 类别下分类提交类型步骤（依赖于提交消息中陈述的开发者意图）不同，此步骤中的重新分类阅读实际的内容差异以识别提交行为，与手动研究期间标记 700 次提交的方式相同。
我们将手动研究的发现总结为按类型的评分标准，通过智能体插件场景中的开发和维护行为定义 CCS 类别（附录 C 中的清单 C），并利用 GPT-5-mini（与在 CCS 类别下进行提交分类期间使用的相同模型）来自动化大规模标记。
我们在带有双重标签样本的 doc、ci、style 提交子集上验证评分标准，与两位评分者共识达到 83% 的一致性 (κ = 0.65)，与评分者之间的 κ = 0.70 一致性相当。

style 扩展到指令措辞精度，其中措辞更改在运行时改变了模型行为，而不是影响代码格式。
refactor 主要由在没有更改预期行为的情况下改写面向 AI 的指令文本和模式重组主导，而不是该标签在传统仓库中携带的代码质量关注。
这四种类型在两个方面偏离了其传统含义。
perf 和 refactor 提交保留了其 CCS 标签，但指的是自然语言 AI 指令而不是编程代码，而 docs 和 style 提交通常属于不同的 CCS 类型，表明存在我们将在下面量化的差距。
feat、fix、chore 和 ci 在插件仓库中保留了其传统含义，feat 和 fix 从源代码转移到自然语言指令文件。
如表 4 所示，feat 提交经常引入新插件、添加组件或扩展现有指令内容。
传统功能开发以实现代码为中心，而插件仓库中的功能开发通常包括用自然语言指定新行为。
大约一半 (49.4%) 的 fix 提交更正了指令文件中的错误行为文本，而不是代码错误。
SKILL.md 或智能体文件中错误的工具引用、不正确的工作流步骤和有缺陷的示例是插件仓库中的主要缺陷类别。
相反，chore 和 ci 保持了接近其传统含义，每种类型中的大多数提交执行传统的维护任务。
Chore 提交遵循插件特定工件的传统发布机制。63.8% 是 plugin.json 或 marketplace.json 中的版本递增，而 12.5% 是注册新技能路径或更新市场注册表条目的非版本清单更新。
70.0% 的 ci 提交管理传统的 GitHub Actions 工作流和发布管道，而其余的来自 CI 分析插件的开发者，他们编写 ci 进行指令更新是因为他们的插件领域是 CI 工具，而不是因为任何管道发生了更改。

6.
RQ3:

插件组件如何协同演化？
6.1.
动机
先前的工作报告称，在传统 OSS 中，基础设施代码和源代码紧密协同演化，这为负责这些更改的人员引入了额外的努力，以保持项目可编译、可部署或可执行
(
Jiang and Adams, 2015
)
。
我们从前面的研究问题的发现表明，智能体插件经常在同一仓库内结合多种组件类型和语言（自然语言和多种编程语言）（RQ1），并且有来自 AI 编程智能体的重大贡献（RQ2）。
组件、语言和贡献的独特组成表明，先前关于传统 OSS 协同演化和耦合的发现可能无法很好地转移到智能体插件仓库。
因此，我们调查智能体插件在组件之间是否具有类似的耦合，在两个层面检查潜在的协同演化：1) 组件间和 2) 组件内。
由于开发主要由自然语言驱动（RQ2），当脚本和 Markdown 文件一起更改时，分类是什么驱动了这种组件间耦合，揭示了维护自然语言工件与维护源代码有何不同。
组件内协同演化在单个组件本身内部运作，其中相同的问题出现在文件类型级别，因为技能和钩子混合了可能在单个目录内协同演化的文件类型。
总之，这些答案为研究人员提供了 AI 原生仓库的首次实证协同演化测量，其中感兴趣的依赖关系不是在两个代码文件之间运行，而是在实现脚本和智能体在运行时读取的自然语言指令之间运行。
6.2.
方法
为了研究插件组件如何协同演化，我们首先收集合并的拉取请求 (PRs)，然后使用第 3.2 节中描述的数据集进行分析。
收集合并的拉取请求。
为了捕获开发者审查的更改单元（其中相关修改被捆绑在一起，使得跨组件的共同变更在单个提交中更加可见
(
Barrak et al., 2021
)
），我们通过 GitHub REST API 跨所有 1,926 个仓库收集合并的拉取请求。
我们检索关闭的拉取请求，并仅保留具有非空 merged_at 时间戳的那些，因为只有合并的拉取请求代表被接受到代码库中的更改，将每个拉取请求的更改文件上限设为 500，以避免在大型非插件更改上超时。
这产生了 112,807 个合并的拉取请求。
对于耦合分析，我们限制在具有超过十个合并拉取请求的 748 个仓库，遵循 Barrak 等人 (2021)，并限制在多组件插件（包含至少两种不同组件类型的插件），因为组件类型之间的关联规则要求数据中出现两种类型，从而从 2,592 个插件中产生了 10,679 个插件拉取请求。
衡量跨组件耦合。
关联规则衡量两个项目在事务中共同出现的频率。
应用于拉取请求，它们捕获两种组件类型在同一个拉取请求中一起更改的频率，以及这种共同变更是否强于随机。
为了了解更新一个组件是否迫使其他组件更新，我们应用了 McIntosh 等人 (2011) 首次引入用于构建协同演化的关联规则方法，后来被 Jiang 和 Adams (2015) 采用，以合并的拉取请求作为工作单元。

衡量组件内耦合。
为了评估不同文件类型是否在单个组件目录内共同变更，我们在 skills/ 和 hooks/ 中应用相同的关联规则方法，使用文件类型作为工作单元而不是组件类型。
任何具有 skills/ 或 hooks/ 目录的插件都符合条件，因为分析只需要单个目录内的两种不同文件类型，而不是跨插件的两种不同组件类型，从而在相同的 748 个仓库中产生了来自 5,353 个插件的 13,587 个技能内拉取请求和来自 1,085 个插件的 1,696 个钩子内拉取请求。
过滤和采样共同变更拉取请求。
为了研究当脚本和 Markdown 文件一起更改时会发生什么，我们对 13,587 个技能内拉取请求应用了两个过滤器。首先，我们仅保留在同一 skills/ 子目录内至少一个脚本（.py、.sh 或 .ts）和至少一个 Markdown 文件共同变更的拉取请求，产生了 1,908 个拉取请求。其次，我们限制在所有此类文件都被修改而不是新创建的拉取请求，排除了脚本及其配对的 Markdown 文件在同一拉取请求中一起引入的情况，产生了 323 个拉取请求。
我们跨六种脚本类型 × Markdown 类型组合（.py、.sh、.ts × SKILL.md、其他 .md）抽取了 64 个拉取请求的分层样本（每层 20%），确保在构建分类法时所有共同变更组合都得到代表。
分类共同变更模式。
我们阅读每个拉取请求的完整脚本和 Markdown 差异，并分类开发者在脚本中更改了什么以及为什么 Markdown 需要相应的更新。
遵循 Dig 和 Johnson (2006)，他们区分了保留组件行为的结构更改和修改它的行为更改，我们通过底层脚本更改的性质而不是触及的文件类型来表征每个共同变更。我们不直接重用他们的面向对象目录。相反，我们通过对样本进行开放编码推导出五个插件特定的耦合类别。
我们遵循用于提交内容类别 (RQ2) 的相同开放编码过程：前两位作者共同检查一小部分拉取请求，并根据底层脚本更改的性质构建初始类别集，然后根据初始类别独立分类更多拉取请求，在拉取请求不适合现有类别时根据需要进行讨论和添加新类别。
两位评分者独立地根据生成的方案对所有 64 个拉取请求进行编码，达到了实质性一致 (Cohen's κ = 0.74)，并通过讨论解决了 13 个分歧，直到每个拉取请求都有一个单一的同意标签。
使用 LLM 分类器扩展分类法。
为了将从 64 个人工编码拉取请求构建的分类法扩展到剩余的 259 个，我们应用了 LLM 分类器，遵循与 RQ2 中提交分类相同的 LLM 辅助扩展方法。我们提示 gpt-5-mini 分类器从其完整的脚本和 Markdown 差异中为每个共同变更拉取请求分配五个类别之一，将 64 个人工编码的拉取请求视为真实情况。
我们根据此真实情况验证分类器的预测，达到了实质性一致 (Cohen's κ = 0.62)，然后将其应用于剩余的 259 个共同变更拉取请求。

6.3.
结果
组件间分析表明，在其他类型更改的至少 43.2% 的拉取请求中，技能与所有其他组件类型共同变更，表明保持技能与插件其余部分的一致性是一项反复出现的工作。
表 6 报告了跨 10,679 个插件拉取请求的所有有向组件对的关联规则指标。在所有四个组件到技能的规则中，置信度至少达到 43.2%，在智能体到技能中达到 56.6% 的峰值。
仓库显著性列显示了该对在该仓库自身内显著耦合的仓库百分比，范围在 16.9%–27.9% 之间。
先前的研究为这些共同变更率的量级提供了背景。
Jiang 和 Adams (2015) 报告了基础设施-代码耦合的中位置信度值在 3.5% 和 45.8% 之间，而 Barrak 等人 (2021) 报告了拉取请求级别 DVC-源代码耦合的中位置信度值在 27.46% 和 91.91% 之间。43–57% 的组件到技能置信度落在这些环境中观察到的跨工件协同演化范围内，表明对其他插件组件的更改经常与对技能的更改重合。
提升度（公式 4）为这些高共同变更率反映了技能的主导地位提供了一个可能的解释。
因为技能是最常见的组件类型，所以无论其他什么发生变化，它都在大多数拉取请求中发生更改，因此每个组件到技能的提升度都低于 1 (0.59–0.78)。
例如，智能体在 56.6% 的拉取请求中与技能一起更改，这是大量且反复出现的共同变更工作，因此共同变更是真实的。
提升度仅为 0.78，所以这可能是由于技能的主导地位，我们不能将其归因于特定于智能体和技能的耦合。
相反，智能体-命令达到了 1.40 的提升度 (p < 0.05)，这是报告的五个对中唯一一个共同变更超过随机概率的对。
