今年早些时候，围绕 OpenClaw 的狂热已经大幅降温。OpenClaw 是一个开源 AI 框架，能将强大的语言模型转化为自主工作者，用户可以通过其最喜欢的渠道（Telegram、iMessage、WhatsApp、Discord 等）向其发送消息。这种狂热在 2026 年 3 月达到了顶峰。

但在周末，OpenClaw 的创建者 Peter Steinberger 和当前的联合开发团队给了世界——尤其是企业——一个重新审视它的理由：他们宣布推出 OpenClaw 2.0，这被称为该框架及周边平台迄今为止最重要的一次更新。

OpenClaw 2.0 试图将最初主要作为个人代理工具的框架，转变为越来越专为团队、共享基础设施和企业工作流设计的产品。

OpenClaw 2.0 引入了重新构建的浏览器界面，将对话、文件、审批、配置和实时的智能体活动整合到一个通用工作区中。它增加了共享云会话和多用户协作功能。此外，它还通过更强大的沙盒机制、基于角色的权限控制、审批控制、机密处理和审计功能，扩展了安全模型。

这些新增功能共同使 OpenClaw 更接近于一种可供组织为员工部署的基础设施，而不仅仅是单个开发者在本地运行的强大智能体。

它们也凸显了围绕该项目的一个竞争性问题：OpenClaw 是否解决了安全和隔离方面的担忧，而这些担忧正是催生 NanoClaw 等更新替代方案的原因。

在能力层面上，答案越来越倾向于“是”——但默认情况下并非如此。

OpenClaw 希望成为共享智能体层

以官方版本号 v2026.8.1 发布的这次更新，涵盖了安装、消息传递、记忆、技能、模型、自动化、浏览器和原生应用程序、插件以及安全性。

Steinberger 将 OpenClaw 2.0 的开发描述为一次使用产品来构建产品本身的实践。

“两个月前，我们开始了‘用 OpenClaw 构建 OpenClaw’的任务，”Steinberger 在 8 月 31 日凌晨于 X 上写道。

他说，在此期间，OpenClaw 逐渐让其团队摆脱了个人本地编码环境，转向 team.openclaw.ai，这是一个能够感知团队成员工作内容的共享智能体环境。

“多人协作编码 + 结合节点和云会话的无限算力，彻底改变了我们的构建方式，”Steinberger 写道，并补充说本地环境现在“感觉就像是过去的遗物”。

这一说法指向了 OpenClaw 企业主张中更重要的变化之一。

AI 编码智能体的主流模式通常是个人的：开发者在终端、IDE 或桌面应用程序中运行智能体，授予其访问代码仓库的权限，并让其在该环境中执行工作。

OpenClaw 2.0 正在推动一些不同的东西。智能体会话可以成为比单个终端或员工寿命更长的持久工作区。它们可以与同事共享，在其他机器或云工作者上执行，并通过浏览器进行监督。

对于企业来说，这有可能将智能体从员工级的生产力应用程序转变为共享的操作层。

新 UI 可能让 OpenClaw 不再局限于开发者

新 OpenClaw UI 宣传截图。图片来源：OpenClaw

重新设计的 Control UI 是该策略的核心。

OpenClaw 摒弃了以“概览”为主的 Web 应用程序，将对话作为主要界面。对话线程位于侧边栏中，而当前活跃的对话占据主工作区。文件、审批、设置和正在进行的智能体活动在其周围保持可访问状态。

该设计有意将 OpenClaw 带近员工已经从 OpenAI 的 ChatGPT、Anthropic 的 Claude、Google 的 Gemini 和其他对话式 AI 产品中熟知的交互模式。

这降低了企业采用的一个重要门槛。开源智能体框架之所以往往很强大，正是因为它们暴露了底层配置、终端、工具和运行时控制。但这些同样的特性也可能使它们难以在工程组织之外部署。

OpenClaw 2.0 试图在保留底层控制的同时，在其上层放置一个对话界面。员工可以要求智能体执行工作，而无需将终端作为主要的产品界面。但 OpenClaw 并没有隐藏底层发生的事情。Control UI 可以显示会话文件、终端活动、基于 Git 的更改、拉取请求状态、浏览器活动和交互式仪表板。

此次发布还更加注重智能体执行过程中的可观测性。工具调用和结果更加清晰地配对显示，文件更改可以显示为聚焦的差异对比，命令活动更易于检查，长时间运行的后台任务可以在对话旁边保持可见。这种组合对企业使用至关重要。

员工获得了一个更简单的委派工作的界面。技术用户保留了对对话背后的工件和执行状态的访问权限。管理员则获得了一个集中配置和监督系统的地方。

重新设计的 Settings 工作区现在涵盖了智能体、记忆、插件、MCP 服务器、设备、通信渠道和设备配对。OpenClaw 还整合了模型提供商管理，包括凭证状态，以及（在提供商公开的情况下）模型可用性、配额、账户余额、预算和支出信息。

受限浏览器用户可以请求管理员权限，而不是自动接收权限，并且需要另一名管理员批准该提权。

这些并不是特别花哨的智能体功能。对于向数十或数百名员工部署 AI 系统的公司来说，它们可能是此次发布中最重要的新增功能。

多人会话将智能体上下文转变为共享上下文

OpenClaw 2.0 还将智能体从个人工作区扩展为协作工作区。

共享云会话允许另一名员工进入正在进行的工作，而不会丢弃智能体已积累的上下文。

多用户网关——连接用户和智能体与工具、文件、凭证和其他资源的服务——可以跟踪谁创建了对话，以及哪些提示是由已识别的参与者提交的。

所有者和管理员可以决定另一名用户是否可以读取会话、建议更改、在草稿模式下工作或直接参与。

界面增加了会话所有权、参与者归属、状态显示甚至输入指示器。对于编码团队来说，这引入了一种比传统 AI 聊天更接近协作软件开发的工作流。

一名开发者可以发起任务，并允许智能体远程处理它。另一名工程师可以检查由此产生的更改。高级工程师或管理员可以批准需要额外权限的操作。工作不必一直依附于它开始时的笔记本电脑或终端。

会话还可以将执行转移到配对的设备或云工作者，同时维护更广泛的工作区。

对于尝试使用长时间运行智能体的企业来说，这意义重大。持久型智能体需要换班、升级、监督和所有权转移的机制。否则，组织只是创建了一群个人智能体，其状态会消失在 individual 用户环境中。

OpenClaw 正试图将这种状态转变为协作基础设施。已经有开源项目开发者之外的一些团队开始采用它。

营销指标软件公司 Solvably 的 CEO Colin Johnson 在 X 上的一篇帖子中描述了他自己开发工作流中的类似转变。

他的团队之前一直通过 Discord 使用 OpenClaw 智能体，开发者可以在其中分配任务、运行命令并与他们的开发环境交互。但他表示，那种模式仍然感觉像是在“给机器人发消息”：开发者可以共享对智能体的访问权限，但实际上并没有共享智能体的工作上下文。

他写道，新的多人 WebUI 改变了这一点，因为两名开发者可以打开同一个实时会话，看到相同的历史记录和工件，并在不首先导出或重建智能体已完成工作的情况下添加信息。“我们在同一个上下文中工作，”Colin 写道。

在一个例子中，另一名开发者正在接手他一直在做的项目；Colin 没有准备传统的交接文档，而是加入了该开发者现有的智能体线程，并直接添加了缺失的项目上下文。“会话本身就成了交接文档，”他写道。

对于企业团队来说，这是一个有用的例证，说明了为什么持久的多人会话可能不仅仅是为了方便：智能体上下文可以成为共享的工作工件，而不是被困在某个员工私人对话中的信息。

Colin 的部署也说明了企业潜力和剩余的安全边界。他的团队在开发服务器上运行 OpenClaw 网关，可通过 GitHub 身份验证、Cloudflare Access 和 Cloudflare Tunnel 访问，而网关本身仅侦听服务器的环回接口，而不是暴露的公共端口。

但他明确警告说，这并不能使共享网关成为多租户环境。开发者们已经相互信任，共享其背后的代码仓库、工具和智能体能力。正如他所说，Cloudflare 控制谁可以进入工作区，而 OpenClaw 跟踪谁创建、拥有或贡献了工作；更强的分离仍然需要独立的基础设施。

安全性变得更加面向企业

这种转变带来了相应的安全问题：共享智能体可能会以比在开发者笔记本电脑上运行的智能体更广泛的组织权限行事。

OpenClaw 2.0 以更精细的控制作为回应。

审批现在可以绑定到特定的请求、命令、会话和个人。命令权限可以限制为特定的参数和工作目录。对于基于脚本的执行，OpenClaw 可以验证正在执行的脚本是否仍然与最初审查的脚本匹配。

会话可以在不同的权限级别下运行，包括只读、受保护、工作区和完全访问模式，最高级别仅限管理员使用。

组织还可以定义操作员角色，要求为由特定身份创建的会话进行沙盒执行。OpenClaw 表示，这些要求无法使用提升的执行或主机覆盖来绕过；如果无法配置所需的沙盒，执行将失败，而不是静默回退到主机。

凭证得到了额外的保护。

OpenClaw 的团队级 Secret Store 将受保护的机密与智能体可用的普通环境数据区分开来。对于支持的请求，受保护的凭证可以替换到网关托管的 HTTPS 请求中，而无需将该凭证直接暴露给模型。

OpenClaw 还可以引用外部系统，包括 1Password 和 Vault。

审计在执行身份、审批、会话操作和出站消息方面得到了扩展。插件安装可以触发与正在安装的特定工件相关的功能审查。

这些控制解决了企业在部署智能体时不可避免地要面临的问题：谁发起了一个操作？哪个智能体执行了它？它能访问哪些资源？谁批准了该操作？当工作在不同人或机器之间转移时，这些权限会发生什么？

NanoClaw 在安全方面仍采取不同方法

OpenClaw 的变化也使得与开源、对企业友好的竞争对手 NanoClaw 的比较更加微妙。

NanoClaw 是围绕 AI 智能体需要更强隔离和更简单安全边界的理念而出现的几个后续项目之一。其架构将操作系统级别的隔离作为设计的核心。

NanoClaw 在 Docker 容器内运行智能体，将这些容器限制为显式挂载的文件系统，并以非特权用户身份运行其进程。会话和智能体组可以保持隔离，而不是自动共享文件和对话历史。

其凭证架构遵循相同的原则。支持的出站请求可以通过 OneCLI 的 Agent Vault，允许由网关注入凭证，而不是将凭证放在智能体容器本身内部。NanoClaw 还提供了一种可选的出口锁定模式，将智能体置于内部 Docker 网络上，并通过网关路由支持的外部流量。

OpenClaw 2.0 现在可以重现这种强化模型的许多元素。它支持 Docker 和 Podman 沙盒、每个智能体和每个会话的沙盒范围、可配置的只读或读写工作区访问、基于角色的沙盒、远程执行节点和一次性云工作者。

关键区别在于初始姿态。OpenClaw 的文档明确指出，沙盒和执行审批默认是关闭的。其基线配置假定是受信任的单个操作员，并允许主机执行，除非管理员配置更强的限制。NanoClaw 则将隔离作为智能体执行结构的基础。

那么 OpenClaw 2.0 在安全性上与 NanoClaw 持平了吗？

就可用的控制而言，它比以前接近得多。但在默认设置和架构理念上，并非如此。企业可以将 OpenClaw 配置为一个实质性强化的环境中，但必须是有意做出这一决定的。

一个网关仍然是一个信任域

另一个限制对于大型组织来说尤为重要。OpenClaw 表示，网关应被视为单个信任域。

其新的多用户权限旨在管理受信任用户之间的协作。它们不应被视为相互不信任的租户之间的硬隔离。

对于需要更强分离的组织——例如在业务部门、客户或其他安全域之间——OpenClaw 建议使用单独的网关实例，称为“单元”，具有独立的状态、凭证和工作区。

用于管理这些单元的集群工具仍处于试验阶段。

对于考虑将 OpenClaw 作为集中运营服务的企业来说，这种区别可能意义重大。

一个网关内基于角色的访问对于受信任的工程部门或内部团队来说可能就足够了。但这与一个旨在隔离应被假定为相互敌对的客户或用户的多租户平台是不同的主张。

NanoClaw 有其自身的配置要求和限制，甚至其更强的出站网络锁定也是可选的。但其较小的架构和以容器为中心的执行模型可能会吸引那些想要更窄、更容易推理的安全边界的组织。

OpenClaw 正在针对更广泛的问题进行优化。

OpenClaw 最大的优势可能是控制平面

权衡之处在于产品的广度。

NanoClaw 强调相对较小的代码库、容器隔离以及通过代码和技能进行定制。其第二代架构支持所有者、管理员和成员角色，单独的监控仪表板可以提供部署的可见性。

OpenClaw 2.0 正试图构建一个更广泛的操作环境。

其 Control UI 结合了员工交互、实时执行、文件、审批、终端、代码审查、模型提供商配置、设备和共享会话。

这为不仅需要安全的智能体执行，还需要围绕它的可用控制平面的企业赋予了 OpenClaw 潜在的优势。

安全团队关心隔离。平台团队还需要部署、身份验证、模型配置、审计和策略执行。员工需要一个他们实际可以使用的界面。管理者需要一种方式来了解正在运行什么。开发者需要在出现问题时访问底层文件和工具。

OpenClaw 2.0 越来越倾向于通过一个系统来服务于所有这些群体。

OpenAI 的角色是什么？

OpenClaw 表示，有 933 名贡献者（包括 569 名首次贡献者）参与了此次发布，其中包含超过 16,000 个拉取请求——大约占该项目有史以来合并的所有拉取请求的一半。

有趣的是，此次发布并不是由 Steinberger 的雇主 OpenAI 分享的。回想一下，这位奥地利开发者于 2026 年 2 月 14 日宣布他将加入 OpenAI，致力于将智能体带给更广泛的受众，OpenAI CEO Sam Altman 第二天公开证实了这一举动。

但 OpenClaw 并没有被并入 OpenAI。Steinberger 当时表示，OpenClaw 将移交给一个基金会并“保持开放和独立”，而 OpenAI 将支持该项目。OpenClaw 现在表示，它由独立的 501(c)(3) 组织 OpenClaw 基金会管理，OpenAI 与微软、GitHub、NVIDIA、Atlassian、腾讯和其他组织一起被列为合作伙伴。

根据现有的公开信息，尽管 Steinberger 受雇于 OpenAI 且 OpenAI 为该项目提供了财务和组织支持，但 OpenClaw 2.0 因此应被视为 OpenClaw 基金会的发布，而不是 OpenAI 的产品或 OpenAI 软件发布。

企业就绪性现在取决于配置

OpenClaw 2.0 并没有消除与自主智能体相关的安全风险，其自身的文档也指出了局限性。

例如，Secret Store 的值本身在静态时并未加密，而是依赖于文件系统保护。受保护的凭证替换并不涵盖所有可能的执行路径，包括一些原始套接字、容器、远程节点和提供商原生框架。其多用户权限是协作控制，而不是针对恶意租户的隔离。

这些警告应防止企业将 OpenClaw 2.0 解释为默认安全的智能体基础设施。但它们也说明了围绕该项目的对话发生了多大变化。相关的比较越来越不仅仅是 OpenClaw 与 NanoClaw 的对比。而是像 NanoClaw 这样以容器为先、受限的系统，与经过刻意强化的 OpenClaw 部署之间的比较，后者提供了更广泛的员工和管理员体验。

对于优先考虑小攻击面、以容器为先的执行和架构简单性的组织，NanoClaw 仍然保持着强大的主张。

OpenClaw 正在押注另一方面：企业最终需要一个既能作为运行时又能作为工作场所的智能体平台。

OpenClaw 2.0 提供了构建该环境所需的许多原语——沙盒、权限、受保护的凭证、审批、身份、审计和隔离部署——以及一个浏览器界面，旨在让那些永远不会在终端中配置智能体的员工也能使用该系统。

剩下的警告很重要：企业必须将这些原语转化为策略。OpenClaw 2.0 并不会自动使 OpenClaw 具备企业就绪性，但它确实使开箱即用的企业级 OpenClaw 部署变得容易得多。

正如 Steinberger 对 OpenClaw 自身开发过程的描述所暗示的那样，长期的野心可能更大。OpenClaw 不是给每个员工另一个 AI 助手，而是将智能体本身定位为共享基础设施——一个持久的层，人员、模型和算力在其中协同完成相同的工作。
