我们最新的模型进展为在 COBOL、Fortran 和 Visual Basic 等低资源编程语言中构建和迁移软件带来了更强的能力。与 Python 和 JavaScript 等语言相比，这些语言可供模型学习的代码和文档较少，但却支撑着世界各地的关键基础设施和基本服务。COBOL 支撑着全球超过 40% 的在线银行系统、80% 的面对面信用卡交易和 95% 的 ATM 交易，而 Fortran 则被用于天气预报和核反应堆安全分析。提升 AI 在这些语言上的工作能力，可以帮助团队维护和现代化这些基本服务所依赖的软件。

这项工作以开发者和企业客户的反馈为指导，他们告诉我们编程模型在处理这些语言时常常力不从心。维护和现代化这类软件可能很困难：文档可能不完整，原始开发者可能已经离开公司，重要的业务规则可能只存在于代码之中。无论是修复缺陷还是迁移到另一种语言，团队都需要保留其系统所依赖的行为。

为了衡量进展，我们开发了两个评估。MultiLangBench 测试模型能否用 20 种不同的编程语言从零开始构建兼容 SQLite 的数据库引擎。我们的 COBOL 迁移评估则测试模型能否在保留现有程序行为的前提下将其迁移到另一种语言。二者共同检验两项互补的技能：构建新软件，以及保留现有软件的功能。

我们最新的模型在这两项评估中均取得显著进步，以更低的成本实现了更高的准确性。

在 MultiLangBench 上，GPT-6 Astra 在 20 种编程语言中实现了 87.4% 的平均测试通过率，相比 GPT-5.6 Sol 的 26.8% 大幅提升，且在所有测试语言中均有改进。GPT-6 Luna 同样优于 GPT-5.6 Sol，达到 40.3% 的通过率，而预估 API 成本降低约 78%。

在我们的 COBOL 迁移评估中，GPT-6.1 Sol 在低推理努力下实现了 86.6% 的准确率，而 GPT-5.6 Sol 仅为 5.4%，同时成本降低 39%。在更高的推理努力下，准确率达到 97.9%，几乎使该评估达到饱和。

这些结果共同表明，我们的模型在处理广泛编程语言方面的能力显著提升，同时成本效率也在不断提高。

1. 从零构建 SQLite（MultiLangBench）

MultiLangBench 要求模型用指定的编程语言构建一个兼容 SQLite 的数据库引擎。模型必须组织代码库、管理状态、处理错误，并在保留现有功能的同时添加新功能。

为了比较不同语言的实现，我们使用数据库文件作为共享接口。候选程序接收一个初始数据库和一条 SQL 查询，然后生成修改后的数据库。我们使用 SQLite 参考实现来检查生成的数据库是否包含预期的内容。这样，无论使用哪种语言构建引擎，我们都能应用相同的测试。

我们将 SQLite 现有测试套件中的测试改编为这种格式。该评估衡量模型在长时间编码会话中能够构建多少可正常工作的功能，并同时报告测试通过率和 API 成本。

在最大推理努力下，GPT-6 Astra 在 20 种语言中实现了 87.4% 的平均测试通过率，相比 GPT-5.6 Sol 的 26.8% 大幅提升。改进覆盖所有测试语言，包括 COBOL（从 10.9% 提升至 72.1%）、OCaml（从 25.6% 提升至 85.8%）、Fortran（从 21.4% 提升至 83.5%）和 Visual Basic（从 27.5% 提升至 89.4%）。Astra 在 20 种语言中的 19 种上得分超过 83%，COBOL 仍然是最难的语言，得分为 72%。

GPT-6 Luna 提供了一个成本更低的选择，在所有测试语言中同样优于 GPT-5.6 Sol。在最大推理努力下，它达到了 40.3% 的平均测试通过率。提升包括 COBOL（从 10.9% 提升至 17.1%）、OCaml（从 25.6% 提升至 34.1%）、Fortran（从 21.4% 提升至 31.4%）和 Visual Basic（从 27.5% 提升至 41.6%）。这些改进的预估平均 API 成本为每样本 0.77 美元，而 GPT-5.6 Sol 为 3.48 美元，降低约 78%。

我们正在 GitHub 上发布 MultiLangBench 的评估设置和测试套件，以及各语言的结果。开发者可以查看评估所测试的内容，审阅自己所用语言的性能表现，并找出对自身工作重要的差距。

2. 迁移 COBOL 代码库

我们的第二个评估要求模型将 COBOL 程序迁移到 C++、Java、Kotlin、Python 或 Rust，同时保留每个程序的原有功能。

成功的迁移需要同时理解程序的业务逻辑和 COBOL 特有的语言行为。COBOL 程序通常处理金融交易和业务记录，其中舍入规则和缺失记录处理等细节反映了业务需求。例如，COBOL 的定点算术会直接丢弃多余的小数位数，除非明确要求舍入。如果重写时对这些值进行舍入，程序可能运行无误，却产生不同的财务结果。

为了检验这些行为是否得到保留，我们在隐藏测试上评估模型，这些测试要求可观察输出达到逐字节一致。只有所有测试全部通过，迁移才被视为成功。这类行为保留能力对于维护和现代化老旧系统的团队非常有用，但将其应用于生产软件仍需专家审查，并针对系统的业务规则和依赖项进行测试。

在这项评估中，GPT-6.1 Sol 在低推理努力下实现了 86.6% 的准确率，而 GPT-5.6 Sol 在相同设置下仅为 5.4%，且 API 成本仅为后者的 61%。在更高的推理努力下，准确率达到 97.9%，使该评估接近饱和。这些评估结果表明，对于正在现代化其业务所依赖软件的团队而言，我们在实现更准确、更经济的代码迁移方面取得了进展。

提升企业软件能力

这些评估，加上来自开发者和企业客户的直接反馈，帮助我们了解模型在哪些方面有所改进，在哪些方面仍有不足。

我们的目标是帮助模型在更多语言中运用软件工程技能：理解陌生的代码库、规划变更、使用构建工具、运行测试以及调试故障。

您可以通过 API 在团队所用语言上执行编程任务，试用我们最新的模型。您对哪些方面有效、模型在哪里遇到困难，以及我们接下来应重点关注哪些语言或工作流程的反馈，将帮助我们塑造模型训练和评估的方式，以更好地支持您所依赖的软件。
