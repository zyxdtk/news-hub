原标题：Learning to Commit: Generating Organic Pull Requests via Online Repository Memory

中文摘要： 本文提出“学习提交”框架，通过“在线仓库记忆”使编码代理从历史提交中学习，生成与项目风格一致的“有机”拉取请求。框架通过监督对比反思提取技能，避免数据泄露，显著提升文件定位、减少补丁膨胀，并在多维评估中优于基线。实验验证了其在真实仓库中的有效性，为代理适应仓库特定惯例提供了新范式。

Xu    Qitai Tan 1 Ting Cao 1† Yunxin Liu 1 1 清华大学 摘要 基于大语言模型（LLM）的编码代理在受控基准测试中表现出色，但通常生成的拉取请求会被实际维护者拒绝。根本原因并非功能错误，而是缺乏“有机性”：生成的代码忽略了项目特定的惯例，重复了内部API已提供的功能，并违反了多年开发积累的隐式架构约束。仅向代理暴露最新的仓库快照是不够的：快照揭示了代码库的最终状态，但未揭示达到该状态的仓库特定变更模式。我们引入“学习提交”框架，通过“在线仓库记忆”弥补这一差距。给定一个严格按时间划分的仓库，代理对早期提交执行“监督对比反思”：盲目尝试解决每个历史问题，将其预测与专家补丁进行比较，并将差距提炼为一个持续增长的“技能”集合——可重用的模式，捕捉编码风格、内部API使用和架构不变量。当新的PR描述到达时，代理基于这些积累的技能进行生成，产生的变更根植于项目自身的演变，而非通用预训练先验。评估在真正未来的、合并的拉取请求上进行，这些请求在技能构建阶段不可能被看到，评估维度包括功能正确性、代码风格一致性、内部API重用率和修改区域的合理性。在具有丰富提交历史的专家维护仓库上的实验表明，在线仓库记忆有效提升了保留未来任务的有机性得分。 2 2 footnotetext: 通讯作者。 1 引言 过去三年见证了AI辅助软件工程的显著加速。基于大语言模型的编码代理现在在SWE-bench等精心策划的基准上解决了大量任务[1]，而HumanEval[2]和MBPP[3]等库已基本饱和。FEA-Bench和FeatureBench等仓库级基准进一步将评估从孤立代码生成扩展到真实仓库中的多文件功能实现[4;5]。这些数字激发了人们对LLM代理工业部署的乐观情绪。然而，复杂仓库的专业维护者仍持谨慎态度：他们承认AI生成的代码通常功能正确，但仍经常拒绝拉取请求，因为代码感觉“陌生”——仿佛由从未读过该项目的人编写。实际上，这种“陌生”特性不仅表现为风格不匹配，还表现为不必要的代码膨胀：代理重新实现了仓库已包含的实用工具、包装器或控制流模式。基准分数与工业合并率之间的差距反映了当前评估编码代理的结构性盲点。SWE-bench等基准仍将软件工程视为一系列孤立的一次性任务：代理看到一个问题，编辑代码库，如果测试通过则成功，但不携带任何累积知识向前。此外，它们通常按非时间顺序评估问题，忽略了仓库及其惯例如何随时间自然演变。COMMIT0[6]强调从API规范实现整个库，而SWE-CI[7]将评估扩展到连续数月的提交。同时，仓库级系统如Repository Memory和SGAgent表明，更丰富的代码库上下文有助于本地化和修复[8;9]，而以PR为中心的工作如Coeditor、Clean-PR和R2E-Gym表明提交和PR历史是宝贵的学习信号[10;11;12]。然而，这些设置仍共享相同的基本前提：代理在开始编写代码前不需要经历任何类似仓库特定的入职过程。这一遗漏很重要，因为当前仓库快照仅显示最终建筑，而非特定支撑、接口和边界引入的原因。更广泛地说，这反映了现在成为代理研究核心的转变：能力不再仅依赖于单次会话内的上下文管理，而越来越依赖于跨会话和跨时间的记忆管理与更新。尽管最近的框架如SWE-Bench-CL[13]尝试按时间顺序评估此类持续学习，但它们依赖无监督自反思。没有明确的专家监督，代理容易积累自我强化的错误。这一缺失的入职步骤正是区分资深贡献者与外包新手的关键。当人类工程师加入成熟代码库时，她不会立即打开文本编辑器。她阅读之前的提交，研究模块边界，发现哪些内部实用工具是惯用的，并内化维护者的偏好。只有这样，她才会提交一个看起来从仓库本身有机生长出来的拉取请求。当前代理完全跳过这一过程，产生我们称之为“陌生代码”的结果：语法正确，通常功能正确，但风格陌生，架构不协调，且充满现有辅助函数的冗余重实现，常常导致补丁尺寸膨胀。即使此类补丁通过单元测试，维护者仍会因与初级工程师首次贡献被要求修改的相同原因而拒绝它们。为了生成不仅正确而且真正“有机”的代码，我们引入“学习提交”框架，核心是“在线仓库记忆”。核心思想很简单：有机性可以从提交历史中学习，提交历史记录了项目如何随时间演变。给定一个严格按时间划分的仓库，代理对早期提交执行“监督对比反思”——盲目尝试每个历史变更，将其预测与专家补丁进行比较，并将差距提炼为一个持续增长、可增量更新的“技能”集合。当新的PR描述到达时，代理检索并基于这些技能进行生成，产生的变更与仓库的命名惯例、首选抽象和维护者偏好保持一致。评估编码代理经常因预训练数据泄露而受损——当前评估中普遍存在的一种漏洞，如最近的SWE-Bench++[14]所示。通过设计，我们的同仓库、时间分割评估本质上保证了零数据泄露。技能仅从截止日期前的提交中构建，而评估任务来自真正未来的合并提交。我们不仅通过功能正确性衡量成功，还通过代码风格一致性、内部API重用和修改区域合理性进行衡量。虽然我们在本工作中验证了一个专家维护的内部仓库，但该流程设计为未来可扩展到高质量的公共GitHub仓库。在本文中，我们确立了仓库个性化适应作为编码代理的首要评估目标。我们的贡献包括： • 我们通过“学习提交”框架形式化了“仓库个性化在线适应”，建立了代理有机对齐演进代码库的在线学习机制和严格的评估范式。 • 我们提出了一种无需训练的在线技能提取方法，通过监督对比反思提炼仓库特定惯例——将代理的盲目尝试与专家补丁进行比较，以积累抽象、可重用的开发“技能”。 • 我们构建并发布了一个严格时间分割的精选仓库基准，包含多维指标（代码风格、API重用、修改区域合理性），证明我们的框架在现有范式上有效提升了有机性。 表1：代表性仓库级基准和代理学习范式的比较。列从基本能力进展到我们的独特贡献：利用历史上下文、跨任务持续学习、严格的数据泄露预防、专家监督的记忆更新和多维有机性评估。符号图例：✓ = 完全满足；✗ = 不支持。 框架/范式 时间顺序评估 历史记忆 早期基准在孤立、无状态环境中评估大语言模型[2;3]，最近演变为SWE-bench[1]及其多文件或生成扩展[4;5;6]等现实仓库级任务。为应对这些复杂场景，近期工作通过自动化PR采集扩展训练数据[11;15;12]，如SWE-Bench++[14]特别设计近期截止点以确保零数据泄露，并设计具有专用角色和推理步骤的多代理工作流[9;16]。然而，这些以数据为中心和工作流为基础的方法将任务视为静态快照，完全忽略了软件的时序演变。虽然SWE-CI[7]引入了时间CI循环以惩罚技术债务，但主要评估性能退化而非赋能代理主动学习和内化仓库特定惯例。关键的是，这些现有范式几乎完全依赖功能测试通过作为成功指标，缺乏多维有机性评估以评估代码库风格一致性、内部API重用和架构契合度。 2.2 代理记忆和软件工程中的持续学习 为捕捉历史开发者意图，模型通过静态权重更新[17;10]或被动检索增强[8]纳入提交历史，但两者均缺乏主动试错学习过程。长时序任务中观察到的性能退化突显了动态持续学习的必要性[7;18]，促使探索不同粒度的在线代理记忆[19;20;21]。最值得注意的是，SWE-Bench-CL[13]按时间顺序评估持续学习，但依赖无监督自反思；因此，当早期尝试失败时，极易出现“垃圾进垃圾出”错误，因为无真实值验证的自主反思常导致自我强化错误[19]。即使有逐步环境反馈[22]，信号仍过于嘈杂，难以提取深层设计模式。我们的工作弥合了这一差距：通过严格划分历史以防止数据泄露，我们的代理尝试历史提交并接收“专家补丁”作为密集监督。通过盲目尝试与专家补丁之间的监督对比提炼，代理将可重用的、仓库特定的开发模式提取到一个持续精炼的技能文档中，确保失败驱动最优、历史条件化的记忆更新。 图1：学习提交框架概览。真实仓库按时间分割为过去提交（用于技能学习）和未来提交（用于评估）。在步骤1中，代理执行策略对比反思：盲目尝试每个历史提交，然后将其预测与专家补丁进行比较，以提取仓库特定的开发模式到结构化技能文档中。在步骤2中，代理在积累的技能指导下为未见过的未来任务生成有机补丁。在步骤3中，生成的补丁在多个维度（包括文件IoU、行偏差和多维LLM判断分数）上与专家提交进行评估。 3.1 问题形式化 令𝒞 = (c₁, c₂, ..., cₜ)表示目标仓库ℛ的高质量提交的时序序列。每个提交cₜ关联一个仓库快照𝒮ₜ（父提交时的代码库状态）、一个专家代码补丁Δₜ和一个合成问题描述dₜ，该描述指定任务意图而不泄露实现。一个时间截止点T*严格将序列划分为学习用的历史前缀𝒞⁻ = {cₜ: t ≤ T*}和评估用的保留测试集𝒞⁺ = {cₖ: k > T*}。 给定未来任务描述dₖ ∈ 𝒞⁺，目标是在代理仅能使用𝒞⁻进行适应的约束下，生成一个同时功能正确且与仓库有机对齐的补丁Δ̂ₖ。学习提交框架将此分解为两个阶段（如图1所示）：(1) 仓库入职（学习阶段），其中代理通过策略对比反思从𝒞⁻迭代构建可重用技能文档ℳ；(2) 技能条件化解决（解决阶段），其中给定dₖ和仓库快照𝒮ₖ，代理在积累的技能ℳ条件下自主解决任务。 3.2 通过对比反思进行仓库入职 学习阶段模仿人类开发者入职新项目的方式：不是被动阅读文档，而是主动尝试任务并从自身输出与专家实践的差距中学习。我们初始化一个空技能文档ℳ(0) = ∅。对于每个学习提交cₜ ∈ 𝒞⁻，代理执行三步循环。 步骤1（盲目尝试）：代理接收仓库快照𝒮ₜ、合成问题描述dₜ和当前技能文档ℳ(t-1)。它使用标准工具使用能力（文件读取、搜索、编辑）自主探索代码库并生成候选补丁Δ̂ₜ。 步骤2（专家揭示和对比反思）：真实专家补丁Δₜ——代表人类领域专家接受的解决方案——被揭示。代理将其自身尝试Δ̂ₜ与Δₜ进行比较，识别文件定位、实现逻辑、API使用和编码风格方面的差异。两者之间的差距作为密集的策略监督：差异越大，学习信号越丰富。 步骤3（技能更新）：基于对比反思，代理通过显式的CRUD操作更新技能文档——为之前未知的模式创建新条目，修订部分正确的条目，并弃用与专家证据矛盾的条目： ℳ(t) = Update(ℳ(t-1), Δ̂ₜ, Δₜ, dₜ)。 (1) 结果技能文档ℳ整合了抽象、可重用的开发模式，通常包括：(1) 编码风格和命名惯例，(2) 内部API实用工具的存在和正确使用，(3) 隐式架构约束和模块边界，以及(4) 维护者偏好模式，如错误处理风格和测试组织。与对提交历史的静态RAG不同，这种策略学习循环确保提取的模式精确校准到代理自身的能力差距——解决代理否则会犯的错误。 3.3 技能条件化解决 当未来任务dₖ ∈ 𝒞⁺到达时，代理接收仓库快照𝒮ₖ、任务描述dₖ和完整的积累技能文档ℳ。然后，代理使用标准工具使用能力——读取相关文件、搜索代码库、应用编辑——在ℳ记录的开发模式条件下自主解决任务。不强制执行刚性检索管道或预计划工作流；代理根据自身判断决定咨询哪些技能和探索哪些文件，模仿具有内化项目知识的人类开发者处理新任务的方式。 3.4 数据集构建 我们在一个大规模内部强化学习训练仓库上初步验证该框架，该仓库的每个提交都经过领域专家审查和批准，确保高质量的真实补丁。数据策展流程分为五个阶段。(i) 提交扫描和质量过滤：我们提取完整的非合并提交历史，应用程序化预过滤器以去除琐碎变更（例如，修改行数少于10行、版本号更新），并使用LLM评估每个剩余提交是否表现出实质性、可学习的开发模式。补丁超过180K标记的提交被排除。在我们的试点仓库中，这显著减少了原始提交池，仅保留高质量候选（具体数字见§4）。(ii) 无监督类别聚类：为防止学习课程坍缩到单一变更模式，我们从第一阶段采样理由并执行无监督聚类以识别核心开发类别（产生七个类别，涵盖架构设计、并发、测试等）。(iii) 类别标记：每个保留的提交随后由LLM分配主要类别标签，该LLM考虑提交标题、理由和完整补丁内容。 在初步标记后，我们构建最终基准集。(iv) 分层抽样与时间分割：提交按时间排序并划分为学习和测试池。在每个池中，我们跨类别执行分层比例降采样以构建平衡课程。(v) 合成查询生成：对于每个任务，LLM从提交消息和补丁中合成一个问题风格的自然语言查询。提示指定任务的“什么”和“为什么”，严格省略实现细节（确切文件路径、函数名或解决方案策略），模拟不泄露专家补丁的真实用户问题。关键的是，严格的时间分割确保所有学习提交早于所有测试提交，完全防止评估任务向技能构建阶段的信息泄露。将此流程扩展到多样化的开源GitHub仓库是未来工作的直接延伸。 3.5 评估指标 评估AI生成补丁的有机性需要超越功能测试通过。我们在两个互补的指标族中评估生成补丁Δ̂ₖ与专家补丁Δₖ。 确定性代码指标。 (1) 文件IoU：代理修改的文件与专家补丁中文件的Jaccard相似度|ℱ(Δ̂) ∩ ℱₖ*| / |ℱ(Δ̂) ∪ ℱₖ*|，衡量定位准确性。 (2) 轨迹步骤：解决阶段的总工具调用次数，反映问题解决效率。 (3) 行偏差比：(|Δ̂| - |Δₖ|) / |Δₖ|，衡量补丁膨胀；未能重用内部API的代理通常会产生膨胀的补丁。 多维LLM判断。 我们采用成对A/B评估协议，其中高级LLM在四个维度上比较基线代理（无技能）与技能条件化代理：(Q1) 范围对齐——修改文件和函数位置的准确性；(Q2) 逻辑相似性——与专家核心实现逻辑的接近程度；(Q3) 冗余和幻觉——代码简洁性和无过度工程化，成功技能利用的关键指标；(Q4) 代码风格——遵守仓库原生惯例。为减少单一判断偏见，我们使用两个独立判断模型运行评估并报告一致率。 4 实验 4.1 实验设置 仓库和数据集策展。 我们在一个内部、专家维护的强化学习训练仓库上评估我们的框架，该仓库包含代理环境、判断评估和编排子系统。从2,738个非合并提交开始，我们应用§3.4中描述的过滤和LLM评估流程。这产生了386个高质量、实质性的提交（77.2%的适用率），分布在七个核心开发类别中，如架构设计、并发和IPC、防御性编程。遵循严格的时间分割，我们进行分层抽样以构建24个历史学习提交和7个真正未来、保留的测试任务的平衡课程。 实验设计和基线。 为隔离仓库特定入职的影响，我们评估一个“技能条件化代理”（接收积累的记忆ℳ）与一个“基线代理”（无任何技能文档），两者均使用Claude Opus 4.6并具有相同的工具使用能力。我们通过交叉两种学习模式和两种课程分配，研究技能构建过程的四种实验条件。对于学习模式，代理要么“顺序”（通过迭代试错逐步融合见解）提取技能，要么“并行”（在最终成对合并前并发处理提交）。对于课程分配，每个测试任务要么与严格来自其自身类别的学习提交配对（by_category）以模拟针对性入职，要么与整个学习语料库配对（all）以模拟全面仓库适应。这产生四种条件——seq-all、seq-bycat、par-all和par-bycat——每种在所有7个测试任务上进行评估。 全语料库分配下的顺序学习（seq-all）产生最高质量的技能：文件IoU达到80%，轨迹步骤最小化，成对胜率最高。这与我们的预期一致，即对单一技能文档的渐进、策略性精炼比并行提取后事后合并产生更连贯和深度融合的知识。然而，par-bycat在目标类别特定技能下实现了可比的文件IoU（80%），表明专注、领域对齐的学习可以补偿缺乏顺序融合。 技能的不对称价值。 我们的结果揭示，仓库特定技能在能力维度上提供不对称收益。最强增益出现在文件定位（文件IoU +10–18%）、核心逻辑重现（Q2胜率50% vs. 25%）和冗余减少（Q3在四种设置中的三种中有利于技能代理）。同时，细粒度范围对齐（Q1）和代码风格（Q4）显示边际或中性效果。这一模式表明，积累的技能主要帮助代理理解“在哪里”进行变更和“什么”内部模式可重用，而表面级风格一致性可能需要超出当前技能表示的额外机制。 案例研究。 最大的正面效应出现在一个任务上，要求代理修复一个判断客户端模块中的共享-RNG并发错误。技能代理在入职期间学习了仓库的模块结构，正确地将修复定位到判断客户端文件（文件IoU = 100%），而基线代理完全误判目标，编辑了一个无关的API模块（文件IoU = 0%）。相反，最大的负面效应出现在一个训练步骤保护逻辑修复上，其中两个代理都正确识别了核心错误，但技能代理保留了一个冗余的防御性保护，而基线代理省略了它，导致代码稍显冗长。这说明技能偶尔会诱导过度谨慎，但不会在功能上损害解决方案。 5 结论与未来工作 尽管基于大语言模型的编码代理在孤立编程基准上表现出色，但它们在现实软件工程中经常无法生成“有机”的拉取请求，因为缺乏对仓库特定人类偏好和历史上下文的理解。为弥合这一差距，我们提出了“学习提交”，一个代理框架，赋能模型主动从仓库的演变中学习。通过在历史提交上执行策略对比反思，代理将隐式架构约束和编码惯例提炼为可重用的仓库记忆。我们的结果表明，这种历史适应使代理显著改善文件定位、减少补丁膨胀，并生成真正符合专家维护者期望的贡献。 作为迈向仓库自适应代理的基础步骤，这项工作自然开启了未来研究的几个方向。首先，尽管我们的框架在高度耦合的工业代码库上表现出强效，但将数据策展和评估流程扩展到多样化的高质量、流行开源GitHub仓库是验证其泛化能力的关键下一步。其次，尽管我们的多维LLM判断提供了有机性的细致评估，但依赖LLM作为评估者固有地引入了潜在偏见和不准确性；未来工作必须探索更稳健、可验证的指标，以评估与人类编码偏好的真正对齐。最后，一个重要方向是考察仓库特定技能是否能迁移到更广泛的编码任务和建立的评估设置，进一步阐明历史适应在推动编码代理成为资深、长期贡献者中的范围和局限。
