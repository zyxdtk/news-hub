摘要
随着 LLM 应用日益复杂，开发者越来越多地采用多智能体架构将工作流分解为专门的协作组件，这引入了约束智能体行为并暴露有用语义可预测性的结构。与在高度动态和不确定条件下运行的传统 LLM 服务不同，这种结构化拓扑提供了减少运行时不确定性的机会，但现有系统未能利用它，将智能体工作负载视为通用流量，导致显著的低效。我们对来自智能体服务平台和内部编码助手的生成轨迹的分析揭示了关键瓶颈，包括低前缀缓存命中率、长上下文请求导致的严重资源争用，以及由于次优扩展导致的严重排队延迟。为了应对这些挑战，我们提出了 Pythia，一个多智能体服务系统，它通过服务层的简单接口捕获工作流语义，解锁了新的优化机会，并在吞吐量和作业完成时间上比最先进的基线有显著提升。

  1. 引言
    通用 LLM 服务的传统观点是一切都是不可预测的：在任何给定时间激活的模型类型和数量都无法预测，指向每个模型的请求类型和数量也是如此。这种不确定性源于模型提供商通常只暴露 API 端点供用户访问其模型，而无法控制这些模型何时或如何被调用。因此，之前关于 LLM 服务的大多数工作都假设一个高度动态的执行环境，其中服务系统的几乎每个配置参数（例如，KV 缓存大小、共享模式或自动扩缩容级别）都必须根据运行时观察到的工作负载进行自适应调整。虽然这种适应性提供了相当大的灵活性，但这是一个完全被动的服务系统。

生产轨迹分析。为了证明现有的黑盒方法如何扼杀效率，我们分析了来自我们智能体服务服务的大规模生产轨迹。我们对内部的编码助手进行了深入的性能分析。我们的分析（§2）揭示了在服务智能体工作负载时的三个根本挑战，这些挑战与普遍假设相矛盾。首先，缓存效率远低于预期：专门的智能体使用不同的提示，并且调用间隔很长，导致先前缓存的前缀被驱逐，从而导致频繁的零命中场景和长预填充延迟。其次，由于缺乏工作流感知的调度，系统遭受严重的资源低效：异构请求被任意混合，导致副本和模型之间的负载不平衡，引发内存争用、频繁抢占和昂贵的重计算。第三，多智能体工作流表现出剧烈的、结构化的突发——通常在一分钟内超过 50% 的峰值——这压倒了服务能力；因为现有系统依赖于被动的、平滑的自动扩缩容而没有工作流依赖感知，它们无法预测这些级联，导致跨多个 LLM 的排队和拥塞。

关键洞察：多智能体工作流是可预测的。与根本不可预测的通用 LLM 服务不同，多智能体工作流（如图 1 所示）呈现出截然不同的场景。虽然底层模型可能是通用的，但固定的智能体类型集及其在工作流中的特定角色严格约束了这些模型如何被调用。在这样的工作流中，高级推理组件——通常是充当架构师、规划器或分解器的强大 LLM——处理复杂的任务需求并将其分解为一组子任务。然后，每个子任务被移交给配备特定（通常较小）模型和一组工具的专门工作者智能体（例如，工程师或研究员）。每个智能体通常执行定义明确的任务，并以一致的方式与其模型交互。在许多工业部署中，GPU 集群专用于服务少数特定的智能体应用（例如，编码助手、深度研究系统）。因此，来自同一智能体的请求往往遵循相似的使用模式，引入了相当程度的资源使用可预测性。

多智能体应用中的资源可预测性源于两个关键因素：（1）可预测的工作流和（2）可预测的工作负载。首先，在服务时，工作流的结构——通常表示为图，其中节点对应于单个智能体，边表示数据流——要么是完全确定的（在静态工作流中），要么遵循重复模式（在通过推理动态演变的工作流中）。这种结构信息揭示了请求如何在智能体之间传播，并支持更明智的优化。例如，每次处理全新输入的工作者智能体从前缀缓存中获益甚微。同样，当智能体部署在多个 GPU 上时，调度可以设计为快速使流水线饱和并最大化利用率，而不是依赖仅仅优先处理较早到达请求的朴素 FCFS 策略。其次，由于每个工作者（非编排器）智能体负责具有有限复杂度的特定任务——其中复杂问题通常被分解为更简单的子任务集合——每个智能体节点上请求的输出长度和执行时间通常遵循相对简单的分布，使得它们可以通过试运行或在线性能分析进行准确估计。一旦表征，这些估计可以在工作流执行期间被利用，以实现精确的提前缓存预热和在调用智能体之前的主动模型自动扩缩容。

Pythia。基于这一洞察，我们设计了 Pythia，一个原生智能体服务系统，它系统地利用工作流可预测性来解锁以前被认为难以处理的优化。传统服务引擎将智能体推理视为一个完全不透明和动态的过程，限制了它们只能进行被动的、次优的资源分配。相比之下，Pythia 通过近似请求的剩余执行时间——从其当前在工作流图中的位置及其特定智能体角色的预期输出足迹推断——来实现主动的全局协调。通过将这些结构洞察转化为基于预期完成时间调度请求的优先级机制，Pythia 实现了细粒度优化，从根本上避免了缺乏工作流感知的系统，显著提高了端到端性能和集群利用率。

挑战。充分利用这些可预测性来有效服务多智能体应用需要克服以下两个挑战。第一个挑战是如何告知服务系统工作流的哪些方面是可预测的。例如，工作流图是需要传达给服务系统的关键信息。然而，随着智能体开发越来越大众化，许多智能体开发者可能不是专家程序员，因此可能无法完全理解或指定底层图结构。这个困难因现实世界的多智能体应用通常生成动态图而加剧，其中智能体节点由编排器根据初始任务的复杂性创建。为了解决这个问题，Pythia 引入了我们的核心贡献：一种示例驱动合成方法，它自动从性能分析数据中合成图表示。这种方法基于两个重要的观察。首先，大多数智能体应用具有简单的结构，几次具有代表性输入的运行已经可以生成足够的性能分析数据来帮助我们构建工作流图。其次，尽管动态图不能静态描述，但它通常由重复模式组成（例如，如图 1(a) 所示的连续 Engineer-Executor 交互）。通过分析这些模式，动态执行流可以完全使用正则表达式来表达和预测。为此，Pythia 只需要智能体框架通过 OpenAI 兼容端点已经支持的 extra_body 负载传递关于应用和智能体类型的轻量级信息，而无需在用户应用中进行任何代码更改。在网关处，Pythia 使用分析器来推导工作流和工作负载洞察——包括捕获工作流图的正则表达式以及每个智能体的输出长度——并将这些注释注入回负载中，供服务系统下游消费。

第二个挑战是如何在服务系统中利用这种预测信息。传统的 LLM 服务引擎依赖于根据当前系统状态管理内存和调度请求的被动范式。天真地过渡到主动模型会引入严重性能下降的风险；如果不仔细管理，激进的、前瞻性的决策很容易触发破坏性的资源颠簸和过早的缓存驱逐。为了减轻这些风险并安全地实现这些优化，Pythia 引入了三个协调机制——每个机制都与我们的轨迹分析中确定的关键机会（§2）相一致——以主动优化执行。在节点级别，推测性缓存管理器用受 Belady 启发的策略增强了被动的 LRU，利用工作流洞察预取共享上下文、驱逐瞬态 token 并异步预热缓存以掩盖预填充延迟。在集群级别，前瞻请求调度器使用预测的输出长度和工作流结构来平衡异构工作负载并优先执行，从而减少内存争用和队头阻塞。作为这些组件的补充，阶段自适应自动扩缩容器预测结构化的工作负载转移，例如扇出和阶段转换，以主动扩大或缩小模型，减轻突发引起的排队并提高整体资源效率。

结果。我们在 SGLang 之上实现了 Pythia，并在代表性的多智能体应用上对其进行了评估。我们的结果表明，平均 JCT 降低了高达 2.9 倍，吞吐量提高了 1.96 倍。Pythia 目前正处于大规模集群规模的广泛测试和试点部署阶段，以便更广泛地采用。

    2.1. 背景
    LLM 服务。当今的 LLM 服务系统架构围绕请求级和 token 级执行。性能优化主要针对孤立的微基准测试，侧重于减少首字时间 (TTFT) 和字间时间 (TBT) 以加速预填充和解码阶段。至关重要的是，通常假设服务层对正在进行的请求的输出和传入的工作负载没有先验知识。将每个请求视为不透明的、孤立的实体迫使服务层依赖保守的、被动的策略。例如，请求调度通常被降级为 FCFS 队列，而前缀缓存管理严格依赖于被动的、基于新近度的驱逐策略。

多智能体工作流。LLM 的交互范式正迅速从孤立的、人在回路中的聊天会话演变为自主的、目标驱动的智能体。在这种转变的驱动下，过去六个月中，由执行多步工作流的智能体生成的推理请求份额激增。在我们的智能体服务平台上，目前超过 80% 的请求来自智能体 AI 应用。在现代多智能体系统中，高级目标被分解为可执行的计划，特定的子任务被委托给专门的工作者 LLM 和工具。这些工作者智能体——由定制的系统提示驱动，通常由特定领域的模型支持——处理不同的角色，如规划、编码和审查。传统服务系统将智能体请求视为正常的 LLM 请求，以对智能体语义不可知的方式处理它们。

分层前缀缓存。前缀缓存存储计算过的键值 (KV) 张量以减少冗余预填充。现代系统使用三层层次结构来平衡延迟和容量：L1 驻留在稀缺的 GPU HBM 中以供立即执行访问；L2 在 CPU 主机 DRAM 中充当宽敞的暂存缓冲区；L3 利用共享存储来持久化跨引擎上下文并最小化全局缓存未命中。

2.2. 服务多智能体工作流 LLM 的挑战
随着智能体 AI 越来越主导生产工作负载，包括我们在内的 MaaS 提供商已经推出了具有专门计费模型的专用产品来支持这些应用。然而，一个根本的架构不匹配仍然存在：这些服务仍然依赖于传统的、应用不可知的推理 API。通过将复杂的工作流扁平化为一系列不透明的、独立的请求，服务层完全不知道结构依赖性或不同的智能体角色。为了证明这种黑盒接口如何扼杀效率，我们分析了来自我们智能体服务平台的大规模生产轨迹，并对部署在该服务之上的内部多智能体编码助手进行了深入的性能分析。这种分析揭示了缺乏工作流可见性直接降低系统性能的三个主要挑战。

图 3. 编码智能体工作流的时间线：每个条形代表一个智能体，“executor”代表命令行执行。

挑战 #1：由于出乎意料的低缓存命中率导致的长预填充时间。虽然现有工作通常假设智能体 AI 应用由于重复的提示结构自然实现高缓存命中率，但我们的生产轨迹揭示了一个截然相反的现实。图 2 报告了具有不同数量 token 缓存命中的请求分布。如图所示，超过 40% 的请求具有零或非常有限的缓存命中率。这是因为专门的智能体依赖于不同的系统提示，阻止了跨智能体边界的前缀共享。此外，这些工作流的顺序执行主动降低了缓存保留。为了说明这一点，图 3 详细说明了编码助手的执行时间线。我们有两个观察：(1) 只有少数连续的 LLM 请求能从前缀缓存中受益；(2) 可能有长时间运行的工具调用（例如，代码编译），在这些请求之间可能需要数十秒。当一个智能体被重新调用时，它先前缓存的前缀大部分已被插入的流量冲刷掉。

挑战 #2：由于负载不平衡和不协调的资源竞争导致的资源浪费。图 4 显示了 8-GPU 集群上编码智能体的一分钟服务轨迹，揭示了一个受内存压力和频繁请求抢占严重制约的系统。这种低效源于在没有任何底层工作流感知的情况下混合异构请求——从轻量级的 Planner 响应到长篇的、千 token 的 Architect 输出。我们确定了这种不平衡的三个关键来源。首先，朴素路由导致同一模型的数据并行副本之间出现显著的负载倾斜。其次，跨模型的资源分配不均，导致一些饱和而另一些未充分利用。第三，缺乏工作流感知导致共置的智能体任意竞争共享 GPU 内存，而不是被协调。结果，过载的副本诉诸于抢占请求；在没有预期输出长度知识的情况下，系统通常不加区分地驱逐较新的请求。这些被抢占的请求必须从头开始重新计算，导致大量的计算浪费和明显的队头阻塞。

挑战 #3：突发引起的跨 LLM 排队和拥塞。多智能体工作流本质上表现出极端的结构波动；在我们的智能体服务平台上，我们观察到计划的自动化任务（例如，批处理 cron 作业）可以在一分钟内触发某些模型高达 50.3% 的请求峰值。如图 5 所示，这些大规模激增迅速压倒了支持系统的多个 LLM。至关重要的是，多智能体工作流的相互依赖性质从根本上加剧了这个问题。入口节点（例如，Explorer 智能体）的突发不会保持孤立；相反，它触发级联的请求波，迅速传播到下游智能体（例如，Chronicler, Architect, Engineer）。然而，由于现有服务系统依赖于平滑的、长期的历史指标和工作流不可知的扩展，它们无法预测这种跨模型传播。标准的被动自动扩缩容需要数十秒来增加容量——在这个延迟期间，突发通常已经转移到流水线中的下一个模型，使系统永远落后于波前，导致队列深度激增。

2.3. 原生智能体服务中的先见之明
为了解决上述挑战，我们必须首先了解当今的推理服务为何未能缓解它们。当前的 LLM 服务引擎围绕一个隐含假设设计：请求由独立的人类用户生成。人类聊天流量的特征是不相关的意图、不可预测的到达时间和任意的提示内容。服务系统被迫作为严格的在线算法运行——在没有任何未来知识的情况下被动地管理缓存、调度请求和扩展容量。然而，智能体流量是由程序生成的。多智能体工作流遵循特定的控制流，重用已建立的提示模板，并表现出由其底层源代码决定的访问模式。虽然确切的执行路径可能是动态生成的，但可能执行的空间比人类交互受限得多。这种程序化性质意味着一个根本性的转变：如果服务系统能够先验地捕获工作流知识，它就可以从被动的、在线猜测转变为主动的、近离线优化。具体来说，我们确定了这种知识的三个关键维度，可以系统地缓解观察到的瓶颈。

机会 #1：工作流图。捕获多智能体应用的结构依赖图解锁了多个关键系统优化。首先，它识别了循环的智能体角色，允许服务层策略性地保留其可重用的前缀，而不是在临时内存压力下朴素地驱逐它们。其次，通过理解请求在工作流中的大致位置，调度器可以估计剩余执行时间和依赖性，实现关键路径感知的请求调度。最后，这种结构意识允许系统通过预期即将到来的阶段变化和扇出模式来主动减轻突发引起的排队。在生产环境中获取这种结构先见之明是高度可行的。虽然像 AutoGen 和 LangGraph 这样的框架理论上支持完全动态的、无约束的智能体群聊，但现实世界的部署很少这样运作。因为不受约束的 LLM 容易产生幻觉和任务漂移，企业应用通常施加更严格的路由约束和操作护栏。例如，我们的内部编码助手通过硬编码的转换规则强制执行，仅将基于 LLM 的群聊选择器作为边缘情况的后备。因此，生产工作流趋于稳定，遵循具有良好约束迭代循环的高度可能的执行路径，导致智能体角色之间的转移概率高度集中。

机会 #2：正在进行的请求的输出长度。预测活动请求的输出长度提供了两个关键的操作优势。首先，它支持资源感知调度以减轻严重的内存争用和负载不平衡。通过基于预测的资源消耗而不是朴素的请求计数来平衡系统，服务层避免了触发灾难性队头阻塞的局部内存压力。其次，估计正在进行的请求的解码持续时间为请求何时到达工作流中的下一个智能体提供了细粒度的时间线。这种时间意识允许服务系统及时获取并预热后续智能体的 KV 缓存。

要点。多智能体工作负载的程序化性质引入了强烈的结构、时间和语义可预测性。然而，这种有价值的先验信息在当今无状态的应用-系统接口中完全丢失。为了解决由此产生的一系列问题——缓存颠簸、负载不平衡和突发驱动的排队，服务层必须被赋予一种先见之明。

预测信息生成。Pythia 的入口点是一个扩展以支持轻量级元数据注释的 OpenAI 兼容 API（§4.1）。这些简单的注释用于直接在流行框架（例如，LangGraph 或 AutoGen）中识别不同的工作流和特定的智能体角色。这种最小的 API 扩展对最终用户完全透明，不需要对应用逻辑进行任何更改。除了收集多智能体工作流的结构信息外，分析器（§4.1）通过在关键路径之外异步操作充当 Pythia 的分析核心。通过持续摄取带注释的请求/响应日志，它提取并维护不同智能体的总体控制流图和程序特征。在收到新请求时，它使用提供的元数据查询这些历史配置文件，进一步为下游模块注释请求的三个关键执行估计。

预测信息消费。Pythia 在服务管道的三个不同位置使用上述预测信息：每个节点（智能体）的前缀缓存管理、全局请求调度以及每个节点的模型扩展，这分别对应于现有技术面临的三个主要挑战（§2）。在节点级别运行时，缓存管理器（§4.2.1）通过从被动 LRU 驱逐转向主动的类 Belady 策略来减轻前缀颠簸。它利用提取的工作流信息准确预取共享上下文，并立即丢弃不再需要的瞬态 token。此外，通过预期即将到来的请求的精确提示组成，它异步预热下一个可能智能体的缓存，有效地在后续请求甚至到达之前隐藏预填充延迟。在集群级别运行时，请求调度器（§4.2.2）利用提取的程序特征执行资源感知的负载平衡和精确的请求优先级排序。通过利用预测的输出长度，它将异构工作负载均匀分布在数据并行副本上。此外，这种配置文件感知的方法建立了更好的执行优先级，有效缓解了驱动请求抢占的局部内存争用和队头阻塞。每个节点的模型自动扩缩容器（§4.2.3）通过预期负载变化而不是对其做出反应来管理集群范围的容量。通过根据提取的工作流模式评估当前活动请求的状态，它预测即将到来的结构变化，例如扇出和阶段转换。这种先见之明允许系统在突发到来之前主动扩展专门模型，并在不再需要时缩小它们，有效缓解突发引起的排队。

4.1. 生成预测信息
为了预测跨服务阶段的资源使用情况，Pythia 首先提取传入请求的语义上下文。我们的目标是在不给应用开发者带来繁重集成开销的情况下，或者在不违反应用逻辑与服务基础设施分离的情况下做到这一点。为此，我们引入了一个最小的、透明的 API 扩展，结合了一个异步后台分析器，该分析器使用经典的程序分析技术对工作流执行进行建模。

API 抽象。标准推理 API 隔离请求，剥夺了总体的应用上下文。为了弥合这一差距，Pythia 利用 OpenAI 兼容端点原生支持的 extra_body 参数。当智能体框架分派请求时，它注入一个轻量级的 app_metadata 负载，标识执行上下文。如清单 1 所示，框架只需提供三个显式标识符：(1) workflow_type_id 唯一标识应用（例如，coding_assistant），允许系统将请求映射到特定的结构配置文件。(2) workflow_id 唯一标识会话，允许服务层跟踪特定执行实例的正在进行的谱系和上下文历史。(3) agent_id 唯一标识工作流中的当前节点或角色（例如，engineer），显式指示当前正在执行哪个子任务。我们将 API 扩展限制为这三个标识符，而不是要求应用传递显式定义的依赖图或调度提示。至关重要的是，要求预先提供完整的工作流图和智能体特征是不切实际的，因为它们通常在运行时动态确定。相反，要求应用开发者手动用系统级提示（例如，“缓存此前缀”）标记请求违反了关注点分离，给他们带来了基础设施资源管理的负担。通过仅传递工作流和智能体的身份，Pythia 可以轻松地将请求与历史模式关联起来，将预测和资源分配的负担完全留给底层服务系统。这种最小的抽象实现了轻松部署。对于构建像 LangGraph 或 AutoGen 这样的编排层的框架开发者来说，与 Pythia 集成不需要根本的架构更改。他们只需配置一个全局 API 拦截器，在分派前自动将当前会话和智能体变量附加到 extra_body 负载。因此，建立在这些框架之上的开发者完全透明地 reap 高级系统级优化的好处，而无需更改其应用逻辑或编写硬件感知代码。

通过正则表达式进行执行轨迹建模。一旦这些带注释的请求流入系统，工作流分析器就会异步摄取日志以重建应用的全局行为。从动态程序分析和程序合成中汲取灵感，我们将智能体调用序列视为智能体角色字母表上的执行轨迹。分析器挖掘历史轨迹以构建概率有限自动机 (PFA)。分析器不仅仅预测下一个智能体；它将 PFA 综合成一个正则表达式，投影整个预期的执行图。考虑一个复杂的编码工作流：planner 委派给几个并行的 explorer，接着是一个迭代细化代码的 engineer，一个 reviewer，以及一个可选的返工循环。分析器不是将其表示为无限的、不可预测的循环——例如 (engineer | reviewer)*——而是将执行限制在其高度可能的结构极限内。如清单 1 中的 predicted_path_regex 字段所示，系统捕获了并行扇出 ((explorer)||3,4)、有界顺序自反 ((engineer)3,6) 和可选的单次重试后向边 ((...)?)。此外，分析器将即将到来的提示结构建模为确定性模板。prompt_composition 中的每个占位符充当严格的内存指针，由三个确切参数组成：(1) 依赖智能体的历史 request_id（例如，req_1），(2) 指示是从该智能体的输入 request 还是生成 response 中提取的标志，以及 (3) 要检索的特定 token 索引范围。清单 1 演示了此模板如何捕获智能体拼接组件的方式。

为主导百分位优化。将程序分析应用于智能体工作流的一个关键洞察是，建模每一个可能的执行边缘情况是适得其反的。由于 LLM 固有的随机性，工作流可能偶尔表现出异常转换，进入混乱的错误恢复循环，或触发失控的 token 生成。试图完全考虑这些异常值会导致无限递归表示和显著过度配置的内存预留。相反，Pythia 在控制流和资源使用中故意为主导执行百分位进行优化。它应用轨迹过滤来修剪低概率转换（例如，那些在不到 5% 的情况下发生的转换），产生一个紧密捕获常见执行图的路径表达式。同样，分析器不是预测确切的输出长度或为最坏情况的上下文窗口预留，而是为每个智能体派生高置信区间（例如，历史 token 使用的第 99 百分位）。这种过滤后的、概率性的视图与现实世界的部署相一致：它反映了使 LLM 保持在稳定路径上的结构化路由和护栏，同时限制了内存使用而不会对罕见的、长尾行为过度反应。

可操作的请求注释。在推理时，分析器在网关处运行。当请求到达时，它提取 app_metadata 并查询过滤后的模型以检索预期输出长度，解析描述即将到来的工作流图的正则表达式，并限制下一个提示的模板。然后，它将这些洞察注入到 extra_body 负载内的 sys_annotations 字段中。这个单一的拦截步骤将一个原本不透明的请求转换为完全知情的數據结构，为下游组件配备精确的执行计划和内存提示，用于主动缓存、全局调度和集群自动扩缩容。

早期缓存驱逐（第 5-10 行）。在每个请求完成时，缓存管理器主动修剪 KV 缓存以防止内存膨胀并保护关键上下文。通过解析 predicted_path_regex，它生成一个确定性的未来智能体节点集合。然后它根据这个集合评估缓存中每个块的谱系。属于不会被重新访问的瞬态步骤的块被分类为死 token 并立即释放，绕过了标准 LRU 策略的延迟回收。相反，谱系出现在未来路径中的块被显式标记为保留。管理器不是简单地将这些保留的块困在本地工作者上，而是积极地将它们写出到所有推理引擎都可以访问的共享 L3 存储层。通过主动将未来相关的上下文持久化在全局缓存空间中，Pythia 将缓存驻留与工作者节点亲和性解耦。这简化了集群的全局路由策略，因为多智能体工作流中的后续请求可以调度到任何可用工作者而不会遭受硬缓存未命中。

前向缓存暂存（第 12-19 行）。为了减轻与智能体之间转换相关的预填充延迟，管理器主动为预期的下一步准备确切的上下文。在请求注释中提供的 prompt_composition 模板的指导下，管理器通过注入来自执行 History() 的相关输入和输出来组装即将到来的提示。一旦组装了目标提示，管理器确保其相应的前缀缓存尽可能靠近计算单元暂存。如果此提示的缓存已经存在于更深的、共享的 L3 存储中，管理器会将其提升到 L2 主机 DRAM (PromoteToHost)。至关重要的是，系统有意将此预取的上下文保留在 L2 主机内存中，而不是立即将其推送到高度受限的 GPU HBM。这种设计选择吸收了两个现实：首先，分析器对下一个智能体的预测是推测性的，可能是不正确的；其次，当前正在执行的请求可能会在很长一段时间内继续生成 token，激进地移动推测性数据会过早地污染有限的 GPU 内存。这种前向暂存的作用类似于物流定位：它将必要的内存块保持在受限较少的环境中，仅一步之遥，准备在实际请求到达时进行即时的、按需的 PCIe 传输。然而，如果组装的提示在缓存层次结构中的任何地方都不存在，管理器会尝试从头开始生成它。缓存管理器机会主义地利用 GPU 的计算单元；如果它检测到空闲的 GPU 周期，它会将异步前向传递排入队列以在后台预计算前缀缓存。通过这种主机级暂存和后台预预填充的组合，系统最大化了在框架发出后续推理请求之前前缀被预热的机会。

基于统计容量的路由。在集群入口处，全局路由器将传入请求分配给特定的工作者节点，如算法 2 所示。由于 LLM 输出生成本质上是随机的，依赖静态最大 token 长度会导致严重的内存利用不足，而依赖简单平均值会由于内存不足 (OOM) 导致请求抢占。Pythia 通过利用分析器提取的高置信区间来解决此问题。对于每个请求 r_i，分析器提供从高置信区间（例如，第 99 百分位，产生错误概率 α_i = 0.01）派生的预期上限长度 u_i。这保证了实际长度 L_i 超过此界限的概率 P(L_i > u_i) ≤ α_i。为了避免假设任何底层统计分布，Pythia 依赖于无分布的严格容量预留。如果所有活动请求 A 和新请求 R 的置信界限总和适合内存，则总 KV 容量为 C 的候选节点被认为具有结构能力：∑{r_i ∈ A ∪ {R}} u_i ≤ C。当此预留成立时，OOM 事件只有在实际 token 生成违反这些单独界限时才会发生。通过应用联合界限（布尔不等式），路由器计算 OOM 事件的最坏情况联合概率 P_oom，其严格受限于单独错误概率的总和：P_oom ≤ ∑{r_i ∈ A ∪ {R}} P(L_i > u_i) ≤ ∑_{r_i ∈ A ∪ {R}} α_i。路由器强制要求这种无分布的失败概率保持在严格的、用户定义的安全阈值 (P_oom ≤ ε) 之下。在数学上安全的节点中，它将请求路由到具有最大预期余量 (C - ∑ u_i) 的节点。虽然在主要容量界限中没有严格执行，但路由器使用前向缓存暂存（§4.2.1）作为确定性的决胜局。如果多个节点提供安全的容量配置文件，路由器优先选择已经持有所需 L2 主机缓存的节点，优雅地将严格的统计负载平衡与瞬时缓存命中结合起来。

图驱动的全局优先级分配。在多个智能体共享相同底层模型副本的多智能体环境中，标准 FCFS 调度经常导致集群范围的饥饿。它忽略了工作流依赖性，允许新生成的、长时间运行的智能体阻塞最终阶段的智能体，这严重延迟了最终阶段的完成。为了解决这个问题，Pythia 实现了全局仲裁策略（算法 3 中的 SetPriority）。在请求被路由到工作者之前，全局调度器为其分配一个静态的 base_priority 分数。这个分数明确平衡了两个集群范围的执行目标。首先，它通过优先考虑最接近其工作流末尾的请求来加速作业完成。由于工作流路径由概率正则表达式而非确定性图定义，调度器计算到终端节点的剩余距离的数学期望 (E[D_remain])。优先级分数与此期望成反比，确保在统计上更接近完成的智能体（例如，最终验证器）本质上抢占早期阶段的智能体，以快速从系统中刷新完成的作业。其次，调度器主动监控集群中所有模型副本的实时队列深度。如果服务于未来智能体的模型副本有变空闲的风险，则最终将解除其阻塞的任何上游请求的优先级都会被提升。至关重要的是，这种提升与当前智能体和饥饿模型之间的预期距离 (E[D_m]) 成反比加权。距离馈送空闲 GPU 仅一步之遥的请求获得更高的优先级峰值，而距离十步之遥的请求获得可忽略的提升。这确保了没有专门的推理工作者在等待停滞的上游依赖时处于空闲状态。

周期性本地批次创建。一旦路由到工作者，执行就由迭代级分派控制。在每个调度窗口开始时，本地工作者通过将老化因子（由累积等待时间缩放）添加到全局 base_priority 来动态重新计算所有请求的有效优先级。然后工作者对池进行排序，并分派适合内存边界的最高优先级子集。这确保了早期阶段的智能体在数学上免受永久饥饿的保护，同时保留了全局图的预期执行顺序。

优先级感知的抢占恢复。当尾延迟生成偶尔迫使工作者进入内存耗尽时，Pythia 覆盖标准的 FCFS 驱逐策略。本地调度器不是盲目地将被驱逐的请求附加到队列后面，而是专门针对具有最低动态计算优先级的活动请求（例如，早期阶段的智能体）作为抢占受害者。此请求被暂停并重新插入本地队列。由于队列在每次迭代之前都严格重新排序，关键路径执行完全不受局部内存峰值的影响，从而实现高有效资源利用率和最小化的工作流级等待时间。

4.2.3. 阶段自适应自动扩缩容
虽然前瞻请求调度（§4.2.2）减轻了负载不平衡，但它无法创造新的容量。智能体应用经常表现出由同步触发器（例如，cron 作业）或大规模结构扇出驱动的极端突发性。在这些剧烈变化期间，仅靠调度无法防止队列饱和；集群必须物理扩展其模型副本。当前的无服务器 LLM 解决方案依赖于被动自动扩缩容，这在多智能体执行典型的激进的、瞬时的阶段变化期间失败了。由于将大量模型权重加载到 GPU 内存中需要数十秒，被动配置不仅太慢——而且是有害的。在受限集群中，启动新模型通常迫使盲目驱逐现有模型。当新副本最终准备好时，瞬态突发通常已经消退，留给系统的是一个空闲模型和被破坏的其他基本模型缓存，触发了破坏性的冷启动级联。Pythia 通过利用工作流分析器提取的常规路径表达式引入预测控制平面来克服这一点。它不是对队列积累做出反应，而是预测即将到来的突发并在流量转变发生之前主动配置副本，完全避免了被动的资源颠簸循环。

针对结构变化的前瞻性扩展。Pythia 不是等待队列峰值，而是持续评估所有活动请求相对于其工作流图的状态，以预测即将到来的需求（算法 4 中的 EstimateImminentDemand）。通过将执行图向前投影定义的步长范围 (H)，自动扩缩容器计算哪些模型将在不久的将来被广泛利用。例如，如果集群当前有五十个活动请求在 planner 阶段执行，并且底层正则表达式规定了 planner → (explorer)||10 的转换，自动扩缩容器在数学上知道不久的将来会有 500 个对 explorer 模型的请求。在 planner 智能体甚至完成生成其输出之前，Pythia 主动触发额外 explorer 模型副本的后台配置。当框架实际分派大规模扇出突发时，新的 GPU 节点已经预热并准备就绪，有效缓解了突发引起的排队并隐藏了冷启动延迟。

预测性缩减和资源回收。在资源受限的集群中，扩展一个专门模型通常需要驱逐另一个模型。标准系统依赖静态的保活超时（例如，在关闭空闲模型之前等待 5 分钟），这在关键阶段变化期间囤积了宝贵的 GPU 内存。Pythia 通过预测性缩减加速了此回收过程。因为自动扩缩容器拥有活动工作负载的完整结构图，它可以识别哪些模型在不久的将来不会被调用。这包括为严格属于过去的智能体提供服务的模型（例如，一旦所有工作流都已转换到 explorer 阶段的 planner）以及为拓扑上太远而不值得立即预热的智能体提供服务的模型（例如，距离当前执行前沿许多步骤的 final_verifier）。为了最大化安全缩减的机会，自动扩缩容器直接与全局调度器协调。一旦模型被识别为在即时前瞻范围内已过时，自动扩缩容器就会向调度器发出信号，停止将新请求负载平衡到那些特定副本。这种主动路由排除允许副本快速排空。一旦目标副本的即时队列为空，Pythia 强力取消配置它，而无需等待任意超时。这种激进的、图驱动的回收确保了集群资源被持续释放并重新分配，以支持即时执行阶段所需的模型。

  1. 讨论
    对许多不同智能体工作流的支持。目前，Pythia 主要为运行少量目标智能体应用集的环境设计。当扩展系统以同时服务大量不同的工作流时，Pythia 成功地保持了其最小化全局平均 JCT 的核心优势。然而，在这种高度异构的环境中，依赖我们当前相对简单的调度启发式方法可能会无意中牺牲某些单独工作流的性能以最大化整体吞吐量。为了有效地平衡集群范围的资源效率与其他用户要求（例如，每个工作流的 SLO 或公平性保证），Pythia 的前瞻调度器可以自然扩展。通过将每个工作流的优先级权重和显式延迟目标直接纳入我们的调度算法，系统可以做出更细致的、SLO 感知的分配决策，保护关键任务工作流，同时仍保留聚合优化。

冷启动和工作流漂移。Pythia 对历史轨迹的依赖在初始部署（冷启动）和应用更新（工作流漂移）期间引入了挑战。为了防止不足或过时数据触发不安全路由，Pythia 可以将显式 API 版本控制与“影子分析”阶段配对。当通过 app_metadata 检测到新工作流版本时，网关临时将其流量路由通过标准的、被动的后备方案，同时在后台对其进行分析。一旦建立了安全的统计置信区间，系统就会无缝地将工作流提升到主动执行层，确保生命周期转换期间的稳定性。

开放式和对抗性工作流。Pythia 依赖于企业应用典型的结构可预测性，这些应用应用路由护栏并假设受信任的输入。在完全不受约束或对抗性的场景中，执行图退化为不可预测的网格，使我们的主动优化无效。为了适应此类环境，未来的部署可以采用混合架构：Pythia 将服务于可验证的、可预测的工作流，而将高度偏离或对抗性的请求卸载到孤立的、被动调度的后备环境。

LLM 服务系统。现代服务引擎跨多层高度优化。对于调度，Orca 引入了迭代级调度来处理不同的请求长度，而 FastServe 使用抢占来减轻队头阻塞。为了管理异构执行阶段，系统探索分离（例如，预填充-解码分离）或共置（例如，分块预填充）这些阶段。内存管理同样关键：PagedAttention 使用操作系统虚拟内存抽象来减少 GPU 内存碎片，而其他工作通过利用缓存和内存层次结构来加速预填充阶段。在算子级别，像 FlashInfer 和 FlashAttention 这样的库提供了基础的高性能注意力内核。最后，多 LLM 服务系统专注于空间和时间复用，以最大化共置在共享硬件上的模型密度。与针对端到端智能体工作流进行优化的 Pythia 不同，这些系统主要针对细粒度的请求级和 token 级指标。

针对智能体 AI 的系统优化。最近的工作已经认识到，服务智能体 AI 应用带来了超越传统 LLM 推理的新系统挑战，促使在专门的运行时和服务框架中进行专用优化。Pancake 设计了一个高效的多层智能体内存系统，DualPath 优化了智能体工作负载的远程前缀缓存的网络瓶颈。诸如 ThunderAgent、Ayo 和 Autellix 等系统专注于改善长视野复杂智能体管道的请求编排，而 KVFlow 和 Continuum 提出了通过跨步前缀缓存共享来减少冗余预填充的内存优化。然而，这些系统没有像 Pythia 那样充分利用可预测的程序语义进行细粒度的服务优化。

  1. 结论
    多智能体 LLM 工作负载的结构化性质从根本上改变了服务设计空间。通过暴露工作流语义，Pythia 将不透明的请求转化为可预测的执行，解锁了传统系统中不可能实现的主动优化。我们的评估证明，利用这种可预测性对于克服缓存低效、资源不平衡和突发引起的拥塞至关重要。
