代码即策略智能体自我修复的再思考：重试成功靠什么？

📅 2026-11-04 📄 arxiv 🔗 原文链接

原标题：Rethinking Self-Repair in Code-as-Policy Agents: What Drives Retry Success?

中文摘要： 本文研究代码即策略智能体失败后反馈对重试成功的贡献。模拟机器人复位重试实验中，基于失败标签的模板反馈使 Qwen2.5-Coder-7B 五次重试内恢复 85.3% 初始失败，高于重采样的 68.3%。但其他回合反馈与固定任务指导恢复率相近，匹配失败标签无额外收益；首次尝试即用固定引导提示词亦获相近成功率。需边缘抓取的螺母插入任务上，中心抓取指令反而有害。建议自我修复评估纳入重采样、不匹配反馈与静态指导基线。

摘要

代码即策略智能体通常利用执行反馈来重试失败的程序。额外采样和任务指导同样可以提升成功率，这使得针对特定失败的反馈的贡献变得不明确。我们在模拟机器人操作中研究这一问题。一个固定的查找表根据失败标签和 API 变体选择反馈模板。一个冻结的代码模型在每次场景重置后生成全新程序。在相同的 252 个初始失败上，Qwen2.5-Coder-7B 在五次重试内恢复了 85.3%，而相同重试上限下的重采样为 68.3%。该优势在固定总 token 预算下依然存在。来自其他回合的反馈和固定任务指导产生相近的恢复率点估计，未检测到匹配粗粒度失败标签带来的收益。在一项独立研究中，从第一次尝试起就使用固定引导提示词所达到的观测总体成功率与基于模板的反馈相近。基于模板的反馈在需要边缘抓取的螺母插入任务上降低了恢复率，这与不兼容的中心抓取指令相一致。机器人自我修复的评估应将重采样、不匹配反馈以及简洁、任务兼容的静态指导作为基线。

关键词：代码即策略智能体、自我修复、执行反馈、测试时评估

1 引言

代码即策略智能体将语言指令转换为可执行的机器人程序 [1]。它们的失败往往遵循清晰的模式：程序可能跳过抓取、在抬起后释放物体，或将物体放置在远离目标的位置。一种常见的应对方式是迭代式自我反思。模型阅读其失败的程序和执行轨迹，撰写批评，然后再次尝试 [2, 3, 4]。重试成功可能反映了额外采样、简洁的任务指令、关于当前失败的反馈，或对先前程序的编辑。我们提出的问题是：失败后的反馈是否比从第一次尝试起就可用的指导更能提升恢复率。

我们使用冻结的 Qwen2.5-Coder-3B/7B 模型在"重置-重试"设置中研究这一问题。每次重试都从原始场景开始。我们的主要条件生成全新程序，且提示词中省略失败的程序。我们使用基于模板的反馈来研究哪些信息能提升重试成功率。一个固定的查找表根据失败标签和 API 变体选择指令，例如"必须（MUST）在抬起前抓取物体"。我们将此条件称为 Compiled（编译式）。该查找表使我们能够将匹配的反馈替换为另一回合的反馈、保持指导固定，或在保持重试循环不变的情况下移除反馈（图 1）。单独的编辑条件会展示先前的程序并要求修改。所有条件都重启原始场景。我们不测试从失败遗留的物理状态中恢复。

Compiled 在五次重试内恢复了 252 个初始失败中的 85.3%，而相同重试上限下的重采样为 68.3%。在固定总 token 预算下，这一增益依然存在。来自其他回合的反馈和每个任务一个固定模板产生相近的点估计。我们未检测到将粗粒度失败标签与当前回合匹配带来的收益。置信区间仍然允许条件之间存在差异。在一项独立研究中，从第一次尝试起就使用固定引导提示词达到了与 Compiled 相近的观测总体成功率，且每个已解决回合使用的 token 更少。该比较同时改变了初始指导和生成指令。它们各自的贡献仍未解决。

我们在匹配的重试预算下比较反馈内容和程序生成策略，以测试额外采样、可复用的任务指导以及失败标签匹配如何影响恢复率。机器人自我修复的评估应将静态指导作为自适应反馈的基线。

2 相关工作

机器人控制的语言模型。 Code as Policies 和 ProgPrompt 从具身机器人技能生成可执行程序 [1, 5]。SayCan 使用语言模型和可供性分数选择动作 [6]。CaP-X 在机器人 API 和反馈模态上评估代码生成智能体，包括不重置场景的多轮交互 [7]。机器人恢复系统通常要求模型解释失败。REFLECT 总结机器人经验以支持失败解释和纠正 [8]。DoReMi 将计划与其执行进行比较 [9]。TCoT 为视觉-语言-动作模型添加轨迹级推理 [10]。我们基于重置的比较在匹配的重试预算下，于配对回合上检验反馈内容和程序生成策略。

迭代式自我修复的评估。 Reflexion 和 Self-Refine 使用模型撰写的批评来改进后续输出 [2, 3]。Self-Debugging 依据先前程序及其执行结果来调节代码生成 [4]。在代码基准上，Olausson 等人 [11] 发现自我修复在匹配计算量下通常不如独立采样。没有外部反馈时，推理的自我纠正也不可靠，而基于外部证据的批评则能有所帮助 [12, 13]。我们将匹配采样的比较扩展到具身代码执行，并测试指导是否必须与当前失败匹配，或是否根本需要跟随失败。

执行反馈与交互式评估。 CodeRL、RLEF 和 MURPHY 使用编译器或测试反馈来更新模型参数 [14, 15, 16]。RLEF 还在推理时测试来自无关编程问题的随机执行反馈。该比较检验了针对当前问题的特定反馈的价值，尽管其训练、任务和反馈构建与我们的不同。ReAct、Voyager 和 LATS 等推理时智能体在搜索或交互过程中使用反馈 [17, 18, 19]。InterCode、AppWorld 和 AgentBoard 评估执行结果和中间进度 [20, 21, 22]。在模型权重固定的情况下，我们探究机器人重试提示词中的哪些信息能够解释恢复。

3 方法

3.1 实验设置

我们在 robosuite 仿真中使用 Panda 机械臂评估冻结的代码模型 [23, 24]。模型接收状态信息并使用有文档说明的机器人 API 生成 Python 程序，不使用图像。主要评估使用 Qwen2.5-Coder-7B-Instruct [25]，在立方体抬起和堆叠任务上使用原语 API。

一个回合包括针对某任务和场景的初始程序执行，以及随后在某一方法下的任意重试。初始执行记为第 0 次尝试。初始失败后，模型最多可进行五次重试。每次重试前，仿真器重置到原始场景。每次重试产生一个完整程序，要么从头生成，要么从先前的程序修改而来。

我们使用 252 个初始失败进行评估，40 个用于开发。这些集合包含不同的初始程序，通过其哈希值识别。评估涵盖 159 种任务、API 变体和场景的组合，其中 24 种也用于开发。所有方法都在相同的存储初始失败上进行评估。端到端研究按场景种子配对方法。

条件恢复率@k 是在 k 次重试内解决的第 0 次尝试失败的比例。该指标衡量顺序重试，不同于从独立样本估计的 pass@k。对于端到端研究，初始成功率是第 0 次尝试的成功率，总体成功率@6 是六次允许执行中任意一次成功的比率。如果一次尝试的程序能够编译、仅使用有文档说明的 API 函数并在超时前完成，则该尝试有效。

泛化研究包括 Qwen2.5-Coder-3B/7B 和另外两个拾取-放置任务。我们汇总满足预定义资格标准的七种设置的结果。单独的研究考察了高层辅助函数更少的 API 变体、Qwen2.5-Coder-32B 和 DeepSeek-Coder-6.7B [26]。软件、任务、评估集和指标的更多细节见附录 A。

3.2 基于模板的反馈

执行失败后，一个基于规则的标注器从 14 类标签体系中分配一个主标签。Compiled 将该标签和 API 变体映射到一个固定的反馈模板，其中包含诊断和简短的 MUST/NEVER（必须/禁止）指令（表 1）。该查找不需要额外的模型调用。这些指令引导代码生成，而不施加执行时检查。

Compiled 累积来自初始失败和后续失败重试的反馈，保留标签和尝试索引。反馈块将最新的反馈放在最前面，省略重复的指令行，并遵守反馈长度限制。生成提示词包含任务、API 文档和累积的反馈，省略先前的程序。早期研究中的一个示例展示了初始失败后紧跟一次成功的全新重试（图 2a）。提示词见附录 B，重置-重试算法见算法 1。

我们在每项研究内使用相同的生成器、任务、API、解码设置和重试上限来比较方法。

重采样重复不带反馈的基础重试提示词。

其他回合反馈将当前回合的反馈替换为来自其他失败的反馈，按任务、API 变体和初始任务进度区间匹配。主要的匹配对照——不同标签反馈——从同一任务的其他回合中选择单条反馈记录，优先选择相同的初始任务进度区间，并尽可能要求不同的失败标签。两者都随着被评估回合累积失败而添加反馈，并使用相同的反馈长度限制。这些对照检验匹配粗粒度失败标签的价值，同时保留有用的任务信息。匹配和回退规则见附录 B.3。

4 结果

4.1 匹配预算下的恢复率

在主要评估中，Compiled 在五次重试内恢复了 252 个留出失败中的 85.3%。相同重试上限下的重采样恢复率为 68.3%，差异为 +17.1 个百分点（95% 置信区间 [+9.9, +24.2]）。¹

¹ pp 表示百分点。带状图和误差线显示 95% 置信区间：恢复比例使用 Wilson 区间，差异使用配对自助法。

Compiled 从第一次重试起就比重采样恢复更多失败（图 1b），并且使用的模型总 token 更少，包括提示词和补全。

在固定 token 预算下，Compiled 在 2,000 token 时比重采样提升 +15.9 个百分点，在 5,000 token 时提升 +14.7 个百分点（图 2b）。固定任务模板和不同标签反馈的观测恢复率与 Compiled 相近，而直接+编译式的恢复率较低。在使用原始生成指令的早期 700 场景端到端研究中，Compiled 的总体成功率也高于重采样（附录 C）。

4.2 反馈匹配与内容

在主要评估中，不同标签反馈和固定任务模板各恢复 86.1%，而 Compiled 为 85.3%。我们未检测到将粗粒度标签与当前失败匹配的优势，尽管配对置信区间并不能确立等价性（表 2；图 2c）。在早期研究中，我们也未检测到 Compiled 相对其他回合反馈、置换标签或仅初始标签的优势（附录 C）。

在主要评估中，探索性的重复 API 规则对照复制了提示词中已有的规则，未能复现 Compiled 的改进。使用原始生成指令的早期比较同样显示，无内容反馈和全模板并集的恢复率低于简洁的反馈模板（附录 C）。

4.3 从第一次尝试开始的指导

在 700 个新场景上，从头静态指导将初始成功率从标准提示词的 19.3% 提升到 36.9%。它从第一次尝试起使用完整的固定任务模板重试提示词，同时改变了任务指导和生成指令。它们各自的贡献仍未解决。

到第六次执行时，从头静态指导达到 92.4% 的总体成功率，而 Compiled 为 89.6%，固定任务模板为 90.1%（图 3）。其相对 Compiled 的优势在多重性校正后不具有统计显著性（+2.9 个百分点；Holm 校正后 p=0.13）。它每个已解决回合使用的模型总 token 也最少。完整结果和提示词差异见附录 C.2。

匹配对照和从头静态指导的结果表明，可复用的任务指导解释了这一增益。这些结果并不能确立模型使用了当前的执行轨迹。

4.4 编辑与反思

直接+编译式在主要评估中达到 21.4% 的恢复率。早期分析显示，编辑带来的程序变化小于全新生成。由于直接+编译式同时改变了代码暴露和生成指令，其恢复率较低的原因仍未解决。

在早期核心评估中，反思达到 56.0% 的恢复率，低于重采样，同时使用了更多补全 token 和实际运行时间。这些发现针对的是所测试的编辑和反思实现。更多编辑和批评结果见附录 C.1。

4.5 泛化与失败案例

图 4：指导的收益因任务和模型而异。各评估设置上 Compiled–重采样的恢复率差异。菱形总结了七个符合条件的泛化设置。

在涵盖四个任务和 354 个初始失败的七个 Qwen2.5-Coder-3B/7B 设置中，Compiled 将 recovery@5 相比重采样提升 +18.1 个百分点（置信区间 [+13.3, +22.9]）。其相对其他回合反馈的差异较小，为 +2.3 个百分点（置信区间 [−1.1, +5.6]），未检测到相对这一同任务反馈对照的优势（图 4；附录 C.3）。

恢复率优势在 API 变体、位姿噪声和生成种子的大多数额外评估中持续存在。然而，在温度 0.2 且位姿偏移的抬起任务上，Compiled 的恢复率比重采样低 19.6 个百分点。

使用 Qwen2.5-Coder-32B 时，Compiled 和重采样在 55 个初始堆叠失败中解决了相同的 52 个（94.5% 的 recovery@5）。如此高的恢复率使得进一步改进的空间有限。

在螺母插入任务上，所需的边缘抓取与拾取-放置模板中 failed_grasp 的中心抓取指令冲突。Compiled 的 recovery@5 为 82.5%，重采样为 97.5%，差异为 −15.0 个百分点（置信区间 [−27.5, −2.5]）。这一下降与不兼容的抓取指令相一致，而尝试有效率保持相近。因此，在一个任务族内有帮助的指导在另一个任务族中可能有害。

5 讨论

我们的结果表明，在所测试的任务中，可复用的任务指导解释了基于模板的反馈相对重采样的恢复率优势。固定指导和来自其他失败的反馈产生与 Compiled 相近的恢复率点估计，未检测到匹配粗粒度失败标签的收益。从头静态指导也达到了与 Compiled 相近的观测总体成功率，同时每个已解决回合使用的 token 更少。评估应将第一次尝试起就使用的固定指导与失败后选择的反馈一同测试。从头静态指导比较同时改变了指导和生成指令，因此它们各自的贡献仍未解决。

因此，自我修复的评估应区分额外采样、可复用指导和失败特定信息的贡献。重采样为额外采样提供基线，各方法的重试和 token 预算相匹配。静态指导测试指令在失败发生前是否有用，而不匹配反馈测试将粗粒度失败标签与当前回合匹配的价值。这些比较应检查与任务需求冲突的指令，例如在需要边缘抓取的任务上使用中心抓取指导。

6 结论

机器人自我修复的评估应包括重采样、不匹配反馈、从第一次尝试开始的静态指导以及先前程序编辑，且各方法的重试和 token 预算相匹配。

我们的发现仅限于使用特权状态和粗粒度反馈的模拟操作。一些比较结合了指令和信息的变化。未来工作应分离这些影响，并考察更大模型在更难任务或更紧预算下的表现。将评估扩展到视觉反馈和物理恢复（包括失败后状态和动作成本），将有助于阐明自适应反馈何时优于静态指导。

A.2 解码、指标和统计分析

初始失败后，每个条件从原始场景最多获得五次重试。在一项研究内，各条件共享模型、任务、API、解码设置和重试上限。除非另有说明，生成使用温度 0.7、top-p 0.95、1,024 token 补全限制和 768 空白 token 反馈上限。反思调用允许 256 个补全 token。

条件恢复率@k 是在 k 次顺序重试内解决的初始失败比例。任务成功由独立的最终状态几何谓词检查。有效程序可编译、仅调用有文档说明的函数并在超时前完成。如果一次执行使物体离开桌面，则计为安全违规。

配对差异的置信区间使用 10,000 次自助重复。精确 McNemar 检验评估最终重试时的显著性，并在每个预定义比较组内进行 Holm 校正。区间为 95%，除非早期次要结果标记为 90%。主要分析将每个存储的初始失败视为一个观测。对 159 个任务–API–场景聚类的探索性自助法考虑了场景配置内的依赖性，并保留了 +17.1 个百分点的 Compiled–重采样差异（95% 置信区间 [+10.1, +24.2]）。

固定 token 分析按顺序重放记录的调用。每次调用的提示词和最大补全配额必须适合剩余预算。Token 使用包括提示词、补全和反思调用。预算为 2,000、5,000 和 9,500 token。原始 1,000 token 预算内无法容纳任何调用。在端到端研究中，每个已解决回合的 token 是所有场景的总 token 使用量（包括第 0 次尝试和未解决场景）除以已解决回合数。

A.3 可复现性说明

开发和评估包含不同的初始程序，但共享 159 个评估场景配置中的 24 个。最早的核心比较配对存储的初始失败，尽管放置采样器种子限制允许重试布局不同。后来的研究对每次重置设置种子，随后使用原始生成指令的评估使用重建的软件。每次比较使用单一软件构建。种子设定不保证按位确定的仿真。

泛化问题在核心结果之后进行了修订，该研究的设置和分析在生成之前固定。从头静态指导研究也在生成之前指定。固定任务模板是在开发数据上选择的，因此其首次留出比较是探索性的。后来的研究复用了这一固定文本。直接+编译式是在单独的 116 失败试点中选择的。

失败标签在脚本化故障上进行了审计，未对自然失败进行人工审计。未测量预言机提示性能和模板编写成本。

- 顶层代码直接运行；如果将步骤包装在辅助函数中，必须调用它。
- 要抓取物体：goto_pose 到其中心位置，然后 close_gripper()。
- 成功在场景的最终状态上检查：被抬起的物体在结束时必须仍被持有（除非任务要求释放，否则抬起后不要调用 open_gripper()）；要放置物体，将其移动到目标上方并 open_gripper()。
- place_on(source, target) 将被持有的物体定位在目标上并自动释放；place_on 之后不要调用 open_gripper()。
