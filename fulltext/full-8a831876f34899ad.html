企业AI智能体基础设施的治理之战

企业 AI 面临一个新的基础设施问题：企业积累 AI 智能体的速度，已经超过了它们开发相应治理系统的速度。

Gartner 估计，到 2028 年，全球财富 500 强企业平均将使用超过 15 万个 AI 智能体，而 2025 年这一数字还不到 15 个。然而该研究公司指出，目前只有 13% 的组织认为自己拥有合适的 AI 智能体治理体系。

这种不断扩大的差距正在催生一个位于单个模型和智能体之上的基础设施市场——负责处理执行、权限、可观测性、内存、对企业系统的访问以及生命周期管理，而无需开发人员为每个新智能体重构这些服务。

xpander.ai 是一家由三位前 AWS 主任工程师创立的初创公司，是最新一家试图占领这一层的公司。

该公司今天正式全面推出其企业级 AI 智能体平台，将其定位为一个供应商中立的控管平面，用于跨不同模型、智能体框架和基础设施环境构建、运行和治理智能体。

在接受 VentureBeat 独家专访时，xpander.ai 首席执行官兼联合创始人 David Twizer 表示，公司越来越多地听到企业客户反映三个问题：智能体在本地运行缺乏集中治理、智能体工作流仅限于单个用户、以及基础设施被绑定到单一 AI 提供商。

“第三个问题是最关键的部分：被锁定在一家供应商身上，”Twizer 告诉 VentureBeat。“你所做的一切实际上都归你选择合作的公司所有——他们的工具、他们的路线图、以及他们对于智能体应如何对你所做的一切做出反应的政治观点。”

需要指出的是，xpander 的供应商中立性并不能消除依赖；它只是将依赖关系向上移动到了技术栈的更高层。企业可以在 xpander 底层替换模型、框架和基础设施，但 xpander 专有的 Universal Harness 和控管平面成为了协调执行、治理、身份、内存和可审计性的那一层。

如果这些配置和操作状态难以迁移到另一个控管平面，这可能会造成一种新的锁定。xpander 的公开文档尚未解释如果客户终止其企业级许可证，该层的可移植性如何。

该公司还宣布完成了 750 万美元的种子轮融资，由 Pico Venture Partners 领投，Emerge Ventures、Samsung Next 和 SeedIL 参投。

但 xpander 进入的这个市场已经发生了相当大的演变，早已超越了专有超大规模云平台和中立替代品之间的简单划分。

战火向模型层之上转移

模型可移植性在智能体基础设施中正变得越来越普遍。

例如，LangChain 的 LangSmith Deployment 为部署和治理生产级智能体提供了基础设施。企业可以完全在自己的 Kubernetes 基础设施内运行其控管平面和智能体服务器，包括针对气隙隔离和对数据驻留敏感的环境。LangChain 还提供混合部署，由客户操作智能体服务器，而 LangChain 管理控管平面。

CrewAI 也在朝着大致相同的方向发展。其企业版产品包括集中治理、SSO、基于角色的访问控制、工作负载身份和策略，同时支持在 CrewAI 云、客户 VPC 或客户自有基础设施中部署。CrewAI 表示其平台可跨模型和云工作，并允许客户保留和修改为其智能体生成的代码。

Temporal 则从另一个方向解决这个问题。它不提供端到端的智能体管理环境，而是为长时间运行的 AI 工作流提供持久化执行，包括崩溃恢复、重试、人工审批以及能在故障中持续存在的状态。其 AI 平台可以跨不同模型、工具和系统编排工作流。

与此同时，模型和云供应商自身也在向上扩展到这一基础设施层。OpenAI 的 Frontier 平台提供共享的企业上下文、权限、智能体执行和管理；而 Google 的 Gemini Enterprise Agent Platform 则将托管运行时基础设施与智能体身份、集中治理、内存、追踪以及围绕智能体与智能体、智能体与工具交互的策略执行结合在一起。

换言之，xpander 的差异化优势不能仅仅是企业可以在一家模型提供商的云之外运行智能体。几家竞争对手已经提供了这种灵活性的不同版本。

其更大的押注在于，企业会希望拥有一个独立于框架的控管平面，它位于日益多样化的模型、智能体框架和面向员工的 AI 界面集合之上。

Twizer 的论点部分源于他在 AWS 七年的工作经历，在那里他目睹了企业如何与上一代基础设施锁定作斗争。

“我们的战略是引入名为云计算的伟大事物，然后尝试创建无服务器解决方案，这本质上就造成了供应商锁定，”Twizer 告诉 VentureBeat。但他表示，企业最终要求的是在提供商之间转移工作负载的能力。

“我认为 AI 也不例外，”他说。“多云、多供应商是必备策略。”

旨在挺过模型更迭的运行时

xpander 平台的核心是它所谓的 Universal Harness——一个与模型、框架和云无关的运行时，用于将智能体作为可移植的企业工作负载来执行。

公司可以使用 xpander 的托管环境，或者在其企业版产品下，在 Kubernetes 或本地基础设施上自行部署。该公司还明确将 AWS、Google Cloud、Microsoft Azure、私有 VPC 和完全气隙隔离的本地环境列为支持的部署目标。

关于框架的声明同样宽泛：xpander 表示，客户可以引入使用包括 LangChain、Strands 和 Agno 在内的框架构建的智能体，以及他们现有的提示词、规则和技能。它支持专有、开放权重和客户微调的模型。

对于开发者，xpander 提供了三个主要集成途径：用于控管平面操作的语言无关 REST API、用于构建智能体和工作流的 Python SDK，以及将智能体和工具暴露给 Claude Desktop 和 Cursor 等 MCP 客户端的模型上下文协议（MCP）支持。REST 接口包括管理和调用智能体、任务和知识库的操作，而 SDK 增加了事件处理和智能体生命周期抽象。

“可以把它想象成一个在你自己的场所、私有云或我们的 xpander 云中运行的 Kubernetes 环境，”Twizer 告诉 VentureBeat。“那个不可知的 harness 可以运行任何供应商的任何智能体。”

Twizer 表示，最终目标是让模型选择变得更类似于为应用程序选择底层算力，而不是让组织承诺绑定一整个软件生态系统。

“你可以从 Claude 切换到 ChatGPT，再到 Kimi 和你自己的微调模型，”他说。“所有这些都将像你使用 CPU 一样被使用。你并不真正关心是谁制造的。你只希望你的应用程序能运行起来。”

这种架构旨在让底层工作负载发生变化，同时编排和操作层保持相对稳定。

随着企业使用不止一家 AI 供应商，这种区别可能会变得更加重要。OpenAI 自己也表示，企业 AI 正从辅助转向由智能体执行委派的工作，其最新企业数据显示，在法务、销售、招聘和营销等职能部门中，智能体的使用量正在迅速增长。

与此同时，Google 正在添加集中式智能体治理、身份和网关控制，专门用于大规模管理智能体和工具之间的交互。这些来自更大供应商的投资强化了 xpander 的基本前提：管理模型 increasingly 只是智能体投入生产的其中一个环节。

“治理”在实践中意味着什么

Twizer 认为，本地运行的智能体使这一操作问题变得尤为尖锐。

“你安装了 Claude 或 ChatGPT 或 Codex 或任何其他在员工笔记本上运行的 AI 系统，你得到的就是一个黑盒，”他告诉 VentureBeat。“没有任何东西被治理，没有任何东西被审计，也没有任何东西被控制。”

他担心的不仅仅是智能体可以访问本地资源，而是 AI 产品已经迅速从生成文本转变为采取行动，而企业不一定围绕它们构建了同等的治理基础设施。

“一夜之间，‘这是一个帮我写邮件的聊天机器人’就变成了‘这是一个可以控制我的机器并进行 API 调用的 AI 智能体’，”Twizer 说。

xpander 的文档提供了更具体的定义，说明了公司将这种活动移入受治理环境意味着什么。

控管平面可以定义谁被允许运行智能体、智能体可以访问哪些资源以及哪些操作需要人工批准。xpander 表示，智能体会获得命名的身份，并且操作可以追溯到调用它们的人类。工具调用、运行、追踪、审批和失败都会被记录下来，并且可以在任务级别归因支出。

对于安全团队而言，一个特别相关的架构细节是凭证处理。xpander 表示，凭证是在工具调用执行时从保险库中注入的，而不是直接暴露给模型。

该公司表示，它已通过 SOC 2 Type II 认证并符合 GDPR。其企业版还包括 SSO 和 OIDC、私有模型网关以及具有按团队使用量归因的子组织。

xpander 试图将自己与 LangSmith 和 CrewAI 等产品区分开来的地方在于，它将底层的智能体框架本身视为另一个可替换的组件，而不是将其自己的框架作为主要的开发环境。

该公司表示，其运行时可以将 xpander 原生智能体与使用其他框架构建的自定义智能体一起操作。这种更广泛的框架中立性是公司单方面的声明，需要在生产环境中得到证明；这些平台之间的重叠已经相当严重。

自行构建智能体层的成本

对于想要集中控制而不采用另一家供应商基础设施的企业来说，另一种选择是越来越多地自行组装这些组件。

Twizer 认为，这就是生产级智能体隐藏成本出现的地方。访问基础模型相对简单；但重新创建围绕复杂托管智能体的操作基础设施却并非如此。

“如果你想以受治理和安全的方式实现像 [Anthropic] Claude Code 这样令人惊叹的东西，你需要构建整个 harness，”Twizer 告诉 VentureBeat。“你需要构建沙箱、身份验证、人在回路、存储、会话管理和内存层。”

“这就像投入两年的基础设施时间，只为了以一种安全的方式运行那个智能体，”他补充道。

该公司的文档表示，其 harness 可以处理长周期和多工具任务、沙箱代码执行、持久内存以及在任务失败或偏离时的恢复。这是 Twizer 论点的重要背景：xpander 不仅仅是提供一个将一个模型 API 替换为另一个的网关；它试图打包许多运行时服务，否则企业必须在那些 API 旁边自行操作这些服务。

Twizer 表示，xpander 听取了在生产环境中使用其技术的政府组织和金融机构的意见，他们表示这种基础设施负担阻碍了他们以受控方式部署智能体。

该公司网站还在“被以下团队使用”标签下展示了包括联想、英特尔、Workday、西门子、英伟达、Intuit、SAP、PagerDuty、Mozilla 和 Salesforce 在内的组织标识。

该公司的答案并不是说企业应该放弃 Anthropic、OpenAI 或其他 AI 提供商的产品。Twizer 反而认为，公司应该保留这些模型，同时将权限、监控和执行转移到他们可以控制的基础设施层中。

“这不是说‘不要使用 Claude’，”他说。“实际上是‘使用 Claude，但要以一种你监视它、保护它、监控它的方式使用’，并对授权的技能以及谁可以访问特定资源进行控制。”

让智能体成为组织化的而非个人化的

xpander 还增加了一个它称之为“Multiplayer AI”的协作层。

其前提是企业智能体越来越需要比单个用户的聊天会话寿命更长。一个工作流可能涉及一个智能体收集数据，另一个系统采取行动，一名员工批准它，而另一个团队在几小时或几天后恢复该过程。

Twizer 认为，本地部署的助手有另一个缺点：员工通过其智能体积累的专业知识——提示词、技能、工作流和上下文——往往只留在这些个人手中。

“你在让 AI 智能体变得更好，但你并没有让公司变得更好，”他告诉 VentureBeat。“你现在投资于该生态系统的所有数据、所有提示词、所有工作流、所有技能都被锁定在那个供应商内部，很难与其他同事分享。”

更复杂的企业工作也很少能整齐地映射到单个聊天会话中。

“工作不是单人的。它是多人的，”Twizer 说。“它发生在多天甚至几周的时间里。对企业有意义的工作流不是聊天机器人。”

xpander 的共享对话旨在将这些交互保持在持久的、受权限限制的线程中。一个智能体可以发布一次供整个组织使用，而员工可以通过 Slack、Teams、ChatGPT、Claude 和 xpander 自己的界面与智能体进行交互。

该公司的文档表示，下游操作可以通过使用 OIDC 的端到端身份验证，识别为调用智能体的人类——对于需要在工作通过智能体移动时保留用户级身份和授权的组织来说，这是一个潜在的重要区别。

对持久执行的要求并非 xpander 独有。Temporal 已将长时间运行、抗故障的工作流作为其 AI 宣传的核心，而 LangSmith 支持持久的智能体部署和生产可观测性。

xpander 试图将这种运行时基础设施与企业协作和治理结合到一个单一的、可移植的、灵活的、供应商中立的控管平面中。

Omni 测试 harness 理论

该公司还正式全面推出了其预构建的智能体 Omni。

将 Omni 简单地称为通用智能体低估了 xpander 现在正在销售的东西。其文档将 Omni 描述为一名“AI 前线部署工程师”，它将请求的业务结果转化为该公司所称的“Agentic Application”（智能体化应用）：一个后端智能体与前端体验相结合，可以包括聊天、交互式 UI 组件、报告、仪表板和可视化。

用户可以描述期望的结果，之后 Omni 将帮助构建应用程序，连接其模型、技能、工具和数据，作为被追踪的任务执行工作，并在 Agent Workspace 中维护文件和可重用的上下文。生成的应用程序随后可以与队友分享。

例如，xpander 的文档显示用户要求 Omni 构建一个 Redshift Analyzer。Omni 旨在收集需求、设计界面、构建后端智能体、附加适当的连接器和工具，并生成第一个实时应用界面。

文档还列出了 Slack、WhatsApp、Telegram 和电子邮件作为 Omni 的渠道，而 xpander 更广泛的平台材料列出了 Teams、Claude、ChatGPT、API、webhook、CLI 和 MCP 作为工作可以到达智能体的方式。由于该公司的材料对 Omni 和更广泛的平台描述了略有不同的渠道集，企业应验证对其特定界面和部署配置的支持。

Omni 也可以在桌面 AI 产品旁边运行，而不是取代它们。Twizer 表示，员工可以继续使用他们首选的桌面智能体，而 Omni 作为一个技能，仅暴露企业批准的数据和连接器。当需要后台执行时，Omni 可以创建一个集中控制的智能体来执行工作。

xpander 表示 Omni 在 GAIA 基准测试中得分为 90.9%，包括在其最困难的任务上的强劲表现。该结果是公司自报的，应被视为 xpander 更广泛论点的证据，而不是对该平台的独立验证。

Twizer 表示，公司故意使用混合模型测试该 harness，而不是围绕单一专有系统进行优化。

“我们拿了 Opus，我们拿了 Sonnet，我们拿了 Kimi，我们拿了 GPT，在那个基准测试中我们得到了 90.9% 的分数，”他告诉 VentureBeat。

对 Twizer 来说，该结果支持了一个论点，即智能体性能越来越取决于围绕基础模型的基础设施。

“它只是证明了价值在于 harness 层，而不是模型层，”他说。“价值在于：你如何处理长时间运行的任务？你如何处理工具调用？你如何做沙箱？你如何保持专注？你如何让智能体专注于任务？”

基准测试结果已公开，允许其他人审查该公司的测试方法，但更广泛的结论仍然是 xpander 对自己结果的解释。

这一论点在业界越来越得到认同。分歧在于谁应该控制这一层。

OpenAI 和 Google 正将其转变为更广泛 AI 平台的一部分。LangChain 和 CrewAI 正在将其开发生态系统扩展到企业运行时。Temporal 则将执行问题作为基础设施来攻克。

xpander 押注企业会希望该控管平面保持独立于这三种选择之外：模型、云和智能体框架。

该公司现在必须证明，在已经变得拥挤的企业 AI 技术栈中，这种额外的抽象层具有足够的价值来证明另一个平台的合理性。

定价与可用性

xpander 的平台和 Omni 现已全面可用，针对使用 xpander 托管服务的团队和在自己的基础设施上运行该平台的企业有两种截然不同的商业模型。

自助服务的 Team 产品不收取席位费，并根据智能体活动以积分形式定价。xpander 将一个积分定义为一美分，即 100 美元可购买 10,000 个积分。唤醒智能体的每个事件或消息在整个回合中花费一个积分，无论该回合持续多长时间，并且每次工具或 API 调用需额外花费一个积分。模型令牌按所选模型的配置费率以积分单独计费。

这使得成本结构比 Twizer 描述的为智能体“输出”付费要精细得多。根据公布的定价，长时间运行本身似乎不会产生基于时长的费用，但工作流可以通过重复调用、工具调用和模型令牌消耗累积成本。

新账户将获得 1,000 个免费积分，而不是有时限的免费试用，客户可以使用信用卡注册。xpander 表示，Team 级别允许无限的智能体、工作流和席位。

模型使用可能占总成本的很大一部分，该公司发布的示例旨在使这笔费用可计算。其定价页面列出了各个模型的不同输入和输出令牌费率，并表示这些模型费用已并入积分系统，从而消除了托管客户的单独模型提供商账单。因此，实际支出在很大程度上取决于所选模型、令牌量和工具调用的数量。

自行托管的企业将获得不同的安排。xpander 的 Enterprise 计划是年度许可证，起价为 50 个智能体，支持在客户的 Kubernetes 基础设施或本地环境上部署。它包括 SSO 和 OIDC、具有共享积分和按团队使用量报告的子组织、私有模型网关连接、入职引导和一级支持。客户还可以自带模型 API 密钥，并使用自己协商的模型提供商费率。

xpander 没有公布该年度企业许可证的美元价格，因此潜在客户无法仅从公开信息计算私有或气隙隔离部署的总成本。定价材料也没有提供 50 个智能体起始承诺的公开美元数字。这些部署需要联系 xpander 获取定制价格。

“你只需为智能体正在做的工作付费，”Twizer 在谈到托管模式时告诉 VentureBeat。“没有订阅费，没有席位费，没有构建者席位，什么都没有。你只需为智能体的实际输出付费。”

对于企业买家来说，这种区别很重要：xpander 的无席位费声明最直接适用于其基于使用量的托管产品。需要拥有部署环境的组织则是在评估一份未公开的年度许可证、基础设施成本以及他们自己的模型提供商支出。

这让 xpander 在企业面临智能体蔓延之际，有了一个直截了当但日益受到挑战的宣传点：继续使用员工觉得有用的任何模型、框架和界面，但将控制这些智能体能做什么的基础设施移入一个组织可以治理的公共层。

企业最终是希望从一家独立的初创公司、一家智能体框架公司，还是从 xpander 试图抽象化的那些超大规模云服务商和模型提供商那里获得这一层，正成为企业 AI 技术栈中的另一个战场。

xpander 与其他智能体基础设施的对比

当直接比较这些产品时，重叠之处变得更加清晰。几家竞争对手现在都支持多个模型提供商、客户控制的基础设施或两者兼有。差异越来越涉及到每个平台试图拥有智能体技术栈的多少部分——以及它是否提供智能体开发框架、中立运行时、持久工作流基础设施或一组托管云服务。

这种对比使简单的供应商中立性宣传变得复杂。例如，AWS AgentCore 支持 Bedrock 外部的模型以及包括 LangGraph、CrewAI 和 Google 的 ADK 在内的框架，而 LangSmith 明确自称框架无关。CrewAI 提供客户控制的部署和广泛的模型选择。Temporal 允许公司完全自托管持久执行层，尽管它解决的是更窄的基础设施问题，而不是提供完整的智能体控管平面。

这使得 xpander 潜在的差异化更加具体。它试图将框架和模型可移植性与企业身份、治理、运行时基础设施以及面向员工的协作层结合起来，而不是仅仅在替换模型或在供应商 SaaS 环境之外部署的能力上进行竞争。xpander 还根据单个智能体唤醒和工具调用（而不是席位）为其托管平台定价，尽管需要自托管的企业面临着一份未公开的、起价为 50 个智能体的年度许可证。
