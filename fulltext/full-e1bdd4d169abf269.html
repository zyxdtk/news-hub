长期运行的Claude用于科学计算

📅 2026-03-23 📄 Anthropic 🔗 原文链接

原标题：Science Long-running Claude for scientific computing

中文摘要： 本文介绍了如何利用Claude等AI代理进行长期、自主的科学计算任务，如实现可微分宇宙学玻尔兹曼求解器。通过制定清晰计划、使用持久记忆（CHANGELOG.md）、测试预言机和Git协调，代理能在数天内完成原本需数月的工作。尽管存在测试覆盖不足和基础错误，但代理持续进步，展示了AI在科学计算中的巨大潜力，压缩了研究周期，改变了科研“空闲时间”的概念。

_在本文中，Siddharth Mishra-Sharma 解释了如何将多日代理编码工作流——测试预言机、持久内存和编排模式——应用于科学计算任务，即使这些任务超出了你的专业领域。_

### **前提** 目前大多数使用AI代理的科学家仍处于对话循环中，对每一步都进行严格控制。随着模型在过去一年左右在长周期任务上取得显著进步（https://metr.org/time-horizons/），一种新的工作方式应运而生：我们不再需要参与每个细节，而是可以指定高层次目标，让一组代理自主工作。这使得原本需要数天、数周甚至数月才能完成的项目，现在只需数小时即可完成。某些类型的科学任务非常适合这种模式，例如重新实现数值求解器、将用旧Fortran方言编写的遗留科学软件转换为现代语言，以及针对参考实现调试大型代码库。这些任务具有明确的工作范围、清晰的成功标准，且人类监督可以是间歇性的而非持续性的。

Anthropic 的 [C 编译器项目](https://www.anthropic.com/engineering/building-c-compiler) 展示了这种模式，其中 Claude 在大约 2,000 个会话中构建了一个能够编译 Linux 内核的 C 编译器。本文描述了如何使用 Claude Code 为科学计算任务设置类似的模式，以典型的学术实验室为背景。作为具体示例，我将演示如何使用 Claude Opus 4.6 实现 [可微分宇宙学玻尔兹曼求解器](https://github.com/smsharma/clax)。这是一种预测大爆炸余辉——宇宙微波背景（CMB）——统计特性的数值代码。它通过演化早期宇宙中光子、重子、中微子和暗物质的耦合方程来实现。

像 [CLASS](http://class-code.net/) 和 [CAMB](https://camb.info/) 这样的玻尔兹曼求解器是宇宙学中的核心科学基础设施，使我们能够利用来自 _Planck_ 和 _Simons Observatory_ 等调查的数据来约束宇宙学模型。可微分版本——能够在整个求解器中传播梯度——使得基于梯度的推断方法得以应用，从而显著加快参数估计速度。用 JAX 编写是自然选择，因为它提供了自动微分和与加速器（如 GPU）的兼容性，几乎无需额外成本。

值得注意的是，该任务并不在我的核心科学领域内——我对工具和科学有高层次的熟悉度，但没有在合理时间内独立完成它的专业知识。那些具备该专业知识的团队已经用 JAX 构建了 [可微分求解器](https://arxiv.org/abs/2311.03291)[](https://arxiv.org/abs/2602.15104)，并具备 CLASS 的部分功能。这些努力通常需要数月到数年的研究人员时间。本文的目的是看看在非领域专家的最小引导下，代理是否能走得更远。

这类任务在结构上与 C 编译器项目不同，后者可以分配给大量并行代理。而玻尔兹曼求解器则是一个深度耦合的流水线——早期宇宙再结合建模中的微小数值误差或不良近似会微妙地影响下游所有结果。因此，它需要不同的代理技能。调试需要追溯整个因果链并运用领域知识，这更适合由单个代理顺序工作，按需生成子代理，并使用参考实现进行二分法排查差异。

我们将使用运行 SLURM 作业调度器的 HPC 集群作为计算环境，但核心思想——进度文件、测试预言机、带有明确规则的代理提示——无论在哪里运行 Claude Code 都适用。

### **起草计划并本地迭代** 在转向管理自主研究代理团队的过程中，你应该花费大部分时间（与 Claude 协商）制定一套清晰说明项目交付成果和相关背景的指令。这些指令应保存在根目录下的 CLAUDE.md 文件中。Claude 会特别对待该文件，将其保留在上下文中，并用于整体计划。关键的是，Claude 在工作过程中可以编辑这些指令，随着问题的解决不断更新以供未来使用。

[这里](https://github.com/smsharma/clax/blob/6a6b2330cf25edded1bb31ec57a0091aa794a5d3/CLAUDE.md) 是宇宙学玻尔兹曼求解器项目的早期 CLAUDE.md，展示了在首次尝试编写求解器后确定的整体计划和设计决策。为了达到这一点，我指定了项目高层次目标——在与参考 CLASS 实现完全功能对等的同时实现完全可微分，并在主要科学交付成果上达到与 CLASS 0.1% 的精度目标——然后与 Claude 迭代，直到计划看起来令人满意。鉴于 0.1% 是 CLASS 和 CAMB 两个经典玻尔兹曼代码之间的典型一致性水平，这似乎是一个良好的科学目标。

### **跨会话记忆** 进度文件（我们约定称为 CHANGELOG.md）是代理的便携式长期记忆，充当一种实验笔记。在 CLAUDE.md 中，Claude 被指示在此文件中跟踪进度。

一个好的进度文件可能包括当前状态、已完成的任务、失败的方法及其原因、关键检查点的精度表以及已知的局限性。失败的方法很重要——没有它们，后续会话可能会重复尝试相同的死胡同。条目可能如下：“尝试使用 Tsit5 对扰动 ODE 进行求解，系统过于刚性。切换到 Kvaerno5。” [这里](https://github.com/smsharma/clax/blob/main/CHANGELOG.md) 是运行示例的变更日志，展示了这些元素。

### **测试预言机** 尽管通过代理进行更开放的科学发现无疑在未来的道路上，但目前长期自主科学工作关键依赖于代理能够判断自己是否取得进展。对于科学代码，这可以是参考实现、明确可量化的目标，或现有的测试套件。指导代理在工作过程中扩展测试套件并运行测试以防止回归也很有帮助。在我的示例任务中，Claude 被指示使用 [CLASS C 源代码](https://github.com/lesgourg/class_public) 作为参考实现，构建并持续运行单元测试。

### **Git 作为协调工具** Git 可以作为一种无干预方式监控和协调代理的进度。代理应在每次有意义的工作单元后提交并推送。这在出现问题时提供可恢复的历史记录，使进度本地可见，并防止在例如计算配额中途耗尽时工作丢失。

实际上，这可以是 CLAUDE.md 中的一组指令，例如：“每次有意义的工作单元后提交并推送。每次提交前运行 `pytest tests/ -x -q`。永远不要提交破坏现有通过测试的代码。”

对于引导代理，你可以随时 SSH 登录集群并手动重新提示和/或更新其指令。通常更符合人体工程学的做法是简单地让本地 Claude Code 实例 SSH 登录并为你运行命令；这同样适用于下文描述的所有内容。

### **执行循环** 如上所述，通常首先在本地迭代计划，直到你有一个看起来合理的计划并编码在 CLAUDE.md 中。然后，在计算节点的终端多路复用器（如 tmux）中启动 Claude Code 会话，告诉代理代码库的位置，然后让它运行。由于会话在 tmux 中运行，你可以分离、关闭笔记本电脑，并偶尔检查进度（对于玻尔兹曼求解器，我会在手机上检查 GitHub，例如在排队买咖啡时）。

在 HPC 集群上，你可能通过 SLURM 调度器请求一个节点，一个启动 Claude Code 的 tmux 会话的示例作业脚本可能如下： ``` #!/bin/bash #SBATCH --job-name=claude-agent #SBATCH --partition=GPU-shared #SBATCH --gres=gpu:h100-32:1 #SBATCH --time=48:00:00 #SBATCH --output=agent_%j.log cd $PROJECT/my-solver source .venv/bin/activate export TERM=xterm-256color tmux new-session -d -s claude "claude; exec bash" tmux wait-for claude ``` 一旦作业开始，你连接到 tmux 会话，给 Claude Code 指令（例如，“阅读 CHANGELOG.md 并继续下一个任务”），并在满意其方向后分离。你可以随时重新连接以检查、引导或使用类似以下命令启动新任务： `srun --jobid=JOBID --overlap --pty tmux attach -t claude`

**Ralph 循环：** 随着模型能力提升，它们对提示工程、RAG 或上下文填充等定制化编排的需求减少。然而，在特定时间点，提供一定程度的框架作为能力提升是有用的。例如，当前模型可能表现出“代理懒惰”——当被要求完成复杂、多部分任务时，它们有时会找借口在完成整个任务前停止（“太晚了，明天再继续吧？”）。

为避免这种情况，一个有用的编排模式是 [_Ralph 循环_](https://ghuntley.com/loop/)，本质上是一个 _for_ 循环，当代理声称完成时将其重新带入上下文，并询问它是否“真的”完成了。这对于长期任务很有用，因为代理会承认任务未达到标准，并继续工作直到达标。其他类似模式包括 [GSD](https://github.com/gsd-build/get-shit-done)（以及 [领域特定](https://arxiv.org/abs/2603.20179)[变体](https://github.com/psi-oss/get-physics-done)）以及 Claude Code 原生的 /loop 命令。

Ralph 可通过 /plugin 安装。在 Claude Code 中的典型调用提示可能如下： `/ralph-loop:ralph-loop “请持续工作，直到在整个参数范围内达到 0.1% 精度的成功标准。” --max-iterations 20 --completion-promise “DONE”` 这里，Claude 将最多迭代 20 次，直到保证任务完成并以“DONE”声明结束。

### **结果** Claude 在几天内从零开始工作于 [该项目](https://github.com/smsharma/clax)，在各种输出上达到了与参考 CLASS 实现的百分之一以下的精度。我要求 Claude 重建项目过程中代码主要输出（各种 CMB 角度功率谱）的精度，并在开发过程中标记里程碑。它生成了下图，展示了通往百分之一以下精度的路径。 ![Image 1](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fd6b037407956ad8d5317c97730fd9f273a6a6afa-1680x880.png&w=3840&q=75) 代理在代码库上工作时，随时间推移达到百分之一以下精度的路径。

代理的开发轨迹有些笨拙。例如，其测试覆盖率存在明显空白——有一段时间它只在单个（标准）参数点测试代码，极大地减少了发现错误的表面面积。它也可能犯基本错误，例如在规范约定上出错，或花费数小时追踪一个宇宙学家会立即发现的错误，但它持续朝着百分之一以下精度的目标前进。

该项目的一个副作用是，我通过观察 git 提交历史学到了大量关于玻尔兹曼求解器及其所建模物理的知识。该项目并非来自我的核心科学领域，但跟踪 Claude 的渐进式进展并查找我不认识的内容，结果成为一种有效的科学知识渗透方式。[提交日志](https://github.com/smsharma/clax/commits/main/) 读起来像一位快速、字面意义的博士后写的实验笔记。

尽管最终的求解器尚未达到生产级别（例如，在所有范围内并未与参考 CLASS 实现达到可接受的精度），但它证明了代理驱动的开发可以将数月甚至数年的研究人员工作压缩到几天内。

这种压缩改变了“空闲时间”的定义。在 AI 研究中，普遍体验是夜间启动实验（例如训练运行），然后在早晨看到结果时获得满足感。不运行实验意味着机会成本。如今，不运行代理也似乎有成本。如果你拥有计算资源和具有明确定义成功标准的项目，那么每个你“没有”让代理为你工作的夜晚，都是潜在进展的浪费。
