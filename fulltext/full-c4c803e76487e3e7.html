中文摘要： 本文提出了一种面向知识图谱多跳检索的查询感知扩散激活方法。该方法通过每步语义门（候选实体描述与问题的余弦相似度）实现查询感知遍历，固定迭代次数，整个检索过程以单条Cypher查询在Neo4j中执行，图数据不离开数据库。在MuSiQue上，该方法在精确匹配上与QAFD-RAG基本持平，并超过HippoRAG。消融实验表明语义门同时提升了F1分数（3.6-7.4分）并降低了检索延迟（1.5-4.9倍）。

面向知识图谱多跳检索的查询感知扩散激活方法

Mykola M. Glybovets, Illia S. Makarov

摘要

基于知识图谱的检索增强生成通过利用图结构，在多跳问答任务中优于扁平段落检索。然而，在大多数现有系统中，问题仅用于设定种子节点；后续遍历变为"查询盲"，仅依赖图结构。QAFD-RAG 是一个例外，它通过流扩散求解器结合边重加权实现了查询感知遍历。该架构需要将完整图加载到 Python 内存中，且迭代求解器的迭代次数可变，使得与图数据库的集成变得复杂。我们提出了一种扩散激活方法，通过每步语义门实现相同的查询感知遍历：步权重为候选实体描述与问题之间的余弦相似度，迭代次数固定。整个检索过程——种子映射、传播、Top-K 选择和上下文组装——被表达为单条 Cypher 查询，在一次往返中执行于 Neo4j；图数据始终不离开数据库。在 MuSiQue 上，我们的方法在精确匹配上与 QAFD-RAG 持平（32.80 vs 33.50），并比我们对比中最强的纯结构基线 HippoRAG 高出 5.3 EM 和 3.4 F1；在 2WikiMultiHopQA 上，HippoRAG 和 QAFD-RAG 由于其短语节点架构而保持优势。禁用门的消融实验证实，该门是 F1 同时提升 3.6 至 7.4 分以及检索延迟降低 1.5 至 4.9 倍的来源。

I 引言

检索增强生成（RAG）通过在推理时直接引入外部证据，补充大语言模型的参数化知识 [1, 2]。主流的检索原语是稠密段落检索 [3]：语料库被分割为段落，每个段落被嵌入到向量空间中，与目标问题最相似的 $k$ 个段落被添加到语言模型的上下文中。该方案对于答案包含在单个段落中的问题非常有效，但在需要综合多个文档证据的多跳问题上质量急剧下降，这些文档之间可能没有表面词汇重叠。这一限制本质上是结构性的：问题与包含答案的段落之间被一条推理链隔开，而向量相似性无法重建这条链。

越来越多的工作通过将语料库索引为知识图谱并在检索时利用其结构来克服这一限制 [4, 5, 6, 7, 8]。尽管遍历算法不同——社区检测（GraphRAG [4]）、个性化 PageRank（HippoRAG [6]）、基于流的路径剪枝（PathRAG [8]）——这些系统在一个方面是相似的：问题仅影响种子节点的选择。遍历本身仅依赖图结构，在这个意义上是"查询盲"的。

例外是最近发表的 QAFD-RAG [9]，据我们所知，这是第一个遍历本身变为查询感知的系统：每条边通过成对相似度与查询相似度的组合函数重新加权。然而，其流扩散求解器需要将整个图加载到 Python 数据结构中，且边级重加权在图数据库的查询语言中难以表达。

我们的方法保留了 QAFD-RAG 的核心思想——遍历必须考虑查询。同时，我们摒弃了在内存中持有图和组合边重加权。所提出的算法从问题中提取的种子实体开始在知识图谱上扩散激活。每个传播步骤通过一个语义门，其强度由候选实体描述与问题之间的余弦相似度设定。整个检索过程——种子节点映射、三次传播迭代、$K$ 条链和实体选择、上下文返回——被表达为单条 Cypher 查询，在一次往返中执行于 Neo4j，不将任何图数据移出数据库。

在两个多跳基准上的实验揭示了三个关键发现。

  1. 查询感知传播同时提升准确率并降低检索延迟。 在两个数据集——MuSiQue 和 2WikiMultiHopQA——上，用所提出的查询感知变体替换结构扩散激活提升了 F1（MuSiQue +7.4，2wiki +3.6），并将检索延迟降低了 1.5 至 4.9 倍。提升的原因是语义门在每次迭代中剪枝低信息分支，从而缩小了下一次迭代操作的工作集。

  2. 检索是单条 Cypher 查询，不将图加载到内存。 HippoRAG 和 QAFD-RAG 都将图物化为 Python 数据结构以执行遍历。相比之下，所提出的方法将整个遍历委托给 Neo4j 的查询规划器；这使得系统在生产环境中部署极为简单，在数据库内部沿激活前沿并行化传播，并确保并发安全。

  3. 更简单的门达到了与最佳查询感知系统相当的 EM。 在 MuSiQue 上，所提出的方法在 EM 上几乎与 QAFD-RAG 持平（32.80 vs 33.50），并比纯结构基线中最强的 HippoRAG 高出 3.4 F1 和 5.3 EM；在 2WikiMultiHopQA 上，基于 PageRank 的方法保持优势。

完整源代码、索引过程和逐问题评估日志可在 https://github.com/kinfi4/qasa-graph-rag 获取，以支持结果复现和进一步研究。

II 相关工作

文献按照问题影响检索的程度进行组织。仅使用问题选择种子节点的方法在第 II-A 节中综述，额外让问题塑造图遍历的方法在第 II-B 节中综述。表 I 在架构选择层面展示了这一比较，指出了所提出方法的位置。

II-A 纯结构遍历的 Graph RAG

GraphRAG [4] 使用语言模型提取实体和关系，对结果图应用 Leiden 社区检测算法，并构建文本摘要层次结构；在查询时，系统通过聚合社区摘要（"全局"模式）或选择最相关的实体（"局部"模式）来回答。该方法对聚焦查询的摘要非常有效，但并非为回答多跳事实性问题而设计。

LightRAG [5] 联合索引实体和关系，执行双层检索，将实体描述上的向量相似度与语言模型生成的关系主题上的关键词检索相结合。此处的遍历是隐式的：每个检索到的实体返回其一跳邻域。LightRAG 在多跳基准上的主要弱点是缺乏显式的多跳扩展：相关证据通常距离任何种子节点两到三跳。

HippoRAG [6] 将检索建模为个性化 PageRank [10]，从问题中提取的一小部分短语实体出发，通过其向量表示匹配到知识图谱节点。图由 OpenIE 三元组构建，因此其节点是短语实体而非段落。每个段落的分数在最后通过聚合其提及的实体的 PageRank 分数来计算。

HippoRAG 2 [7] 改进了架构：在短语节点上添加了段落节点，种子选择阶段使用查询到三元组的匹配，并在遍历前应用基于语言模型的"识别记忆"过滤器；PPR 仍然是遍历原语。

PathRAG [8] 通过与查询关键词的向量相似度选择节点，然后基于网络流原则计算每对检索节点之间的路径：每条路径按以固定衰减遍历后剩余的资源量评分。结果是一组关系路径，按可靠性升序呈现给语言模型。这种排序缓解了语言模型"迷失在中间"的位置偏差 [11]。与前面的系统一样，路径评分仅依赖结构。

II-B 查询感知图遍历

QAFD-RAG [9] 在概念上是最接近我们的先前工作。在那里，检索被表述为实体图上的流扩散问题，其中每条边 $(u,v)$ 通过组合函数 $H_{\mathrm{sim}}(u,v)\cdot\bigl(a+b\,(H_{\mathrm{sim}}(u,q)+H_{\mathrm{sim}}(v,q))\bigr)$ 重新加权，其中 $H_{\mathrm{sim}}$ 是相似度分数，$q$ 是查询，$a,b$ 是超参数（作者在实验中选择 $a=1$，$b=1/4$）。扩散通过原始-对偶迭代过程——在 $\varepsilon$ 收敛准则下的随机坐标下降——求解，作者为此证明了子图恢复保证。在实践中，迭代次数取决于具体查询、种子实体和图结构，且不预先固定；加上每条边的流状态，这使得算法难以在图数据库的查询语言中表达，因此已发表的实现将图加载到 Python 数据结构中。

所提出的方法建立在相同的中心思想之上——遍历必须考虑查询——但用仅依赖目标节点且可在图数据库查询语言中表达的单步门替换了组合边加权和流扩散求解器。

III 方法

系统分两个阶段运行：索引阶段从语料库构建类型化 Neo4j 知识图谱（第 III-A 节），查询阶段在单次数据库往返中为语言模型组装上下文（第 III-B 节）。整体架构如图 1 所示。

III-A 知识图谱构建

实体和关系提取。 共享同一标题的段落被合并为单个文档，在单次调用中以结构化输出模式传递给语言模型（Gemini 2.5 Flash）。模型返回命名实体列表，每个实体分配了 {PERSON, ORGANIZATION, LOCATION, EVENT, WORK} 中的类型和文本描述，以及二元关系列表——三元组 (source_name, relation, target_name)。提取遵循严格规则：不使用代词，仅使用完整专有名词，描述为必填项。结果以文档哈希为键缓存在磁盘上，使重复运行不消耗 token。

实体消解。 第二遍合并语料库中以不同表面形式出现的同一实体的提及（例如"Louis XIII"和"Louis XIII of France"）。在每个实体类型内，通过确定性标准构建合并候选集：如果一对名称中一个的词元是另一个的子集，则形成边；此关系的连通分量通过并查集结构分组。这种预过滤避免了二次方数量的语言模型调用，并将模型的任务缩小为验证已形成簇内的正确性。每个非空簇连同候选描述在单次调用中以结构化输出模式传递给语言模型。响应包含零个或多个不相交的组；每个组的规范名称限于输入名称集合，输入实体可以不属于任何组，因此在单个输入簇内模型可以区分多个不同的规范实体。每个组内的实体描述被聚合为单个描述。此后，三元组中的每个别名提及在写入 Neo4j 之前被重写为其对应的规范名称；如果重写将三元组的两个端点折叠为同一实体，则该三元组作为无信息自环被丢弃。

图 1：两阶段架构。 索引阶段（上）通过 LLM 从语料库提取实体和关系，进行消解和嵌入，并将结果作为类型化知识图谱存储在 Neo4j 中。查询阶段（下）使用 LLM 将问题映射到种子节点，在单条 Cypher 查询中运行 $T$ 次迭代的扩散激活，并将激活的子图传递给 LLM 生成答案。

写入 Neo4j。 消解后的实体和关系被写入图 2 所示的模式。每个 :Entity 节点携带名称、类型、文本描述、该描述的 768 维向量表示（使用 Google text-embedding-004 计算），以及确保幂等性的哈希。使用 Neo4j Graph Data Science 库在嵌入属性上构建向量索引。

图 2：知识图谱模式。 文档和段落节点保留语料库的原始结构；:MENTIONS 边在两个层级记录实体提及：文档级（聚合）和段落级（带精确位置）。实体及其类型化二元关系构成多跳推理的基础。自环表示 :RELATES_TO 边，它连接两个实体并将关系标签存储为属性。

III-B 查询感知检索

问题实体提取和种子节点映射。 对于每个问题，结构化语言模型调用提取其提及的命名实体。每个问题实体通过精确名称匹配映射到图节点，或否则使用其嵌入在实体描述索引中进行向量搜索。所有此类匹配构成种子节点集 $S$。每个节点 $u \in S$ 被分配匹配分数 $s_u$，精确名称匹配时等于 1，向量匹配时等于问题与实体描述之间的余弦相似度。每个 $v \in S$ 被赋予初始激活 $r^{(0)}(v)=s_{v}/\max_{u\in S}s_{u}$；对所有其他节点 $r^{(0)}=0$。此归一化确保最佳匹配的种子节点以激活值 1 开始，且下面引入的激活阈值 $\tau$ 在相同的绝对范围内运行，无论种子节点的数量和质量如何。

带查询感知加权的扩散激活。 遍历原语是扩散激活，这是信息检索中的经典机制 [12]。令 $\mathbf{e}{q}$ 表示问题的向量表示，$\mathbf{e}{v}$ 表示实体描述的向量表示。传播运行固定迭代次数 $T$（默认 $T=3$）。在迭代 $t=1,\dots,T$ 中，每个节点 $v$ 接收一个激活增量，将查询感知语义门 $\sigma(v)=\max(\cos(\mathbf{e}{v},\mathbf{e}{q}),0)$ 与活跃前沿上的求和结合：

$$\Delta r^{(t)}(v) = \alpha\,\sigma(v)\sum_{u\in A^{(t)}(v)}r^{(t-1)}(u), \tag{1}$$

$$A^{(t)}(v) = \bigl{u:(u,v)\in E,\;r^{(t-1)}(u)>\tau,\;r^{(t-1)}(u)>r^{(t-1)}(v)\bigr}.$$

这里，$\alpha\in(0,1]$ 是固定衰减因子，$\tau$ 是固定阈值；单调激活递减条件 $r^{(t-1)}(u)>r^{(t-1)}(v)$ 仅允许来自更高激活节点的贡献，防止循环增强。阈值 $\tau$ 和门 $\sigma$ 在约束前沿中起互补作用：$\sigma$ 按与查询的相关性剪枝邻居，$\tau$ 按增量的绝对大小剪枝。没有阈值，小增量会在 $T$ 次迭代中累积，传播将覆盖整个连通子图，Top-$K$ 选择将收集许多弱激活实体。因此，激活更新仅在 $\Delta r^{(t)}(v)>\tau$ 时应用：

$$r^{(t)}(v)=\begin{cases}r^{(t-1)}(v)+\Delta r^{(t)}(v),& \Delta r^{(t)}(v)>\tau,\ r^{(t-1)}(v),& \text{otherwise}.\end{cases} \tag{2}$$

与 QAFD-RAG 的组合加权 $H_{\mathrm{sim}}(u,v)\bigl(a+b\,(H_{\mathrm{sim}}(u,q)+H_{\mathrm{sim}}(v,q))\bigr)$ [9] 不同，所提出的因子仅依赖目标节点和查询，并在 Cypher 中表达为单个余弦，无每边状态；单调性条件替代了流守恒，因此传播运行固定次数的遍历而无需迭代求解器。该过程在算法 1 中形式化。

2: $q$ 的生成答案

6: 对所有 $v\notin S$：$r^{(0)}(v)\leftarrow 0$
7: $\mathbf{e}{q}\leftarrow\textsc{Embed}(q)$

9: for all $v\in V$ s.t. $A^{(t)}(v)\neq\emptyset$ do ▷ $A^{(t)}(v)$ 如式 (1)
10: $\sigma(v)\leftarrow\max\bigl(\cos(\mathbf{e}{v},\mathbf{e}{q}),\,0\bigr)$
11: $\Delta r^{(t)}(v)\leftarrow\alpha\cdot\sigma(v)\cdot\sum{u\in A^{(t)}(v)}r^{(t-1)}(u)$ ▷ 式 (1)
12: if $\Delta r^{(t)}(v)>\tau$ then
13: $r^{(t)}(v)\leftarrow r^{(t-1)}(v)+\Delta r^{(t)}(v)$
14: end if
15: end for

19: 其中 $v_{0}\in S$，$l\in[1,4]$，$r^{(T)}(v_{i})>0$；按平均激活排序

尽管每条 :RELATES_TO 边在图中存储为有向——从三元组的主语到宾语（图 2）——扩散激活将其视为无向：如果三元组（Shevchenko, wrote, Kobzar）存在于图中，来自"Kobzar"的激活必须到达 Shevchenko，就像在反方向一样。方向仅在链被序列化给语言模型时保留，因为方向对三元组的语义解释至关重要。

链和实体选择。 传播后，选择 $r^{(T)}$ 最高的 $K_e$ 个实体及其存储的描述，以及任意种子节点 $s\in S$ 与任意活跃节点之间的 $K_c$ 条链——长度最多四条边，仅经过扩散算法触及的节点，按链上平均激活排序。四条边的长度限制覆盖了目标基准中的典型推理深度（MuSiQue 为 2-4 跳），同时限制了选择随着路径长度指数增长的组合成本；已访问节点过滤器丢弃经过扩散算法未触及的结构相邻节点的链；按平均而非最小或总激活排序有利于路径上所有节点都被良好激活的链，而不仅仅是端点。链被去重：反向序列 $(v_{0},\dots,v_{l})$ 和 $(v_{l},\dots,v_{0})$ 被视为单条链，且作为更长链前缀的链被吸收。链被线性化为保留关系方向的节点-关系-节点三元组序列，实体格式为"名称 (TYPE): 描述"。

上下文组装和生成。 语言模型的上下文由连接线性化链和实体描述形成。语言模型在结构化输出模式驱动下返回两个字段，answer 和 reasoning；评估仅依赖 answer 字段。

参数值。 除非另有说明，所有实验使用以下固定值：激活阈值 $\tau=0.01$，选择限制 $K_e=K_c=30$，每个问题总回退向量搜索预算为 5 个候选，按 $k_{\text{per_entity}}=\max(1,\lfloor 5/|S|\rfloor)$ 分配给从问题中提取的实体。传播深度 $T$ 和衰减因子 $\alpha$ 在消融研究中变化（第 V-C 节）；默认配置为 $T=3$，$\alpha=0.7$。

III-C Cypher 实现

整个检索过程——从种子节点映射到返回 Top-$K$ 上下文——被表达为单条 Cypher 查询，客户端在一次往返中发送给 Neo4j。传播状态存在于局部 resource_map 变量（一个 Cypher MAP）中，通过 WITH 子句在阶段间传递；客户端和数据库之间不交换中间数据。查询由三个顺序阶段组装——种子节点初始化、传播迭代（重复 $T$ 次）和链与实体选择；完整文本在附录中给出，下面我们逐步介绍每个阶段的关键 Cypher 构造。

种子节点初始化。 对于从问题中提取的每个实体（UNWIND $entity_data AS ent），首先执行 OPTIONAL MATCH (exact:Entity {name: ent.name})。后续子查询 CALL (ent, exact) { ... UNION ALL ... } 包含两个由 CASE WHEN exact IS NOT NULL 和 CASE WHEN exact IS NULL 守卫的分支：第一个返回分数为 1 的精确匹配，而第二个——仅在无精确匹配时——在实体描述索引上调用 db.index.vector.queryNodes 并返回 $k$ 个最近候选及其余弦分数。由于这些守卫，对于给定的问题实体，两个分支中恰好一个执行，这在 Cypher 层面实现了第 III-B 节的"精确名称匹配，否则向量搜索"语义，无需额外的客户端逻辑。指向同一节点的不同问题实体的匹配通过 max(seed_score) 去重；然后所有分数通过除以最大值归一化，之后 apoc.map.fromPairs 从归一化激活构建初始 resource_map。

传播迭代。 单个传播步骤（代码清单 1）是一个子查询 CALL (resource_map) { ... }，它读取当前状态并返回 deltas——目标节点及其激活增量列表。UNWIND keys(resource_map) 遍历活跃前沿；过滤器 WHERE src_res > $threshold 将其限制为激活高于 $\tau$ 的节点。条件 (resource_map[dst.name] IS NULL OR resource_map[dst.name] < src_res) 实现了式 (1) 中 $A^{(t)}(v)$ 定义的单调递减条件 $r^{(t-1)}(u)>r^{(t-1)}(v)$。语义门 $\sigma(v)=\max\bigl(\cos(\mathbf{e}{v},\mathbf{e}{q}),\,0\bigr)$ 计算为 gds.similarity.cosine(dst.description_embedding, $qe) 后跟 CASE WHEN sim > 0 THEN sim ELSE 0 END。来自不同活跃邻居对单个目标节点的增量通过 sum 聚合，匹配式 (1) 中对集合 $A^{(t)}(v)$ 的求和；条件 WHERE incoming > $threshold 实现了式 (2) 的更新阈值。在子查询外部，apoc.map.merge(resource_map, apoc.map.fromPairs(...)) 将 deltas 添加到当前 resource_map 值，形成下一次迭代的状态。

代码清单 1：Cypher 中的查询感知传播单步。 该块在查询文本中重复 $T$ 次，由客户端组装；每次重复通过 WITH 子句从前一次的输出获取 resource_map。

CALL (resource_map) {
  UNWIND keys(resource_map) AS src_name
  WITH src_name, resource_map[src_name] AS src_res, resource_map
  WHERE src_res > $threshold
  MATCH (src:Entity {name: src_name})-[:RELATES_TO]-(dst:Entity)
  WHERE dst.description_embedding IS NOT NULL
    AND (resource_map[dst.name] IS NULL OR resource_map[dst.name] < src_res)
  WITH dst, src_res,
       gds.similarity.cosine(dst.description_embedding, $qe) AS sim
  WITH dst.name AS dst_name,
       sum(src_res * $decay *
           CASE WHEN sim > 0 THEN sim ELSE 0 END) AS incoming
  WHERE incoming > $threshold
  RETURN collect({name: dst_name, incoming: incoming}) AS deltas
}
WITH seed_names,
     apoc.map.merge(
       resource_map,
       apoc.map.fromPairs(
         [d IN deltas | [d.name,
          coalesce(resource_map[d.name], 0) + d.incoming]]
       )
     ) AS resource_map

链和实体选择。 $T$ 次迭代后，两个子查询读取最终的 resource_map。第一个是变长路径模式 MATCH path = (seed:Entity)-[:RELATES_TO*1..4]-(target:Entity)，指示 Neo4j 规划器枚举种子节点与任意活跃节点之间长度为一到四条边的所有路径。第 III-B 节中"仅经过传播触及的节点"的限制通过量词 ALL(n IN nodes(path) WHERE resource_map[n.name] IS NOT NULL) 表达，而附加条件 ALL(i IN range(0, size(nodes(path))-2) WHERE NOT nodes(path)[i] IN nodes(path)[(i+1)..]) 丢弃有重复节点的路径。按链上平均激活排序实现为 reduce(w = 0.0, n IN nodes(path) | w + coalesce(resource_map[n.name], 0)) / size(nodes(path))，之后 ORDER BY ... DESC LIMIT $top_k_paths 保留 Top-$K_c$ 路径。第二个子查询按激活对 resource_map 的键排序，返回 Top-$K_e$ 实体及其类型和描述。第 III-B 节描述的反向和吸收链的去重在客户端对返回结果执行。

此实现的一个架构后果是完整图从不离开 Neo4j，整个遍历由查询规划器执行——不同于 HippoRAG [6] 和 QAFD-RAG [9]，它们将图物化为 Python 数据结构。

IV 实验

IV-A 数据集和评估协议

评估在两个公开的多跳问答基准上进行。

MuSiQue [13] 通过组合两到四个单跳问题构建，明确构造使得单跳启发式无法产生正确答案；它是同类中最难的基准之一。

2WikiMultiHopQA [14] 利用 Wikipedia 的结构化证据（表格、信息框），覆盖两种问题类型——"桥接"和"比较"。

在两个基准中，每个问题都附带自己的段落集，包括支持段落和干扰段落。从 1,000 个采样问题中提取的段落被合并为每个基准的单一语料库，从中构建知识图谱；此协议遵循 HippoRAG [6]。表 II 报告了每个基准在索引阶段获得的文档、段落、实体、提及和关系的数量。MuSiQue 语料库在每项指标上大约比 2Wiki 大 1.7-2.2 倍，且每个实体的提及数显著更多（1.74 vs 1.43）；然而，图级密度（每个实体的关系数）在两个语料库中几乎相同。这在解释第 V-D 节的检索延迟和输入 token 成本时很重要。

IV-B 评估指标

我们使用两个指标评估：token 级 F1 和精确匹配（EM）。在计算 EM 和 F1 之前，预测和参考答案被转为小写，并移除冠词、标点和冗余空格。

IV-C 基础设施

图存储为 Neo4j 5.26 社区版（LTS），配备 Graph Data Science 和 APOC 插件，运行在本地 Docker 容器（Docker Desktop）中，具有 4 GB 堆和 2 GB 页缓存。所有延迟测量在单台机器上进行——配备 Apple M1 Pro 芯片（10 核：8 性能核和 2 能效核）、16 GB RAM 和内置 NVMe SSD 的 MacBook Pro。实体提取、问题实体提取和答案生成均使用 Google Gemini 2.5 Flash，温度为 0；向量表示使用 768 维 Google text-embedding-004 模型计算。

V-B 同时提升准确率和速度

在式 (1) 中添加查询感知语义门 $\sigma(v)$ 相对于均匀传播，在两个数据集上同时提升了答案质量并降低了检索延迟。在控制配置 no-query-aware 中，门 $\sigma$ 被替换为常数 1，而算法的其余部分不变，从而隔离其贡献。在 $n=1{,}000$ 的标准样本上（表 IV），查询感知传播在 MuSiQue 上提升 F1 7.4 分（41.68 vs 34.27），在 2Wiki 上提升 3.6 分（55.00 vs 51.44）；增益与执行完整消融的 $n=500$ 控制子样本一致（第 V-C 节）。同时，检索延迟下降 1.5-4.9 倍（详细测量在第 V-D 节报告）。因此，门同时改善了两个指标——它比均匀传播既更准确又更快。

这种同时提升质量和速度的机制是透明的。没有语义门，活跃节点的每个邻居在每次迭代中都会收到正流入，激活前沿大致几何增长，直到覆盖图的相当一部分。有了语义门，描述与查询无关的邻居收到乘以接近零或恰好为零的门 $\sigma(v)$ 的流入，低于阈值 $\tau$，并从下一次迭代的前沿中被剪枝。结果是一个更小的工作集，且——因为低信息实体根本不会进入 Top-$K$ 排名——为语言模型提供了噪声更小的上下文。

V-C 组件消融

为衡量关键组件的贡献，在每个数据集上评估了十一种配置：

  • naive-vector——在实体描述上的扁平向量搜索；作为无图基线配置。
  • no-query-aware——在式 (1) 中，语义门 $\sigma(v)$ 被替换为常数 1（均匀传播）。
  • 深度扫描——$T\in{1,2,3,4}$，$\alpha=0.7$ 固定。
  • 衰减扫描——$\alpha\in{0.3,0.5,0.7,0.9,1.0}$，$T=3$ 固定。
  • 默认配置（$T=3$，$\alpha=0.7$）属于两个扫描。

V-E 按基准分析

两个基准上的结果差异显著。在 MuSiQue 上，每个问题由异构 Wikipedia 材料上的两到四个单跳问题组成，所提出的方法在 EM 上与 QAFD-RAG 基本持平并超过 HippoRAG；在此基准上，每步语义门证明足以定位和遍历相关推理链，而无需 QAFD-RAG 的额外组合加权机制。在 2WikiMultiHopQA 上，相比之下，HippoRAG 和 QAFD-RAG 保持约 15 F1 的优势。我们将这一差距归因于基准的两个结构特性，基于 OpenIE 的短语节点架构（HippoRAG、QAFD-RAG）更适合这些特性。

第一，实体表示的粒度。 我们的离线阶段在五类固定类型模式 {PERSON, ORGANIZATION, LOCATION, EVENT, WORK} 下提取实体（第 III-A 节），而 2Wiki 中相当一部分黄金答案是不属于这些类别的属性：日期、国籍、语言、职业和是/否答案。这些事实在我们的图中不作为单独节点存在——它们仅在其承载实体的文本描述中以聚合方式被提及，因此扩散激活无法单独到达它们，它们不会直接进入 Top-$K$。HippoRAG 从 OpenIE 三元组构建图，没有固定类型模式，因此诸如"1845"、"British"或"French painter"等短语节点可以直接访问。这一差距被 2Wiki 基于 Wikipedia 结构化片段（表格、信息框）构建的事实放大，OpenIE 将这些片段特别干净地分解为原子三元组。

第二，"比较"类问题的性质，这类问题在 2Wiki 中占相当比例。诸如"谁出生更早——A 还是 B？"或"A 和 B 都位于国家 C 吗？"之类的问题不能简化为遍历单条推理链：必须并行找到关于已给定实体的两个特定事实，并在语言模型层面进行比较。图遍历在此处增加的价值不大，因为关键操作不是找到实体之间的连接，而是选择正确的属性。所提出的方法恰好针对 MuSiQue 中占主导地位的链推理问题进行了优化。所提出的方法未适应这两种情况。消除这些限制的方向——用异构节点（段落、短语节点）扩展图模式，如 HippoRAG 2 [7] 所做——在第 VII 节中讨论。

VI 限制

我们注意到以下限制。

  1. 比较条件不匹配。 表 III 中竞争方法的数字是 QAFD-RAG 作者在单一实验协议下对基线的自身复现 [9]。[9] 中获得这些数字的评估样本的组成未提供，因此其与我们 $n=1{,}000$ 样本的重叠无法确定。在 [9] 中，主要语言模型报告为 GPT-4o-mini，而所提出的系统使用 Gemini 2.5 Flash。两个模型属于同一价格层级和同一功能类别的轻量级（Flash/mini）模型，来自领先提供商，因此任一生成器的实质性优势不太可能。分配给本工作的 API 预算仅允许使用 Gemini，因此使用相同模型对四个竞争系统进行完整复现以进行完全受控比较超出了该预算；表 III 中的比较是在实验协议接近的假设下进行的。

  2. 2WikiMultiHopQA 上的差距。 所提出的方法在 2Wiki 上落后 HippoRAG 和 QAFD-RAG 约 15 F1。第 V-E 节给出了此差距的结构性解释；第 VII 节讨论了可能缩小差距的架构扩展。

  3. 控制实验的样本量。 控制运行在 $n=500$ 个问题上执行以限制总推理成本；解释这些实验时应考虑相应的 95% 置信区间（第 IV-A 节）。表 III 中的关键比较在 $n=1{,}000$ 的标准样本上执行。

  4. 对语言模型的未测量敏感性。 所提出系统中的所有语言模型调用——索引期间的实体提取、问题实体提取和答案生成——使用相同的 Gemini 2.5 Flash 模型。系统对不同提取器或生成器的敏感性尚未评估。特别是，门 $\sigma(v)$ 的判别能力取决于语言模型合成的实体描述在多大程度上聚焦于实体的识别特征而非上下文特征；这种与提取器属性的交互仍然未被测量。

VII 结论

我们提出了一种查询感知扩散激活方法用于 Graph RAG，实现为发送给 Neo4j 的单条 Cypher 查询。该算法从问题中提取的种子实体在知识图谱上传播激活，运行固定迭代次数：在每一步中，邻居贡献乘以仅依赖当前节点和查询的每步余弦门，单调性条件将传播限制为更高激活的节点。不同于 HippoRAG [6] 和 QAFD-RAG [9] 将完整图加载到 Python 数据结构中（且 QAFD-RAG 额外地迭代求解流扩散问题至收敛准则，使得求解器步数因查询而异且无法表达为固定 Cypher 查询），整个检索过程——从种子节点映射到 Top-$K$ 链和实体的选择——被表达为单条 Cypher 查询并直接由 Neo4j 查询规划器执行。因此，知识图谱的大小不受 RAM 量的限制，部署系统简化为运行 Neo4j，索引、数据完整性、备份和复制由数据库的内置机制提供。

在 MuSiQue [13] 上，该方法在精确匹配上与 QAFD-RAG [9] 基本持平，并超过 HippoRAG [6] 3.4 F1 和 5.3 EM。在 2WikiMultiHopQA [14] 上，纯结构的 HippoRAG 和流扩散的 QAFD-RAG 保持约 15 F1 的优势。与同一方案的均匀变体的受控比较（no-query-aware，表 IV 和 VI）表明，在两个基准上添加查询感知门同时提升了准确率并将检索延迟降低了 1.5-4.9 倍——门在每次迭代中剪枝低信息分支。

我们强调两个有前景的方向。第一，将扩散激活扩展到异构节点——特别是模式中已存在的段落节点，如 HippoRAG 2 [7] 所做——可以在保持 Cypher 可表达性的同时缩小 2Wiki 上的部分差距。第二，所提出的门可以嵌入迭代检索方案中，其中一次遍历的结果作为下一次遍历的种子节点，这将有助于定位中间"桥接"实体而无需在每次迭代时重新加载完整图。

附录：Cypher 查询完整文本

完整查询实现了第 III-C 节的过程，由客户端通过连接三个片段组装：种子节点初始化、传播块（重复 $T$ 次）和链与实体选择。查询参数为：$entity_data——从问题中提取的实体列表，包含字段 name 和 emb（描述的嵌入）；$qe——问题的嵌入；$decay——衰减因子 $\alpha$；$threshold——阈值 $\tau$；$top_k_entities、$top_k_paths——限制 $K_e$、$K_c$；$k_per_entity——每个问题实体的回退向量搜索候选数。

// === Fragment 1: seed-node initialization ===
UNWIND $entity_data AS ent
OPTIONAL MATCH (exact:Entity {name: ent.name})

CALL (ent, exact) {
  UNWIND CASE WHEN exact IS NOT NULL THEN [exact] ELSE [] END AS e
  RETURN e.name AS seed_name, 1.0 AS seed_score
  UNION ALL
  UNWIND CASE WHEN exact IS NULL THEN [ent] ELSE [] END AS e
  CALL db.index.vector.queryNodes(
    'entity_description_embeddings',
    $k_per_entity,
    e.emb
  )
  YIELD node, score
  RETURN node.name AS seed_name, score AS seed_score
}

WITH seed_name, max(seed_score) AS seed_score
WITH collect({name: seed_name, score: seed_score}) AS raw,
     max(seed_score) AS mx
WITH [s IN raw | s.name] AS seed_names,
     apoc.map.fromPairs([s IN raw | [s.name, s.score / mx]]) AS resource_map

// === Fragment 2: propagation block (repeated T times) ===
CALL (resource_map) {
  UNWIND keys(resource_map) AS src_name
  WITH src_name, resource_map[src_name] AS src_res, resource_map
  WHERE src_res > $threshold
  MATCH (src:Entity {name: src_name})-[:RELATES_TO]-(dst:Entity)
  WHERE dst.description_embedding IS NOT NULL
    AND (resource_map[dst.name] IS NULL OR resource_map[dst.name] < src_res)
  WITH dst, src_res,
       gds.similarity.cosine(dst.description_embedding, $qe) AS sim
  WITH dst.name AS dst_name,
       sum(src_res * $decay *
           CASE WHEN sim > 0 THEN sim ELSE 0 END) AS incoming
  WHERE incoming > $threshold
  RETURN collect({name: dst_name, incoming: incoming}) AS deltas
}
WITH seed_names,
     apoc.map.merge(
       resource_map,
       apoc.map.fromPairs(
         [d IN deltas | [d.name,
          coalesce(resource_map[d.name], 0) + d.incoming]]
       )
     ) AS resource_map

// === Fragment 3: chain-and-entity selection ===
CALL (seed_names, resource_map) {
  MATCH path = (seed:Entity)-[:RELATES_TO*1..4]-(target:Entity)
  WHERE seed.name IN seed_names
    AND resource_map[target.name] IS NOT NULL
    AND seed <> target
    AND ALL(n IN nodes(path) WHERE resource_map[n.name] IS NOT NULL)
    AND ALL(i IN range(0, size(nodes(path))-2)
            WHERE NOT nodes(path)[i] IN nodes(path)[(i+1)..])
  WITH reduce(w = 0.0, n IN nodes(path) |
              w + coalesce(resource_map[n.name], 0))
       / size(nodes(path)) AS path_weight,
       [n IN nodes(path) | n.name] AS names,
       [i IN range(0, size(relationships(path))-1) |
        {relation: relationships(path)[i].relation,
         forward: startNode(relationships(path)[i]) = nodes(path)[i]}] AS edges
  ORDER BY path_weight DESC
  LIMIT $top_k_paths
  RETURN collect({names: names, edges: edges,
                  path_weight: path_weight}) AS paths
}

CALL (resource_map) {
  UNWIND keys(resource_map) AS name
  WITH name, resource_map[name] AS resource
  ORDER BY resource DESC LIMIT $top_k_entities
  MATCH (e:Entity {name: name})
  RETURN collect({
    name: e.name,
    resource: resource,
    type: e.type,
    description: e.description
  }) AS entities
}

RETURN seed_names, paths, entities
