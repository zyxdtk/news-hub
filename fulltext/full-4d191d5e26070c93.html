Abstract
LLM-based vulnerability detectors have shown promising results in identifying memory-safety bugs and well-established vulnerability classes, where violations can often be expressed in terms of established security properties such as unsafe data propagation, bounds violations, or invalid memory accesses. Logic vulnerabilities, however, pose a fundamentally different challenge, as their identification requires inferring application-specific security invariants and often relies on implicit assumptions about intended behavior. Even frontier agentic models struggle in this setting, despite their ability to inspect and traverse large repositories, because the security invariants relevant to these vulnerabilities are often implicit and buried among large amounts of unrelated code. Motivated by this gap, we present
Antaeus
, a framework for detecting logic vulnerabilities that grounds LLM reasoning in repository-level code context.
Antaeus
follows a repository-scale pipeline that combines function prioritization, context-grounded reasoning, comparative validation, and structured reporting. First, it ranks functions using lightweight repository-wide security signals, directing costly LLM analysis toward the most relevant code regions and reducing model calls, cost, and triage effort. For each prioritized function,

This grounded input enables the model to reason about how the function is executed within the broader application rather than as an isolated snippet.

2.1.1
Non-Local Security Invariants
Many logic vulnerabilities are not confined to the function under analysis. The defining evidence lives in the repository around it. The safety of a function depends not on its local syntax, but on invariants the codebase as a whole is meant to enforce. As
1
illustrates,
virDomainAgentSetResponseTimeout
reads as a standard libvirt API wrapper, and no line within it signals that a read-only check is missing. The violated invariant, that write-privileged public APIs must reject read-only callers, is encoded in libvirt’s connection model and in how sibling APIs guard the same boundary, not in any artifact reachable by reading the function alone. Connecting the operation to the policy it viola

tes requires reconstructing repository-level conventions, evidence that local context cannot supply.
2.1.2
Absence of Syntactic and Dataflow Anchors
Tracking the conditions under which an operation is unsafe requires first knowing which operations are security-sensitive and where to look. For memory-safety and dataflow bugs, a detector has a stable scaffolding. There is a dangerous operation to flag, a tainted source to trace from, a sink to trace to, and a flow that links them. For logic bugs, none of these anchors exists. In
1
, there is no tainted input to track and no dataflow trail that walks toward the defect. The security-relevant operation is a configuration mutation that changes an agent timeout, which becomes sensitive only once the repository’s classification of it as a write operation is recovered. The evidence required to judge the function is thus a semantic classification the codebase assigns rather than a syntactic property a detector can pattern-match.
2.1.3
Distinguishing Violations from Project Norms
Detecting a logic vulnerability requires determining not only that a safety condition is unmet, but whether the unmet condition is a genuine anomaly rather than a repository-wide convention. An LLM model evaluating a function locally is usually assertive
[
8
,
29
]
. Shown a sensitive-looking operation, it tends to raise the safety conditions appropriate to that kind of operation, regardless of whether the surrounding codebase already addresses them. Across a r

epository, this yields a characteristic false-positive pattern, in which the same unsatisfied condition is reported for many structurally similar sinks, often in similar phrasing. A genuine logic vulnerability, by contrast, is an anomaly
[
10
,
33
]
, a deviation from how comparable code in the same project handles the same operation. When many similar operations are handled uniformly, that uniformity is the norm rather than a defect, and a model that raises the same concern across all of them is flagging the norm rather than a distinctive violation. As
1
shows, the missing read-only check is meaningful only relative to the sibling APIs that do enforce the boundary. A suspected violation, therefore, remains only a hypothesis until it can be set against the project’s enforced pattern.
2.2
Insights for Context-Grounded Logic Vulnerability Detection
The challenges above motivate context grounding, which constrains model reasoning to explicit evidence about how a repository defines its security invariants rather than letting the model fall back on local syntax and generic priors. Grounding combines two complementary layers. Local program evidence ties claims about a function to concrete repository artifacts, and repository-level context supplies the application-specific invariants against which a local operation must be judged. This perspective leads to three design insights.
Insight
1
:
Prioritize candidates before grounding. Because logic vulnerabilities admit no syntactic anch

or, every function is a nominal candidate, but grounding each one is impractical. Detection should begin with repository-wide prioritization that surfaces functions likely to involve security-relevant behavior, spending the analysis budget only where a policy violation could plausibly occur.
Insight
2
:
Pair local evidence with repository context. The information needed to judge a function lies outside it, so the model should reason over both layers simultaneously. Local code, callees, macros, constants, and types anchor claims to concrete artifacts, while a repository-level security summary of the application’s purpose, protected objects, and trust topology supplies the invariants the operation must satisfy.
Insight
3
:
A missing safety condition is meaningful only relative to how comparable code in the same repository handles the same operation. Each flagged condition should be validated against analogous sinks, discarding those that recur uniformly as project norms and retaining those that set the target apart.
These insights shape the design of
Antaeus
, a staged framework that grounds LLM-based logic vulnerability detection in repository evidence. A repository-wide prioritizer narrows the candidate set to security-relevant functions; a grounding stage pairs local code augmentation with a stable repository-level security summary; a structured reasoning stage produces findings in terms of security-sensitive sinks and their required safety conditions; and a comparative vali

dator confirms genuine violations by setting each finding against analogous code. The following section details each stage.
2.3
Threat model
We consider an adversary who interacts with the target software through its intended interfaces, such as API calls, configuration options, files, command-line arguments, or network requests. The adversary cannot modify the program code, but can choose inputs, parameters, call sequences, and execution contexts to violate security-relevant assumptions made by the application. We focus on logic vulnerabilities in which the executed code is syntactically valid, but an operation is performed under semantically unsafe conditions.
Antaeus
assumes access to the source repository under analysis, but does not assume exploit inputs, runtime traces, or an execution environment. Its goal is to statically detect and explain candidate logic vulnerabilities by linking security-sensitive code to the repository context that determines whether its use is safe. Memory-safety bugs and purely syntactic defects are out of scope.

Design
The design follows directly from the insights identified in
subsection 2.2
.
Antaeus
is a five-stage repository-level pipeline, shown in
Figure 1
: function prioritization, context-grounding, structured reasoning, comparative validation, and reporting. These stages also reflect recent state

-of-the-art practice in LLM-based vulnerability detection
[
4
,
35
]
. First, function prioritization ranks functions using lightweight repository-wide security signals, focusing LLM analysis on the most relevant code regions. Second, context-grounding supplies the model with local code augmentation and a repository-level security summary, tying its reasoning to concrete repository evidence. Third, structured reasoning prompts the model to identify security-sensitive sinks together with the safety conditions required for their safe use, and to record whether each condition is locally satisfied. Fourth, comparative validation checks whether a flagged condition is distinctive with respect to similar sinks in the same repository, pruning conditions that recur as project norms. Finally, reporting presents the retained findings as actionable, evidence-grounded explanations. The remainder of this section examines each stage in detail.
3.1
Prioritization
At repository scale, the first challenge is deciding where to apply expensive LLM analysis. As discussed in
subsection 2.2
, exhaustive repository exploration spends most of the budget on irrelevant code, while letting an agentic model search unaided does not guarantee that every security-relevant function is examined and may lead it to rely on superficial cues rather than repository evidence.
Antaeus
therefore begins with a lightweight, high-recall prioritization stage. The goal of this stage is not to classify functions as vulnera

ble, but to reduce the repository to a ranked set of functions that are most likely to contain logic-relevant behavior. This lets the later LLM stages operate at the repository level while keeping the number of detailed analyses tractable. The prioritization stage first prunes the codebase, retaining only C/C++ source and header files. It then applies broad keyword-based heuristics to remove functions that are unlikely to involve authorization, access control, trust-boundary enforcement, configuration changes, or other security-sensitive operations. These heuristics are intentionally loose: they are designed to remove clearly irrelevant functions while preserving recall for functions that expose even weak security signals. After this initial pruning,
Antaeus
compresses the remaining repository into a lightweight function-level representation. For each retained function, it removes the internal implementation logic and keeps only the function signature together with the callees invoked inside the function body, as illustrated in
2
. This abstraction is deliberately simple. It discards local implementation detail, but preserves the repository-wide call and naming signals that are useful for identifying security-relevant code regions. In particular, it allows the model to see many more functions and callees than would fit if full function bodies were provided. The compressed repository is then split into chunks that fit within the model’s context budget, with each chunk represen

ted as a single line aggregating the functions it contains. These chunks are passed to an agentic LLM, which ranks the functions by their relevance to the target logic vulnerability classes.
This design serves two purposes. First, it gives the prioritization model a global view of the repository’s security signals. Rather than inspecting a small subset of files or relying on its training-time knowledge of popular projects, the model receives a compact representation of the functions that remain after high-recall pruning. This makes it more likely to identify functions whose names, callees, or surrounding API structure indicate relevance to CWE-284 or CWE-200. Second, it limits the cost of the subsequent analysis. The detailed context-grounded reasoning stage is applied only to prioritized functions, reducing model calls, token usage, and the number of candidate reports that must be reviewed by a human auditor.

3.2
Contextual Grounding
The contextual grounding stage constructs the evidence needed to interpret a function in its repository context. The unit of analysis is a single function, but a function does not stand alone. Its meaning depends on the types of values it receives

，它所调用函数的函数体、它所使用宏的展开、它所引用的常量，以及决定作用域内名称的头文件和导入。让大语言模型（LLM）在孤立状态下对函数进行推理，会迫使它根据通用知识或训练期间见过的模式来填补这些空白。在真实的 C/C++ 项目中，这种做法是不可靠的。项目特定的宏可能并不会展开为模型所假设的那样，封装 API 的行为可能与其最相似的公共库接口不同，而常量的定义值可能会改变某项检查的含义。

出于这个原因，我们使用从代码库中提取的局部增强包（local augmentation bundle）来充实每个函数。我们通过基于 Tree-sitter 的轻量级静态分析过程来构建此增强包。解析器会识别函数定义、调用点、宏和常量引用以及包含关系，借此我们构建了一个代码库级别的图谱，将每个被分析的函数与解释该函数所需的程序构件连接起来。该图谱并非旨在成为程序的完整语义模型；相反，它提供了一个高效的索引，用于在整个代码库中检索相关证据，而无需进行完整编译或重量级的全程序分析。

局部增强包包含深度为 1 的直接被调用函数的签名、这些被调用函数在项目内定义时的函数体、函数中所引用宏和常量的文本定义，以及相关

ant typedefs and imports in scope. This material is supplied as explicit program evidence rather than left to the model. Claims about what an identifier denotes, what a callee does, or what a constant means can therefore be cross-checked against supplied code. The choice of depth one is deliberate. Expanding the call graph further increases prompt size and dilutes the model’s attention, yet still fails to guarantee complete interprocedural coverage. In our setting, one level is sufficient to disambiguate the immediate semantics of the function and its directly invoked project APIs, while keeping the input within budget. Deeper semantic dependencies are instead captured, when relevant, through the repository context bundle.
Local augmentation pins down what each line of the function means, but it does not explain what the program is for. Logic CWE-284 and CWE-200 vulnerabilities depend on repository-level semantics. Deciding whether a sink is safe requires understanding the kind of artifact the project implements, who interacts with it, the resources it mediates, the information it returns, and where its trust boundaries lie. None of this is reliably recoverable from a single function, even with depth-one expansion.
We therefore compute, once per repository, a structured context bundle that summarizes the project at the level needed to interpret individual functions. The bundle is produced by a repository-level LLM agent before function-level analysis. The agent is given the c

omplete repository and is asked to extract a stable description of the project’s purpose, actors, resources, outputs, and exposed interfaces. Its task is not to decide whether any function is vulnerable, but to provide the shared repository context that subsequent function-level prompts can rely on. Each item in the bundle is associated with repository-relative paths and short code excerpts, so that later reasoning can be tied back to concrete evidence rather than to the model’s general prior knowledge.
The bundle contains five sections. The
system purpose
section describes what kind of artifact the repository implements, its deployment context, and its primary consumers. The
principal model
section identifies the actors or callers that the code appears to distinguish, together with how their identity is established and through which interfaces they reach the system. The
protected objects
section records repository objects that appear security-relevant, such as configuration state, service handles, credentials, filesystem paths, or shared state tables, without deciding which principals are allowed to access them. The
information outputs
section summarizes externally observable outputs, including functional responses, errors, status information, configuration data, and internal state exposed through return paths or response builders. Finally, the
trust topology
section records the interfaces exposed by the project and the structural boundaries they create, such as library APIs

, IPC channels, local sockets, filesystem interfaces, or network-facing entry points. This shared bundle gives each function-level query the same repository-level frame while avoiding repeated rediscovery of the project’s purpose, actors, resources, outputs, and trust boundaries.
3.3
Structured LLM Reasoning
The structured LLM reasoning stage uses the grounded input to produce a function-level finding. The LLM is not asked to return an unconstrained vulnerability label. Instead, it is queried for a fixed-format finding whose elements must be tied to observable code or to explicit repository evidence. This design also aligns with prior observations that explanations should be grounded in verifiable evidence rather than unconstrained post-hoc rationalizations
[
23
]
. This output format determines what the contextual grounding stage must provide: enough local and repository-level evidence for the model to identify security-sensitive operations and state whether the required safety properties are satisfied by the analyzed function.
For each function analyzed, the model first identifies a set of
sinks
. A sink is an operation syntactically present in the function whose execution is potentially sensitive to the CWE under consideration. For CWE-284, a sink is any operation that affects a protected resource, such as a privileged system call, a write to a resource exposed across a trust boundary, or a state update performed on behalf of a principal. For CWE-200, a sink is any operati

on that emits data across a trust boundary into a region observable by a less privileged principal, such as returning data through an API, writing to a network channel, logging sensitive information, or exposing internal state through an externally visible interface.
For each sink, the model then derives a set of
safety conditions
. A safety condition is a predicate over the surrounding code, local checks, or relevant calling context that must hold for the sink to be safe in this repository. Each safety condition carries a
locally_satisfied
flag and a short justification. Both must be tied to specific code in the function or to explicit material supplied by the contextual grounding stage. A function is reported as a candidate vulnerability when at least one safety condition of at least one sink is not locally satisfied.
This scheme has three purposes. First, it anchors the model’s reasoning in concrete evidence. By committing to specific sinks and checkable predicates, the model cannot hide a vague intuition behind generic prose, which mitigates the unfaithfulness of free-form LLM rationales. Second, the resulting output is directly useful to an auditor. The auditor is told which operation is security-sensitive and which predicate must be verified, rather than being handed a binary verdict to validate from scratch. Third, the format enables sharper evaluation. In fact, a finding is only accepted when both the vulnerability judgment and the supporting reasoning are accurate. F

indings whose final label is correct but whose justification is inconsistent with the grounded evidence are discarded as incorrectly reasoned.
3.4
Comparative Validation
The comparative validation stage operationalizes the observation in
subsubsection 2.1.3
, that a genuine logic vulnerability is an anomaly relative to its peers while a recurring concern reflects a project norm. It reframes false-positive elimination as anomaly detection over the structured findings produced by the LLM. For each flagged condition, the stage compares the target against structurally similar sinks in the same repository, retaining the condition when it sets the target apart from its peers and discarding it when the same concern recurs uniformly across them.
To decide whether an unsatisfied safety condition is distinctive or merely a
recurring pattern, the validation stage compares the target sink against similar
sinks from the same repository. Similarity is computed in two steps. First, each
sink is represented by its
sink identifier
, i.e., the code fragment that
corresponds to the security-sensitive operation reported by the model. We embed
these sink identifiers with UniXcoder
[
13
]
and use cosine similarity to build a
neighborhood of sinks that are syntactically or semantically close at the code
level. This step compares operations, not model explanations. Second, validation compares the unsatisfied safety conditions attached to those
sinks. Safety conditions are natural-language predicates

Evaluation Procedure:
A repositor

Each pass instantiates the pipeline with the sink and safety-condition definitions appropriate to its class, so that prioritization, structured reasoning, and validation are all specialized to the vulnerability type under consideration rather than to the specific CVE. The two passes are otherwise identical and operate on the same repository. Unless stated otherwise, the per-repository figures we report aggregate both passes.
Metrics:
We report the number of true positives (TPs) and false positives (FPs). Scoring recall for logic vulnerabilities is nontrivial, since a tool may flag the right function for the wrong reason, and a binary vulnerable versus non-vulnerable match would overstate how well the underlying flaw was understood. We therefore exploit
Antaeus
’s structured output. Because each finding names a security-sensitive sink together with the conditions under which it is safe, we count a detection as a true positive only when the reported sink and its conditions actually explain the CVE, rather than when the flagged function merely overlaps with the vulnerable one. Concretely, a vulnerability is counted as detected when the pass corresponding to its CWE class reports a finding t

hat explains it, while the opposing pass contributes only to the false-positive count for that repository. The number of false positives is then the count of reported findings that do not correspond to a real flaw.

We compare

5
Discussion
Our aim is not a complete or formally sound vulnerability-analysis framework, but a practical method for recovering repository-specific security invariants under realistic analysis budgets.

Antaeus
deliberately trades exhaustive coverage for tractability at repository scale, and we therefore make no claim of exhaustive detection, completeness over all logic vulnerabilities, or formal correctness of the invariants it infers. The results should be read as evidence that repository-grounded invariant recovery can materially improve discovery effectiveness in practice. In the rest of this section we examine what this trade buys, where its boundaries currently lie, and how the design positions
Antaeus
to extend past them, with those boundaries understood in that light rather than as failures to meet a guarantee we never set out to provide.
Depth of local grounding.
The local augmentation bundle expands the call graph to depth one, which keeps prompts within budget. The consequence is that a safety condition whose justification lives two or more levels away may be judged on incomplete evidence. The repository-level context bundle partially offsets this by supplying project-wide semantics, though as a summary it does not restore arbitrary interprocedural reach. How deep to expand the call graph is a tunable point in the design rather than a fixed limit, and deeper grounding can be traded against prompt budget where a target repository warrants it.
Reliance on model judgment.
Sink identification and safety-condition derivation come from an LLM, and although the structured output ties each claim to supplied code, the model can still omit a relevant sink, propose a spurio

us condition, or offer reasoning that is plausible but unfaithful
[
29
]
. Comparative validation mitigates this by pruning conditions that recur across peers, but it operates on what the reasoning stage reports and cannot recover a sink the model never surfaced. This is the central reason
Antaeus
favors structured, evidence-linked output over free-form verdicts: making each claim inspectable is what allows downstream validation, and what lets a human reviewer audit a finding rather than take it on trust.
Role of prioritization.
Detection examines only the functions that survive prioritization, so this stage bounds what the reasoning stage can ever see. It rests on both keyword heuristics for initial pruning and the agent’s ranking of the survivors, either of which may overlook code whose relevance is not evident from its name, callees, or structure. We keep the heuristics deliberately high-recall, but surfacing security-relevant code at repository scale without exhaustive analysis is an open problem in its own right. We therefore treat prioritization as a pluggable component, and
Antaeus
stands to benefit directly from advances along this line.
Sensitivity to prompt design.
Each LLM stage is driven by prompts, and the space of formulations is effectively unbounded. We iterated on the prompts for prioritization, context extraction, and structured reasoning to obtain reliable, well-structured outputs, but make no claim of optimality: a different phrasing, ordering, or level of

instruction could move the results either way. The numbers we report should be read as the outcome of one carefully chosen, not exhaustively searched, configuration, which also means there is likely headroom a more systematic prompt search could recover.
Calibration of validation.
Comparative validation calibrates its thresholds per repository from the empirical similarity distribution. Where comparable sinks are few, the neighborhood may be too small for the pruning rule to fire, and the stage defaults to retaining the finding, a conservative choice that favors recall over precision. The strictness parameters expose this trade-off directly, giving an operator a knob to tune toward precision or recall according to how a given deployment weighs missed findings against review effort.
Generality of the evaluation.
Our study covers 28 real-world C and C++ repositories with confirmed CWE-200 and CWE-284 vulnerabilities. Labeled logic vulnerabilities of this kind are scarce, so assembling even this many is non-trivial, and the set is substantial relative to what is available for the class. The sample is nonetheless small in absolute terms, which limits statistical power and may not capture the full diversity of C and C++ conventions; results may likewise not transfer directly to other languages, to proprietary codebases with different norms, or to vulnerability classes beyond the two we target. We see broadening across languages and CWE classes as the natural next step, and the la

nguage-agnostic structure of the pipeline, prioritize, augment, reason, validate, is intended to make that extension straightforward.

Related Work
6.1
Traditional Approaches to Logic Vulnerabilities
The earliest systematic treatments of logic flaws come from the web domain. Felmetsger et al. derive likely invariants from observed executions and report paths that contradict them
[
11
]
, an approach later extended by black-box techniques that learn behavioral models from request traces and synthesize inputs to break them
[
25
,
7
]
. Domain-specific systems specialize this idea further to application workflows and e-commerce checkout logic
[
17
,
28
]
. These works establish that the violated property is defined by the application rather than by a fixed code pattern, but the signals they rely on, such as sessions, forms, and navigation structure, have no analog in systems software.
A separate tradition infers correctness rules from the code itself and treats violations as defects. Engler et al. extract implicit programming rules from systems code and surface statistical outliers as candidate bugs
[
10
]
, and Chucky identifies missing security checks by contrasting a function with structurally comparable code and reporting the omissions that stand out
[
33
]
. For the invariants we target, none of these anchors is available, and project-specific rules can encode them only at a manual cost that does not scale across repositories.
Antaeus
retains the anomaly-based intuition of

the missing-check line of work, but applies it over structured, model-produced findings.
6.2
LLM- and Agentic-Based Approaches.
A growing body of work applies language models to vulnerability detection. Many systems operate at the function level, presenting a single function and asking for a label or report
[
8
,
6
]
. A line of work augments the model with external knowledge, retrieving distilled vulnerability descriptions or CWE references at inference time to steer the judgment
[
9
,
3
]
. A complementary direction couples models with program analysis so that reasoning is anchored to extracted facts rather than raw text. IRIS infers taint specifications with an LLM and drives a static analyzer over the whole repository
[
19
]
, LLift and the interleaving approach of Chapman et al. embed model queries inside a static-analysis loop and feed the answers back into subsequent analysis
[
16
,
5
]
, and LLMxCPG compresses a code property graph into compact slices that let a model reason over segments spanning multiple functions
[
15
]
. These systems anchor on a tainted source, a specification, or a graph path, the kind of scaffold that logic flaws do not provide.
A further line moves detection from the function to the repository. Benchmarking efforts show that inter-procedural detection is a distinct and largely open problem, and supply call-graph dependencies as the bridge from intra- to inter-procedural reasoning
[
32
]
. Autonomous auditing agents instead traverse a reposito

ry to locate and explain defects
[
14
]
. Both rely on a dependency or anchor to follow, which the CWE-284 and CWE-200 issues lacks, leaving open-ended search prone to both wasted budget and drift.
Antaeus
instead fixes a bounded sequence of steps. It narrows the candidate set, attaches targeted evidence, and prunes by comparison. Recent results show that frontier models can uncover real vulnerabilities when given sufficient scaffolding and compute
[
4
]
. The open question is therefore not whether the capability exists, but how to harness it at repository scale without making the analysis prohibitively expensive
[
26
]
. To the best of our knowledge,
Antaeus
is the first system to address this challenge for logic vulnerabilities, targeting repository-level reasoning while keeping costs under control.
7
Conclusion
We presented
Antaeus
, a repository-level framework for detecting logic vulnerabilities by grounding LLM reasoning in codebase-wide context.
Antaeus
follows a five-stage pipeline that combines function prioritization, context-grounding, structured reasoning, comparative validation, and reporting to make LLM analysis both evidence-grounded and cost-aware. It prioritizes security-relevant functions, grounds each in local and repository-level evidence, derives sinks and safety conditions, validates candidate findings against similar sinks, and reports retained violations with supporting evidence. Our evaluation on 28 real-world C and C++ repositories with confirmed CWE

-284 and CWE-200 vulnerabilities shows that
Antaeus
detects and explains 15 vulnerabilities, substantially outperforming function-level LLM analysis and frontier-agentic baselines while maintaining comparable token usage and cost budgets. These results suggest that repository-specific grounding and staged validation are key to efficiently applying frontier LLM capabilities to logic vulnerability detection.

Ethical Considerations
This work focuses on the automated detection of logical vulnerabilities in software repositories. Our benchmark consists exclusively of previously disclosed vulnerabilities with public CVE identifiers

. While automated vulnerability-detection tools pose inherent dual-use risks, our tool is intended to support defensive security analysis, targets context-dependent logical flaws, and does not generate weaponized exploits. This research does not involve human subjects or user data.
Open Science
In the spirit of open science, we provide the artifacts underlying our experiments at
•
https://anonymous.4open.science/r/PromptPrioritizationAntaeus-00C3
The bundle includes the prioritization prompts, the per-repository ranked function lists they produce, and the prompts for the structured LLM analysis, letting reviewers inspect the inputs given to each model stage and the prioritized function sets on which our results are computed. We are currently polishing the full implementation of
Antaeus
and plan to release it as open source.
