Antaeus: Hunting Repository-Level Logic Vulnerabilities via Context-Grounded LLM Reasoning Michele Armillotta Nicolò Romandini Rebecca Montanari Lorenzo Cavallaro Abstract LLM-based vulnerability detectors have shown promising results in identifying memory-safety bugs and well-established vulnerability classes, where violations can often be expressed in terms of established security properties such as unsafe data propagation, bounds violations, or invalid memory accesses. Logic vulnerabilities, however, pose a fundamentally different challenge, as their identification requires inferring application-specific security invariants and often relies on implicit assumptions about intended behavior. Even frontier agentic models struggle in this setting, despite their ability to inspect and traverse large repositories, because the security invariants relevant to these vulnerabilities are often implicit and buried among large amounts of unrelated code. Motivated by this gap, we present Antaeus , a framework for detecting logic vulnerabilities that grounds LLM reasoning in repository-level code context. Antaeus follows a repository-scale pipeline that combines function prioritization, context-grounded reasoning, comparative validation, and structured reporting. First, it ranks functions using lightweight repository-wide security signals, directing costly LLM analysis toward the most relevant code regions and reducing model calls, cost, and triage effort. For each prioritized function, A

ntaeus grounds the model in explicit repository evidence, combining local code context with a repository-level view of the application’s functionality, security-relevant resources, and trust boundaries. This grounded input enables the model to reason about how the function is executed within the broader application rather than as an isolated snippet. Antaeus then identifies security-sensitive sinks, derives the safety conditions required for safe execution, and checks whether those conditions are locally satisfied. Candidate findings are subjected to comparative validation, which prunes concerns that reflect project-wide norms rather than distinctive violations. Unlike memory-safety bugs, which often manifest through invalid memory accesses, or dataflow vulnerabilities, which can often be expressed as

propagation from sources to sinks, logic vulnerabilities stem from missing, misplaced, or incorrectly composed enforcement of application-specific security invariants [ 21 , 22 ] . These invariants define who may perform an operation, which resources may be accessed, what information may be exposed, and under which workflow conditions an action is safe. Their detection depends on reconstructing the intended security invariants implicitly encoded by the surrounding codebase, rather than matching local code against known dangerous patterns. Logic vulnerabilities have long been recognized as an important but comparatively underexplored class of software defects [ 20 ] . Most automated vulnerability-detection techniques have focused on bug classes with clearer syntactic or semantic anchors, such as memory-safety errors, injection flaws, or tainted source-to-sink flows. Traditional pattern-based and taint-based tools, such as CodeQL [ 12 ] and Semgrep [ 27 ] , are effective when a vulnerability can be tied to a recurring code shape, a known dangerous operation, or a traceable source-to-sink flow. For logic vulnerabilities, however, there is often no universal source, canonical sink, or distinguished value to track. Although project-specific analyses can sometimes encode these invariants manually, building and maintaining them requires substantial expertise and does not scale across repositories. Existing work on logic vulnerabilities has made important progress, but it has largel

y studied web applications [ 17 , 28 ] . White-box approaches [ 11 ] infer application invariants from normal executions and check whether alternate program paths violate them, while black-box approaches [ 25 , 7 ] infer behavioral models from HTTP traces and generate tests that break observed workflow or data-propagation patterns. These works show that logic vulnerabilities vary by application and that detection depends on recovering intended security invariants rather than matching fixed code patterns. However, their assumptions remain tied to the web domain. They ground the analysis in requests, sessions, forms, URLs, navigation graphs, database-backed state, and user workflows. The problem remains less explored for repository-level C and C++ software. In this setting, security invariants are harder to recover because they are often distributed across large codebases and encoded through APIs, callbacks, flags, resource handles, configuration interfaces, and project-specific conventions. The evidence needed to judge a function is rarely contained in the local code alone. A function may look benign in isolation, while its safety depends on repository conventions, trust boundaries, or checks enforced by comparable code. Detecting logic vulnerabilities in this setting, therefore, requires recovering security invariants from code structure and repository context, rather than from web interaction semantics. Recent work applies Large Language Models (LLMs) to vulnerability detect

ion [ 14 , 6 ] , including agentic systems that can inspect repositories, navigate code, and produce natural-language explanations. These systems are promising because frontier models can reason about program intent, integrate heterogeneous evidence, and discover real vulnerabilities when appropriately scaffolded [ 2 , 4 ] . The limitation is not the intrinsic model’s incapability, but the way evidence is selected, structured, and budgeted during reasoning [ 18 ] . Function-level analysis provides too little context, forcing the model to infer project-specific security invariants from an isolated code fragment. Exhaustive repository exploration, on the other hand, can provide the missing evidence, but only by spending a substantial analysis budget on large amounts of irrelevant code. Even when effective, such search-heavy strategies are difficult to scale and can still cause the model to lose focus on the specific semantic facts needed to assess a candidate operation. The key issue is therefore context quality and cost, not simply context quantity. LLM-based vulnerability reasoning remains breakable without structured program-semantic support [ 30 , 34 ] , especially when interprocedural dependencies and vulnerability-triggering constraints must be inferred from raw code alone. At the same time, recent systems show that LLMs can be effective when embedded in pipelines that select relevant context, structure the reasoning task, and validate candidate findings [ 35 ] . The central question is not how much repository context can be supplied to a model, but whether that context can be used to reconstruct the security assumptions under which the repository is intended to operate, and then to judge a candidate operation against them. Based on this observation, we present Antaeus , a repository-level framework for detecting C and C++ logic vulnerabilities through context-grounded model reasoning. Rather than analyzing every function in isolation, Antaeus organizes detection as a staged pipeline. It first performs lightweight repository-wide prioritization to identify functions likely to involve security-relevant behavior, reducing the cost and triage burden of model analysis. The defining evidence lives in the repository around it. The safety of a function depends not on its local syntax, but on invariants the codebase as a whole is meant to enforce. An LLM model evaluating a function locally is usually assertive [ 8 , 29 ] . Shown a sensitive-looking operation, it tends to raise the safety conditions appropriate to that kind of operation, regardless of whether the surrounding codebase already addresses them. Across a r

epository, this yields a characteristic false-positive pattern, in which the same unsatisfied condition is reported for many structurally similar sinks, often in similar phrasing. A genuine logic vulnerability, by contrast, is an anomaly [ 10 , 33 ] , a deviation from how comparable code in the same project handles the same operation. When many similar operations are handled uniformly, that uniformity is the norm rather than a defect, and a model that raises the same concern across all of them is flagging the norm rather than a distinctive violation. As 1 shows, the missing read-only check is meaningful only relative to the sibling APIs that do enforce the boundary. A suspected violation, therefore, remains only a hypothesis until it can be set against the project’s enforced pattern. 2.2 Insights for Context-Grounded Logic Vulnerability Detection The challenges above motivate context grounding, which constrains model reasoning to explicit evidence about how a repository defines its security invariants rather than letting the model fall back on local syntax and generic priors. Grounding combines two complementary layers. Local program evidence ties claims about a function to concrete repository artifacts, and repository-level context supplies the application-specific invariants against which a local operation must be judged. This perspective leads to three design insights. Insight 1 : Prioritize candidates before grounding. Because logic vulnerabilities admit no syntactic anch

or, every function is a nominal candidate, but grounding each one is impractical. Detection should begin with repository-wide prioritization that surfaces functions likely to involve security-relevant behavior, spending the analysis budget only where a policy violation could plausibly occur. Insight 2 : Pair local evidence with repository context. The information needed to judge a function lies outside it, so the model should reason over both layers simultaneously. Local code, callees, macros, constants, and types anchor claims to concrete artifacts, while a repository-level security summary of the application’s purpose, protected objects, and trust topology supplies the invariants the operation must satisfy. Insight 3 : A missing safety condition is meaningful only relative to how comparable code in the same repository handles the same operation. Each flagged condition should be validated against analogous sinks, discarding those that recur uniformly as project norms and retaining those that set the target apart. These insights shape the design of Antaeus , a staged framework that grounds LLM-based logic vulnerability detection in repository evidence. A repository-wide prioritizer narrows the candidate set to security-relevant functions; a grounding stage pairs local code augmentation with a stable repository-level security summary; a structured reasoning stage produces findings in terms of security-sensitive sinks and their required safety conditions; and a comparative vali

dator confirms genuine violations by setting each finding against analogous code. The following section details each stage. 2.3 Threat model We consider an adversary who interacts with the target software through its intended interfaces, such as API calls, configuration options, files, command-line arguments, or network requests. The adversary cannot modify the program code, but can choose inputs, parameters, call sequences, and execution contexts to violate security-relevant assumptions made by the application. We focus on logic vulnerabilities in which the executed code is syntactically valid, but an operation is performed under semantically unsafe conditions. Antaeus assumes access to the source repository under analysis, but does not assume exploit inputs, runtime traces, or an execution environment. Its goal is to statically detect and explain candidate logic vulnerabilities by linking security-sensitive code to the repository context that determines whether its use is safe. Memory-safety bugs and purely syntactic defects are out of scope. The remainder of this section examines each stage in detail. 3.1 Prioritization At repository scale, the first challenge is deciding where to apply expensive LLM analysis. As discussed in subsection 2.2 , exhaustive repository exploration spends most of the budget on irrelevant code, while letting an agentic model search unaided does not guarantee that every security-relevant function is examined and may lead it to rely on superficial cues rather than repository evidence. Antaeus therefore begins with a lightweight, high-recall prioritization stage. The goal of this stage is not to classify functions as vulnera

ble, but to reduce the repository to a ranked set of functions that are most likely to contain logic-relevant behavior. This lets the later LLM stages operate at the repository level while keeping the number of detailed analyses tractable. The prioritization stage first prunes the codebase, retaining only C/C++ source and header files. It then applies broad keyword-based heuristics to remove functions that are unlikely to involve authorization, access control, trust-boundary enforcement, configuration changes, or other security-sensitive operations. These heuristics are intentionally loose: they are designed to remove clearly irrelevant functions while preserving recall for functions that expose even weak security signals. After this initial pruning, Antaeus compresses the remaining repository into a lightweight function-level representation. For each retained function, it removes the internal implementation logic and keeps only the function signature together with the callees invoked inside the function body, as illustrated in 2 . This abstraction is deliberately simple. It discards local implementation detail, but preserves the repository-wide call and naming signals that are useful for identifying security-relevant code regions. In particular, it allows the model to see many more functions and callees than would fit if full function bodies were provided. The compressed repository is then split into chunks that fit within the model’s context budget, with each chunk represen

ted as a single line aggregating the functions it contains. These chunks are passed to an agentic LLM, which ranks the functions by their relevance to the target logic vulnerability classes. This design serves two purposes. First, it gives the prioritization model a global view of the repository’s security signals. Rather than inspecting a small subset of files or relying on its training-time knowledge of popular projects, the model receives a compact representation of the functions that remain after high-recall pruning. This makes it more likely to identify functions whose names, callees, or surrounding API structure indicate relevance to CWE-284 or CWE-200. Second, it limits the cost of the subsequent analysis. The unit of analysis is a single function, but a function does not stand alone. Its meaning depends on the types of values it receives

Claims about what an identifier denotes, what a callee does, or what a constant means can therefore be cross-checked against supplied code. The choice of depth one is deliberate. Expanding the call graph further increases prompt size and dilutes the model’s attention, yet still fails to guarantee complete interprocedural coverage. In our setting, one level is sufficient to disambiguate the immediate semantics of the function and its directly invoked project APIs, while keeping the input within budget. Deeper semantic dependencies are instead captured, when relevant, through the repository context bundle. Local augmentation pins down what each line of the function means, but it does not explain what the program is for. Logic CWE-284 and CWE-200 vulnerabilities depend on repository-level semantics. Deciding whether a sink is safe requires understanding the kind of artifact the project implements, who interacts with it, the resources it mediates, the information it returns, and where its trust boundaries lie. None of this is reliably recoverable from a single function, even with depth-one expansion. We therefore compute, once per repository, a structured context bundle that summarizes the project at the level needed to interpret individual functions. The bundle is produced by a repository-level LLM agent before function-level analysis. The agent is given the c

omplete repository and is asked to extract a stable description of the project’s purpose, actors, resources, outputs, and exposed interfaces. Its task is not to decide whether any function is vulnerable, but to provide the shared repository context that subsequent function-level prompts can rely on. Each item in the bundle is associated with repository-relative paths and short code excerpts, so that later reasoning can be tied back to concrete evidence rather than to the model’s general prior knowledge. The bundle contains five sections. The system purpose section describes what kind of artifact the repository implements, its deployment context, and its primary consumers. The principal model section identifies the actors or callers that the code appears to distinguish, together with how their identity is established and through which interfaces they reach the system. The protected objects section records repository objects that appear security-relevant, such as configuration state, service handles, credentials, filesystem paths, or shared state tables, without deciding which principals are allowed to access them. The information outputs section summarizes externally observable outputs, including functional responses, errors, status information, configuration data, and internal state exposed through return paths or response builders. Finally, the trust topology section records the interfaces exposed by the project and the structural boundaries they create, such as library APIs

, IPC channels, local sockets, filesystem interfaces, or network-facing entry points. This shared bundle gives each function-level query the same repository-level frame while avoiding repeated rediscovery of the project’s purpose, actors, resources, outputs, and trust boundaries. 3.3 Structured LLM Reasoning The structured LLM reasoning stage uses the grounded input to produce a function-level finding. The LLM is not asked to return an unconstrained vulnerability label. Instead, it is queried for a fixed-format finding whose elements must be tied to observable code or to explicit repository evidence. This design also aligns with prior observations that explanations should be grounded in verifiable evidence rather than unconstrained post-hoc rationalizations [ 23 ] . This output format determines what the contextual grounding stage must provide: enough local and repository-level evidence for the model to identify security-sensitive operations and state whether the required safety properties are satisfied by the analyzed function. For each function analyzed, the model first identifies a set of sinks . A sink is an operation syntactically present in the function whose execution is potentially sensitive to the CWE under consideration. For CWE-284, a sink is any operation that affects a protected resource, such as a privileged system call, a write to a resource exposed across a trust boundary, or a state update performed on behalf of a principal. For CWE-200, a sink is any operati

on that emits data across a trust boundary into a region observable by a less privileged principal, such as returning data through an API, writing to a network channel, logging sensitive information, or exposing internal state through an externally visible interface. For each sink, the model then derives a set of safety conditions . A safety condition is a predicate over the surrounding code, local checks, or relevant calling context that must hold for the sink to be safe in this repository. Each safety condition carries a locally_satisfied flag and a short justification. Both must be tied to specific code in the function or to explicit material supplied by the contextual grounding stage. A function is reported as a candidate vulnerability when at least one safety condition of at least one sink is not locally satisfied. This scheme has three purposes. First, it anchors the model’s reasoning in concrete evidence. By committing to specific sinks and checkable predicates, the model cannot hide a vague intuition behind generic prose, which mitigates the unfaithfulness of free-form LLM rationales. Second, the resulting output is directly useful to an auditor. The auditor is told which operation is security-sensitive and which predicate must be verified, rather than being handed a binary verdict to validate from scratch. Third, the format enables sharper evaluation. In fact, a finding is only accepted when both the vulnerability judgment and the supporting reasoning are accurate. F

indings whose final label is correct but whose justification is inconsistent with the grounded evidence are discarded as incorrectly reasoned. 3.4 Comparative Validation The comparative validation stage operationalizes the observation in subsubsection 2.1.3 , that a genuine logic vulnerability is an anomaly relative to its peers while a recurring concern reflects a project norm. It reframes false-positive elimination as anomaly detection over the structured findings produced by the LLM. For each flagged condition, the stage compares the target against structurally similar sinks in the same repository, retaining the condition when it sets the target apart from its peers and discarding it when the same concern recurs uniformly across them. To decide whether an unsatisfied safety condition is distinctive or merely a recurring pattern, the validation stage compares the target sink against similar sinks from the same repository. Similarity is computed in two steps. First, each sink is represented by its sink identifier , i.e., the code fragment that corresponds to the security-sensitive operation reported by the model. We embed these sink identifiers with UniXcoder [ 13 ] and use cosine similarity to build a neighborhood of sinks that are syntactically or semantically close at the code level. This step compares operations, not model explanations. Second, validation compares the unsatisfied safety conditions attached to those sinks. Safety conditions are natural-language predicates

produced by the model, so we embed them with all-MiniLM-L6-v2 sentence-transformer model and compare them using cosine similarity. A target condition is considered repeated when enough neighboring sinks have an unsatisfied condition that is semantically similar to it. In that case, the condition is treated as a repository-wide recurring pattern rather than as evidence of a distinctive logic violation. Both comparisons require a notion of similar enough . We avoid fixed global thresholds because similarity distributions vary across repositories: some codebases contain many near-duplicate API wrappers, while others are more heterogeneous. We therefore calibrate thresholds per repository using the empirical distribution of similarities observed in that repository. Antaeus deliberately trades exhaustive coverage for tractability at repository scale, and we therefore make no claim of exhaustive detection, completeness over all logic vulnerabilities, or formal correctness of the invariants it infers. The results should be read as evidence that repository-grounded invariant recovery can materially improve discovery effectiveness in practice. In the rest of this section we examine what this trade buys, where its boundaries currently lie, and how the design positions Antaeus to extend past them, with those boundaries understood in that light rather than as failures to meet a guarantee we never set out to provide. Depth of local grounding. The local augmentation bundle expands the call graph to depth one, which keeps prompts within budget. The consequence is that a safety condition whose justification lives two or more levels away may be judged on incomplete evidence. The repository-level context bundle partially offsets this by supplying project-wide semantics, though as a summary it does not restore arbitrary interprocedural reach. How deep to expand the call graph is a tunable point in the design rather than a fixed limit, and deeper grounding can be traded against prompt budget where a target repository warrants it. Reliance on model judgment. Sink identification and safety-condition derivation come from an LLM, and although the structured output ties each claim to supplied code, the model can still omit a relevant sink, propose a spurio

us condition, or offer reasoning that is plausible but unfaithful [ 29 ] . Comparative validation mitigates this by pruning conditions that recur across peers, but it operates on what the reasoning stage reports and cannot recover a sink the model never surfaced. This is the central reason Antaeus favors structured, evidence-linked output over free-form verdicts: making each claim inspectable is what allows downstream validation, and what lets a human reviewer audit a finding rather than take it on trust. Role of prioritization. Detection examines only the functions that survive prioritization, so this stage bounds what the reasoning stage can ever see. It rests on both keyword heuristics for initial pruning and the agent’s ranking of the survivors, either of which may overlook code whose relevance is not evident from its name, callees, or structure. We keep the heuristics deliberately high-recall, but surfacing security-relevant code at repository scale without exhaustive analysis is an open problem in its own right. We therefore treat prioritization as a pluggable component, and Antaeus stands to benefit directly from advances along this line. Sensitivity to prompt design. Each LLM stage is driven by prompts, and the space of formulations is effectively unbounded. We iterated on the prompts for prioritization, context extraction, and structured reasoning to obtain reliable, well-structured outputs, but make no claim of optimality: a different phrasing, ordering, or level of

instruction could move the results either way. The numbers we report should be read as the outcome of one carefully chosen, not exhaustively searched, configuration, which also means there is likely headroom a more systematic prompt search could recover. Calibration of validation. Comparative validation calibrates its thresholds per repository from the empirical similarity distribution. Where comparable sinks are few, the neighborhood may be too small for the pruning rule to fire, and the stage defaults to retaining the finding, a conservative choice that favors recall over precision. The strictness parameters expose this trade-off directly, giving an operator a knob to tune toward precision or recall according to how a given deployment weighs missed findings against review effort. Generality of the evaluation. Our study covers 28 real-world C and C++ repositories with confirmed CWE-200 and CWE-284 vulnerabilities. Labeled logic vulnerabilities of this kind are scarce, so assembling even this many is non-trivial, and the set is substantial relative to what is available for the class. The sample is nonetheless small in absolute terms, which limits statistical power and may not capture the full diversity of C and C++ conventions; results may likewise not transfer directly to other languages, to proprietary codebases with different norms, or to vulnerability classes beyond the two we target. We see broadening across languages and CWE classes as the natural next step, and the la

nguage-agnostic structure of the pipeline, prioritize, augment, reason, validate, is intended to make that extension straightforward. 6 Related Work 6.1 Traditional Approaches to Logic Vulnerabilities The earliest systematic treatments of logic flaws come from the web domain. Felmetsger et al. derive likely invariants from observed executions and report paths that contradict them [ 11 ] , an approach later extended by black-box techniques that learn behavioral models from request traces and synthesize inputs to break them [ 25 , 7 ] . Domain-specific systems specialize this idea further to application workflows and e-commerce checkout logic [ 17 , 28 ] . These works establish that the violated property is defined by the application rather than by a fixed code pattern, but the signals they rely on, such as sessions, forms, and navigation structure, have no analog in systems software. A separate tradition infers correctness rules from the code itself and treats violations as defects. Engler et al. extract implicit programming rules from systems code and surface statistical outliers as candidate bugs [ 10 ] , and Chucky identifies missing security checks by contrasting a function with structurally comparable code and reporting the omissions that stand out [ 33 ] . For the invariants we target, none of these anchors is available, and project-specific rules can encode them only at a manual cost that does not scale across repositories. Antaeus retains the anomaly-based intuition of

the missing-check line of work, but applies it over structured, model-produced findings. 6.2 LLM- and Agentic-Based Approaches. A growing body of work applies language models to vulnerability detection. Many systems operate at the function level, presenting a single function and asking for a label or report [ 8 , 6 ] . A line of work augments the model with external knowledge, retrieving distilled vulnerability descriptions or CWE references at inference time to steer the judgment [ 9 , 3 ] . A complementary direction couples models with program analysis so that reasoning is anchored to extracted facts rather than raw text. IRIS infers taint specifications with an LLM and drives a static analyzer over the whole repository [ 19 ] , LLift and the interleaving approach of Chapman et al. embed model queries inside a static-analysis loop and feed the answers back into subsequent analysis [ 16 , 5 ] , and LLMxCPG compresses a code property graph into compact slices that let a model reason over segments spanning multiple functions [ 15 ] . These systems anchor on a tainted source, a specification, or a graph path, the kind of scaffold that logic flaws do not provide. A further line moves detection from the function to the repository. Benchmarking efforts show that inter-procedural detection is a distinct and largely open problem, and supply call-graph dependencies as the bridge from intra- to inter-procedural reasoning [ 32 ] . Autonomous auditing agents instead traverse a reposito

ry to locate and explain defects [ 14 ] . Both rely on a dependency or anchor to follow, which the CWE-284 and CWE-200 issues lacks, leaving open-ended search prone to both wasted budget and drift. Antaeus instead fixes a bounded sequence of steps. It narrows the candidate set, attaches targeted evidence, and prunes by comparison. Recent results show that frontier models can uncover real vulnerabilities when given sufficient scaffolding and compute [ 4 ] . The open question is therefore not whether the capability exists, but how to harness it at repository scale without making the analysis prohibitively expensive [ 26 ] . To the best of our knowledge, Antaeus is the first system to address this challenge for logic vulnerabilities, targeting repository-level reasoning while keeping costs under control. 7 Conclusion We presented Antaeus , a repository-level framework for detecting logic vulnerabilities by grounding LLM reasoning in codebase-wide context. Antaeus follows a five-stage pipeline that combines function prioritization, context-grounding, structured reasoning, comparative validation, and reporting to make LLM analysis both evidence-grounded and cost-aware. It prioritizes security-relevant functions, grounds each in local and repository-level evidence, derives sinks and safety conditions, validates candidate findings against similar sinks, and reports retained violations with supporting evidence. Our evaluation on 28 real-world C and C++ repositories with confirmed CWE

-284 and CWE-200 vulnerabilities shows that Antaeus detects and explains 15 vulnerabilities, substantially outperforming function-level LLM analysis and frontier-agentic baselines while maintaining comparable token usage and cost budgets. These results suggest that repository-specific grounding and staged validation are key to efficiently applying frontier LLM capabilities to logic vulnerability detection.
