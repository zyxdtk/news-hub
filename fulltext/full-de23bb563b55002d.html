摘要

智能体工作流使 AI 智能体能够按计划或响应仓库事件来执行重复性的仓库任务。现有研究考察了工作流定义及其输出，但对执行过程中发生了什么提供的证据有限。我们提出了 GH-AWTrace，这是一个将 5,051 个仓库中的 25,014 个经过验证的 GitHub Agentic Workflows 与 4,112,526 条运行记录和 562,877 个非空执行日志归档相关联的数据集。该数据集在 GitHub 日志保留期限的限制下保存了执行证据，并将其与仓库元数据和生成的工作流配置相关联。示例案例展示了日志如何揭示工具拒绝、提供商故障、智能体方法的改变以及智能体之间的委托。这些观察结果为执行失败、工具使用以及报告的运行结果与可见任务进度之间关系的研究提供了支持。不同工作流之间的覆盖范围有所差异，日志提供的是部分观察结果，而非完整的智能体轨迹。

I 引言

智能体 AI 可以通过开发工具检查仓库、编辑代码、运行测试并解决软件问题 [1]。在常见的编码智能体使用中，开发者通过分配 issue 或编写提示词来启动每项任务，然后审查提议的更改 [2]。智能体工作流让开发者只需一次性指定重复性任务，即可按计划或仓库事件运行它们，而无需人工启动每次执行 [3]。

GitHub Agentic Workflows（gh-aw）以 Markdown 形式实现了这一模型：一个文件将智能体的任务与其触发器、权限和允许的输出结合在一起 [3]。gh-aw 将该文件编译为 GitHub Actions YAML 工作流，该工作流会启动一个编码智能体，并可以生成可审查的 issue、评论或拉取请求 [3]。在 Azure/azure-dev 中，一个每周运行的工作流会读取已合并拉取请求上的反馈，并将重复出现的审查者请求转化为对仓库 Copilot 指令的拟议更新 [4]。2026 年 8 月，它检查了 49 个拉取请求，并提出了拒绝被忽略的命令行标志、以及在日志中打印 URL 前对其中的凭据进行脱敏的规则 [5]。仓库设置阻止了该工作流打开拉取请求，因此它保存了一个分支和一个带有补丁的 issue；一位维护者通过拉取请求 #9731 完善并合并了这些更改 [5, 6]。

Khelifi 等人 [7] 研究了开发者如何指定和维护 gh-aw 工作流。Valenzuela-Toledo 等人 [8] 发布了将 Markdown 定义与生成的 YAML 相关联的历史记录。Sun 等人 [9] 测量了 AI 代码审查 Actions 的评论是否导致了代码更改。Wang 等人 [10] 使用静态分析在智能体 GitHub Actions 工作流中查找提示注入路径。Isbarov 等人 [11] 在实际运行的 AI 驱动 CI/CD 工作流中测试了提示注入攻击。这些研究为工作流规范、输出和安全性提供了互补的视角。然而，工作流定义描述的是预期行为，而运行层面的结果只是总结了执行情况，并未解释中间发生的操作。执行日志为工具交互、访问限制、基础设施故障和恢复尝试提供了额外的证据。保存并关联这些证据尤为重要，因为 GitHub 的保留期限限制会使其随时间推移而变得不可用。

为了支持对智能体工作流执行的研究，我们发布了 GH-AWTrace，它将来自 5,051 个仓库的 25,014 个经过验证的 gh-aw 工作流与 4,112,526 条运行记录和 562,877 个非空执行日志归档相关联。其贡献有三方面：(1) 一个执行日志归档，这些日志在 GitHub 的保留政策下原本可能会变得不可用；(2) 相关联的工作流、仓库、运行和日志元数据，支持可追溯的分析；(3) 示例用例，展示了该数据如何支持对失败、工具交互和运行内智能体协作的研究。

II 数据集收集与整理

我们分三个阶段构建 GH-AWTrace：1) 识别生成的 gh-aw 工作流，2) 收集其运行元数据，3) 归档可用的执行日志。图 1 总结了这些阶段的覆盖情况。

II-A GitHub 智能体工作流识别

首先，我们通过 GitHub REST API 代码搜索 [12]，分别对 .yml 和 .yaml 文件使用以下搜索查询来查找 gh-aw 生成的工作流：

"This file was automatically generated by gh-aw" path:.github/workflows extension:yml fork:true size:0..393216

GitHub 对每个查询最多返回 1,000 条代码搜索结果 [12]。为了触及超出此限制的文件，我们按字节搜索互不重叠的文件大小范围。当某个范围报告了允许的最大值 1,000 个匹配项时，我们将其一分为二并搜索两个较小的范围。我们从最终范围中检索每一页，并使用仓库 ID 和确切的文件路径去除重复文件。

经过进一步调查，我们注意到目标短语可能作为引用文本出现，而非生成器注释。我们在搜索返回的 blob 修订版本处获取每个文件，仅当生成器短语出现在任何配置键之前的开头 YAML 注释中时才接受该文件。在 5,059 个仓库中的 25,227 个候选文件里，有 63 个缺少所需的头部，150 个已索引的 blob 无法检索。该过程最终得到了 5,051 个仓库中的 25,014 个经过验证的 gh-aw 工作流文件。

II-B GitHub 智能体工作流运行收集

我们使用 GitHub REST API 为每个 gh-aw 工作流收集运行记录，按工作流 ID 进行查询，并保存运行列表 API 返回的所有数据字段 [13]。我们通过仓库 ID 和确切路径将运行记录与发现阶段索引的 YAML 修订版本相关联。如果工作流发生了更改，该修订版本可能与运行所使用的版本不同。运行元数据保留了其 head_sha。由于 GitHub 保留政策会在 400 天后删除运行记录 [14]，本阶段得到了 4,112,526 条日期从 2025 年 8 月 14 日至 2026 年 9 月 21 日的运行记录。

II-C 日志收集

最后，GitHub 会在最多 90 天后自动删除公开的工作流执行日志 [14]。因此，我们选择了 2026 年 6 月 23 日至 9 月 21 日（即运行截止日期前 90 天）创建的 2,453,263 条运行记录。对于这些运行，我们下载并保存了 1,633,215 个执行日志归档（56.1 GB），每个已下载的尝试对应一个 ZIP [13]。一次运行有一个 GitHub 运行 ID。每次重新运行都保留该 ID 并获得新的尝试编号，因此我们通过运行 ID 和尝试编号来标识一个归档。我们检查每个 ZIP 的完整性，并记录其 SHA-256 哈希值和文件列表。在所选运行中，有 821,672 次运行没有已下载的归档，这可能反映了保留期限、删除、访问限制或未完成的运行。在已下载的 ZIP 中，有 1,070,338 个不包含文件，562,877 个包含日志文件。这 562,877 个含文件的归档属于 561,367 次运行，其中 18,337 个归档来自第一次之后的尝试。在对 2,900 个带有已保存作业元数据的空 ZIP 的早期审计中，2,699 个在可用页面中仅显示被跳过的作业，195 个未列出任何作业。我们无法确定每个空 ZIP 的成因。图 1 总结了工作流、运行记录和日志归档的覆盖情况。

阶段 A：工作流 | 阶段 B：运行 | 阶段 C：日志

III 数据集特征

III-A 模式与存储文件

图 2 展示了仓库、gh-aw 工作流、运行和日志归档之间的关联方式。一个仓库可以包含一个或多个 gh-aw 工作流，通过 repo_id 关联。当一个工作流执行时，它会有一次或多次运行，通过 repo_id 及其确切的 YAML 路径关联。一次运行可能没有已下载的日志归档，或者有一个通过 run_id 关联的归档。如果一次运行被重新运行，每个已下载的尝试归档都通过其尝试编号（attempt）来区分。

  • 仓库：id（整数）、full_name（文本）、stars（整数）、fetched_at（时间）、metadata（JSON）—— repository.json
  • 工作流：repo_id（整数）、path（文本）、workflow_id（整数）、name（文本）、sha（文本）、verified（布尔值）、state（文本）、metadata（JSON）、discovered_at（时间）—— 源文件 .yml / .yaml
  • 运行：id（整数）、repo_id（整数）、path（文本）、created_at（时间）、status（文本）、conclusion（文本）、attempts（整数）、verification（文本）、metadata（JSON）—— run-page JSON / run.json
  • 尝试日志：run_id（整数）、attempt（整数）、kind（文本）、state（文本）、path（文本）、bytes（整数）、sha256（文本）、files（整数）、error（文本）—— logs.zip / logs.receipt.json
  • 各实体间关系均为 1:N（一对多）

图 2：数据集模式。彩色圆点标记键和连接字段。连接线表示一对多关系，阴影页脚标注了所保存的文件。

III-B 可用内容

JSON 字段保留了额外的 GitHub 元数据，包括每次运行的事件、参与者、分支、提交 SHA 和时间戳。CSV 索引支持直接连接，而原始 YAML、API 响应和 ZIP 则保存了底层内容。下载记录行记录了归档是已保存还是不可用；已保存的 ZIP 仍可能不包含任何文件。其回执列出了每个成员及校验和。因时间久远而被跳过的运行没有已下载的归档。

IV 分析与潜在用例

以下摘录复现了每个所引用运行的归档第一次尝试智能体作业日志中的文本。我们省略了重复的前导 UTC 时间戳。颜色为编辑添加，省略号标记了省略的文本或中间行。

IV-A 智能体工作流失败分析

在 562,877 个非空日志归档中，有 178,151 个（31.7%）与结论为 failure 的运行记录相关联。这并不意味着将每次运行失败都归因于其智能体。示例 1 和示例 2 分别展示了一个被阻塞的任务和一个提供商故障。

示例 1：ISSUE TRIAGE（问题分类）—— 运行 30125677266 [15]

⌞ MCP 服务器 'github'：McpError: MCP error 0: [Filtered] 被完整性策略过滤（Resource
… 我无法读取其内容以执行分类。
∙ report_incomplete (MCP: safeoutputs) · 原因: …

示例 2：FAILURE SCANNER（故障扫描器）—— 运行 35294030895 [16]

新的、稳定的 QUIC 故障。我将配对 …
在 http://172.30.0.30:10002 处的提供商身份验证失败（HTTP 403）。
[copilot-harness] 尝试 1：部分执行后提供商身份验证失败 - 将重试一次 …
[copilot-harness] 尝试 2：身份验证失败 --- 不再重试

[error]进程以退出代码 1 结束。

扫描器的两次尝试是同一次 GitHub 运行内的重试。此类成对的消息支持对任务、访问策略和基础设施失败的研究，包括是否尝试了恢复。

IV-B 可见的智能体决策轨迹

智能体作业日志可以记录提示文件的路径和大小、可见的智能体消息、工具调用及响应。在以下案例中，完整的提示文本并不存在，因此这些轨迹不应被视为完整的提示或私有推理。在示例 3 和示例 4 中，一个智能体在工具被拒绝后更改了其发布命令，而另一个智能体在发布其结论之前检查了依赖项更新。

在这些 Copilot 运行中，生成的 YAML 将执行步骤 Execute GitHub Copilot CLI 标记为 id: agentic_execution。其作业日志在启动器启动之前打印 [INFO] Executing agent command...。ZIP 成员 *_agent.txt 是完整的作业日志，而不是每条消息的角色标签。

示例 3：ISSUE TRIAGE（问题分类）—— 运行 35351834895 [17]

∙ 读取 issue-context.md
✗ 发布 issue #50643 的分类摘要
⌞ 由于以下规则，运行此工具的权限被拒绝：'shell(cat)'
让我换一种方法：
完美！分类摘要已成功发布。

示例 4：DEPENDENCY CHECK（依赖检查）—— 运行 33057082627 [18]

现在我需要检查 2.4.1 和 2.5.0 之间关于 async_blocking 和安全性的差异，并检查 PR 链接。
∙ 获取 2.4.1 和 2.5.0 之间的差异
现在我已掌握所需的所有信息。让我汇总结论：
∙ add_comment (MCP: safeoutputs) · 正文: …
⌞ {"result":"success","temporary_id":"aw_k0yXps72","comment":"#aw_k0yXps72"}

这些序列支持对工具选择、被拒绝后的适应以及证据如何转化为行动的研究。日志中记录的任务陈述是智能体输出，不能替代完整的提示。

IV-C 多智能体协作

示例 5 展示了一次审查运行，它分派了三个后台审查者，并利用两个响应者之间的一致意见来筛选发现。它展示了运行内的委托和综合，但没有提供跨运行共享记忆的证据。

示例 5：EXPERT CODE REVIEW（专家代码审查）—— 运行 31484611735 [19]

[7] ⧫ 这是一个仅涉及文档的 PR（4 个文件，全部为 docs/README）。现在分派 3 个并行专家审查者。
[8] ✓ task(name: reviewer-1, description: 审查者 1：深度推理审查, …)
[10] ✓ task(name: reviewer-3, description: 审查者 3：替代视角审查…, …)
[97] ✓ read_agent(agent_id: reviewer-2, timeout: 180, wait: true)
[101] ⧫ 审查者 3 未产生响应 → 双审查者模式。两个已完成的审查者意见一致 (2/2) …

该轨迹支持对劳动分工、缺失响应以及智能体之间的一致意见如何改变最终审查的分析。

V 结论

我们提出了 GH-AWTrace，这是一个将 5,051 个仓库中的 25,014 个经过验证的 GitHub Agentic Workflows 与 4,112,526 条运行记录和 562,877 个非空执行日志归档相关联的数据集。通过将执行证据与工作流和运行元数据一起保存，该数据集支持仅凭工作流定义或运行结论无法开展的分析。示例案例揭示了访问限制、提供商故障、智能体行为的改变以及运行内的委托。

该数据集提供的是对执行的部分观察。日志可用性受到保留期限和检索覆盖范围的限制，且非空归档不一定包含完整的智能体轨迹。因此，分析时应区分工作流运行与执行尝试、报告的结果与观察到的任务完成情况、以及智能体行为与基础设施故障。具体的研究方向包括构建失败分类体系、考察工具拒绝后的恢复、以及研究运行结论与可见任务进度之间的一致性。GH-AWTrace 为探索这些问题提供了保存下来的证据，而更广泛的论断则需要系统抽样和验证。

数据可用性

GH-AWTrace（包括其关联的数据表、非空日志归档、模式和访问说明）已在 https://huggingface.co/datasets/jaykay9999/GHAWTrace 公开提供。一个 Python 示例连接了各数据表，复现了 31.7% 的结果，并提取了一个被引用的智能体日志。
