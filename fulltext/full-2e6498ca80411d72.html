摘要

LLM 智能体使用上下文压缩来管理不断增长的交互历史，但用大模型总结长历史会带来显著延迟。因此，压缩需要在信息保留与延迟之间取得平衡。我们观察到，结构化摘要槽位在独立生成时仍能保留信息。基于这一观察，我们提出了 SpecCompact——一个通过槽位并行语义投机加速压缩的框架。SpecCompact 微调一个小型起草模型并并行生成各槽位。目标模型验证每一行提议内容并修复被拒绝的内容，而后续起草使用更新后的槽位前缀。系统优化进一步减少了重复的上下文处理和模型调用。在使用两个目标模型的 AppWorld 和 τ³ 基准上，SpecCompact 相比 Hermes 式摘要实现了 2.04–5.63 倍的压缩加速。独立的下游评估揭示了依赖于模型和任务的性能权衡。在 Hermes 内进行的用户研究进一步显示出 8.68 倍的中位压缩加速。

1 引言

大语言模型（LLM）智能体如今处理着日益广泛的任务，尤其是个人工作和编程（Meta, 2026; OpenAI, 2026; Anthropic, 2025; OpenAI, 2025）。虽然更长的上下文窗口带来了更好的长时程性能，但也使智能体能够积累更大的用户请求、工具输出和中间决策历史。智能体系统通常使用上下文压缩来缩短这些历史，同时保留后续操作所需的信息（OpenClaw, 2026; Nous Research, 2026）。然而，压缩本身需要处理长上下文并逐个 token 地解码摘要，由此产生的延迟会显著降低用户体验。因此，压缩需要在信息保留与生成摘要的延迟之间取得平衡。

token 级投机解码是一种通用的解码加速方法，可以加速这一压缩过程。具体而言，一个推理成本更低的小模型可以加速生成，同时通过目标模型验证保持目标模型的输出分布（Leviathan et al., 2023; Chen et al., 2023）。然而，有效的摘要在措辞上可以不同，但对后续操作的影响相同。因此，尽管投机解码保持了无损压缩行为，它可能无法充分利用这种灵活性。近期的语义投机方法使用目标模型判断来接受句子级草稿（Pan et al., 2025; Hu et al., 2026），使其更适合压缩任务。然而，将这些方法应用于单个摘要仍需要顺序生成，这对于长上下文来说可能很慢。此外，异步压缩将摘要与智能体的持续执行重叠进行，而并行压缩则并发地总结输入块（Chen et al., 2026; Cim et al., 2026）。这些方法引出了一个进一步的问题：摘要本身的结构能否引导并行生成和目标模型验证？

现有的压缩模板提供了一个有用的起点。诸如 OpenClaw 和 Hermes 之类的智能体框架（OpenClaw, 2026; Nous Research, 2026）将摘要组织为目标、约束、进展、决策和后续步骤等字段。我们将这些字段称为槽位（slots）。每个槽位描述任务状态的一个方面，可以直接从共享历史中生成。在我们的初步研究中，不使用其他槽位输出而生成的槽位仍然保留了必要的信息，显示了独立槽位生成的潜力。此外，反转槽位生成顺序对保留的信息影响很小。这些发现表明，槽位可以作为独立并行生成的单元，并在每个槽位内进行验证和修复。

我们介绍了 SpecCompact，一个通过槽位并行语义投机加速智能体上下文压缩的框架。微调后的小模型根据共享历史和该槽位中已被接受的内容起草每个槽位。目标模型检查每一行提议是否得到历史的支持并与已接受的内容一致，然后接受该行或生成局部替换。这些起草–验证–修复循环并行运行，其输出被组合成结构化摘要。我们还引入了系统级优化，以减少执行开销并进一步加速压缩。

我们的贡献如下：

  • 我们表明，摘要槽位无需以其他槽位的输出为条件即可保留相关信息，支持将其用作并行压缩的单元。
  • 我们介绍了 SpecCompact，它结合了训练、并行起草以及带局部修复的逐行语义验证。我们进一步优化其执行以减少重复的上下文处理和模型调用。
  • 我们展示了相比 Hermes 式摘要 2.04–5.63 倍的压缩加速，以及下游任务评估和原生 Hermes 用户研究。

2 背景与动机

2.1 背景

投机解码使用小型草稿模型提出若干 token，由较大的目标模型在单次前向传播中验证（Leviathan et al., 2023; Chen et al., 2023）。被接受的前缀被保留，第一个被拒绝的 token 在恢复起草之前被替换。这使得每次目标模型调用可以产生多个 token，同时相对于仅目标模型解码保持无损。

语义投机通过基于草稿内容的含义进行评估，放宽了无损要求。相关方法如 SpecReasons（Pan et al., 2025）和 DREAM-R（Hu et al., 2026）将这一思想应用于推理步骤，实现有损但快得多的投机推理。与投机解码一样，这些方法使用小模型起草 token 序列。目标模型不验证单个 token，而是将序列作为完整的推理步骤进行评估，并输出接受或拒绝的决定。在上下文压缩中，措辞不同的摘要可以保留后续操作所需的相同信息。因此，我们采用语义投机进行压缩，根据草稿是否保留后续操作所需的信息来判断其优劣。

2.2 动机

智能体框架已经使用结构化模板进行上下文压缩。如图 2(a) 所示，OpenClaw 和 Hermes 将摘要组织为字段（OpenClaw, 2026; Nous Research, 2026）。在我们的语境中，我们将这些字段称为槽位。每个槽位描述任务状态的一个方面，例如目标或当前进展。槽位提供了自然的生成单元，但将所有槽位作为一个序列生成仍然需要后面的槽位等待前面的槽位。因此，我们研究这种顺序依赖是否必要。

我们在 100 条轨迹上比较了整体生成与独立槽位生成。整体生成在单个输出中产生所有六个槽位，而独立生成从相同的历史中生成每个槽位，且无法访问其他槽位的输出。我们使用 LLM 评判器评估每个槽位对完整历史中相关信息的保留程度，分数为 0 到 5，由五个二元标准求和得到。如图 2(b) 所示，独立生成的平均得分为 4.73，而整体生成为 4.44。得分至少为 4 的槽位比例分别为 93% 和 85%。反转整体生成的槽位顺序或独立生成的调用顺序，平均得分的变化至多为 0.03。这些结果表明，槽位所需的信息通常可以从历史中恢复，而无需以其他槽位为条件。这激发了从共享历史并行生成槽位的想法。

观察。 不使用其他槽位输出而生成的槽位仍能保留相关信息。这支持从共享历史并行生成槽位。

图 3：SpecCompact 概览。

图 3 提供了 SpecCompact 的概览。我们首先在目标模型生成的槽位内容上微调一个小型起草模型。在压缩过程中，起草模型从共享历史并行生成各槽位。目标模型根据历史和已接受的槽位前缀验证每一行提议，并修复被拒绝的行。每个槽位从其更新后的前缀继续，一旦所有槽位完成，它们就被组装成压缩后的上下文。

3.1 槽位条件化起草

基于我们的观察，我们使用槽位作为并行生成的单元。我们遵循 OpenClaw 的六槽位摘要模式（OpenClaw, 2026）：目标、约束与偏好、进展、关键决策、后续步骤和关键上下文。每个槽位都有一个指定其内容和输出格式的指令。每个请求包括共享的对话历史和完整的模式，但只要求起草模型生成所请求的槽位。图 5 提供了提示模板和槽位契约。

在定义了槽位结构之后，我们接下来微调起草模型以进行槽位条件化生成。我们首先使用目标模型配合生成提示产生监督训练数据。我们选择一个独立的小模型作为起草模型，在实验中使用 Qwen3-0.6B（Yang et al., 2025）。与原始投机解码不同，语义投机不要求起草模型和目标模型共享词表。我们通过监督微调（SFT）使起草模型与目标模型的槽位生成对齐。对于每个训练样本，我们最小化交叉熵损失：

$$\mathcal{L}{\mathrm{SFT}}(\theta)=-\sum{j=1}^{L_{s}}\log q_{\theta}!\left(y_{s,j}\mid H,c_{s},y_{s,<j}\right), \tag{1}$$

其中 $q_{\theta}$ 是起草模型，$H$ 是历史，$c_{s}$ 是槽位指令，$y_{s}$ 是目标模型生成的槽位内容，在起草模型的分词器下表示为 $L_{s}$ 个 token。其他目标函数，例如对齐输出分布之间的 KL 散度，也可以使用。我们使用纯文本监督以避免存储目标概率分布。我们为每个历史–槽位对构建一个训练样本，因此包含 $T$ 条历史的数据集产生 $6T$ 个 SFT 样本。

在压缩过程中，我们为每个槽位运行一个独立的起草流。所有流使用相同的微调起草模型和共享历史，但维护各自的槽位指令和已接受前缀。虽然 SFT 使用完整的槽位输出，但在线起草通过行级提议进行。起草模型自回归地生成 token，并将每行提议提交给目标模型进行验证。

对于槽位 $s$，令 $A_{s,t-1}$ 表示步骤 $t$ 之前已接受的前缀，$A_{s,0}$ 初始为空。该前缀包含已被接受的行或由目标模型生成作为替换的行。给定历史 $H$ 和槽位指令 $c_{s}$，起草模型 $q_{\theta}$ 提出下一行：

$$\tilde{\ell}{s,t}\sim q{\theta}!\left(\cdot\mid H,c_{s},A_{s,t-1}\right). \tag{2}$$

提议的行只有在验证后才被添加到前缀中。如果被接受，则原样追加；否则，改为追加目标模型生成的替换内容。更新后的前缀随后作为后续起草的条件，因此起草模型从摘要中保留的内容继续，包括任何目标模型的修复。历史和槽位指令在整个过程中保持不变。每个槽位仅依赖于自己的前缀，使得六个起草流可以并行运行。

3.2 语义验证

与 DREAM-R（Hu et al., 2026）一样，我们使用二元语义验证。对于每行提议 $\tilde{\ell}{s,t}$，目标模型检查其内容是否得到历史 $H$ 的支持并与已接受的槽位前缀 $A{s,t-1}$ 一致。验证提示包括历史、槽位指令、已接受前缀和提议行。它要求目标模型在两个条件都成立时返回 positive，否则返回 negative。图 6 提供了验证提示。我们通过共享前缀缓存减少重复处理历史的成本，详见第 3.3 节。

目标模型生成一个判断 token，我们从中获得 top-$k$ token 概率。令 $\hat{p}^{+}{s,t}$ 和 $\hat{p}^{-}{s,t}$ 分别表示 positive 和 negative 的概率估计。我们计算归一化接受分数为

$$r_{s,t}=\frac{\hat{p}^{+}{s,t}}{\hat{p}^{+}{s,t}+\hat{p}^{-}_{s,t}}, \tag{3}$$

当 $r_{s,t}\geq\eta$ 时接受该行。虽然我们只定义了 positive 和 negative 两个标签，但每个标签在目标分词器中可能有多种 token 形式。例如，positive 可能以大写字母开头或包含前导空格。对于每个标签，我们使用其返回的 token 变体中的最高概率。如果某个标签未出现在返回的 top-$k$ token 中，我们首先将剩余概率质量计算为 $1-\sum_{i=1}^{k}p_{i}$，其中 $p_{i}$ 是第 $i$ 个返回 token 的概率。然后我们将该值与最小的返回 token 概率进行比较，并使用较小的值作为替代概率。

当某行被拒绝时，目标模型在相同的历史、槽位指令和已接受前缀的条件下生成替换内容，被拒绝的行不包含在此输入中。给定被接受的草稿行或有效的目标替换，我们更新槽位前缀为

$$A_{s,t}=\begin{cases}A_{s,t-1}\oplus\tilde{\ell}{s,t},&\text{若被接受},\ A{s,t-1}\oplus\ell^{\mathrm{T}}_{s,t},&\text{若被拒绝},\end{cases} \tag{4}$$

其中 $\ell^{\mathrm{T}}_{s,t}$ 是目标模型生成的替换内容，$\oplus$ 表示拼接。然后从更新后的前缀继续起草，而无需重新生成先前已接受的内容。

3.3 高效的槽位并行执行

图 4：SpecCompact 中的执行优化：独立槽位调度、共享前缀缓存、草稿缓冲、行感知停止，以及带终止规则的轻量级检查。

并行生成槽位本身并不能使逐行投机变得高效。每个槽位反复调用起草模型和目标模型，这些调用包含相同的长历史。如果没有复用，即使是一 token 的验证响应也需要另一次昂贵的预填充。单独请求每行草稿也会增加模型调用开销，而修复生成可能会解码从未使用的额外行。我们通过以下优化来解决这些成本。

独立槽位调度。 我们并发运行六个槽位流，每个流都有自己的已接受前缀以及顺序的提议、验证和修复循环。当一个槽位等待目标验证或修复时，其他槽位可以继续起草或提交自己的验证请求。这使得起草模型和目标模型上的工作可以重叠，并支持跨槽位的服务器端批处理，减少了串行等待。所有流完成后，我们按模式顺序组装它们的输出。

共享前缀缓存。 每次验证或修复调用都包含完整的对话历史。即使目标模型只生成简短的响应，重复预填充这一长输入也可能很昂贵。因此，我们组织目标请求使用包含历史和所有六个槽位契约的公共前缀。槽位指令和已接受前缀跟随这一共享部分，验证时还包括提议行。这使得前导 token 在不同槽位和步骤之间保持不变。

草稿缓冲。 为每行单独调用起草模型会增加请求开销。因此，我们让起草模型在单次调用中生成多行。我们将第一行发送给目标模型进行验证，并将其余完整的行存储在缓冲区中。如果某行被原样接受，下一个缓冲的行可以在不进行另一次草稿调用的情况下被检查。复用要求生成该行所用的前缀与当前已接受的前缀 $A_{s,t-1}$ 完全匹配。如果目标修复改变了前缀，我们丢弃剩余的缓冲行，并从修复后的前缀生成新的续写。每个缓冲的提议在被接受之前都要经过相同的逐行检查。

行感知停止。 拒绝后的每次修复操作替换一行被拒绝的行。然而，目标模型可能继续生成未被使用的额外行。我们将目标服务器配置为在下一个换行符处停止生成（受 token 限制约束），避免在这些未使用的行上进行计算。为了检测换行符，我们将所有以换行符结尾的 token 包含在停止集合中。其中一些 token 还包含文本，因此我们在停止时保留该文本。我们在构建下一个输入时保留行和段落分隔，并保留序列结束前生成的任何最终内容。分词器和停止 token 集在多次调用之间复用，以避免重复设置。

检查与终止。 在实践中，起草模型有时会产生重复或异常长的行。我们检查提议的行是否与已接受的行重复或超过配置的字符限制。这样的行直接进入目标修复，避免在替换之前进行额外的语义验证调用。我们还限制每个请求生成的 token 数以及每个槽位保留的行数和 token 数，防止重复生成无限继续。当槽位的预算达到或提议的添加会超出预算时，槽位停止。目标替换具有相同的检查和预算验证，无需进一步的语义验证。如果替换为空或未通过这些检查，我们停止该槽位并保留其已接受的前缀。结构化摘要可能产生独立的标题。在长度和重复检查之后，我们直接接受以 # 开头的行和已识别的空槽位标记（如 (none)），避免对这些标准输出形式进行语义验证调用。空行作为格式保留。组装完成后，我们检查总摘要 token 预算，如果超出则报错。

4 实验

我们使用 Gemma4-31B-IT（Team et al., 2026）和 Qwen3.5-122B-A10B（Qwen Team, 2026）作为目标模型评估 SpecCompact，每个目标模型都配备单独微调的 Qwen3-0.6B 起草模型（Yang et al., 2025）。我们使用 AppWorld（Trivedi et al., 2024）和 τ³（Shi et al., 2026）评估压缩后的历史是否保留了后续智能体操作所需的信息。AppWorld 通过代码和应用 API 测试任务完成情况，而 τ³ 通过用户交互和工具使用测试任务完成情况。我们在完整的 AppWorld Test-Normal 和 Test-Challenge 数据集上进行评估，并为每个目标模型在 τ³ 随机选取的 80 个任务的子集上对每个任务运行三次试验。我们在 AppWorld 上报告任务目标完成率（TGC）和场景目标完成率（SGC），在 τ³ 上报告任务成功率。除智能体任务外，我们还在 LongBench（Bai et al., 2023）和 RULER（Hsieh et al., 2024）上评估长上下文压缩。对于 LongBench，我们使用 GovReport 和 QMSum 子集并报告 ROUGE-L。对于 RULER，我们在 8k 和 16k 上下文长度下使用官方的特定任务匹配指标评估全部五种任务类型。为了测量压缩延迟和吞吐量，我们从 AppWorld、τ³ 和 LongBench 构建较小的子集，而不是使用完整集合。

我们从 AppWorld、τ³ 和 LiveClawBench（Long et al., 2026）构建了约 5 万条训练数据，使用每个目标模型生成槽位级监督。训练和验证样本按轨迹 ID 分离。我们对每个起草模型进行一个 epoch 的微调，将 LoRA（Hu et al., 2021）应用于所有线性层，使用秩 16、缩放因子 32 和零 dropout。训练使用 AdamW（Loshchilov and Hutter, 2019），学习率为 $10^{-4}$，余弦衰减，预热比例为 0.05，零权重衰减，梯度裁剪为 1.0。我们使用每设备批大小为 2、梯度累积步数为 16、BF16 精度、最大序列长度为 16,384 token、随机种子 42。交叉熵损失仅在目标槽位内容上计算。

在智能体评估期间，我们每八次智能体模型调用压缩一次交互历史，保留系统和设置消息以及当前输入。新消息不断累积直到下一次压缩。对于延迟实验，我们在 NVIDIA RTX PRO 6000 Blackwell GPU 上使用 vLLM（Kwon et al., 2023）部署模型。Gemma4 在一块 GPU 上以 BF16 运行，而 Qwen3.5 在两块 GPU 上以 FP8 运行。SpecCompact 为起草模型使用一块额外的 GPU，并发运行六个槽位，接受阈值为 $\eta=0.7$。起草和修复每次请求最多允许 64 个新 token，而验证使用一个 token。每个槽位限制为 12 行和 320 个 token。SpecCompact 和基线方法的摘要预算为 2,048 个 token。

表 4 比较了系统优化前后的 SpecCompact。两种实现都已经并发生成槽位，使我们能够检查优化执行带来的额外收益。优化使 Gemma4 的压缩延迟降低 1.88–2.44 倍，Qwen3.5 降低 1.19–1.51 倍。例如，Gemma4 在 AppWorld Normal 上的延迟从 20.17 秒降至 8.26 秒。这些收益突显了在槽位并行之外减少重复上下文处理、模型调用和不必要解码的价值。该表测量的是优化的综合效果，而不是每个组件的贡献。完整的任务评估使用原始实现，尚未在包含所有系统优化的情况下重复进行。

4.5 用户研究

为了评估真实智能体环境中的用户体验，我们将 SpecCompact 集成到 Hermes 代码库中，并在四块 NVIDIA RTX PRO 6000 GPU 上使用 Gemma4 部署该系统。我们从自己的工作流程中构建了三个场景，涵盖编程、数学和多任务问答。对于每个场景，我们提前运行 Hermes 并在固定检查点暂停以保存上下文快照。用户使用每种方法从相同快照触发压缩，并在不知道方法身份的情况下选择哪种感觉更快。我们还在后台记录实际压缩时间。压缩后，我们要求智能体生成摘要，并收集对两个输出的单独盲偏好。

根据收集的压缩数据，SpecCompact 将中位压缩延迟从 63.74 秒降至 7.28 秒，中位配对加速为 8.68 倍。这些测量表明，压缩加速也延续到了原生智能体部署中。在 28 份摘要偏好回复中，11 份（39.3%）偏好我们的方法，8 份（28.6%）偏好 Hermes，8 份（28.6%）认为两者相似，1 份（3.6%）无法判断。

5 相关工作

5.1 智能体上下文管理

LLM 智能体通过外部记忆和上下文压缩来管理不断增长的历史。记忆系统存储和检索过去的信息（Packer et al., 2024; Xu et al., 2025），而提示和 KV 缓存压缩减少提示长度或缓存大小（Jiang et al., 2023; Xu et al., 2023; Li et al., 2024）。对于长时间运行的智能体，上下文压缩将交互历史总结为更短的工作上下文。现有方法改进压缩指南（Kang et al., 2026）、定期总结轨迹（Wu et al., 2026）或训练智能体管理其上下文（Zhou et al., 2025; Lu et al., 2025; Sun et al., 2025; Ye et al., 2025）。其他工作改进压缩的执行方式。Slipstream 将压缩与智能体的持续执行并行运行，并使用后续步骤验证摘要（Chen et al., 2026）。并行压缩并发地总结输入块（Cim et al., 2026）。SpecCompact 通过槽位并行语义投机加速结构化摘要的生成和验证。

5.2 投机解码与推理

投机解码使用小模型起草 token，由目标模型并行验证，保持目标模型的输出分布（Leviathan et al., 2023; Chen et al., 2023）。语义投机放宽了这一要求。SpecReason 使用目标模型判断来验证完整的推理步骤（Pan et al., 2025）。DREAM-R 进一步通过强化学习对齐起草模型，并并行化起草和验证（Hu et al., 2026）。这种方法适合上下文压缩，因为不同的摘要可以保留后续操作所需的信息。SpecCompact 通过并行槽位生成和逐行验证将语义投机适配到压缩任务。

6 讨论与局限

局限。 SpecCompact 关注准确性与压缩速度之间的权衡，重点在于框架及其系统实现。它没有提供相对于目标模型摘要的一致准确性优势。我们相信更好的起草模型–目标模型对齐，例如 DREAM-R（Hu et al., 2026）中使用的强化学习方法，可以提高准确性并提供更好的权衡。

讨论。 我们还发现，不同槽位从历史中获取信息的位置不同。进展和决策使用分布在整个上下文中的证据，而目标、约束和后续步骤主要依赖开头或结尾。这表明槽位条件化的滑动窗口注意力可以进一步加速起草。由于时间和资源有限，我们将这一方向留待未来工作。

7 结论

我们提出了用于加速 LLM 智能体上下文压缩的 SpecCompact。SpecCompact 结合槽位并行起草、逐行语义验证和系统优化来降低压缩延迟。在智能体和长上下文基准上的实验展示了显著的加速以及准确性权衡，而原生 Hermes 用户研究证实了延迟收益。
