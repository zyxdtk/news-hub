摘要 现代大语言模型（LLM）通常需要多阶段训练流程以实现强大的下游性能，其中后训练是适配开放权重模型的主要接口。我们推出了 torchtune，这是一个 PyTorch 原生库，旨在简化 LLM 的后训练生命周期，实现高效的微调、实验和面向部署的工作流。与许多现有微调框架（通常以牺牲透明度和可扩展性为代价来优化易用性、专用配方或硬件效率）不同，torchtune 强调模块化、可修改性以及对底层 PyTorch 组件的直接访问。本文介绍了 torchtune 背后的设计原则，描述了这些原则如何体现在其模型构建器、训练配方和分布式训练栈中，并在代表性的后训练设置下评估了该库。我们与流行的微调框架（包括 Axolotl 和 Unsloth）进行了比较，表明 torchtune 在许多设置下提供了强大的性能和内存效率，同时保持了足够的灵活性以进行快速的研究迭代。这些结果将 torchtune 定位为可复现的 LLM 后训练研究的实用基础。

1 引言 后训练，包括监督微调、偏好优化、蒸馏和基于 RL 的对齐，现在是使开放权重 LLM 适应下游任务的主要工作阶段 (Lai et al., 2025)。然而，支持这一阶段的框架已经发展成为复杂的堆栈，使得在单一工具中难以平衡可扩展性、性能和快速实验。

现有的 LLM 后训练框架包括 Axolotl (Axolotl maintainers and contributors, 2023)、Hugging Face 的 trl/transformers/peft 堆栈 (von Werra et al., 2020; Mangrulkar et al., 2022) 和 Unsloth (Daniel Han and team, 2023)。这些系统在设计空间中占据不同的位置：Axolotl 强调配置驱动的微调，Hugging Face 生态系统强调广泛的集成和模型覆盖，而 Unsloth 强调高效的 LoRA (Hu et al., 2022) 和 QLoRA (Dettmers et al., 2023) 微调。在这些系统中，有几个反复出现的权衡促使了 torchtune 的诞生：

1. 庞大的依赖堆栈。围绕 transformers 及相邻库构建的框架继承了广泛的传递依赖，这可能会使专注的后训练实验的部署、调试和复现变得复杂。 2. 紧密耦合的训练决策。模型构建、训练器逻辑、分布式策略和适配器插入通常分散在工厂层或训练器抽象中，使得细粒度修改比直接更改底层 PyTorch 模块更困难。 3. 对现代 PyTorch 性能路径的访问不均。通用实现可能会在内存和吞吐量上留下遗憾，相对于 FSDP2 PyTorch Community (2023)、DTensor (PyTorch Community, 2026)、损失并行和 torch.compile；内核专用系统改进了一些路径，但可能使训练循环不那么透明。 4. 碎片化的多配方支持。监督微调 (SFT)、直接偏好优化 (DPO)、近端策略优化 (PPO)/组相对策略优化 (GRPO)、知识蒸馏和量化感知训练通常存在于单独的库、配方系列或适配器系统中，这使得受控比较变得困难。 5. 分布式训练的可组合性。多节点训练、张量并行和上下文并行在框架间的支持不均，通常需要不同的后端或在不同规模下需要不同的抽象。

我们推出了 torchtune，一个 PyTorch (Paszke et al., 2019) 原生的后训练库，围绕可组合的构建块而非单体训练器设计。torchtune 提供了可修改的模型构建器、受 Hydra (Yadan, 2019) 启发的 YAML 驱动配方，以及一小组正交的优化开关，其对内存和吞吐量的影响可以独立测量并自由组合。相同的组件可以从单个 H100 扩展到多节点 FSDP2 集群，而无需重写训练循环。

本文的贡献如下： 1. 一个模块化组件模型 (§3)，使模型变体、LoRA、量化和架构更改局部于显式的 PyTorch 构建器。 2. 一种用于 LLM 训练的反向传播内优化器融合 (§4.1)，减少了梯度缓冲区的生命周期并提高了大型模型微调的内存可行性。 3. 一个基于 PyTorch DTensor 构建的可组合并行堆栈 (§5)：FSDP2、张量和序列并行、MoE 的专家并行、损失并行和上下文并行 (PyTorch Community, 2026)。 4. 一个异步 GRPO 配方 (§7)，通过 Ray 协调的队列和回放缓冲区将推出生成与策略更新解耦，支持在线策略同步和有界的离线策略滞后。 5. 一项实证研究 (§5.1)，在单 GPU 和多 GPU 后训练设置中将 torchtune 与 Axolotl 和 Unsloth 进行比较。

我们的实证部分量化了整个评估中使用的优化选择。在单 GPU 和多 GPU 的 Llama 3.3 70B 训练扫描中，我们分离了编译、激活检查点 (Chen et al., 2016)、线性交叉熵、序列打包、低位优化器状态和反向传播内优化器融合的影响。结果表明，这些优化是互补的：编译是中小型模型强大的吞吐量杠杆，而面向内存的技术决定了更大规模下的可行性。

2 相关工作 通用训练框架。PyTorch Lightning (Falcon and The PyTorch Lightning team, 2019) 和 DeepSpeed (Rasley et al., 2020) 是大规模训练中最广泛采用的系统之一。Lightning 将训练循环抽象为高级 Trainer API，实现了跨各种任务的模块化和快速原型设计。DeepSpeed 通过 ZeRO 系列优化器 专注于扩展效率，通过优化器和激活分区支持万亿参数模型。这两个框架在范围上都是通用的，并非针对 LLM 后训练的具体挑战量身定制。

Hugging Face 生态系统。Hugging Face 堆栈提供了用于适配预训练模型的专用库。trl 库实现了 SFT、DPO (Rafailov et al., 2023)、PPO 和强化学习管道（如 GRPO）(von Werra et al., 2020)，构建在 transformers (Wolf et al., 2020) 和 accelerate 库之上。与此互补，peft 库 (Mangrulkar et al., 2022) 引入了参数高效微调方法，如 LoRA 和 QLoRA (Dettmers et al., 2023)。这些框架强调易用性以及在 Hugging Face 模型中心内的集成，但严重依赖 transformers 训练抽象。

社区驱动的框架。Axolotl (Axolotl maintainers and contributors, 2023) 已成为社区导向的 LLM 微调替代方案，公开了基于 YAML 的配置，并与 Hugging Face 库、PEFT 适配器和分布式运行时（如 DeepSpeed 和 DDP）进行了广泛集成。Axolotl 通过提供大量预配置模板降低了用户的门槛，但继承了底层堆栈的复杂性。Unsloth (Daniel Han and team, 2023) 代表了另一条工作路线，通过自定义 CUDA/Triton 内核 针对消费级硬件实现最大效率，将 LoRA 和 QLoRA 微调加速高达 5 倍，同时减少内存使用。虽然有效，但 Unsloth 优先考虑吞吐量和内存优化，而不是训练循环的透明度。

torchtune 的定位。相比之下，torchtune 是专门为 LLM 的后训练生命周期设计的。它没有引入新的训练抽象，而是为 SFT (Ouyang et al., 2022)、知识蒸馏 (KD) (Hinton et al., 2015)、强化学习 (RL) 变体（DPO、PPO (Schulman et al., 2017)、GRPO）和量化感知训练提供了透明的 PyTorch 原生配方。扩展是通过原生 PyTorch FSDP 实现的，并将节省内存的技术集成到参考配置中。此外，torchtune 与 Hugging Face Hub、LM Evaluation Harness (Gao et al., 2024) 和 TorchAO (Or et al., 2025) 互操作，同时通过轻量级、可修改的脚本保持可修改性。这使其介于高级自动化训练器和低级性能专用内核之间。

3 设计 torchtune 库围绕模块化架构设计，促进了代码重用和实验。图 1 总结了各部分如何组合。该库提供低级 Transformer 构建块、将这些块组装成完整架构的模型构建器，以及协调优化、数据加载、检查点和分布式执行的训练配方。目标不是将 PyTorch 隐藏在新的训练器抽象之后，而是让研究面接近实际执行的代码。

3.1 模块化组件和构建器 在模型层面，torchtune 保持模块组装的显式性：核心 Transformer 块接受预构建的子模块，而构建器为每个架构选择具体的注意力、前馈、归一化、嵌入和投影实现。这使得架构变体局部于构建时间：LoRA 适配器、量化投影、替代注意力内核或特定架构的块可以交换，而无需重写共享的解码器逻辑或训练配方。

构建器还定义了受控实验的边界。相同的配方可以比较全量微调、LoRA、QLoRA、量化感知训练或自定义模块替换，同时保持数据、优化器、日志记录和分布式策略不变。附录 C 提供了解码器、注意力模块、构建器循环和 LoRA 替换的缩写代码示例。

3.2 开箱即用的支持 通过移除对 transformers 框架的依赖，torchtune 提供了现代开源 LLM 的纯 PyTorch 参考实现，这些实现在数值上与其原始 transformers 对应物等效，但阅读和修改起来要简单得多。支持的模型系列列表在表 5 中给出；添加新架构相当于按照第 3 节的风格编写一个构建器函数。

torchtune 还为常见的后训练模式（如聊天、指令、多模态聊天、偏好 (DPO) 和文本补全）提供了内置的数据集适配器，列在表 6 中，因此用户策划的数据集可以通过选择匹配的适配器插入，而无需编写自定义整理代码。

其他支持的工作流。除了本文进行基准测试的 SFT、DPO 和 GRPO 配方外，相同的组件模型还用于支持多模态微调（早期和深度融合视觉语言模型，如 Llama 3.2-Vision）、具有专用 KD 损失的知识蒸馏，以及通过 TorchAO 的量化感知训练 (Or et al., 2025)。

4 实现 4.1 反向传播内优化器融合 动机。LLM 训练的传统优化器遵循两阶段过程：首先为所有参数累积和存储梯度，然后在单独的优化器步骤中消耗。这需要完整的梯度缓冲区 $G_{t}=\{\nabla_{\theta_{i}}\mathcal{L}\}$ 保留在内存中，直到优化器更新完成，除了激活和优化器状态外，还增加了显著的内存开销。

设计。torchtune 引入了反向传播内优化器融合，其中优化器更新作为反向传播的一部分执行。当参数 $\theta_{i}$ 的梯度可用时，优化器（例如 AdamW）立即消耗它以更新其状态 $(m_{i},v_{i})$ 和参数值。然后可以释放梯度，而无需为全局步骤保留。这种设计将梯度张量的生命周期从整个反向传播减少到单个更新站点。

实现。具体来说，torchtune 的 OptimizerInBackward 包装器为每个参数实例化一个优化器对象，并在每个参数上注册一个 register_post_accumulate_grad_hook，一旦梯度最终确定，就调用 step() 和 zero_grad()。每个参数的优化器状态单独保留，并在包装器的 state_dict 中重新组装用于检查点。在每次反向传播进行一次优化器更新 ($K{=}1$) 的情况下，生成的参数轨迹与标准 AdamW 按位相同：每个参数的更新是可交换的，因为每个 $\theta_{i}$ 都有自己的状态 $(m_{i},v_{i})$，在 AdamW 的更新规则中没有跨参数依赖。将优化器步骤构建到反向传播中在 PyTorch 原语级别本身并不新鲜；我们的贡献是将其集成到 LLM 后训练配方中，并表征其在单 GPU 和多 GPU 70B 机制下的内存和吞吐量影响 (§5.1)。

好处。融合策略提供了两个主要优势： • 内存效率：峰值梯度内存减少，因为梯度被立即消耗和丢弃。在我们的实验中，这是 Llama 3.3 70B 在 8 个 H100 上 OOM 和可行运行之间的区别。 • 计算重叠：部分优化器工作负载与反向传播重叠，这可以产生适度的吞吐量收益。

限制。 • 梯度累积：该方法假设每次反向传播进行一次优化器更新。当必须在 $K>1$ 个微批次上累积梯度时，部分更新将被过早应用；因此，基准测试通过提高每步的批量大小来补偿。 • 分布式训练：该包装器自然地与 FSDP2 组合，因为每个 rank 持有相关的每个参数的分片，但需要小心地与本身假设全局步骤的优化器状态分片的 ZeRO 风格 方案结合使用。

4.2 线性交叉熵损失 动机和设计。LLM 训练中最终的交叉熵步骤是频繁的峰值内存热点：具体化形状为 $[B,S,V]$ 的 logits 可能会在大词汇量下主导内存。遵循 Cut Cross-Entropy 的动机 (Wijmans et al., 2025)，torchtune 的 LinearCrossEntropyLoss 将最终输出投影与交叉熵计算融合，在投影前屏蔽忽略的 token，并分块处理隐藏状态，从而永远不会具体化密集的 $[B,S,V]$ 张量。

组合和效果。在张量并行下，损失通过在词汇维度上分片输出投影与 PyTorch 的损失并行上下文组合 (§5)。在我们的扫描中，LCE 通常不是主要的吞吐量杠杆，但它可靠地减少了损失计算期间的峰值内存，并有助于更大的配置与编译和 Optim Bwd 组合 (§5.1)。

5 并行 torchtune 利用 PyTorch 较新的 DTensor API 进行分布式训练，允许多个并行设置的无缝集成。

数据并行使用 FSDPv2 API (Zhao et al., 2023)。数据并行涉及二维网格，除了分片外还支持数据并行复制，以最大化高带宽节点内通信的利用，同时减少节点间通信。

对于张量并行，torchtune 指定了关键模型架构的张量和序列并行计划，以及混合专家模型的自定义专家并行计划。这允许对仅用数据并行训练过大的模型进行高效并行化。

为了减少在交叉熵损失计算期间最常出现在 logit 和 softmax 张量中的峰值内存使用，torchtune 利用 PyTorch 的损失并行上下文管理器，在张量并行网格上沿词汇维度分片输出特征。这有助于避免具体化完整的 logits，并有助于在词汇维度上分片内存和计算。除了自定义线性交叉熵实现外，这允许在具有长上下文的输入上训练具有超大词汇量的模型。

除了经典的并行类型，torchtune 还包括通过 Ring Attention 的上下文并行 (Liu et al., 2023)。torchtune 中的上下文并行在附录 A 中分析。

6 应用优化分析 torchtune 公开了一组可组合的训练时优化，主要针对 计算峰值激活内存、优化器状态内存 和 内核/图效率。我们在受控的单 GPU 设置中跨 Qwen3 模型大小（表 2）以及在并行下的更大规模配置（表 1）评估这些标志。总体而言，结果说明了一个一致的权衡面：减少内存压力的技术通常会引入重计算或降低算术强度，而编译器和内核级优化主要提高吞吐量，有时可以通过融合操作和消除中间体来间接减少内存。

在 Qwen3-0.6B/1.7B/4B 中，启用 compile (Ansel et al., 2024) 产生了最可靠的吞吐量改进，并且在几种情况下也相对于基线减少了峰值内存（表 2）。例如，Qwen3-0.6B 从 5.2k → 7.9k tok/s 改进，同时将峰值内存从 8.6 → 7.0 GB 减少，Qwen3-1.7B 在 compile 下达到了最高吞吐量 (9.6k tok/s)。相比之下，LCE（分块损失计算）提供了相对适度和依赖于模型的收益：它可以在某些设置下略微提高吞吐量或稳定性，但与编译或激活重物化相比，它不是主要的驱动因素，而它对于平滑损失计算步骤期间的峰值内存很有用。激活检查点 (AC) 是一个可靠的内存杠杆：它全面减少了峰值内存（ notably 使 Qwen3-8B 能够在基线配置 OOM 的地方运行），代价是吞吐量降低。

对于优化器和梯度状态内存变得突出的大型模型，两种额外的策略实质性地扩展了可行性（表 1）。首先，在反向传播期间执行优化器步骤 可以通过减少梯度缓冲区的生命周期，在内存受限的机制中显著提高吞吐量（同时也施加了限制，例如与梯度累积的兼容性有限，以及在梯度可能很小的情况下没有改进：FSDP 运行或参数很少的模型）。其次，低位优化器状态 (AdamW8Bit) 在 Qwen3 扫描中产生了最大的绝对内存减少（例如，Qwen3-1.7B：11.7 → 4.9 GB），但可能会根据配置降低吞吐量。值得注意的是，对于 Llama 3.3 70B，基线配置 OOM，而包含 AC 的组合使训练成为可能，Optim Bwd 进一步提高了吞吐量（表 1）。

最后，我们将序列打包作为一个单独的分析轴（表 3），因为它改变了有效的 token 利用率并与内存/吞吐量平衡相互作用。

7 异步 GRPO GRPO (Shao et al., 2024) 使用在采样生成组上计算的标量奖励来优化策略。torchtune 提供了两种分布式全量微调配方：grpo_full_finetune_distributed（同步，紧密遵循原始算法）和 async_grpo_full_finetune_distributed，它重叠生成和优化以提高端到端加速器利用率。

动机。在同步 GRPO 中，解码和优化在同一组设备上序列化，这可能导致当一个阶段明显比另一个阶段更昂贵时（通常是长推出的解码）利用率不足。异步 GRPO 通过将推出生成与策略更新解耦并并发执行两个阶段来缓解这一问题。

调度机制。图 2 总结了我们的实现支持的三种调度机制： 同步基线，即生成和训练的同步交替； 具有周期性同步的在线策略异步管道； 允许有界策略滞后以换取更高利用率的受控离线策略变体。

系统架构和设计选择。异步配方实现为一组 Ray 协调的工作器，在 GRPO 算法计算和 编排和系统关注点之间进行了刻意的分离。

编排作为配方。我们将分布式系统实现为编排配方，其职责是实例化和连接可重用的工作器角色（生成、后处理、训练、日志记录）。这使得 GRPO 数学封装在现有的 torchtune 工作器内，并使得更改执行模型（同步 vs. 异步）变得简单，而无需重写学习算法。

通过队列 + 回放缓冲区解耦。推出通过两个显式数据结构移动：一个有界的 Ray Queue，用于推出工作器和后处理工作器之间的低延迟交接和背压控制；以及一个 torchrl RayReplayBuffer (Bou et al., 2024)，用于存储处理后的轨迹以供训练。队列控制突发性；回放缓冲区提供统一的采样 API，自然支持受控的策略滞后。

工作器角色。 • 推理（推出工作器）：基于 vLLM 的收集器 抽样分组响应和 token 级别的对数概率，并将原始推出推入共享队列。 • 后处理（参考工作器）：PostProcessingWorker 参与者弹出推出，计算 GRPO 特定的训练字段（例如，奖励、掩码和每轨迹元数据），并将处理后的轨迹写入回放缓冲区。 • 训练（演员工作器）：分布式 TrainingWorker 参与者从回放缓冲区消耗小批量并应用策略更新。

权重同步。训练在 PyTorch distributed (FSDP) 下运行，而生成在 vLLM (Kwon et al., 2023) 中运行，带有可选的张量并行。我们通过一个专用的 vLLM 参数服务器连接这两个世界，训练工作者可以发布到该服务器，推出工作者通过轻量级权重更新接收器轮询该服务器。这种设计在线刷新解码权重，而无需重启收集器。

可观测性和并发旋钮。为了使异步行为可调试，我们在所有角色中注入一个单独的 MetricLoggerWorker，用于一致地报告推出延迟、队列/背压行为、回放缓冲区吞吐量和奖励统计；并在配置中公开关键的并发/资源选择（例如，队列最大大小、回放缓冲区容量和 Ray max_concurrency）。

端到端流程。在运行时， 生成器产生分组推出（提示、抽样响应和相关的对数概率）， 训练器用奖励和特定于优化的字段（参考对数概率、优势和掩码）增强轨迹， 训练器更新策略并以可配置的节奏触发参数同步。

评估范围。我们将异步 GRPO 作为一项系统设计贡献提出：该配方将 GRPO 计算与编排关注点（排队、回放、权重同步）分离，同时在配置中公开在线策略和有界滞后执行。我们将头对头的奖励和吞吐量比较留给未来的工作，因为它们对奖励设计、抽样随机性和策略滞后调整很敏感。该配方 (async_grpo_full_finetune_distributed) 包含在发布的代码中。

8 结论 我们提出了 torchtune，一个用于 LLM 后训练生命周期的 PyTorch 原生库，优先考虑模块化、透明度和硬件效率。通过围绕可组合的模型构建器、数据管道、配方和优化选择组织后训练，torchtune 实现了快速实验，而不会强迫用户陷入僵化的抽象中。在支持的模型和数据集接口（表 5 和表 6）中，该库提供了实用的默认值，同时保持了对自定义架构和数据格式的可扩展性。

我们的评估表明，与广泛使用的后训练框架相比，torchtune 可以实现具有竞争力或更优的效率，同时保持易于检查和调整的实现。实验还表明，优化选择是互补的：编译在许多中小型设置中提高了吞吐量，面向内存的技术通常决定了大型配置是否可行，线性交叉熵减少了损失计算期间的峰值内存。总之，这些结果将 torchtune 定位为平衡清晰度、可扩展性和性能的可复现后训练研究的实用基础。
