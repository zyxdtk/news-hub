摘要

Transformer 推理在预填充（prefill）和解码阶段存在不同的瓶颈。预填充在许多 token 之间复用权重，主要由矩阵乘法和激活数据搬运主导。单 token 解码的数据复用有限，主要由权重和 KV 缓存的读取主导。我们提出 FuTransformer，这是一个面向 NVIDIA Hopper GPU 的 Llama 式 Transformer 块的 CUDA 实现。CODA 展示了如何将 Transformer 训练算子表示为"GEMM 加尾声"程序。FuTransformer 将这一原则应用于推理。它增加了直接的 KV 缓存放置、将固定的 RMSNorm 增益折叠进权重、使用延迟缩放从产生数据的尾声直接写入 FP8 值，并支持无填充的预填充。对于解码，FuTransformer 使用 INT4 投影权重和 KV 缓存的 INT4 副本。键和权重遵循 Tensor Core 片段布局，因此内核可以将它们直接反量化为 MMA 操作数，而无需创建完整的中间分块。块对角 Hadamard 变换使 INT4 缓存量化对离群通道不那么敏感。在单块 H100 上，预填充比编译后的 PyTorch FP8 快至多 1.48 倍，并达到 1.29 PFLOP/s。对于最接近的共享操作（gate/up 投影后接 SwiGLU），BF16 路径在 8B 形状上比已发布的 CODA 内核快 1.13 倍。我们的 FP8 推理路径比所评估的 BF16 CODA 路径快 2.02–2.18 倍。在 8B 和 70B 形状上、批量 1 到 32 的范围内，INT4 解码比每个点上更快的那个 PyTorch 解码块快 1.3–2.4 倍：比编译后使用 CUDA 图的 BF16 块快 2.1–3.3 倍，比使用 PyTorch INT4 投影内核（该内核为单查询行而构建，在批量 32 时输给它自己的 BF16 块）的同一块快 1.3–6.3 倍。INT4 解码也比我们的 FP8 解码路径快 31–51%。对于完整的 Llama-3.1-8B 模型，批量为一时一次 INT4 解码步骤耗时 2.8 毫秒，而编译后的 transformers 实现需要 8.1 毫秒。在 Llama-3.1-8B 上，通过 INT4 权重路径解码每个 WikiText-2 token，使用四舍五入（round-to-nearest）权重时困惑度从 6.24 升至 7.23，使用以相同格式存储的 GPTQ 权重时升至 6.99。旋转后的 INT4 缓存再增加 0.20。内核路径与量化参考计算的结果相差不超过 0.001 困惑度。

1 引言

矩阵乘法主导了 Transformer 的浮点运算量，但数据搬运和其他操作也会影响执行时间。解码器块还执行归一化、残差更新、位置编码、激活函数、精度转换和 KV 缓存更新。这些操作的算术量很少，但经常读写大型中间张量。随着 Tensor Core 变得更快，这种数据搬运在总执行时间中占据更大的份额。

CODA（Guo 等，2026）通过将许多 Transformer 算子表示为"GEMM 加尾声"程序，解决了训练中的这一问题。优化的 GEMM 主循环产生一个输出分块。然后，可编程尾声在该分块仍在片上时对其进行处理。这使得成对操作（如 RoPE 和 SwiGLU）以及残差更新、缩放和部分归约得以运行，而无需对全局内存进行单独的读写。

FuTransformer 将相同的"GEMM 加尾声"原则用于自回归推理。推理增加了两个要求。首先，预填充必须管理持久状态。它必须将 K 和 V 直接写入 KV 缓存，为后续投影产生低精度激活，并支持不同长度的请求。其次，解码的行数太少，无法表现得像大型 GEMM。在小批量下，每层仅为少数几行读取其权重，而注意力则为每个查询读取缓存的 K 和 V 值。因此，解码路径必须减少读取的字节数，并防止反量化延迟主计算。

对于预填充，FuTransformer 使用持久 FP8 GEMM，并在编译时选择尾声策略。这些策略应用 RoPE 或 SwiGLU、将 K 和 V 写入缓存、收集 RMSNorm 统计量、恢复缩放因子，并可选地直接写入 FP8 输出。推理权重是固定的，因此学习到的 RMSNorm 增益可以在量化前折叠进下一个投影。然后在该投影的尾声中应用逐行归一化因子。这在保持量化计算的同时消除了归一化激活张量。打包输入还消除了具有不同请求长度的批次中的填充投影行。

对于解码，FuTransformer 使用 INT4 权重和 KV 缓存的 INT4 副本。Hopper 没有 INT4 Tensor Core MMA，其 FP8 MMA 需要大型 warpgroup 形状，而解码中少量的查询行无法填满。因此，内核必须在 16 位 MMA 之前扩展 INT4 值。主要的设计选择是在哪里执行这种扩展。FuTransformer 按 MMA 片段所需的顺序存储键和权重。字节索引查找将打包的缓存值转换为 FP16 对。一小段逻辑和打包 BF16 操作直接在寄存器中转换权重半字节。组缩放在累加后应用。在缓存量化之前，块对角 Hadamard 变换分散大的通道值。在查询和注意力输出上的匹配变换在量化前保持了注意力计算。

主要贡献如下：

  • 面向推理的 GEMM 尾声。 从 CODA 的"GEMM 加尾声"表述出发，FuTransformer 增加了直接的 KV 缓存放置、将固定的 RMSNorm 增益折叠进权重、以延迟缩放写入 FP8 生产者输出，并支持打包预填充。
  • 片段对齐的 INT4 解码。 INT4 权重和缓存条目按使用它们的 MMA 片段所需的布局打包。值在寄存器中或通过小型查找表反量化。缩放在逐元素内循环之外应用。
  • 离群值感知的缓存量化。 当键包含大的通道离群值时，块对角 Hadamard 变换可减少 INT4 缓存误差。在量化之前，该变换保持精确的注意力点积。
  • 最终结果评估。 我们将完整的预填充和解码层与 PyTorch 进行比较。我们还将完整的 Llama-3.1-8B 模型与 PyTorch 进行比较，并将最接近的共享 gate/up–SwiGLU 阶段与 CODA 进行比较。我们报告性能和数值误差，并标注使用不同精度的比较。使用训练好的 Llama-3.1-8B 检查点，我们通过 INT4 路径解码每个 WikiText-2 token，并测量困惑度、逐层误差以及跨层累积误差。

2 背景与定位

2.1 Llama 式推理块

设 X ∈ ℝ^(M×H) 包含 M 个 token 向量，每个向量的隐藏宽度为 H。设 I 表示前馈宽度，H_q 表示查询头数，H_kv 表示 KV 头数，D 表示头维度。我们评估以下块：

X̂ = RMSNorm(X; γ₁),
(Q, K, V) = X̂ W_qkv^⊤, (1)
O = Attention(RoPE(Q), K_c, V_c),
X₁ = X + O W_o^⊤, (2)
X̂₁ = RMSNorm(X₁; γ₂),
Z = SiLU(X̂₁ W_g^⊤) ⊙ (X̂₁ W_u^⊤), (3)
Y = X₁ + Z W_d^⊤. (4)

K_c 和 V_c 存储先前 token 和当前 token 的键和值。该块使用因果分组查询注意力（GQA）（Ainslie 等，2023）和 RMSNorm（Zhang 和 Sennrich，2019）。gate 和 up 投影共享一个 GEMM，因此总共有四个投影 GEMM 和一个注意力阶段。

在预填充期间，M = BS，其中 B 是批量大小，S 是序列长度。每个权重分块在许多 token 行之间复用。在单 token 解码期间，M = B。在本文研究的小批量下，读取权重占投影延迟的大部分。注意力延迟随上下文长度 T 增长，因为注意力必须读取 KV 缓存。

2.2 "GEMM 加尾声"程序与 CODA

高性能 GEMM 有两部分。主循环加载输入分块并执行矩阵乘累加操作。尾声处理并存储每个完成的输出分块。此时，输出已经在寄存器或共享内存中。因此，尾声可以执行局部操作，而无需先将中间张量写入 HBM。

CODA（Guo 等，2026）提供了一种在 Transformer 训练中使用这一思想的结构化方法。它保持 GEMM 主循环不变，并提供五组可组合的尾声操作：逐元素和成对映射；向量加载和存储；分块加载和存储；分块归约（部分结果由小型辅助内核合并）；以及有状态变换。CODA 还表明，逐行 RMSNorm 因子可以穿过后续 GEMM 并在其尾声中应用。这些操作合起来覆盖了 Transformer 块前向和反向传播中几乎所有非注意力工作。

FlashAttention 引入了旨在减少数据搬运的分块注意力，以及在线 softmax。后续工作将执行调度适配到更新的 GPU 流水线和低精度（Dao 等，2022；Dao，2024；Shah 等，2024）。FuTransformer 的预填充注意力遵循这一方法。其解码设计专注于低位 K 和 V 值如何存储并扩展到使用它们的 MMA 片段中。

2.3 低精度权重与 KV 缓存

FP8 E4M3 在保持 Tensor Core 执行的同时减少了投影读写的数据量（Micikevicius 等，2022）。若 A_mk ≈ a_m A^q_mk 且 W_nk ≈ b_n W^q_nk，则

C̃_mn = a_m b_n Σ_k A^q_mk W^q_nk. (5)

行和列缩放可以在累加后应用，而不是应用于每个乘积。诸如 Transformer Engine 之类的系统使用延迟缩放（NVIDIA，2026b）：生产者使用先前执行期间收集的缩放因子立即写入 FP8 输出。

GPTQ 和 AWQ 使组缩放的 INT4 权重变得实用（Frantar 等，2023；Lin 等，2024）。Marlin 展示了按 Tensor Core 片段顺序打包权重并在寄存器中反量化的好处（Frantar 等，2024）。KIVI 研究了低位 KV 缓存（Liu 等，2024）。QuaRot 和 SAW-INT4 使用 Hadamard 旋转来减少激活和缓存离群值（Ashkboos 等，2024；Jia 等，2026）。FuTransformer 将这些思想结合到一个完整的 Hopper 解码块中，其布局专为其注意力和投影片段设计。

3 FuTransformer 设计

3.1 概述

FuTransformer 使用分开的预填充和解码路径，因为它们有不同的瓶颈。预填充保持大型 GEMM 的高效性并减少它们之间的数据搬运。解码减少为权重和缓存读取的字节数，然后按 MMA 操作数所需的布局反量化值。

预填充投影内核使用 128×256×128 的 CTA 分块、四级 TMA 流水线、一个生产者 warpgroup 和两个消费者 warpgroup。其主循环使用 Hopper FP8 WGMMA 和 Tensor Memory Accelerator（NVIDIA，2026a）。在编译时选择的尾声策略控制每个完成的片段如何处理和存储。因此，QKV、输出、gate/up 和 down 投影可以执行不同的推理操作，同时共享一个优化的 GEMM 主循环。

解码路径有两个内核家族。寄存器流式内核处理 M = 1，瘦矩阵内核处理 2 ≤ M ≤ 32。两者都读取打包的 INT4 权重，并将其直接扩展为 MMA 片段，以便与 BF16 激活累加。解码注意力读取 INT4 缓存副本。对于长上下文，它使用 split-KV 归约。

3.2 面向推理的 FP8 预填充

3.2.1 直接 KV 缓存放置

在训练中，K 和 V 是在同一遍中稍后使用的激活。在推理中，它们必须被写入持久的缓存地址。常规实现首先写入稠密的 K 和 V 张量，然后启动另一个内核将它们散射到缓存中。FuTransformer 直接从 QKV 尾声将它们写入缓存。

对于每个输出行 m，元数据给出请求和 token 位置 p_m。尾声将每个输出列映射到 Q、K 或 V 中的一个头和通道。它恢复投影缩放因子，对 Q 和 K 应用 RoPE，以注意力使用的布局写入 Q，并将 K 和 V 存储在 offset(request(m), head, p_m, channel) 处（式 6）。每个缓存元素只有一个写入者，有效范围之外的元素被屏蔽。这消除了稠密 K/V 中间张量和单独的缓存散射过程。

3.2.2 折叠冻结的 RMSNorm 增益

该块在 QKV 和 gate/up 投影之前应用 RMSNorm。定义

q_m = Σ_h x²_mh, ρ_m = (q_m/H + ε)^(−1/2). (7)

对于投影权重行 W_n 和学习到的增益 γ，输出为

C_mn = Σ_h x_mh ρ_m γ_h W_nh = ρ_m Σ_h x_mh W′_nh, W′_nh = γ_h W_nh. (8)

CODA 将行因子 ρ_m 穿过下一个 GEMM 并在该 GEMM 的尾声中应用。在推理期间，γ 和 W 是固定的。因此，FuTransformer 在量化和重新打包权重之前，一次性将 γ 折叠进 W。然后 GEMM 读取原始激活 X 和预处理后的权重 W′。使用 FP8 操作数时，输出为

C̃_mn = ρ_m a_m b_n Σ_h X^q_mh (W′)^q_nh. (9)

产生残差流的尾声还计算部分平方和。小型归约合并所有输出分块的结果以获得 q_m。下一个投影使用 ρ_m，因此无需将归一化激活张量写入 HBM。

3.2.3 延迟 FP8 输出

down 投影读取 SwiGLU 输出 Z。如果 gate/up 尾声以 BF16 写入该输出，则单独的量化内核必须读取它并写入 FP8 副本。对于 M 行和前馈宽度 I，两种方法分别搬运

B_separate = 5MI, B_producer = MI (10)

字节。分离路径写入 BF16，再次读取它，并写入 FP8。生产者路径只写入 FP8 一次。

FuTransformer 使用延迟的逐张量缩放。调用 t 使用在调用 t−1 期间收集的最大值对其输出进行量化。同时，尾声为调用 t+1 计算当前最大幅值。因此，它可以立即处理并存储每个片段。内核不需要在等待全局最大值时在片上内存中保留完整的输出行。

缩放状态有三个要求。第一次调用必须具有有效的初始缩放。还必须为全零张量定义缩放。并发的请求组必须保持独立的缩放状态，除非它们被有意一起运行。生产使用还需要饱和计数器，因为值范围的突然变化可能使先前的缩放不合适。

3.2.4 打包预填充

对于长度为 S₁, …, S_B 的请求，填充执行处理 B·max_b S_b 行。打包执行只处理

M_packed = Σ_(b=1)^B S_b (11)

行。前缀和数组将每个打包行映射到其请求和 token 位置。该映射还定义了注意力边界和 KV 缓存位置。FuTransformer 为填充和打包输入编译单独的内核，因此填充路径不需要运行时布局检查。

3.3 片段对齐的 INT4 解码

3.3.1 为什么解码需要不同的路径

设 P 为一层中投影权重元素的数量。除去小的元数据字段，解码期间读取的最小字节数为

B_decode = Pw + 2BTH_kv Dk, (12)

这里，w 是每个权重的字节数，k 是每个缓存的 K 或 V 元素的字节数。对于批量为一的 8B 形状，投影权重包含 2.181 亿个元素。这些权重在 BF16 中占用 436 MB，在 E4M3 中占用 218 MB，在 INT4 中占用 109 MB。因此，减少 w 和 k 直接减少了必须读取的数据，并可以降低延迟。

在 H100 上，小 M 解码内核无法使用直接读取这些打包值的 INT4 MMA。它们的行数也太少，无法使用预填充中使用的大型 FP8 WGMMA 形状。因此，FuTransformer 将低位值扩展为 16 位 MMA 操作数。其布局允许这种扩展在构建片段时发生，而无需单独的反量化阶段。

3.3.2 INT4 KV 缓存镜像

FuTransformer 保留 BF16 KV 缓存作为预填充和兼容性的主副本，并为解码维护一个 INT4 副本。每个字节存储两个有符号 4 位值。每个 token 和 KV 头有一个 FP32 缩放，计算为 amax/7。

缩放在逐元素循环之外执行。对于 K，缩放应用于完成的查询-键点积。对于 V，它在概率-值 MMA 之前应用于注意力概率。因此，内核避免了对每个解包元素单独缩放。

一个具有 256 个条目的共享内存表将每个打包字节映射到两个 FP16 值。一次查找将两个半字节扩展为 MMA 片段所需的对格式。该表不依赖于 token 缩放，因为缩放在累加后应用。

键遵循 mma.sync.m16n8k16 的 B 操作数所需的字节顺序。每个 lane 读取其片段大小的连续段，并使用字节索引查找直接填充操作数寄存器。这避免了创建反量化的 K 分块并通过共享内存移动它。V 保持自然通道顺序，因为概率-值 MMA 对值的分组方式不同。在使用前通过共享内存进行转置。

注意力 CTA 量化它将在当前解码步骤中使用的新缓存行。异步拷贝流水线将缓存缩放与它们的 K/V 分块一起加载。这使得缓存更新和缩放加载保持在串行的注意力内循环之外。

3.3.3 针对缓存离群值的 Hadamard 变换

当少数通道具有较大值时，均匀 INT4 量化可能会损失精度。遵循 QuaRot 和 SAW-INT4（Ashkboos 等，2024；Jia 等，2026），FuTransformer 在写入每个缓存行之前应用归一化的块对角 Hadamard 矩阵 H。查询使用相同的变换：

(Hq)^⊤(Hk) = q^⊤H^⊤Hk = q^⊤k. (13)

注意力输出每个查询行变换回来一次。该变换使用通过寄存器和 warp shuffle 实现的 Walsh–Hadamard 蝶形。每个缓存行在写入时旋转一次。查询和输出每个解码步骤各旋转一次。因此，注意力循环对每个缓存 token 执行相同的工作，增加的旋转成本不随上下文长度增长。默认情况下，每个块覆盖完整的头维度，但也可以使用更窄的块。

3.3.4 INT4 投影权重

权重离线量化，每个输出通道和每 128 个输入元素的组有一个对称缩放。半字节遵循解码 MMA 的 B 片段所需的顺序，因此每个 warp 可以为其输出分块加载连续的权重段。该格式定义每个半字节存储在哪里，而不是其值如何选择。值可以来自库的四舍五入量化器或校准方法（如 GPTQ）。两种量化网格都离线打包到相同的布局中。

权重在寄存器中反量化。每个半字节被插入 BF16 值 128.0 的尾数位。逻辑操作产生形如 (128+n, 128+m) 的打包 BF16 值。然后一次打包 BF16 融合乘加减去 136。这消除了基值 128 和用于将无符号半字节转换为有符号值的偏移量 8。每组单独累加。其组缩放在结果加到运行中的 FP32 累加器之前应用。内核从不创建完整的 BF16 权重分块。

对于 M = 1，每个 warp 读取一个输出分块的权重和归约维度的四分之一。CTA 中的四个 warp 通过共享内存合并它们的部分和。对于 2 ≤ M ≤ 32，瘦内核通过多级异步拷贝流水线加载激活分块、打包权重和缩放。当需要额外的 CTA 来保持 GPU 占用时，它使用跨 CTA 的 split-K。

5 讨论与局限

基线精度。 PyTorch 预填充比较使用相同的投影和注意力精度，但激活缩放策略不同。FuTransformer 与 CODA 之间的 BF16 gate/up 比较是最接近的同类比较，尽管它们的训练和推理 API 保留不同的辅助数据。INT4 解码与 PyTorch BF16 参考之间的比较使用不同的精度：参考具有 BF16 权重和 BF16 缓存。在 FuTransformer 内部比较 BF16、FP8 和 INT4 隔离了存储精度的效应。

范围。 性能测试覆盖一块 H100 上的单个 Transformer 层和 4.5 节中的完整 Llama-3.1-8B 模型。4.8 节的质量测试使用相同的完整模型。这些测试不包括多层调度、分布式通信、请求准入或完整的服务延迟。405B 标签描述一层的维度；我们没有在一块 GPU 上运行完整的 405B 模型。

准确性。 合成测试覆盖一层。训练检查点测试覆盖一个模型、一个用于困惑度的数据集和两个用于准确性的零样本多选任务。INT4 解码使困惑度增加 9–15%（取决于协议），并使 ARC-Challenge 准确性降低最多 7.6 个百分点。这是一个有意义的质量损失。延迟 FP8 缩放在预热后的稳定工作负载上测试。生产使用还需要安全的缩放初始化、饱和监控和请求本地状态。在部署之前，仍必须验证训练检查点上的任务准确性。

可移植性。 该实现专为 Hopper 片段布局、异步拷贝和资源限制而设计。支持另一代 GPU 需要不同的分块形状、流水线和打包布局。主要原则仍然可以应用，但内核细节取决于架构。

6 结论

FuTransformer 分别优化预填充和解码。预填充保持 FP8 GEMM 高吞吐量并减少操作之间的数据搬运。它以面向推理的缓存放置、固定的 RMSNorm 增益折叠、延迟 FP8 生产者输出和打包输入扩展了 CODA 的"GEMM 加尾声"表述。解码通过使用 INT4 权重和 INT4 KV 缓存副本读取更少的字节。两种格式都遵循使用它们的 MMA 片段所需的布局，因此值在 Tensor Core 使用它们的位置附近被反量化。

在一块 H100 上，FuTransformer 预填充比编译后的 PyTorch FP8 快至多 1.48 倍，并达到 1.29 PFLOP/s。对于最接近的共享 BF16 gate/up–SwiGLU 阶段，FuTransformer 在 8B 形状上比 CODA 快 1.13 倍。在 8B 和 70B 形状上、批量 1 到 32 的范围内，INT4 解码块比每个点上 PyTorch 两个解码块中较强的那个快 1.3–2.4 倍。单独测量时，它比编译后 CUDA 图的 BF16 块快 2.1–3.3 倍，比使用 PyTorch INT4 投影内核的同一块快 1.3–6.3 倍。它也比 FuTransformer 的 FP8 路径快 31–51%。完整的 8B 模型在批量一时比编译后的 PyTorch 快 2.9 倍解码。在 Llama-3.1-8B 上，INT4 权重使用四舍五入量化使 WikiText-2 困惑度增加 0.99，使用相同格式的 GPTQ 增加 0.75。旋转的 INT4 缓存增加 0.20，得到比 BF16 高 0.94 的完整 INT4 块。不旋转时，仅量化缓存将增加 0.54。内核路径与模拟量化参考在 0.001 困惑度内匹配。这些结果支持预填充使用 GEMM 尾声、解码使用片段对齐的低位执行。
