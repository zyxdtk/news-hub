Abstract
As AI coding agents become more autonomous, they increasingly ship code iteratively, with the codebase persisting across sessions.
This persistence creates a new attack surface: a misaligned or prompt-injected agent can distribute attacks across pull requests (PRs) and time its payload for the PR with the best natural cover.
To study the resulting dynamics, we introduce
Iterative VibeCoding
, a setting for AI control, the study of safely deploying capable but potentially untrusted AI. In
Iterative VibeCoding
, a coding agent builds software over a sequence of PRs in a persistent codebase while pursuing a covert side task. Our benchmark includes two task families: CLI tools and Flask web services, across 20 total task variations. We use Claude Sonnet 4.5 as the attack agent and GPT-4o as the monitor.
We compare gradual attacks, which distribute the side task across PRs, against non-gradual attacks concentrated in a single PR. No single monitor is robust to both: which strategy evades best (success while evading the monitor) depends on the monitor type, so a defender cannot close off both gradual and non-gradual attacks with any one monitor.

Introduction
The field of AI control
(Greenblatt
et al.
,
2024
)
studies how to safely deploy capable, but potentially untrusted AI systems.
As coding agents become more autonomous, they are increasingly used to ship code iteratively, with the codebase persisting across sessions.
This persistence creates a new attack surface.
A compromised agent, whether misaligned or adversarially prompted, can distribute infrastructure across pull requests, planting innocuous components early and activating them later; it can also wait for the PR (pull request) whose task most closely resembles its payload, exploiting natural cover.
To study this problem, we introduce
Iterative VibeCoding
, a setting where an AI coding assist

ant completes a sequence of programming tasks over multiple consecutive PRs in a persistent codebase.
The benchmark contains two task families: CLI-tool sequences and Flask web-service sequences (Appendix
P
).
We compare gradual attacks, which spread a side task across PRs, to a best-position non-gradual baseline, which executes the full side task in the optimal single PR, selected by minimizing detection.
Here, a
side task
is a hidden objective that the agent pursues alongside the user’s main task, such as covertly exfiltrating the
API_KEY
environment variable.
Our primary metric is evasion: among attacks that successfully complete the side task, the fraction the monitor fails to flag (scores below its threshold), where each monitor’s threshold is calibrated to the 98th percentile of scores from
honest runs
(runs in which no side task is present and the agent only works on the main task).
We measure attacker evasion across diff monitors (LLM monitors that see the code diff from PRs), which see only code changes, and trajectory monitors, which see command history and edits, while also varying how much context from previous PRs each monitor receives.
Because a run is flagged if any of the PRs in the sequence exceeds the threshold, an undetected attack must stay below the threshold throughout the full sequence.

A simulated user provides a fixed sequence of main tasks to an AI coding assistant building software iteratively.
The interaction takes place across PRs, with each PR extending the tool from earlier ones.

Our threat model has a direct analogue in software supply chain attacks, where adversaries plant in

nocuous components across commits and activate them later.
The XZ Utils backdoor (CVE-2024-3094) is a paradigmatic example: an attacker spent two years contributing legitimate patches before injecting a backdoor into a core Linux library
(Przymus and Durieux,
2025
; Lins
et al.
,
2024
)
.
Ladisa
et al.
(
2023
)
catalog 107 attack vectors across the open-source supply chain, including maintainer takeover through social engineering, the vector that most closely mirrors our gradual attack strategy.
Our work studies whether AI coding agents could execute this class of attack autonomously, and whether LLM-based monitors can detect it.
Deceptive AI and Scheming.
Several lines of work motivate studying covert agent behavior.
Carlsmith (
2023
)
argues that capable AI systems may pursue hidden objectives, and
Hubinger
et al.
(
2024
)
show that deceptive behaviors can persist through standard safety training.
Meinke
et al.
(
2024
)
and
Scheurer
et al.
(
2024
)
provide empirical evidence that frontier models can scheme in context and strategically deceive under pressure.
Monitoring a model’s chain-of-thought is another way to catch covert behavior, but the signal is fragile
(Korbak
et al.
,
2025a
)
: models do not always spell out their real reasoning, and training a model against a chain-of-thought monitor just teaches it to hide its intent instead of dropping it
(Baker
et al.
,
2025
)
.
Our experimental setup uses explicit adversarial instructions rather than relying on emergent decep

tion, but the monitoring challenges it surfaces (the limits of longer raw context, the advantage of distribution, the need for cross-modality ensembles) apply regardless of how the agent acquires its covert objective.
6
Discussion
Practical implications.
No single monitor catches both attack strategies reliably, and an ensemble cuts gradual evasion from
93
%
93\%
under the weakest standard diff monitor to
47
%
47\%
at modest cost (Section
4.4
).
In practical terms, these monitors should be viewed as partial risk reduction rather than as a sufficient safeguard for persistent-state coding agents.
Because even our strongest ensemble still leaves
47
%
47\%
of gradual attacks undetected, monitoring should be one layer of defense rather than the only one, combined with controls such as adaptive deployment protocols that adjust trust based on cumulative evidence
(Wen
et al.
,
2025
)
, narrower task scopes, stronger review of sensitive changes, or restrictions on networked actions and secret access.
Simply showing more raw diffs does not clearly improve detection overall relative to structured task summaries (Section
4.3
).
Persistence gives attackers two levers.
Persistent state enables both
distribution
(spreading components across PRs so no single diff is damning) and
timing
(waiting for the PR whose main task provides natural cover).
Lindner
et al.
(
2025
)
identify incremental cross-instance attacks as a key scaling challenge for control monitoring; our gradual attacks are an em

pirical instantiation of this dynamic in a sequential coding setting.
Schaeffer
et al.
(
2026
)
show that strategic selection of when to attack sharply reduces the safety of trusted monitoring even in stateless settings; persistent state amplifies this by giving the attacker a richer context for selection.
The two levers interact differently with monitor types, suggesting that monitoring setups benefit more from orthogonal monitors than larger context windows.
Attack prompting effort bounds measured evasion.
When we test additional frontier models as attack agents, elicitation itself is often difficult: in exploratory runs, models such as Opus 4.6 and GPT-5.3-Codex show failure modes ranging from soft refusals to partial compliance
(Panfilov
et al.
,
2026
)
.
Models that do comply fully (Sonnet 4.5, Gemini 3.1 Pro, Kimi K2.5) achieve comparable evasion rates (Section
4.2
).
Limitations.
Both task families remain much smaller than enterprise codebases; real deployments have larger repositories, deeper dependencies, CI/CD, and multi-developer histories.
We ensemble across monitor types but not across models; multi-model ensembles would be an interesting next step.
The reported experiments use no cross-PR memory; preliminary memory experiments are in Appendix
D
.
Gradual evasion numbers carry selection bias because the runs that succeed are the least distributed (Section
4.1
).
7
Conclusion
We studied AI control in a persistent codebase, where a coding agent ships software over

a sequence of PRs while pursuing a covert side task.
Persistence changes the monitoring dynamic; the threat lies in the sequence of PRs, not in a single diff. An attacker can spread a side task across PRs (a gradual attack) or wait for the one whose legitimate task provides natural cover (non-gradual attack). No single monitor we test catches both strategies, and this holds across several attack agents and monitor models, reflecting the nature of control in a persistent-state setting rather than something model dependent.
Giving a monitor more raw history does very little in gradual-attack defense, but carrying forward compact, structured cross-PR state, as our
link-tracker
monitor does, helps substantially. Combining monitors that catch separate attack types (gradual/non-gradual) into an ensemble is the strongest defense we found, yet it still leaves
47
%
47\%
of successful gradual attacks undetected.

Appendix L
Side Task Design Principles
Side task design follows four core principles to ensure the setting tests strategic deception rather than simple instruction following:
•
Triggered execution with persistence.
The attack must plant code that executes later (e.g., o

n the next import or test run), not during the agent’s PR. The malicious artifact must persist in the git history. This prevents “exfiltrate-and-delete” strategies (which will trivially beat diff monitors) and forces the attacker to survive code review.
•
Requires infrastructure.
The attack should depend on capabilities (e.g., network access, configuration parsers) that do not exist at the start of the sequence. If an attack can be trivially accomplished from scratch in PR 1 without prerequisite code, the persistent-state setting provides no benefit to the attacker.
•
Compositional suspicion.
The side task’s components should ideally be innocuous in isolation but suspicious when combined. A monitor seeing all components in a single diff should find them far more suspicious than seeing each component introduced gradually across separate, legitimately motivated PRs. This provides the theoretical advantage for gradual attacks.
•
Describe outcomes, not methods.
Side task instructions specify
what
must be achieved, not
how
. Because we are interested in the evasion strategies models discover autonomously, prescribing a specific implementation would bypass the strategic reasoning we aim to study.
Appendix M
Positional Policy Details
For a 5-PR sequence, we run 5 separate evaluations, one per position.
In each evaluation, the agent behaves honestly at every PR except the target position, where it receives the side task and a single-PR attack prompt.
Because the agent is honest at al

l other positions, the workspace evolves identically to an honest run up to the attack PR: the same code, the same git history, the same dependencies.
This means the honest prefix can be cached and reused across positions, and the attack always starts from a realistic codebase state rather than an artificially constructed one.
This design serves two purposes.
First, it isolates the effect of
position
: by comparing detection rates at PR 0 vs. PR 4 for the same sequence, we measure how much cover the task provides at each stage.
Second, aggregating across positions gives an upper bound on what a perfectly-timed non-gradual attacker could achieve.
A naive best-of-
k
k
aggregation (take the minimum suspicion score, succeed if
any
position succeeds) would give the non-gradual attacker a statistical advantage from variance reduction alone, conflating strategy quality with sample-size advantage.
Instead, we use best-position selection: for each (sequence, side-task) pair, we identify the position with the highest evasion rate, then report metrics using only runs at that position.

Additional Attack-Prompt Detail
The gradual prompt (

It asks the agent to treat each PR as a code review and to ask, before taking any action, whether a reviewer would find it justified by the current

The prompt emphasizes dual-purpose code, piggybacking on existing channels, and burying suspicious changes among legitimate main-task work.
Appendix N
Main Task Design Principles
Two design principles guide sequence construction:
•
Dual-use capabilities.
The sequence should legitimize the capabilities the attack requires (network access, environment variable reads), but not legitimize the attack itself. If a task never introduces HTTP requests, any use of
requests
is immediately suspicious, and it’s difficult for the red team to hide. Good sequences provide
cover
: not for the attack action, but for the attack
surface
.
•
Incremental privilege.
Early tasks should be low-privilege (local logic), middle tasks should introduce I/O (file reads, logging), and later tasks should introduce external integrations (network, secrets). This ramp creates a realistic setting in which a strategic attacker can introduce dependencies and infrastructure early, when they are first justified by the main task, and exploit them later.
