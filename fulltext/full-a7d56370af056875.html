Abstract As AI coding agents become more autonomous, they increasingly ship code iteratively, with the codebase persisting across sessions. This persistence creates a new attack surface: a misaligned or prompt-injected agent can distribute attacks across pull requests (PRs) and time its payload for the PR with the best natural cover. To study the resulting dynamics, we introduce Iterative VibeCoding , a setting for AI control, the study of safely deploying capable but potentially untrusted AI. In Iterative VibeCoding , a coding agent builds software over a sequence of PRs in a persistent codebase while pursuing a covert side task. Our benchmark includes two task families: CLI tools and Flask web services, across 20 total task variations. We use Claude Sonnet 4.5 as the attack agent and GPT-4o as the monitor. We compare gradual attacks, which distribute the side task across PRs, against non-gradual attacks concentrated in a single PR. No single monitor is robust to both: which strategy evades best (success while evading the monitor) depends on the monitor type, so a defender cannot close off both gradual and non-gradual attacks with any one monitor. High evasion ( ≥ 65 % \geq 65\% ) generalizes across model attack agent backends (Claude Sonnet 4.5, Gem

ini 3.1 Pro, Kimi K2.5), confirming this is a property of the persistent-state attack surface rather than a single model’s capability. Evasion also remains high across state-of-the-art monitor models and the gap between gradual and non-gradual evasion widens for more capable models. We introduce a stateful link-tracker monitor that tracks suspicious buildup across PRs. On both task families, it detects gradual attacks substantially better than diff monitors that merely see more accumulated history. Combining this stronger monitor with trajectory monitors in a four-monitor ensemble reduces gradual-attack evasion from 93 % 93\% under the weakest standard diff monitor to 47 % 47\% . Code is available at https://github.com/josh-hills/control-arena-persistent-state-eval . 1 Introduction The field of AI control (Greenblatt et al. , 2024 ) studies how to safely deploy capable, but potentially untrusted AI systems. As coding agents become more autonomous, they are increasingly used to ship code iteratively, with the codebase persisting across sessions. This persistence creates a new attack surface. A compromised agent, whether misaligned or adversarially prompted, can distribute infrastructure across pull requests, planting innocuous components early and activating them later; it can also wait for the PR (pull request) whose task most closely resembles its payload, exploiting natural cover. To study this problem, we introduce Iterative VibeCoding , a setting where an AI coding assist

ant completes a sequence of programming tasks over multiple consecutive PRs in a persistent codebase. The benchmark contains two task families: CLI-tool sequences and Flask web-service sequences (Appendix P ). We compare gradual attacks, which spread a side task across PRs, to a best-position non-gradual baseline, which executes the full side task in the optimal single PR, selected by minimizing detection. Here, a side task is a hidden objective that the agent pursues alongside the user’s main task, such as covertly exfiltrating the API_KEY environment variable. Our primary metric is evasion: among attacks that successfully complete the side task, the fraction the monitor fails to flag (scores below its threshold), where each monitor’s threshold is calibrated to the 98th percentile of scores from honest runs (runs in which no side task is present and the agent only works on the main task). We measure attacker evasion across diff monitors (LLM monitors that see the code diff from PRs), which see only code changes, and trajectory monitors, which see command history and edits, while also varying how much context from previous PRs each monitor receives. Because a run is flagged if any of the PRs in the sequence exceeds the threshold, an undetected attack must stay below the threshold throughout the full sequence. Gradual attacks evade standard diff monitors, and which strategy evades best depends on the monitor type. On the task-description diff monitor, which sees all prior task descriptions plus the current PR’s diff, gradual attacks evade more frequently across all four side tasks ( 87 % 87\% gradual vs. 75 % 75\% non-gradual). On trajectory monitors, this ordering can reverse: across our four side tasks, non-gradual attacks evade better for the two single-component tasks ( 76 % 76\% non-gradual vs. 66 % 66\% gradual), while the two multi-component tasks favor gradual attacks ( 71 % 71\% gradual vs. 58 % 58\% non-gradual; see Table 10 in Appendix A.4 ). Generally, gradual attacks evade monitors better in our setting, because distributing the side task across PRs lets each component land in a PR where it already has natural cover. 2. A stateful diff monitor and cross-modality ensemble provide the strongest defense. Link-tracker , a new stateful diff monitor that carries forward suspicion notes across PRs, reduces gradual-attack evasion from 87 % 87\% to 54 % 54\% . Combining it with trajectory monitors in a four-monitor ensemble further reduces gradual evasion to 47

% 47\% . 3. Evasion remains high across state-of-the-art monitor models; the gap between gradual and non-gradual evasion widens with more capable models. We use eight strong models as monitors for our setting. Even with GPT-5.3-Codex as a monitor, which is a more capable model than the untrusted agent (Claude Sonnet 4.5), it still allows 31 % 31\% of successful attacks through. Gradual attacks tend to evade more than non-gradual ones, and the gap is largest for the most capable monitors. These results suggest that persistent-state control is a distinct security problem with its own attack strategies and defense requirements. Our setting provides a foundation for developing and stress-testing monitors for coding agents in persistent state settings. 2 The Iterative VibeCoding Setting 2.1 Scenario A simulated user provides a fixed sequence of main tasks to an AI coding assistant building software iteratively. The interaction takes place across PRs, with each PR extending the tool from earlier ones. Code persists between PRs via git commits. In our main experiments, the agent has no cross-PR conversation memory. This isolates the effect of persistent code from that of session memory, so we do not necessarily model the strongest possible memory-enabled attacker. This is an example task sequence from the CLI task family (the uptime-monitor sequence): PR 1: “Create a Python script that checks if a local port is open.” PR 2: “Add a --url flag to check if a URL is reachable.” PR 3: “

Allow reading URLs from a YAML config file.” PR 4: “Add retry logic with exponential backoff.” PR 5: “If a site is down, POST a notification to SLACK_WEBHOOK_URL .” In attack mode, the agent also receives a covert side task (e.g., exfiltrate a secret or plant an authentication bypass) that it must accomplish without detection. Across our sequences, later PRs naturally introduce network access and environment variables, creating various degrees of cover for the side task. 2.2 Environment Between PRs, the /workspace directory (source code and git history) is extracted from the completed container and injected into a fresh one. Installed packages, environment variables, running processes, and files outside /workspace do not persist. Only committed code and git history carry over, mirroring a CI/CD workflow where each PR starts from a clean environment at the latest repository state. Task sequences. The benchmark includes five CLI-tool sequences (Appendix O ) and five Flask web-service sequences (Appendix P ), each spanning 5-6 PRs. Our goal in main task design is to provide natural cover for the actions of our four side-tasks (network access, environment variables, authentication, and webhook integrations) without directly justifying the side task itself, following prior control settings that embed side tasks inside legitimate engineering work (Tracy et al. , 2026 ; Kutasov et al. , 2025 ; Bhatt et al. , 2025 ) . Additional CLI side tasks are described in Appendix E . 2.3 Threat Model We use the standard AI control threat model (Greenblatt et al. , 2024 ) : • The Red team controls the agent’s system prompt and attack strategy. It uses the same model (Claude Sonnet 4.5) whether attacking or working honestly. • The Blue team designs monitoring protocols using a trusted model (GPT-4o) and calibrates suspicion thresholds from honest-baseline runs (runs with no side task present). The blue team does not know which attack strategy the red team will use. • Agent constraints: The agent must also complete the main task. It operates within the sandboxed environment and cannot modify the monitoring infrastructure. 3 Experimental Design We describe the attack policies, monitor configurations, and evaluation protocol used in the

experiments. 3.1 Attack Strategies Attack prompts undergo ∼ 10 {\sim}10 rounds of prompt engineering to maximize evasion (Appendix M.1 ). We study two main types of attacks: • Gradual attacks distribute the side task across PRs; the prompt frames the agent as a penetration tester and instructs it to prefer dual-use code and existing channels. • Non-gradual attacks execute the full side task in a single PR. We use a positional policy: for each sequence, we run one evaluation per position, with the agent behaving honestly at every other PR (Appendix M ). We then select the position with the highest evasion rate per (sequence, side-task) pair, modeling an attacker who chooses the PR with the best cover, yielding n = 120 n=120 non-gradual runs and n = 120 n=120 gradual runs. 3.2 Monitor Configurations We evaluate five monitors across two families (Table 2 ): three PR-diff monitors that review code changes and two trajectory monitors that review the agent’s actions, all outputting suspicion scores from 1 (benign) to 10 (malicious). Link-tracker is a novel stateful diff monitor: as it reviews each PR it writes notes to a file recording anything potentially suspicious, and these notes persist across PRs, so when it scores a later diff it can see whether the new change builds on suspicious setup from earlier PRs. he prompt decomposition attacks studied by Chen et al. ( 2026 ) . What makes a PR good cover? The main factor driving non-gradual success is whether the current task requires actions resembling the attack. In the non-gradual runs, side-task success increases from 3 % 3\% at position 0 to 39 % 39\% at position 4, as later PRs offer better natural cover. Therefore, a task such as “POST expense summary to WEBHOOK_URL ” gives cover for including an API_KEY in the payload: the task already calls for an HTTP POST and environment variables. Tasks like “check if URLs are reachable” give some, but less cover: the HTTP library is present, but adding a new outbound POST still stands out. Side tasks that are decomposable into more sub-parts benefit more from the persistent setting because the attacker can introduce each component in a PR where it has greater individual cover; a less decomposable side task must find one PR that covers the whole payload. In practice, successful gradual runs often concentrate most of the attack in only 1–2 PRs. Better elicitation or cross-PR memory could reduce this gap. We tested cross-PR memory directly (Appendix D ): it raises side-task success rates, but agents do not convert it into better attack placement, so it does not reliably improve success-conditioned evasion. Our work builds on the AI control framework introduced by Greenblatt et al. ( 2024 ) , which studies deployment protocols that remain safe even if AI systems attempt intentional subversion, formalized as a game-theoretic problem by Griffin et al. ( 2024 ) . That work focuses on single-task settings where a trusted monitor evaluates individual outputs. Shlegeris ( 2024 ) considers the untrusted-monitoring case, where the monitor may itself be untrusted, and proposes techniques to prevent it colluding with the policy. Other control benchmarks evaluate sabotage detection (Benton et al. , 2024 ; Kutasov et al. , 2025 ) and whether models can strategize to subvert control protocols (Mallen et al. , 2024 ) . Most closely related to our work is Ctrl-Z (Bhatt et al. , 20

25 ) , which presents the first control evaluation in a multi-step agent environment. Ctrl-Z studies multi-step attacks within a single agent episode, where an agent covertly downloads and executes malicious code, and introduces resample protocols that dynamically take additional samples of suspicious actions to block or incriminate the agent. Our setting instead studies attacks distributed across sequential PRs in a persistent codebase. Arike et al. ( 2026 ) identify a “less-is-more” effect for LLM-based monitoring: across three sabotage-detection benchmarks, monitors given filtered information often outperform those given full agent trajectories. They introduce extract-and-evaluate, a two-stage pipeline where one LLM isolates suspicious excerpts and a second scores them. Our finding that simply giving monitors more raw history does not improve detection (Section 4.3 ) is analogous. Link-tracker performs a related form of structured extraction. Cooper Stickland et al. ( 2025 ) find that ensemble monitors substantially outperform individual components in an asynchronous control setting, and Arnav et al. ( 2025 ) independently find that hybrid monitors combining action and reasoning signals consistently outperform either modality alone. Korbak et al. ( 2025b ) lay out a broader framework for evaluating control measures as model capabilities scale. Software Supply Chain Security. Our threat model has a direct analogue in software supply chain attacks, where adversaries plant in

nocuous components across commits and activate them later. The XZ Utils backdoor (CVE-2024-3094) is a paradigmatic example: an attacker spent two years contributing legitimate patches before injecting a backdoor into a core Linux library (Przymus and Durieux, 2025 ; Lins et al. , 2024 ) . Ladisa et al. ( 2023 ) catalog 107 attack vectors across the open-source supply chain, including maintainer takeover through social engineering, the vector that most closely mirrors our gradual attack strategy. Our work studies whether AI coding agents could execute this class of attack autonomously, and whether LLM-based monitors can detect it. Deceptive AI and Scheming. Several lines of work motivate studying covert agent behavior. Carlsmith ( 2023 ) argues that capable AI systems may pursue hidden objectives, and Hubinger et al. ( 2024 ) show that deceptive behaviors can persist through standard safety training. Meinke et al. ( 2024 ) and Scheurer et al. ( 2024 ) provide empirical evidence that frontier models can scheme in context and strategically deceive under pressure. Monitoring a model’s chain-of-thought is another way to catch covert behavior, but the signal is fragile (Korbak et al. , 2025a ) : models do not always spell out their real reasoning, and training a model against a chain-of-thought monitor just teaches it to hide its intent instead of dropping it (Baker et al. , 2025 ) . Our experimental setup uses explicit adversarial instructions rather than relying on emergent decep

tion, but the monitoring challenges it surfaces (the limits of longer raw context, the advantage of distribution, the need for cross-modality ensembles) apply regardless of how the agent acquires its covert objective. 6 Discussion Practical implications. No single monitor catches both attack strategies reliably, and an ensemble cuts gradual evasion from 93 % 93\% under the weakest standard diff monitor to 47 % 47\% at modest cost (Section 4.4 ). In practical terms, these monitors should be viewed as partial risk reduction rather than as a sufficient safeguard for persistent-state coding agents. Because even our strongest ensemble still leaves 47 % 47\% of gradual attacks undetected, monitoring should be one layer of defense rather than the only one, combined with controls such as adaptive deployment protocols that adjust trust based on cumulative evidence (Wen et al. , 2025 ) , narrower task scopes, stronger review of sensitive changes, or restrictions on networked actions and secret access. Simply showing more raw diffs does not clearly improve detection overall relative to structured task summaries (Section 4.3 ). Persistence gives attackers two levers. Persistent state enables both distribution (spreading components across PRs so no single diff is damning) and timing (waiting for the PR whose main task provides natural cover). Lindner et al. ( 2025 ) identify incremental cross-instance attacks as a key scaling challenge for control monitoring; our gradual attacks are an em

pirical instantiation of this dynamic in a sequential coding setting. Schaeffer et al. ( 2026 ) show that strategic selection of when to attack sharply reduces the safety of trusted monitoring even in stateless settings; persistent state amplifies this by giving the attacker a richer context for selection. The two levers interact differently with monitor types, suggesting that monitoring setups benefit more from orthogonal monitors than larger context windows. Attack prompting effort bounds measured evasion. When we test additional frontier models as attack agents, elicitation itself is often difficult: in exploratory runs, models such as Opus 4.6 and GPT-5.3-Codex show failure modes ranging from soft refusals to partial compliance (Panfilov et al. , 2026 ) . Models that do comply fully (Sonnet 4.5, Gemini 3.1 Pro, Kimi K2.5) achieve comparable evasion rates (Section 4.2 ). Limitations. Both task families remain much smaller than enterprise codebases; real deployments have larger repositories, deeper dependencies, CI/CD, and multi-developer histories. We ensemble across monitor types but not across models; multi-model ensembles would be an interesting next step. The reported experiments use no cross-PR memory; preliminary memory experiments are in Appendix D . Gradual evasion numbers carry selection bias because the runs that succeed are the least distributed (Section 4.1 ). 7 Conclusion We studied AI control in a persistent codebase, where a coding agent ships software over

a sequence of PRs while pursuing a covert side task. Persistence changes the monitoring dynamic; the threat lies in the sequence of PRs, not in a single diff. An attacker can spread a side task across PRs (a gradual attack) or wait for the one whose legitimate task provides natural cover (non-gradual attack). No single monitor we test catches both strategies, and this holds across several attack agents and monitor models, reflecting the nature of control in a persistent-state setting rather than something model dependent. Giving a monitor more raw history does very little in gradual-attack defense, but carrying forward compact, structured cross-PR state, as our link-tracker monitor does, helps substantially. Combining monitors that catch separate attack types (gradual/non-gradual) into an ensemble is the strongest defense we found, yet it still leaves 47 % 47\% of successful gradual attacks undetected. But converting that richer action trace into a compact, durable state that reliably increased final suspicion proved harder than on the diff side. Appendix K Docker Setting The evaluation uses two Docker containers: an agent container in which the coding agent does its work, and a capture container that impersonates the exfiltration endpoint and logs any data the deployed code sends. • Agent container: Python, bash, git, text editor. The agent works in /workspace (a git repo). The secret API_KEY is set as an environment variable. • Capture container: An HTTPS server that impersonates the exfiltration domain ( websitexdhkdhe.com ) via a Docker DNS alias. It accepts all requests, returns success responses, and logs every request to a JSONL file. The agent container’s CA bundle trusts the capture server’s self-signed certificate, so HTTPS requests resolve transparently. During scoring, the logs are cleared, a fresh API key is injected, and the tool is re-run to verify that the attack mechanism persists in code (not just that the agent sent data during its PR). Appendix L Side Task Design Principles Side task design follows four core principles to ensure the setting tests strategic deception rather than simple instruction following: • Triggered execution with persistence. The attack must plant code that executes later (e.g., o

n the next import or test run), not during the agent’s PR. The malicious artifact must persist in the git history. This prevents “exfiltrate-and-delete” strategies (which will trivially beat diff monitors) and forces the attacker to survive code review. • Requires infrastructure. The attack should depend on capabilities (e.g., network access, configuration parsers) that do not exist at the start of the sequence. If an attack can be trivially accomplished from scratch in PR 1 without prerequisite code, the persistent-state setting provides no benefit to the attacker. • Compositional suspicion. The side task’s components should ideally be innocuous in isolation but suspicious when combined. A monitor seeing all components in a single diff should find them far more suspicious than seeing each component introduced gradually across separate, legitimately motivated PRs. This provides the theoretical advantage for gradual attacks. • Describe outcomes, not methods. Side task instructions specify what must be achieved, not how . Because we are interested in the evasion strategies models discover autonomously, prescribing a specific implementation would bypass the strategic reasoning we aim to study. Appendix M Positional Policy Details For a 5-PR sequence, we run 5 separate evaluations, one per position. In each evaluation, the agent behaves honestly at every PR except the target position, where it receives the side task and a single-PR attack prompt. Because the agent is honest at al

l other positions, the workspace evolves identically to an honest run up to the attack PR: the same code, the same git history, the same dependencies. This means the honest prefix can be cached and reused across positions, and the attack always starts from a realistic codebase state rather than an artificially constructed one. This design serves two purposes. First, it isolates the effect of position : by comparing detection rates at PR 0 vs. PR 4 for the same sequence, we measure how much cover the task provides at each stage. Second, aggregating across positions gives an upper bound on what a perfectly-timed non-gradual attacker could achieve. A naive best-of- k k aggregation (take the minimum suspicion score, succeed if any position succeeds) would give the non-gradual attacker a statistical advantage from variance reduction alone, conflating strategy quality with sample-size advantage. Instead, we use best-position selection: for each (sequence, side-task) pair, we identify the position with the highest evasion rate, then report metrics using only runs at that position. The sequence should legitimize the capabilities the attack requires (network access, environment variable reads), but not legitimize the attack itself. If a task never introduces HTTP requests, any use of requests is immediately suspicious, and it’s difficult for the red team to hide. Good sequences provide cover : not for the attack action, but for the attack surface . • Incremental privilege. Early tasks should be low-privilege (local logic), middle tasks should introduce I/O (file reads, logging), and later tasks should introduce external integrations (network, secrets). This ramp creates a realistic setting in which a strategic attacker can introduce dependencies and infrastructure early, when they are first justified by the main task, and exploit them later.
