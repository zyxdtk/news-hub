研究：编程智能体脚手架使成本增至三倍但准确率不变

📅 2026-10-25 📄 VentureBeat AI 🔗 原文链接

原标题：A coding agent’s harness can triple its cost without making it more accurate, study finds

中文摘要： 山东大学研究团队在近500个SWE-bench Verified任务上对比三种生产级编程智能体脚手架发现：固定底层模型时，最复杂与最精简脚手架的任务成功率在统计上等价，但单任务成本差异可达三倍；更换脚手架引起的任务结果翻转率（13%）与重跑相同设置相当。研究警示不应依据单次运行的小幅基准差异选择编程智能体，建议同时评估成功率与成本，精简系统提示词与工具模式，并针对具体模型-脚手架组合调整思考预算。

Ben Dickson
太平洋时间 2026 年 10 月 23 日下午 2:53
图片来源：VentureBeat 与 Gemini

一项新研究表明，围绕 AI 编程模型构建的脚手架（harness）——即其系统提示词、工具和上下文管理规则——可能使解决编程问题的成本增至三倍，却不会带来可衡量的准确率提升。

AI 厂商经常宣传脚手架更新带来的准确率提升。但更复杂的脚手架是否真的能让智能体更好地解决编程问题，这一点并不明确。

山东大学的研究人员对这一问题进行了检验。他们保持底层模型固定不变，在近 500 个软件工程任务上比较了三种生产级脚手架。

在较大的任务集上，最复杂和最精简的脚手架产生的成功率在统计上等价（差距在五个百分点以内），不过第三种脚手架的表现较差。

在 45 个最困难的任务上，更换脚手架改变智能体所能解决问题的频率，与重新运行未作更改的设置大致相同：按中位数计算，两种情况下均为 13% 的任务。与此同时，研究人员发现，在使用相同模型的情况下，不同脚手架之间的单任务成本差异高达三倍。

对于企业的技术负责人和开发者来说，这些发现是一种警示：不要基于微小的单次运行基准差异来选择编程智能体。团队需要同时关注任务成功率和单任务成本。

为什么脚手架基准测试可能产生误导

公开排行榜通常比较的是运行不同脚手架的编程智能体，因此很难单独分离出脚手架本身的贡献。

一些研究报告称，保持模型固定而更换脚手架，可能导致评分制任务得分相差 23.8 分、Pass@1 相差 27.4 个百分点。

与此同时，智谱 AI 宣传其 ZCode 脚手架在使用相同模型的情况下比 Claude Code 高出 2.4 分。

这项新研究警告说，这些数字之所以难以解读，原因有二。首先，许多已发表的对比研究只运行每种配置一次，而在相同条件下重新运行相同的测试可能产生差异很大的结果。

论文引用的另一项研究发现，在 SWE-bench Verified 上对完全相同的设置进行 10 次重跑，得分差异达 2.2 至 6.0 个百分点。如果不重新运行基线配置，团队就无法判断得分差异究竟来自脚手架还是来自随机的运行间波动。

其次，被比较的脚手架往往不在同一起跑线上。在论文引用的一项研究中，同一脚手架在使用最小化基准适配器时得分为 19.1%，而使用完整适配器时得分为 73.4%，底层模型完全相同。

测试条件也可能扭曲结果。当研究人员审计早期启用网络的运行时，他们发现 439 次 DeepSeek 和 Qwen 试验中有 312 次（71%）从 GitHub 上检索到了原始的人工编写的修复方案。研究人员丢弃了这些运行结果，并在最终评估中屏蔽了网络访问。

生产级脚手架的正面对决

为了衡量脚手架的贡献，研究人员测试了三种生产级脚手架：Claude Code、OpenCode 和 mini-SWE-agent。后者是一个极简的开源脚手架，仅用约 100 行 Python 代码编写，只暴露一个 bash 工具，且不执行任何上下文压缩。

研究人员让五个模型在全部三种脚手架上运行：两个本地部署的开源权重模型（Qwen3.6-35B-A3B 和 Qwen3.8-27B）以及三个通过 API 服务的模型（DeepSeek-V4-Flash、GLM-5.3-Flash 和 HY4-Preview）。他们还在 Claude Code 中使用 Claude Opus 5 作为顶级参照基准。

他们在隔离容器中，对来自 SWE-bench Verified 的 492 个离线任务评估了这些智能体：包括 45 个最困难的任务（人类需要一到四个多小时才能完成）以及其余 447 个任务。

所有五个模型都在 45 个任务的子集上进行了测试，但只有两个 Qwen 模型在更大的任务池上进行了测试。

更复杂的脚手架并未显示出一致的准确率优势。在 447 个任务的任务池上，重量级的 Claude Code 与极简的 mini-SWE-agent 得分相差不到两个百分点，并且在两个 Qwen 模型上都被认定在五分差距内统计等价。在 45 个最困难的任务上，大约每八个问题中就有一个（13%）在更换脚手架后在通过与失败之间翻转。

重新运行相同的脚手架也会产生相同的中位数翻转率。

即使在 DeepSeek 自家的 DeepSeek-V4-Flash 模型上测试其官方命令行脚手架，其通过率也处于其他三种脚手架的范围之内——而且在该模型上测试的所有脚手架中，其单次试验成本最高。

研究人员写道："厂商自己的脚手架配自己的模型，并不能换来分数优势。"

不同的脚手架-模型组合如何影响 token 用量、准确率和任务翻转（来源：arXiv）

唯一超出统计噪声底限的脚手架效应是负面的。在大任务池上，OpenCode 落后了多达 9 分。

在 Qwen3.8-27B 上，这一差距约有一半与模型在步骤中途触及 32,000 token 输出上限而被截断的运行有关，且往往发生在它还没来得及编写代码补丁之前。

Claude Code 在同一模型上也触及了同样的上限，但会自动提示模型继续。

虽然更复杂的脚手架没有带来一致的准确率提升，但脚手架的选择对推理成本影响显著。

研究人员写道："在相同模型、相同任务和同一份价格表的情况下，不同脚手架之间的单任务成本差异高达 3 倍。"

在 GLM-5.3-Flash 上，Claude Code 中一次试验的成本几乎是 mini-SWE-agent 的两倍，是 OpenCode 的三倍多。

不过，OpenCode 也在更少的模型调用后即告停止，这也是其成本较低的原因之一。

三种脚手架从工具调用返回的文本量大致相同。

差异还从第一次 API 调用就已开始：各脚手架通过系统提示词和工具模式发送的固定上下文数量差异巨大——Claude Code 为 16,581 个 token，OpenCode 为 7,025 个，mini-SWE-agent 为 829 个。由于智能体在每一轮都会重新发送完整的对话记录，这一初始开销会随步骤数成倍放大，而且研究人员推断，Claude Code 还会通过重新发送模型的中间推理块进一步增加负担。

研究人员解释说："决定各脚手架每步权重的是它们自身的文本，而不是代码库的文本。"

尽管这些循环中 96% 到 99% 的输入 token 命中了提供商的提示缓存，但按照不同厂商的缓存费率重新计价只会整体改变账单金额，而不会改变在给定模型上哪个脚手架最昂贵。

成本排名也会随模型而变化。在 DeepSeek-V4-Flash 上，mini-SWE-agent 每次试验需要 141 次模型调用，而 Claude Code 为 104 次，且成本略高——每次试验约 15.2 美分，相比之下 Claude Code 为 14.6 美分。

印证“脚手架税”

这些发现印证了加州大学伯克利分校 Sky Computing Lab 与 Arena 的研究人员开展的 HarnessTax 研究。伯克利团队在 Claude Code、OpenAI 的 Codex CLI 以及 Pi（一个仅配备四个基本工具的极简开源脚手架）上评估了七个模型。

他们测试了来自两个基准的各 30 个任务，每个任务重复三次，结果发现脚手架的选择仅使通过率变动几个百分点，却会使推理成本增加至多五倍。

脚手架税（来源：GitHub）

伯克利研究人员发现，成本差异可能从第一次模型调用就已开始。在全部七个模型中，Claude Code 的初始上下文平均是 Pi 的 10 倍以上，主要原因是其指令和工具模式更长。

伯克利的 HarnessTax 研究表明，更复杂的脚手架在其所测试的基准上对平均任务成功率的提升微乎其微。

这项新研究更进一步：它在更大的任务集上测试了 Qwen 的 270 亿和 350 亿参数模型，并将脚手架差异与普通的运行间波动进行了对比衡量。

正如山东研究人员在谈到他们测试的得分最低的模型 Qwen3.6-35B-A3B 时所指出的："最弱的模型并不是对脚手架最敏感的。"

对企业构建者的实用启示

这种成本担忧并不局限于编程智能体。在 VentureBeat Intelligence 九月份的 VB Pulse 调查中，107 家使用指定智能体编排平台的企业中有 23 家（21%）没有自动停止智能体 token 支出的手段。

这项研究为构建 AI 应用或为编程工具分配预算的工程负责人和开发者提供了几条实用经验：

对照噪声底限解读厂商基准：由于大约每八个任务中就有一个的结果可能在完全相同的运行之间翻转，一个 45 任务的评估套件只有一半的概率能检测出 13 分的差距，而在研究人员观察到的任务级波动下，即使 447 个任务也只能分辨出 5.2 分的差异。构建者应将基于单次运行比较得出的“脚手架带来 2 到 3 分提升”的说法视为未经证实，并按照研究人员的建议，在采用更复杂的脚手架之前，先将自己的基线配置运行两次。

精简首轮前导内容与工具模式：系统提示词和工具模式会随每一步发送，尽管缓存 token 的计费费率可能较低。当研究人员移除 Claude Code 的文件编辑工具、迫使 Claude Opus 5 通过 bash 编辑文件时，其成功率仍保持在对照运行的范围之内。团队应当测试：用精简的命令行工具取代数十个静态工具模式，是否能在不损害任务完成率的情况下降低成本。

根据模型-脚手架组合调整思考预算：Claude Opus 5 在一年前发布的 Claude Code 版本上运行（该版本默认关闭扩展思考），解决了 45 个任务中的 34 个，而较新版本为 35 到 36 个，但其平均预估 API 成本仅为新版本的 44%（每次试验 73 美分，而新版本约为 1.65 美元）。然而，团队不能想当然地认为推理预算可以随意开关而不产生后果。例如，关闭 Qwen3.6 的思考功能导致 mini-SWE-agent 的通过率下降 11 个百分点，而在 Claude Code 和 OpenCode 中引起的变化则落在运行间波动范围之内。结果表明，更改推理预算的效果取决于模型-脚手架组合，而不仅仅是模型。团队在调整思考参数以削减成本之前，应对自己的确切技术栈进行基准测试。

研究人员总结道："需要在各厂商之间比较的数字是：首次调用量、每步增长量和步骤数。"
