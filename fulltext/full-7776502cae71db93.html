摘要。
技术文档是为人类开发者编写的，但现在越来越多的软件变更由自主编码智能体编写。这些智能体会查阅哪些文档、何时查阅以及之后做什么，目前仍不得而知。我们对智能体与文档的交互进行了一项基于行为的研究，结合了两个互补的公开数据集：来自 SWE-chat（Baumann 等 2026）的 557 个真实智能体编码会话，从中我们提取了 94,813 个开发事件，包括 3,033 次文档交互；以及来自 AIDev（Li 等 2026）的 33,097 个智能体拉取请求，我们对其中的 690,260 条文件级变更记录进行了分类。四项发现挑战了当前文档实践背后的假设。首先，智能体的文档工作以面向智能体的产物为主：智能体指令文件和智能体工作笔记占所有文档交互的 60.5%，而经典技术文档占 10.6%，API 参考文档占 1.3%。其次，查阅与代码编辑之间的关联仍悬而未决：相邻转移概率为 0.002，未调整的三事件提升度为 1.05，而阶段调整模型将该关联置于 1 以上（OR 1.33 [1.09, 1.62]）。相反，文档创建在未调整分析中有所升高（提升度 1.67），但其调整后的区间包含 1。第三，未观察到明确的基于文档的验证序列，且查阅与较少的即时测试相关（提升度 0.23，聚类 CI 0.08–0.45；调整后 OR 0.39 [0.25, 0.60]）。第四，文档查阅绝大多数是主动发起的（70.2%），远高于失败驱动（7.5%），且文档滞后于代码而非引领代码：在同时更改两者的多提交拉取请求中，先触碰代码的频率比先触碰文档高 4.7 倍。从这些痕迹中，我们推导出了一个智能体与文档交互的描述性模型，该模型呈双叶循环而非线性旅程的形式，并且我们展示了“智能体友好”文档的两个被广泛假设的属性——可操作性和可验证性——在此语料库中缺乏一致的行为支持。我们发布了我们的提取流水线、编码方案和事件级数据。

1.
引言
软件文档研究传统上关注单一受众：人类开发者。文档质量框架、陈旧度指标和可读性指南都预设了一个会形成意图、感到困惑并询问同事的读者。这种预设不再总是成立。开源领域中相当大且不断增长的一部分代码变更是由自主编码智能体编写的，它们在没有人类参与每个步骤的情况下阅读存储库、执行命令并打开拉取请求。
如果智能体现在是文档消费者的一个重要类别，那么文档设计应该基于智能体实际做的事情。目前，缺乏此类证据是因为它们的行为尚未被测量。关于“智能体友好”文档的新兴指南——编写清晰的标题、提供可运行的示例、发布 llms.txt——依赖于对智能体应该如何表现的直觉，而不是对它们实际如何表现的观察。
本文采取了相反的路线。我们没有提出文档质量并询问智能体是否受益，而是观察了真实开发会话中的智能体行为，并从这些观察中推导出文档启示。我们提出三个研究问题：
RQ1 智能体用文档做什么？
在任务的哪个阶段，通过哪些行为，查阅哪种文档类型？
RQ2 文档交互之前和之后发生了什么？
哪些事件触发了查阅，哪些开发操作在之后更有可能或更不可能发生？
RQ3 代码与文档的循环是双向的吗？
智能体是否消费和生产文档，以及相对于代码的顺序是什么？
我们的回答在四个方面偏离了该领域的工作假设，而且偏离很大，而非微不足道。
主要的文档类型是全新的。
我们原本期望智能体查阅 API 参考、架构文档和故障排除指南。相反，60.5% 的观察到的文档交互针对的是因智能体而存在的产物：指令文件，如 AGENTS.md 和 CLAUDE.md（35.4%），以及智能体工作笔记——计划、thoughts/ 目录、头脑风暴、验证日志（25.1%）。API 参考文档作为大多数文档工具的焦点，仅占交互的 1.3%；故障排除文档占 0.4%。
从阅读到编码的联系尚未解决。
通常假设的模式——阅读文档，然后编写代码——在相邻转移层面上几乎不存在：P(edit code | read doc) = 0.002。在三事件范围内，未调整的提升度在会话基准率之上为 1.05，而阶段调整后的估计值高于 1（OR 1.33 [1.09, 1.62]）。文档阅读之后最常见的反而是推理（0.245）或进一步的文档阅读（0.270）。
未观察到明确的基于文档的验证。
我们没有观察到将文档明确用作检查代码的预言机的实例。此外，阅读文档与较少的即时测试（提升度 0.23）和构建（提升度 0.15）相关。
文档作为输出几乎与作为输入一样频繁。
生产（1,401 个事件）的发生率是查阅（1,615 个事件）的 0.87 倍，且 41.5% 的智能体拉取请求更改了文档。然而，在时间上方向是不对称的：代码先于文档的频率比相反情况高 4.7 倍。
我们的贡献包括： 跨两个数据集和两个分析单元的智能体文档交互的行为特征； 发布的提取流水线，针对数据集自身的工具调用计数进行了评估，该流水线从四种异构智能体记录格式中恢复文档事件（文档类型分类器本身未经人工验证）； 经验推导的交互模型，用双叶循环取代了假设的线性旅程； 文档设计启示，每个启示都与特定的测量相关联，并附有我们的数据不支持的常见断言启示的明确列表。
2.
相关工作
五条文献线索汇聚在本文中，每一条都基于一个我们的数据所挑战的假设：智能体或开发者查阅的文档是为人类编写的、与代码相关的，并且是由他人生产的。前四条线索揭示了这种张力；第五条确立了方法论先例。
2.1.
编码智能体和基于 LLM 的软件工程智能体
该领域的评估 apparatus 将智能体的任务定义为问题解决。SWE-bench 根据智能体的补丁是否通过测试来对其评分（Jimenez 等 2023），而为在此基准上取得成功而构建的架构通过其在文件和 shell 上的动作空间来描述（Yang 等 2024；Wang 等 2024b；Zhang 等 2024）。调查按任务类型映射了智能体能力，但未将文档作为一个类别纳入（Liu 等 2024；Wang 等 2024c）。由于没有基准奖励文档工作，证据必须来自观察数据。无智能体流水线可以在没有探索性阅读循环的情况下匹配智能体流水线（Xia 等 2025）；因此我们关于阅读主要导致进一步阅读和推理的发现（第 4 节）描述的是智能体做了什么，而不是它们必须做什么。
两条观察性研究提供了最接近的先例。轨迹研究在动作序列层面比较了成功和失败的运行（Majgaonkar 等 2025；Mehtiyev 和 Assunção 2026），激发了我们的转移分析，尽管两者都没有将文档编码为产物类别。产物研究挖掘智能体编写的拉取请求：采用率（Robbes 等 2026）、随时间的活动（Popescu 等 2026）、PR 描述特征（Watanabe 等 2026）、重构（Horikawa 等 2025）、日志记录（Ouatiti 等 2026）和失败原因（Ehsani 等 2026）。日志研究提供了一个有用的模板：它询问智能体是否以与人类相同的方式处理非功能性关注点。我们针对文档提出了相应的问题，并测量了一个以前未报告过的数量：智能体生产文档的频率是其查阅频率的 0.87 倍（第 4 节）。智能体求助已被基准化为向人类升级，而不是查阅产物（Trinh 等 2026）；我们对主动发起和失败驱动交互的区分没有先前的基线。
2.2.
LLM 之前的软件文档研究
在 LLM 出现之前进行的研究提供了最清晰的比较点。观察到的人类开发者更严重依赖代码和同事而不是文档（Roehm 等 2012；Maalej 等 2014；Ko 等 2007），围绕陈旧度进行选择性查阅（Lethbridge 等 2003），将需求表述为任务型问题（Sillito 等 2006；Sillito 等 2008），并在网络上搜索外部信息（Sadowski 等 2015；Xia 等 2017）。理解消耗了开发者的大部分时间（Xia 等 2018），而文档并未作为其主要输入。与该基线相比，文档交互发生在我们超过一半的抽样会话中（56.7%），并且主要是主动发起的（70.2%）——这是文档工程研究一直试图在人类开发者中鼓励的行为（Forward 和 Lethbridge 2002；Garousi 等 2015；Zhi 等 2015）。
更尖锐的对比在于查阅哪种文档。这些文献以 API 参考为中心：是什么让 API 难以学习（Robillard 2009），API 文档如何失败（Uddin 和 Robillard 2015），网络上存在多少（Parnin 和 Treude 2011），如何按任务导航（Treude 等 2015）。质量分类法是从这些产物类型构建的（Aghajani 等 2019；Aghajani 等 2020），而 README 分类法关注面向人类的部分（Prana 等 2018）。我们的分布反转了这种重点：API 参考占智能体文档交互的 1.3%，故障排除文档占 0.4%，而 60.5% 涉及面向智能体的文档（第 4 节）。提高 API 参考质量能改善查阅者结果的假设可能对人类成立，但在我们的数据中，API 参考仅占可观察的存储库本地查阅的 2.3%。关于入职障碍的研究（Steinmacher 等 2015）和文档创建的研究（Dagenais 和 Robillard 2010）为我们的生产与消费分析提供了人类比较点。
2.3.
代码与文档的协同演化
AIDev 组件建立在成熟的共变文献基础上，这些文献记录了持续存在的问题：注释更新代码的频率低于应有水平（Fluri 等 2007；Fluri 等 2009），不一致性很常见且与缺陷相关（Tan 等 2007；Wen 等 2019；Ibrahim 等 2012），注释在重构时静默失效（Ratol 和 Robillard 2017），文档链接衰减（Hata 等 2019）。我们将共变挖掘传统中的方法（Zimmermann 等 2005）应用于文件级的智能体 PR。由此得出两个观察结果。首先，相对于该文献中报告的人类注释维护率，41.5% 的文档变更率很高。其次，在顺序可观察的情况下，文档滞后于代码，再现了自动化注释更新工作所预设的不对称性（Panthaplackel 等 2020）。当该文献考虑根据代码检查文档时，检查是由静态分析器执行的（Zhong 和 Su 2013）；它不假设智能体会执行检查，这与我们未观察到此类事件一致（第 4 节）。
2.4.
LLM、文档和智能体上下文文件
检索研究将文档视为模型输入：检索改进了代码生成（Zhou 等 2022；Wang 等 2024a），存储库级检索也是如此（Zhang 等 2023；Zhang 等 2025）。这些文献最直接地编码了我们的发现所挑战的假设：文档作为代表模型注入的可检索 API 参考是有价值的。我们数据中的智能体反而打开了它们被告知要遵循的指令文件和它们自己写的笔记；这些交互是主动发起的，而不是外部检索的。
2025–2026 年关于上下文文件的新兴文献探讨了这些产物，但其结论仍未定论。描述性研究将 AGENTS.md 和 CLAUDE.md 表征为产物（Chatlatanagulchai 等 2025a；Chatlatanagulchai 等 2025b；Mohsenimofidi 等 2025）。相关工作报告了存储库内容的基础率（Hora 等 2026）并检查了计划产物（Abubakar 等 2026），这是与我们工作笔记类别最接近的现有类似物。有效性的证据好坏参半：报告了效率提升（Lulla 等 2026），任务级结果不一（Gloaguen 等 2026；Khatri 2026），以及发现随机规则与精心策划的规则一样有帮助（Zhang 等 2026）。维护研究报告了陈旧度（Treude 和 Baltes 2026）并记录了无限增长（Chakrabarti 2026）；通过智能体动作管理上下文已成为一种技术（Liu 等 2025）。这些工作都没有测量智能体相对于它们阅读的其他所有内容，查阅这些文件的频率。我们 35.4% 的指令文件和 25.1% 的工作笔记数据提供了该分母，相互冲突的有效性发现促使我们以描述性方式报告这些数据。
2.5.
方法先例
软件事件日志的过程挖掘已确立（van der Aalst 等 2012；Poncin 等 2011），开发者 IDE 交互流的序列挖掘也是如此（Damevski 等 2017；Kersten 和 Murphy 2006；Ashraf 等 2019）。我们编码方案的人工验证被我们确定为必要的下一步（第 7 节），将遵循既定的可靠性 apparatus——具有常规区间的 Cohen's kappa（Cohen 1960）（Landis 和 Koch 1977），或 Krippendorff's alpha（Krippendorff 2004），遵循既定指南报告（McDonald 等 2019；Seaman 1999）。我们在此不报告此类统计数据。我们的主要区间是聚类自助法；Wilson 区间（Wilson 1927）仅作为假设独立性的参考出现；我们依赖于它们在小计数和零计数时的行为（Brown 等 2001）。
3.
研究设计
3.1.
数据集
我们使用两个具有互补分析单元的公开数据集。两者都无法单独回答我们的问题：SWE-chat 记录了开发过程但没有合并结果，而 AIDev 记录了产物但没有保留工具使用轨迹。
SWE-chat（Baumann 等 2026）包含由使用几种命令行智能体工具的开发者贡献的真实智能体编码会话。每个会话包括完整的记录，包含用户消息、智能体消息、工具调用、工具结果和代码变更。该发布版包含 5,850 个带记录的会话（10.4 GB）；我们抽样了 559 个（第 3.2 节）。该数据集是我们过程证据的来源：它回答了 RQ1 和 RQ2，并为 RQ3 提供了会话内的证据。
AIDev（Li 等 2026）包含编码智能体在公共 GitHub 存储库上打开的拉取请求，包含提交、文件级差异、审查和时间线。完整语料库包含跨 116,211 个存储库的 932,791 个 PR；我们使用作者策划的子集，即来自 2,807 个超过 100 星的存储库的 33,596 个 PR，以及其文件级提交详情表。以下所有 AIDev 数据均源自该子集，因此我们明确报告了过滤步骤。
提交详情表在删除 5,132 行空文件名行（0.72%）后产生了 711,923 行文件 × 提交记录；排除第三方路径又删除了 16,531 行（2.32%），剩下跨 278,192 个唯一路径的 690,260 行，其中 29,597 个是文档路径。在 PR 层面，33,596 个 PR 中的 33,097 个保留了至少一个命名的非第三方文件（98.5%）；被排除的 499 个中，16 个没有文件级行，475 个只有空文件名，8 个只有第三方文件。该数据集提供了我们的产物证据，并大规模回答了 RQ3。
这两个数据集描述了相关但不同的人群。因此，我们将它们用作互补来源而不是交叉验证，并且从不合并它们的分​​析单元。
3.2.
抽样
我们从 SWE-chat 中抽取了一个按智能体和会话长度分层的样本，跨越四个长度层级（轮次计数 ≤ 3，4–8，9–18，> 18），使得琐碎或病态的会话都不会占主导地位。我们对少数派智能体进行过采样以允许特定于智能体的估计，并排除大于 25 MB 的记录（语料库最大值：61.8 MB）。样本为 559 个会话，其中 557 个产生了可解析的事件。由于分配是非比例的，智能体级别的统计数据单独报告，从不合并。
3.3.
文档识别
我们使用存储库相对文件路径的两级分类器来操作化“文档”。
第一级是确定性的。文件名和路径规则分配 15 种文档类型之一和两个正交标志。machine_readable 标志识别 OpenAPI、JSON Schema 和 Protobuf 产物，它们既用作 API 文档又用作可执行规范。vendored 标志识别第三方路径，智能体可能会读取它但存储库并不拥有它。非文档文件在 {source, config, test, data, build, other} 中接收一个 kind，因此单个函数同时支持文档识别和共变分析。
第二级解决模棱两可的路径。第一级将 54% 的文档事件放在一个残余类别中。由于这个类别太大而无法悬而未决，我们用语言模型对其 527 个不同的路径进行了分类：500 个被标记，覆盖了 98.4% 的模棱两可事件，27 个使用关键字回退规则分配。这一级揭示了 agent_working_note 作为一个我们初始方案中没有的大的、独特的类别。
两个决定值得强调。首先，我们没有编码交互目的，尽管它出现在我们的初始方案中。目的无法从工具调用日志中恢复，从文件读取中推断意图是无法证伪的；我们报告触发器、交互类型和结果。其次，第三方路径被标记而不是删除：阅读 node_modules/pkg/README.md 是真正的文档交互，即使存储库不拥有它。
3.4.
事件提取
SWE-chat 使用四种不兼容的记录格式，我们通过检查它们的结构识别了这些格式。
在抽样的 559 个会话中，406 个使用带内容块工具调用的行分隔 JSON，100 个使用带 parts 数组的单个 JSON 文档，43 个使用 {type, payload} 事件日志，10 个使用 messages 数组。两个会话没有产生事件并被排除，留下 557 个分析样本。
每种格式的单独提取器发出一个基于 20 符号字母表的通用模式，跨越文档和非文档动作，因此文档事件保留在其原始轨迹上下文中。
两个提取细节实质性地影响了结果，如果不报告可能会使此类研究产生偏差。首先，通过 shell 路由文件操作的智能体将编辑表示为 apply_patch here-documents，其目标路径仅出现在命令文本中；如果不解析这些路径，一个智能体家族将记录到零个文档事件。其次，工具输出在某些格式中作为字符串到达，在其他格式中作为列表或字典到达。支持这些额外类型恢复了 9 个会话和 4,358 个事件，包括 77 个文档事件。
我们提取的工具事件计数在六个抽查会话中的五个中与 SWE-chat 自身的 tool_call_count 完全匹配。
3.5.
编码方案和派生测量
每个文档事件沿四个维度编码：文档类型（15 个规则类别加上第 4 节中的两个新增）；交互类型（发现、搜索、阅读、编辑、创建）；触发器，使用四事件回溯；结果，使用工具输出中的成功和失败信号。开发阶段遵循轨迹启发式：第一次写入前为定向，第一次写入起为实现，通过测试或构建后为验证，失败信号后为调试，版本控制活动占主导时的最后一次写入后为交付。每个事件保留其证据字符串，因此标签是可审计的。
对于 RQ2，我们报告相对于基准率的提升度而不是原始条件概率，因为在整个会话中常见的动作也会在查阅后频繁出现。我们将文档查阅（阅读、搜索或发现；n=1,615 锚点）三个事件内动作的概率与同一会话中每个非锚点事件估计的相应概率（n=93,198；此基线包括文档编辑，它们不是查阅锚点）进行比较。
观察范围。
我们的工具观察存储库本地、基于文件的文档交互：目标解析为存储库路径的工具调用，加上罕见的显式文档检索调用。它不观察通过浏览器阅读的 API 网站、模型权重中已有的知识或源代码中的文档字符串。运行时在会话开始时加载的上下文文件仅在智能体稍后显式读取或编辑它们时才可见，因此指令文件计数是暴露的下限。所有声明都涉及这个可观察的切片。
交互循环阶段的操作化。
表 10 中的候选阶段构成了对相同事件的第二个、更粗略的编码。它们并不互斥，因此计数总和不为 3,033。每个都是一个可观察的模式：
• Orient：定向阶段的事件（第一次写入前）。
• Discover：分类为搜索或发现的事件（282+5）。
• Retrieve：阅读（1,328）加上文档工具调用（16），代表检索而不是文件读取——因此是 1,344。
• Interpret：紧接着推理的阅读或搜索。
• Revisit：紧接着另一次阅读的阅读。
• Apply：随后对记录的产物进行编辑或读取的阅读。
• Recover：第一个恢复动作是阅读文档的失败情节（109）。
• Contribute/Update：交互类型编辑或创建（1,401）。
• Validate：随后进行测试或构建运行的阅读。
• Escalate：随后向用户请求的阅读——不同于表 4 中的九个 Ask user 恢复动作，后者跟随失败。
3.6.
统计处理
由于样本是故意非比例的，我们在三种加权方案下报告主要比例——合并事件、会话相等和将会话重新加权到语料库智能体分布（表 8）。第三种仅纠正智能体级别的过采样：样本按智能体和会话长度分层，并且长度层级的人口边际无法从发布的索引中恢复，因此我们不提出联合层级估计。
由于事件嵌套在会话中且拉取请求嵌套在存储库中，观察结果不是独立的伯努利试验——仅最大的 AIDev 存储库就贡献了 8,911 个拉取请求。因此，我们使用聚类自助法（2,000 次重采样）获得我们的主要不确定性估计，对 SWE-chat 重采样整个会话，对 AIDev 重采样整个存储库。我们使用固定种子计算百分位区间（提升度为 13，转移为 11，比例为 7），并且每次重采样从聚类内计数的总和中重新计算合并比例。对于 RQ2 动作窗口，我们还拟合了一个逻辑 GEE（可交换工作相关，按会话聚类），调整了开发阶段、会话内位置、对数会话长度和智能体家族，因为查阅在轨迹阶段中分布不均；我们报告调整后的关联以及未调整的提升度，而不是取代它。表 6 将聚类区间与假设独立性的 Wilson 区间进行比较；聚类加宽了每个区间，在 AIDev 方面高达 14 倍。Wilson 区间作为假设独立性的参考保留在每次分析的表格中，但不是我们的主要估计。
我们不应用对检查的层级数量的校正，因此不解释相邻层级之间的微小差异。

4.1.
RQ1：文档类型、任务阶段和交互行为
4.1.1.
任务阶段
文档交互分布在整个轨迹中，而不是集中在任务开始时。按开发阶段，54.4% 的文档事件发生在调试期间，27.2% 发生在实现期间，15.2% 发生在定向期间，3.0% 发生在验证期间，0.1% 发生在交付期间。
阶段启发式是粘性的：一旦出现失败信号，会话将保持在调试阶段直到测试或构建通过，从而膨胀了该份额。因此，我们只提出稳健的负面主张：文档查阅不限于定向阶段。因此，将文档纯粹视为任务开始活动的模型与我们的观察不一致。跨阶段的分布不应被解释为精确的分配。
4.1.2.
文档类型
表 1 展示了完整的分布，这是本文的核心实证结果。两个类别的面向智能体文档占主导地位。
智能体指令文件——包括 AGENTS.md、CLAUDE.md、SKILL.md 以及 Cursor 和 Copilot 的规则文件——占 1,074 个事件（35.4%）。智能体工作笔记——计划、thoughts/ 目录、头脑风暴和智能体为自己使用编写的审查日志——占 760 个（25.1%）。这两个类别合计占 3,033 个事件中的 1,834 个，即 60.5%。
因此，我们的主要对比是在面向智能体的产物（60.5% 的事件，会话聚类 95% CI 53.9–66.5%；在智能体重加权下为 55.1%）和所有其他存储库文档（39.5%；在智能体重加权下为 44.9%）之间。
作为次要对比，处于文档研究传统核心的九种体裁占 323 个事件（10.6%）。这个边界是有争议的：添加 README、配置和需求文档会将份额提高到 33.8%。因此，除了极端类别之外，我们不提出任何主张：API 参考占 40 个事件（1.3%），而预期作为调试资源的故障排除文档占 11 个（0.4%）。
agent_working_note 类别在我们的初始方案中并不存在。它从未解析路径的第二级分类中出现，这些路径主要由智能体编写的计划和推理文档主导。这些文件是否算作技术文档是一个我们明确做出的定义选择：我们将它们作为关于软件的持久散文产物包含在内，这些产物被提交到存储库并可被下一个参与者阅读，但我们始终将它们单独报告，以便以不同方式划定边界的读者可以重新计算每个份额（排除它们，仅智能体指令文件就是 2,273 个事件中的 1,074 个，47.2%）。

4.1.3.
交互行为
我们观察到五种交互类型：阅读（1,328 个事件）、编辑（1,007）、创建（394）、搜索（282）和发现（5）。在剩余的 17 个事件中，12 个是失败的工具调用，5 个不适合任何交互类型。这些事件带有文档类型和触发器标签，并贡献于这些分布，但不贡献于交互类型统计。生产（编辑 + 创建 = 1,401）的发生率是查阅（阅读 + 搜索 + 发现 = 1,615）的 0.87 倍。
我们初始方案中的三种交互类型未被证实：比较（将两份文档相互对照阅读）、跟随引用（在文档之间导航链接）和验证（根据文档检查代码）。这些可能发生在模型推理内部，我们的工具无法看到，但它们没有作为工具调用行为出现，因此我们删除它们而不是将它们报告为罕见的。
最常见的循环转移如下（会话聚类自助法 95% CI；2,000 次重采样）。
P(read doc | read doc) = 0.270 [0.232, 0.307],
P(reasoning | read doc) = 0.245 [0.205, 0.295],
P(edit doc | read doc) = 0.107 [0.081, 0.132],
P(edit doc | edit doc) = 0.350 [0.288, 0.404].
第一个估计表明文档阅读是连续发生的，而不是孤立的。
在相邻转移层面，通常假设的模式——阅读文档，然后编写代码——几乎不存在：
P(edit code | read doc) = 0.002 [0.000, 0.005].
这个估计代表在 1,328 次文档阅读中出现了三次。阅读之后更有可能跟随推理或进一步阅读，而不是立即编辑代码。

5.1.
痕迹衍生的描述模型：双叶循环
转移结构显示了两个松散耦合的活动叶。
查阅叶（Orient → Discover → Retrieve → Interpret）在内部是循环的：其最强的转移是 Retrieve 回到自身，为 0.270（CI 0.232–0.307），其最强的向外出转移是到推理，为 0.245（CI 0.205–0.295）。因此，智能体在此叶内循环，并比进入即时动作更常进入推理。
生产叶包含比任何其他阶段都多的文档事件。未调整的分析表明从查阅进入此叶的关联：文档创建在查阅后升高（提升度 1.67）。然而，其阶段调整后的区间包含 1（表 3）。
两个连接在规格上都不一致。未调整的估计对于查阅 → 文档为 1.67，对于查阅 → 代码为 1.05；相应的调整后 OR 为 1.41 和 1.33。文档区间仅在调整前排除了 1，而代码区间仅在调整后排除了 1。失败很少馈入查阅叶（5.4% 的失败情节），并且在记录的工具调用痕迹中没有观察到的边从任一叶进入验证。
因此，我们修改后的描述不是从信息需求到验证实现的流水线。相反，智能体与文档的交互是一个循环的查阅过程，它产生推理和进一步的文档，并且仅与很大程度上独立的代码修改过程松散耦合。
5.2.
为什么与人类开发者的差异很重要
人类信息寻求文献经常描述开发者查阅文档、应用他们学到的东西并检查结果——我们的线性模型编码的循环。在我们的痕迹中，智能体执行第一步，但未观察到检查步骤，并且文档创作以可测量的速率跟随查阅。
两种机制似乎可以解释这一点；区分它们需要未来的工作。
智能体可能将推理外化到文件中，因为它们的上下文窗口是有限的，使得文档成为一种工作记忆而不是参考；计划和 thoughts/ 目录的突出与这种可能性一致。或者，它们可能不根据散文进行验证，因为更便宜的预言机，即测试套件，被直接调用。在任一情况下，我们都没有观察到散文作为规范起作用。
6.
对文档设计的启示
我们仅在特定测量支持的情况下陈述启示，并单独列出我们的数据不支持的该领域常见断言的启示。第二个列表与第一个同样重要：这项研究提供了关于其中几个问题的初步行为证据，但不支持一些广泛重复的建议。
6.1.
支持的启示
智能体指令文件是最常用的文档表面。
它们是最常用的文档类型（1,074 个事件，35.4%），并且是智能体拉取请求中最常更改的文件之一。相比之下，API 参考收到 40 个事件（1.3%）。指令文件接收的交互大约是 API 参考的 27 倍。对于分配有限文档资源以支持智能体贡献者的项目，这种差异表明应优先考虑指令文件的正确性和清晰度。
本地可检索性值得特别关注。
文档阅读经常跟随进一步的阅读（转移概率 0.270），而 Follow-reference 完全未被证实。这种模式激发了研究具有本地可检索结构的自包含文档，而不是假设智能体导航丰富交叉链接的文档。然而，它并没有确立链接卫生没有行为后果。
智能体编写的文档创建了新的维护表面。
文档创建在查阅后具有 1.67 的未调整提升度，尽管阶段调整后的区间包含 1。智能体工作笔记占所有文档交互的 25.1%。我们测量了它们的体积和修改，而不是它们的维护成本、陈旧度或不一致性。计划、thoughts/ 目录和验证日志作为持久产物在存储库中积累。存储库卫生工具、代码审查清单和文档质量指标目前没有针对它们的类别。
可执行文档提供了通往规范的可测试途径。
未观察到明确的基于文档的验证序列，并且查阅与较少的即时测试相关（提升度 0.23，聚类 CI 0.08–0.45）。使这种检查可观察可能需要智能体可以执行的产物——可运行的示例、doctest、模式契约——而不是必须信任智能体会遵守的散文。这个提议是干预研究的假设，而不是本研究的发现。
文档很少作为第一个恢复资源出现。
它是在 2,034 个失败情节中的 109 个（5.4%，聚类 CI 3.8–7.3%）中的第一个恢复动作，而故障排除文档在整个语料库中仅占 11 个事件。无论故障排除指南对人类开发者有何价值，它们都不是此处观察到的智能体恢复行为的突出部分。
6.2.
我们的数据不支持的启示
可操作性。
关于文档应以便智能体可以直接对其采取行动的方式编写的声明，预设了阅读 → 行作的耦合。相邻转移概率为 0.002，未调整的提升度为 1.05，而调整后的 OR 为 1.33 [1.09, 1.62]。可操作性可能仍然是可取的，但这些分析没有为该耦合提供一致的行为证据，并且我们的观察设计无法显示提高可操作性会改变行为。
可验证性。
关于文档应以便智能体可以根据它验证其工作的方式编写的声明，没有描述任何观察到的行为：零验证事件。因此，不能仅通过诉诸在此语料库中观察到的行为来证明可验证性的合理性。
文档作为失败恢复。
将文档定义为智能体卡住时求助于的主要资源的框架，既不受触发器分布（7.5% 失败驱动）的支持，也不受恢复分析（5.4% 的情节）的支持。
恢复策略排名。
我们明确拒绝得出基于文档的恢复更有效的结论，尽管它具有最高的点估计（63.6%）。由于只有 11 个情节具有可观察的结果，区间跨越 35.4–84.8% 并与所有替代方案重叠。
6.3.
对于数据集和工具构建者
两个测量观察概括了本研究之外的内容。首先，通过 shell 命令路由文件操作的智能体将其文件访问隐藏在命令字符串中。任何仅基于工具名称的语料库分析都会系统性地低估此类智能体，并且跨智能体比较将反映提取覆盖率而不是行为。其次，面向智能体的文档对 2024 年之前构建的文件类型分类法是不可见的。任何没有 agent_instruction 和 agent_working_note 类别的文档分类器都会将大多数智能体文档交互放在残余桶中，就像我们在添加它们之前所做的那样。
7.
效度威胁
7.1.
建构效度
文档由文件路径识别。
文档字符串、内联注释和嵌入在源文件中的散文对我们的工具是不可见的。这系统性地低估了文档工作，并且低估是非均匀的：偏爱源代码内文档的语言和项目代表性不足。因此，我们的绝对比率是下限。比较发现——面向智能体与项目文档、阅读与编写——只有在源代码内文档在这些类别中的分布与路径识别的文档非常不同时才会受到影响，我们无法排除这种情况。
目的未测量。
我们的初始方案包括一个目的维度。我们删除了它，因为目的无法从工具调用日志中恢复：文件读取与许多意图兼容，而分配一个将是无法证伪的。我们报告触发器、交互类型和结果。因此，根据设计，我们不分析智能体阅读特定文档的原因。
第二级标签未验证。
agent_working_note 类别——占文档事件的 25.1%，并且是我们的主要发现之一——依赖于对 500 个模棱两可的路径（98.4% 的模棱两可事件）的语言模型分类，其中 27 个路径回退到关键字规则。尚未对这些标签进行人工验证。必要的下一步是对 200–300 个事件的子样本进行双人人工编码，使用 Cohen's κ 或 Krippendorff's α 测量评估者间可靠性。在此之前，该类别的确切份额应被视为暂定的。智能体编写的工作文档构成一个大的且以前未分类的类别的定性发现比其确切大小更稳健，因为它在原始路径中可见。
7.2.
内部效度
阶段分配是一个粘性启发式。
一旦出现失败信号，会话将保持在调试阶段直到测试或构建通过。这膨胀了调试份额。我们只提出负面主张（文档不限于定向），并且不将阶段分布解释为精确的分配。
结果检测使用工具输出上的正则表达式。
当输出不包含可识别的指示符时，我们的成功/失败信号缺失，而缺失不等于失败。解决率仅为 2,034 个具有可观察结果的情节中的 662 个计算。如果没有可观察结果的情节与可观察的情节系统性地不同，则解决率将受到我们无法量化的选择效应的影响。
转移概率是一阶的。
从文档阅读到代码编辑的接近零的相邻转移并不排除更长范围的影响。三事件范围提升度分析是我们的缓解措施；其未调整的估计显示没有关联（提升度 1.05），尽管调整后的模型显示有（OR 1.33 [1.09, 1.62]）。更长范围的影响，或通过我们无法观察的推理介导的影响，将不会被任一分析检测到。
触发器分配使用固定的回溯。
触发器使用四事件窗口分配。由该窗口之外的事件提示的文档阅读最有可能被错误地归因于智能体主动性，这是我们最大的类别，因此也是最容易受到此错误影响的类别。
7.3.
提取保真度
我们针对数据集独立计算的 tool_call_count 验证了提取；计数在六个抽查会话中的五个中完全匹配。提取器处理四种记录格式。我们在研究期间识别并修复了两个缺陷：未能解析 shell 嵌入的路径，这导致一个智能体家族似乎没有文档事件；以及未能处理非字符串工具输出，这排除了九个会话。这两个缺陷都是通过不合理的结果而不是专门的测试检测到的。对于以 shell 为中心的智能体，可能仍然存在残余低估，因此我们将每个智能体的比率报告为不同紧密度的下限，而不是直接可比较的估计。
7.4.
外部效度
SWE-chat 是选择性加入的遥测。
这些会话由使用智能体 CLI 的开发者贡献，并且 87% 的语料库来自单个智能体家族。选择共享的开发者可能比智能体用户群体更有经验、更以开源为导向，或者正在处理更可共享的任务。
AIDev 包含早期采用智能体的公共存储库。
它过度代表了接受智能体贡献的项目。
这两个数据集都不一定能推广到私有代码库。
文档实践、审查规范和智能体配置在私有环境中可能都不同。
这两个数据集不代表同一人群。
我们将它们用作关于过程和产物的互补证据；我们从不合并它们的单元，它们之间的一致性证实了一种模式，但并不构成测量的交叉验证。
语料库是快速移动实践的快照。
面向智能体的文档约定大约有两年历史，并且正在变化。特定的 60.5% 份额表征了此快照，而不是稳定的常数；我们期望持续存在的发现是该类别的存在和突出，而不是其确切大小。
7.5.
统计效度
主要不确定性估计是具有 2,000 次重采样的聚类自助法区间——对 SWE-chat 统计数据重采样会话，对 AIDev 重采样存储库——通过固定种子的百分位法计算，每次重采样从聚类内计数的总和中重新计算合并比例。Wilson 区间仅作为假设独立性的参考伴随它们。转移和提升度区间使用相同的会话级过程。我们不应用跨检查的层级（智能体、语言、任务类型、星标桶、结果）的多重比较校正，因此相邻层级之间的微小差异不应被过度解释；我们不基于这种差异得出主张。在单元格较小的情况下，我们陈述此限制并避免得出结论，如恢复策略排名（n=11）。
8.
结论
我们测量了编码智能体在 557 个真实智能体会话和 33,097 个智能体拉取请求中如何与技术文档交互。主要发现是智能体开发产生了一种文档研究尚未研究的体裁：智能体指令文件和智能体工作笔记，它们合计占观察到的文档交互的 60.5%，并且由智能体编写的频率几乎与阅读的频率一样高。当前工具和质量框架针对的文档类型——API 参考和故障排除文档——分别占交互的 1.3% 和 0.4%。
三个假设的机制未得到数据的一致支持。查阅与后续代码编辑之间的关联仍悬而未决：未调整的估计显示没有升高，而阶段调整后的估计显示有。文档很少是第一个失败恢复资源：它是在 2,034 个失败情节中的 5.4% 中的第一个恢复动作。最后，未观察到明确的基于文档的验证序列，这意味着可验证性——一个被常规描述为面向智能体文档所期望的属性——对应于我们的工具未记录的任何行为，因此必须被设计而不是被假设。
实际启示是努力的重新分配：改进智能体指令文件有可能比在 API 参考散文上的同等工作更频繁地触达智能体。研究启示是文档现在有两个具有可测量不同行为的受众，而较新的受众编写的几乎和它阅读的一样多。
数据和材料可用性
这两个数据集都是公开的。SWE-chat 是受限的，但在接受其 ODC-BY 条款的前提下可免费获取；我们使用了 2026 年 8 月 19 日的快照，包含 5,851 个会话。其中，5,790 个带有来自至少 20 个会话的六个家族之一的智能体标签，并构成智能体重加权的基础；其余 61 个包含 52 个没有智能体标签的会话和 9 个来自较小家族的会话。AIDev 可公开下载；我们使用了其策划的子集。
复制包包含四种特定于格式的提取器和 20 符号事件字母表；所有 527 个模棱两可路径的第一级路径规则和第二级标签；带有证据跨度的 3,033 个编码交互的事件级表；带有固定种子的聚类自助法和 GEE 脚本；以及图表生成代码，它直接从分析输出中生成每个表，因此没有表格值是手工转录的。
