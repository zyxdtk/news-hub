Reva：基于大语言模型上下文探测的实时漏洞检测

📅 2026-10-26 📄 arxiv 🔗 原文链接

原标题：Reva: Real-Time Vulnerability Detection through Contextual Probing of Large Language Models

中文摘要： Reva 是一种实时 AI 漏洞检测器，将安全上下文与代码理解整合到 LLM 单次前向传播中。它为每个新函数提供预计算威胁模型、静态分析结果和调用图，由训练好的探针读取 LLM 内部表示输出风险分数。在 PrimeVul 测试集上，基于 GLM-5.3-Flash 的 Reva 以每函数约一秒达到 60.0% 准确率，与最先进的智能体检测器 VulTriage 相当，但快逾 250 倍、成本不足其十分之一。结果表明 LLM 内部表示已编码智能体推理所得的大部分漏洞信息。

Reva：通过上下文探测大语言模型实现实时漏洞检测

作者： Amine Lbath、Massih-Reza Amini

单位： 法国格勒诺布尔阿尔卑斯大学（Université Grenoble Alpes）、法国国家科学研究中心（CNRS）

摘要

漏洞在软件生命周期中被发现得越晚，修复成本越高。随着编码智能体生成代码的速度超过开发者审查代码的速度，软件需要一道更强的第一道防线，在每个新函数生成时对其进行实时筛查。LLM 智能体近来已能够像安全专家那样工作，发现真实世界的漏洞：它们运行分析工具、探索周围代码、测试假设并权衡证据，然后形成自己的判断。然而，这种推理跨越多次模型调用，导致每个判定需要数分钟的计算时间，远远无法跟上代码生成的速度。更快的基于 AI 的检测器（微调深度学习模型或提示 LLM 直接给出判定）的准确性则低得多：它们在没有智能体所收集上下文的情况下判断函数，而且先前的工作已证明，即使提供了部分上下文，LLM 生成的判定也不可靠。

我们提出 Reva（REal-time Vulnerability Analysis，实时漏洞分析），这是一种 AI 漏洞检测器，它将智能体检测器背后的安全上下文与代码理解组件整合到 LLM 的单次前向传播中。对于每个新函数，Reva 为 LLM 提供其模块的预计算威胁模型，以及轻量级静态分析结果和调用图信息。Reva 不要求 LLM 给出判定，而是让训练好的探针读取 LLM 在此上下文中对该函数的内部表示。在 PrimeVul 的保留测试集上，基于 GLM-5.3-Flash 的 Reva 在每个函数约一秒内达到 60.0% 的准确率。这与在同一 LLM 上运行的文献中最先进的函数级智能体检测器 VulTriage（59.2%）相当，同时速度快 250 倍以上，成本不到其十分之一。在相同提示下，探针比 LLM 自身的直接判定准确率高 14% 至 17%。在三个开源 LLM 上，Reva 至少与 VulTriage 一样准确，且在其中两个上准确率高约 10%。这些结果表明，LLM 的内部表示已经编码了智能体检测器通过推理获得的大部分信息。

索引词： 漏洞检测、大语言模型、内部表示、探测、编码智能体

I 引言

漏洞在软件生命周期中被发现得越晚，修复成本越高 [1]。因此，在编写代码的同时检测到漏洞时，修复成本最低。编码智能体如今生成代码的速度已超过开发者审查的速度，这就需要一道第一道防线，在每个新函数生成时对其进行实时筛查。

静态分析器可以实时运行，但在智能体生成代码的规模下，它们产生的报告数量超过开发者的审查能力，其中许多是误报 [2, 3]。LLM 智能体近来已能够通过将此类工具与自身对代码的分析相结合来发现真实世界的漏洞 [4, 5]，而智能体检测器将这一方法应用于函数级检测。VulTriage [6] 是函数级检测文献中最先进的方法，VulAgent [7] 用检索到的漏洞知识和程序事实来丰富提示，VulTrial [8] 则让多个智能体就判定进行辩论。然而，这种推理跨越多次模型调用，相当于每个函数需要数分钟。更快的基于 AI 的检测器（微调深度学习模型或提示 LLM 直接给出判定）降低了这种延迟，但准确性要低得多 [9, 10, 11]。

Reva 旨在弥合速度与更高准确性之间的差距。Reva 不让 LLM 通过多轮工具调用收集上下文，而是将上下文组装进提示，包括函数所属模块的威胁模型、其静态分析结果、其调用图及其文件。随后，LLM 在单次前向传播中处理该提示而不生成文本，由一个在带标签函数上训练的小型探针将其对代码 token 的内部表示映射为风险分数，而非通过推理得出判定。后一选择基于如下证据：LLM 编码了其答案未表达的知识，例如关于陈述真实性 [12, 13, 14] 或其自身答案正确性 [15, 16] 的知识，以及思维链解释并不总是忠实于底层计算 [17]。

我们在 PrimeVul [9] 上评估 Reva，这是一个高质量的漏洞 C 与 C++ 函数数据集，每个漏洞函数与同一函数的良性版本配对，涵盖 651 个项目和 121 种漏洞类型（CWE）。在其保留测试集上，基于 GLM-5.3-Flash [18] 的 Reva 与 VulTriage 相当，且比在同一 LLM 上运行的 VulAgent 更准确，每个函数约一秒，比 VulTriage 快 250 倍以上。在另外两个开源 LLM 上，它比两个智能体检测器都准确 9% 至 13%。

本文做出三项贡献：我们提出 Reva，一种将针对性安全上下文与 LLM 内部表示探针相结合的漏洞检测器，每个函数只需单次前向传播； 我们将其与在相同三个 LLM 上运行的最先进函数级智能体检测器在 PrimeVul 保留测试集上进行比较，从准确性、成本和鲁棒性三方面评估； 我们概述了一个研究议程，朝着这样的检测器发展：在编码智能体生成每个函数时进行筛查，并将可能的漏洞升级给更强大的智能体以构建漏洞证明。

II 背景与相关工作

基于 LLM 的漏洞检测。 非智能体设置下的 LLM 通常难以区分漏洞函数与其良性对应版本：在 PrimeVul [9] 上，带思维链的 GPT-4 仅在 12.9% 的配对中将两个版本都正确标记，而在非智能体设置下被要求给出判定的 LLM 对安全问题的推理常常不一致 [19, 20]。Reva 则读取 LLM 的内部表示，而非其答案或推理。

智能体检测器。 最近的检测器通过添加知识和推理步骤来提高准确性。VulTriage 检索 CWE 描述并将控制流与数据流事实语言化 [6]；VulAgent 让专门的智能体针对项目代码提出并验证假设 [7]；VulTrial 在智能体之间组织辩论 [8]。它们的成本随每次调用而增长，且其上下文可能超出 LLM 的上下文窗口。Reva 则将此上下文的关键部分预加载到提示中，并用单次被探测的前向传播替代多步推理。

探测 LLM 内部表示。 探针是在模型隐藏状态上训练的小型分类器 [21]。对于代码，线性探针表明在玩具数据集上具有一定的区分安全与不安全代码的能力 [22, 23]，并能预测生成的代码是否不安全或不正确 [24, 25]。这些探针仅读取代码本身，而 Reva 探测的是在针对性安全上下文中读取的真实世界函数。

漏洞基准的陷阱。 检测器可能利用数据集的虚假特征，例如与漏洞无关的代码度量或语义 [26, 27]。这样的检测器倾向于用相同的标签分类漏洞函数及其良性对应版本，因为两者共享这些特征。因此，我们对每个函数独立评分，然后检查每对中的两个版本是否获得了正确的标签。

III Reva 的上下文探测

在 Reva 中，LLM 在一次前向传播中读取新函数及其安全上下文，探针将代码 token 的隐藏状态映射为风险分数（图 1）。

① 带安全上下文的提示。 提示包含新函数及其周围的上下文，分为带标签的部分（图 1）。威胁模型由 LLM 智能体工作流对整个软件按项目构建一次，描述项目（摘要、攻击者控制的输入、信任边界）以及包含该函数的模块（角色、到达它的输入、典型的汇聚点与防护措施）。提示还添加了该函数的 Semgrep [28] 发现、其调用位置及其所调用辅助函数的签名，以及用 tree-sitter 从存储库中提取的其文件的包含、类型、宏和同级函数。该上下文可用于 84% 的训练函数；否则提示仅包含函数及其 Semgrep 发现。提示的中位数为 3,840 个 token，其中 601 个为代码。

② 单次前向传播。 LLM 在一次前向传播中处理提示，该传播在四个被探测层中最深一层之后停止，因此其余层永远不会运行，也不生成任何输出 token。我们探测中间层，探测研究通常发现这些层信息量最大 [21]：从 LLM 深度的 38% 到 85% 之间均匀间隔的四层，通过交叉验证选择。

③ 代码 token 状态。 在每个被探测层，Reva 仅保留函数 token 的隐藏状态。每个状态被归一化并投影到 1,024 维，然后将四层拼接起来。

④ 注意力探针。 一个具有 8 个注意力头的探针将 token 状态汇聚成一个风险分数。它有 0.57M 参数，在 PrimeVul 的训练函数上训练。其损失函数将逐函数分类项与将每个漏洞函数排在其良性对应版本之上的排序项相结合。这些配对仅用于训练：Reva 对每个函数独立评分。

实际使用。 LLM 和 Semgrep 的规则在启动时加载一次，因此无需为每次新分析重新启动，每个项目的威胁模型提前构建。对于每个新函数，Reva 提取其上下文、运行 Semgrep、构建提示、运行前向传播并应用探针。在单个 H200 GPU 上使用 Muse-Glimmer-30B 时，每个函数耗时 0.93 秒，其中 0.46 秒用于上下文提取。

  • RQ3： Reva 的哪些部分重要，其准确性对泄漏和选择是否鲁棒？

IV-A 实验设置

数据集与指标。 PrimeVul [9] 将每个漏洞 C/C++ 函数与同一函数的良性版本配对。它包含 3,789 个训练对、480 个验证对和 435 个测试对。遵循 [9]，我们统计两个版本都被正确标记（P-C）、都被标记为漏洞（P-V）、都被判定为良性（P-B）或标签反转（P-R）的配对数量。我们的主要指标是所有函数的准确率，每个函数独立评分。

协议。 我们仅在训练集和验证集上做出所有设计选择。交叉验证（CV）准确率涵盖训练集的五折（同一提交的所有函数位于同一折），以及由在完整训练集上训练的探针评分的验证集。测试集在开发期间保持未见状态，仅用最终配置进行评分。

LLM。 我们使用三个开放权重 LLM：Muse-Glimmer-30B [29]、Qwen3.8-27B [30] 和 GLM-5.3-Flash [18]，后者是一个更大的混合专家模型。在 GLM-5.3-Flash 上，智能体检测器使用 LLM 的 FP8 版本，而 Reva 使用精确的 BF16 转换，这使其交叉验证准确率保持不变（66.2% 对 65.9%）。

基线。 我们在其发布的代码上运行 VulAgent 和 VulTriage，使用与 Reva 相同的 LLM。当检测器未返回判定时，该函数视为失败，通常是因为推理超出了 token 限制。我们在所有函数上比较所有方法，将失败函数计为良性。已发表的 GPT-4o 结果仅作参考。

IV-B RQ1：准确性

在 GLM-5.3-Flash 上，Reva 达到 60.0% 的准确率（95% CI [57.8, 62.2]），而在同一 LLM 上运行的 VulTriage 为 59.2%，VulAgent 为 52.8%（表 I）。在所有测试函数上，Reva 比 VulTriage 高 0.8 个百分点（CI [−2.1, +3.8]），比 VulAgent 高 7.2 个百分点（CI [+4.4, +10.3]）。在 Qwen3.8-27B 和 Muse-Glimmer-30B 上，Reva 比两个智能体检测器都准确 5.1 至 6.7 个百分点，且所有四个置信区间均不包含零。

除准确率之外，当两者在同一 LLM 上运行时，Reva 与最先进的函数级智能体检测器 VulTriage 相比也表现更优。在所有三个 LLM 上，Reva 的误报率（FPR）更低，标签反转的配对（P-R）更少，且在其中两个 LLM 上完全正确标记的配对（P-C）更多。因此，Reva 不仅在准确率上匹配或超过 VulTriage，而且能更可靠地区分漏洞函数与良性函数，这表明探针捕获的是漏洞本身，而非漏洞函数与其安全对应版本共享的表面特征。

图 2 总结了这种权衡。在每个 LLM 上，Reva 至少与两个智能体检测器一样准确，同时快 100 到 6,000 倍。其准确率在不同 LLM 之间的变化也很小，仅为 1.1 个百分点，而 VulTriage 为 5.6 个百分点，因此 Muse-Glimmer-30B 上的 Reva 与 GLM-5.3-Flash（VulTriage 表现最好的 LLM）上的 VulTriage 相当。由此可见，探针读取的信号在所有三个 LLM 中都存在，而智能体检测器的准确性则取决于每个 LLM 对代码的推理能力。VulTriage 在 GPT-4o 上报告了更高的准确率（63.6%），但我们无法复现这些结果。

RQ1 的回答： 从单次前向传播来看，Reva 在所有三个 LLM 上匹配或超过两个函数级智能体检测器。在六次同 LLM 比较中的五次中，它显著更准确，且在每个 LLM 上的误报都少于 VulTriage。

IV-C RQ2：计算成本

端到端来看，Reva 每个函数耗时 0.88 至 1.33 秒，而在相同 LLM 上的智能体检测器为 108 至 5,614 秒。虽然这些在并行负载下测得的时间夸大了单请求延迟，但 token 数量证实了这一差距。Reva 每个函数读取约 3,100 至 3,400 个 token 且不生成任何 token，而智能体检测器处理的 token 多 3 至 70 倍，其中许多是生成的。由于 Reva 需要 LLM 的隐藏状态，它无法在 API 后面运行。在租用的 H200 GPU 上，它筛查 1,000 个函数花费 0.9 至 1.3 美元，而按相同 LLM 的公共 API 费率，VulTriage 为 9 至 61 美元，VulAgent 为 63 至 307 美元。

RQ2 的回答： Reva 约一秒筛查一个函数，而智能体检测器需要数分钟，在相同 LLM 上成本低 10 至 360 倍，且为每个函数返回分数。

IV-D RQ3：消融与鲁棒性

我们在 Muse-Glimmer-30B 验证集上对 Reva 的每个组件进行消融（图 3）。在相同提示上要求同一 LLM 给出是/否判定（而非探测它）会将准确率降至随机水平。在测试集上，它比探针低 7.4 至 8.7 个百分点，而单独使用 Semgrep、Cppcheck 和 Flawfinder 也处于随机水平（50.8% 至 51.3%）。因此，LLM 的内部表示携带了其判定和静态分析结果均无法单独提供的信息。在探针内部，用 token 状态的简单平均替换注意力池化会使准确率降低 4.2 个百分点，这表明漏洞的证据存在于少数 token 中。使用单层、省略标准化或去掉排序项会使准确率降低 0.4 至 1.5 个百分点，移除存储库上下文或仅保留函数分别降低 1.0 和 1.9 个百分点，这些均不显著。在 PrimeVul 的短函数上，仅函数本身就携带了大部分信号；我们预期上下文对过程间漏洞更为重要。

评估数据上的泄漏和选择可能会夸大探测结果 [21, 31]。当没有项目同时出现在训练和评估折中时，交叉验证准确率仅下降 1.3 至 2.7 个百分点，因此探针所学的大部分内容可以迁移到未见过的项目。同样，仅在训练折上（而非所有开发数据上）选择四个被探测层，准确率变化不到半个百分点，因此层选择不会夸大结果。然而，测试集上的准确率比交叉验证低 6 个百分点（GLM-5.3-Flash 上为 60.0% 对 66.2%）。由于 PrimeVul 按时间顺序划分数据，这一差距可能反映了向较新代码的偏移，而交叉验证未能捕捉到这一点。

RQ3 的回答： 探针是必不可少的。同一 LLM 的直接判定降至随机水平，用 token 状态的平均替换注意力池化损失 4.2 个百分点，而存储库上下文在 PrimeVul 上没有显著影响。准确率在未见过的项目上基本保持。

V 未来计划

步骤 1：完成比较。 我们将在更大的开源 LLM 上运行两个智能体检测器和 Reva。我们还将测试在简短的自生成分析之后读取内部表示是否能增加信息。
成功标准： Reva 在相同 LLM 上在每个规模上都匹配或超过它们。

步骤 2：编码智能体中的校准筛查。 我们将学习依赖于项目和函数的阈值，并将 Reva 集成到编码智能体循环中，仅将高风险函数升级给智能体检测器或漏洞证明检查 [32]。
成功标准： 在给定的升级预算下，该循环比单独的智能体检测器发现更多漏洞。

步骤 3：超越 PrimeVul 的泛化。 我们将在其他数据集 [33, 34, 35]、过程间漏洞 [36, 32] 以及每个 LLM 训练截止日期之后披露的漏洞上进行评估，并研究用相同目标微调 LLM。
成功标准： Reva 在 LLM 不可能见过的漏洞上保持其准确性。

VI 结论

Reva 通过在单次前向传播中探测 LLM 对函数及其安全上下文的内部表示来检测漏洞。在 PrimeVul 的保留测试集上，它匹配或超过在同一 LLM 上运行的智能体检测器，误报更少，每个函数约一秒，成本仅为其一小部分。因此，LLM 的内部表示携带了比其判定更多的漏洞信息，读取这些表示使得在编写每个函数时进行实时筛查成为可能。
