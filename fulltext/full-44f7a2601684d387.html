技能非孤岛：智能体技能供应链的依赖与风险度量

原标题：Skills Are Not Islands: Measuring Dependency and Risk in Agent Skill Supply Chains

中文摘要： 本文提出智能体技能供应链（ASSC）概念，建模技能-包-服务的混合依赖结构。作者开发了SkillDepAnalyzer（SDA）工具，从自然语言指令和代码中提取依赖证据，生成SkillBOM文档。在SKILL-DEP基准上SDA取得0.95的F1分数，优于所有基线。对143万技能的大规模分析揭示了四种结构模式：元数据治理薄弱、多通道依赖集中、递归复用导致隐藏包清单、以及依赖簇形成。安全分析表明60-98%的安全信号仅通过传递依赖传播，仅检查根技能会遗漏大量风险。

技能非孤岛：智能体技能供应链的依赖与风险度量

Changguo Jia¹, Tianqi Zhao², Runzhi He¹, Minghui Zhou¹

摘要

智能体技能为大语言模型（LLM）智能体封装了可复用的操作知识——但随着其规模不断扩大，它们已成为承载依赖的制品，其身份、版本和来源在很大程度上仍然隐含不明。这种不透明性不仅仅是带来不便：它已经在社区中表现为依赖重复和安装不一致等问题，暴露了依赖管理尚未弥合的缺口。

在本研究中，我们通过引入智能体技能供应链（Agent Skill Supply Chains，ASSCs）来研究智能体技能中包含的依赖复杂性（混合的技能-包-服务依赖），期望帮助弥合这一缺口。借鉴软件物料清单（Software Bill of Materials，SBOMs）的思想，我们设计了 SkillDepAnalyzer（SDA），用于捕获自然语言依赖证据并将技能建模为承载依赖的制品。

在 SKILL-DEP 基准测试中，SDA 准确且全面地恢复了技能元数据和完整依赖图，大幅优于基于 LLM 的基线方法和以包为中心的 SBOM 工具。我们将 SDA 应用于超过 143 万个技能，获取了 ASSC 并探索了其结构多样性和安全信号。

我们发现了四种结构模式：技能元数据具备激活就绪性但治理薄弱；依赖图跨越技能、包和服务依赖且复用高度集中；递归技能复用扩展了依赖图并创建了隐藏的包依赖清单；技能依赖簇围绕相关工作流形成。我们还发现，仅检查技能文档本身是不够的，因为安全相关信号可能隐藏在其依赖中。通过分析 ASSC，我们识别并报告了在 ASSC 中持续存在的已知恶意技能及其开发者。

基于这些发现，我们建议采用类型化依赖清单、一等公民依赖簇管理、面向技能基础设施维护者（如技能包管理器开发者和技能注册表维护者）的风险警告审计命令，以及面向技能开发者的类锁文件记录。

I 引言

智能体技能封装了可复用的操作知识，使大语言模型（LLM）智能体能够执行专业任务 [4, 28, 29]。一个典型的技能包含前置元数据、自然语言指令和代码脚本，它们共同规定了任务的执行方式。截至目前，公开可用的技能数量已达 143 万个，仅在三个月内就增长了九倍 [37]。这些技能涵盖网络、金融、数据分析和软件开发等多个领域。

为避免重复造轮子，开发者越来越多地通过复用现有技能、软件包和外部服务来组合新技能。这种广泛的复用加速了技能开发，但也引入了分层的依赖关系，将技能从孤立文件转变为承载依赖的制品。

然而，现有的依赖管理机制尚未跟上这一新兴的复用实践。技能依赖并非显式声明，而是隐含地散布在元数据、指令和脚本中。因此，开发者无法可靠地识别技能的依赖、确定其版本或追溯其来源。

最近的社区报告显示，这种不透明性已经导致了实际的依赖管理问题。Claude Code 社区的一次讨论报告称，技能以复制快照的方式分发，导致其上游仓库、路径和版本信息在提交后丢失 [34]。结果，来源追踪和可靠更新变得困难。Claudekit 社区的另一个问题报告了技能所需包依赖处理的不一致，不同情况下调用不同的包管理器，导致依赖管理行为不可预测 [17]。这些案例共同表明，管理技能依赖的系统化机制仍然缺乏。

因此，我们提出智能体技能供应链（ASSCs）来建模混合的技能-包-服务依赖结构。ASSC 是一个有向依赖图，其节点代表技能、软件包和外部服务，边代表依赖关系。ASSC 显式表示了之前隐含的技能依赖，使得追溯依赖来源、维护复用组件和审计传递性风险成为可能。

据我们所知，现有方法无法构建 ASSC。最接近的技术是传统的软件物料清单（SBOMs）[20, 31]，它从软件清单中恢复依赖。然而，这一假设对智能体技能不成立。一方面，技能依赖通常以自然语言而非机器可读清单表达。另一方面，技能涉及的依赖类型超出了传统软件包分析器的范围，包括技能间复用和对外部服务（如模型上下文协议（MCP）服务器）的依赖。

为系统化构建 ASSC，我们开发了一个名为 SDA 的自动化技能依赖分析工具。

首先，SDA 从前置元数据和技能正文中恢复直接依赖候选。其次，SDA 评估每个候选的置信度。低置信度候选作为注释保留以保持可追溯性，而高置信度候选由类型化扫描器分为三个依赖通道——技能、包和服务。第三，SDA 递归解析技能和包依赖，增量恢复传递依赖以构建 ASSC。最后，SDA 将恢复的 ASSC 序列化为技能物料清单文档，这是一种基于 SBOM 中间表示（SBOM-IR）[16] 的面向技能的表示。

值得注意的是，SkillBOM 专为技能定制，同时与现有 SBOM 标准兼容。这种兼容性使基于 SBOM 的工具链可以复用于 ASSC 分析。

借助 SDA，我们可以系统化地大规模分析技能依赖，实现对 ASSC 的大规模研究。

首先，我们构建 SKILL-DEP 基准来验证 SDA，评估其在恢复技能元数据和依赖方面的准确性和全面性。其次，我们将验证后的工具应用于 143 万个技能，刻画 ASSC 的结构模式。最后，我们检查安全相关的技能、包和服务如何通过 ASSC 暴露。

据此，我们提出以下三个研究问题。

RQ1（分析器评估）：SDA 分析技能元数据和依赖的准确性和全面性如何？

RQ2（ASSC 特征）：ASSC 具有哪些结构模式？

RQ3（安全传播）：安全相关的技能、包和服务如何通过 ASSC 暴露？

为回答 RQ1，我们构建了人工标注的 SKILL-DEP 基准来评估 SDA。在准确性方面，SDA 在单层基准上取得了 0.95 的总体 F1 分数，在三个依赖类别中均优于所有基线，并在元数据字段上达到完美准确率（1.00）。在全面性方面，它在多层基准的技能依赖图上取得了 0.95 的 F1 分数，证实了其增量 BOM 构建能力。

为回答 RQ2，我们将 SDA 应用于 143 万个技能，揭示了 ASSC 的四个结构特征，为治理建议提供了依据。

第一，技能元数据基础设施具备激活就绪性但治理薄弱。名称和描述广泛可用，但依赖、许可证和版本声明仍然稀疏。名称冲突进一步复杂化了大规技能身份解析，58.73% 的技能具有非唯一名称。

第二，ASSC 表现出多通道依赖且复用高度集中。技能依赖跨越三个通道：技能（8.92%）、软件包（15.48%）和外部服务（22.25%）。复用高度集中于一小部分技能和包，表明 ASSC 建立在狭窄的可复用核心之上。

第三，ASSC 表现出递归依赖扩展和隐藏的包清单。技能复用大幅倍增了技能的包依赖，引入了许多技能本身未显式声明的传递包。在 npm 和 PyPI 中，分别有 71.87% 和 73.33% 的包是通过技能复用继承的，对直接技能声明不可见。

第四，ASSC 形成依赖簇。总体而言，30.41% 承载依赖的根技能属于依赖簇，这些簇通常连接实现同一工作流不同阶段的技能。这些簇自然成为依赖管理和治理的高层单元。

为回答 RQ3，我们分析了安全模式如何通过 ASSC 传播。我们发现，跨技能、包和服务的安全相关信号传播存在于直接依赖之外。具体而言，60–78% 的安全相关技能依赖、98.01% 的 axios 包依赖和 93.10% 的潜在脆弱 MCP 服务依赖仅通过传递依赖继承，对仅检查根技能的审查者不可见。

利用 ASSC，我们识别了实际场景中的安全相关问题，包括 Demerzels-lab/elsamultiskillagent 仓库中恶意 clawhub1 技能的副本，并将其报告给相应开发者。

这些结果为两类群体提供了治理建议。对于技能基础设施维护者（如技能包管理器开发者和技能注册表维护者），我们建议采用类型化多通道依赖清单，区分技能、包和服务依赖，同时记录其来源和版本信息。我们还建议一等公民依赖簇管理，允许紧耦合的依赖簇作为高层单元进行声明、解析和审计。此外，技能包管理器可以提供风险警告审计命令来报告脆弱的传递依赖。对于技能开发者，我们建议维护类锁文件记录，在跨仓库复用依赖时保留固定版本和源仓库。

总之，本文做出以下贡献：

  • 我们将智能体技能供应链（ASSCs）定义为混合的技能-包-服务依赖图，并提出了一种检索和分析 ASSC 的方法。
  • 我们开发了 SDA，一种自动化分析技能依赖并输出 SkillBOM（面向技能的 BOM 表示）的工具。我们构建了 SKILL-DEP 基准，SDA 在该基准上优于所有以包为中心的 SBOM 生成器和基于 LLM 的基线。
  • 我们将 SDA 应用于 143 万个技能来刻画 ASSC 结构，揭示了激活就绪但治理薄弱的元数据、多通道且集中的依赖图、依赖扩展和隐藏包清单，以及依赖簇。
  • 我们分析了 ASSC 中的安全传播，表明仅检查根技能会遗漏传递依赖中出现的安全相关信号，包括通过 ASSC 检查发现的已知恶意技能。

II 背景与相关工作

II-A 背景

智能体技能通常是以 SKILL.md 文件为中心的制品，可选地包含脚本、引用或其他按需加载的捆绑资源 [4, 28]。先前工作将技能文档刻画为三部分制品：YAML 前置元数据、自然语言指令和代码脚本 [47]。这些部分扮演不同角色。前置元数据通常描述技能元数据信息，如名称和描述；自然语言指令解释智能体何时以及如何使用该技能；代码脚本可以编码具体操作，如包安装、API 调用或辅助脚本执行。

与传统软件包不同，技能不提供标准化的依赖声明机制。因此，依赖证据可能散布在这三个部分中的任何一个。前置元数据可能包含类似依赖的字段，如 dependencies 或 requires；自然语言指令可能提及所需的包、复用的技能或 MCP 服务器；代码脚本可能包含安装命令、导入语句、API 客户端或配置片段。

因此，技能不能仅作为纯文本提示或传统包清单来分析。依赖分析必须跨元数据、指令和代码收集证据，同时区分每个依赖指向的是包、另一个技能还是外部服务。

II-B 相关工作

II-B1 软件供应链透明度

软件供应链已经为传统软件制品提供了成熟的透明度格式和工具。SBOM 标准，如 SPDX [20] 和 CycloneDX [31]，定义了软件包的关系和元数据。生成器，如 Syft [3]、Cdxgen [32]、ScanCode [1]、ORT [30] 和 Microsoft sbom-tool [23]，通过从清单、锁文件和构建元数据中提取包依赖来支持自动化供应链可见性。

这些 SBOM 标准和工具适用于以包为中心的软件供应链，但不适用于技能。现有 SBOM 不将技能视为独立组件，也不表示技能特定的关系，如技能间复用。现有生成器还假设以包为输入，因此无法从 SKILL.md 元数据、自然语言指令和代码中恢复这些关系。这一差距促使我们开发新的技能依赖分析器 SDA 和新的输出表示 SkillBOM。

II-B2 技能复用

最近的工作将智能体技能框架化为可复用制品而非孤立提示。OpenAI 的技能文档将技能描述为智能体工作流的可复用扩展点 [29]。SkillClone 将智能体技能视为多通道制品，检测跨 YAML 元数据、自然语言指令和代码脚本的克隆关系 [47]。它表明技能克隆可以传播质量和安全问题。这些研究确立了技能被大规模复用，且复用可能带来隐藏的维护和安全成本。我们的工作研究了一种不同的关系。我们不是检测两个技能是否为克隆，而是重建技能、包和服务之间的依赖链接。这一依赖图使我们能够分析 ASSC 结构和安全相关模式。

II-B3 技能安全

技能特定的安全工作研究技能内部的风险。注册表级别的实证工作分析了第三方技能注册表，报告了已确认的恶意技能，其行为包括凭证窃取、远程代码执行和对抗性指令 [21]。市场规模的研究报告了漏洞模式，包括提示注入、数据外泄、权限提升和供应链风险 [22]。基准工作进一步测量了智能体是否遵循放置在技能文件中的提示注入 [36]。红队工作表明，非恶意技能仍可通过对抗性提示被利用 [11]。

我们的工作关注不同视角。我们分析安全相关的技能、包和服务如何通过 ASSC 变得可达。

III SkillDepAnalyzer

本节介绍我们开发的自动化 SkillDepAnalyzer 工具（SDA）。SDA 是本研究的基础设施。

III-A 概述

SDA 通过图 1 所示的流水线将技能文档转换为结构化的 SkillBOM。

首先，给定一个技能文档，SDA 从技能内容中提取根技能元数据和依赖线索。其次，SDA 评估每个候选的置信度，并将确认的依赖分为三个通道：技能、包和外部服务。第三，SDA 递归解析引用的技能和包，并记录外部服务以构建 ASSC。最后，恢复的 ASSC 被序列化为结构化的 SkillBOM。

图 1：SDA 生成工作流。

III-B 结构感知的技能解析

SDA 首先将每个技能文档分离为前置元数据和技能正文。前置元数据通常以 YAML 编写，因此 SDA 对其进行结构化分析，恢复根技能信息，如 name、version 和 description。这些字段被视为根技能身份的最高优先级证据。如果前置元数据缺失或未提供足够的元数据，SDA 回退到技能正文。分析器使用元数据关键词匹配和依赖模式匹配来补充根技能元数据，并从依赖字段、命令或自然语言提及中收集依赖线索。

III-C 证据校准的依赖分析

所有收集的线索形成初始候选依赖证据池。由于同一制品可能在不同上下文中以不同语义出现（例如，一个包可能是安装命令所需的，或仅在示例中展示），SDA 结合周围上下文和支持证据评估每个候选。确认的候选随后被分为三个依赖通道——包、技能和外部服务——而模糊的候选作为注释保留。

包依赖从包特定的证据模式中分析，包括包管理器、安装命令、清单条目和 Docker 片段。强证据，如安装命令和清单条目，直接建立包依赖边。对于较弱的包提及，如从文本描述而非显式安装指令中提取的包名，SDA 查询相应的包注册表，仅在找到精确包匹配且周围上下文支持依赖解释时才创建依赖边。否则，候选作为注释保留，使示例和故障排除文本不进入依赖图。

技能依赖需要超越名称匹配，因为技能经常被克隆或重命名。因此，SDA 使用名称和身份信息（包括仓库和路径）来解析候选技能。由仓库或路径证据确认的匹配被记录为技能依赖，而仅通过技能名称识别的候选（在运行环境或技能数据集中没有对应匹配）作为注释保留。

外部服务遵循类似的校准路径。一个技能可能假设一个 MCP 服务器、API 端点或 webhook。SDA 从自然语言指令或代码脚本中提取服务线索，并将可观察的服务使用证据记录为服务记录。

总体而言，此阶段产生根技能元数据及其第一层证据校准的依赖，涵盖直接包依赖、直接技能依赖、服务记录和注释。只有高置信度边被视为下游分析的真实依赖，而较低置信度的匹配作为注释保留。

III-D 增量 BOM 构建

此阶段以前一阶段的根技能元数据和第一层依赖为输入。SDA 首先为根技能构建种子 SkillBOM。然后通过两个依赖通道扩展种子：包通道（丰富包元数据和包级传递依赖）和技能通道（导入匹配的依赖技能及其生成的 SkillBOM）。由于服务记录主要描述外部服务，SDA 不为传递依赖扩展它们。包和技能的传递事实随后通过递归解析的包和技能依赖记录进入最终结果。

包通道将直接包依赖扩展为包级依赖图。SDA 在可用时优先使用本地运行环境的证据。SDA 扫描环境以恢复已安装的包元数据和每个包的传递依赖，然后使用这些记录构建包依赖图。如果没有可用的运行环境，SDA 回退到注册表级别的解析。当可以推断出包注册表或包管理器时，SDA 查询相应的包管理器或注册表以恢复包元数据和依赖。通过本地运行环境和包注册表，SDA 查询和验证包信息，然后构建全面的包依赖图。

技能通道从直接技能依赖开始。对于每个依赖技能，SDA 首先搜索本地运行环境，然后搜索技能数据集。使用多个身份字段匹配候选技能，包括技能名称、仓库、路径、所有者和仓库星标，较早的字段被赋予更高优先级。因此，由技能名称、仓库和路径确认的匹配被认为比仅由较弱证据（如仓库星标）支持的匹配更可靠。如果未找到精确的技能名称匹配，SDA 进一步考虑前缀和后缀名称匹配，并使用相同的排序策略对结果候选进行排序。得分最高的候选在其分数超过置信阈值时被选为解析的依赖；否则，候选作为注释保留。

选择匹配技能后，SDA 使用相同的流水线分析该技能文档以获取其元数据和技能-包-服务图，并将其生成的 SkillBOM 导入当前根结果。此导入是递归的且感知循环的。由于技能依赖簇的存在，SDA 维护一个已访问技能列表：一旦技能被添加到图中，后续对同一技能的访问将停止扩展。合并步骤规范化重复项并保留关系证据。

总体而言，此阶段将根本地的 SkillBOM 种子扩展为全面的依赖图，同时保留每个导入记录如何进入结果的信息。

III-E 结构化模式验证的 SkillBOM 输出

在此阶段，SDA 将前一阶段的依赖图转换为结构化的、模式验证的 SkillBOM，在一个机器可读对象中表示所有技能、包和外部服务。在输出之前，SDA 规范化重复组件，保留关系证据和注释，并根据 SkillBOM 模式验证结果以确保统一表示。

SkillBOM 是基于 SBOM IR [16] 构建的面向技能的表示。它将技能视为一等公民组件，分配基于 UUID 的技能标识符，并记录技能特定的组件类型。其关系模型还捕获面向技能的依赖，如 USES_SERVICE 等外部服务使用关系。由于 SkillBOM 基于 SBOM-IR 构建，它保持与 SPDX [20] 和 CycloneDX [31] 等国际 SBOM 标准的兼容性。因此，SkillBOM 可以导入和导出 SBOM 文档，并复用现有的基于 SBOM 的工具链进行 ASSC 分析。

IV RQ1：分析器评估

RQ1 检验 SDA 是否能作为 ASSC 分析的可信测量工具。我们使用 SKILL-DEP 基准评估 SDA，该基准包含用于元数据和直接依赖恢复的单层基准，以及用于完整技能依赖图构建的多层基准。单层基准测量 SDA 在元数据和直接依赖方面的准确性，而多层基准测量其在构建完整技能依赖图方面的全面性。

IV-A SKILL-DEP 基准构建

单层基准。 单层基准由 500 个技能文档的分层样本构建。每个采样单元是一个根技能文档，每个单元标注两个黄金目标：根技能元数据和该文档中表达的包、技能和服务使用依赖集合。我们在基准构建过程中全程使用开放标注。由于依赖证据稀疏且分布不均，我们按依赖证据类型对样本进行分层，以确保覆盖包依赖证据、技能依赖证据和服务使用证据。

我们在 50 个技能的试点上校准标注指南。两位具有技能使用经验的软件工程研究人员独立提取依赖记录，比较分歧，完善定义，并在全面标注前冻结指南。最终指南定义了依赖包含标准、包/技能/服务依赖之间的边界、目标规范化规则和记录的关系类型。每条记录包含源技能、目标类型、规范化的目标名称、关系类型和证据位置；技能级元数据（如名称、仓库、路径和许可证）在可用时也被记录。

然后，两位研究人员在冻结的指南下独立标注 500 个技能的基准。我们按源技能、目标类型、规范化的目标名称和关系类型对齐提取的记录。在裁定之前，两位标注者分别提取了 1,583 和 1,590 条依赖记录，其中 1,581 条匹配。剩余 11 条争议记录通过共识讨论解决：5 条被保留为有效依赖，6 条被拒绝为非依赖或超出范围的情况（如仅示例性提及）。匹配的记录加上保留的争议记录构成冻结的裁定参考集。

多层基准。 为验证完整依赖图构建，我们采样 100 个技能并应用相同的冻结指南和标注程序。这些技能专注于技能图构建：包含 80 个深度为 3 的图、18 个深度为 4 的图和 2 个深度为 5 的图。我们用它来测试 SDA 的增量构建是否一致地提取多层技能依赖。

IV-B 实验设置

基线。 我们将 SDA 与两类基线进行比较。

第一类是以包为中心的 SBOM 生成器基线。我们从 GitHub 上标记有 sbom 主题的仓库中选择广泛使用的开源工具。我们纳入至少有 2,000 星标且具有显式 SBOM 生成能力的工具：Syft [3]、ScanCode [1]、ORT [30] 和 Microsoft sbom-tool [23]。此外，我们纳入 Cdxgen [32]，这是由 CycloneDX 社区维护的星标最多的 SBOM 生成器，以覆盖在主要 SBOM 标准社区内开发的生成器。

第二类基线是基于 LLM 的提取器，测试仅语义提取是否能恢复依赖记录和元数据。考虑到在运行完整基准时模型能力与评估成本之间的实际平衡，我们使用 DeepSeek-v4-pro，采用固定提示，指示模型作为具有技能使用经验的软件工程研究人员，并仅返回有效的 JSON。提示包含关于提取哪些依赖以及如何格式化输出的指令。我们使用温度 0 以最小化采样方差。

基于 LLM 的基线补充了以包为中心的 SBOM 生成器（后者无法提取技能和服务使用依赖），并为评估 SDA 的类型化分析是否优于基于 LLM 的语义提取器提供了直接比较点。

IV-C2 全面性

在多层基准上，SDA 取得精确率 0.98、召回率 0.93、F1 0.95。由于没有基线支持多层依赖提取，我们直接对照人工标注的基准评估 SDA。结果表明 SDA 的增量 BOM 构建在多层技能依赖图上保持高准确性，证明了其在构建完整技能依赖图方面的全面性。

回答 RQ1： SDA 准确且全面地分析技能元数据和依赖。它在单层基准上取得 0.95 的总体依赖 F1，在三个依赖类别中均优于所有基线，并在所有元数据字段上达到 1.00 的准确率。在多层基准上，它取得 0.95 的 F1，证实了其构建完整依赖图的能力。

V RQ2：ASSC 特征

在本节中，我们从 SkillsMP 注册表构建大规模技能数据集，并应用 SDA 构建 ASSC，从元数据基础设施和依赖图两个视角进行分析。

V-A 技能数据集

我们从 SkillsMP 注册表 [37] 构建技能数据集。SkillsMP 索引了来自 GitHub 的所有公开技能文件，并按关键词、创建者和源仓库进行组织，使其成为大规模技能分析的合适入口。2026 年 6 月 6 日，SkillsMP 列出了 1,640,440 个技能。在捕获当天的注册表快照后，我们检索了每个技能的 GitHub URL 并成功下载了 1,434,046 条 GitHub 支持的记录，覆盖了约 87.4% 的已列技能。其余记录无法获取，因为其 GitHub 链接不可访问、仓库已变为私有，或在爬取时源内容不可用。分析的快照包含仓库/路径元数据和 SHA-256 内容哈希。我们保留这些身份而非去重 0.52% 的哈希相同记录，因为相同的技能文件可能出现在影响下游依赖解析的不同名称或上下文中。

V-B 元数据基础设施

技能携带了足够的前置元数据来支持智能体激活，但远远不足以支持供应链治理。在 1,434,046 个技能中，99.55% 的技能存在前置元数据；name 出现在 99.49% 中，description 出现在 99.52% 中。相比之下，license 仅出现在 11.25% 的技能中，version 仅出现在 20.12% 中。可能携带类似依赖声明的字段（如 dependencies、requires）仅出现在 1.40% 的技能中，而超过 30% 的技能实际携带包、技能或服务使用依赖。

这种对比是结构性的而非偶然的。技能格式为智能体调度而设计：名称和描述告诉智能体何时调用技能。告诉人类审查者或自动化扫描器技能依赖什么的字段很少被标准化。

更糟糕的是，即使存在的元数据字段作为标识符也很脆弱。有效名称（包括从前置元数据 name 或父目录 slug 派生的名称）跨仓库冲突：58.73% 的技能与至少一条其他记录共享其有效名称。在这些冲突名称中，88.76% 跨多个仓库，99.31% 对应不同的内容哈希。这不是相同技能出现在多个位置的良性场景，而是不同技能共享相同或相似名称的更困难情况。描述同样不可靠：25.88% 的技能与至少一条其他记录共享规范化描述，11.57% 的技能前置元数据 name 与其父路径 slug 不同。

没有良好管理和标准化的元数据声明，依赖解析、来源追踪和风险通知都变得相当棘手。社区已经开始讨论这类问题 [7]。当前提案仍限于在技能使用时通过非确定性的基于智能体的推理来填充可能的元数据。这一问题已成为任何技能治理系统必须解决的元数据基础设施的可测量模式。

依赖扩展和隐藏包清单。 我们使用依赖放大因子 [6]，即传递依赖与直接依赖的比率，来衡量根的依赖在递归技能导入后扩展了多少。表 V 显示了高度偏斜的模式。总放大的中位数仅为 0.5，但尾部很大：p99 总体达到 130.5 倍，技能最大 347 倍，包最大 1,754 倍，服务最大 194 倍。

一个典型案例解释了这一机制。windows-95-web-designer 声明没有包依赖且仅有三个技能依赖，但其依赖图导入了 1,754 个包和 1,938 个总组件——645 倍放大。对此和其他高放大根的手动检查显示，这些根通常充当工作流编排器：它们命名几个入口点技能来执行具体功能，而这些技能递归导入各自的依赖。

这种扩展产生了可测量的治理后果：隐藏包清单。在承载依赖的技能中，22.42% 仅通过复用技能获得包，使这些包在根层不可见。一个具体例子是 npm/rimraf：1,495 个根直接声明它，但另有 5,160 个根通过技能复用继承它，这意味着每有一个显式依赖 rimraf 的技能，就有超过四个其他技能在未命名的情况下携带它。

这种隐藏包清单将 ASSC 与软件供应链耦合。在 npm 包暴露中，71.87% 通过技能复用继承而非直接声明；对于 PyPI，这一比例达到 73.33%。因此，ASSC 不形成孤立的供应链岛屿。它位于 npm、PyPI 和其他供应链之上，技能复用充当跨技能边界携带包清单的桥梁。

依赖簇。 上述放大极端并非孤立的异常。它们指向 ASSC 中的一个结构现象：技能依赖簇。技能经常双向引用彼此，形成互依赖簇，概念上更接近 npm 的对等依赖，即包声明彼此兼容。数据证实了这一点。技能依赖图不是树：30.41% 的有依赖根技能包含至少一个循环中的技能，30.03% 有汇聚的下游节点。其中，最具特色的结构是包含至少一个强连通分量的依赖网络，其成员被拉入一个相互引用的簇。当此类簇中的任何技能被安装时，其依赖拉入其他技能，使整个簇成为一个高层捆绑单元。

一个具体示例来自 OpenTideHQ/AgentTide 的 microsoft-defender-endpoint，一个 Defender 高级狩猎技能。根技能将通用检测规则设计委托给 detection-engineering，后者又与 microsoft-sentinel 和 threat-hunting 互链。这些依赖技能执行特定功能并返回相应结果，如平台特定的检测指导和威胁狩猎实践。结果是一个小型依赖簇，其成员必须被理解为一个耦合的工作流单元。

同样的模式在 claude-dev-suite/claude-dev-suite 的 bitcoin-psbt 套件中以更大规模出现，该套件围绕比特币托管知识组织了 140 个相互引用的技能，从时间锁和签名到 Taproot 脚本、钱包描述符和金库保护。

当技能形成这样的依赖簇时，传统治理任务就会失效。孤立地审查或审计单个技能是不够的，因为其依赖和操作面由簇扩展，而非由其自身的 SKILL.md 扩展。修补或移除簇中的一个成员可能需要跨所有成员的协调变更，而任何单个技能中的漏洞或风险指令会传播到依赖该簇任何入口点的每个技能。

回答 RQ2：
(1) 激活就绪但治理薄弱的元数据：99.55% 的技能存在前置元数据，但类似依赖的字段仅出现在 1.40% 中。同时，58.73% 的技能名称冲突，表明元数据基础设施脆弱。
(2) 多通道且集中的依赖图：ASSC 跨越技能、包和服务依赖，暴露 ASSC 的不同部分，而复用集中于一小部分技能和包，规范化基尼系数分别为 0.925 和 0.944。
(3) 依赖扩展和隐藏包清单：递归技能复用扩展依赖图：p99 包放大达到 350 倍，22.42% 的承载依赖技能仅通过复用技能获得包，npm 和 PyPI 的继承包比例分别达到 71.87% 和 73.33%。ASSC 治理必须检查图级别的包暴露。
(4) 依赖簇：技能依赖图包含簇：30.41% 的承载依赖根包含循环。这些结构通常连接描述同一工作流不同部分的技能，使依赖簇成为高层治理单元。

VI RQ3：安全传播

在本节中，我们研究来自技能、包和服务的安全相关信号如何通过 ASSC 依赖图传播。为此，我们通过两种互补方法收集安全相关信号。

  • 来自公开威胁报告的指标
  • 技能：Koi [18]、Snyk [43, 41] 和 Antiy [5] 报告的恶意技能标签；
  • 包：来自已记录供应链攻击的包，包括 Cline [40]、Nx [38] 和 axios [15]；

  • 服务：具有已发布 CVE 或恶意 MCP 服务的 MCP 服务，包括 mcp-remote [14]、postmark-mcp [42]、MCP Inspector [13] 和 figma-developer-mcp [12]。

  • 基于正则表达式的安全模式

  • 技能：从学术论文和公开报告 [21, 39] 中总结的六类技能安全相关信号：远程载荷执行、危险代码模式、提示注入、凭证外泄、持久化和后门命令、以及密钥暴露。
  • 服务：从官方文档和公开报告 [24, 33] 中总结的五类服务安全相关信号：代码仓库和问题跟踪器权限、本地资源和浏览器权限、协作和消息权限、数据后端权限、以及仅机制型 MCP 攻击模式。

两种方法共同识别潜在的安全相关指标。我们扫描技能数据集和所有生成的 SkillBOM，观察这些指标如何通过依赖图传播。然后我们手动确认了如持续存在的 clawhub1 恶意技能和未固定版本的 axios 包等案例。

综合来看，三个通道讲述了同样的故事：脆弱制品可以通过任何通道进入 ASSC，在发现后长期持续存在，并通过依赖图传播到可能不知道自己授权或使用它们的根技能。

回答 RQ3： 安全相关信号通过技能、包和服务进入 ASSC。恶意技能或服务可以通过克隆持续存在，而未固定版本的安装命令使脆弱包保持可达。依赖图放大了这一问题：仅依赖性暴露高达 98.01%，因此根级检查通常会遗漏仅在完整图中可见的暴露。

VII 讨论

VII-A 启示与建议

基于我们对 ASSC 结构特征和安全传播模式的分析，我们概述了改善 ASSC 管理的建议和潜在解决方案。这些建议面向两个目标群体：技能基础设施维护者（如技能包管理器开发者和技能注册表维护者）和技能开发者。

面向技能基础设施维护者。 管理技能的早期基础设施已经存在。Vercel Labs 的 Skills CLI 和 skills.sh 索引等工业工具通过 npx skills 支持安装、更新和移除等技能管理操作 [45, 46]；Skilldex 等研究工具提出了合规性评分和技能注册表 API [35]。然而，现有技能包管理器仍缺乏依赖管理和向用户警告脆弱依赖的系统化机制。因此，我们建议三项改进。

第一，注册表可以要求类型化依赖清单。清单可以区分 skillDependencies、packageDependencies 和 serviceDependencies，而不是将所有引用视为通用的相关技能，并为每个依赖记录元数据（如来源和版本）。

第二，技能包管理器可以将技能依赖簇概念引入依赖管理。npm 在对等依赖方面的经验说明了将簇状关系视为一等依赖管理对象的重要性，以避免 npm 4–6 在弱对等依赖执行下经历的版本治理失败 [25, 26]。这一紧迫性要求在声明和安装两个层面进行治理。在声明层面，依赖清单可以包含 skillDependencyCluster 字段，将同一簇中的相关技能作为共享依赖单元分组，包括特定工作流的可选依赖。在安装层面，技能包管理器可以遵循 npm v7 的自动解析和冲突阻止实践 [26]。当消费者安装技能时，管理器应验证簇兼容性，并在所需簇依赖缺失或不兼容时阻止安装。

第三，技能包管理器可以提供类似于 npm audit [27] 的审计命令。skill audit 可以解析完整的技能依赖图并报告已确认的脆弱依赖，包括受影响版本和证据通道。

面向技能开发者。 开发者可以在技能开发过程中维护类锁文件记录。社区讨论已经表明，当复用的技能依赖未正确保留其来源时，下游用户可能失去重新安装或审计所需的上下文 [44, 9]。因此，每当技能引入另一个依赖时，可以维护一个技能锁文件。它可以记录确切的依赖版本、源仓库、路径和可选状态，以便下游用户或包管理器可以重现依赖图并审计继承的风险。

VII-B 有效性威胁

构念效度。 SDA 仅将确认的依赖边记录为依赖，将低置信度匹配作为注释保留并排除在分析之外。遵循传统软件供应链实践 [19, 2]，我们考虑了运行时需求之外的依赖，包括可选和其他声明的依赖类型，因此在分析中纳入了技能、包和服务使用依赖。RQ3 中的安全相关模式是审计信号而非已确认的漏洞，关键标记案例经过手动检查。

内部效度。 SDA 既是 RQ2 和 RQ3 的制品也是测量工具，因此依赖提取中的不准确可能影响报告的发现。我们通过在独立标注的 SKILL-DEP 基准上评估 SDA、为每条提取的依赖保留支持证据、以及手动检查代表性的标记案例来减轻这一威胁。

外部效度。 我们的研究覆盖了 GitHub 支持的 SkillsMP 技能快照，不包括私有和企业技能。尽管 SKILL-DEP 使用分层抽样构建，其规模可能无法完全代表整个技能语料库的多样性，特别是长尾领域和不常见的依赖模式。此外，技能的快速增长意味着结构模式可能发生变化。

VIII 结论

智能体技能正在成为可复用的软件制品，但其依赖在很大程度上仍然隐含。本文引入了智能体技能供应链（ASSC）作为混合的技能-包-服务依赖图，并提出了 SDA，它从技能重建 ASSC 并输出 SkillBOM。在 SKILL-DEP 基准上的评估表明，SDA 准确且全面地恢复了 ASSC。

我们将 SDA 应用于 143 万个技能，刻画了 ASSC 的结构及其安全模式。我们发现了四种结构模式：ASSC 尽管具备激活就绪性但治理薄弱；ASSC 跨越技能、包和服务依赖且复用集中；递归技能复用创建了依赖扩展和隐藏包清单；技能依赖簇围绕相关工作流形成。

我们还发现，仅检查根技能是不够的，因为安全相关的技能、包和服务即使在下游技能从未直接提及它们时，也能到达下游技能。

这些发现呼吁图感知的 ASSC 治理：面向技能基础设施维护者的类型化依赖清单、依赖簇管理、风险警告审计命令，以及面向技能开发者的类锁文件记录。
